# 실사용자 환경 프레임 드롭 가설 검증

**Status:** Draft (설계 중, 구현 전)
**Date:** 2026-04-08
**선행 문서:** [`perf-bottleneck-hypothesis.md`](./perf-bottleneck-hypothesis.md)

---

## 1. 가정 (Hypothesis)

> not4k의 **실제 사용자 환경**에서 의미 있는 빈도의 프레임 드롭이 발생하며, 그 드롭은 특정 디바이스 클래스·차트·구간에 편중되어 있다.

이 가정이 참이라면, 어떤 사용자가 어떤 조건에서 드롭을 겪는지가 데이터로 드러나고, 그에 맞춘 최적화 우선순위를 정할 수 있다. 거짓이라면 추가 성능 작업의 정당성이 사라진다.

이 문서는 해결책을 정의하지 않는다. **사용자 환경에서 드롭이 실제로 존재하는가, 존재한다면 어디에 편중되는가**를 측정하기 위한 설계 합의 문서다.

---

## 2. 왜 이 가설이 필요한가

선행 문서(`perf-bottleneck-hypothesis.md`)의 결론:
- 데스크탑(Intel i7-11700, Chrome No throttling) 환경: judge+coords ≈ 2~3%, 가정 ❌
- CPU 4× slowdown 환경: judge+coords ≈ 11%, ⚠️
- judge 카테고리가 throttling에 가장 민감(×4.8 ~ ×6.9)

남은 미지의 영역:
- 합성 throttling은 실제 저사양 디바이스의 프록시일 뿐, 동치가 아니다
- 측정은 단 한 사람·한 곡·한 디바이스에서만 이루어졌다
- 사용자 입력은 없었다(오토 플레이)
- 따라서 "실제 사용자가 실제로 드롭을 겪는가"는 여전히 답이 없다

이 공백을 메우는 가장 비용 효율적인 방법은 **사용자 측에서 드롭 이벤트를 자동 수집해 서버로 보내는 것**이다.

---

## 3. 가정이 참 / 거짓일 때

| 결과 | 의미 | 다음 행동 |
|---|---|---|
| ✅ 의미 있는 디바이스 클래스/차트/구간에서 드롭 편중 발견 | 가정 참 | 편중된 영역을 대상으로 최적화 RFC 작성 (대상은 데이터가 결정) |
| ⚠️ 드롭은 발생하나 특정 패턴 없음 | 가정 약함 | 일반적 성능 작업으로 우선순위 낮춤. 데이터 수집은 유지 |
| ❌ 드롭이 거의 발생하지 않음 | 가정 거짓 | 성능 작업 자체를 후순위로. 텔레메트리는 회귀 감시용으로만 유지 |

기준선("의미 있는"의 정의)은 데이터 수집을 시작하기 전에 §6.7에서 합의한다.

---

## 4. 비목표 (Non-Goals)

- 드롭의 **원인을 자동으로 진단**하지 않는다 — 데이터는 사람이 본다
- **실시간 알람**을 만들지 않는다 — 일단 적재만
- 드롭이 발생할 때 사용자에게 **개입하지 않는다** (UI 변경 없음)
- 사용자 행동 분석/마케팅 텔레메트리를 만드는 것이 아니다 — 성능 데이터에 한정

---

## 5. 측정 방법 (개요)

이 섹션은 **무엇을 잴지**만 다룬다. **어떻게 구현할지**(전송 방식, 스토리지, 컨텍스트 항목)는 §6의 미해결 질문에서 결정한다.

### 5.1 무엇을 측정할 것인가
- 곡 1회 플레이 동안의 프레임 드롭 발생 시각·횟수
- 드롭 발생 직전 몇 프레임의 평균 프레임 시간
- 곡·차트 식별자
- 디바이스/브라우저 컨텍스트
- 빌드 식별자(커밋 SHA)

### 5.2 무엇을 측정하지 않을 것인가
- 사용자 식별 정보 (이름, 이메일, 정확한 위치)
- 사용자의 입력 패턴·플레이 스타일
- 화면 캡처
- 게임 외 페이지의 성능

### 5.3 측정 시점
- 게임 화면(`PlayScreen`) 진입~퇴장 사이로 한정
- 곡 종료 시(또는 사용자가 곡을 중단할 때) 1회 batch 전송

### 5.4 측정 도구의 제약
- 측정 코드 자체가 게임 프레임에 영향을 주면 안 된다 → §6.6에서 다룸

## 6. 결정해야 할 것들 (미해결 질문)

이 문서가 다음 단계로 가려면 아래 7개 질문에 답이 필요하다. 답은 사용자(프로덕트 결정권자)와 합의 후 본 문서 §7에 채운다.

### Q1. "드롭"의 정의
- (a) `requestAnimationFrame` 콜백 사이 간격 > 17ms (60Hz 기준)
- (b) `PerformanceObserver({type:'longtask'})` > 50ms task
- (c) Pixi ticker deltaTime > 임계
- (d) 위 조합
- 권장: **(a) + (b)** — (a)는 사용자 체감과 직결, (b)는 원인 추적용
- **임계값 자체**도 정해야 함 (17ms? 33ms? 50ms?)

### Q2. 드롭 1건에 함께 기록할 컨텍스트
필수 후보:
- 발생 시각 (곡 내 위치 ms)
- 직전 N프레임 평균 프레임 시간 (N=?)
- chart_id, song_id, 차트 버전(updated_at)
- 빌드 커밋 SHA

선택적 후보:
- User-Agent (브라우저·OS 식별용)
- `navigator.hardwareConcurrency`
- `navigator.deviceMemory` (Chrome 한정)
- 화면 해상도 / DPR
- 활성 스킨 ID
- 드롭 시점 화면에 보이는 노트 수
- 활성 이벤트 마커 (auto, trill 등)
- 익명 세션 ID (재방문 사용자 그룹화용)

→ **어디까지 수집할 것인가?** 많을수록 분석 가치 ↑, 프라이버시·페이로드 ↓.

### Q3. 전송 빈도와 묶음 단위
- (a) 매 드롭 즉시
- (b) 곡 종료 시 batch 1회 ← 권장
- (c) 일정 시간/개수 도달 시 flush
- 비정상 상황(드롭 100건+)에서는 곡 중간 강제 전송할 것인가?

### Q4. 샘플링과 동의
- 100% 수집 vs N% 샘플링 — not4k 사용자 규모에 따라 결정
- 사용자 동의가 필요한가? 설정 토글을 제공할 것인가?
- 약관·개인정보처리방침 갱신이 필요한가?

### Q5. 전송 대상과 저장소
- (i) Supabase 테이블 `perf_events` 직접 insert (RLS 정책 필요)
- (ii) Supabase Edge Function 경유 (서버 측 검증·필터·rate limit 가능)
- (iii) 외부 SaaS (Sentry·PostHog 등) — 새 의존성·계정·비용
- 권장: **(i) 또는 (ii)** — 기존 인프라 재사용

테이블 스키마 초안 필요 (Q2 답이 정해진 후).

### Q6. 측정 코드의 게임 영향 최소화
- 평상시: `rAF` 간격을 카운터로만 계산, 객체 생성 0
- 드롭 감지 시점에만 컨텍스트 수집
- 전송: `navigator.sendBeacon` 또는 `fetch(..., {keepalive:true})`로 곡 종료 후
- 메모리: 곡당 드롭 이벤트 상한(예: 1000) 두기
- → 위 원칙으로 충분한가, 측정의 관찰자 효과를 한 번 검증해야 하는가?

### Q7. 데이터로 무엇을 결정할 것인가 (가장 중요)
**알람·리뷰 주기 없이 적재만 하면 데이터는 영영 보지 않게 된다.** 사전에 정해야 할 것:

- 어떤 SQL/대시보드를 보면 §3의 ✅/⚠️/❌ 판정을 할 수 있는가?
- 정기 리뷰 주기는? (주 1회? 데이터 모인 후 1회?)
- "의미 있는 빈도"의 정량 기준은?
  - 예: "주간 활성 디바이스의 X% 이상에서 곡당 평균 Y건 이상의 드롭"
  - X, Y의 잠정값을 데이터 수집 시작 전에 정해둔다
- 최소 관찰 기간은? (1주? 2주? 4주?)

## 8. 위험과 완화

| 위험 | 완화 |
|---|---|
| 데이터만 쌓이고 아무도 보지 않음 | Q7에서 알람·리뷰 주기 사전 합의 |

| 새로운 큰 가설 사슬에 빠지는 함정 | 본 문서는 *측정 설계*만, 구현·분석은 별도 단계 |

## 9. 후속 단계 (가정과 무관하게 정해두는 것)

본 문서가 §7까지 채워진 뒤의 작업 흐름:

1. **MVP 구현** — Q1~Q6의 결정대로 최소 코드 작성. 클라이언트 + 서버 테이블/엔드포인트 1개씩.
2. **수집 기간** — Q7에서 정한 최소 관찰 기간 동안 데이터만 적재.
3. **1차 분석** — Q7에서 정한 SQL/대시보드로 §3의 ✅/⚠️/❌ 판정.
4. **결정**:
   - ✅ → 편중된 영역에 대한 최적화 RFC 시작
   - ⚠️ → 본 문서의 미해결 질문 재방문, 가설 재구성
   - ❌ → 텔레메트리는 회귀 감시용으로 유지하되 성능 작업은 후순위로
5. **본 문서 §10에 결과 기록**
