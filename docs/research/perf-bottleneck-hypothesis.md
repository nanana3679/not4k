# 성능 병목 원인 가정 검증

**Status:** Draft (측정 전)
**Date:** 2026-04-08
**관련 문서:** (측정 결과에 따라 후속 RFC 연결 예정)

---

## 1. 가정 (Hypothesis)

> not4k의 게임 플레이 중 **프레임 시간 p99는 판정(judgment)·노트 좌표 계산(coords)이 지배한다.**

이 가정이 참이라면, 해당 두 영역을 더 빠르고 결정적인 실행 환경(예: Rust/WASM)으로 옮기는 것이 의미 있는 개선이 된다. 거짓이라면 동일한 노력은 효과가 거의 없거나 잘못된 방향이다.

이 문서의 목적은 **가정이 맞는지 측정으로 확인**하는 것이다. 해결책(WASM 등)은 이 문서의 범위가 아니다.

---

## 2. 가정이 참일 때 / 거짓일 때

| 결과 | 의미 | 다음 행동 |
|---|---|---|
| ✅ `judge + coords`가 프레임 시간의 **30% 이상**을 차지 | 가정 참 | 계산 영역을 대상으로 한 최적화 RFC 착수 (언어 전환 포함 검토 가능) |
| ⚠️ 차지 비율이 **10~30%** | 가정 약함 | 다른 카테고리와 함께 우선순위 재검토. 단일 해결책 RFC 보류 |
| ❌ 차지 비율이 **10% 미만** | 가정 거짓 | 실제 지배 카테고리(예: pixi.render, react, audio)를 대상으로 별도 조사 시작 |
| ⚪ 어떤 카테고리도 두드러지지 않고 p99가 이미 충분히 낮음 | 문제 없음 | 성능 작업 자체를 후순위로 이동 |

기준선은 측정 후 필요시 조정할 수 있으나, **측정 전에 결정해 둔다** — 결과를 보고 사후에 기준을 옮기지 않기 위함이다.

---

## 3. 측정 방법

### 3.1 카테고리 정의

1프레임 동안 소비된 시간을 다음 카테고리로 분해해 누적한다. 카테고리는 **상호 배타적**이어야 한다.

| 카테고리 | 정의 | 측정 지점 |
|---|---|---|
| `judge` | 입력 1건당 판정 처리 | `JudgmentEngine` 진입~반환 |
| `coords` | 매 프레임 노트 화면 좌표 계산 | `GameNoteRenderer`의 좌표 갱신 루프 |
| `pixi.update` | sprite 속성(위치/알파/텍스처) 갱신 | 좌표 적용 ~ `renderer.render` 직전 |
| `pixi.render` | 실제 draw call | `renderer.render(stage)` 진입~반환 |
| `audio` | AudioEngine 콜백 처리 | `AudioEngine`의 콜백 본문 |
| `etc` | 위에 속하지 않는 모든 시간 | 프레임 시간 − 위 합계 |

> `etc`는 GC, 브라우저 내부, 미계측 함수 등을 모두 포함한다. `etc`가 비정상적으로 크면 측정 누락을 의심해야 한다.

### 3.2 측정 도구

- **계측 API**: `performance.now()` 양끝, `performance.mark` / `measure`
- **수집기**: `src/game/debug/PerfProbe.ts` (신설 예정). dev/preview 빌드에서만 활성, prod 빌드는 no-op로 tree-shake.
- **장기 관찰**: `PerformanceObserver`로 `longtask`, `event`, `frame` 보조 수집
- **출력**: 곡 종료 시 카테고리별 누적 ms, 비율, p50/p95/p99 콘솔 + JSON dump

이 문서 자체에는 측정 코드가 포함되지 않는다. 코드는 별도 PR로 추가하며, 추가 시점에 본 문서의 §4에 결과를 채운다.

### 3.3 측정 시나리오

재현성과 민감도를 동시에 보기 위해 **2×2 매트릭스**로 측정한다.

|  | 일반 속도 | CPU 4× slowdown |
|---|---|---|
| **곡 A** (밀도 중간) | 측정 ① | 측정 ② |
| **곡 B** (밀도 높음 + 트릴) | 측정 ③ | 측정 ④ |

- 곡 A: `chart_id = 7584369c-3802-4387-8382-9dbb574ac80e` (처음부터 끝까지 auto 마커로 덮인 측정용 차트)
- 곡 B: (미정 — 밀도 높고 트릴 포함된 차트로 추후 선정)
- 모드: 오토 플레이 (입력 변동을 제거해 측정 노이즈 감소)
- 빌드: `pnpm build && pnpm preview` (prod 빌드만 사용)
- CPU throttling: Chrome DevTools Performance 패널 → CPU "4× slowdown"
- 반복: 각 칸 5회 → 총 20개 데이터 포인트, 칸별 중앙값 사용
- 환경: 측정 시 실제 사용한 OS/브라우저/CPU를 §4에 기록

**읽는 법**:
- 측정 ①이 ✅이면 가장 강한 증거. 가정 참.
- 측정 ①은 ❌인데 ②에서 ✅로 바뀌면 → "현재 데스크탑은 괜찮지만 저사양에선 병목". 후속 RFC의 타깃이 저사양 사용자임을 명시.
- 측정 ①·② 모두 ❌면 가정 거짓.
- 측정 ①과 ③이 크게 다르면 곡 특성에 의존 → 일반화 불가, 곡을 더 추가해 재측정.

### 3.4 측정하지 않는 것 (이번 라운드)

- 에디터 화면 — 가정의 범위 밖
- 곡 선택 화면, 라우팅, Supabase 통신 — 게임 루프 밖
- React 리렌더 — 게임 화면은 Pixi 캔버스 한 장에 수렴한다고 가정. 만약 `etc`가 비정상적으로 크면 그때 다시 의심한다.
- 사람 입력 — 오토 플레이로 대체. 사람 입력에서는 judge·UI 비용이 더 클 수 있음을 인지하고 §6에 보류 항목으로 기록.
- 멀티 브라우저 — 1차는 1종 고정. 다른 브라우저에서 결과가 뒤집힐 위험은 §6에 명시.
- 실제 모바일·저사양 디바이스 — CPU throttling으로 일부 대체. 완전 대체는 아님.

## 4. 결과

### 4.1 측정 환경
- OS / 브라우저 / CPU: Windows / Chrome 146.0.7680.165 / Intel Core i7-11700 @ 2.50GHz
- 빌드: `pnpm build && pnpm preview` (prod)
- 측정 일자: 2026-04-08
- 곡: `chart_id = 7584369c-3802-4387-8382-9dbb574ac80e` (전곡 auto 마커)
- 측정 도구: Chrome DevTools Performance 패널 (수동 녹화)
- 곡 B는 측정하지 못함 — 곡 A 결과만으로도 판정이 가능하여 1차 라운드는 곡 A로 종결.

### 4.2 카테고리별 Self Time 비율 (Bottom-Up 기준)

| 카테고리 | 측정 ① No throttling | 측정 ② CPU 4× | 변화 배수 | 비고 |
|---|---|---|---|---|
| `judge.update` (`JudgmentEngine.update`) | 1.0% | 6.9% | ×6.9 | not4k 코드 중 throttling에 가장 민감 |
| `judge.checkLongNoteBodyHold` | 0.7% | 1.9% | ×2.7 | |
| `judge.checkLongNoteBodyEnd` | 0.5% | 1.8% | ×3.6 | |
| **judge 합계** | **~2.2%** | **~10.6%** | ×4.8 | §2의 30% 기준 미달 |
| `coords` (≈ `renderFrame` 일부) | <1% | ~0.7% | — | 분리 측정 불가, 보수적 추정 |
| `pixi._tick` | 8.3% | 18.8% | ×2.3 | Pixi 내부 |
| WebGL (`clear`/`tex*`/`bufferSubData` 등) | ~1.5% | ~3.5% | — | |
| 브라우저 (`rAF` + 커밋 + 사전 페인트) | ~14% | ~29% | — | |
| `gameLoop` (PlayScreen.tsx) | 2.7% | 8.7% | ×3.2 | |
| GC (C++ + 기타) | ~1.4% | ~1.0% | — | |
| react-dom wrapper "함수 호출" | 47.7% | 19.5% | ×0.4 ↓ | **측정 인공물로 판단** — §4.4 참조 |

### 4.3 핵심 지표

| 지표 | 측정 ① | 측정 ② |
|---|---|---|
| Long Task (>50ms) 발생 수 | 미수집 | 미수집 |
| 프레임 드롭률 | 미수집 | 미수집 |

> 1차 라운드는 카테고리 비율만으로도 판정이 가능했기에 정량 지표는 수집하지 않았다. 후속 라운드(실 사용자 텔레메트리)에서 다룬다.

### 4.4 관찰 메모

- **측정 ①의 "함수 호출 47.7%"는 측정 인공물이다.** 동일 항목이 측정 ②에서 19.5%로 줄어들었고, 그 자리를 사용자 코드 항목들(`_tick`, `gameLoop`, `JudgmentEngine.update`)이 정상적인 비율로 채웠다. 이는 측정 ①에서 사용자 코드의 절대 시간이 너무 짧아 wrapper의 self time 비중이 부풀려졌음을 시사한다. → §6 Q5의 답: 관찰자 효과는 실재했고, 단일 측정의 비율을 곧이곧대로 믿어선 안 된다.
- **judge 카테고리는 throttling에 가장 민감하게 반응했다** (×4.8 ~ ×6.9). 다른 어떤 카테고리보다 큰 증가율이다. 이는 "저사양 사용자 환경에서는 judge 비중이 비례 이상으로 커질 수 있다"는 별도 가설의 근거가 된다.
- **coords 카테고리는 두 환경 모두에서 1% 미만으로, 사실상 비병목**이다. WASM 이식의 명분 중 하나였던 "노트 좌표 계산 가속"은 본 측정 데이터로는 정당화되지 않는다.
- 곡 B는 측정하지 못했다. 곡 A 결과의 방향성이 명확하여 1차 라운드는 종결한다.

## 5. 결론

- **가정 판정**: ❌ (데스크탑 일반 환경) / ⚠️ (CPU 4× slowdown 환경)
- **근거**:
  - 측정 ① judge + coords ≈ **2~3%** → §2의 ❌ 기준(10% 미만)
  - 측정 ② judge + coords ≈ **11~12%** → §2의 ⚠️ 기준(10~30%, 하단)
  - 두 환경 모두 §2의 ✅ 기준(30% 이상)을 충족하지 못함
- **다음 행동**:
  1. **WASM 전환 RFC 초안은 폐기한다.** 본 측정 데이터는 RFC를 정당화하지 못한다. 옮길 수 있는 가장 큰 덩어리(judge + coords)가 데스크탑 ~3%, 4× ~11%이며, 이를 0으로 만들어도 사용자 체감 개선은 미미하고 Rust/WASM 도입 비용을 회수하지 못한다. 네이티브 앱(ASIO exclusive mode)으로의 전환 역시 검토하였으나, not4k는 히트 사운드가 없어 오디오 절대 지연이 캘리브레이션 오프셋으로 완전 흡수되므로, 브라우저 WASAPI shared mode의 수십 ms 불리가 체감 문제를 만들지 않는다. **웹 단일 트랙을 확정한다.**(2026-04-11)
  2. 측정 ②에서 **judge 카테고리가 throttling에 비례 이상으로 민감하게 반응**한 사실은 별도의 조사 가치가 있다. 단, 합성 throttling은 실제 사용자 환경의 프록시일 뿐이므로 실증이 필요하다.
  3. 위 검증은 **실제 사용자 환경의 텔레메트리**로 수행한다 → 후속 가설 문서로 분리한다: `docs/research/realworld-frame-drops-hypothesis.md` (예정).
- **부산물**:
  - 측정 ①의 react-dom wrapper "함수 호출 47.7%"는 측정 인공물이었다. 본 프로젝트에서 향후 DevTools Performance 데이터를 해석할 때 단일 환경의 비율을 단독 근거로 삼지 말 것.

## 6. 미해결 질문

1. 곡 B는 어떤 차트로 고정할 것인가 (밀도 높음 + 트릴 포함). chart_id 필요.
2. 측정 도구가 미정이다 — 후보: (a) Chrome DevTools Performance 수동 녹화 (b) 코드에 작은 계측 헬퍼 신설. 1차는 (a)로 충분할 수 있음.
3. `etc`가 큰 비율을 차지할 경우, 한 번 더 분해할 가치가 있는가? (GC, 미계측 함수, react 리렌더 재의심 등)
4. 가정이 ✅로 나와도 그게 **데스크탑 1종 + 오토 플레이**에 한정된 결론일 위험. 사람 플레이·저사양·타 브라우저로의 일반화는 어느 시점에서 다룰 것인가.
5. 측정 자체의 관찰자 효과 — `performance.now()` 호출 비용, DevTools 녹화 중 프레임 시간 증가가 결과를 왜곡할 가능성. 한 번 검증할 가치가 있는가.
6. 차트가 추후 재업로드되어 노트가 바뀌면 측정 ①과 후속 측정의 비교가 무효화됨. 차트 버전을 고정하는 메커니즘이 있는가?
