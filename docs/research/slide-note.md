# 슬라이드 노트 리서치 리포트

> 시작점 이후 궤적/경로를 따라가는 "슬라이드 노트"의 기존 리듬게임 사례를 정리하고, not4k의 현재 구현이 어느 계열에 속하는지 분석한다.

---

## 1. 용어와 분류 축

**슬라이드 노트**: 시작점을 잡은 뒤, 흘러오는 경로(궤적/영역)를 따라 입력 지점을 옮겨 가며 유지하는 노트의 총칭. 게임마다 명칭이 다르다(슬라이드, 슬라이더, Slide Note 등).

사례를 가르는 핵심 축은 **"손을 실제로 움직여야 하는가"** 이다.

- **모션 요구형**: 경로 위에 입력이 있어도 *움직이지 않으면* 판정을 주지 않는다. 슬라이드의 본질을 "공간 이동 동작"으로 본다.
- **존재 확인형**: 경로(또는 체크포인트 시점) 위에 입력이 *존재하기만* 하면 최고 판정을 준다. 타이밍/이동 정밀도를 거의 요구하지 않는다.

모바일 대중화·접근성 방향으로 갈수록 모션 요구형 → 존재 확인형으로 완화되는 경향이 있다.

---

## 2. 기존 리듬게임의 사례

### 2.1. 뱅드림! 걸즈 밴드 파티 (가루파) — スライドノーツ "슬라이드 노트"

- **입력**: 롱노트의 응용. 시작점을 탭하고 누른 채, 흘러오는 **녹색 라인**에 손가락을 맞춰 횡이동한다.
- **판정 구조**: 시작점·끝점에 더해 중간 **중계점(中継点)**(녹색 라인 부분)마다 판정이 성립한다. 중계점에서 손이 멈춰 있거나 이동이 너무 느리면 콤보가 끊긴다.
- **분류**: **모션 요구형**.
- **특이사항**: 끝에서 튕기는 **플릭(フリック)** 노트가 별도로 존재한다. EXPERT의 지그재그 긴 슬라이드는 "○" 표시 지점만 잡고 있어도 콤보가 이어지는 완화 규칙이 있다.

### 2.2. 프로젝트 세카이 (프로세카) — スライドノーツ "슬라이드 노트"

- **입력**: 시작점에 손가락을 올린 뒤 경로를 따라간다.
- **판정 구조**: 중간 경로는 타이밍 판정이 거의 없고, **경로 위에 손가락이 있기만 하면 최고 판정**을 부여한다. 시작/끝점은 PERFECT ±41.7ms(모바일 표준 윈도우).
- **분류**: **존재 확인형**.
- **특이사항**: 끝에 플릭이 결합된 슬라이드 변형이 흔하다. (저장소 내 정리: `auto-best-judgment-note.md` 2.3, `judgment-windows.md` 5.1)

### 2.3. 츄니즘 (CHUNITHM) — スライド "슬라이드"

- **입력**: 파란 반투명 영역이 좌우로 이동하므로, 슬라이더를 홀드하며 손을 따라 움직인다.
- **판정 구조**: **"슬라이드 판정"** — 잡고만 있고 손이 움직이지 않으면 슬라이드를 안 한 것으로 보고 MISS를 줄 수 있다. 콤보 가산 간격은 BPM<120 → 16분, 120~240 → 8분, 240+ → 4분. **가시중간점(파란 오브제)**은 계속 눌러야 한다.
- **분류**: **모션 요구형**.
- **예외**: 시작점·끝점이 겹치거나, 경사가 급하거나, 홀드 위에 있는 경우 등은 슬라이드 판정이 면제된다. 아케이드의 **면적 입력 슬라이더** 하드웨어에 의존한다(저장소 `chunithm.md`, `../context/rationale.md`에 "PC 이식 불가"로 언급).

### 2.4. 디모 (DEEMO) — Slide Note

- **입력**: 노란 몸체 노트. 판정선에 닿을 때 손가락으로 **쓸어야(slide/swipe)** 한다. 가만히 두면 인식되지 않으며, 모션으로만 hit 처리된다. 탭도 가능하지만 빠른 곡은 슬라이드가 유리하다.
- **판정 구조**: Charming(판정선 근접) / Normal / Miss. 곡 속도가 빠를수록 거리 허용치가 넓어진다.
- **분류**: **모션 요구형** (원작 기준).
- **특이사항**: 후속작 **DEEMO II에서는 단순화** — 슬라이드가 오는 자리에 손가락을 가만히 둬도 처리되고, 판정도 Charming/Miss(100%/0%)로 이분화되어 **존재 확인형으로 전환**되었다.

## 4. not4k의 현재 구현

not4k의 슬라이드 노트는 **"길이 0 hold-only" 노트**로 구현되어 있다(`../rfd/0005-hold-only-long-note.md`).

- **판정**: 노트 시점 ±Good 윈도우 동안 해당 레인이 held이면 Perfect를 부여한다(Perfect/Miss 이분법). 즉 **그 시점에 손가락이 눌려 있기만 하면 통과하는 체크포인트**이다.
- **분류**: **존재 확인형** — 프로세카·디모 II 계열에 해당한다. 4키 키보드에는 "면적/궤적 이동"이라는 물리적 슬라이드가 없으므로, 모션 요구형(뱅드림·츄니즘·디모 원작)을 그대로 이식할 수 없고 "그 시점의 held 존재"로 번역한 결과다.
- **참조 구현**: `../../src/game/judgment/JudgmentEngine.ts`의 `checkLengthZeroHoldOnly` / `checkSlideReleaseOnRelease`, `../spec/note-system.md`(길이 0 = 슬라이드 노트형).

---

## 5. 시사점

1. "슬라이드 = 가만히 있으면 안 되고 손이 움직여야 한다"가 원형(뱅드림·츄니즘·디모 원작)이며, 접근성 방향으로 갈수록(프로세카·디모 II) "경로 위 존재만 확인"으로 완화된다.
2. not4k는 키보드 환경의 제약상 **존재 확인형**을 채택했고, 이는 입력 매칭 인프라를 재사용하며 모션 추적 없이 구현 가능하다는 실용적 이점이 있다.
3. 향후 "이동 동작"의 쾌감을 도입하고 싶다면, 키보드에서는 *레인 간 입력 지점 이동*(예: 인접 레인 순차 입력)으로 모션 요구형을 근사할 수 있으나, 이는 별도 RFD 대상이다.
