## 현재 결론

- 같은 확정 시각·같은 대표 등급에서는 타이밍 표시가 허용된 실제 입력을 우선한다. 여러 개면 절대 오차가 큰 입력의 FAST/SLOW를 사용하며, 유지 성공의 타이밍 정보를 새로 만들지 않는다(§104).

- 유지 노트 성공에도 해당 레인에 일반 노트와 같은 타격 이펙트를 표시한다. 기존 스킨·효과 설정을 따르며 미확정 상태·종속 0점에는 성공 이펙트를 만들지 않는다(§103).

- 같은 확정 시각에 여러 등급이 나오면 가장 낮은 등급을 대표 판정 글자로 표시한다. 마지막 처리 결과로 덮어쓰지 않으며, 각 항목의 점수·콤보·고도 정산은 기존 계약을 유지한다(§102).

- 유지 노트도 성공 확정 시 Perfect 판정 글자를 표시한다. 타이밍 오차·FAST/SLOW는 추가하지 않고, 미확정 대기나 종속 0점에는 새 성공·실패 글자를 만들지 않는다(§101).

- 해당 바디의 시작 Point를 실제로 처리한 재누름의 같은 키 재사용 예외를 싱글 바디에 붙은 더블 릴리즈에도 적용한다. 아무 재누름·다른 Point·double 유지 두 몫의 같은 키 충족으로 확대하지 않는다(§100).

- 앞 바디를 정상 유지한 채 이미 누른 키가 이어져 있으면 뒤 바디는 자기 차트상 시작 시각에 시작한다. 짧은 뒤 바디의 Point 미처리를 이유로 건강한 승계를 미시작으로 바꾸지 않는다. 기존 미리 누름 규칙의 재확인이다(§99).

- 바디와 릴리즈의 개수 차이는 금지하지 않으며 명시 수량을 자동 보정하지 않는다. 싱글 바디 끝의 더블 릴리즈를 금지하는 제안은 채택하지 않았다. 사용자가 든 2→1 감소 예시는 바디 2·싱글 릴리즈 1이며, 이를 감소 지점의 더블 릴리즈 허용으로 확대한 질문은 철회했다(§97·§98).

- 우클릭 드래그 도중 Esc를 누르면 그 드래그의 삭제만 복구하고 취소한다. 드래그 전의 편집은 유지하며, 취소된 조작의 새 Undo 기록은 만들지 않는다(§96).

- 우클릭 드래그의 연속 삭제는 한 드래그 전체를 Undo 한 번으로 복구한다. 별개의 드래그는 별도 기록으로 두며 다른 편집의 전역 병합 정책은 이번 결정으로 바꾸지 않는다(§95).

- 새 에디터는 의미 위반이 남은 항목도 선택 해제·선택 변경을 허용한다. 기존 RFD 0017 §3-5의 위반 항목 선택 해제 제한은 없애고, 위반 표시·저장·플레이 검증은 유지한다(§94).

- 길이 0 바디+릴리즈도 단독 릴리즈와 시각적으로 구별하기 어려우므로 금지한다. 단독 릴리즈와 양수 길이 바디 끝+릴리즈는 허용을 유지한다(§93).

- 길이 0 바디와 같은 위치의 Point 조합은 시각적으로 표현할 수 없어 기존 금지를 유지한다. 바디 무점수·릴리즈 분리만으로 허용하는 제안은 채택하지 않는다(§92).

- 우클릭 드래그에서 개별 노트를 지워 드러난 바디는 같은 드래그 동안 보호한다. 그 바디까지 지우려면 버튼을 뗀 뒤 새로 우클릭해야 한다(§91).

- 선택된 바디를 우클릭하면 클릭한 바디와 그 바디의 연결 항목 중 선택에 남은 것만 삭제한다. 다른 선택 항목과 제외한 릴리즈는 남기고, 유지 표식 제외로 바디 삭제가 불가능한 경우에는 기존 삭제 차단을 적용한다(§90).

- 미선택 바디를 우클릭·삭제 모드로 직접 지우면 같은 시작점 Point·소속 유지 표식·끝점 릴리즈를 함께 삭제한다. 개별 노트 직접 삭제는 해당 노트만 대상으로 한다(§89).

- 미선택 바디의 끝 핸들을 바로 잡아 리사이즈할 때도 바디 클릭과 같이 연결 항목을 함께 선택한다. 이미 선택된 바디의 선택 집합과 개별 제외는 유지한다(§88).

- 구형 노트라는 이유로 별도 배지·라벨·강조·빗금은 추가하지 않는다. 구형 노트 자체의 표시·편집과 내부 의미 구별, 실제 배치 위반의 기존 표시는 유지한다(§87).

- 과도기에는 구형·신형 혼합 차트의 저장·재불러오기를 허용해 사람이 일부만 고친 상태에서도 수리를 이어갈 수 있게 한다. 구형 항목의 존재 자체는 저장을 막지 않으며 인게임 재생만 막는다. 실제 배치 위반의 저장 제한은 유지한다(§86).

- 실패한 바디는 실패색으로 스크롤되어 화면 밖까지 남긴다. 더블의 일부 실패는 실패한 쪽에만 실패색을 적용한다(§81).

- 더블 바디는 한쪽 몫만 정상 완료하면 전체 alpha 0.7로 남기고, 두 몫 모두 정상 완료하면 숨긴다. 릴리즈 성공 수와 바디 완료 상태를 혼동하지 않는다(§80).

- 정상 완료된 바디는 이른 종료·연결 여부와 관계없이 완료 확정 시 즉시 숨긴다. 명시 릴리즈의 별도 표시·판정 대기는 보존한다(§79).

- 유지 표식은 성공 확정 시 즉시 숨긴다. 더블은 성공한 쪽만 숨기고 남은 쪽의 위치·크기·밝기를 유지한다. 바디 탈락으로 종속 0점이 확정된 미래 표식도 즉시 실패색으로 바꾼다(§74～76).

- 더블 릴리즈의 한쪽 실패·다른 쪽 성공은 부분 실패 도안 전체 alpha 0.7로 남긴다. Grace 릴리즈의 전체 흰 외곽은 일부·전체 실패를 포함해 본체가 보이는 동안 원래 밝기로 유지하고 본체가 사라질 때 함께 숨긴다(§77～78).

- 실패가 확정된 릴리즈는 실패색으로 바꾸고 차트 스크롤에 따라 화면 밖으로 나갈 때까지 남긴다. 바디 실패로 입력 기회를 잃은 릴리즈도 포함하며, 유예·미확정 상태를 먼저 실패 표시하지 않는다. 당시 남겼던 더블 혼합 합성과 유지 노트 표시는 후속 §74～78을 따른다(2026-10-25 사용자 확인, §70).

- 새 모델에는 별도의 바디 끝 마감 에셋을 두지 않는다. 릴리즈 없는 끝은 바디만 끝나고 명시된 릴리즈가 있을 때 그 노트가 J2-C 그림을 담당한다. 바디 끝 마감과 릴리즈를 이중으로 그리지 않는다. 시작 마감으로 뒤집어 쓰던 표현도 사용하지 않는다(2026-10-25 사용자 확인, §68·§69).

- Grace 더블 릴리즈의 한 몫 성공·나머지 대기에는 본체 전체 alpha 0.7을 적용하고 전체 Grace 외곽은 원래 밝기를 유지한다. 두 몫 모두 성공하면 본체와 외곽을 함께 숨긴다. 실패가 포함된 표시 수명·혼합 합성·외곽 수명은 후속 §70·§77·§78의 확정 규칙을 따른다(§67).

- 더블 릴리즈에서 한 몫이 성공하고 나머지 입력을 기다리는 일부 성공은 정상 도안 전체 alpha 0.7로 표시한다. 사용자가 50%에서 70%로 바꾼 것이 의도된 변경임을 확인했다. §64의 반쪽 숨김과 §65의 50% 후보를 대체한다. 일부 실패는 해당 절반의 실패색, 일부 성공은 전체 alpha 0.7로 별도 합성하고, 유지 노트는 성공한 표식만 숨기는 예외를 적용한다(§66·§77·§82).

- 유지 노트 성공도 일반 Perfect와 같은 고도 계산 입력으로 전달한다. 명시된 표식의 수가 회복 기회에도 영향을 주며 표식 없는 바디에는 자동 회복을 추가하지 않는다. 종속 0점의 추가 고도 손실 금지와 `flightRule`별 후속 규칙 설계는 유지한다(2026-10-25 사용자 확인, §63).

- 유지 노트 성공은 표식 하나당 Perfect 3점·이론 가중치 3과 콤보 +1로 처리한다. 표식 없는 바디 유지·종료에는 자동 콤보를 만들지 않으며 실패에 종속된 유지 노트의 0점 정산도 추가 콤보 이벤트를 만들지 않는다. 성공 콤보의 공통 확정 순서와 같은 묶음의 Miss 우선 규칙은 유지한다(2026-10-25 사용자 확인, §62).

- 구형 차트는 새 에디터에서 열어 사람이 수정할 수 있게 한다. 읽기 파서·편집 호환은 유지하고, 사람 대신 새 노트 배치를 결정하는 자동 처리·일괄 수정은 제외한다. 위반 배치도 수정용으로 불러오며 저장·플레이 전에 검증하고, 수정 후 새 형식의 저장 왕복을 지원한다(§60·§61, 2026-10-25 사용자 재확인).

- 트릴 바디에는 유지 노트를 놓지 않는다. 별도의 트릴 유지 노트를 도입하지 않으며 트릴 바디·교대·릴리즈 규칙까지 바꾸지 않는다(2026-10-24 사용자 확인, §58).

- single Point가 붙은 double에서 Point를 놓쳐도 다른 한 몫은 자기 시작 조건을 충족하면 시작한다. 창 전부터 누른 키 하나로는 차트상 시작 시각에 시작하며 Point Miss 확정까지 기다리지 않는다. Point가 맡는 몫만 실패에 종속시키고 앞 바디나 이미 탈락한 몫을 복구하지 않는다(2026-10-24 사용자 확인, §54).

- single Point가 붙은 double→double 경계에서도 뒤 double의 두 몫 모두 자기 조건으로 새로 시작할 수 있다. 앞 double의 전체 탈락을 뒤 한 몫의 시작 금지로 이어받지 않는다. Point 하나의 판정으로 두 몫이 자동 충족되는 것은 아니며 기존 hold 수·몫별 시작 조건을 유지한다(2026-10-24 사용자 확인, §53).

- Point·릴리즈 없는 2→1 감소 지점의 유지 노트는 뒤 single을 확인하는 표식 하나로 둔다. 건강한 몫이 이어지면 뒤 single의 상태에 따라 판정하고 두 몫이 모두 탈락했으면 표식도 종속 0점으로 정산한다. 표식이 새 시작이나 탈락 복구를 허용하지 않는다(2026-10-24 사용자 확인, §52).

- 1→2 증가 지점에 놓는 유지 노트는 뒤 double의 두 몫을 확인하는 표식 두 개로 둔다. 앞 single의 탈락을 이 표식에 복사하지 않고 뒤 double의 시작·유지·몫별 상태를 따른다. 같은 위치의 Point·릴리즈 중첩 금지는 유지한다(2026-10-24 사용자 확인, §51).

- Point 없는 double→double 경계에 릴리즈가 하나만 있어도 뒤 double 전체의 새 시작을 허용한다. 앞 두 몫이 모두 탈락했어도 뒤 두 몫은 각각 자기 시작 조건을 따른다. 앞의 확정 탈락·릴리즈 종속 0점은 유지하며 릴리즈 수를 뒤 바디의 새 시작 가능 몫 수로 쓰지 않는다(2026-10-24 사용자 확인, §50).

- Point 없이 릴리즈만 놓인 single→single 경계는 앞 single의 탈락과 별개로 뒤 single의 새 시작을 허용한다. 앞 릴리즈의 종속 0점은 유지하고 뒤 바디는 자기 시작 조건을 따른다. 릴리즈의 up과 뒤 바디의 hold를 함께 요구하는 배치이며, 새 down이나 두 입력의 정확한 동시성을 추가로 강제하지 않는다(2026-10-24 사용자 확인과 기존 입력 계약의 적용, §49).

- Point 없는 2→1 감소에서 두 몫이 모두 이미 탈락했다면 뒤 single도 탈락을 유지한다. 감소 위치의 재누름으로 뒤 single을 새로 살리지 못한다. 한 몫만 탈락했다면 건강한 몫을 뒤 single로 이어주는 기존 결정은 유지한다(2026-10-24 사용자 확인, §48).

- Point·릴리즈 없이 1→2로 증가하는 경계에서도 앞 single 탈락과 별개로 뒤 double 전체를 새로 시작할 수 있다. 뒤 double의 두 몫은 각각 자기 시작 조건을 충족해야 하며, 앞의 확정 탈락·종속 0점은 되돌리지 않는다. 같은 hold 수의 단순 연결과 구별하고 유지 표식 유무로 이 새 시작 허용을 바꾸지 않는다(2026-10-24 사용자 재확인, §47).

- 같은 hold 수의 1→1·2→2 연결점에는 유지 노트를 놓지 않는다(§57). §45의 유지 노트 연결 허용 전제를 대체하며 §55의 경계 표식 정산 질문도 배치 금지로 종료한다. 표식 없는 같은 hold 수의 Point·릴리즈 없는 연결은 §46대로 탈락을 공유하되 정상 상태의 실제 경계·분리 연주·시작과 끝 창은 보존한다. 한 바디 내부와 독립 길이 0 바디의 유지 표식은 허용하고, 1→2·2→1 경계의 표식은 §51·§52대로 뒤 바디를 따른다(2026-10-24 사용자 확인).

- 유지 노트에 제작자가 정하는 별도 소속 설정이나 소속 ID 저장을 요구한다는 전제는 두지 않는다. 기존 `trillZone` 편집처럼 위치에서 관계를 찾을 수 있다. 바디의 판정 상태를 참조하는 관계와 명시적인 소속 속성을 구별하며, 앞뒤 소속 선택을 묻던 에이전트의 접근은 재검토한다(2026-10-24 사용자 질문, §43). 경계의 판정·정산 규칙은 이 구별만으로 자동 확정하지 않는다.

- 독립적인 길이 0 바디와 유지 표식도 일반 선택 규칙을 따른다. 표식 클릭은 표식만, 바디 클릭은 바디와 표식을 함께 선택하고 실제 선택 집합으로 이동·복사·삭제한다. 표식만 삭제하면 길이 0 바디를 남기며 빈 바디도 유효하다. §42의 무조건 동반·빈 바디 자동 삭제는 후속 에디터 결정으로 대체했다(현재 계약(`orchestration-20261025/contract-draft.md#관계는-위치에서-도출`)).

- 바디가 없는 빈 위치에 유지 표식을 새로 찍으면 같은 위치의 길이 0 싱글 바디와 표식 1개를 함께 생성한다. 배치 상태에서 같은 길이 0 싱글 유지 노트를 다시 누르면 바디와 표식을 더블로 바꾸고, 이미 더블이면 그대로 둔다. 단순 이동·붙여넣기에는 바디를 임의 생성하지 않는다(§41·§85).

- 유지 노트는 타임라인의 표식 자체를 직접 선택·이동·삭제하는 방식으로 편집한다(§39). 바디 선택 시 소속 표식을 함께 선택하지만 개별 제외를 허용하며, 이동·복사·삭제는 실제 선택 집합을 따른다. 유지 표식이 삭제 집합에 빠진 바디 삭제와 표식을 밖으로 내보내는 축소는 막는다. 다른 바디로 옮긴 표식의 수는 새 바디의 hold 수에 맞춰 자동 변경한다(§40·§84 및 후속 에디터 계약(`orchestration-20261025/contract-draft.md#후속-에디터-논의에서-확정한-규칙`)).

- 유지 노트를 허용하는 1→2·2→1 경계에서는 뒤 바디를 기준으로 정산한다. 증가 위치에는 두 표식, 감소 위치에는 한 표식을 둔다(§51·§52). 같은 hold 수 연결점은 §57에 따라 금지한다. 한 바디 내부 표식은 바디 경계를 만들지 않으며 제작자의 명시적 소속 ID를 요구하지 않는다.

- 같은 레인·같은 시각에는 서로 다른 노트 의미를 겹쳐 놓지 않는다. Point+릴리즈, Point+유지 노트, 릴리즈+유지 노트를 모두 금지한다. 같은 의미의 수량을 나타내는 더블과 바디 위의 노트 배치는 기존 허용을 유지한다(2026-10-24 사용자 확인, §37).

- 유지 노트는 바디와 같은 판정에 명시적 점수 정산만 더한다. 입력을 별도로 소비하거나 별도의 시작·유지·실패 조건을 만들지 않는다. 같은 down으로 Point 판정과 바디·유지 노트 조건을 함께 충족할 수 있다(2026-10-24 사용자 확인, §36).

- 유지 노트 자체의 허용 창과 창 안 down에 의한 미래 표식 선판정은 없다(§56이 §35의 독립 창을 대체). 정상 유지 중이면 표식 시각에 Perfect로 정산한다. 바디의 최초 시작 판정·유지 유예 중이면 결과를 기다리고 유효한 늦은 시작·회복은 성공, 확정 실패는 종속 0점으로 처리한다. 유효한 이른 정상 종료에서는 해당 종료의 남은 표식을 함께 Perfect로 정산한다. 길이 0에도 바디 자체의 시작 허용을 적용한다. 이미 성공한 표식을 되돌리지 않으며 §32의 Good 예외도 복원하지 않는다.
- Point가 붙은 double에서 Point가 맡지 않는 몫까지 시작 직후 재충전 기회를 넓히는 제안은 채택하지 않는다. 한 번 시작한 몫이 끊겼을 때는 기존 유지 유예를 적용한다. 아직 시작하지 않은 몫의 최초 시작 창을 없애거나, Point 없는 시작의 재충전 규칙까지 철회하는 결정은 아니다(2026-10-24 사용자 거절, §25).
- 릴리즈 없는 짧은 double 바디도 서로 다른 두 물리 키로 처리한다. 시작·끝 창이 겹치더라도 같은 키를 두 번 눌러 두 몫을 완료할 수 없다. 두 키의 입력 시각이 같을 필요는 없으며, 각 몫의 시작·종료 자격은 기존 합의를 따른다(2026-10-24 사용자 확인, §24).
- 바디가 시작 down을 소비한다는 추가안은 **전체 철회**했다. RFD 0032 §2-1의 hold 수 기반 시작·유지와 Point의 down 소비를 유지한다.
- 옛 연결 head 주변의 up을 점수 없이 자동 소비하는 연결 release 처리는 제거한다. up은 명시된 릴리즈의 자격·우선순위에 따라 배정하며, Point 탭이나 교대에서 생겼다는 이유로 별도 소비하지 않는다. 릴리즈 창 안의 적격 up이 뒤 릴리즈를 일찍 처리할 수 있다는 대가를 포함해 사용자가 동의했다(2026-10-24, §18).
- 이미 눌린 키도 바디의 시작·유지에 참여한다. 모든 바디에 새 down을 요구하지 않는다. 시작 허용 창이 열릴 때 이미 눌려 있던 키로는 창 시작에 바디를 미리 시작하지 않고, 차트상 바디 시작 시각에 필요한 hold 수가 충족되면 시작한다(2026-10-24 사용자 확인).
- head 없는 독립 single·double에서 새 down으로 바디를 시작하는 시점은 시작 창 안이어야 한다. 그 시각의 hold 수로 충족하는 몫을 시작하며 down은 소비하지 않는다. 짧은 바디라도 끝 창 안이라는 이유만으로 시작 창 밖의 down을 즉시 시작으로 인정하지 않는다. 끝 창을 시작 허용 범위로 추가하는 안은 사용자의 최종 정정에 따라 철회했다. 이미 누른 키의 hold 참여와 차트상 시작 시각의 자동 시작은 유지한다(2026-10-24, §16).
- head 없는 1→2에서 추가되는 몫에도 같은 시작 시각 규칙을 적용한다. 기존 몫을 정상 유지하면서 증가 지점의 시작 창 안에 새로 눌러 hold 수 2를 충족하면 추가 몫은 그때 시작한다. 두 키를 창이 열리기 전부터 계속 누르고 있었다면 차트상 증가 시각에 추가 몫이 시작한다. 실제 시작한 추가 몫은 자기 끝의 허용 창 안에서 일찍 종료할 수 있다(2026-10-24 사용자 확인, §20).
- 이어진 바디를 앞 바디 종료와 뒤 바디 시작으로 나누어 읽는 연주도 허용한다. 1→2를 기존 몫의 연장과 추가 몫만으로 제한해, 앞 single 실패 뒤 새 한 몫만 키 하나로 시작하도록 하려던 에이전트 제안은 채택하지 않는다. 뒤 double을 별개로 시작하는 연주는 뒤 바디의 두 몫을 자기 시작 창에서 채우는 것으로 대조한다. 앞 바디의 실패를 취소하는 것과 뒤 바디의 새 시작은 구별한다(2026-10-24 사용자 정정, §21). 이어진 경계의 시작 자격은 §22의 후속 정정을 따른다.
- 바디를 시작하려는 누름이 같은 레인의 뒤 Point를 의도치 않게 처리하는 배치는 차트 제작 지침으로 피한다. Point 후보를 엔진에서 숨기거나 바디가 down을 선점하는 예외를 만들지 않는다.
- 앞 바디 끝과 뒤 바디 시작이 맞닿아도 뒤 바디의 시작은 유효하다는 §22의 결정을 보존하되, 이를 모든 연결에서 앞 탈락 뒤에도 뒤 바디만 새로 살릴 수 있다는 규칙으로 적용하지 않는다. 같은 hold 수의 Point·릴리즈 없는 단순 연결은 §46에 따라 탈락을 공유하고 연결점의 유지 노트는 §57에 따라 금지한다. 실제 경계를 합치거나 정상 상태의 시작·끝 창을 삭제하지 않으며 바디의 입력 미소비도 유지한다.
- 같은 레인·같은 시각의 Point와 릴리즈 동시 배치는 허용하지 않는다. 사용자는 시각적 정보가 너무 복잡해지는 것을 이유로 명시했다(2026-10-24, §23). 바디 끝과 릴리즈의 조합은 계속 허용한다. 기존 차트에서 누름과 끝 릴리즈가 겹치면 새 모델 이행 시 충돌로 다루며 한쪽을 자동 삭제하거나 생략하지 않는다.
- 실제 바디 끝의 이른 뗌 허용 창은 일반 릴리즈와 같은 이른 허용 폭을 사용하며, 릴리즈 없는 바디의 종료는 up을 소비하지 않는다. 바디 자체는 점수 항목이 아니다.
- 릴리즈 없는 바디의 이른 종료는 **바디가 이미 시작한 상태**를 전제로 한다. 시작 허용 창 안의 누름으로 일찍 시작한 바디도 끝 허용 창 안에서 일찍 뗄 수 있다. 에이전트가 제안한 “시작 전이어도 끝 창의 up만으로 종료”로 확대하지 않는다(2026-10-24 사용자 정정). 아직 시작하지 않은 상태의 up을 곧바로 실패로 확정한다는 뜻도 아니다.
- 바디에 연결된 릴리즈도 해당 바디 몫이 실제로 시작한 상태여야 판정할 수 있다. 시작 전에는 끝 창 안의 up만으로 릴리즈를 처리하거나 바디를 완료하지 않는다. 기존 RFD 0032 §2-3의 미시작 종료 규칙은 새 모델에 적용하지 않는다. 실제 시작했어도 유지 실패로 기회를 잃은 몫은 제외하며, 정상 완료 후 릴리즈 창이 남은 경우에는 기회를 유지한다(2026-10-24 사용자 정정, §17).
- 끝까지 정상 유지한 바디는 차트상 끝 시각에 무점수로 완료하고, 연결된 릴리즈만 자기 판정 창 끝까지 기다린다. 늦은 허용 창 안의 up은 릴리즈를 판정하며, 끝내 떼지 않으면 릴리즈만 Miss로 처리한다. 이미 완료한 바디에 유지 실패를 추가하지 않는다. 앞서 유지 실패한 바디의 릴리즈 기회 소멸은 유지한다(2026-10-24 사용자 확인).
- double 바디 끝에 같은 종류의 릴리즈 두 몫이 연결된 경우, 바디 한 몫의 유지 실패는 그 몫의 릴리즈 기회 하나만 없앤다. 정상 유지한 나머지 몫의 릴리즈는 판정할 수 있으며, hold 수를 다시 채워도 실패한 몫의 기회는 돌아오지 않는다. 사용자는 이 결론에 동의하며 더블 릴리즈의 일부 실패 에셋도 필요하다고 요청했다(2026-10-24). 한 몫 실패·한 몫 판정 가능 상태를 표시할 에셋을 계획에 포함한다.
- double 바디 끝에 릴리즈 한 몫만 두는 조합을 허용한다. 바디는 두 키의 유지를 요구하지만 끝의 릴리즈는 실제 뗌 한 번만 요구한다. 다른 한 키는 끝 이후 계속 눌러도 뗌 누락으로 실패하지 않는다. 바디 한 몫만 유지 실패하면 실패 효과는 반영하되 정상 유지한 몫으로 릴리즈 기회 하나를 보존한다. 두 몫 모두 유지 실패하면 릴리즈 기회가 사라지고 재누름으로 복구하지 않는다(2026-10-24 사용자 확인).
- 같은 더블 릴리즈의 두 몫은 모두 일반 또는 모두 Grace로 통일한다. 일반 한 몫과 Grace 한 몫을 섞지 않는다(2026-10-24 사용자 확인).
- 2→1 감소는 double의 두 몫을 서로 다른 끝 시각에 나누어 끝내는 구조다. 감소 전에 한 몫이 이미 실패했다면 건강한 몫을 뒤 single로 이어주고, 실패한 몫에 감소 지점의 명시된 릴리즈를 귀속시켜 기회를 닫는다. 해당 릴리즈는 추가 Miss 없이 원래 가중치의 0점으로 한 번만 정산한다. 사용자는 "2 1 감소는 2의 릴리즈를 두번에 나눠 하는거야"라고 근거를 설명했다(2026-10-24, §19). 릴리즈가 없는 끝에 입력 요구를 자동 생성한다는 뜻은 아니다.
- Grace 릴리즈의 최대 허용 창은 일반 릴리즈와 이른 쪽·늦은 쪽 폭을 각각 같게 둔다. 유효 입력은 창 안에서 항상 Perfect이며 FAST/SLOW를 집계하지 않는다. 후속 합의로 일반 릴리즈의 각 등급은 앞뒤 대칭으로 두며, Grace의 최대 허용 창도 대칭이다. 구체적인 ms 수치는 미정이다(2026-10-24 사용자 확인).
- 일반 릴리즈의 Perfect·Great·Good 창은 누름의 해당 등급 창과 같게 둔다. 연결 release 제거 뒤 확대 결정을 철회했다(2026-10-24 사용자 확인, §34). Grace의 최대 허용 창과 릴리즈 없는 바디의 이른 종료 폭도 기존 공유 관계에 따라 누름 Good 폭을 사용한다.
- 일반 릴리즈의 Perfect·Great·Good 판정 창은 각각 이른 쪽과 늦은 쪽의 폭을 같게 둔다. 같은 크기의 타이밍 오차는 이르든 늦든 같은 등급을 받는다. 일반 릴리즈의 이른 최대 폭을 공유하는 릴리즈 없는 바디에는 늦은 뗌 요구를 추가하지 않는다(2026-10-24 사용자 확인).

제작 지침과 철회 근거는 저장소 `docs/context/chart-design.md` 10항과 `docs/rfd/0032-body-held-count.md` §9-5에 기록했다. 관련 컨텍스트 요약은 `src/editor/CONTEXT.md`에 동기화했다. 이 로컬 초안의 구간·시각에 관한 나머지 합의는 공식 문서 반영 전이며, 잔여 결정 추적은 기존 PRD §12의 바디 전환·입력 매칭·릴리즈 이행 항목을 따른다.

## 배경과 논의 이력

RFD 0032 §2-1은 head 없는 바디가 down을 별도로 소비하지 않고, down은 Point가 소비하며, 미리 누른 키로도 hold 수를 충족할 수 있다고 정했다. 수리 코어도 이 전제를 따른다. RFD 0035는 바디와 릴리즈를 분리하고 `holdOnly`를 폐지했으므로, 옛 상태 완료 점수와 경계를 새 모델에 그대로 옮길 수 없다.

### 1. 짧은 독립 바디의 시작 down 소비를 추가로 검토

2026-10-23에는 릴리즈 없는 바디 1000～1060ms, 뒤 Point 1020ms, A down 900ms·up 950ms를 논의했다. 설명용 시작·끝 허용 폭은 120ms이며 최종 수치가 아니다.

사용자는 다음과 같이 설명했다.

> 900down에서 body가 down을 안끌어오면 1020에 노트있으면 그게 받으니까 down을 소비해야되지 그럼 900down에서 바디를 끌어오기(미리시작) 되고 바디가 시작됐으니까 미리 뗄수도 있는데 그게 1060으로부터 윈도우 안에 있기만 하면되지

당시에는 바디가 900ms down을 소비해 일찍 시작하고, 이미 시작한 바디는 끝 허용 창 안의 950ms up으로 종료할 수 있다고 기록했다. 에이전트가 처음 추천한 “차트상 시작 전이라면 실패”는 채택하지 않았다. 이어 미리 누른 키로도 시작하는 기존 규칙을 유지하자는 질문에 사용자는 “ㅇㅇ”라고 답했다.

**현재 처리:** 위 설명 중 바디의 down 소비는 4항에서 전체 철회했다. 뒤 Point가 입력을 받지 못한다는 당시 기대값을 새 회귀 기준으로 쓰지 않는다. 이미 시작한 바디의 이른 종료와, 실제로 언제 시작한 것으로 보는지는 소비 여부와 구분한다.

### 2. 옛 연결 사례에 같은 규칙을 적용하려다 잘못된 경계를 발견

옛 RFD 0032 §1-1의 사례는 N1 바디 1000～1500ms, N2 바디 1500～1560ms, N3 head 1560ms, N4 바디 1560～1760ms에 A 1000～1430ms, D 1490～1760ms를 입력한다. 에이전트는 N1·N2에는 릴리즈를 두지 않고 N4 끝에 명시적 릴리즈를 둔다고 설명하면서도, 옛 N1/N2 경계는 그대로 남겼다.

“N2가 D down을 소비하고 N3에는 별도 누름이 필요하다”는 질문에 사용자는 “ㅇㅇ”라고 답했다(2026-10-24). 이어 사용자가 “근데 holdonly 가 이제 없는데”라고 지적했다. 에이전트가 새 모델의 차트 구조를 먼저 확인하지 않고 옛 경계를 가져온 것이 잘못이었다.

당시 같은 레인·같은 hold 수의 릴리즈 없는 접점은 하나의 연속 구간으로 보자는 후속 질문에 사용자는 “ㅇㅇ”라고 답했다. 에이전트는 접점의 시작·끝 창을 없애는 것으로 정리했다. **이 경계 제거 해석은 §22의 후속 정정으로 철회한다.** 바디의 down 소비 추가안은 별도로 전체 철회했으므로, 경계가 유지되어도 "N2가 down을 소비해 N3가 받지 못한다"는 기대값은 되살리지 않는다. 새 바디 표현과 입력 자격으로 사례를 다시 대조한다.

### 3. 구형 엔진 그림은 새 모델 합의용으로 사용하지 않음

기존 작업트리 `09b72f8e`의 해당 연결 사례 출력은 `Perfect 2 · Great 1 · Good 0 · Miss 1 · 달성률 88.89% · Full Combo 아님 · 미정산 0`이었다. N3가 D down으로 Great를 받고 N2는 시작 실패한다. 그림은 `../case-images/body-start-connection-conflict-old-reference.png`에 과거 구현 기록으로 보존한다.

현재 `case:image` 입력 모델은 독립 릴리즈 노트와 무점수 바디를 직접 표현하지 못한다. `holdOnly`가 표시되는 구형 그림을 새 모델의 합의용 그림으로 다시 제시하지 않는다. 새 표현의 배치·기대 결과와 실제 엔진 출력은 구분해야 한다.

### 4. 시작 down 소비 추가안 전체 철회와 제작 지침 채택

사용자는 2026-10-24에 다음과 같이 요청했다.

> 철회하고 바디시작 이후에 노트를 놔서 바디를 먼저 눌렀을때 포인트가 굳이 나오게 배치하면 안되겠네 차트 제작 지침

“철회 대상은 ‘바디가 시작 down을 소비한다’는 규칙 전체인가요?”라는 범위 확인에 사용자는 **“전체 철회”**라고 답했다. 앞선 연결 사례만 철회하는 것이 아니라 독립 바디를 포함한 시작 down 소비 추가안을 모두 철회한다.

바디의 hold 수 기반 시작·유지와 Point의 down 소비는 유지한다. 바디를 시작하는 자연스러운 누름과 뒤 Point의 판정 창이 간섭하는 배치를 제작·플레이테스트 단계에서 피한다. 바디 시작 정박뿐 아니라 허용되는 이른·늦은 입력을 대조하며, 같은 레인의 홀드 중 탭 전체를 금지하거나 고정된 박 간격을 새 규칙으로 만들지 않는다.

### 5. 미리 누른 키의 시작 시각

에이전트는 head 없는 독립 single 바디에서 시작 허용 창 안에 hold 수가 처음 충족되는 순간을 시작으로 삼고, 창이 열릴 때 이미 눌린 키도 그때 시작시키자고 제안했다. 사용자는 다음과 같이 정정했다(2026-10-24).

> 미리 누르고 있으면 창 시작이 아니라 실제 시작 지점에서 시작

창이 열릴 때 이미 눌린 키가 있다는 이유만으로 조기 시작시키자는 제안은 채택하지 않는다. 이 경우에는 차트상 바디 시작 시각에서 hold 수를 확인해 시작한다. 이 답만으로 창 안에서 새로 누른 입력의 조기 시작 시점까지 확정하지 않았으며, 그 후속 확인은 아래 6항에 기록한다. 시작 down 미소비와 Point의 down 소비는 유지한다.

### 6. 창 안에서 새로 누르면 그 순간부터 시작

“창 안에서 새로 누르면 그 순간부터 미리 시작하는 것으로 둘까요?”라는 질문에 사용자는 “ㅇㅇ”라고 답했다(2026-10-24). 논의 대상은 head 없는 독립 single 바디이다.

- 창 안에서 새로 누른 입력으로 필요한 hold 수를 채우면 그 입력 시각에 시작한다. 차트상 시작보다 이르면 실제 이른 시작이다.
- 바디는 down을 소비하지 않는다. 같은 down을 Point가 처리하더라도 실제 hold가 바디에 참여할 수 있다.
- 미리 눌러둔 키의 차트상 시작과 구분한다. double의 일부 몫·연결·hold 수 변화 경계까지 이 답으로 일반화하지 않는다.
- 기존 RFD 0032 §2-3의 “head 없는 시작은 down을 소비하지 않으므로 창 안의 down도 바디를 미리 시작시키지 않는다”는 설명과 시작 시각이 달라진다. 공식 문서 반영 때는 입력 소비와 실제 시작 전이를 분리해 이 설명·관련 사례를 함께 갱신해야 한다. down 미소비를 철회한 것은 아니다.

### 7. 이른 뗌은 바디가 이미 시작한 상태를 전제로 함

에이전트는 미리 누른 키가 짧은 바디의 차트상 시작 전에 떼어지는 경우를 들어, 아직 시작하지 않은 바디도 끝 허용 창 안의 up으로 종료시키자고 추천했다. 사용자는 다음과 같이 답했다(2026-10-24).

> 키를 미리 눌러서 바디가 시작했으면 미리 뗄수있음

확인한 조건은 **이미 시작한 바디 → 끝 허용 창 안의 뗌 → 이른 종료**다. 차트상 시작 전이라도 창 안의 새 누름으로 이미 시작했다면 이 조건을 충족한다. “미리 누름”이라는 표현만으로 항상 바디가 시작했다고 보거나, 시작하지 않은 바디를 종료시켜도 된다는 승인으로 확대하지 않는다. 에이전트의 미시작 종료 추가안은 채택하지 않는다.

이 질문은 릴리즈 없는 독립 single 바디를 대상으로 했다. 별도 릴리즈 노트의 자격·실패 종속까지 한꺼번에 바꾸지 않으며, 미시작 상태의 up 자체를 즉시 Miss로 만드는 결정도 아니다. 정상 종료의 무점수·up 미소비와 실패한 바디의 복구 금지는 유지한다.

### 8. 정상 유지 완료와 릴리즈 대기의 분리

“바디 유지는 차트상 끝 시각에 완료하고, 릴리즈만 자기 판정 창 끝까지 기다림”이라는 추천에 사용자는 “ㅇㅇ”라고 답했다(2026-10-24).

- 끝까지 정상 유지한 바디는 차트상 끝 시각에 완료한다. 바디 완료 자체에 점수는 없다.
- 연결된 릴리즈가 아직 미판정이면 릴리즈의 늦은 허용 창 끝까지 실제 up을 기다린다. 바디가 완료됐다는 이유로 릴리즈 기회를 닫지 않는다.
- 유효한 up이 없으면 릴리즈만 Miss로 처리하며, 완료된 바디에 별도 유지 실패를 추가하지 않는다.
- 이미 유지 실패한 바디의 릴리즈 기회가 사라진다는 RFD 0035 규칙은 바꾸지 않는다. 정상 완료와 실패를 구분한다.

### 9. double 일부 실패의 릴리즈 귀속과 표시

double 바디 끝에 같은 종류의 릴리즈 두 몫이 연결된 경우, 한 몫의 유지 실패로 연결된 릴리즈 하나만 기회를 잃고 정상 유지한 나머지 몫은 계속 판정할 수 있다는 추천에 사용자는 다음과 같이 답했다(2026-10-24).

> ㅇㅇ 그럼 더블 릴리즈 일부실패 에셋도 필요하네

실패한 몫의 릴리즈는 RFD 0035에 따라 0점·원래 가중치로 한 번만 정산하며, 추가 끝 Miss·고도 손실·콤보 이벤트를 만들지 않는다. 이후 hold 수를 다시 채워도 실패한 몫을 복구하지 않는다. 이 답으로 종류가 서로 다른 릴리즈의 귀속, double 바디에 릴리즈 한 몫만 연결한 경우, 연결·감소 경계의 귀속까지 확정하지 않는다.

표시에는 더블 릴리즈의 **한 몫 실패·한 몫 판정 가능** 상태를 표현하는 에셋이 필요하다. 실패한 몫과 남은 입력 요구를 구별할 수 있어야 한다. 기존 스킨의 `terminalDoublePartialFailedLeft/Right`와 바디 부분 실패 표시는 참고 자료다. 별도 릴리즈의 디자인·에셋 재사용 여부나 표시 좌우와 물리 키의 대응까지 승인한 것은 아니다. 구체적인 시안과 상태 전환은 표시 단계에서 검토하며, 잔여 결정 추적은 PRD §12를 따른다.

### 10. double 바디 끝의 릴리즈 한 몫 허용

두 키를 유지하는 double 바디 끝에 릴리즈 하나만 두어 끝에서는 한 번만 떼도록 만드는 조합을 허용하자는 추천에 사용자는 “ㅇㅇ”라고 답했다(2026-10-24).

바디의 요구 hold 수와 끝의 릴리즈 요구 수가 같아야 한다는 제약을 두지 않는다. 이 조합은 정상 유지에 두 키가 필요하고, 끝에는 명시된 릴리즈 하나의 뗌만 필요하다. 나머지 키를 끝 이후에도 유지할 수 있다. 명시하지 않은 두 번째 릴리즈나 점수 항목을 자동 생성하지 않는다.

이 답은 배치와 입력 요구 수를 확정했다. 당시 바디 한 몫이 유지 실패했을 때 유일한 릴리즈의 기회를 보존할지는 후속 논의로 남겼으며, 그 결론은 아래 11항에 기록한다.

### 11. double 바디에 릴리즈 한 몫이 있을 때의 일부 유지 실패

한 몫만 실패하면 유지 실패를 반영하면서 정상 유지한 나머지 몫으로 릴리즈 하나의 기회를 보존하고, 두 몫 모두 실패하면 기회가 사라진다는 추천에 사용자는 “ㅇㅇ”라고 답했다(2026-10-24).

- 한 몫만 유지 실패한 상태에서는 릴리즈 하나가 계속 판정 가능하다. 실패한 바디 몫의 실패 효과를 지우거나 그 몫을 복구하는 것은 아니다.
- 두 몫 모두 유지 실패하면 아직 판정하지 않은 릴리즈의 기회가 사라진다. 다시 누르고 떼어도 복구하지 않는다.
- 기회가 사라진 릴리즈는 RFD 0035에 따라 0점·원래 가중치로 한 번 정산하며, 별도 끝 Miss·고도 손실·콤보 이벤트를 더하지 않는다.
- 바디 몫과 물리 키를 고정 연결하지 않는 기존 RFD 0032 §2-1을 유지한다. 새 키도 정상 유지한 몫의 유지와 릴리즈에 참여할 수 있으며, 실패한 몫에 고정 배정하지 않는다.

이 결정은 끝 릴리즈 한 몫의 기회 보존 범위이다. 서로 다른 종류의 릴리즈나 연결·감소 경계의 귀속을 자동 확정하지 않는다. 잔여 결정 추적은 PRD §12를 따른다.

### 12. 더블 릴리즈 안의 일반·Grace 종류 통일

같은 더블 릴리즈의 두 몫을 모두 일반 또는 모두 Grace로 통일하자는 추천에 사용자는 “ㅇㅇ”라고 답했다(2026-10-24).

한 더블 릴리즈 안에서 일반 한 몫과 Grace 한 몫을 섞는 구성은 허용하지 않는다. 따라서 그 혼합에서 입력을 어느 종류에 배정할지, 일부 유지 실패 시 어느 종류의 기회를 잃을지에 관한 규칙을 추가하지 않는다. 부분 실패 후 남은 릴리즈는 원래 더블 릴리즈의 종류를 유지한다.

이 결정은 같은 더블 릴리즈 내부의 종류에 관한 것이다. 서로 다른 시각에 배치한 별도 릴리즈의 종류까지 통일하거나 일반·Grace의 판정 창 수치를 확정하는 결정은 아니다.

### 13. 일반·Grace 릴리즈의 최대 허용 창 공유

### 14. 일반 릴리즈의 세 등급 판정 폭 완화

### 15. 릴리즈의 등급별 판정 창은 앞뒤 대칭

일반 릴리즈의 각 등급에서 이른 뗌과 늦은 뗌의 폭을 같게 두자는 추천에 사용자는 “ㅇㅇ”라고 답했다(2026-10-24).

릴리즈 없는 바디의 이른 종료에는 이 대칭 창의 이른 최대 폭만 사용한다. 계속 유지해도 되는 바디 끝에 늦은 up 요구나 누락 Miss를 새로 만들지 않는다. 구체적인 ms 수치와 세 등급의 확대 비율은 여전히 미정이며 PRD §12의 떼는 판정 창 항목을 따른다.

### 16. double의 시작과 짧은 바디의 끝 창 안 down

head 없는 독립 double 바디에서도 시작 창 안의 새 down이 들어오면 그 순간 hold 수로 충족하는 몫들을 시작하자는 추천에 사용자는 “ㅇㅋ”라고 답했다. 당시 제안은 한 키를 미리 누른 상태에서 창 안에 다른 키를 누르면 두 몫 모두 그때 시작하고, 두 키를 창이 열리기 전부터 계속 누르고만 있었다면 차트상 시작 시각에 시작하는 것이었다.

이어 사용자는 다음과 같이 시작 허용 범위의 문제를 지적했다(2026-10-24).

> 근데 이런 조건 보다는 길이가 짧아서 종료지점 윈도우안에서 다운 하면 시작 해야할거 같은데 안그러면 짧은 더블 바디 입력할때 약간 빨리누르면 입력 안될듯

에이전트는 바디 시작 창에 누름 노트의 좁은 판정 폭을, 끝 창에 넓힌 릴리즈 폭을 임의로 대입해 끝 창이 먼저 열릴 수 있다고 설명했다. 이어 두 창의 개방 시각 중 더 이른 쪽부터 시작을 받고 늦은 기한은 유지하자고 제안했다. 사용자는 다음과 같이 정정했다.

> 무조건 시작 창이 먼저 열리잖아

에이전트는 이 반박에 창의 개방 순서 설명까지 철회한다고 답했다. 이후 사용자는 다음과 같이 정리했다.

> 아니구나 끝 창을 완화하기로 했지 근데 그래도 누름은 시작 창 안에서 해야지

**현재 결론은 새 down으로 시작하려면 시작 창 안이어야 한다는 것이다.** 끝 창이 열려 있다는 이유로 시작 창 밖의 새 down을 즉시 시작으로 인정하는 안과, 시작 기한을 끝 창까지 확장하려던 검토는 철회한다. 이미 누른 키는 실제 hold 수에 남으며 기존 합의대로 차트상 시작 시각에 참여할 수 있다. 바디의 down 미소비·실패한 몫의 복구 금지도 유지한다.

**개방 순서와 입력 자격을 구분한다.** 시작을 `S`, 끝을 `E`, 시작 창의 이른 폭을 `P`, 끝 창의 이른 폭을 `R`이라 하면 끝 창이 먼저 열리는 조건은 `E-R < S-P`, 즉 `E-S < R-P`다. 끝 창 완화로 이 조건이 성립할 수 있다는 설명 자체는 조건부로 맞다. 에이전트의 잘못은 그 사실에서 down의 시작 자격 확대를 바로 도출한 것과, 반박을 받자 산술을 확인하지 않고 개방 순서 설명까지 뒤집은 것이다. 시작은 시작 창으로 판단한다는 최종 결정은 어느 창이 먼저 열리는지와 독립적이다. 이 식은 구간 산술이며 새 엔진의 실행 결과가 아니다.

에이전트는 기존 RFD 0032 §2-3의 미시작 종료 규칙을 들어 시작 창 조건을 우회할 수 있다고 설명하고 변경 여부를 물었다. 사용자는 아래 §17과 같이 바디 활성화가 이미 전제라고 정정했다. 이 문제를 미결정으로 남기거나 옛 규칙을 새 모델에 이식하지 않는다.

### 17. 바디에 연결된 릴리즈는 실제 시작이 전제

### 18. 연결 release의 up 자동 소비 제거

당시 에이전트는 같은 hold 수의 릴리즈 없는 접점을 연속 바디로 합치는 전제로, 옛 연결 head 주변 up 하나를 점수 없이 소비하던 예외를 남길지 논의했다. Point는 down을 처리하고 명시된 릴리즈만 up을 소비하도록 하자는 추천에 사용자는 "ㅇㅇ"라고 답했다(2026-10-24). 바디 경계를 없애는 전제는 §22에서 철회하지만, 명시된 릴리즈만 up을 소비한다는 결론은 유지한다.

사용자는 이전 `o-o-`의 중간에서 릴리즈 때문에 콤보가 두 번 늘어나던 동작을 직관적이지 않게 느꼈으며, 새 모델은 더 직관적이고 규칙도 간단해졌다고 설명했다. 새 모델에서 중간에 Point만 명시하고 릴리즈를 두지 않으면 그 Point의 성공으로만 콤보가 1 늘고, 연속 바디 자체는 콤보를 올리지 않는다. 이는 바디 무점수·명시된 누름과 릴리즈만 점수 항목을 만드는 결정의 효과다. 점수가 없던 옛 연결 up 소비의 제거와 콤보 항목의 변경은 구별한다.

### 19. 2→1 감소의 일부 실패와 릴리즈 귀속

감소 전에 double의 한 몫이 이미 실패한 경우, 건강한 몫은 뒤 single로 이어주고 실패한 몫이 감소 지점에서 끝나며 그곳의 명시된 릴리즈 기회를 닫자는 제안에 사용자가 동의했다. 사용자는 이유를 다음과 같이 설명했다(2026-10-24).

> ㅇㅇ 왜냐면 2 1 감소는 2의 릴리즈를 두번에 나눠 하는거야

2→1 감소는 double의 두 몫이 서로 다른 시각에 끝나는 구조다. 한 몫은 감소 지점에서 끝나고 다른 몫은 single 구간으로 이어져 그 뒤의 끝에서 끝난다. 일부 실패 시 건강한 몫을 뒤 구간에 이어주며, 감소 지점의 명시된 릴리즈는 실패한 몫에 종속되어 기회를 잃는다. 실패 때 해당 릴리즈를 0점·원래 가중치로 한 번만 정산하고 끝에서 추가 Miss·고도 손실·콤보 이벤트를 만들지 않는다. 이미 실패한 몫은 재누름으로 되살리지 않는다.

이는 double 전체가 같은 시각에 끝나고 릴리즈를 하나만 명시한 구성에서 건강한 몫으로 그 릴리즈 기회를 보존하는 결정과 구분한다. 2→1에서는 건강한 몫이 뒤 바디로 이어진다. 몫은 고정 물리 키를 뜻하지 않으며, 릴리즈를 두지 않은 끝에는 별도 뗌 요구나 점수 항목을 자동 생성하지 않는다.

head 없는 1→2에서 추가되는 몫에도 독립 바디와 같은 시작 시각 규칙을 적용하자는 제안에 사용자는 "응"이라고 답했다(2026-10-24).

기존 한 몫을 정상 유지하는 상황에서 증가 지점의 시작 창 안에 새 down으로 hold 수 2를 충족하면 추가 몫은 그 입력 시각에 시작한다. 추가 키까지 창이 열리기 전부터 계속 눌려 있었다면 창이 열리는 순간이 아니라 차트상 증가 시각에 추가 몫이 시작한다. 추가 몫이 실제로 시작한 뒤에는 자기 끝의 허용 창 안에서 일찍 종료할 수 있다. 끝 창만으로 시작 범위를 확장하거나 시작 전에 릴리즈를 허용하지 않는다.

이 답은 추가 몫의 활성화 시각을 정한다. 기존 몫의 재충전 유예나 head가 있는 증가의 전체 계약을 함께 변경하는 것으로 해석하지 않는다. 증가 전에 기존 몫이 이미 실패한 경우의 새 시작 범위도 이 답만으로 확정하지 않는다. 해당 적용 범위의 추적은 PRD §12의 바디 전환 항목을 따른다.

### 21. 이어진 바디를 나누어 읽는 연주

에이전트는 기존 single이 이미 실패한 뒤 1→2가 되면 기존 몫의 실패를 그대로 이어가고 추가 몫 하나만 키 하나로 시작하게 하자고 제안했다. 사용자는 다음과 같이 정정했다(2026-10-24).

> 이어져있어도 서로 끊어져 있는걸로 읽는것도 허용하거든

연결을 기존 몫의 연장으로만 해석해서는 안 된다. 앞 바디를 끝내고 뒤 바디를 따로 시작하는 연주도 허용한다. 이는 기존 RFD 0032 §8-2에서 앞 바디를 끝 창 안에서 끝내고 뒤 바디의 모든 몫을 자기 시작 창에서 채우는 연주를 인정한 전제와 일치한다. 에이전트의 "추가 몫 하나만 새로 시작" 제안은 채택하지 않는다.

이번 1→2 문맥에서의 도출은 앞 single의 실패가 뒤 double 전체의 새 시작 기회를 막지 않는다는 것이다. 뒤 double을 따로 시작하려면 그 바디의 두 몫을 채워야 하며, 앞 single이 실패했다는 이유로 뒤 double의 요구를 한 몫으로 낮추지 않는다. 앞 바디의 확정 실패와 그 바디에 종속되어 이미 닫힌 릴리즈 기회를 되돌리는 것은 아니다. 이어받아 유지하는 연주와 별개로 시작하는 연주를 모두 대조해야 한다.

에이전트는 이어서 분리 지점을 Point나 hold 수 변화가 있는 곳으로 제한하자고 제안했으나, 사용자는 §22와 같이 이어진 경계 자체도 바디 시작이라고 정정했다. 이 제한안은 채택하지 않는다.

### 22. 이어진 경계 자체가 바디 시작

후속 §45·§46에서 유지 노트만 놓인 연결과 같은 hold 수의 표식 없는 단순 연결은 탈락을 공유한다고 확인했다. 아래 시작 허용을 이 연결의 탈락 뒤 복구까지 허용하는 규칙으로 읽지 않는다. 정상 상태의 경계 연주와 확정 탈락 뒤 복구 가능 여부를 구별한다.

에이전트는 Point나 hold 수 변화처럼 구분할 수 있는 지점에서만 분리해서 치는 것을 허용하자고 제안했다. 사용자는 다음과 같이 정정했다(2026-10-24).

> 포인트는 당연하고 이어진 경계도 바디 시작인데

앞 바디의 끝과 뒤 바디의 시작이 맞닿아 있다는 이유로 뒤 바디의 시작이 없어지지 않는다. Point가 있는 시작은 물론 head 없는 연결 시작에도 뒤 바디의 시작 창이 있다. Point·릴리즈 유무나 hold 수 변화 여부를 시작 자격의 추가 조건으로 붙이지 않는다. 따라서 같은 hold 수의 릴리즈 없는 접점을 합쳐 시작·끝 창을 없애는 앞선 정리와, Point가 있어야 분리해서 읽을 수 있다는 제한안은 철회한다.

이어 누르는 연주와 앞 바디를 끝내고 뒤 바디를 따로 시작하는 연주를 모두 허용한다. 뒤 바디는 자기 시작 창에서 필요한 hold 수를 채울 기회를 가지며, 앞 바디의 확정 실패를 취소하는 것으로 취급하지 않는다. 한 바디 중간의 임의 위치를 새 시작으로 만들거나 실패한 같은 바디를 되살리는 규칙은 아니다. 바디 경계의 존재와 입력 소비는 구별하므로, 시작 down 미소비·릴리즈 없는 끝의 up 미소비·명시된 릴리즈만 up 소비는 유지한다.

저장·컴파일 단계에서 실제 바디 경계를 합쳐 없애지 않아야 한다. 경계의 표시와 편집 표현은 이 판정 의미를 보존하도록 설계한다. 기존 RFD 0032 §8-2의 앞 끝·뒤 시작 창과 재충전 규칙을 새 릴리즈 표현에 맞춰 대조한다.

### 23. 같은 위치의 Point와 릴리즈 동시 배치 금지

에이전트는 같은 레인·같은 시각에 Point와 릴리즈를 함께 명시하고 각각 판정하는 조합을 허용하자고 추천했다. 사용자는 다음과 같이 거절했다(2026-10-24).

> 불가, 시각적 정보가 너무 복잡함

같은 레인·같은 시각의 Point와 릴리즈 동시 배치를 금지한다. 판단 근거는 입력 가능 여부가 아니라 화면에서 읽어야 하는 정보의 복잡성이다. Point와 릴리즈가 겹치는 조합의 허용안은 채택하지 않는다. 바디 끝과 릴리즈의 조합을 허용한 RFD 0035의 결정은 유지한다.

이 금지는 같은 배치 위치에 적용한다. 서로 다른 시각 노트의 판정 창이 겹치는 것까지 금지하는 규칙으로 확대하지 않는다. 기존 head가 있는 2→1 감소처럼 누름과 내장 끝 릴리즈가 같은 위치였던 사례는 새 차트 표현으로 옮길 때 충돌을 드러내야 한다. 어느 입력을 남길지 또는 위치를 바꿀지는 차트 의도에 따라 정하며, 변환기가 Point나 릴리즈를 자동 삭제하거나 릴리즈를 숨은 요구로 남기지 않는다.

### 24. 릴리즈 없는 짧은 double의 서로 다른 두 키 요구

에이전트는 시작·끝 창이 겹치는 릴리즈 없는 짧은 double 바디에서도 같은 키의 반복 누름으로 두 몫을 처리하지 못하게 하고, 서로 다른 두 물리 키를 요구하자고 추천했다. 사용자는 “ㅇㅇ”라고 동의했다(2026-10-24).

릴리즈가 없거나 길이가 짧다는 이유로 double의 두 키 요구를 없애지 않는다. 서로 다른 두 키의 입력 시각은 달라도 되며, 각 몫의 시작 창과 실제 시작 뒤의 종료 자격을 적용한다. 같은 키를 두 번 눌러 두 몫을 완료하는 연주는 허용하지 않는다. 바디 완료에 점수 항목을 추가하지 않는다.

이 결정은 각 바디 몫에 물리 키를 고정 배정하는 규칙이 아니다. 기존 키 교대와 이미 누른 키의 참여를 유지하며, 별도 릴리즈의 키 자격 예외까지 이 합의만으로 변경하지 않는다.

### 25. Point가 있는 double의 재충전 확대 제안 거절

에이전트는 single Point가 붙은 double에서 Point가 맡지 않는 추가 유지 요구에도, 시작 창이 닫힐 때까지 다시 채울 기회를 주자고 제안했다. 사용자가 설명을 요청해 한 번 시작한 뒤 끊긴 경우의 재충전 확대라는 뜻을 풀어 설명했고, 사용자는 “ㄴㄴ”라고 답했다(2026-10-24). 이 확대안은 채택하지 않는다.

해당 몫이 한 번 시작한 뒤 부족해지면 기존 유지 유예를 적용하며, 시작 창이 남았다는 이유로 실패 확정을 그 창의 끝까지 늦추지 않는다. Point가 맡는 몫의 기존 유지 규칙과 Point 없는 바디의 재충전 규칙은 유지한다.

이 답으로 아직 시작하지 않은 몫의 최초 시작 창을 없애지 않는다. 또한 앞 바디의 끝과 뒤 바디의 시작을 별개로 읽는 권리, 실제 바디 경계의 보존, 이미 확정된 실패의 복구 금지는 유지한다. head Miss 뒤 종속 정산을 실제 플레이 확인 뒤 검토하기로 한 일정도 바꾸지 않는다.

### 26. 동시 up과 키 재사용의 국소 배정 검토

사용자는 추가 검토 항목 중 동시 up과 같은 키 재사용 예외를 먼저 대조하는 데 동의했다(2026-10-24). 이 절은 검증 범위와 관찰 결과이며 새 제품 규칙을 승인받았다는 기록이 아니다.

`checks/release-assignment-order.ts`는 보관된 `ReleaseAssigner`에 열린 후보를 직접 넣어 입력 순서와 키 이름을 바꿔 본다. 새 바디 진행, Point 판정, 차트 컴파일, 점수 정산은 실행하지 않는다. 후보 상태의 실제 차트 도달 가능성과 새 세션 전체의 결과는 별도로 검증해야 한다.

- double의 첫 릴리즈만 적격인 상태에서 두 키의 up이 함께 들어오고, 뒤에 해당 double의 연결 head를 처리한 재누름으로 둘째 릴리즈가 열리는 후보 상태를 대조했다. 같은 키 재사용 예외를 제거하면 앞에서 어느 키를 배정했는지에 따라 둘째 입력의 자격이 달라진다. 기존 §3-3 예외를 적용하면 이 차이가 사라진다. 연결 release의 숨은 소비를 제거했다는 이유만으로 재누름 예외까지 삭제할 근거가 되지 않는다.
- 서로 다른 끝의 창이 겹치면 위 예외만으로 충분하지 않다. 한 키가 앞·뒤 후보 모두에 적격이고 다른 키는 앞 후보에만 적격인 상태에서, 수신 순서대로 하나씩 배정하면 처리 가능한 항목을 남길 수 있다. 동일 시각 up의 가능한 배정을 함께 대조하면 두 입력 모두 쓸 수 있는 배정이 존재한다. 국소 검증은 이 상태에서 기존 단일 up 배정 호출의 순서 의존성을 확인한 것이며, 기존 게임이나 새 엔진의 실제 차트 버그를 재현했다는 뜻은 아니다.
- 일반적인 double의 서로 다른 두 키 처리는 순서를 바꿔도 두 항목이 배정된다. Point 없는 같은 키 반복에는 둘째 자격이 생기지 않는다. 재누름 예외를 아무 Point나 다른 바디의 Point까지 확대하지 않는다.

같은 관측 묶음에 함께 들어온 동일 raw 시각 up의 수신 순서가 결과를 바꾸지 않는다는 기존 계약을 구현 계획에 명시한다. 구체적인 배정 알고리즘은 구현 선택이며, 다른 raw 시각 입력의 순서·같은 키의 down/up 인과관계·확정 판정 불번복은 그대로 보존해야 한다. 이 국소 검사만으로 새 모델의 동시 입력 검증을 완료 처리하지 않는다.

겹치는 창의 후보 상태로 이어지는 설계 입력을 `checks/overlapping-release-witness.json`에 따로 기록했다. 앞의 짧은 Point 있는 바디를 자기 시작 창 안에서 늦게 시작하고, 뒤의 Point 없는 double은 미리 누른 두 키로 시작하는 구성이다. 먼저 뒤 double의 릴리즈 하나가 처리되고 앞 바디가 늦게 시작하면, 앞 릴리즈와 키 사용 이력이 있는 뒤 릴리즈가 함께 남는다. 시간 창·경계·Point 소속은 산술 검사로 확인했으며, 실제 바디 활성화·완료·후보 생성 전이는 새 엔진 검증 대상으로 남긴다. 현재 `case:image`가 읽을 수 있는 에디터 차트나 엔진 실측 결과로 가장하지 않는다.

### 27. 재누름 예외 유지와 동시 up의 공동 배정 확인

사용자는 두 항목을 하나씩 설명해 달라고 요청했다. 에이전트는 먼저 해당 double 바디의 시작 Point를 실제로 처리한 재누름에 한해 같은 키의 남은 릴리즈 자격을 인정하는 기존 예외를 설명했고, 사용자는 “ㅇㅋ”라고 답했다. 이어 같은 시각의 up은 각 키가 처리할 수 있는 대상을 함께 확인해, 배정 가능한 릴리즈를 수신 순서 때문에 놓치지 않도록 하자는 설명에도 “ㅇㅋ”라고 답했다(2026-10-24).

차트상 이른 릴리즈 우선과 키 재사용 제한을 지키면서 같은 시각 입력의 배정을 함께 결정한다. 해당 바디의 Point를 실제로 처리한 경우에 한하는 기존 재누름 예외도 유지한다. 특정 배정 알고리즘을 확정하거나, 서로 다른 시각의 입력을 묶는 새 허용 폭을 도입하거나, 확정 판정을 되돌리는 결정은 아니다. 구현·검증 범위는 §26과 구현 계획을 따른다.

### 28. 끝 시각 뒤에 유효하게 시작한 single 바디

에이전트는 양수 길이의 짧은 single 바디에서 차트상 끝이 지났어도 시작 창이 남은 경우를 설명했다. 유효한 누름으로 바디를 실제로 시작하고, 유지할 구간이 이미 끝났으므로 즉시 유지 완료한 뒤, 명시된 릴리즈가 있으면 별도로 실제 뗌을 기다리자는 처리에 사용자는 “ㅇㅋ”라고 답했다(2026-10-24).

실제 시작 없이 끝 시각만 지났다고 정상 완료하지 않는다. 유효한 시작 이후에는 추가 유지 시간을 만들지 않으며 바디 완료의 점수도 없다. 릴리즈를 명시했다면 바디 완료가 그 릴리즈를 자동 성공시키지 않는다. 시작 실패가 이미 확정된 바디를 되살리거나 시작 창을 늘리는 결정도 아니다. 길이 0 바디나 옛 길이 0 `holdOnly`의 이행을 이 답으로 확정하지 않는다.

### 29. 앞 바디 실패와 뒤 바디의 새 시작 대조

아래는 §45·§46 이전의 적용 범위 대조다. 후속 결정에 따라 유지 노트만 놓인 연결과 같은 hold 수의 표식 없는 단순 연결은 앞뒤 탈락을 공유한다. 이 범위에 아래의 "실패 상태를 복사하지 않는다"를 그대로 적용하지 않는다.

§21·§22의 새 시작 허용과 RFD 0035의 실패 릴리즈 기회 소멸을 함께 대조했다. 앞 바디의 확정 실패와 그 끝 릴리즈의 종속 0점은 앞 바디에 남고, 실제 경계 뒤의 별도 바디는 자기 시작 조건에 따라 시작할 수 있다. 뒤 바디 시작으로 앞 릴리즈를 다시 후보에 넣거나 앞 실패를 취소하지 않는다. 앞 실패 상태를 복사해 뒤 바디의 새 시작을 막지도 않는다.

뒤 바디에 명시된 릴리즈는 뒤 바디의 실제 시작·유지 결과로 판단한다. 이는 새 제품 결정을 추가한 것이 아니라 기존 합의의 적용 범위를 대조한 결과다. 같은 hold 수의 연결과 1→2 증가에서 새 시작을 보존하고, 2→1의 건강한 몫 이어받기와 감소 릴리즈 귀속을 혼동하지 않는지 새 세션에서 검증해야 한다. 문서상 양립을 확인한 것이며 새 엔진 실행 결과는 아니다.

### 31. PR #338 최신본의 확정 내용과 보강할 적용 범위

유지 유예와 이른 종료 정산의 아래 검토는 §32에서 구체화했다. 이후 §34에서 릴리즈 확대를 철회하고 §35에서 유지 창도 누름 Good과 같게 확정하여, 창 차이에서 제안했던 Good 예외는 제거했다.

사용자가 다시 읽고 부족한 점을 확인하라고 요청하여 최신 head `33012a9a2f4dab06e29268a23fd331e0697f27bb`의 [RFD 0036](https://github.com/nanana3679/not4k/blob/33012a9a2f4dab06e29268a23fd331e0697f27bb/docs/rfd/0036-sustain-notes.md), glossary·scoring·PRD와 컨텍스트 변경을 대조했다. 이전 초안 기준으로 유지 노트의 Perfect/Miss 점수 여부를 다시 물은 질문은 철회한다.

최신 문서는 바디와 같은 시작 자격·hold 수·유지 유예·몫별 실패 상태, 이른 down·해당 위치에서의 유지·늦은 down이라는 세 확인 경로, 항목당 Perfect 3점·이론 가중치 3을 사용자 확인 사항으로 명시한다. 별도의 유지 노트 실패 조건을 만들지 않고, 바디 Miss 확정 시 미처리 유지 노트는 추가 실패 효과 없이 0점·원래 가중치로 정산한다. 더블 유지 조건 전체를 다시 미정으로 분류하지 않는다.

구현 전에 보강할 적용 범위는 다음과 같다. 새 실패 규칙을 제안하는 목록이 아니라 기존 합의로 상태 전이를 고정하기 위한 문서 검토다. 미정 추적의 권위는 계속 [PRD §12](https://github.com/nanana3679/not4k/blob/33012a9a2f4dab06e29268a23fd331e0697f27bb/docs/prd.md#12-미정-사항)이다.

- **유지 유예 중 성공 확정:** RFD 0032 §2-2에서 유예는 Miss 확정의 보류다. 유지 노트 위치에서 hold가 부족하되 바디 실패가 아직 미확정이면, 즉시 Perfect를 확정하는지 회복 결과를 기다리는지 문장으로 정해야 한다. 별도 Miss를 만들지 않는다는 문장만으로 성공 정산 시점까지 유일하게 도출되지는 않는다. 기존 세 확인 경로·유예 공유를 철회하는 질문과 구별한다.
- **정상 종료와 미처리 표식:** 이 대화의 유효한 이른 종료로 실제 hold가 끝난 뒤에도, 차트상 뒤에 미처리 유지 노트가 있을 수 있다. “해당 위치에서 유지 중”만 검사하면 정상 종료한 바디의 표식이 미처리로 남는 경로가 있다. 바디 정상 완료와 실제 held를 구분해 성공을 정산하는 시점·경로를 명시해야 하며, 정상 바디에 별도 유지 노트 Miss를 추가하거나 이른 종료를 금지해서 해결하지 않는다. 늦은 유효 시작 뒤 즉시 완료와 길이 0도 같은 완료 경로에서 검증한다.
- **입력 공유의 범위:** PRD에 남아 있는 공유·소비 항목을 Point와의 동시 처리, 겹치는 유지 노트 창에서 한 down·held가 여러 표식을 확인하는지로 구체화한다. 유지 조건이 바디와 같다는 결정과 down을 독점 소비하는지는 구별하며, 옛 `holdOnly` 입력 규칙을 자동 이식하지 않는다.
- **실제 경계와 새 바디 소속:** 현재 예시는 뒤 Point가 시작하는 새 바디만 보여 준다. 이 대화에서 확인한 head 없는 실제 경계의 새 시작도 표현해야 한다. 앞 바디의 소멸한 표식과 뒤 바디의 새 표식을 구별하고, 경계 위치의 소속과 더블 부분 실패 뒤 몫별 연결은 앞 실패의 복구와 혼동하지 않도록 명시한다. 새 시작을 Point가 있을 때로 제한하는 결정은 없다.

창의 구체적인 수치·0점 정산 시점·배치·트릴·저장 및 이행은 이미 PRD에 남아 있다. 점수 여부나 별도의 유지 노트 Miss 정책을 다시 결정할 항목으로 추가하지 않는다. 이 검토는 문서와 합의의 대조이며 새 엔진의 실행 검증은 아니다.

### 32. 회복 대기와 이른 종료 시 유지 노트 정산

회복 대기와 일괄 정산은 유지한다. 이 절의 창 밖 Good 예외는 §34·§35의 창 공유 결정으로 제거했으며 아래는 당시 논의 기록이다.

사용자는 다음과 같이 결정했다(2026-10-24).

> 회복여부기다림 바디일찍끝나면 남은유지 한번에처리 근데릴리즈판정이 넓어져서 릴리즈는 굳인데 유지 윈도우에는 안들어왔으면 유지도 굳 나오게

유지 노트 위치에서 hold가 부족하고 유지 유예 중이면 성공을 즉시 확정하지 않고 바디의 회복 여부를 기다린다. 바디 규칙상 유효하게 회복하면 보류한 유지 노트를 성공 처리하고, 바디 Miss가 확정되면 미처리 기회를 닫아 원래 가중치의 0점으로 정산한다. 별도의 유지 노트 Miss를 추가하지 않는다.

바디를 유효하게 일찍 정상 종료하면 그 종료에 속한 남은 미처리 유지 노트를 같은 종료 시점에 정산한다. 이미 처리한 표식을 다시 정산하거나 실패로 소멸한 기회를 되살리지 않는다. 정상 확인의 Perfect는 유지하되, 넓힌 릴리즈 창 때문에 일반 릴리즈는 Good이고 해당 유지 노트의 창에는 아직 들어오지 않은 경우에는 그 유지 노트도 Good으로 정산한다. Good은 공통 규칙상 1점이고 이론 가중치는 3으로 유지한다. 이 예외는 PR #338 `33012a9`의 “성공은 항상 Perfect”를 부분적으로 수정한다.

에이전트는 유지 창 밖의 이른 종료를 릴리즈 등급과 무관한 Good으로 통일할지, 릴리즈 등급을 따를지 물었다. Grace 릴리즈가 Perfect인 경우를 들어 전자를 추천했으나 답은 받지 않았다. 이어 사용자가 §33의 창 확대 자체를 재검토하여 이 질문은 그 뒤로 미뤘다. Grace·릴리즈 없음·일반 릴리즈의 다른 등급까지 Good 예외를 자동 확장하지 않는다.

### 33. 연결 릴리즈 제거 뒤 창 확대 필요성 재검토

이 절의 추천은 §34에서 사용자 확인을 받았다. 아래는 그 확인 전의 논의 기록이다.

사용자는 §32 뒤에 다음과 같이 물었다(2026-10-24).

> 근데 이제 o-o에서 릴리즈 요구 안하는데 릴리즈 범위를 넓힐필요가있나싶네

RFD 0032 §4-1과 PRD §12의 「떼는 판정 창의 완화」를 다시 확인했다. 기록된 직접 근거는 연결 Point를 누른 뒤 떼는 입력이 경계보다 늦어져, 연결 release의 허용 범위를 벗어나 뒤의 실제 release에 배정될 수 있다는 것이었다. §18에서 연결 release와 그 up 소비를 제거했으므로 이 보정 목적은 더 이상 유지되지 않는다. 실제 릴리즈의 창을 넓히면 Point 탭·교대 up이 명시된 릴리즈를 일찍 처리할 수 있는 범위는 커진다. 일반 릴리즈의 조작 부담 완화는 별도의 목적일 수 있지만, 연결 보정의 필요만으로 창 확대를 유지할 근거는 아니다.

에이전트 추천은 릴리즈의 Perfect·Great·Good 창을 우선 누름과 같게 두고 실제 플레이에서 별도 완화 필요성을 확인하는 것이다. 아직 사용자 결정은 아니다. 대칭·Grace의 최대 창 공유·릴리즈 없는 끝의 이른 허용 폭 공유는 확대 여부와 별개로 유지한다. 유지 노트의 허용 폭도 같은 최대 폭이라면, 넓은 끝 창 때문에 아직 유지 창에 들어오지 않은 미래 표식을 일찍 정산하는 상황은 생기지 않는다. 이 조건 없이 §32의 Good 예외를 자동 삭제하지 않는다. 유지 창의 실제 폭을 누름과 같게 확정한 답도 아직 없다.

유예 중 회복 대기와 이른 종료 시 남은 유지 노트 일괄 정산은 그대로 보존한다. 창 확대의 철회 여부를 먼저 논의하고, 그 결과에 따라 Good 예외가 필요한 범위와 공식 문서 이행을 정리한다. 위 기록은 구현 결과가 아니다.

### 34. 릴리즈 창 확대 철회와 누름 창 공유

이 절에서 남겨둔 유지 노트의 허용 폭도 §35에서 확정했다.

에이전트가 “우선 릴리즈 창 확대를 철회하고 누름과 같은 창으로 돌아갈까?”라고 묻자 사용자는 “ㅇㅇ”라고 답했다(2026-10-24).

일반 릴리즈의 Perfect·Great·Good 창을 누름의 해당 등급 창과 같게 둔다. 기존 앞뒤 대칭을 유지하고 별도의 릴리즈 확대 비율을 도입하지 않는다. Grace 릴리즈는 같은 Good 최대 허용 창 안에서 항상 Perfect이며, 릴리즈 없는 바디의 이른 종료도 그 Good 이른 폭을 공유한다. 실제 up 요구·바디 시작 자격·입력 소비·실패 종속은 그대로다.

양수 길이 바디에서 시작·끝의 최대 폭이 같으면 끝 창이 시작 창보다 먼저 열리지 않는다. 시작 창 안의 down만 새 시작으로 인정하고 실제 시작 뒤에만 이른 종료할 수 있다는 규칙은 창 개방 순서와 독립적으로 유지한다. 앞서 넓은 끝 창을 전제로 했던 설명은 역사적 조건부 분석으로 남긴다.

회복 대기와 이른 종료 시 남은 유지 노트 일괄 정산은 유지한다. 이번 답은 릴리즈의 등급별 폭에 대한 확인이며 유지 노트의 허용 폭을 따로 확정한 답으로 확대하지 않는다. 유지 노트도 누름 Good과 같은 최대 폭을 쓰면, 끝 창만 넓어서 미래 유지 노트 창 밖에서 조기 정산하는 경우가 없어지므로 §32의 해당 Good 예외는 필요하지 않게 된다. 그 공유 여부를 다음에 확인한다. Grace와 유지 Good의 조합을 묻던 질문은 아직 다시 진행하지 않는다.

### 35. 유지 노트 허용 창 공유와 Good 예외 제거

유지 노트 자체의 허용 창은 후속 §56에서 폐지했다. 아래는 당시 결정 기록이며, Perfect 정산·회복 대기·이른 종료 일괄 정산·Good 예외 제거는 유지한다.

에이전트가 “유지 노트의 이른·늦은 허용 창도 누름의 Good 창과 같은 폭으로 맞출까?”라고 묻자 사용자는 “ㅇㅇ”라고 답했다(2026-10-24).

각 유지 노트의 차트 시각을 기준으로 누름 Good과 같은 이른·늦은 허용 폭을 사용한다. 바디의 시작 자격·hold 수·유지 유예·몫별 실패 상태는 그대로 따른다. 유효하게 확인한 유지 노트의 성공은 항상 Perfect 3점·이론 가중치 3이며, Great·Good으로 나누지 않는다.

릴리즈의 최대 허용 폭과 유지 노트 허용 폭이 같으므로, 넓은 릴리즈 창만으로 미래 유지 노트 창 밖에서 일찍 정산되는 경우가 사라진다. 바디 끝을 E, 공통 폭을 W, 유효한 이른 종료 시각을 t, 그 뒤 남은 표식 시각을 M이라 하면 E-W ≤ t ≤ M ≤ E이므로 M-W ≤ t ≤ M이다. 따라서 그 표식은 자기 창 안에 있다. 이 산술은 종료 뒤에 놓인 미처리 표식에 대한 설명이며 실제 엔진 실행 결과가 아니다.

§32에서 넓은 릴리즈 창을 전제로 추가했던 유지 Good 예외는 제거한다. Grace의 등급을 유지 노트에 복사할지 묻던 후속 질문도 더 이상 진행하지 않는다. 일반 릴리즈가 Good이어도 유지 노트가 유효하게 처리되면 Perfect이며, 두 노트의 점수는 각각 정산한다.

유지 유예 중에는 회복 여부를 기다린다. 바디 규칙상 유효하게 회복하면 보류한 표식을 Perfect로 정산하고, 바디 Miss가 확정되면 미처리 기회는 원래 가중치의 0점으로 한 번 정산한다. 유효한 이른 정상 종료에서는 해당 종료의 남은 미처리 표식을 그 시점에 함께 Perfect로 정산한다. 이미 처리한 항목을 다시 처리하거나 실패한 기회를 복구하지 않으며, 별도 유지 노트 Miss를 만들지 않는다.

### 36. 바디와 같은 판정과 유지 노트의 입력 미소비

아래 §35의 유지 노트 독립 창을 유지한다는 당시 기록은 후속 §56에서 대체했다. 입력 미소비·바디 상태 공유·Perfect 점수·실패 비중복은 유지한다.

에이전트가 같은 down으로 Point 판정과 유지 노트 확인을 함께 허용할지 묻자 사용자는 다음과 같이 답했다(2026-10-24).

> ㅇㅇ 바디랑 똑같은 판정 하는 대신 점수만 올라가게

유지 노트는 해당 바디의 판정 조건과 상태를 그대로 따르며 명시된 위치의 점수 항목만 정산한다. 바디와 별도로 down·up을 소비하지 않고, 이미 유지 중인 상태에 새 down을 요구하지 않는다. 같은 down이 Point에 배정되어도 그 hold는 바디와 유지 노트 조건을 함께 충족할 수 있다. 입력을 유지 노트끼리 선착순으로 독점 배정하는 규칙도 추가하지 않는다. 같은 hold 상태가 여러 표식 각각의 확인 조건을 충족하면 각 항목을 한 번씩 정산한다.

시작 자격·실제 활성화·필요 hold 수·유지 유예·몫별 실패·이른 종료와 실제 경계의 새 시작은 바디 규칙을 따른다. Point가 없는 실제 경계에서도 뒤 바디가 자기 조건으로 시작하면 그 바디의 유지 노트는 그 상태를 따른다. 앞 바디의 이미 소멸한 기회는 복구하지 않는다. 바디와 다른 유지 노트 전용 실패 조건이나 부활 조건을 추가하지 않는다.

§35의 누름 Good 허용 폭, 성공 Perfect 3점·이론 가중치 3, 유예 중 회복 대기, 이른 종료 시 미처리 표식 일괄 정산을 유지한다. 바디 Miss에 따른 종속 0점도 원래 가중치로 한 번만 처리하며 추가 실패 이벤트를 만들지 않는다. 점수는 명시된 표식에만 생기고 바디 자체나 자동 주기 틱에는 생기지 않는다.

구현에서는 별도의 바디 판정 규칙을 유지 노트용으로 복제하지 않고 같은 바디 판정 결과를 점수 정산에서 사용한다. 구체적인 클래스·함수 구조는 구현 선택이다. 검증은 같은 바디·Point·릴리즈와 같은 입력에서 유지 표식만 추가하거나 제거해도 바디 진행, 기존 Point·릴리즈의 배정과 판정, 바디 실패 효과가 변하지 않는지 비교한다. 추가되는 것은 명시된 유지 노트의 점수 항목과 그에 따른 정산이다. 실제 엔진 검증은 후속 구현 단계에서 한다.

### 37. 한 위치에 서로 다른 노트 의미의 중첩 금지

에이전트가 같은 레인·같은 시각의 Point와 유지 노트를 함께 놓지 못하게 할지 묻자 사용자는 다음과 같이 답했다(2026-10-24).

> 금지 한 위치에 두개 의미 금지

특정 두 종류의 조합에만 예외를 붙이지 않고, 같은 레인·같은 시각에는 서로 다른 노트 의미를 겹쳐 놓지 않는 원칙으로 적용한다. 기존 Point+릴리즈 금지에 더해 Point+유지 노트와 릴리즈+유지 노트도 금지한다. Grace 여부로 이 금지를 우회하지 않는다.

싱글·더블은 같은 의미의 요구 수 표현이므로 기존 더블 허용을 철회하지 않는다. 바디는 이 배치 규칙에서 별도의 점수 노트 종류로 세지 않는다. 바디 위 유지 노트, 바디 시작의 Point, 바디 끝의 릴리즈와 실제 연결 경계는 기존 규칙을 유지한다. 일반·Grace를 같은 더블 릴리즈 안에 섞지 않는 결정도 그대로다.

이 제약은 차트의 같은 위치에 관한 것이다. 서로 다른 시각의 허용 창이 겹치거나 같은 물리 입력이 Point 판정과 바디·유지 조건에 함께 참여하는 §36의 규칙을 철회하지 않는다. 연결 경계의 유지 노트가 앞뒤 어느 바디에 속하는지는 별도의 문제이며 이 답으로 자동 확정하지 않는다.

차트 의미 검증·에디터 저장 및 플레이 검증에 같은 제약을 적용한다. 기존 데이터 변환에서 충돌 항목은 보고하고 한쪽을 자동 삭제하거나 다른 의미로 바꾸지 않는다. 이 기록은 로컬 논의 초안이며 원격 PR #338이나 게임 구현에 반영된 상태는 아니다.

### 38. 연결 경계 소속보다 에디터 차트 표현을 먼저 검토

에이전트는 연결 경계에 놓인 유지 노트를 뒤 바디에 소속시키는 규칙을 추천했다. 사용자는 다음과 같이 지적했다(2026-10-24).

> 유지노트를 에디터 차트상에 어떻게 표현할지에 따라 다를듯

뒤 바디로 고정하는 규칙은 사용자 결정이 아니다. 에디터에서 유지 표식을 배치하고 선택하는 방식, 바디와의 관계를 드러내는 표현을 먼저 검토한 뒤 경계의 소속을 결정한다. 이 답은 특정 편집 방식이나 저장 스키마를 채택한 것도 아니다.

이미 결정한 바디 종속 판정과 한 위치의 서로 다른 노트 의미 중첩 금지는 유지한다. 편집 중의 소속 표시뿐 아니라 실제 플레이에서도 같은 모습이 서로 다른 요구나 실패 종속을 숨기지 않는지 함께 검토한다. 실제 바디 경계와 유지 표식의 위치를 구별하며, 표식을 추가했다는 이유만으로 바디를 분할하거나 새 시작 기회를 만든다고 가정하지 않는다.

직접 편집은 바디 없이 떠 있는 유지 노트를 허용한다는 뜻이 아니다. 양수 길이 또는 길이 0 바디 위에 둔다는 기존 계약과 한 위치의 서로 다른 노트 의미 중첩 금지는 유지한다. 이 답만으로 바디 이동·삭제·길이 변경 때의 표식 동반 동작, 경계의 소속이나 소속 변경 조작, 선택 강조의 구체적인 시각 표현까지 확정하지 않는다.

### 40. 바디와 유지 표식의 편집 관계는 trillZone과 내부 노트를 따름

기존 `zoneContainedNoteIndices`는 양 끝점을 포함해 내부 노트를 찾는다. 맞닿은 두 바디의 경계에 있는 유지 표식을 이 함수처럼 앞뒤 모두에 귀속시키는 것은 승인된 계약이 아니다. 경계 소속·그 관계가 보이는 방식은 §38에 따라 계속 검토한다. 이 편집 관계를 트릴의 키 교대 판정이나 일반 노트와의 배타 규칙까지 유지 노트에 적용하라는 뜻으로 확대하지 않는다.

### 41. 빈 위치의 유지 표식 배치 시 길이 0 바디 함께 생성

에이전트가 바디가 없는 빈 위치에 유지 노트를 찍으면 길이 0 바디까지 함께 만들지 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-24).

빈 위치의 유지 표식 배치 한 번으로 같은 위치의 길이 0 바디와 그 위의 유지 표식을 함께 생성한다. 별도로 길이 0 바디를 먼저 그리는 조작을 요구하지 않는다. 유지 노트가 항상 양수 길이 또는 길이 0 바디 위에 존재한다는 기존 계약을 보존하며, 누름 노트나 양수 길이 바디를 대신 만들지 않는다.

이 결정은 바디가 없는 빈 위치에서의 생성에 관한 것이다. 기존 바디 내부나 맞닿은 경계에 길이 0 바디를 겹쳐 생성하는 규칙으로 확대하지 않으며, 기존 바디의 실패를 피해 독립적인 유지 판정을 추가하는 방식으로 쓰지 않는다. Point·릴리즈 등과 같은 위치의 서로 다른 의미 중첩 금지도 유지한다.

생성 이후 길이 0 바디와 표식을 이동·복사·삭제할 때의 묶음 범위는 이 생성 승인만으로 확정하지 않았으며 §42에서 후속 확인했다. 생성 조작의 undo/redo에서 두 항목의 생성과 취소가 함께 반영되는지 검증한다.

### 42. 독립적인 길이 0 바디와 유지 표식의 묶음 편집

**후속 개정(2026-10-25):** 사용자는 길이 0에서도 바디가 표식보다 커서 따로 클릭할 수 있다고 지적하며 선택 예외를 거부했다. 표식 클릭은 표식만, 바디 클릭은 둘을 함께 선택한다. 아래 원래 결정의 무조건 동반 선택·이동·복사는 후속 에디터 선택 규칙(`orchestration-20261025/contract-draft.md#선택과-hit`)으로 대체한다. 사용자는 이어서 표식만 삭제하면 길이 0 바디를 남기는 것도 허용했다. 빈 바디를 자동 제거하던 기존 편집 규칙은 철회한다. 후속 질문에서 사용자는 표식 없는 길이 0 바디를 플레이 가능한 유효 요소로 허용하는 데도 동의했다. 점수는 없고 일반 바디의 hold 요구·바디 실패 규칙은 유지한다.

에이전트가 빈 위치에 생성한 독립적인 길이 0 바디와 유지 표식을 한 묶음으로 이동·복사·삭제할지 묻자 사용자는 "ㅇㅋ"라고 답했다(2026-10-24).

해당 길이 0 요소에서는 유지 표식을 잡아도 소속 바디와 함께 이동하고, 복사·삭제에도 두 항목을 함께 처리한다. 이동은 같은 박·레인 오프셋을 적용하고, 복사본은 원본 바디가 아니라 함께 복사한 바디 위에 놓인다. 삭제하면 유지 표식만 사라지고 빈 길이 0 바디가 남지 않는다.

양수 길이 바디 위 유지 표식의 개별 편집은 그대로다. 이 결정은 독립적인 길이 0 요소의 편집 단위를 정한 것이며, 실제 바디 경계의 소속이나 길이 변경 때의 전환 동작을 자동 확정하지 않는다. 편집 묶음이라는 이유로 판정·점수 모델에서 바디와 유지 노트의 구분을 없애지 않는다.

구현 시 표식 히트에서 묶음 이동으로 이어지는 경로, 복사본의 바디 소속, 묶음 삭제, undo/redo와 저장 왕복을 검증한다. 기존 구간 내부 이동의 범위 제한만 복사해 길이 0 표식을 이동 불가능하게 만들지 않는다.

### 43. 명시적인 소속과 바디 판정 상태 참조의 구별

§42 뒤 에이전트는 연결 경계의 유지 표식을 뒤 바디에 자동 귀속시키자고 다시 추천했다. 사용자는 다음과 같이 물었다(2026-10-24).

> 소속이 필요함?

제작자가 앞뒤 바디 소속을 지정하거나 차트가 별도의 소속 ID를 반드시 저장해야 한다는 요구는 기존 합의에 없었다. 에이전트가 바디 판정 상태를 참조하는 관계를 명시적인 소속처럼 구체화한 점을 바로잡는다. 뒤 바디 고정 추천은 사용자 확인을 받지 않았으며, 소속 선택을 별도 제품 개념으로 먼저 도입하지 않는다.

현재 트릴 `PointNote`는 종류·레인·박 위치를 저장하며 `trillZone` ID를 저장하지 않는다. 구간 편집은 `zoneContainedNoteIndices`에서 위치를 기준으로 내부 노트를 찾는다. 유지 표식도 이러한 위치 기반 관계로 바디와 함께 편집하거나 판정 상태를 참조할 수 있으므로, 앞서 기록한 "소속 보존"이 반드시 사용자 설정이나 저장 필드를 뜻하는 것은 아니다. 정확한 새 저장 구조는 여전히 구현 전 계약에서 정한다.

바디 실패로 미처리 유지 기회가 사라지는 기존 규칙은 유지한다. 따라서 현재 hold 수만 확인하는 독립 판정으로 바꾸는 것도 아니다. 시작·유예·실패·정상 종료 상태는 바디 판정에서 가져와야 한다. 위치에서 관계를 찾더라도 맞닿은 경계에서 어떤 상태로 표식을 정산하는지, 앞 종료와 뒤 시작이 각각 어디까지 영향을 미치는지는 기존 바디 전환 규칙과 대조해야 한다. 소속 필드를 없애면 이 경계 동작까지 저절로 정해진다고 주장하지 않는다.

이 절은 사용자 질문을 계기로 한 에이전트의 전제 수정이다. 새 소속 정책이나 경계의 기대 판정을 사용자가 승인한 기록으로 취급하지 않는다.

### 44. 경계 상태를 확인할 사례: 앞 실패 뒤 새 시작

이 절은 사용자 답을 받기 전의 제안 기록이다. 아래의 "N3 새 시작 가능" 전제와 N2 Perfect 추천은 §45에서 철회했다. 연결의 앞뒤가 탈락을 공유하는 후속 설계 도식(`cases/sustain-boundary-shared-failure-confirmed.png`)이 최신 기대 동작이다.

사용자가 §43에서 말한 결정이 필요한 예시를 요청했다(2026-10-24). 설계 도식(`cases/sustain-boundary-new-start-design.png`)과 입력 자료(`cases/sustain-boundary-new-start-design.json`)를 작성했다. 현재 `case:image`는 새 유지 노트를 표현하지 못하므로 기존 엔진 결과로 대신하지 않았다. 이 PNG는 별도로 그린 설계 도식이며 `engineVerified=false`다. 기존 엔진을 실행하거나 기대값을 검증한 기록이 아니다.

같은 레인의 single 바디 N1은 1000～2000ms, 뒤 바디 N3은 2000～3000ms이고, 유지 노트 N2를 경계인 2000ms에 둔다. Point와 명시적 릴리즈는 없다. A를 1000ms에 누르고 1500ms에 뗀 뒤 유지 유예가 끝날 때까지 회복하지 않는다. N1은 실패가 확정된다. A를 N3의 시작 허용 창 안인 1990ms에 다시 누르고 3000ms까지 유지하면, 기존 합의상 N3은 새로 시작할 수 있다. 이 새 누름으로 N1의 실패가 취소되지는 않는다.

경계 표식 N2에 N1의 실패를 적용하면 종속 0점이고, N3의 새 시작을 적용하면 Perfect다. 이 두 결과는 검토할 기대 동작이며 실제 엔진 비교 결과가 아니다. 에이전트는 경계를 새 시작으로 읽는 기존 방향에 따라 N2도 Perfect가 되는 쪽을 추천한다. 명시적인 소속 설정을 도입하기보다 새 시작의 효력이 경계 표식에도 미치는지 명시할 사례로 다룬다. 아직 사용자 답을 받지 않았으므로 어느 쪽도 확인된 기대값으로 기록하지 않는다.

### 45. 유지 노트만 놓인 연결은 바디 탈락을 공유

후속 §57에서 같은 hold 수의 바디 연결점에 유지 노트를 놓는 배치를 금지했다. 아래는 그 배치를 허용했던 당시의 실패 전파 결정 기록이다. 표식 없는 단순 연결의 탈락 공유는 §46대로 유지한다.

§44의 예시에 사용자는 다음과 같이 답했다(2026-10-24).

> 유지 노트로만 이어진 바디는 탈락시 같이 탈락

유지 노트만 놓인 연결에서는 앞뒤 바디가 탈락을 공유한다. 제시한 single 사례에서 N1이 탈락하면 N3도 탈락 상태를 따르며, 1990ms의 재누름으로 N3만 새로 시작해 N2를 성공시키지 않는다. 미처리 유지 노트 N2는 기존 실패 종속 계약에 따라 원래 가중치의 0점으로 한 번 정산한다. 별도의 유지 노트 Miss를 추가하지 않는다.

에이전트가 N3의 새 시작을 이미 확정된 사실처럼 표시하고 N2 Perfect를 추천한 것은 이 연결에 적용할 계약이 아니다. 확인된 기대 동작의 설계 도식(`cases/sustain-boundary-shared-failure-confirmed.png`)과 입력 자료(`cases/sustain-boundary-shared-failure-confirmed.json`)에 정정한다. 사용자 확인 기대값이며 새 엔진 실행·검증 결과는 아니다.

§22의 실제 경계 시작을 이 연결의 탈락 뒤 복구 근거로 쓰지 않는다. 이번 답은 탈락 공유에 관한 것이므로 정상 상태의 분리 연주·시작과 끝의 허용 창, 실제 경계 저장 자체까지 자동 폐기하지 않는다. 이미 확정한 점수를 되돌리거나 double의 건강한 다른 몫까지 실패시키는 변경도 이 single 사례에서 도출하지 않는다.

현재 입력 구조에서 유지 표식을 지운 같은 연결에도 탈락 공유를 적용하는지는 당시 후속 질문으로 남겼고, §46에서 사용자 확인을 받았다. 유지 노트는 바디 판정에 점수만 더한다는 §36의 원칙에 따라 표식의 존재만으로 앞 탈락 뒤 재시작 가능 여부가 달라지는 예외를 넣지 않는다.

### 46. 같은 hold 수의 표식 없는 단순 연결도 탈락 공유

에이전트가 "같은 hold 수로, 아무 노트 없이 맞닿은 바디도 앞 탈락 뒤 재누름으로 살리지 못하게 할까?"라고 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-24).

같은 레인·같은 hold 수로 맞닿은 바디에 Point·릴리즈·유지 표식이 없어도 앞뒤 탈락을 공유한다. 이미 앞 바디가 탈락했다면 접점의 뒤 시작 허용 창에 다시 눌렀다는 이유만으로 뒤 바디를 살리지 못한다. 유지 표식만 추가하거나 제거해도 바디의 탈락과 재누름 복구 가능 여부는 같고, 명시된 점수 항목만 달라진다.

§22·§29의 "모든 실제 경계에서 앞 실패와 무관하게 뒤 바디 새 시작"이라는 적용은 이 단순 연결에 더 이상 쓰지 않는다. 이번 답은 확정 탈락 뒤 복구 금지에 관한 것이므로 정상 상태의 경계 분리 연주, 실제 경계 보존과 바디의 입력 미소비를 자동 폐기하지 않는다. 앞서 별도로 정한 Point가 있는 시작과 1→2 증가의 적용 범위도 같은 hold 수의 이번 답만으로 일괄 변경하지 않는다.

검증에서는 유지 표식이 있는 연결과 없는 연결에 같은 입력을 적용해 바디 탈락·복구 금지가 같은지 대조한다. 표식이 있는 경우의 종속 0점은 유지하되, 표식이 없는 경우에 숨은 점수 항목을 만들지 않는다. 실제 엔진 검증은 구현 이후에 한다.

### 47. 1→2 증가 경계의 뒤 double 전체 새 시작 유지

에이전트가 같은 hold 수 연결의 탈락 공유를 정리한 뒤 "Point·릴리즈 없이 1→2로 바뀌는 경계는, 기존대로 뒤 double 전체의 새 시작을 허용할까?"라고 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-24).

1→2 증가에서는 앞 single이 이미 탈락했더라도 뒤 double 전체를 자기 시작 조건에 따라 새로 시작할 수 있다. 추가된 한 몫만 새로 시작하도록 제한하지 않으며, 앞 single 탈락을 이유로 뒤 double의 요구 수를 하나로 낮추지도 않는다. 뒤 double의 각 몫은 기존 시작 창·실제 시작·필요 키 수 규칙을 따른다. 앞 바디의 확정 탈락과 이미 소멸한 점수 항목은 되돌리지 않는다.

같은 hold 수의 단순 연결과 1→2 증가의 규칙을 구분한다. 유지 노트는 점수만 추가하므로 증가 위치의 유지 표식 유무로 바디의 새 시작 가능 여부를 바꾸지 않는다. 새로 시작할 수 있는 뒤 double의 유지 노트·릴리즈도 뒤 바디의 상태에 따른다는 기존 원칙을 적용하며, 앞 바디의 잃은 기회를 복구하지 않는다.

이 답은 §21의 1→2 결정을 후속 탈락 공유 규칙과 대조해 유지한 것이다. 2→1 감소의 모든 몫 탈락 뒤 새 시작까지 같은 답으로 확정하지 않는다. 증가와 감소가 대칭이라는 구현 가정을 두지 않으며, 감소의 한 몫 실패 시 건강한 몫을 뒤 single로 이어준다는 §19의 결정도 유지한다.

### 48. Point 없는 2→1 감소에서 두 몫 탈락 시 뒤 single도 탈락 유지

에이전트가 "두 몫 모두 탈락했다면, 감소 경계에서 다시 눌러 뒤 single을 살릴 수 없게 할까?"라고 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-24). 질문의 범위는 Point 없는 2→1 감소다.

감소 전에 double의 두 몫이 모두 탈락했다면 뒤 single도 탈락 상태를 유지한다. 감소 위치의 시작 허용 창에 다시 눌렀다는 이유만으로 뒤 single을 새로 시작하지 못한다. 감소는 기존 두 몫이 서로 다른 시각에 끝나는 구조라는 §19의 원칙을 따른다.

한 몫만 탈락한 경우에는 건강한 몫을 뒤 single로 이어주고, 감소 지점의 명시된 릴리즈는 실패한 몫에 귀속시키는 기존 규칙을 유지한다. 명시된 릴리즈가 있는 경우에도 그 판정 기회가 이미 소멸했다면 재누름으로 되살리지 않는다. 미처리 유지 노트와 릴리즈는 기존 실패 종속 계약에 따라 정산하며, 이미 확정한 결과를 되돌리지 않는다.

앞 single 탈락 뒤에도 뒤 double 전체의 새 시작을 허용하는 1→2 증가와 구별한다. Point가 없는 감소에 관한 답이므로 뒤 바디 시작을 맡는 Point의 성공까지 이 복구 금지에 포함하지 않는다. 정상 상태의 분리 연주·시작과 끝의 허용 창을 이번 탈락 결정만으로 삭제하지 않는다.

검증에서는 Point 없는 2→1의 정상 유지·한 몫 탈락·두 몫 탈락을 대조한다. 건강한 몫이 남으면 뒤 single로 이어지고, 두 몫 모두 탈락하면 감소 위치의 재누름으로 뒤 바디나 종속 점수 항목이 복구되지 않아야 한다. 증가와 감소를 같은 새 시작 조건으로 처리하는 구현 가정을 피한다.

### 49. 릴리즈만 놓인 single→single 경계의 새 시작과 연주 의미

에이전트가 "Point 없이 릴리즈만 놓인 single→single 경계에서 앞 바디와 릴리즈가 이미 탈락했더라도 뒤 single의 새 시작을 허용할까?"라고 묻자 사용자는 "ㅇㅇ 그리고 그 배치는 자연스럽에 o-o- 에서 똄과 동시에 입력을 요구하네"라고 답했다(2026-10-24).

앞 single이 이미 탈락해 앞 릴리즈가 종속 0점으로 정산됐더라도 뒤 single은 자기 시작 조건에 따라 새로 시작할 수 있다. 앞의 확정 탈락·릴리즈 결과를 되돌리거나, 뒤 바디의 시작 조건으로 앞 릴리즈 성공을 요구하지 않는다. 같은 hold 수의 Point·릴리즈 없는 단순 연결과 구별한다. 이번 확인은 single→single의 릴리즈 경계이며 double의 일부 릴리즈 경계까지 자동 일반화하지 않는다. Point 없는 2→1 전체 탈락의 승계 금지(§48)도 그대로 유지한다.

사용자는 이 배치가 떼면서 뒤를 이어 누르는 동작을 자연스럽게 요구한다는 연주 의미를 짚었다. 기존 계약을 적용하면 정상 연주에서 명시된 릴리즈는 유효한 up을, 뒤 바디는 시작·유지에 필요한 hold 수를 요구한다. 뒤에 Point를 추가하거나 별도 down 판정을 만드는 것은 아니다. 미리 누른 키의 참여도 유지하므로 새 down과 up이 반드시 같은 시각이어야 한다는 규칙으로 해석하지 않는다. 앞 릴리즈와 뒤 바디는 각자의 허용 창·실제 시작 조건을 따른다.

검증에는 앞 바디 정상·탈락 뒤의 뒤 single 시작을 포함한다. 릴리즈 성공을 뒤 시작의 선행 조건으로 묶거나 이미 소멸한 앞 릴리즈를 되살리지 않아야 한다. 정상 상태에서는 새 down을 이용한 교대와 미리 누른 키를 이용한 뒤 바디 시작을 함께 대조한다. 릴리즈와 Point의 동시 배치나 숨은 누름 점수 항목을 생성하지 않는다. 실제 엔진 검증은 구현 이후에 한다.

### 50. 릴리즈 하나인 double→double 경계의 뒤 double 전체 새 시작

에이전트가 "Point 없는 double→double 경계에 릴리즈가 하나만 있을 때, 앞 double이 모두 탈락했어도 앞 릴리즈의 0점은 유지하면서 뒤 double의 두 몫을 자기 시작 조건으로 새로 시작할 수 있게 할까?"라고 묻자 사용자는 "ㅇㅋ"라고 답했다(2026-10-24).

이 경계에서는 뒤 double 전체에 새 시작 기회를 준다. 앞 double의 두 몫이 모두 탈락했더라도 뒤 double의 각 몫을 자기 시작 조건에 따라 시작할 수 있다. 한 몫만 새로 시작하도록 제한하거나 뒤 double의 요구 hold 수를 하나로 낮추지 않는다. 앞 바디의 확정 탈락과 그 바디에 종속된 릴리즈·유지 노트의 소멸한 기회는 되돌리지 않는다.

릴리즈 하나는 앞 끝에서 요구하는 뗌의 수이며 뒤 바디의 새 시작 가능 몫 수가 아니다. 바디의 요구 hold 수와 끝의 릴리즈 수를 구별한 §10의 원칙을 이 연결에도 적용한다. 뒤 시작에 앞 릴리즈 성공이나 같은 시각의 새 down을 추가로 요구하지 않고, 기존 실제 시작·시작 창·미리 누른 키·서로 다른 두 키의 조건을 따른다.

§49에서 자동 일반화하지 않고 남겼던 double의 릴리즈 하나인 연결을 이번 답으로 확인했다. 릴리즈 없는 같은 hold 수의 단순 연결은 여전히 탈락을 공유하며, Point 없는 2→1 감소의 두 몫 탈락 뒤 single 복구 금지(§48)도 유지한다. 실제 경계 없이 바디 중간의 임의 위치에 새 시작 기회를 만들지 않는다.

검증에는 이 연결의 앞 double 정상·일부 탈락·전체 탈락을 포함하고, 뒤 두 몫의 새 시작과 앞의 확정 결과 보존을 함께 확인한다. 릴리즈 하나라는 이유로 뒤 한 몫만 시작 가능하게 만드는 구현을 막는다. 새 엔진에서의 실행 검증은 구현 이후에 한다.

### 51. 1→2 증가 위치의 유지 노트는 뒤 double 기준

에이전트가 "1→2 증가 지점의 유지 노트는 뒤 double 기준으로 둘까?"라고 묻자 사용자는 "ㅇㅋ"라고 답했다(2026-10-24). 제안은 그 위치에 표식 두 개를 놓고 뒤 double의 두 몫 상태를 확인하는 것이다.

증가 위치의 유지 노트는 뒤 double을 확인한다. 앞 single의 끝 상태를 확인하는 표식 하나나 앞뒤를 합한 표식 세 개로 해석하지 않는다. 해당 위치부터 요구하는 hold 수 2와 뒤 바디의 시작·유지·몫별 실패 상태를 따른다. 성공은 기존 유지 노트 계약대로 항목당 Perfect이며 별도의 down이나 up을 소비하지 않는다.

앞 single이 탈락했더라도 뒤 double 전체를 자기 조건으로 새로 시작할 수 있다는 §47을 적용한다. 증가 위치의 두 표식은 뒤 바디의 상태에 따르며 앞 single의 실패를 이유로 미리 소멸시키지 않는다. 앞의 확정 실패와 이미 소멸한 점수 항목은 복구하지 않는다. 표식이 뒤 double을 스스로 활성화하거나 실패한 몫을 되살리는 규칙도 추가하지 않는다.

같은 레인·같은 시각의 다른 노트 의미 중첩 금지(§37)는 유지한다. 따라서 이 위치에 유지 노트를 놓는 구성에는 Point나 릴리즈를 함께 두지 않는다. 두 표식은 같은 의미의 수량이므로 허용한다. 관계를 정한 것이며 제작자에게 별도 소속 선택이나 소속 ID 저장을 요구하는 결정이 아니다.

검증에는 앞 single 정상·탈락 뒤의 증가 위치 표식과 뒤 double의 시작·몫별 상태를 포함한다. 앞 바디의 실패 종속이나 이른 종료 일괄 정산에 뒤 기준인 두 표식을 잘못 넣지 않아야 한다. 유지 표식 유무로 1→2의 새 시작 조건을 바꾸지 않고 표식 항목만 각각 한 번 정산한다. 저장·컴파일·편집·표시에서도 뒤 double 기준의 두 표식이라는 의미를 보존한다. 2→1 감소 위치의 표식 수·기준은 이번 답으로 자동 확정하지 않는다.

### 52. 2→1 감소 위치의 유지 노트는 뒤 single 기준

에이전트가 "Point·릴리즈 없는 2→1 감소 지점도 뒤 single 기준의 유지 표식 하나로 둘까?"라고 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-24).

감소 위치의 유지 노트는 뒤 single의 상태를 확인하는 표식 하나로 둔다. 앞 double의 두 몫을 확인하거나 끝나는 몫과 이어지는 몫을 모두 채점하는 위치로 해석하지 않는다. §51의 증가 위치와 함께 그 위치부터 요구하는 바디의 hold 수를 표시한다. 별도의 소속 설정이나 소속 ID를 제작자에게 요구하는 결정은 아니다.

감소 전에 앞 double의 한 몫만 탈락했다면 건강한 몫이 뒤 single로 이어지는 기존 규칙을 적용한다. 그 single이 유지 조건을 충족하면 표식은 Perfect로 정산할 수 있다. 앞에서 끝나는 실패 몫에 이 표식을 종속시켜 0점으로 만들지 않는다. 두 몫 모두 탈락했다면 §48에 따라 뒤 single도 탈락을 유지하며 미처리 표식은 원래 가중치의 종속 0점으로 한 번 정산한다. 유지 표식 위치에 다시 눌러 뒤 single이나 소멸한 표식을 복구하지 않는다.

같은 위치에는 Point나 릴리즈를 함께 놓지 않는다. 명시하지 않은 감소 릴리즈나 끝나는 몫의 유지 표식을 자동 생성하지 않는다. 유지 노트 추가·삭제가 감소의 정상 승계·실패 전파·재시작 금지에 영향을 주지 않으며, 별도 입력 소비나 추가 유지 노트 Miss도 만들지 않는다.

검증에는 감소 전 정상·한 몫 탈락·두 몫 탈락을 포함한다. 표식 수가 하나이고 뒤 single의 판정 상태를 따르는지, 끝나는 몫의 처리와 중복 정산되지 않는지 확인한다. 유지 유예 중 회복 대기와 유효한 이른 종료 정산에는 기존 바디·유지 노트 계약을 적용한다. 저장·컴파일·편집·표시에서도 이 관계를 보존하며 실제 엔진 실행 검증은 구현 이후에 한다.

### 53. single Point가 있는 double→double의 두 몫 새 시작

에이전트가 "single Point가 있는 이 경계에서도 뒤 double 전체에 새 시작 기회를 줄까?"라고 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-24). 앞 double이 모두 탈락했을 때 뒤 한 몫만 시작할 수 있는지, 뒤 두 몫 모두 자기 조건으로 새로 시작할 수 있는지를 확인한 질문이다.

뒤 double의 두 몫 모두 새 시작 기회를 갖는다. single Point의 누름 요구 수를 뒤 바디의 새 시작 가능 몫 수로 사용하지 않는다. Point 하나를 판정했다고 두 몫을 자동 활성화하거나 두 키의 유지 요구를 하나로 낮추지 않는다. 뒤 각 몫은 기존의 시작 조건과 hold 수를 충족해야 한다.

앞 바디의 확정 탈락과 소멸한 종속 점수 항목은 그대로 둔다. 뒤 바디가 이미 시작한 후 탈락한 몫을 늦은 Point 판정으로 되살리는 결정도 아니다. Point가 맡는 몫의 실제 down 기준과 다른 몫의 시작·유지 조건을 구별하고, §25에서 거절한 시작 뒤 재충전 확대를 다시 도입하지 않는다. 바디 중간의 임의 Point를 새 바디 경계로 삼지 않는다.

검증에서는 앞 double 정상·일부 탈락·전체 탈락에서 뒤 두 몫의 시작 가능 범위를 대조한다. 실제 두 키와 몫별 시작 조건을 충족했을 때 앞의 실패 수나 Point 수 때문에 뒤 시작을 제한하지 않아야 한다. 앞의 소멸한 기회와 뒤 바디 자체에서 이미 확정된 실패도 복구하지 않는다. 이번 답은 새 시작 기회의 범위이며, Point를 놓친 경우의 종속 정산 범위까지 새로 확정한 것으로 확대하지 않는다. 실제 엔진 검증은 구현 이후에 한다.

### 54. single Point Miss와 별개로 나머지 한 몫 시작

§53 뒤에 에이전트는 건강하게 승계할 몫이 없는 double→double에서 single Point를 놓쳤어도, Point가 맡지 않는 한 몫이 정상 시작·유지했다면 그 몫을 유지하자는 제안을 했다. 사용자의 그림 요청과 도구·표현 확인은 판정 제안 승인으로 취급하지 않았다. 이후 사용자가 "한몫 시작 되는걸로"라고 답해 이 시작을 확정했다(2026-10-24).

설계 그림(`cases/single-point-miss-double-one-share-proposal.png`)과 설계 입력(`cases/single-point-miss-double-one-share-proposal.design.json`)은 N1 double 바디 1000～2000ms, N2 single Point 2000ms, N3 double 바디 2000～3000ms를 사용한다. A·B는 1000～1400ms에 누른 뒤 떼고, A만 1700～3000ms에 다시 누른다. 릴리즈·유지 노트는 놓지 않는다. 설명용 Point Good 폭은 ±120ms, 유지 유예는 20ms다.

N1은 유지 유예 안에 회복하지 않아 두 몫이 탈락한다. A의 1700ms down은 N2의 1880～2120ms 창 밖이며 창 안에 새 down이 없어 N2는 Miss다. N3의 차트상 시작 시각에는 A만 이미 눌려 있다. 이 hold로 N3의 Point가 맡지 않는 한 몫은 2000ms에 새로 시작한다. 창이 열리는 1880ms에 미리 시작시키거나 N2 Miss가 확정될 때까지 시작을 미루지 않는다. 시작한 뒤에는 일반 바디의 유지 유예·실패·종료 규칙을 따른다.

Point가 맡는 몫만 N2 Miss에 종속시킨다. N2 Miss를 N3 전체 탈락으로 확대하거나 같은 원인의 바디 Miss를 더하지 않는다. 앞 N1의 확정 실패는 유지하고, N3 자체에서 이미 탈락한 몫도 복구하지 않는다. 몫은 특정 물리 키에 고정된 소유권이 아니다.

검증에는 N3의 2000ms 시작, 이후 정상 유지와 유지 실패, N2의 독립적인 Miss 및 비중복 실패 정산을 포함한다. N2를 놓쳤다는 이유로 정상 시작한 다른 몫을 취소하지 않는지 대조한다. 설명 그림은 `pnpm case:image --design`으로 기존 스킨 에셋·입력·창을 그리며 제목과 본문은 이미지 밖의 텍스트로 둔다. 사용자 결정에 따른 기대값이며 엔진 실행 결과가 아니다.

### 55. 같은 hold 수 연결의 경계 유지 노트와 앞 바디 이른 종료 — 배치 금지로 종료

후속 §57에서 이 배치를 금지했다. 앞 종료에 따른 Perfect와 뒤 시작 실패에 따른 0점 중 하나를 채택하지 않으며, 아래는 당시 비교한 대안 기록이다. 공유 그림은 배치 금지 결론으로 갱신하고 이전 입력은 보관한다.

§54를 기록한 뒤 남은 경계 정산 사례를 대조한다. §45·§46은 앞 바디가 탈락한 연결의 실패 공유를 정했다. 앞 바디가 정상 종료했지만 뒤 바디는 시작하지 않은 경우의 경계 표식 정산은 그 실패 공유만으로 정해지지 않는다. §51·§52에서 증가·감소 위치의 유지 표식을 뒤 바디 기준으로 정했으나, 같은 hold 수 경계까지 자동 승인된 것으로 확대하지 않는다.

[설계 그림](https://share.onorca.dev/a/JkMyf8-0FQSA)과 당시 설계 입력(`cases/maintain-boundary-after-early-end-proposal.before-same-count-ban.design.json`)은 N1 single 바디 1000～2000ms, N2 유지 노트 2000ms, N3 single 바디 2000～3000ms를 사용한다. A를 1000ms에 눌러 1900ms에 떼고 다시 누르지 않는다. 설명용 바디 시작 허용 폭은 ±120ms, 이른 종료 허용 폭은 120ms다. N1은 끝의 허용 창 안에서 정상 종료하지만 N3는 자기 창 안의 새 down도, 시작 시각의 hold도 없어 시작하지 못한다. §56에 따라 N2 자체의 창은 그림에서 제거했다.

추천은 N2를 뒤 N3 기준으로 확인하여 N1의 이른 종료 일괄 정산에서 제외하는 것이다. 이 사례에서는 N3의 시작 실패에 종속해 N2를 원래 가중치의 0점으로 정산하고 추가 유지 노트 Miss를 만들지 않는다. 비교하는 선택은 N1의 정상 종료 때 N2도 Perfect로 정산하는 것이다. 뒤 바디를 시작하지 않아도 경계 점수만 얻을 수 있는 차이가 있다.

다음 질문은 같은 hold 수의 연결 경계에서도 유지 노트를 뒤 바디 기준으로 둘지다. 아직 사용자 답은 없으며 추천을 확정 계약이나 엔진 결과로 기록하지 않는다. `pnpm case:image --design`으로 기존 스킨 바디·임시 유지 표식·입력·창을 그렸고, 제목과 설명은 이미지 밖 텍스트로 표시한다.

### 56. 유지 노트의 독립 허용 창과 선판정 폐지

§55에 답하기 전에 사용자는 "어차피 바디 안에서는 계속 유지여야 하니까 유지노트는 창이 필요없는걸까?"라고 물었다. 에이전트가 "유지 노트의 별도 창과 그에 따른 선판정은 없애고, 바디 판정만 따르는 것으로 바꿀까?"라고 묻자 사용자는 "ㅇㅋ"라고 답했다(2026-10-24). §35의 유지 노트 독립 허용 창을 폐지하며, 같은 hold 수 경계의 기준 바디까지 확정한 답으로 확대하지 않는다.

유지 노트에 독립적인 ±Good 창을 두지 않고 바디의 판정 상태에 점수 정산만 연결한다. 정상 유지 중이면 표식 시각에 Perfect로 정산한다. 그 시각에 바디의 최초 시작 판정이나 유지 유예가 진행 중이면 바디 결과를 기다린다. 유효한 늦은 시작·회복이면 보류한 표식을 성공 처리하고, 실패가 확정되면 미처리 표식은 원래 가중치의 종속 0점으로 정산한다. 유효한 이른 정상 종료 때 해당 바디의 남은 표식을 함께 Perfect로 정산하는 결정을 유지한다. 길이 0 바디에도 바디 자체의 시작 허용을 적용하며 정확한 한 시각에만 누를 수 있게 좁히지 않는다.

단순한 중복 설정 제거만은 아니다. 기존 세 확인 경로 중 유지 노트의 이른 창 안에 새 down이 들어왔다는 이유로 미래 표식을 미리 성공시키는 경로를 제거한다. 바디의 이른 시작만으로 미래 표식을 모두 성공 처리하지 않으며, 정상 종료에 따른 일괄 정산 외에는 표식 시각의 바디 상태와 필요한 판정 대기를 따른다. 이미 성공한 표식을 이후 바디 실패로 되돌리는 규칙은 추가하지 않는다. 성공 Perfect 3점·이론 가중치 3, 입력 미소비와 실패 효과 비중복도 유지한다.

검증에서는 미래 표식의 선판정 금지, 표식 시각의 정상 유지, 시작 판정·회복 유예 중 보류, 유효한 늦은 시작·회복, 정상 이른 종료와 길이 0 바디를 대조한다. 표식만의 기한으로 바디의 합법 입력을 차단하거나, 이미 실패한 바디를 복구하거나, 바디 판정 결과와 다른 유지 노트 Miss를 만들지 않는다.

별도 유지 창을 없애도 경계 표식이 어느 바디 결과를 따르는지는 남는다. §55의 앞 정상 종료와 뒤 미시작 사례는 보류했던 질문으로 이어간다. 이번에는 논의 기록과 구현 계획·설계 그림만 갱신하며 엔진 동작은 변경하지 않았다. 보류했던 같은 hold 수 경계 질문은 후속 §57의 배치 금지로 종료했다.

### 57. 같은 hold 수의 유지 노트 연결 금지와 증가·감소 위치 허용

사용자는 "유지 노트로 바디가 이어질수 없다고 보면 어떄"라고 제안했다. 에이전트가 증가·감소까지 모든 연결점에서 유지 노트를 금지할지 묻자, 사용자는 "1-2 2-1로 변할때는 있어도 될거같은데"라고 범위를 정정했다(2026-10-24).

같은 hold 수의 두 바디가 맞닿는 위치에는 유지 노트를 놓지 않는다. 1→1과 2→2의 연결점이 대상이다. 하나의 긴 바디 내부에 유지 표식을 놓는 배치는 허용하며, 표식을 놓았다는 이유로 그 위치에 바디 끝·시작 경계나 추가 허용 창을 만들지 않는다. 독립적인 길이 0 바디와 유지 노트도 기존대로 허용한다.

1→2 증가와 2→1 감소 위치에는 유지 노트를 허용한다. §51·§52대로 증가 위치의 두 표식은 뒤 double을, 감소 위치의 한 표식은 뒤 single을 확인한다. 표식 자체가 증가·감소나 새 시작을 만드는 것은 아니며 바디의 기존 시작·승계·실패 규칙을 따른다. 같은 위치의 Point·릴리즈 중첩 금지와 유지 노트 자체의 창·선판정 폐지도 유지한다.

§55의 같은 hold 수 연결 사례는 합법 배치가 아니므로 어느 바디의 정산을 따를지 선택할 필요가 없다. §45의 유지 노트 연결 허용 전제도 이 범위에서 대체한다. 표식 없는 실제 경계의 존재·정상 분리 연주와 §46의 탈락 공유까지 폐지하는 결정은 아니다. 편집 중 두 바디를 자동 병합하거나 기존 차트를 일괄 변환하라는 승인으로도 확대하지 않는다.

검증에서는 같은 hold 수 연결점의 표식 금지, 한 바디 내부 표식·독립 길이 0·1→2·2→1의 허용을 구별한다. 합법 배치에서 표식 추가·제거가 바디 판정을 바꾸지 않는지 대조하고, 구형 연결 사례의 0점·Perfect 기대값을 새 모델에 그대로 이식하지 않는다. 논의 기록과 계획·설계 그림만 갱신하며 게임 구현과 기존 차트는 변경하지 않는다.

### 58. 트릴 바디 위 유지 노트 금지

에이전트가 트릴 바디에도 유지 노트를 허용하되 교대 입력을 요구하거나 교대 이력을 바꾸지 않고 유지 결과에 점수만 더할지 묻자, 사용자는 "ㄴㄴ"라고 답했다(2026-10-24).

트릴 바디에는 유지 노트를 배치하지 않는다. 트릴 전용 유지 노트나 교대를 요구하는 유지 노트를 대신 도입한 결정도 아니다. 일반 single·double 바디와 독립 길이 0 바디, §57에서 허용한 증가·감소 위치의 유지 노트는 기존 계약을 따른다. 이 답을 트릴 바디 자체의 판정·교대 추적·릴리즈 규칙 변경으로 확대하지 않는다.

차트 의미 검증·저장·플레이 진입에서 트릴 바디 위 유지 표식을 금지 배치로 검증할 계획에 반영한다. 에디터의 기존 낙관적 편집 원칙과 구분하며 이번 논의에서 구현하거나 기존 차트를 수정하지 않는다.

### 59. 구형 양수 길이 holdOnly 변환 시 끝 유지 표식 추가 여부 — 자동 변환 제외로 종료

사용자가 §60에서 기존 차트를 사람이 직접 수정하기로 정했다. 아래 자동 변환 규칙의 추천은 채택하지 않으며, 끝 유지 표식의 추가·제거는 차트별 수정 의도에 맡긴다.

트릴 바디 위 유지 노트 금지 뒤에는 기존 차트 이행에서 남은 선택을 검토한다. 같은 위치의 Point·릴리즈 충돌을 보고하고 자동 삭제하지 않는 방향은 §23에 이미 기록되어 있으므로 같은 결정을 다시 묻지 않는다.

구형 양수 길이 `holdOnly`는 현재 컴파일러가 끝에 몫당 가중치 3의 상태 점수 항목을 만든다. 새 릴리즈 없는 바디로만 옮기면 그 자동 점수 항목이 사라진다. 명시적인 유지 표식을 끝에 추가하면 점수 항목을 남길 수 있지만, 트릴 바디 위 표식이나 같은 hold 수 연결점 등 새 배치 금지와 충돌할 수 있다.

추천은 양수 길이 구형 `holdOnly`를 릴리즈 없는 바디로 옮기고 끝 유지 표식을 자동 추가하지 않는 것이다. 바뀌는 점수 분모·콤보 기회는 변환 보고에 명시하고, 필요한 유지 표식은 새 차트 제작 의도로 배치한다. 길이 0 `holdOnly`의 유지 노트 대체 방향은 이 질문과 구별한다. 아직 사용자 확인 전이며 실제 변환이나 데이터 변경을 수행하지 않는다.

### 60. 기존 차트는 사람이 직접 수정하고 자동 변환기는 제외

후속 §61에서 구형 파일을 에디터로 읽어 수정하는 호환은 필수라고 정정했다. 아래 자동 변환 제외를 읽기 파서나 편집을 위한 호환 연결까지 제거하는 뜻으로 해석하지 않는다.

구형 양수 길이 `holdOnly`의 자동 변환 방향을 묻자 사용자는 "차트 몇개 없어서 그냥 사람이 바꾸게함"이라고 답했다(2026-10-24).

기존 플레이 차트는 사람이 새 규칙과 형식에 맞춰 직접 수정한다. 자동 변환기·일괄 변환과 이를 위한 노트별 자동 대응 규칙은 구현 계획에서 제외한다. §59의 양수 길이 `holdOnly` 끝 표식 자동 추가 여부도 더 이상 자동 변환의 제품 결정으로 묻지 않는다. 길이 0 상태 노트를 새 유지 노트로 표현할 수 있다는 모델 결정은 유지하지만 구형 데이터를 자동 치환하는 기능을 뜻하지 않는다.

새 차트의 저장·불러오기·의미 검증·왕복 보존과 사람이 수정한 차트의 플레이 확인은 필요하다. 회귀 테스트 입력, 튜토리얼·Lab의 코드 내 예제는 새 계약을 검증하고 설명할 수 있게 개발 작업에서 갱신한다. 이 결정은 실제 플레이 차트를 에이전트가 대신 수정하거나 원격 데이터를 변경·삭제하라는 지시가 아니다.

새 에디터가 구형 파일을 불러올 때의 호환 범위는 이 답만으로 확정하지 않는다. 자동 변환을 전제로 한 분석 보고서·반복 안전 변환 테스트는 완료 조건에서 제거하며, 기존 런타임과 보관된 회귀 기록의 삭제 시점은 별개로 유지한다.

### 61. 구형 차트 읽기·편집 호환은 유지

에이전트가 새 에디터에서 구형 파일을 열지 않고 사람이 먼저 새 형식으로 수정하게 하자고 추천하자, 사용자는 "읽기는 해야함 사람이 수정하려면"이라고 정정했다(2026-10-24).

읽기·편집 호환을 유지하고 사람이 편집한 뒤 새 규칙 검증과 새 형식 저장을 거치는 흐름으로 정리하자 사용자는 "ㅇㅋ"라고 확인했다(2026-10-25).

새 에디터는 구형 차트를 불러와 사람이 수정할 수 있어야 한다. 외부에서 JSON 형식을 먼저 고치도록 요구하거나 구형 버전이라는 이유만으로 열기를 거부하는 추천은 철회한다. §60에서 제외한 것은 사람이 할 차트 수정을 대신 결정하는 자동 처리와 일괄 변환이다. 읽기 파서와 편집 가능한 상태로 연결하는 호환 처리는 필요하다.

노트의 위치·길이·종류·속성과 차트 메타데이터를 사람이 확인하고 고칠 수 있도록 보존한다. 구형 의미와 새 규칙이 충돌하는 곳을 숨기거나 읽는 과정에서 임의로 노트를 삭제하지 않는다. 구체적인 편집 모델과 구형 속성의 표현은 구현 설계에서 이 요구를 만족하도록 정하며, 새 노트 배치를 일괄 확정하는 자동 대응 규칙을 이 답만으로 채택하지 않는다.

기존 에디터는 `loadChart`에서 위반 차트도 열어 수리하도록 허용하고 저장·플레이 진입에서 검증한다(RFD 0017). 새 규칙에 맞지 않는 부분이 있다는 이유로 수정용 불러오기를 막지 않고 같은 편집·검증 원칙을 유지한다. 수정 완료 후 새 형식으로 저장하고 다시 불러와 같은 내용을 편집·플레이할 수 있는 경로를 계획에 포함한다. 읽기 호환을 위해 구형 판정 엔진을 영구 유지하거나 구형 형식으로 다시 저장하는 기능까지 추가한 결정은 아니다.

이번 수정은 계획과 논의 기록에 한정하며 구형 파일·실제 차트·원격 데이터를 변경하지 않는다.

### 62. 유지 노트 성공은 표식 하나당 콤보 증가

§36의 "바디랑 똑같은 판정 하는 대신 점수만 올라가게"는 입력 미소비와 같은 바디 조건으로 정리했다. 유지 노트 성공의 Perfect 3점·이론 가중치 3과 실패 시 추가 콤보 이벤트 없음은 확인했지만 성공 시 콤보 증가까지 명시적으로 구분하지 않아, 에이전트는 "유지 노트도 점수와 함께 콤보를 올리는 걸로 할까?"라고 물었다. 사용자는 "ㅇㅇ"라고 답했다(2026-10-25).

성공한 유지 표식 하나당 콤보를 1 올린다. 명시된 점수 노트에 기존 성공 규칙을 적용하며 표식 없는 바디 유지·종료에는 자동 콤보를 만들지 않는다. 더블의 각 표식도 각각 한 항목으로 처리하고, 유효한 이른 종료로 여러 표식을 함께 정산할 때 이미 정산한 항목을 다시 세지 않는다. 실패에 종속된 유지 노트는 기존대로 0점·원래 가중치만 정산하며 추가 Miss·콤보 단절을 만들지 않는다.

`docs/spec/scoring.md`의 확정 순서와 같은 timestamp·phase 묶음의 Miss 우선 규칙은 유지한다. 따라서 표식의 성공 콤보 기여를 추가하되 같은 확정 묶음의 Miss가 만든 콤보 단절을 취소하지 않는다. 일반 성공·회복 뒤 보류 해소·이른 종료 일괄 정산·부분 실패의 비중복 집계를 검증 계획에 포함한다. 고도 회복 등 다른 성공 효과는 이번 콤보 질문의 답으로 자동 확정하지 않으며 엔진 구현은 변경하지 않는다.

### 63. 유지 노트 성공도 일반 Perfect처럼 고도 계산에 참여

기존 확정 효과 처리(`src/game/judgment/confirmedJudgmentEffects.ts`)는 일반 성공과 Grace·기존 `holdOnly` 성공의 판정 등급을 고도 계산에 전달하고, 종속 0점에는 고도 효과를 만들지 않는다. 새 유지 노트가 이 성공 효과에도 참여하는지는 §62의 콤보 확인과 구별한다.

에이전트가 "유지 노트 성공도 일반 Perfect처럼 고도 계산에 반영할까?"라고 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-25). 유지 노트의 성공도 일반 Perfect와 같은 고도 계산 입력으로 전달한다. 명시된 표식의 배치 밀도가 회복 기회에도 영향을 준다는 대가를 포함한 결정이다. 표식 없는 바디 유지 자체에는 자동 회복을 추가하지 않으며 실패에 종속된 표식의 추가 손실 금지도 유지한다.

이번 결정은 성공 효과에 참여하는지에 한정한다. `flightRule`별 실제 회복량·시각 고도·실패 정책은 RFD 0022와 PRD §12에서 남겨 둔 별도 범위이며 옛 `Survival` 규칙을 새 난이도에 자동 승계하지 않는다. 정상 확인·회복 대기 뒤 성공·이른 종료 일괄 정산에서 성공한 표식마다 고도 입력을 한 번만 내고, 이미 처리한 항목과 종속 0점에는 다시 내지 않는지 검증한다. 엔진 구현은 변경하지 않는다.

### 64. 더블 릴리즈 성공 몫 숨김과 남은 몫 위치 보존

후속 §65의 비교 제안과 §66의 전체 알파 70% 확인으로 아래 반쪽 숨김 결정은 대체됐다. 아래는 당시 논의 기록이며 최종 표시 기준으로 사용하지 않는다.

에이전트가 "더블 릴리즈에서 한 몫이 성공하면 그 표식은 사라지고, 남은 한 몫만 원래 위치에 표시"하여 남은 뗌 요구를 읽을 수 있게 하자고 제안하자 사용자는 "ㅇㅋ"라고 답했다(2026-10-25).

성공한 릴리즈 몫의 표식은 성공 확정 시 숨긴다. 다른 몫의 판정 상태는 독립적으로 보존하며, 남은 표식은 더블에서 사용하던 원래 위치와 크기를 유지한다. 한 몫만 남았다고 가운데로 옮기거나 싱글 릴리즈 그림으로 바꾸지 않는다. 표시 좌우는 고정 물리 키 소유권이 아니다.

PR #339의 `331b5a6`에는 `release-double-unit-left.png`와 `release-double-unit-right.png`, 각 실패본과 SVG·2배 PNG가 이미 있다. 기본 200×40 좌표와 투명 여백을 보존한 분리 레이어이므로 성공한 몫을 숨기고 남은 몫만 그릴 수 있다. 이 결정에 새 일부 성공 도안을 추가 제작할 필요는 없다. 실제 스킨 등록과 렌더러 연결은 단계 7에서 진행한다.

이번 답으로 유지 노트의 성공 표시, 실패 몫의 표시 수명, Grace 외곽의 남는 범위까지 확정하지 않는다. 일반·Grace 릴리즈의 본체에서 성공한 몫 숨김을 검증하고, 늦은 릴리즈 기회가 남아 있는데 바디 완료를 근거로 전체 표식을 없애지 않는지 확인한다. 계획과 논의 기록만 갱신하며 게임 구현은 변경하지 않는다.

### 65. 더블 릴리즈 일부 성공은 전체 알파 50% 시안과 비교

사용자는 일부 성공과 일부 실패를 구별한 뒤 PR #339에 요청 댓글을 남기라고 했다. 댓글 게시 전에 "몫이 아니라 그냥 알파50 보이게 할까"라고 제안했다(2026-10-25). §64의 반쪽 숨김을 그대로 최종 요구로 게시하지 않고, 더블 릴리즈 전체 도안의 알파를 0.5로 낮추는 대안을 비교 시안으로 요청했다.

현재 일반 더블 `Point`는 일부 성공에 전체 alpha 0.7을 사용한다. 전체 반투명 방식은 기존 표현과 맞고 표시 좌우를 물리 키로 오해할 여지를 줄인다는 이유로 추천했다. 다만 0.5는 별도 수치이므로 바디 위 가독성을 실제 시안에서 확인한다. 일부 성공은 원래 색·모양·좌표를 보존하고 투명도만 낮추는 후보이며, 실패색과 좌우 일부 실패 처리를 섞지 않는다.

[PR 요청 댓글](https://github.com/nanana3679/not4k/pull/339#issuecomment-6390513121)은 대기 100%·일부 성공 50%·모두 성공 숨김을 반쪽 숨김 시안과 비교하도록 요청한다. 단색 배경과 바디 위에서 확인하고 정상 원본과 표시 alpha를 기록한다. 별도 반투명 PNG 제작은 요구하지 않는다. 댓글 기록(`pr339-partial-success-alpha-comment.json`)을 보관했다.

후속 업로드 `e2c846e`에서는 릴리즈 원본이 J2-C로 교체되고 일부 성공 시안의 알파가 0.7로 올라왔다. 자료 단위 테스트 9개·독립 정적 갤러리의 브라우저 검사 12개와 138개 에셋 재생성 일치를 확인했다(검증 기록(`pr339-e2c846e-review.json`)). 당시에는 사용자 확인 전이었으며, 후속 §66에서 70% 변경이 의도된 것이라는 답을 받았다.

50% 후보는 후속 §66의 70% 확인으로 대체했다. 실제 게임 구현은 변경하지 않는다. 기존 Point의 수치, 유지 노트·바디의 표시, Grace 외곽의 알파·범위와 실패 표시 수명도 이 제안으로 함께 바꾸지 않는다. 후속 결정 추적은 기존 PRD §12의 전환 항목을 따른다.

### 66. 더블 릴리즈 일부 성공은 전체 알파 70%

업로드된 `e2c846e`가 요청 댓글의 50%와 달리 70%를 사용하므로 의도적인 변경인지 묻자 사용자는 "ㅇㅇ 의도임"이라고 확인했다(2026-10-25).

더블 릴리즈에서 한 몫은 성공했고 나머지 입력을 기다리는 상태에는 정상 도안 전체 alpha 0.7을 적용한다. 원래 위치·크기·색·모양을 보존하고 표시 알파만 낮춘다. §64의 성공한 반쪽 숨김과 §65의 전체 50% 후보를 이 표시로 대체한다. 대기는 전체 alpha 1, 두 몫 모두 성공하면 숨김을 사용하며 별도의 반투명 PNG를 추가 제작하지 않는다.

이것은 릴리즈 본체의 일부 성공 표시다. 판정 상태를 하나로 합치거나 이미 성공한 몫을 다시 입력 대상으로 돌리지 않는다. 일부 실패, 성공과 실패가 함께 확정된 상태의 표시 수명, 유지 노트·바디의 표시와 Grace 외곽의 밝기·범위는 이 답으로 확정하지 않는다. 기존 일반 더블 Point의 alpha 0.7은 변경할 필요가 없다.

[PR #339 확인 댓글](https://github.com/nanana3679/not4k/pull/339#issuecomment-6390804166)에 의도된 변경임을 전달하고 문서·manifest·갤러리의 미확정 항목에서 이 본체 표시 결정만 구분해 달라고 요청했다. 최신 커밋의 단위 9개·브라우저 12개 및 재생성 일치 검증은 기록(`pr339-e2c846e-review.json`)을 따른다. 게임 구현은 변경하지 않았다.

### 67. Grace 일부 성공은 본체만 70%, 외곽 밝기는 유지

더블 릴리즈의 전체 알파 70% 확인 뒤 에이전트가 "일부 성공 때 본체만 70%로 낮추고, Grace 외곽은 원래 밝기를 유지"하자고 추천했다. 남은 릴리즈의 Grace 정보를 유지하며 기존 Point의 표현 방식과 맞추는 이유를 설명하자 사용자는 "ㅇㅋ"라고 답했다(2026-10-25).

Grace 더블 릴리즈에서 한 몫이 성공하고 나머지 입력을 기다리는 동안 정상 본체 전체의 표시 alpha는 0.7, 별도 Grace overlay의 표시 alpha는 원래 값으로 유지한다. 외곽은 전체 도안을 두르며 반쪽으로 자르지 않는다. 본체와 overlay를 같은 알파로 낮추거나 기존 합성 참고본 위에 overlay를 다시 겹치지 않는다. 외곽 에셋 내부의 번짐·투명도 자체를 불투명하게 만드는 뜻은 아니다.

두 몫 모두 성공하면 성공 노트 숨김에 따라 본체와 외곽을 함께 숨긴다. 일부 실패·성공과 실패가 함께 확정된 상태의 외곽 및 표시 수명까지 이 답으로 확정하지 않는다. 입력 자격·판정 창·점수·몫별 상태는 바꾸지 않으며 바디·유지 노트에는 Grace 표시를 추가하지 않는다.

기존 별도 overlay와 정상 본체를 그대로 사용할 수 있어 새 합성 에셋 제작은 필요하지 않다. [PR #339의 확인 댓글](https://github.com/nanana3679/not4k/pull/339#issuecomment-6390804166)을 갱신해 미확정 표기 정리와 Grace 일부 성공 미리보기 추가를 요청했다. 이전 커밋의 검증을 이 새 미리보기의 검증으로 취급하지 않으며, 후속 표시 검증에서 본체만 70%·외곽 원래 밝기·중복 합성 없음·모두 성공 뒤 외곽 잔존 없음을 확인한다. 게임 구현은 변경하지 않았다.

### 68. 별도의 바디 끝 마감 에셋은 불필요

PR #339의 최신 자료가 바디 마감과 릴리즈에 같은 J2-C 도안을 사용한다고 설명하므로, 에이전트는 릴리즈 없는 끝에서는 바디만 끝나게 하고 J2-C 그림은 명시된 릴리즈에만 사용하자고 추천했다. 사용자는 "ㅇㅇ 바디 끝 이라는 에셋이 필요 없지"라고 답했다(2026-10-25).

새 모델은 별도의 바디 끝 마감 에셋을 요구하지 않는다. 릴리즈가 없는 끝에는 바디 끝 마감 그림이나 릴리즈 그림을 붙이지 않는다. 명시된 릴리즈가 있으면 해당 노트가 자기 시각·종류·수·판정 상태에 따라 표시된다. 바디 끝에 릴리즈가 있다는 이유로 마감과 릴리즈를 두 번 겹쳐 그리지 않는다.

릴리즈 없음과 뗌 요구의 차이를 시각적으로 드러내기 위한 결정이다. 바디의 끝 시각·유지 판정·정상 완료나 실제 경계의 시작 자격을 없애거나 여러 바디를 병합하는 뜻이 아니다. 이미 확정한 바디 무점수와 릴리즈 입력·점수 계약은 유지한다.

J2-C 자료를 새 런타임에서 바디 끝 terminal과 릴리즈 양쪽에 연결하라는 이전 에셋 전달 지침은 정정한다. 정상·실패·일부 실패는 명시적 릴리즈의 상태로 연결한다. 자료의 `terminal-j2-*` 파일명은 원본 출처로 남길 수 있으며 원본·기존 런타임·보관본을 삭제하라는 요청이 아니다. 시작 마감은 당시 이 답의 범위 밖이었으며, 후속 §69에서 별도 마감 없이 바디만 시작하는 것으로 확인했다.

[PR #339 정정 댓글](https://github.com/nanana3679/not4k/pull/339#issuecomment-6390954414)에 역할·필수 상태 목록·README·manifest·Lab를 정리하고 릴리즈 없는 끝과 명시적 릴리즈가 있는 끝을 비교해 달라고 요청했다. 단계 7에서 바디 끝 장식의 자동 생성 없음·릴리즈 중복 합성 없음·노트 수에 따른 표시·실제 바디 경계 보존을 검증한다. 계획과 논의 기록만 갱신했으며 런타임은 변경하지 않았다.

### 69. 바디 시작도 별도 마감 없이 표시

바디의 정상 완료가 확정되면 즉시 숨긴다. 이른 정상 종료도 실제 완료 시점에 적용하며, 연결 바디만 원래 끝 시각까지 남기는 기존 표시 예외를 새 모델에 이식하지 않는다. 실제 바디 경계와 판정 상태·기회는 보존한다. 바디가 숨겨져도 명시 릴리즈가 아직 판정 대기 중이면 그 노트는 별도 상태와 판정 창에 따라 표시·판정한다. 바디 완료를 릴리즈 성공이나 실패로 대신하지 않는다.

이 답은 정상 완료 바디의 표시 수명이다. 더블의 일부 몫만 정상 완료됐을 때의 구성과 실패한 바디의 표시 수명까지 이 답으로 자동 확정하지 않는다. 실제 판정 코어와 렌더러는 아직 변경하지 않았다.

### 80. 더블 바디의 일부 정상 완료는 전체 알파 70%

더블 바디에서 한쪽만 먼저 정상 종료하면 해당 쪽만 숨기고 나머지를 남길지 묻자 사용자는 "70프로 알파로 남김"을 선택했다(2026-10-25).

한쪽 바디 몫만 정상 완료되고 다른 쪽이 아직 유지 중이면 전체 바디 도안을 alpha 0.7로 남긴다. 정상 완료한 쪽만 잘라 숨기는 방식은 쓰지 않는다. 두 몫 모두 정상 완료되면 §79에 따라 전체를 즉시 숨긴다. 이 표시 알파는 판정 코어의 바디 완료 상태를 기준으로 정하고, 릴리즈 성공 개수에서 추정하지 않는다. 릴리즈가 하나뿐인 double, 바디 완료 뒤 릴리즈 대기 등에서 두 항목의 상태를 구별한다. 기존 held/부분 실패 표현과 실패 바디의 표시 수명은 별도 상태로 다룬다.

### 81. 실패한 바디는 실패색으로 스크롤 밖까지 남김

실패한 바디를 실패색으로 남겨 남은 구간이 스크롤되어 화면 밖으로 나갈 때까지 표시할지, 더블 일부 실패면 해당 쪽에만 실패색을 적용할지 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-25).

실패한 바디는 즉시 숨기지 않고 실패색으로 표시하며 남은 구간이 화면 밖으로 스크롤될 때 제거한다. 더블 일부 실패는 실패한 쪽에만 실패색을 적용하고, 살아 있는 다른 쪽까지 실패색으로 바꾸지 않는다. 정상 완료 즉시 숨김(§79)과 일부 정상 완료 전체 alpha 0.7(§80)은 별도 상태로 구별한다. 한쪽 정상 완료·다른 쪽 실패의 혼합 상태 알파를 이 실패색·수명 결정만으로 확정하지 않는다. 표시가 남아 있다고 실패한 몫의 입력 기회·정산·Miss 효과를 다시 만들지 않는다.

### 82. 일부 실패는 절반 실패색·일부 성공은 전체 70%로 합성

더블 바디의 한쪽 정상 종료·다른 쪽 실패도 릴리즈에서 고른 B처럼 부분 실패 도안 전체 alpha 0.7로 남길지 묻자 사용자는 다음과 같이 정리했다(2026-10-25).

> 일부 실패는 절반이 실패색 일부 성공은 70퍼로 통일

일부 실패의 색과 일부 성공의 표시 alpha를 별도 상태로 합성한다. 실패한 쪽만 실패색으로 표시하며, 일부 성공이면 도안 전체에 alpha 0.7을 적용한다. 따라서 한쪽 정상 완료·다른 쪽 실패인 바디와 릴리즈 모두 실패한 절반의 색을 가진 전체 도안을 alpha 0.7로 남긴다. 모두 성공 시 숨김과 실패 표시 수명은 앞선 규칙을 따른다. Grace 릴리즈 외곽의 별도 alpha는 §78을 유지한다.

후속 질문에서 §76의 유지 노트 성공 쪽 숨김도 철회하고 전체 alpha 0.7로 통일할지 묻자 사용자는 "유지 노트는 색깔이아니라 개수로 나타나니까 예외"라고 설명했다. 따라서 유지 노트는 이 성공 알파 통일의 예외로, 성공한 표식만 숨기고 남은 표식의 밝기를 유지한다. 요구 수의 표현 방식이 다른 것이 이유이며, 실패한 유지 표식을 실패색으로 바꾸는 §75의 결정은 유지한다.

### 83. 바디 위 유지 노트는 바디의 hold 수에 맞춰 한 번에 배치

바디 위에 유지 노트를 찍으면 싱글 바디에는 표식 1개, 더블 바디에는 표식 2개를 한 번에 생성할지 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-25).

기존 바디 위의 유지 노트 배치는 그 위치에 소속되는 바디의 hold 수를 따른다. 싱글 1개·더블 2개 표식을 하나의 배치·취소·undo 단위로 생성한다. 기존 바디 내부나 합법적인 증가·감소 경계에 길이 0 바디를 중첩 생성하지 않으며, 경계 소속은 기존 뒤 바디 기준을 따른다. 바디 없는 빈 위치에서 길이 0 바디와 표식을 함께 생성하는 §41의 규칙은 별도로 유지한다. 이 답만으로 바디 사이를 이동할 때 표식 수를 자동 변경하는지까지 확정하지 않는다.

### 84. 유지 노트 이동 시 새 바디에 맞춰 표식 수 자동 변경

더블 바디의 유지 노트를 싱글 바디로 옮길 때 표식 수를 1개로 자동 변경할지, 2개를 유지한 채 불일치 빗금을 표시할지 물었다. 점수 항목 수도 2개에서 1개로 줄어드는 점을 설명하자 사용자는 "변경"을 선택했다(2026-10-25).

유지 노트가 다른 바디로 옮겨져 소속이 바뀌면 새 바디의 hold 수에 맞춰 표식 수를 자동 변경한다. 더블→싱글은 2→1, 싱글→더블은 1→2이며 점수 항목 수와 이론 가중치도 해당 수량을 따른다. 이전 표식 수를 고정해 정상 소속 관계에 개수 불일치 위반을 남기지 않는다. 소속은 여전히 레인·Beat에서 도출하고 제작자에게 소속 ID나 수량 수리를 요구하지 않는다. 바디 밖으로 옮긴 표식의 수리 가능한 의미 위반과, 단순 이동 때 새 길이 0 바디를 임의 생성하지 않는 기준은 유지한다. 이 답이 저장 스키마의 수량 필드 유무까지 확정하는 것은 아니다.

### 85. 빈 위치의 유지 노트는 싱글 생성·길이 0에서 재클릭하면 더블

바디가 없는 빈 위치에서 유지 노트를 생성할 때 싱글·더블을 선택하게 할지 묻자 사용자는 다음과 같이 결정했다(2026-10-25).

> 싱글만 생성하고 (길이0 유지노트에) 한번 더누르면 더블로변경

유지 노트를 배치하는 상태에서 빈 위치를 클릭하면 길이 0 싱글 바디와 유지 표식 1개를 함께 생성한다. 같은 길이 0 싱글 유지 노트를 다시 클릭하면 기존 길이 0 바디를 더블로 바꾸고 유지 표식을 2개로 함께 변경한다. 유지 표식 수와 바디 hold 수는 일치해야 하므로 표식만 늘려 두지 않는다. 중복 바디나 중복 유지 노트 엔티티를 추가하지 않으며, 변경은 하나의 undo 단위다. 일반적인 재클릭 조작이며 별도의 빠른 더블클릭 시간 조건을 이 답에서 요구하지 않는다.

이 규칙은 길이 0 유지 노트의 생성·변경 조작에 한정한다. 양수 길이 바디의 hold 수를 표식 재클릭으로 바꾸는 규칙으로 확대하지 않는다. Select 모드에서 표식을 클릭하면 표식만 선택하는 앞선 규칙도 유지한다.

후속 질문에 사용자는 "토글까지는 안해도 될듯"이라고 답했다. 이미 더블인 길이 0 유지 노트를 다시 클릭해도 더블 상태를 유지한다. 싱글로 되돌리는 토글·중복 항목 생성·변경 없는 undo 기록은 만들지 않는다.

### 86. 과도기에는 구형·신형 혼합 차트도 저장 허용

기존 모델·에디터 제안은 구형 노트가 남으면 새 형식 저장까지 막아, 두 구형 롱노트 중 하나만 수정한 상태를 저장하고 나중에 이어갈 수 없었다. 구형·신형이 섞인 수정 중 차트도 저장은 허용하고 인게임 재생만 막을지 묻자 사용자는 "ㅇㅋ"라고 답했다(2026-10-25).

과도기에는 혼합 상태를 손실 없이 저장·재불러와 수리를 계속할 수 있어야 한다. 미수정 구형 항목의 끝점·`holdOnly` 의미와 사람이 새로 만든 바디·Point·릴리즈·유지 노트의 의미, 메타데이터와 main/aux 자료를 보존한다. 저장하려고 나머지 구형 항목을 자동 변환하거나 버리지 않는다. 구체적인 버전·필드·저장 표현은 구현 선택이다.

구형 노트가 하나라도 남으면 새 compiler/인게임 재생은 막는다. 구형 항목의 존재 자체와 실제 배치 위반은 구별하며, 앞서 정한 바디 밖 유지 표식·바디 내부 릴리즈 등 의미 위반의 저장·플레이 제한은 유지한다. 구형 항목이 남으면 저장까지 막는 이전 검토 제안은 이 결정으로 대체한다. 과도기 종료 시점과 관리 대상 차트의 범위는 앞선 결정대로 사용자가 정한다.

### 87. 구형 노트 구별용 별도 표시는 추가하지 않음

혼합 차트에서 수리할 구형 노트를 찾도록 작은 "구형" 표시를 붙일지 묻자 사용자는 "표시 안해도됨"이라고 답했다(2026-10-25).

구형 노트임을 드러내기 위한 별도 배지·라벨·강조·빗금은 추가하지 않는다. 구형 노트 자체를 숨기거나 새 의미로 추정 변환하는 결정은 아니며, 기존 읽기·표시·선택·편집과 저장 왕복의 의미 보존은 유지한다. 실제 배치 위반의 빗금 등 기존 진단 표시도 유지한다. 구형 노트의 존재에 따른 새 인게임 재생 차단은 별도 표시 없이도 적용한다.

### 88. 미선택 바디의 끝 핸들도 연결 항목을 함께 선택

현행 에디터는 미선택 바디의 끝 핸들을 바로 잡으면 바디만 선택하므로, 새 모델에서도 그대로 적용하면 끝 릴리즈가 따라오지 않는다. 이때도 바디 클릭처럼 연결 항목을 함께 선택해 끝 릴리즈가 따라오게 할지 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-25). 이미 선택한 바디에서 릴리즈를 의도적으로 제외한 경우에는 제외를 유지한다는 조건도 함께 확인했다.

미선택 바디의 끝 핸들로 리사이즈를 시작할 때 바디·같은 시작점 Point·소속 유지 표식·끝점 릴리즈를 함께 선택한다. 선택된 끝 릴리즈는 리사이즈 끝점을 따라간다. 이미 선택된 바디의 핸들을 잡을 때는 현재 선택 집합을 다시 확장하거나 바디만으로 교체하지 않는다. 마우스·터치의 동일 조작에 같은 원칙을 적용한다.

시작 Point·내부 유지 표식은 선택되어 있어도 끝점 리사이즈로 비례 이동하지 않는다. 유지 표식을 밖으로 내보내는 축소 차단과 선택에서 제외한 릴리즈의 원래 위치 유지 등 기존 리사이즈 규칙은 그대로 적용한다. 이는 새 모델의 계획이며 현행 코드의 리사이즈 동작을 이번 논의 기록만으로 수정하지 않는다.

### 89. 미선택 바디의 직접 삭제도 연결 항목과 함께 처리

선택 없이 우클릭·삭제 모드로 바디를 바로 지울 때 시작 Point·유지 표식·끝 릴리즈까지 함께 지우고, 개별 노트를 직접 지우면 그 노트만 대상으로 할지 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-25).

미선택 바디의 직접 삭제는 바디 클릭의 동반 선택과 같은 범위를 하나의 편집으로 삭제한다. 바디·같은 시작점 Point·소속 유지 표식·끝점 릴리즈가 대상이며, 유지 표식을 먼저 제거한 뒤 바디를 제거한다. 바디 중간 Point나 다른 바디의 항목은 포함하지 않는다. 개별 Point·유지 표식·릴리즈를 직접 지우는 경우에는 해당 노트만 대상으로 한다. 더블 노트는 기존 결정대로 전체가 한 삭제 단위다.

이 답은 미선택 바디의 직접 삭제를 확인한 것이다. 선택된 바디에서 의도적으로 제외한 항목을 삭제 집합에 다시 추가하는 승인으로 확대하지 않는다. 기존의 유지 표식 잔존 시 바디 삭제 차단·잘라내기 사전 검사는 유지한다. 새 모델의 계획에 반영하며 이번 기록만으로 현행 코드의 직접 삭제를 변경하지 않는다.

### 90. 선택된 바디 우클릭은 클릭한 바디 쪽만 삭제

### 100. 시작 Point를 처리한 재누름 예외를 싱글 바디의 더블 릴리즈에도 적용

§99로 건강한 승계의 실제 시작을 재확인한 뒤 [같은 키 재사용 설계 그림](https://share.onorca.dev/a/N2DF8Bd0B5DK)을 제시했다. N4는 싱글 바디, N5는 그 끝의 더블 릴리즈다. A의 첫 뗌 1010ms로 N5의 한 릴리즈를 처리한 뒤 A를 1020ms에 다시 눌러 N3 Point를 처리하고, 1060ms에 다시 떼는 입력이다.

싱글 바디에서도 이 재누름을 근거로 같은 A로 남은 릴리즈를 처리하도록 기존 예외를 확대할지 묻자 사용자는 "ㅇㅇ"라고 답했다(2026-10-25). 해당 바디의 시작 Point를 실제로 처리한 재누름이면 싱글 바디에 붙은 더블 릴리즈에도 같은 키 재사용을 허용한다.

§27에서 double 바디로 한정해 기록했던 예외의 범위를 위 조건으로 확장한다. 임의의 재누름·다른 바디의 Point·어떤 Point든 성공하면 재사용 허용으로 넓히지 않는다. 한 up은 한 릴리즈만 처리하며, 실제 바디 시작·유지 실패 종속·허용 창은 그대로 적용한다. 이미 정상 완료한 N4를 다시 시작시키거나 유지 점수를 추가하지 않는다. double 바디의 두 유지 몫을 한 키로 채우도록 바꾸는 결정도 아니다.

원본은 `cases/same-key-single-body-double-release-design.json`과 PNG이며, 질문 시점의 설계 그림을 보존한다. 창 수치는 설명용이고 엔진을 실행한 검증 결과는 아니다. 이 사례의 같은 키 자격 기대값을 공식 규칙 반영과 새 모델 회귀 테스트로 옮긴다.

### 101. 유지 노트 성공에도 Perfect 판정 글자 표시

에이전트가 유지 노트의 타이밍 평가 부재와 다른 판정의 표시를 덮을 가능성을 이유로 Perfect 글자를 생략하자고 추천하자, 사용자는 "띄워야지"라고 답했다(2026-10-25). 생략 제안은 채택하지 않는다.

유지 노트도 성공 확정 시 Perfect 판정 글자를 표시한다. 정상 유지 중 표식 시각의 성공뿐 아니라 시작·회복 대기 뒤의 성공과 유효한 이른 종료의 남은 표식 일괄 성공에도 적용한다. 성공을 기다리는 미확정 상태에서 먼저 표시하지 않으며, 이미 처리한 표식이나 표시 상태 복구로 같은 성공 효과를 재실행하지 않는다.

점수·콤보·고도·표식 숨김의 기존 결정은 유지한다. 유지 노트에 타이밍 오차·FAST/SLOW를 추가하지 않고, 바디 실패에 종속된 0점 정산에는 별도 Miss 글자나 성공 글자를 만들지 않는다. 이 기록은 표시 계약이며 새 엔진의 실행 검증 결과가 아니다.

### 102. 같은 확정 시각의 판정 글자는 낮은 등급 우선

유지 Perfect와 다른 항목의 Good 등이 같은 확정 시각에 나오는 경우, 현행 코드처럼 마지막 처리 결과로 덮어쓰는 대신 낮은 등급을 대표 글자로 표시하자고 추천했다. 사용자는 "ㅇㅋ"라고 답했다(2026-10-25).

같은 확정 시각의 표시 대상 중 가장 낮은 등급을 대표 판정 글자로 표시한다. 예를 들어 Perfect와 Good이 함께 확정되면 Good을 표시한다. 유지 노트만의 예외가 아니라 같은 시각의 판정 표시에 공통 적용한다. 바디 실패에 종속된 0점 정산은 기존처럼 별도 판정 글자의 후보가 되지 않는다.

이는 대표 글자를 고르는 규칙이다. 각 항목의 점수·통계·콤보·고도·성공/실패 상태 정산을 합치거나 생략하지 않으며, 서로 다른 확정 시각을 프레임 단위로 묶거나 새 시간 허용 폭을 만들지 않는다. 같은 확정 시각의 후보 수신·호출 순서가 달라도 대표 등급이 달라지지 않아야 한다. 이후 확정 시각의 글자는 정상적으로 갱신할 수 있다. 유지 노트의 타이밍 오차·FAST/SLOW 비표시도 유지한다.

회귀 검증에는 동시 Perfect/Good·성공/Miss와 종속 0점 제외, 후보 순서 변경, 서로 다른 확정 시각의 표시 갱신을 포함한다. 현재 구현은 변경하지 않았으며 공식 규칙 반영과 새 표시 경로 구현 때 테스트로 옮긴다.

### 103. 유지 노트 성공에도 일반 레인 타격 이펙트 표시

유지 노트가 성공한 위치를 알 수 있도록 일반 노트와 같은 레인 타격 이펙트를 내자고 추천하자, 사용자는 "ㅇㅇ"라고 답했다(2026-10-25).

유지 노트 성공 확정에도 해당 레인의 일반 타격 이펙트를 표시한다. 정상 유지 중 확인, 시작·회복 대기 뒤 성공, 유효한 이른 바디 종료에 따른 남은 표식의 일괄 성공을 포함한다. 기존 스킨과 타격 이펙트 설정을 따르며, 판정선 위치·리프트 등 일반 노트의 이펙트 배치 규칙을 함께 사용한다.

아직 확정되지 않은 시작·회복 대기에서 먼저 성공 이펙트를 내지 않는다. 바디 탈락에 종속된 0점 정산과 이미 처리한 항목의 재조회·표시 상태 복구도 새 성공 이펙트를 만들지 않는다. 대표 판정 글자의 등급 선택은 §102를 따르며, 대표 글자 선택 때문에 개별 유지 성공의 점수·콤보·고도·타격 이펙트를 없애지 않는다. 판정·효과 경로 구현 때 회귀 검증으로 옮기며 현재 게임 구현을 변경한 기록은 아니다.

### 104. 같은 대표 등급의 타이밍 표시는 실제 입력의 큰 절대 오차 우선

같은 시각·같은 등급끼리 겹칠 때 타이밍 정보가 있는 실제 입력을 우선하고, 여러 개면 절대 오차가 큰 입력을 FAST/SLOW 표시에 사용하자고 추천했다. 사용자는 "ㅇㅋ"라고 답했다(2026-10-25).

먼저 §102에 따라 같은 확정 시각의 가장 낮은 대표 등급을 고른다. 그 등급의 후보 안에서 타이밍 표시가 허용된 실제 입력을 우선하고, 그런 입력이 여러 개면 raw 타이밍 오차의 절대값이 가장 큰 입력을 사용한다. 더 높은 등급의 큰 오차를 끌어와 대표 글자와 결합하지 않는다. 타이밍 차이 수치 표시를 켠 경우도 같은 입력의 오차를 사용한다.

유지 Perfect나 Grace처럼 타이밍 표시를 만들지 않는 후보가 함께 있다고 실제 입력의 타이밍 표시를 지우지 않는다. 반대로 대표 등급에 표시 가능한 타이밍 정보가 없으면 FAST/SLOW와 타이밍 수치를 새로 만들거나 다른 등급에서 빌려 오지 않는다. 오차 0인 실제 입력도 타이밍 정보가 있는 입력이며, FAST/SLOW의 기존 표시 임계값과 사용자 표시 설정은 유지한다. 각 항목의 타이밍 통계는 대표 표시 선택과 별개로 정산한다.

회귀 검증에는 유지/일반 Perfect 동시 확정, 같은 등급의 서로 다른 절대 오차, 대표 등급 밖 후보 제외, Grace·유지의 표시 제외와 각 항목의 통계 보존을 포함한다. 같은 절대 오차의 동률을 안정적으로 고르는 구체적인 방식은 구현에서 정한다. 현재 게임 코드 변경이나 실행 검증은 아니다.

## 구현 계획에 주는 영향

- 같은 확정 시각의 대표 등급 안에서 표시 가능한 실제 입력의 타이밍을 우선하고, 여러 개면 가장 큰 절대 오차를 사용한다(§104). 유지/Grace 후보로 실제 입력의 표시가 지워지지 않고 다른 등급의 오차가 섞이지 않는지 검증한다. FAST/SLOW 임계값·설정과 항목별 통계는 보존한다.

- 유지 노트 성공에도 해당 레인의 일반 타격 이펙트를 전달한다(§103). 정상 확인·대기 뒤 성공·이른 종료 일괄 성공, 기존 스킨·효과 설정 적용, 미확정 상태·종속 0점·표시 복구의 효과 비재생을 검증한다.

- 같은 확정 시각의 대표 판정 글자는 낮은 등급을 우선한다(§102). 종속 0점은 후보에서 제외하고, 표시 후보 순서·호출 분할에 따라 대표 등급이 바뀌지 않는지 검증한다. 각 항목의 기존 정산과 서로 다른 확정 시각의 표시 갱신은 보존한다.

- 유지 노트의 성공 확정에도 Perfect 판정 글자를 전달한다(§101). 정상 확인·대기 뒤 성공·이른 종료 일괄 정산에서 표시하고, 미확정 상태·종속 0점·이미 정산한 표식의 중복 표시를 막는다. 타이밍 오차·FAST/SLOW는 만들지 않는다.

- 중간 재생은 §71의 새 재생 흐름에서 별도로 설계한다. 현행 커서 앞 바디 제외와 종속 노트 동반 제외를 새 모델의 고정 계약이나 공통 모델 착수 조건으로 삼지 않는다.

- 실패 확정된 릴리즈는 실패색으로 스크롤되어 화면 밖까지 남긴다(§70). 종속 0점도 같은 표시 수명을 따르며, 화면 잔존이 입력 기회 복구나 추가 판정 효과를 만들지 않는지 검증한다. 미확정 상태와 더블의 성공·실패 혼합 합성은 구별한다.

- 별도 바디 시작·끝 마감 에셋과 새 terminal 상태 연결을 구현 목록에서 제거한다(§68·§69). 바디 자체만 시작·끝나며 명시된 Point·릴리즈·유지 표식만 자기 상태로 그린다. 뒤집은 시작 마감·바디 끝 장식의 자동 생성이나 노트 이중 합성 없이 실제 경계를 보존하는지 검증한다.

- Grace 더블 릴리즈의 일부 성공은 본체 전체 alpha 0.7과 원래 밝기의 전체 외곽을 조합한다(§67). 부모 알파로 외곽까지 흐려지거나 overlay를 중복 합성하지 않는지 검증하고 모두 성공하면 본체와 외곽을 함께 숨긴다.

- 더블 릴리즈는 대기 전체 alpha 1 → 한 몫 성공·나머지 대기 전체 alpha 0.7 → 모두 성공 숨김을 표시한다(§66). 본체의 위치·크기·색·모양과 바디의 알파를 보존하고, 한 몫 성공이 다른 몫의 판정 기회를 종료하지 않는지 검증한다. 실패한 릴리즈의 표시 수명은 §70을 적용한다. 성공·실패 혼합은 부분 실패 도안 전체 alpha 0.7이며 Grace 외곽은 본체가 보이는 동안 전체 원래 밝기로 유지한다(§77·§78·§82).

- 유지 노트 성공을 일반 Perfect와 같은 고도 계산에 한 번씩 전달한다. 여러 표식의 일괄 정산·부분 실패·재정산 방지를 검증하고 표식 없는 바디의 자동 회복과 종속 0점의 추가 고도 손실을 만들지 않는다.

- 유지 노트 성공마다 콤보 기여 1회를 반영한다. 정상 확인·회복 대기 뒤 성공·이른 종료 일괄 정산·더블 일부 실패를 대조하고, 이미 처리한 표식의 재집계와 종속 0점의 추가 콤보 이벤트를 막는다. 공통 확정 순서와 같은 묶음의 Miss 우선도 유지한다.

- 구형 파일을 에디터에서 열어 사람이 수정할 수 있도록 읽기·편집 호환을 유지한다. 원본 정보 보존, 새 규칙 위반의 수정 가능성, 일부만 수리한 구형·신형 혼합 상태의 저장 왕복(§86)을 검증한다. 구형 항목의 존재로 인한 새 플레이 차단과 실제 배치 위반의 저장 제한을 구별한다. 사람 대신 노트 배치를 결정하는 자동 처리·일괄 변환은 제외하며 새 포맷 검증과 개발용 예제 갱신은 유지한다.

- 트릴 바디 위 유지 노트는 금지 배치로 검증한다. 트릴 전용 유지 노트를 추가하지 않고, 일반 single·double 바디와 허용된 증가·감소 위치의 유지 표식과 구별한다.

- 유지 노트는 1→1·2→2의 실제 연결점에서 금지하고 한 바디 내부·독립 길이 0·1→2·2→1에서는 허용한다. 증가·감소의 표식 수와 뒤 바디 기준을 유지한다. §55의 배치를 합법 판정 사례로 구현하지 않으며, 표식 없는 경계와 정상 분리 연주를 임의로 병합하지 않는다.

- 유지 노트만의 ±Good 창·기한과 창 안 down에 의한 미래 표식 선판정을 구현하지 않는다. 표식 시각의 바디 상태, 시작 판정·유지 유예의 결과 대기, 유효한 이른 종료 정산을 사용한다. 길이 0·늦은 시작·몫별 실패와 이미 정산한 점수의 보존을 검증한다.

- single Point Miss와 별개로 뒤 double의 다른 한 몫이 미리 누른 hold로 차트상 시작 시각에 새로 시작하는지 검증한다. Point Miss로 그 몫을 취소하거나 시작을 지연하지 않으며, 시작 뒤에는 일반 유지 규칙을 적용한다. Point 몫의 종속 실패와 추가 바디 Miss 방지, 앞의 확정 실패 보존을 대조한다.

- single Point가 있는 double→double에서 앞의 전체 탈락과 무관하게 뒤 두 몫이 각자 시작할 수 있는지 검증한다. Point 하나로 두 몫을 자동 충족시키거나 이미 탈락한 뒤 몫을 복구하지 않으며, Point가 맡는 몫의 시작 시점과 다른 몫의 조건·기존 유지 유예를 보존한다.

- Point·릴리즈 없는 2→1 감소 위치에는 뒤 single 기준의 유지 표식 하나를 둔다. 감소 전 정상·일부 탈락·전체 탈락에서 건강한 몫의 승계와 전체 탈락의 종속 0점을 대조한다. 끝나는 몫의 표식·릴리즈 자동 생성이나 경계 표식의 중복 정산, 표식에 의한 재시작을 막는다.

- 1→2 증가 위치의 유지 표식 두 개를 뒤 double의 몫별 상태로 정산한다. 앞 single의 탈락·이른 종료에 잘못 종속시키지 않으며 뒤 시작 조건, 표식의 중복 정산 방지, 같은 위치의 다른 노트 의미 중첩 금지를 함께 검증한다.

- Point 없는 double→double의 릴리즈 하나인 경계에서는 뒤 두 몫 전체의 새 시작을 검증한다. 앞 double의 정상·일부 탈락·전체 탈락을 대조하고, 앞 릴리즈의 소멸한 기회와 확정 결과는 보존한다. 릴리즈 수와 뒤 바디의 새 시작 가능 몫 수를 같은 값으로 처리하지 않는다.

- 릴리즈만 놓인 single→single에서는 앞 탈락·릴리즈 종속 0점을 유지하면서 뒤 single의 새 시작을 허용한다. 릴리즈의 up과 뒤 바디의 hold 조건을 각각 검증하며, 새 down 강제·정확한 동시 입력·숨은 Point를 추가하지 않는다. 이 결정을 2→1 감소나 double의 일부 릴리즈 경계로 일반화하지 않는다.

- Point 없는 2→1 감소의 정상·일부 탈락·전체 탈락을 대조한다. 두 몫 탈락 뒤 single 재시작은 막고 한 몫 탈락 시 건강한 몫의 승계는 유지한다. 앞 탈락 뒤 새 시작을 허용하는 1→2 증가와 다른 기대값을 고정한다.

- 같은 hold 수의 Point·릴리즈 없는 연결에서는 탈락 뒤 재누름 복구를 막되, 1→2 증가에서는 뒤 double 전체의 새 시작을 허용하는 차이를 검증한다. 합법 위치의 유지 표식 유무에 따른 바디 동작 차이를 만들지 않으며 뒤 double의 두 몫 시작 조건과 앞 탈락·종속 정산의 불번복을 함께 대조한다.

- 같은 hold 수의 표식 없는 단순 연결의 탈락 공유·재누름 복구 금지를 반영한다. 그 연결점의 유지 노트는 §57에 따라 금지하고, 한 바디 내부 등 합법 위치의 표식만 추가·제거하여 바디 판정 불변을 대조한다. §44·§55의 유지 노트 연결 배치를 합법 판정 사례로 구현하지 않는다.

- 독립적인 길이 0 바디와 유지 표식도 일반 선택 규칙을 따른다. 표식 클릭은 표식만, 바디 클릭은 둘을 선택하며, 이동·복사는 선택 집합만 대상으로 한다. 위치 기반 소속·위반 표시·undo/redo·저장 왕복을 검증한다. 표식만 삭제하면 길이 0 바디를 남기고 자동 제거하지 않는다.

- 빈 위치의 유지 표식 생성은 길이 0 바디와 표식을 함께 만든다. 한 번의 배치와 undo/redo·저장 왕복에서 두 항목의 관계를 보존하며, 기존 바디 내부나 경계의 배치와 구별해 검증한다.

- 유지 표식 자체의 직접 선택·이동·삭제와 바디 유닛의 이동·복사·삭제에 따른 소속 표식 동반을 지원한다. 증가·감소 경계의 뒤 바디 기준, 같은 hold 수 연결점과 트릴 바디 위의 표식 금지를 적용한다. 표식을 앞뒤 양쪽에 자동 귀속시키지 않으며 저장 스키마는 이 편집 관계와 구별해 정한다.

- PR #338의 유지 노트 계약·바디 소속·저장·컴파일·세션·표시·편집·이행을 계획에 포함한다. 같은 바디 판정·입력 미소비와 Perfect 정산, 회복 대기·이른 종료 일괄 정산을 반영한다. 유지 노트 자체의 창과 선판정은 §56에 따라 폐지하고, §34의 릴리즈 창 공유·§35의 Good 예외 제거·§36의 입력 공유는 유지한다. 배치·저장·더블 새 시작 연결을 구체화하고 바디 무점수·`holdOnly` 폐지·Grace 실제 뗌은 유지한다.

- Point가 있는 double에서 아직 시작하지 않은 몫의 시작 창과, 한 번 시작한 몫의 유지 유예를 구별한다. Point가 맡지 않는 몫에 시작 창 끝까지의 재충전을 임의로 추가하지 않으며, Point 없는 바디에 이미 허용한 재충전은 유지한다.

- 릴리즈 없는 짧은 double에서 서로 다른 두 키의 시차 입력과 같은 키의 반복 입력을 대조한다. 시작·끝 창이 겹쳐도 같은 키로 두 몫이 완료되지 않아야 하며, 바디 무점수·실제 시작 필요·고정 키 소유권 없음과 함께 검증한다.

- 바디 시작 후보가 Point와 down 소비를 경쟁하는 구현 항목을 제거한다. 바디는 실제 hold 수를 관찰하고 Point가 down을 소비한다.
- 같은 down이 Point 판정과 hold 수 충족에 함께 참여할 수 있음을 보존한다. 철회한 추가안의 Point 미판정·Miss 기대값을 구현하지 않는다.
- 연결 head 주변 up의 자동 소비를 제거한다. Point 탭·교대의 적격 up이 명시된 릴리즈를 처리하는 경우와, 릴리즈 없는 연속 접점의 Point 성공만 콤보를 1 올리는 경우를 새 모델의 회귀 검증에 포함한다. 옛 연결 release 점수나 소비 대상을 자동 생성하지 않는다.
- 같은 레인·같은 시각의 서로 다른 노트 의미를 새 차트의 의미 검증에서 금지한다. Point+릴리즈, Point+유지 노트, 릴리즈+유지 노트를 대조하고, 같은 의미의 더블과 바디 위 노트의 합법 배치와 구분한다. 사람이 수정한 차트 검증에서 충돌을 보고하며 에디터 저장·플레이 검증과 관련 사례 명세에 같은 제약을 적용한다.
- 실제 시작·종료 시각, 연속 구간의 유지 실패, 명시적 릴리즈와의 관계는 새 차트 표현에서 검증한다. down 소비 철회로 시작 시각 문제까지 자동 해결됐다고 간주하지 않는다.
- head 없는 독립 single·double은 시작 창 안의 새 down 시각에 hold 수로 충족하는 몫을 시작하며 down 소비를 추가하지 않는다. 끝 창만으로 시작 범위·실패 기한을 확장하지 않는다. 시작 창 밖의 down도 실제 hold에는 반영하므로 기존 미리 누른 키의 참여 규칙과 구별해 검증한다.
- head 없는 1→2에서도 시작 창 안의 새 down에 따른 추가 몫의 즉시 시작과, 창 전부터 계속 누른 두 키에 따른 증가 시각의 시작을 구분해 검증한다. 추가 몫이 실제로 시작한 뒤 자기 끝 창 안에서 일찍 종료하는 경우와 미시작 종료 금지를 함께 확인한다.
- 1→2에서 앞 바디를 이어받는 연주와 앞 바디를 끝내고 뒤 double을 따로 시작하는 연주를 모두 대조한다. 앞 single 실패를 이유로 뒤 double의 새 시작을 한 몫으로 제한하지 않으며, 앞 바디의 실패 취소와 뒤 바디의 새 시작을 별도로 검증한다. 기존 RFD 0032 §8-2의 경계 연주를 누락하지 않는다.
- 같은 hold 수·Point 없음·릴리즈 없음이어도 실제 바디 끝과 다음 시작의 경계를 보존한다. 저장 왕복·컴파일·편집이 경계를 합쳐 시작 기회를 지우지 않는지와, 앞 끝 창·뒤 시작 창에서 나누어 치는 연주를 검증한다. 바디 경계만으로 down·up 소비나 점수 항목을 추가하지 않는다.
- 짧은 double의 시작 창 안 두 입력이 조금 다른 시각에 들어와도 충족한 몫을 시작하는지 검증한다. 끝 창 안이지만 시작 창 밖인 down의 즉시 시작 금지, 이미 누른 키의 참여, 실제 시작 뒤의 이른 종료, 미시작과 유지 실패를 각각 구별한다.
- 연결된 릴리즈는 실제 시작한 몫만 후보로 삼는다. 미시작 몫의 끝 창 안 up으로 릴리즈 성공·바디 완료가 발생하지 않는지 검증하고, 실제 시작 후의 이른 성공·정상 완료 후 늦은 성공·유지 실패 후 기회 소멸을 각각 대조한다. 옛 미시작 종료 기대값을 새 모델에 남기지 않는다.
- 릴리즈 없는 바디의 이른 종료에는 실제 시작 여부를 대조한다. 차트상 시작 전이라는 이유로 이미 시작한 바디의 종료를 막지 않으며, 아직 시작하지 않은 바디까지 끝 창의 up만으로 완료시키는 추가안은 구현하지 않는다.
- 바디 정상 완료와 릴리즈 정산을 별도로 표현한다. 차트상 끝 이후에는 완료한 바디의 hold 유지 실패를 새로 만들지 않고, 남은 릴리즈의 up·기한만 처리한다. 정상 완료 후 늦은 up 성공·릴리즈 누락과 기존 유지 실패의 기회 소멸을 구분해 검증한다.
- 같은 종류의 끝 릴리즈 두 몫이 연결된 double의 일부 유지 실패는 릴리즈 한 몫만 닫는다. 남은 한 몫의 성공·누락, hold 회복 후 실패 몫 복구 금지, 종속 0점의 비중복 정산을 회귀 검증에 포함한다.
- 2→1 감소 전 일부 실패에서는 건강한 몫이 뒤 single로 이어지고 감소 지점의 릴리즈만 종속 0점이 되는지 검증한다. 감소 지점의 릴리즈를 정상 판정한 뒤 이어지는 몫이 실패한 경우에는 이미 확정한 앞 릴리즈를 되돌리지 않는지도 대조한다. 릴리즈를 생략한 끝에는 정산할 항목이나 입력 요구를 추가하지 않는다.
- double 바디와 끝 릴리즈 한 몫의 조합을 차트 검증·저장 왕복·컴파일·에디터·AutoPlayer에서 보존한다. 두 키 정상 유지 후 끝에서 한 번만 떼고 다른 키를 계속 유지하는 연주를 검증한다. 릴리즈 두 몫으로 자동 보충하지 않는다. 한 몫 실패 후 릴리즈 성공·누락, 두 몫 실패 시 기회 소멸·종속 0점 비중복 정산, 재누름으로 실패를 복구하지 않는 동작을 검증한다.
- 더블 릴리즈의 종류를 두 몫에 공통으로 적용하고 일반·Grace 혼합을 허용하지 않는다. 차트 검증·저장 왕복·에디터의 종류 변경에서 이 제약을 보존하며, 일부 실패 후에도 남은 몫의 종류·등급 규칙이 바뀌지 않는지 검증한다.
- 일반·Grace 릴리즈가 누름 Good의 이른 쪽·늦은 쪽 최대 허용 폭을 공유하도록 구현한다. 양쪽 경계 안·경계와 같은 시각·경계 밖의 자격과 Grace Perfect·FAST/SLOW 제외를 함께 검증한다.
- 일반 릴리즈의 Perfect·Great·Good 창을 누름의 해당 등급 창과 같게 구현한다. 등급별 경계와 Grace 최대 허용 폭·릴리즈 없는 바디의 이른 종료 폭 공유를 함께 검증한다. 철회한 확대 값을 이식하지 않는다.
- 일반 릴리즈의 세 등급 창을 앞뒤 대칭으로 정의하고 같은 크기의 양수·음수 오차가 같은 등급인지 검증한다. 일반 릴리즈의 FAST/SLOW 방향 구분과 Grace의 집계 제외는 유지한다.
- 더블 릴리즈 일부 실패 에셋과 릴리즈 상태 전달을 표시 단계에 포함한다. 바디의 `held`나 전체 실패 여부만으로 릴리즈 전체를 표시하지 않으며, 일반·그레이스 릴리즈에서 모두 부분 실패와 남은 판정 가능 상태를 확인한다. RFD 0028의 기존 원칙에 따라 켜짐 효과가 없는 스킨에서도 부분 실패 표시를 검증한다.
- 구형 차트의 모든 경계·기대 점수를 그대로 옮기지 않고, 차트 구조 → 실제 시작·끝 → 입력 배정과 판정 순서로 사례를 대조한다.
