# Pull request workflow

에이전트가 만든 PR은 사람이 무엇을 반드시 읽어야 하는지 드러내고, 머지 전에 그 내용을 사람이 실제로 이해했는지 대화로 확인한다. 자동 리뷰가 통과하거나 "읽었다"는 답을 받아도, 사람이 핵심 변경을 이해하지 못한 채 머지되는 일을 막기 위한 절차다.

## 리뷰 중요도

PR 본문에 `리뷰 중요도` 절을 두고 변경 파일을 세 등급으로 나눈다.

| 등급 | 기준 | 사람의 리뷰 |
| --- | --- | --- |
| 필수 | 실제 게임·에디터 동작을 바꾸는 코드, 저장 데이터·스키마·권한, 빌드·배포 설정(`vite*.config.ts`, 의존성, `.github/workflows`), 여러 모듈이 쓰는 타입·공유 모델, 제품 결정 문서(`docs/rfd/`, `docs/context/`) | 줄 단위로 읽는다 |
| 권장 | Lab·dev 전용 코드, 스크립트·도구, 테스트, 스펙 문서 | 무엇을 바꾸고 검증하는지 훑어본다 |
| 생략 가능 | 생성물·보관본·시안, 테스트로 검증되는 고정 데이터, 잠금 파일의 자동 변경 | 읽지 않아도 된다 |

- 등급은 경로가 아니라 영향으로 정한다. 예를 들어 Lab 파일이라도 일반 배포 번들이나 실제 게임 화면에 영향을 주면 필수다. 애매하면 높은 등급으로 둔다.
- 등급마다 파일 수와 추가·삭제 줄 수를 적는다.
- 필수 파일은 파일마다 한 줄로 무엇이 바뀌었고 무엇을 깨뜨릴 수 있는지 적고, 위험이 큰 순서로 읽는 순서를 매긴다.
- 생략 가능한 생성물은 `.gitattributes`에 `linguist-generated=true`로 표시해 GitHub 리뷰 화면에서 접는다. 플레이어가 실제로 보는 에셋(`public/skins/` 등)의 변경은 접지 않는다.
- 필수 파일이 많아 한 번에 읽기 어렵다면 PR을 나누거나 생성물을 분리하는 방안을 먼저 제안한다.

## 머지 전 이해 확인

- 머지는 기존 규칙대로 사용자의 명시적 지시가 있을 때만 한다.
- "읽었다"는 답만으로 확인을 끝내지 않는다. 에이전트는 필수 파일마다 내용을 이해해야 답할 수 있는 열린 질문을 대화로 던지고, 사람이 자기 말로 답하게 한다.
  - 질문은 PR 본문에 적은 필수 파일별 "바뀐 내용·깨질 수 있는 것"에서 뽑는다. 필수 파일당 하나를 기본으로 하고, 함께 봐야 하는 파일은 묶어서 물어도 된다.
  - 예: "이 파일이 바뀌어도 기존 스킨 화면이 그대로인 이유는?", "이 변경이 깨뜨릴 수 있는 상황 하나를 들어 주세요", "이 규칙이 막으려는 문제는?"
  - "맞나요?", "이해하셨나요?" 같은 예/아니오 질문이나 답이 질문에 들어 있는 유도 질문은 쓰지 않는다.
  - 질문은 사람이 파일을 읽었다고 말한 뒤에 한다. 미리 질문을 보여 주지 않는다.
- 에이전트는 답을 실제 diff와 대조한다. 핵심을 짚으면 그 파일은 확인된 것으로 본다. 빠지거나 틀린 부분이 있으면 관련 diff 조각을 보여 주며 설명하고, 다른 각도로 다시 묻는다.
- 모든 필수 파일이 확인되기 전에는 머지하지 않는다. "머지해", "ㅇㅋ", "읽었다" 같은 답이나 서브에이전트·CodeRabbit 등 자동 리뷰의 승인은 이 확인을 대신하지 않는다.
- 확인이 끝나면 PR 본문의 `머지 전 확인` 체크박스를 체크하고 확인한 사람, 날짜, 확인 시점 커밋, 파일별로 확인한 요점을 한 줄씩 적는다. 대화 전문은 옮기지 않는다.
- 확인 뒤 필수 파일이 다시 바뀌면 바뀐 부분에 대해 다시 묻는다.
