# RFD 0107: 곡 공통 타이밍은 `songs` 행에 두고 곡·차트 저장은 DB 함수로 한 번에 확정한다

**Status:** Accepted (2026-11-01) · 런타임 미구현

## 기존 결정과 문제의식

[RFD 0095](0095-song-shared-bpm-and-audio-offset.md)는 같은 곡의 모든 차트가 BPM·박자표·음원 정렬 오프셋을 공유하도록, [RFD 0096](0096-song-shared-display-metadata-and-records.md)은 제목·아티스트·자켓을 곡이 소유하도록, [RFD 0098](0098-song-info-drawer-and-save-scope.md)은 곡 저장과 차트 저장을 나누도록 정했다. 곡 정보 사본 정리와 정본 참조, 곡 타이밍 저장 구조, 저장 반영 절차는 [PRD §12](../prd.md#12-미정-사항)에 미정으로 남아 있었다.

현재 구현(2026-11-01 조사, main `c05d1167`)은 다음과 같다.

- `songs` 행은 제목·아티스트·자켓·음원 경로와 프리뷰 구간(`preview_start`·`preview_end`)·플레이 구간(`gameplay_start`·`gameplay_end`·`gameplay_fade_in`·`gameplay_fade_out`)을 갖지만 공통 타이밍은 없다.
- 차트 JSON의 `meta`에 제목·아티스트·자켓·오프셋 사본이 있고, `charts.offset_ms`에도 오프셋 사본이 있다. 초기 BPM·BPM 변경·박자표는 차트마다 `chart.events`에 있다. 게임은 차트 JSON의 이벤트와 오프셋으로 타이밍을 계산한다.
- Save Chart는 메인 JSON·보조 JSON 업로드, `charts` 행 갱신, 미디어 업로드와 `songs` 경로·구간 갱신을 따로 요청하며 중간 실패를 되돌리지 않는다.
- 마이그레이션에는 `songs` 갱신(UPDATE) 정책이 없는데 코드는 `songs`를 갱신한다. 운영 DB에 적용된 정책은 확인하지 못했다.
- 기록 저장·랭킹은 아직 구현되지 않았다([PRD §12](../prd.md#12-미정-사항) "기록 저장·랭킹"). 미출시라 기존 사용자 데이터도 없다.

## 결정 (사용자 확인, 2026-11-01)

1. **곡 공통 타이밍의 정본은 `songs` 행에 둔다.** BPM 변경 목록·박자표·음원 정렬 오프셋을 `songs` 행의 JSON 열과 리비전 번호로 저장한다. 별도 타이밍 테이블(이력 구조가 분명하지만 조인과 권한 정책이 늘어남)과 차트마다 사본을 두고 곡 저장 때 모두 고치는 방식(사본끼리 어긋날 수 있고 쓰기가 차트 수만큼 늘어남)은 채택하지 않는다.
2. **차트 JSON의 사본은 형식을 유지하되 곡 행이 있으면 무시한다.** 곡 행이 있는 차트는 로더 한 곳에서 항상 곡 행의 값을 쓰고, 곡이 없는 차트 파일(튜토리얼 실습·Lab 연습 차트·판정 사례 PNG 도구·E2E 픽스처)은 자기 값을 쓴다. 차트 파일 형식을 "타이밍 있음/없음" 두 종류로 나누는 대안은 채택하지 않는다. 곡 타이밍으로 올리는 이행은 RFD 0095대로 관리자가 기준 차트 하나를 골라 그 타이밍을 곡 공통값으로 쓰고, 다른 차트는 박 좌표를 유지한다.
3. **곡 저장은 파일을 먼저 새 경로에 올리고 DB 함수 하나로 확정한다.** 자켓·음원처럼 파일이 바뀌면 새 경로에 먼저 올린 뒤, 관리자 권한을 확인하는 DB 함수 하나가 `songs` 행을 한 트랜잭션으로 바꾼다. 에디터가 열 때 본 리비전과 다르면 거부한다. 실패하면 DB는 저장 전 상태로 남고, 쓰이지 않는 새 파일만 남는다. 차례로 덮어쓰는 방식은 일부만 바뀐 상태를 남기므로 채택하지 않는다.
4. **음원·프리뷰 구간·플레이 구간은 곡 저장 범위다.** 음원 경로·길이, 프리뷰 구간, 플레이 구간과 페이드는 곡 저장이 3의 DB 함수로 함께 확정하고 곡 정보 드로어에서 편집한다. 차트 저장은 노트·차트별 이벤트·난이도만 다룬다.
5. **차트 저장도 같은 방식으로 확정한다.** 메인·보조 JSON을 새 경로에 먼저 올리고, DB 함수 하나가 `charts` 행이 새 파일을 가리키게 바꾼다. 실패하면 이전 차트가 그대로 남는다.

곡 단위 타이밍으로는 특정 차트만의 BPM 연출을 할 수 없다. 차트별 연출이 필요하면 BPM이 아니라 차트별 스크롤 계수 이벤트로 한다(사용자 확인, 2026-11-01). 스크롤 계수 이벤트는 이번 범위가 아니다.

## 미루는 것

- 공통 타이밍 수정으로 입력 시각이 달라진 차트의 기록 버전 분리 판정은 기록 저장을 구현할 때 정한다(RFD 0095·0096의 원칙은 유지).
- 이행 도구의 형태(스크립트·관리자 UI), 온라인 차트에 남는 쓰이지 않는 사본 필드와 새 경로 업로드 뒤 남는 옛 파일의 정리 시점은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

## 영향과 검증

- `supabase/migrations`: `songs`의 타이밍 열·리비전, `charts`의 파일 경로·리비전, 곡 저장·차트 저장 DB 함수와 관리자 권한 확인. 새 마이그레이션 번호는 모든 원격 브랜치와 대조한다.
- 공용 로더: 곡 행이 있으면 곡 타이밍·표시 정보를 쓰고, 없으면 차트 파일 값을 쓰는 해석을 게임과 에디터가 함께 쓴다.
- 에디터: 곡·차트의 저장 기준 상태와 미저장 표시를 따로 두고, 곡 저장·차트 저장을 각 DB 함수로 바꾼다. RFD 0098의 드로어·이탈 확인·통합 Undo는 이 저장 구조 위에서 구현한다. 통합 Undo는 이력 스냅샷에 곡 정보와 차트를 함께 담는 구현을 기본으로 한다.
- [glossary 곡 저장](../context/glossary.md#곡-저장)·에디터 컨텍스트·[에디터 스펙](../spec/chart-editor.md#곡-타이밍-공유-미구현)·PRD에 저장 범위와 절차를 반영한다.
- 검증: DB 함수의 리비전 충돌 거부·권한 거부·트랜잭션 원자성, 로더의 곡 행 우선 해석, 곡이 없는 차트 파일의 기존 동작 유지, 저장 실패 시 이전 상태 유지.
