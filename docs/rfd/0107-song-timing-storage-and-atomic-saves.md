# RFD 0107: 곡 공통 타이밍은 `songs` 행에 두고 곡·차트 저장은 DB 함수로 한 번에 확정한다

**Status:** Accepted (2026-11-01) · 런타임 미구현 · PR1 DB 마이그레이션·저장 함수·정적 계약 테스트 작성 (2026-11-01) · PR #433 리뷰의 삭제·재등록 충돌 보호와 #396 선행 조건 반영 (2026-11-01) · PR2 공용 로더 구현 (2026-11-01) · PR #434 리뷰의 제목·아티스트 편집 보호와 NULL 자켓 보존 반영, PR3 타이밍 이행은 PR4 곡 저장 연결 이후로 제한 (2026-11-01) · PR1 마이그레이션 운영 DB 적용·열·함수·권한 확인 (2026-11-01) · 이행은 별도 도구 없이 이행 전 곡의 곡 저장이 열린 차트의 타이밍을 올리는 것으로 결정 (2026-11-01) · PR4a 에디터 곡 저장 구현 (2026-11-01) · PR4a를 저장 버튼 하나로 정리 (2026-11-01) · 이행 전 곡은 Save마다 이행 확인(취소 시 차트만 저장)으로 결정 (2026-11-02) · PR4b 차트 저장 원자화 구현 (2026-11-02)

구현 세부: 차트 저장은 UUID·예상 리비전으로 기존 행만 갱신하고, Save As는 새 UUID를 만든다. 곡은 차트가 없으면 삭제·같은 text ID 재등록이 가능하므로 기존 행·신규 행·저장에 공유 비순환 시퀀스 리비전을 사용한다. `save_song` 인자는 유지하며 리비전은 연속 횟수가 아닌 충돌 검사값이다. 세 함수의 관리자 확인은 운영에 2026-10-31 적용된 PR #396의 `profiles.is_admin` 자기 승격 차단에 의존하며, 보호가 없는 환경에는 적용하지 않는다. 서명·권한·검증 경계는 [RLS 정책 문서](../../supabase/RLS_POLICIES.md#곡차트-저장-함수-rfd-0107)를 따른다.

PR2 구현 범위: 게임·에디터 공용 읽기에서 곡 행의 표시 정보·검증된 타이밍을 우선 적용한다. NULL 타이밍은 파일 값을 유지하며 잘못된 타이밍은 로드 오류다. 에디터의 초기 설정 배치 후 상태가 깨끗한 로드 기준이다. 세부 계약은 [차트 포맷](../spec/chart-format.md#곡-행-우선-읽기)을 따른다. 운영 DB 적용은 확인·수행하지 않았으며, 앱보다 PR1 마이그레이션을 먼저 적용해야 한다. 새 경로 읽기·저장 함수 연결·이행 도구·기록 버전 분리는 후속 작업이다.

PR2의 알려진 제한:

- Save Chart는 제목·아티스트를 차트 JSON의 `meta` 사본에만 쓰고 `songs.title`·`artist`를 갱신하지 않는다. PR4 곡 저장 연결 전까지 곡 행이 있는 차트의 Meta 모달에서 Title·Artist를 읽기 전용으로 두고 곡 저장에서 편집할 예정임을 안내한다. 곡 행이 없는 차트의 편집은 유지한다.
- 자켓·음원 업로드는 이미 Save Chart에서 `songs.jacket_url`·`audio_url`을 갱신하므로 그대로 유지한다. 로더는 `jacket_url`이 NULL이면 기존 에디터처럼 차트의 `imageFile`을 유지한다.
- 현재 모든 곡의 `songs.timing`이 NULL이라는 운영 전제에서 오프셋·BPM·박자표 편집은 기존 파일 타이밍을 사용한다. **PR3 이행 도구로 단 한 곡이라도 non-null 타이밍을 쓰기 전에 PR4 곡 저장 연결이 먼저 반영되어야 한다.** 그 전에 이행하면 Save Chart가 파일에만 쓴 타이밍 편집을 다시 열 때 곡 행 값으로 덮어써 편집이 되돌아간다. PR1의 스키마 적용과 PR3의 데이터 이행은 별개다.

## 기존 결정과 문제의식

[RFD 0095](0095-song-shared-bpm-and-audio-offset.md)는 같은 곡의 모든 차트가 BPM·박자표·음원 정렬 오프셋을 공유하도록, [RFD 0096](0096-song-shared-display-metadata-and-records.md)은 제목·아티스트·자켓을 곡이 소유하도록, [RFD 0098](0098-song-info-drawer-and-save-scope.md)은 곡 저장과 차트 저장을 나누도록 정했다. 곡 정보 사본 정리와 정본 참조, 곡 타이밍 저장 구조, 저장 반영 절차는 [PRD §12](../prd.md#12-미정-사항)에 미정으로 남아 있었다.

현재 구현(2026-11-01 조사, main `c05d1167`)은 다음과 같다.

- `songs` 행은 제목·아티스트·자켓·음원 경로와 프리뷰 구간(`preview_start`·`preview_end`)·플레이 구간(`gameplay_start`·`gameplay_end`·`gameplay_fade_in`·`gameplay_fade_out`)을 갖지만 공통 타이밍은 없다.
- 차트 JSON의 `meta`에 제목·아티스트·자켓·오프셋 사본이 있고, `charts.offset_ms`에도 오프셋 사본이 있다. 초기 BPM·BPM 변경·박자표는 차트마다 `chart.events`에 있다. 게임은 차트 JSON의 이벤트와 오프셋으로 타이밍을 계산한다.
- Save Chart는 메인 JSON·보조 JSON 업로드, `charts` 행 갱신, 미디어 업로드와 `songs` 경로·구간 갱신을 따로 요청하며 중간 실패를 되돌리지 않는다.
- 마이그레이션에는 `songs` 갱신(UPDATE) 정책이 없는데 코드는 `songs`를 갱신한다. 운영 DB에 적용된 정책은 확인하지 못했다.
- 기록·랭킹 테이블은 초기 스키마에 있지만 앱 코드는 기록을 로컬 store에만 두고 그 테이블을 읽거나 쓰지 않는다([PRD §12](../prd.md#12-미정-사항) "기록 저장·랭킹"). 운영 DB에 기록 데이터가 있는지는 확인하지 않았다.

## 결정 (사용자 확인, 2026-11-01)

1. **곡 공통 타이밍의 정본은 `songs` 행에 둔다.** BPM 변경 목록·박자표·음원 정렬 오프셋을 `songs` 행의 JSON 열과 리비전 번호로 저장한다. 별도 타이밍 테이블(이력 구조가 분명하지만 조인과 권한 정책이 늘어남)과 차트마다 사본을 두고 곡 저장 때 모두 고치는 방식(사본끼리 어긋날 수 있고 쓰기가 차트 수만큼 늘어남)은 채택하지 않는다.
2. **차트 JSON의 사본은 형식을 유지하되 곡 행이 있으면 무시한다.** 곡 행이 있는 차트는 로더 한 곳에서 항상 곡 행의 값을 쓰고, 곡이 없는 차트 파일(튜토리얼 실습·Lab 연습 차트·판정 사례 PNG 도구·E2E 픽스처)은 자기 값을 쓴다. 차트 파일 형식을 "타이밍 있음/없음" 두 종류로 나누는 대안은 채택하지 않는다. 곡 타이밍으로 올리는 이행은 RFD 0095대로 관리자가 기준 차트 하나를 골라 그 타이밍을 곡 공통값으로 쓰고, 다른 차트는 박 좌표를 유지한다.
3. **곡 저장은 파일을 먼저 새 경로에 올리고 DB 함수 하나로 확정한다.** 자켓·음원처럼 파일이 바뀌면 새 경로에 먼저 올린 뒤, 관리자 권한을 확인하는 DB 함수 하나가 `songs` 행을 한 트랜잭션으로 바꾼다. 에디터가 열 때 본 리비전과 다르면 거부한다. 실패하면 DB는 저장 전 상태로 남고, 쓰이지 않는 새 파일만 남는다. 차례로 덮어쓰는 방식은 일부만 바뀐 상태를 남기므로 채택하지 않는다.
4. **음원·프리뷰 구간·플레이 구간은 곡 저장 범위다.** 음원 경로·길이, 프리뷰 구간, 플레이 구간과 페이드는 곡 저장이 3의 DB 함수로 함께 확정하고 곡 정보 드로어에서 편집한다. 차트 저장은 노트·차트별 이벤트·난이도만 다룬다.
5. **차트 저장도 같은 방식으로 확정한다.** 메인·보조 JSON을 새 경로에 먼저 올리고, DB 함수 하나가 `charts` 행이 새 파일을 가리키게 바꾼다. 실패하면 이전 차트가 그대로 남는다.

곡 단위 타이밍으로는 특정 차트만의 BPM 연출을 할 수 없다. 차트별 연출이 필요하면 BPM이 아니라 차트별 스크롤 계수 이벤트로 한다(사용자 확인, 2026-11-01). 스크롤 계수 이벤트는 이번 범위가 아니다.

### 이행 전 곡의 곡 저장 (사용자 확인, 2026-11-01)

곡 타이밍으로 올리는 이행은 별도 도구 없이 에디터의 곡 저장으로 한다. `songs.timing`이 NULL인 곡의 차트를 열고 곡 저장을 누르면 열린 차트의 BPM·박자·오프셋을 곡 타이밍으로 올린다. 이것이 RFD 0095의 "관리자가 기준 차트 하나를 고른다"에 해당한다. 처음 올릴 때 "이 차트의 타이밍을 곡 공통 타이밍으로 올리며 이 곡의 다른 차트도 이 타이밍을 따른다"는 확인을 한 번 받고, 다른 차트의 타이밍이 다르면 그 사실도 함께 보여 준다. 별도 이행 도구(스크립트·관리자 UI)는 만들지 않는다.

저장 버튼을 하나로 합친 뒤(RFD 0098) 사용자는 이행 전 곡에서는 Save할 때마다 이행 확인을 받기로 정했다(2026-11-02). 곡 단위 값을 바꾸지 않고 노트만 고쳤거나 아무것도 바꾸지 않았어도 이행 확인을 띄우며, 확인하면 열린 차트의 타이밍을 곡 타이밍으로 올리고 바뀐 쪽을 저장한다. 취소하면 곡 저장 없이 차트만 저장한다. 별도의 이행 메뉴 동작은 두지 않는다("아무 변경사항이나 만들어서 저장하면 되니까 메뉴 동작을 추가할 필요는 없고 이행 전에는 세이브할때마다 확인").

## 정하지 않은 것

이 RFD는 다음을 정하지 않으며 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

- 공통 타이밍 수정으로 입력 시각이 달라진 차트를 찾아 기록 버전을 나누는 판정 방법(RFD 0095·0096의 원칙은 유지)
- 온라인 차트에 남는 쓰이지 않는 사본 필드와 새 경로 업로드 뒤 남는 옛 파일의 정리 시점

## 영향과 검증

- `supabase/migrations`: `songs`의 타이밍 열·리비전, `charts`의 파일 경로·리비전, 곡 저장·차트 저장 DB 함수와 관리자 권한 확인. 새 마이그레이션 번호는 모든 원격 브랜치와 대조한다.
- 공용 로더: 곡 행이 있으면 곡 타이밍·표시 정보를 쓰고, 없으면 차트 파일 값을 쓰는 해석을 게임과 에디터가 함께 쓴다.
- 에디터: 곡·차트의 저장 기준 상태와 미저장 표시를 따로 두고, 곡 저장·차트 저장을 각 DB 함수로 바꾼다. RFD 0098의 드로어·이탈 확인·통합 Undo는 이 저장 구조 위에서 구현한다.
- [glossary 곡 저장](../context/glossary.md#곡-저장)·에디터 컨텍스트·[에디터 스펙](../spec/chart-editor.md#곡-타이밍-공유-미구현)·PRD에 저장 범위와 절차를 반영한다.
- 검증: DB 함수의 리비전 충돌 거부·권한 거부·트랜잭션 원자성, 로더의 곡 행 우선 해석, 곡이 없는 차트 파일의 기존 동작 유지, 저장 실패 시 이전 상태 유지.
