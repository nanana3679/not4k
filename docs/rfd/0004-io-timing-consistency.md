## 1. 배경 및 목적

리듬게임에서 판정 일관성은 최상위 품질 축이다. not4k의 타깃 유저층은 오디오 인터페이스 수준의 하드웨어 투자로 ms 단위 지연을 줄이려는 플레이어이며, 게임이 **추가 지터**를 얹으면 그 하드웨어 투자가 통계적으로 무의미해진다.

본 RFD가 다루는 것은 "절대 지연 감소"가 아니라 "추가 지터를 만드는 범인의 제거"이다. 절대 지연은 이미 `audio-visual-sync.md`가 설계로 다루고 있으며(일부 미구현 포함), 본 RFD는 그 스펙을 보완하면서 **지터·분산** 축에서 비어 있는 작업 항목을 채운다.

## 2. 전제 (Scope)

- **타깃 환경**: 유선 키보드 + 유선 오디오(또는 오디오 인터페이스). BT/무선은 범위 밖
- **절대 지연 한계**: 브라우저(Chrome)는 Windows WASAPI shared mode로 동작하며 네이티브 ASIO 대비 수십 ms 불리. 이 차이는 웹 기술로 극복 불가능. 본 RFD는 이를 좁히는 것을 목표로 하지 않음
- **히트 사운드 없음**: 오디오 출력 경로의 지터원은 곡 재생 1개뿐. 이펙트 사운드 스케줄링은 고려 대상이 아님
- **캘리브레이션**: 시각/오디오 분리되어 이미 구현됨 (`audioOffsetMs`, `judgmentOffsetMs`)
- **이미 구현된 대응**: `KeyboardEvent.timeStamp` 사용, 핸들러 큐 지연(`handlerDelay`) 보정 — 회귀 방지 대상

## 3. 원칙

> **"not4k는 당신의 환경이 제공하는 기본 지연에 추가 지터를 얹지 않는다"** 를 구현·측정·증명한다.

이 선언을 구체 작업으로 환원한 것이 §4의 W1~W4이다. 이 선언을 **숫자로 증명**할 도구가 §5의 F1~F6이다.

## 4. 작업 항목 (Actionable)

각 항목은 개별 PR. 각 PR은 `CLAUDE.md`의 테스트 규칙에 따라 해당 기능의 단위 테스트를 동반한다.

### W1. `AudioContext`에 `latencyHint: 'interactive'` 명시

**현재:** `src/game/audio/AudioEngine.ts:23`
```ts
this.ctx = new AudioContext();
```

**문제:** 기본값은 브라우저/OS 구현에 의존한다. 일부 환경은 안정성 위주로 큰 버퍼를 할당할 수 있으며, 이는 ASIO급 환경을 가진 사용자에게 불필요하게 지연을 늘린다. 명시가 안전.

**변경:**
```ts
this.ctx = new AudioContext({ latencyHint: 'interactive' });
```

**리스크:** 매우 저사양 환경에서 under-run 발생 가능. 타깃 환경 전제(§2)상 허용 가능.

**단위 테스트:**
- `AudioEngine` 생성 후 `ctx.baseLatency`가 0보다 큰 값으로 기록되는지 확인하는 회귀 테스트 (정확한 값은 환경 의존이므로 존재/범위 검증)

**검증:**
- 생성 직후 `ctx.baseLatency + ctx.outputLatency`를 dev 빌드 콘솔에 로그
- 사용자가 설정에서 "안정성 우선" 옵션을 추후 요구할 경우 `'playback'`으로 전환 가능하도록 코드 구조 유지

### W2. 입력 핫패스 할당 제거

**배경:** GC 일시정지는 입력 판정 파이프라인의 직접 지터원이다. 이벤트당 새 객체 할당이 누적되면 GC가 예측 불가능한 시점에 발생해 수 ms 단위 지터를 만든다.

**범위:**
- `src/game/input/InputSystem.ts` — `onKeyDown`, `onKeyUp`
- `src/game/screens/PlayScreen.tsx` — `onLanePress`, `onLaneRelease` 콜백 본문
- 이 경로에서 `JudgmentEngine.onLanePress`까지의 호출 사이 전체

**작업 절차:**
1. Chrome DevTools Performance의 **Allocation sampling**으로 오토 플레이 1곡 전체의 핫패스 할당 프로파일 수집
2. 이벤트당 할당 포인트 식별 — 예상 원인:
   - 콜백 내부 객체 리터럴 (`{ lane, timestamp, ... }`)
   - `Map.get()`의 반환값 언박싱 과정
   - 로그/디버그 경로의 템플릿 리터럴
3. 재사용 가능한 버퍼로 변환하거나 사전 할당 후 in-place 업데이트로 변경
4. 재측정으로 할당 감소 확인

**리스크:** 코드 가독성 저하. 핫패스에 한정해 최소 범위로 진행. 디버그 로깅 경로는 `if (DEBUG)` 가드로 분리해 prod에서 tree-shake.

**단위 테스트 (약한 검증이지만 회귀 방지):**
- 핫패스 함수를 N회 호출한 뒤 동일 입력으로 한 번 더 호출했을 때 결과가 동일한지 (상태 오염 없음)
- 할당 계측 자체는 단위 테스트로 강제 불가 — §10-Q2 참조

### W3. 판정 이펙트를 rAF 타이밍에 고정 (상대적 일관성 확보)

**배경:** 판정 이펙트, 콤보 숫자, 판정 텍스트 등이 판정 시각(`performance.now()` 기준)에 즉시 렌더 트리거되면 각 이펙트가 다음 프레임 어디쯤에 찍히는지가 매번 다르다. 이것이 사용자가 체감하는 "이펙트가 튄다"의 주범 후보이다.

**설계:**
- 판정 결과는 즉시 **이벤트 큐**에 쌓기만 한다 (렌더 트리거 금지)
- 다음 rAF tick에서 큐를 일괄 소비하여 이펙트를 생성
- 이렇게 하면 모든 이펙트는 항상 "판정 후 정확히 1 rAF tick 뒤"에 표시됨
- 절대 지연: 최대 +16.6ms (60Hz) / +6.9ms (144Hz)
- 분산: 0에 수렴

**사용자 확인 (2026-04-11):** 1프레임 일정 지연이 가변 지터보다 우월하다는 데 동의.

**적용 대상:**
- 판정 텍스트 (PERFECT/GOOD/BAD 팝업)
- 콤보 숫자 업데이트
- 노트 히트 이펙트
- 노트 소멸 애니메이션 시작 시점

**단위 테스트:**
- 판정 큐에 n건 push 후 rAF 1회 소비 시 n건 모두 처리되는지
- rAF 미호출 시 큐가 유지되는지

**검증:**
- 플레이 화면 고속 녹화(240fps 외부 카메라 또는 스크린 캡처)로 판정~이펙트 프레임 간격이 **일정**한지 프레임 단위 확인

**미해결 (§10-Q3):** 위 대상 목록에 빠진 요소 있는지 사용자 확인 필요

### W4. `AudioContext.outputLatency` 주입 — `audio-visual-sync.md` §A 구현

**현재 상태:** `audio-visual-sync.md` 우선순위 1번으로 설계되어 있으나 **미구현**. `AudioEngine.getOutputLatencyMs()` 함수는 존재하지만 `PlayScreen`에서 호출되지 않는다.

**스펙 요약 (`audio-visual-sync.md` §보정 설계 A):**
```ts
const audioOutputLatencyMs = (ctx.baseLatency + ctx.outputLatency) * 1000;
const songTimeMs = audioEngine.currentTimeMs + settings.audioOffsetMs;
const visualTimeMs = songTimeMs + audioOutputLatencyMs;

judgmentEngine.update(songTimeMs);      // 판정: 그대로
renderer.renderFrame(visualTimeMs);     // 렌더: 출력 지연만큼 미래
```

**BT 배제 전제의 영향:** `outputLatency`는 동적 주입이 아니라 **세션 시작 시 1회 값**으로 충분하다. 유선 환경에서는 재생 중 변하지 않는다고 가정.

**Safari 폴백:** 스펙대로, 값이 없으면 0 (= 현재 동작).

**마이그레이션 (§10-Q1):** 기존 사용자의 캘리브레이션 값은 outputLatency를 이미 내부에 흡수한 상태이다. W4 도입 후 다음 중 하나:
- (a) 사용자에게 재캘리브레이션 권고 — 정직하지만 마찰
- (b) 기존 offset에서 현재 `outputLatencyMs`를 자동 차감 후 저장 — 계산 가능하지만 사용자에게 "건드린 것"
- (c) 신규 사용자에게만 적용, 기존 사용자는 opt-in — 복잡도 증가

사용자 결정 필요.

**단위 테스트:**
- `visualTimeMs = songTimeMs + outputLatencyMs` 계산 정확성
- `outputLatency` 미지원 환경(undefined) 폴백 동작

**검증:** 유선 환경에서 캘리브레이션으로 잡던 오프셋의 일부가 자동 흡수되는지 수치 확인.

## 5. 연기 항목 (Future Work — 본 RFD에서 구현하지 않음)

다음 항목들은 본 RFD 범위 밖이지만, 추후 별도 작업이 가능하도록 설계 결정을 문서화한다. 각 항목은 독립적으로 진행 가능.

### F1. 판정 히스토그램 (리절트 화면 + 플레이 중 옵션)

- **목적**: 사용자가 "지터 문제"와 "오프셋 문제"를 스스로 구분. 체감 불안에 대한 투명성 제공
- **설계**: 리절트 화면에 [-40ms, +40ms] 구간 히스토그램. 빈 크기 2ms 권장. 평균·중앙값·표준편차 병기
- **장르 관행**: osu!, Etterna, Quaver 등 주요 리듬게임이 모두 기본 제공. 타깃 유저층은 이 UI를 읽을 줄 안다고 가정
- **선행 조건**: 없음 (독립 작업 가능). 단 W1~W4가 먼저 들어가면 그 효과를 히스토그램으로 정량 검증 가능
- **주의**: 히스토그램을 먼저 만들면 W1~W4의 before/after를 숫자로 확인할 수 있어 **W1~W4와 동시에 진행할 가치가 있음** (§10-Q4 참조)

### F2. 입력 큐 지연 (`now - e.timeStamp`) 세션 p50/p95/p99 수집·표시

- **목적**: "게임이 네 입력을 얼마나 지연 후 받았는가"를 숫자로 증명. 사용자가 "내 환경은 정상"을 확인할 수 있게 함
- **설계**: 세션 중 롤링 수집 후 곡 종료 시 리절트에 표시. p99 임계 초과 시 비공격적 배너 (차단 없음)
- **선행**: `realworld-frame-drops-hypothesis.md`의 텔레메트리 파이프라인과 통합. 그 문서의 수집 스키마에 필드 추가로 구현 가능

### F3. rAF 간격 표준편차 수집·표시

- **목적**: 프레임 지터의 정량화. F2와 짝으로 작동
- **설계**: rAF delta 롤링 수집, 곡 종료 시 p50/p95/stdDev. `perf-bottleneck-hypothesis.md`가 수집 안 한 정량 지표에 해당
- **선행**: `realworld-frame-drops-hypothesis.md`의 드롭 카운트 수집 확장으로 구현. 추가 작업 최소

### F4. 캘리브레이션 `stdDev` 게이팅·표시

- **목적**: 사용자 환경의 본질 지터를 캘리브레이션 시점에 공개
- **설계**: `calibrationLogic.ts`는 이미 `stdDev`를 반환 중 — UI 표시만 추가. 라벨: `< 5ms 매우 안정` / `5~10ms 일반` / `> 10ms 불안정 감지`. **차단 없음**, 정보 제공만
- **선행**: 없음. 언제든 독립 작업 가능
- **주의**: 경고 문구는 "환경이 이상할 수 있음"까지만 — 원인 추측(BT 등) 금지. 타깃 유저층은 본인 환경을 더 잘 앎

### F5. AudioContext ↔ performance.now() 드리프트 감시

- **목적**: 두 클록이 장시간 재생 중 어긋나는지 확인
- **설계**: 1초 주기 샘플링, 임계 초과 시 로그
- **선행**: 실제 드리프트가 문제인지 선확인 필요. 선제 구현 불필요
- **관련 문서**: `audio-visual-sync.md`도 이 리스크를 §보정 설계 B의 주의사항에서 언급 중

### F6. 페이지 가시성 복귀 시 clock 재동기

- **목적**: alt-tab 후 복귀 시 AudioContext 시각과 내부 시각 재정렬
- **설계**: `visibilitychange` 이벤트에서 두 시계 비교·보정
- **선행**: 실측으로 문제 발생 여부 확인 후. 현재 가설 단계

## 7. ASIO 한계 고지

본 RFD의 모든 작업 항목은 다음 약속의 구현체이다:

> **"당신의 환경이 제공하는 기본 지연에 not4k는 추가 지터를 얹지 않는다"**

not4k는 네이티브 ASIO 환경을 **대체하지 않는다**. 브라우저(Chrome)는 Windows에서 WASAPI shared mode로 동작하며, 네이티브 ASIO exclusive mode 대비 절대 지연에서 수십 ms 불리하다. 이 차이는 본 RFD가 해결하지 못한다.

not4k가 줄일 수 있는 것은 **분산**이다. 평균 지연이 ASIO 환경보다 크더라도, 그 값의 표준편차가 작다면 사용자는 캘리브레이션으로 평균을 잡아낸 뒤 일관된 판정 경험을 얻는다. 타깃 유저층의 요구는 **"절대 지연 0"이 아니라 "예측 가능한 지연"** 이라는 가정 위에 본 RFD가 설계된다.

이 가정이 틀리면 RFD 전제가 무너진다. 가정이 맞는지는 F1~F4의 데이터 수집 이후 사용자 피드백으로 재검증한다.

## 8. 검증 전략

### 8.1 측정 기준
작업 전후 비교를 위해 측정 기준을 먼저 고정한다.

| 항목 | W1 | W2 | W3 | W4 |
|---|---|---|---|---|
| `baseLatency + outputLatency` (ms) | ↓ | - | - | (값 기록) |
| 핫패스 이벤트당 할당량 (bytes, Allocation profiler) | - | ↓↓ | - | - |
| 판정~이펙트 프레임 간격 stdDev (영상 분석) | - | - | ↓↓ | - |
| 캘리브레이션 사용자 수동 오프셋 크기 | - | - | - | ↓ (자동 흡수분만큼) |

### 8.2 측정 환경
- 타깃 환경에 맞춘 유선 데스크탑 고정 1종 (Windows / Chrome)
- prod 빌드 (`pnpm build && pnpm preview`)
- CPU throttling **미적용** (현실 환경 우선)
- 동일 차트 3회 반복, 중앙값 사용
- 측정 일자·환경은 결과 문서화 시 기록

### 8.3 측정 시점
- 기준선: W1 착수 전 현재 빌드
- 중간: W1, W3, W2, W4 각 PR 머지 직후 (작업 순서와 일치)
- 최종: 전체 머지 후

### 8.4 측정 가능한 절대 목표
- W1 후 `baseLatency + outputLatency` ≤ 기준선
- W2 후 핫패스 이벤트당 할당 ≈ 0 bytes (완전 0은 불가능할 수 있음)
- W3 후 판정~이펙트 프레임 간격 = 1 frame 고정 (분산 0에 수렴)
- W4 후 사용자가 수동으로 넣던 `audioOffsetMs`의 일부가 자동 흡수됨

### 8.5 측정 도구 제약
- **영상 분석**은 W3 검증에 필요하나 자동화 어려움. 수동 측정 허용
- **Allocation sampling**은 Chrome DevTools에 의존. 재현성을 위해 동일 브라우저 버전 기록
- **엔드-투-엔드 마이크+카메라 측정**은 본 RFD 범위 밖 (비용 과다). 단 F1~F4 도입 후 사용자 보고 불일치 시에는 이 방법이 유일한 지상진실임

- **CLAUDE.md 테스트 규칙**: 본 RFD의 모든 W 항목은 Vitest 단위 테스트 동반 필수

## 10. 미해결 질문

1. **W4 마이그레이션 전략** — 기존 사용자의 `audioOffsetMs`가 `outputLatency`를 이미 흡수한 상태에서 W4를 도입하면 사용자 입장에서 오프셋이 "한 번 튐". 재캘리브레이션 권고 / 자동 차감 / 신규만 적용 / opt-in 중 어느 쪽? → **사용자 결정 필요**

2. **W2 할당 0 회귀 방지** — Vitest로 "핫패스에서 새 객체 생성 없음"을 강제할 표준 도구가 없다. heapUsed 델타 비교는 노이즈가 큼. 대안:
   - 개별 함수 단위 스냅샷 테스트 (허용된 할당 목록만)
   - 수동 리뷰 의존
   - 개발 시 DevTools Allocation 주기적 확인
   → **수동 리뷰 + 주기 측정**으로 합의할 것인가?

3. **W3 적용 대상 확정** — §W3의 대상 목록(판정 텍스트, 콤보 숫자, 히트 이펙트, 노트 소멸)에서 누락이 없는가? `GameNoteRenderer`·`JudgmentUI` 코드를 한 번 훑어 확정할 필요 있음

4. **F1 시점 당김** — F1(판정 히스토그램)을 W1~W4와 **동시에** 진행하면 효과를 숫자로 검증할 수 있음. 연기의 의미가 줄어듦. 사용자가 F1을 W 그룹에 편입할 의향이 있는지? → **"P1은 나중에 작업"이라는 지시와 충돌 가능**. 추가 판단 필요

5. **W3 리스크 수용 범위** — 이펙트 최대 +16.6ms 지연이 "모든 대상"에 일괄 적용되는 것이 맞는가, 아니면 일부는 즉시 렌더 유지가 맞는가? 예: 노트가 판정선에 닿아 사라지는 시점은 rAF에 자연 고정되므로 추가 지연 불필요
