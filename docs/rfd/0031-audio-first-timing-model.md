# RFD 0031: 소리 기준 타이밍 모델과 입력·시각 오프셋

**Status:** 채택 (2026-10-13, 사용자 결정) · 구현 대기

## 기존 결정과 문제

플레이 중 시간은 [`GameClock`](../../src/game/time/GameClock.ts)이 만든다. 오디오 재생 위치 P(`AudioEngine.currentTimeMs`, `AudioContext.currentTime` 기반)에서 세 시간을 파생한다.

```
판정 시간 J = P + 오디오 오프셋(audioOffsetMs)
시각 시간 V = J + L                          (L = baseLatency + outputLatency, 매 질의 새로 읽음)
입력 시간   = 키 이벤트 순간의 J + 입력 오프셋(judgmentOffsetMs)
```

캘리브레이션은 둘이다. Audio 캘리브레이션은 비프에 맞춘 탭으로 오디오 오프셋을, Visual 캘리브레이션은 깜빡임에 맞춘 탭으로 입력 오프셋을 채운다. 부호는 리듬게임 판정 타이밍 관례(늦게 누르면 음수)로 [PR #242](https://github.com/nanana3679/not4k/pull/242)에서 정했다.

지연은 셋이다.

- **L(소리 출력):** `AudioContext`가 지금 처리한 소리가 스피커에서 L ms 뒤에 들린다. 브라우저가 `baseLatency + outputLatency`로 대략 알려 준다(Safari는 `outputLatency`가 없음).
- **D(화면 표시):** 지금 그린 렌더 프레임이 모니터에 D ms 뒤에 보인다. 브라우저가 알려 주지 않는다.
- **I(입력):** 키를 누른 순간부터 `KeyboardEvent.timeStamp`까지 I ms가 걸린다. 브라우저가 알려 주지 않는다. 이벤트 처리까지의 지연(`handlerDelay`)은 이미 뺀다.

2026-10-08 의도 감사([#249](https://github.com/nanana3679/not4k/issues/249))에서 다음 문제가 드러났다.

- **T1 시각 시간의 L 부호가 반대다.** 소리는 L만큼 늦게 들리므로 화면도 L만큼 늦게 그려야 한다. 오프셋이 0이면 노트가 소리보다 약 2L 일찍 판정선에 닿는다(D가 일부 상쇄). [`audio-visual-sync.md`](../spec/audio-visual-sync.md)의 목표("스피커에서 비트가 나오는 순간 노트가 판정선 위")는 맞지만 공식이 반대다.
- **T3 입력 지연 I를 두 번 뺀다.** Audio 캘리브레이션은 L+I(+체감)를, Visual 캘리브레이션은 D+I(+체감)를 잰다. 두 결과가 모두 입력 시간에 더해진다.
- **오디오 오프셋이 화면도 움직인다.** 오디오 오프셋은 J를 옮기므로 입력 지연까지 섞인 보정값만큼 노트 표시도 밀린다.
- **T4 Audio 캘리브레이션 비프를 rAF에서 바로 재생한다.** 비프가 기준 박자보다 최대 한 렌더 프레임 늦게 나고, 탭은 이상적인 박자 시각(`performance.now()` 기준)과 비교된다.
- **T6 L을 매 프레임 새로 읽는다.** 값이 흔들리면 노트 위치와 판정 기준이 함께 흔들린다. [RFD 0004](0004-io-timing-consistency.md)는 세션당 한 번 읽기를 원칙으로 둔다.
- **T8 재생 배속에서 단위가 섞인다.** P는 곡 시간(실제 경과 × 배속)인데 L·오프셋·`handlerDelay`는 실제 시간 ms 그대로 더한다.
- **D3 `judgmentOffsetMs`는 판정 결과가 아니라 입력 시각을 옮기는 값이라 이름이 하는 일과 맞지 않는다.**
- **[#245](https://github.com/nanana3679/not4k/issues/245) auto 노트의 키빔·키봄이 입력 시간 기준으로 만들어져, 입력 오프셋만큼 늦거나 일찍 보인다.**

## 결정

1. **소리 기준.** 판정과 화면의 기준은 스피커에서 소리가 들리는 순간이다. 입력은 들린 소리와 비교해 판정하고, 화면은 그 소리에 맞춰 노트를 그린다.
2. **L은 브라우저 값을 자동으로 쓰고 곡을 시작할 때 한 번 읽어 고정한다.** 보정과 플레이가 같은 L을 쓰므로, 브라우저 값의 고정 오차는 보정값에 흡수된다. 출력 장치를 바꿔 L이 달라지면 브라우저 값이 따라가므로 다시 보정하지 않아도 된다. 브라우저가 알려 주지 않으면 L = 0이다.
3. **오프셋은 입력 오프셋과 시각 오프셋 두 개다.** 오디오 오프셋(`audioOffsetMs`)은 없앤다. 입력과 화면을 같은 양만큼 함께 옮기는 값이라 두 오프셋을 같이 바꾸는 것과 같기 때문이다. 음원 자체의 어긋남은 차트 오프셋(`offsetMs`)이 맡는다.
4. **시각 보정은 보고 맞춘다.** 비프와 함께 노트가 판정선으로 떨어지는 화면에서 사용자가 시각 오프셋을 움직여(슬라이더, 키로 ±1ms) 소리와 노트가 동시에 닿는 값을 고른다. 탭을 쓰지 않으므로 I가 섞이지 않는다. 입력 보정은 지금처럼 비프에 맞춘 탭으로 하되, 비프를 `AudioContext` 시계로 예약하고 탭을 들린 비프 시각과 비교한다.
5. **이름과 부호.**

   | | 입력 오프셋 | 시각 오프셋 |
   |---|---|---|
   | 코드 | `inputOffsetMs` (`judgmentOffsetMs`에서 바꿈) | `visualOffsetMs` (새로 만듦) |
   | 설정 | `Input Offset` | `Visual Offset` |
   | 부호 | 늦게 누르면(SLOW) 음수(PR #242 관례 유지) | 화면이 소리보다 늦게 보이면 양수. 화면 지연 D를 그대로 적는 값이고, 그만큼 노트를 앞당겨 그린다 |
   | 채우는 곳 | 입력 보정(탭) | 시각 보정(보고 맞추기) |

6. **범위.** 이 RFD는 T1·T3·T4·T6·T8·D3·#245를 다룬다. T5(`ctx.currentTime` 계단 다듬기)는 지터 문제로 RFD 0004 쪽 후속에서, T9(일시정지 중 입력)·T10(창 전환)·T11(곡 끝 판정 창)·T12(게임 루프 예외)는 각각 이슈로 다룬다.

### 새 계산식

배속을 r, 곡을 시작할 때 읽은 L을 L₀라 한다. 실제 시간(ms) 값은 곡 시간으로 바꿀 때 r을 곱한다.

```
판정 시간 J(t) = P(t) − L₀·r                         (지금 들리는 곡 위치)
시각 시간 V(t) = J(t) + visualOffsetMs·r
입력 시간      = J(t) − handlerDelay·r + inputOffsetMs·r
```

- 게임 로직(롱노트 유지·미스·끝점 판정·auto)은 J를 쓴다. 입력 시간과 같은 "들린 소리" 타임라인이라 미스와 늦은 입력의 순서가 어긋나지 않는다.
- 렌더러와 화면 피드백은 V를 쓴다. auto 노트의 키빔·키봄도 판정용 auto 입력과 별개로 V 기준으로 보인다(#245).
- 판정 창은 바꾸지 않는다. 지금처럼 곡 시간 기준이라 배속을 올리면 실제 시간으로는 좁아진다.

## 검토한 대안

- **화면 기준(기각):** 보이는 노트에 맞춰 판정하고 소리는 어긋나도 둔다. 음악 게임에서 박자를 듣고 누르는 플레이와 맞지 않는다.
- **L을 쓰지 않고 보정에 모두 맡기기(기각):** 입력 오프셋이 L+I를, 시각 오프셋이 D−L을 떠안는다. 구조는 단순하지만 출력 장치를 바꾸면 두 보정을 모두 다시 해야 한다.
- **오디오 오프셋을 남겨 세 개 두기(기각):** 같은 효과를 내는 길이 둘이 되어 어느 값을 바꿀지, 보정 결과가 어디에 들어가는지 흐려진다.
- **시각 보정을 탭 차이로 계산(기각):** 깜빡임 탭(I+D+체감)에서 비프 탭(I+체감)을 빼 D를 구한다. 사람은 소리 박자에는 수십 ms 앞서 누르는 경향이 있고 시각 박자에는 더 흔들려서 체감 항이 서로 지워지지 않는다. 입력 보정을 먼저 해야 하는 순서 제약도 생긴다.
- **시각 보정을 탭 차이로 대략 잡고 보고 다듬기(기각):** 화면이 둘로 늘어나는 데 비해, 판정에 닿지 않는 시각 오프셋에서 얻는 정밀도가 작다.

## Trade-off

- 저장된 오디오 오프셋·입력 오프셋은 의미가 바뀐다. 미출시라 이전하지 않고, 바뀐 뒤 처음 플레이할 때 다시 보정한다.
- L을 곡 시작 때 고정하므로 곡 도중 출력 장치를 바꾸면 그 곡이 끝날 때까지 어긋난다.
- 브라우저의 L 값이 실제와 e만큼 다르면 J가 실제 들린 위치에서 e만큼 어긋나고, 그 e는 입력 오프셋과 시각 오프셋에 같은 양으로 들어간다. 보정과 플레이가 같은 L을 쓰는 한 결과는 맞는다.
- 시각 보정은 사람의 판단이라 ±10~20ms 정도 흔들릴 수 있다. 시각 오프셋은 판정에 닿지 않고 노트가 보이는 위치만 바꾸므로 받아들인다.

## 구현 계획

PR을 셋으로 나눈다. 각 PR은 해당 문서를 함께 고친다.

1. **계산식과 설정:** `GameClock` 새 계산식(L₀ 고정·배속 환산), 오디오 오프셋 제거, `inputOffsetMs` 이름 바꿈과 `visualOffsetMs` 추가(설정 화면 숫자 입력 포함), #245. 이 PR이 머지되면 지금 캘리브레이션 결과는 쓰지 않고, 입력 오프셋은 숫자로 직접 넣는다.
2. **입력 보정:** 비프를 게임과 같은 설정의 `AudioContext` 시계로 예약하고, 탭(`event.timeStamp`)을 오디오 시계로 옮겨 들린 비프 시각(예약 시각 + L₀)과 비교한다. 결과의 반대 부호를 입력 오프셋에 저장한다.
3. **시각 보정:** 비프와 함께 떨어지는 노트 화면에서 시각 오프셋을 직접 맞추는 화면을 만든다.
