# RFD 0031: 소리 기준 타이밍 모델과 입력·시각 오프셋

**Status:** 채택 (2026-10-13, 사용자 결정) · 구현 대기

## 기존 결정과 문제

플레이 중 시간은 [`GameClock`](../../src/game/time/GameClock.ts)이 만든다. 오디오 재생 위치 P(`AudioEngine.currentTimeMs`, `AudioContext.currentTime` 기반)에서 세 시간을 파생한다.

```
판정 시간 J = P + 오디오 오프셋(audioOffsetMs)
시각 시간 V = J + L                          (L = baseLatency + outputLatency, 매 질의 새로 읽음)
입력 시간   = 핸들러 처리 순간의 J − handlerDelay + 입력 오프셋(judgmentOffsetMs)
```

캘리브레이션은 둘이다. Audio 캘리브레이션은 비프에 맞춘 탭으로 오디오 오프셋을, Visual 캘리브레이션은 판정선에 닿는 노트에 맞춘 탭으로 입력 오프셋을 채운다. 부호는 리듬게임 판정 타이밍 관례(늦게 누르면 음수)로 [PR #242](https://github.com/nanana3679/not4k/pull/242)에서 정했다. [PRD §10.3](../prd.md#103-오프셋)은 "원인이 다르므로" 오디오 오프셋(출력 장치)과 입력 오프셋(입력 장치·체감)을 나눴다.

지연은 셋이다.

- **L(소리 출력):** `AudioContext`가 지금 처리한 소리가 스피커에서 L ms 뒤에 들린다. 브라우저가 `baseLatency + outputLatency`로 추정값을 알려 준다. 브라우저에 따라 `outputLatency`가 없을 수 있어(기능 감지로 확인), 없으면 그 몫은 0으로 두고 `baseLatency`는 그대로 쓴다.
- **D(화면 표시):** 지금 그린 렌더 프레임이 모니터에 D ms 뒤에 보인다. 브라우저가 알려 주지 않는다.
- **I(입력):** 키를 누른 순간부터 `KeyboardEvent.timeStamp`까지 I ms가 걸린다. 브라우저가 알려 주지 않는다. 이벤트 처리까지의 지연(`handlerDelay`)은 이미 뺀다.

2026-10-08 의도 감사([#249](https://github.com/nanana3679/not4k/issues/249))에서 다음 문제가 드러났다.

- **T1 시각 시간의 L 부호가 반대다.** 소리는 L만큼 늦게 들리므로 화면도 L만큼 늦게 그려야 한다. 오프셋이 0이고 배속이 1이면 노트가 소리보다 약 2L − D 일찍 판정선에 닿는다. [`audio-visual-sync.md`](../spec/audio-visual-sync.md)의 목표("스피커에서 비트가 나오는 순간 노트가 판정선 위")는 맞지만 공식이 반대다.
- **T3 입력 지연 I를 두 번 뺀다.** Audio 캘리브레이션은 L+I(+체감)를, Visual 캘리브레이션은 D+I(+체감)를 잰다. 두 결과가 모두 입력 시간에 더해지므로 I는 두 번, 화면 지연 D도 입력 시간에서 빠진다.
- **오디오 오프셋이 화면도 움직인다.** 오디오 오프셋은 J를 옮기므로 입력 지연까지 섞인 보정값만큼 노트 표시도 밀린다.
- **T4 Audio 캘리브레이션 비프를 rAF에서 바로 재생한다.** 비프가 기준 박자보다 최대 한 렌더 프레임 늦게 나고, 탭은 이상적인 박자 시각(`performance.now()` 기준)과 비교된다.
- **T6 L을 매 프레임 새로 읽는다.** 지금은 L이 시각 시간에만 들어가므로 값이 흔들리면 노트 위치가 흔들린다(새 모델에서는 판정까지 흔들린다). [RFD 0004](0004-io-timing-consistency.md)(Draft) W4도 세션 시작 때 한 번 읽은 값을 제안했다.
- **T8 재생 배속에서 단위가 섞인다.** P는 곡 시간(실제 경과 × 배속)인데 L·오프셋·`handlerDelay`는 실제 시간 ms 그대로 더한다.
- **D3 `judgmentOffsetMs`는 판정 결과가 아니라 입력 시각을 옮기는 값이라 이름이 하는 일과 맞지 않는다.**
- **[#245](https://github.com/nanana3679/not4k/issues/245) auto 노트의 키빔·키봄이 입력 진행 시각 기준으로 만들어져, 입력 오프셋만큼 늦게 보인다.**

## 결정

1. **소리 기준.** 판정과 화면의 기준은 스피커에서 소리가 들리는 순간이다. 입력은 들린 소리와 비교해 판정하고, 화면은 그 소리에 맞춰 노트를 그린다.
2. **L은 브라우저 값을 자동으로 쓰고, 곡마다 한 번 읽어 고정한다(L₀).**
   - **읽는 시점:** `AudioContext`가 running이 되고 출력이 시작된 뒤 한 번 읽는다. 출력이 시작되기 전에는 0이나 초기 추정치가 나올 수 있으므로, 재생을 시작한 뒤 값이 안정될 때까지 짧게 기다린다.
   - **수명:** 일시정지·재개 동안 유지한다. Retry와 다음 곡은 새 `AudioEngine`(새 `AudioContext`)이라 다시 읽는다.
   - **흡수:** 보정과 플레이가 같은 절차로 같은 L₀를 얻으면 브라우저 값의 고정 오차는 보정값에 흡수된다. 출력 장치를 바꿨을 때 브라우저 값이 실제 지연 변화를 정확히 반영하는 만큼은 다시 보정하지 않아도 된다. 장치마다 브라우저 오차가 다르면 그 차이만큼 두 오프셋을 다시 맞춰야 한다.
3. **오프셋은 입력 오프셋과 시각 오프셋 두 개다.** 오디오 오프셋(`audioOffsetMs`)은 없앤다. 입력과 화면을 같은 양만큼 함께 옮기는 값이라 두 오프셋을 같이 바꾸는 것과 같기 때문이다. 음원 자체의 어긋남은 차트 오프셋(`offsetMs`)이 맡는다. PRD §10.3이 나눈 원인 중 출력 장치는 L₀가 자동으로 맡고, 입력 장치·체감은 입력 오프셋이, 화면 표시는 시각 오프셋이 맡는다.
4. **보정.**
   - **입력 보정:** 비프에 맞춘 탭으로 한다. 비프는 `AudioContext` 시계로 예약해 곡 좌표의 정해진 위치에서 나게 한다. 측정하는 동안 입력 오프셋은 0으로 두고, 탭을 플레이와 같은 방식으로 입력 시간(L₀를 뺀 "들린 소리" 좌표)으로 옮겨 같은 좌표의 비프 위치와 비교한다. 측정 중앙값의 반대 부호를 입력 오프셋에 저장한다.
   - **시각 보정:** 보고 맞춘다. 비프와 함께 노트가 판정선으로 떨어지는 화면에서 사용자가 시각 오프셋을 움직여(슬라이더, 키로 ±1ms) 소리와 노트가 동시에 닿는 값을 고른다. 탭을 쓰지 않으므로 I가 섞이지 않는다.
   - **경로 일치:** 보정 화면은 게임과 같은 `AudioContext` 생성 함수(`latencyHint` 포함), 같은 L₀ 읽기 절차, 같은 `GameClock` 계산(판정·시각·입력 시간과 `handlerDelay` 변환)을 쓴다. 시각 보정의 노트는 게임과 같은 Pixi 노트 그리기 경로로 그린다([#224](https://github.com/nanana3679/not4k/issues/224)에서 게임과 캘리브레이션의 노트 기준을 맞춘 선례). 이 조건이 깨지면 보정과 플레이의 체계 오차가 달라져 흡수되지 않는다.
5. **이름과 부호.**

   | | 입력 오프셋 | 시각 오프셋 |
   |---|---|---|
   | 코드 | `inputOffsetMs` (`judgmentOffsetMs`에서 바꿈) | `visualOffsetMs` (새로 만듦) |
   | 설정 | `Input Offset` | `Visual Offset` |
   | 부호 | 늦게 누르면(SLOW) 음수(PR #242 관례 유지) | 화면이 소리보다 늦게 보이면 양수. 그만큼 노트를 앞당겨 그린다. L₀가 정확하면 화면 지연 D와 같다 |
   | 채우는 곳 | 입력 보정(탭) | 시각 보정(보고 맞추기) |

   장치가 늦으면 입력 오프셋은 음수, 시각 오프셋은 양수로 부호가 반대다. 입력은 PR #242의 판정 타이밍 관례를 따르고, 시각은 지연 자체를 적기 때문이다.
6. **범위.** 이 RFD는 T1·T3·T4·T6·T8·D3·#245와, 새 계산식이 직접 바꾸는 곡 끝 처리(T11)를 다룬다. T5(`ctx.currentTime` stepping 보정, smoothing)는 지터 문제로 RFD 0004 쪽 후속에서, T9(일시정지 중 입력, 재개 직후 이미 들린 L₀ 구간을 J가 다시 지나는 일 포함)·T10(창 전환)·T12(게임 루프 예외)는 각각 이슈로 다룬다.

### 새 계산식

배속을 r(`AudioEngine.playbackRate`, 0.1~4.0으로 제한된 실제 값)이라 한다. 실제 시간(ms) 값은 곡 시간으로 바꿀 때 r을 곱한다. t는 지금 시각(입력 시간에서는 핸들러가 이벤트를 처리하는 시각)이다.

```
판정 시간 J(t) = P(t) − L₀·r                         (지금 들리는 곡 위치)
시각 시간 V(t) = J(t) + visualOffsetMs·r
입력 시간      = J(t) − handlerDelay·r + inputOffsetMs·r
```

- **판정 진행:** 한 프레임에 기한을 진행하는 상한(미스 확정)은 지금처럼 `min(J, 지금의 입력 시간)`이다(PR #242, `stepPlaySession`). 늦게 누르는 사람의 입력 시간은 J보다 뒤처지므로, J까지 바로 진행하면 정당한 늦은 입력보다 미스 확정이 먼저 온다. 큐에 쌓인 입력 처리와 auto 입력 생성 규칙도 지금처럼 둔다. auto 입력은 진행 상한까지 만들되, 이미 수집한 입력이 그보다 앞서 있으면 그 시각까지(`max(진행 상한, 큐의 마지막 입력 시각)`) 먼저 만들어 순서를 지킨다.
- **시각 시간을 쓰는 곳:** 시간으로 위치를 정해 그리는 것(노트·마디선·구간, auto 노트의 키빔·키봄 같은 시각 피드백)은 V를 쓴다(#245, auto 키봄은 `SessionRendererAdapter`의 확정 효과 경로도 포함). 실제 입력에 대한 피드백(키빔·판정 글자)은 처리 즉시 보인다.
- **곡 끝:** `AudioEngine.currentTimeMs`는 재생 구간 끝에서 멈추므로 J = P − L₀·r은 끝에 닿지 못한다. 오디오가 끝난 뒤에도 J를 실제 시간으로 계속 진행한다. 결과로 넘어가는 조건은 두 가지를 모두 만족할 때다. (1) 들린 끝(오디오 끝 + L₀)에 도달했고, (2) 진행 상한 `min(J, 지금의 입력 시간)`이 마지막 노트의 판정 기한(늦은 판정 창 끝)을 지났다. 그 전에 남은 기한을 강제로 정산(`finalize`)하지 않는다. 곡 끝 L₀·r 안의 노트가 소리가 나기 전에 정산되거나(오프셋이 0인 사람에게도 새로 생기는 일), 마지막 노트의 늦은 판정 창이 잘리는 일(T11)을 함께 막는다. 이 대기 중에 일시정지하면 진행을 멈추고, 재개하면 멈춘 곳부터 이어 가며, 이미 끝난 음악을 다시 재생하지 않는다.
- **판정 창과 표시 단위:** 판정 창은 바꾸지 않는다. 지금처럼 곡 시간 기준이라 배속을 올리면 실제 시간으로는 좁아진다. Show Timing Diff·FAST/SLOW·디버그 `deltaMs`도 곡 시간 ms로 둔다. 디버그 로그의 오프셋 추천값은 입력 오프셋 기준이며 ÷r로 실제 ms로 바꿔 보여 주고, 노트 위치 기록(`noteCenterY`)은 V 기준으로 계산한다.

## 검토한 대안

- **화면 기준(기각):** 보이는 노트에 맞춰 판정하고 소리는 어긋나도 둔다. 음악 게임에서 박자를 듣고 누르는 플레이와 맞지 않는다.
- **L을 쓰지 않고 보정에 모두 맡기기(기각):** 입력 오프셋이 L+I를, 시각 오프셋이 D−L을 떠안는다. 구조는 단순하지만 출력 장치를 바꿀 때마다 두 보정을 모두 다시 해야 한다. 브라우저 값을 쓰면 그 값이 장치 차이를 반영하는 만큼은 다시 보정하지 않아도 된다.
- **오디오 오프셋을 남겨 세 개 두기(기각):** 같은 효과를 내는 길이 둘이 되어 어느 값을 바꿀지, 보정 결과가 어디에 들어가는지 흐려진다.
- **시각 보정을 탭 차이로 계산(기각):** 노트 탭(I+D+체감)에서 비프 탭(I+체감)을 빼 D를 구한다. 사람은 소리 박자에는 수십 ms 앞서 누르는 경향이 있고 시각 박자에는 더 흔들려서 체감 항이 서로 지워지지 않는다. 입력 보정을 먼저 해야 하는 순서 제약도 생긴다.
- **시각 보정을 탭 차이로 대략 잡고 보고 다듬기(기각):** 화면이 둘로 늘어나는 데 비해, 판정에 닿지 않는 시각 오프셋에서 얻는 정밀도가 작다.

## Trade-off

- 오디오 오프셋은 없어지고, `judgmentOffsetMs`는 키 이름이 바뀌어 저장값이 버려진다. 미출시라 이전하지 않고, 옛 키(`audioOffsetMs`, `judgmentOffsetMs`, 예전 `offsetMs` 이전 코드)는 설정에서 지운다. 바뀐 뒤 처음 플레이할 때 다시 보정한다.
- L₀를 곡마다 고정하므로 곡 도중 출력 장치를 바꾸면 그 곡이 끝날 때까지 어긋난다.
- 브라우저 보고값이 실제보다 e만큼 크면(e = L₀ − L) J는 실제 들리는 위치보다 곡 시간으로 e·r만큼 뒤처지고, 보정 결과는 입력 오프셋 −I + e, 시각 오프셋 D + e가 되어 두 값이 모두 실제 시간으로 +e를 떠안는다. 보정과 플레이가 같은 절차로 같은 L₀를 얻는 한 판정과 화면은 맞는다.
- 시각 보정은 사람의 판단이라 탭 보정보다 흔들릴 수 있다. 시각 오프셋은 판정에 닿지 않고 노트가 보이는 위치만 바꾸므로 받아들인다.
