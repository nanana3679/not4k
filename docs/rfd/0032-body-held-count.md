# RFD 0032: hold 수로 바디의 시작과 유지 판단

- 날짜: 2026-10-15
**Status:** 일부 채택 · 결정 기록(2026-10-15~2026-10-20, 부록 B 변경 로그) · 유지 유예는 임시 20ms · release 계약 재검토 중 · double head 연결의 head별 판단은 잠정 · 엔진 구현 중(2026-10-17~, [#287](https://github.com/nanana3679/not4k/issues/287), 회귀 장치 PR #288·`LaneHoldTracker` PR #289 머지) · 판정 코어 타이밍 규칙 기록(2026-10-20, PR #326, [§2-3 구현 규칙](#구현-규칙-판정-시각과-입력-순서))
- 범위: 키 교대 논의에서 합의한 판정 모델의 전환 방향. 전체 상태 전이의 명세·검증 완료를 뜻하지 않는다. 잔여 검토는 [PRD의 미정 사항](../prd.md#12-미정-사항)에서 추적한다.
- 대조 기준: `main`의 `5aa6006a1ca257beee45da657b3461c42001da08`과 PR #188의 `c847d89f31789af8c09825d952a283edc4b47a68`. 아래 실제 실행 결과는 PR #188 기준이다. 다만 [§2-3 구현 규칙](#구현-규칙-판정-시각과-입력-순서)의 “수리 브랜치 실측”은 공개 전 로컬 브랜치 `repair/hold-count-core`의 `7fece8e` 기준이다.

이 문서는 롱노트 바디의 시작과 유지를 등록된 유지 키가 아니라 같은 레인의 실제 hold 수로 판단하는 모델을 정하고, 그 모델에서 up이 실제 release·감소 release·연결 release·`holdOnly` 끝 중 어디에 쓰이는지를 패턴별로 정한다. 결정은 패턴마다 허용 입력과 기대 결과를 사용자에게 확인하며 내렸고, 남은 적용 조건은 계속 확인하며 [PRD의 미정 사항](../prd.md#12-미정-사항)에서 추적한다. **판정 엔진은 아직 이전 모델(RFD 0020의 등록 키 기반)이며, 이 문서의 규칙은 구현하지 않았다.**

본문은 주제별로 지금 유효한 규칙만 적는다. 각 항목은 규칙, 대표 차트와 입력·기대 결과, 근거가 된 사용자 발언(원문 그대로, 날짜 포함)으로 이루어진다. 기대 결과는 확인한 규칙에서 도출한 값이며, 괄호 안의 “PR #188”은 c847d89의 실제 실행 결과다. 판정 창은 따로 적지 않으면 Normal 기준(Perfect ±41ms, Good ±120ms)이다. 노트 이름은 N1, N2, …이고 `N1u2`는 N1의 둘째 unit이다. 채택하지 않은 대안은 [부록 A](#부록-a-검토한-대안)에, 결정과 번복의 순서와 이전 절 번호(§1~§37)는 [부록 B](#부록-b-변경-로그)에 둔다. 공식 용어는 [glossary의 release 판정](../context/glossary.md#release-판정), 미정 사항은 PRD를 따른다.

## 1. 배경과 원칙

### 1-1. 기존 결정과 문제

현재 [RFD 0020](0020-note-judgment-units-and-inheritance.md)은 head·시작 입력·정당한 승계로 등록한 키를 바디 유지에 사용한다. 고정 물리 owner를 두는 모델은 아니지만, 바디 도중 아무 노트에도 쓰이지 않은 down은 유지 키가 되지 않는다.

사용자가 제시한 필요는 다른 레인의 Point를 치기 위해 진행 중인 롱노트를 다른 손으로 넘기는 것이다. 예를 들어 왼손 E/R로 유지하던 레인 2/3을 오른손 PageDown/Numpad7로 먼저 잡고 왼손을 떼는 입력이다. 바디 유지에 새 키가 참여하지 못하면 이 손 이동이 실패한다. 같은 레인 바디 내부의 Point 배치 제약만으로는 다른 레인까지 포함한 손 이동 필요를 설명할 수 없다.

기존 이력에는 raw held의 자동 시작, up의 잘못된 release 배정, 12ms 유예의 보류 처리 문제가 함께 있었다([RFD 0008](0008-release-engage-key-attribution.md), [RFD 0014](0014-press-release-pairing-key-lifecycle.md), [RFD 0015](0015-binary-release-judgment.md), RFD 0020). 이번 선택은 그 보정을 모두 복원하는 결정이 아니라, 바디가 요구하는 입력과 Point가 요구하는 입력을 다시 구분하는 결정이다.

**PR #188 결정 4와 달라지는 사례.** N1=`holdOnly [1000,1500]`, N2=`long [1500,1560]`, N3=`head 1560`, N4=`long [1560,1760]`이다.

```text
노트: holdOnly 1000-1500 | long 1500-1560 | head 1560 | long 1560-1760
입력: A 1000-1430 | D 1490-1760
```

PR #188은 D down을 N2의 시작에 소비해 N1 holdOnly Perfect, N3 head Miss, N4 release Perfect이며 Miss 1이다. 당시 사용자는 A를 일찍 뗐다면 D 뒤에 한 번 더 눌러야 한다고 결정했다.

[PR #188의 기존 결정 4와 테스트](https://github.com/nanana3679/not4k/blob/c847d89f31789af8c09825d952a283edc4b47a68/src/game/judgment/noteJudgmentHoldOnlyCases.test.ts#L720-L741)

새 규칙의 기대 결과는 N1 holdOnly Perfect, N3 head Great(-70), N4 release Perfect이며 Miss 없이 Full Combo이다. D down은 N3를 판정하고, D의 hold 수 1이 N2와 N4를 유지한다. N2에는 별도 release 점수 항목이 없으므로 한 up으로 release 둘을 처리하는 것도 아니다. 사용자는 “D 한 번의 누름으로 N3 판정과 N2·N4 유지를 함께 충족하는 결과”에 “인정”이라고 답했다(2026-10-15). 따라서 이 사례의 추가 down 요구를 폐기한다. 이는 RFD 0020의 “head 없는 바디도 시작 down을 소비한다”는 전제를 바꾸는 명시적 선택이며, 기존 결과를 실수로 보존하지 못한 회귀로 취급하지 않는다.

### 1-2. 패턴을 먼저 정하고 교대 자체의 점수 손해를 금지

사용자는 교대와 끝 판정 창의 겹침을 제작 지침만으로 피하기 어렵다고 보았다. 16분음표 한 칸은 `15000 / BPM` ms이므로, 끝보다 한 칸 앞의 up이 Normal의 Good ±120ms 안에 드는 경계는 125 BPM, Easy의 ±150ms에서는 100 BPM이다. 이는 판정 창과 박 간격의 환산이며 특정 패턴 전체의 허용 여부를 결정한 것은 아니다.

사용자는 판정 규칙보다 게임에서 다룰 패턴과 각 패턴에서 허용할 입력을 먼저 정하는 접근을 제안했다. 허용하는 연주가 Miss만 피하면 되는 것인지, 교대 자체로 점수 손해가 없어야 하는 것인지 확인하자 다음을 선택했다(2026-10-16).

> 교대 자체로는 점수 손해가 없어야 하는 것

**허용한 교대 자체로는 점수 손해가 없어야 한다.** 이 목표를 “일반 롱노트의 교대 up을 엔진이 언제나 release에서 제외한다”는 규칙으로 확대하지 않는다. 단독 롱노트의 끝 창에서 교대한 up은 이른 release로 인정하고 그 손해가 차트의 의도가 아니면 Grace를 배치한다([§2-5](#2-5-바디-중간-교대와-끝-창-안의-교대)). 판정 모델이 손해 없이 처리해야 하는 연주는 [의도된 연주](#9-1-의도된-연주의-정의)로 정의한다. 교대로 인정하는 범위와 실제 끝 입력의 요구는 패턴별로 확인한다.

검토는 다음 순서를 따른다.

- 차트 패턴 자체의 허용 여부와 그 패턴에서 각 입력의 허용 여부·기대 결과를 구별한다. 하나의 패턴에서 입력을 바꾸며 확인하고 `pnpm case:image`의 노트 이름을 사용한다.
- 현재 엔진의 실행 결과, 사용자가 직접 확인한 결과, 규칙에서 도출한 예상 결과를 구분한다. 엔진에서 나온 등급을 새 모델의 정답으로 자동 채택하지 않는다.
- 합의한 사례를 회귀 테스트의 기준으로 삼고, 전체를 일관되게 설명하는 공통 판정 규칙을 찾는다. 결과가 충돌하면 어떤 패턴·입력을 지원할지 다시 판단하며 입력의 의도를 추측하는 예외를 자동 추가하지 않는다.
- 실제 떼는 동작의 필요, 한 up으로 여러 실제 release를 중복 처리하지 않는 원칙, hold 수 기반 시작·유지와 임시 20ms 유지 유예를 출발점으로 둔다. 이 원칙들 사이의 충돌도 사례로 드러내며 조용히 변경하지 않는다.
- 손 선택 사전 유도와 자연스러운 탭·교대 up을 함께 보는 제작 지침([§9-3](#9-3-제작-지침-48항))은 유지한다. 제작 지침을 근거로 허용한 교대의 점수 손해를 정당화하거나, 패턴별 합의 전에 에디터의 자동 금지 규칙을 추가하지 않는다.

이 기준을 정하며 이른 up 보관·등급 개선, 이진 release, 일반 롱노트의 `holdOnly` 기본화를 함께 비교했으나 채택하지 않았다([부록 A-4](#a-4-이른-up-보관과-등급-개선-이진-release-holdonly-기본화)).

### 1-3. 바디와 Point의 역할

**바디는 구간에서 필요한 hold 수와 끝 판정을 담당한다. 누르는 타이밍을 판정하려면 별도 Point를 배치한다.** 사용자의 설명은 다음과 같다(2026-10-15).

> 왜냐면 우리 롱노트는 시작 부분에 판정이 없고 끝부분에만 있으니까 늘어나는 부분에 판정 없어 판정이 필요하면 거기에 싱글 포인트 놓으면 돼

- head 없는 바디의 시작에는 시작 점수나 시작 타이밍 등급이 없다.
- Point를 처리한 down의 hold도 바디 유지에 참여한다. 그 Point 앞에서 끝나는 바디에도 적용한다([§1-1](#1-1-기존-결정과-문제)의 D). Point 자체의 입력 요구와 등급은 남는다.
- 사용자는 등록된 유지 키만 인정하는 안과 시작 후 누른 여분 키만 교대에 인정하는 안 대신, 같은 레인의 실제 hold 수로 판단하는 방향을 선택했다([부록 A-1](#a-1-등록-키만-인정하거나-나중에-누른-키만-교대에-인정)). 미리 누른 키와 바디 도중 누른 키를 모두 포함하고, Point는 별도로 down을 판정한다.

### 1-4. Trade-off와 영향 범위

미리 누른 키로 독립 시작과 증가 경계를 충족할 수 있어, 기존에 시작용 down을 요구하던 차트의 치는 법이 달라진다. 제작자가 누르는 타이밍을 요구하려면 해당 위치에 Point가 있어야 한다. 키 교대가 가능해지는 대신 끝 창 안의 여분 up은 release 등급이나 이후 노트에 영향을 줄 수 있다.

이 결정은 [RFD 0020 §3](0020-note-judgment-units-and-inheritance.md#3-대안과-채택-이유)에서 채택하지 않았던 “raw held 또는 다른 Point의 down을 공유해 독립 시작”을 뒤집는다. RFD 0020은 정상적인 앞 노트의 입력이 뒤 바디를 조기 실패시키는 문제와 시작 생략을 이유로 들었고, 새 모델에서도 그 위험은 남는다. 예를 들어 Point 1000 뒤 head 없는 `holdOnly [1010,1500]`에서 A를 1000–1030에 탭하면, A의 hold로 바디가 1010에 시작하고 A up 1030부터 hold가 부족하다. 유지 유예만 적용하면 1050에 실패해 시작의 Good 기한(1130) 안인 1060에 B를 눌러도 되살리지 못한다. 이 조기 실패의 위험은 시작 직후의 재충전([§8-1](#8-1-시작-직후의-재충전))으로 해소했다. 실패 기한이 1130으로 늦춰지고 B down 1060이 바디를 이어 간다. 시작 생략은 받아들인 trade-off로 남는다.

영향은 중간 교대 허용 한 곳에 그치지 않는다. `NoteJudgmentCore`의 시작 입력 소비·Point 우선순위·유지 키 계산·release 자격, 시작과 승계를 전제한 판정 회귀, 관련 AutoPlayer·튜토리얼·Lab의 기대 결과를 함께 대조해야 한다. hold 수 모델 전환 자체는 점수 항목을 새로 추가하지 않는다(head가 있는 2→1의 감소 release는 [§6-3](#6-3-head가-있는-21과-감소-release)에서 RFD 0020 §2.13의 제거를 되돌린 것이다).

전체 계약을 확정하여 이행할 때는 `docs/context/glossary.md`를 먼저 정리하고 루트 및 `src/game/CONTEXT.md`, 노트·판정 사례 명세, RFD 0020의 대체 범위를 함께 동기화한다. 판정 PR 작성 시 사용자가 읽는 학습 HTML도 설명·코드 범위·기준 SHA를 맞춘다. glossary와 요약 문서에는 패턴별로 확인한 새 모델의 규칙을 “후속 모델”·“엔진 이행 전”으로 표시해 반영했으며, 구현은 아직 이행하지 않았다.

## 2. 기본 모델

### 2-1. hold 수로 시작과 유지 판단

- **single 바디는 같은 레인의 서로 다른 키 1개 이상, double 바디는 2개 이상의 hold로 유지한다.** 특정 시작 키가 계속 눌려 있는지를 유지 조건으로 삼지 않는다. 미리 누른 키와 바디 도중 누른 키를 모두 포함한다.
- **head 없는 바디의 시작은 down을 별도로 소비하지 않는다.** 독립 바디와 연결의 1→2 증가 모두 미리 누른 키로 필요한 hold 수를 채울 수 있다. down은 Point가 소비한다.
- **시작 시 필요한 hold 수가 부족하면 기존처럼 S+Good까지 채울 수 있다.** 사용자는 시작 후 50ms에 누른 사례에 대해 “지금처럼 good 안에 누르면 됨”이라고 확인했다(2026-10-15). 시작 점수나 시작 타이밍 등급을 추가하지 않는다. 시작 직후 hold를 잃은 경우도 같은 기한까지 다시 채울 수 있다([§8-1](#8-1-시작-직후의-재충전)).
- head가 있는 바디는 head를 처리한 실제 down부터 유지를 판단한다. 적용 범위는 [§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)을 따른다.
- **부분 실패 뒤 hold 수가 회복되어도 실패한 unit은 되살리지 않는다.** 새 키는 남아 있는 정상 unit의 유지에 참여할 수 있으며, 실패한 unit에 그 키를 고정 배정하지 않는다.

마지막 항목은 `doubleLong [1000,3000]`에서 A 1000–1800, B 1000–3000, C 1830–3000으로 한 몫이 유지 실패한 사례([§2-2](#2-2-유지-유예)의 사례 1)에서 확인했다. 사용자는 “N1u2는 실패했으니까 냅두고”라고 답하고, C가 남은 유지 키와 교대할 수 있으며 C의 up도 release를 처리할 수 있다고 설명했다(2026-10-15). 원래 사례에서는 A가 1800에 이미 떼어진 상태이므로, 사용자의 “a를 떼면 c가 교대”는 계속 누르고 있던 B를 나중에 떼는 상황으로 해석하여 대화에서 명시했다. 그 변형의 기대 결과는 C의 hold로 N1u1을 계속 유지하는 것이다. 모델상 실패는 특정 C 키에 귀속되지 않고 N1에서 hold 수가 부족했던 몫에 해당한다.

### 2-2. 유지 유예

사용자는 교대할 때 아주 잠깐 hold가 끊어질 수 있으므로 유예도 필요하지 않느냐고 지적했다. hold 수 전환만으로는 필요한 수보다 적어지는 공백을 허용할 수 없고, 시작의 S+Good 허용도 바디 도중의 공백에 대한 유예를 대신하지 않는다.

- **유지 부족의 Miss 확정을 G ms 보류한다. G는 임시로 20ms이며 최종값은 나중에 정한다.** 사용자는 유지 실패에만 유예를 적용하는 안에 “좋음”이라고 답한 뒤, “일단 유예시간은 임시로 20으로 하고 확정은 나중에”라고 결정했다(2026-10-15). 최종값의 확정과 구체적인 경계 대조는 [PRD의 미정 사항](../prd.md#12-미정-사항)에서 추적한다.
- **각 몫에 필요한 hold 수 기준 아래로 내려간 때부터 그 기준을 회복할 때까지 각각 시간을 잰다.** double에서는 hold 수가 2 미만인 시간과 1 미만인 시간을 따로 잰다. 0→1 회복은 1 기준의 공백만 끝내며 2 기준의 공백은 계속된다. 각 기준을 G 안에 회복하면 해당 몫을 실패로 확정하지 않고, 회복하지 못하면 그 몫의 유예 기한에 실패를 확정한다.
- **유예는 유지에만 적용한다.** 실제 release를 교대 여부를 알아보려고 보류하지 않으며, 이미 처리한 Point·실제 release·`holdOnly` 완료를 재입력이나 hold 회복 때문에 취소하지 않는다([§2-3](#2-3-release-등급과-자격-판정-창-기준)). 끝 창 안의 up이 이미 실제 release를 처리했다면 이 유예가 그 등급을 되돌리지 않는다.
- **경계에서는 다른 기준을 쓴다.** head가 있으면 head를 처리한 down부터(적용 범위는 [§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)), head 없는 시작과 head 없는 경계 뒤 바디는 S+Good까지([§8-1](#8-1-시작-직후의-재충전), [§8-2](#8-2-head-없는-경계)) 판단한다. 경계에서 떨어진 바디 중간의 끊김에는 유예만 적용한다.

**사례 1: double 바디에서 30ms 동안 한 개 부족.**

```text
노트: dlong 1000-3000
입력: A 1000-1800 | B 1000-3000 | C 1830-3000
```

1800~1830의 30ms 동안 실제 hold 수는 1이다. 20ms 유예를 적용한 기대 결과를 묻자 사용자는 “유예보다 기니까 c는 끊어지지”라고 답했다(2026-10-15). 30ms 공백이 유예보다 길어 유지 실패가 발생한다(PR #188은 유예 없이 1800에 유지 실패를 확정해 Perfect 1·Miss 1). 실패한 몫의 처리는 [§2-1](#2-1-hold-수로-시작과-유지-판단)을 따른다.

**사례 2: hold 수 2→1→0→1→2의 유예는 각 hold 수 기준으로 계산.**

```text
노트: dlong 1000-3000
입력: A 1000-1800 | B 1000-1810 | C 1815-3000 | D 1825-3000
```

사용자는 각 hold 수 기준을 회복할 때까지 재는 방식을 선택했다(2026-10-15). 먼저 부족해진 몫부터 새 누름으로 채우는 계산은 채택하지 않았다([부록 A-5](#a-5-double-공백을-먼저-부족해진-몫부터-채우는-계산)).

> 홀드 수가 2에서 감소해서 다시 2가 되는 기간
> 1에서 다시 1이 되는 기간

hold 수 2 기준의 공백은 1800~1825의 25ms로 유예 20ms를 초과하므로 N1u2는 유지 실패다. hold 수 1 기준의 공백은 1810~1815의 5ms로 유예 안에 회복하므로 N1u1은 유지한다. 1815의 회복으로 2 기준의 유예까지 취소하거나 새로 시작하지 않는다. 1825에 hold 수가 2로 회복되어도 이미 실패한 N1u2는 되살리지 않는다. 기대 결과는 N1u1 release Perfect와 N1u2 유지 Miss로 Perfect 1·Miss 1이다(PR #188은 유예가 없어 1800과 1810에 각각 유지 실패, Miss 2).

**유예 길이의 기준.** 제품 기준은 초견에서 필요한 손 교대를 불합리하게 실패시키지 않는 것이다. 사용자는 “게임으로서 사용자가 불합리함을 느끼지 않을 정도”, “처음 보는 차트에서 … 어쩔수 없이 교대가 일어났을때 충분히 반응할 시간이 있어야” 한다고 설명했다(2026-10-15). 지각상 동시로 느끼는 한계만으로 수치를 정하지 않고, 실제 교대에서 발생하는 hold 부족 시간과 플레이 체감을 확인해 최종값을 정한다.

- 유지 유예가 직접 보호하는 시간은 필요한 hold 수보다 적어진 순간부터 회복할 때까지이다. 차트를 알아보고 교대를 결정하는 데 필요한 시간과는 시작점이 다르므로, 초견의 대응 가능성을 검토할 때에는 노트가 미리 보이는 시간도 구분해서 살핀다. 이 구분으로 노출 시간이나 스크롤 설정을 변경하기로 결정한 것은 아니다.
- 참고 자료로, Lange 등의 촉각 실험에서는 양손 검지의 전기 자극에 30ms 차이를 주었을 때 약 52~55%, 45ms 차이에서는 약 30~34%의 시행을 동시라고 보고했다. 이는 감각 자극의 동시성 판단이며, 키보드 교대의 운동 오차나 적절한 게임 유예를 직접 측정한 결과가 아니다. 이 수치를 게임의 고정 허용시간으로 간주하지 않는다.

[Lange 등, Fluctuations of Prestimulus Oscillatory Power Predict Subjective Perception of Tactile Simultaneity](https://pmc.ncbi.nlm.nih.gov/articles/PMC4705338/)

과거 논의에서는 `holdOnly`의 이른 완료를 12ms 기다린 뒤 같은 키의 복귀로 취소하고, 성공을 원래 up 시각 순서로 반영하려 전 레인의 결과를 보류하는 큐까지 검토했다. 이 모델은 [RFD 0020 §2.9](0020-note-judgment-units-and-inheritance.md#29-보류-판정의-콤보는-확정-순서로-반영--후속-채택)의 확정 순서를 유지하므로 그 소급 순서를 위한 전체 결과 보류를 요구하지 않는다. 대신 유지 Miss의 확정이 늦어진다.

### 2-3. release 등급과 자격, 판정 창 기준

**상태:** 아래 계약은 2026-10-15에 정했다. 2026-10-16 [§1-2](#1-2-패턴을-먼저-정하고-교대-자체의-점수-손해를-금지)의 기준(교대 자체의 점수 손해 금지)에 따라 release 후보·소비·등급을 재검토하기로 했으며, 그 뒤 패턴별 결정이 연결 release([§4-1](#4-1-연결-release)), 경계 전 연결 release([§4-2](#4-2-경계-전에-뗀-연결-release)), 창 밖 up([§2-5](#2-5-바디-중간-교대와-끝-창-안의-교대)), 시작 여부와 무관한 자격(아래), `holdOnly` 끝의 up([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다))을 정했다. 재검토를 마쳤다고 따로 정한 기록은 없으므로 이 계약은 재검토 중인 기준으로 둔다([glossary의 release 판정](../context/glossary.md#release-판정)도 같다).

- **등급:** 실제 release는 Perfect / Great / Good / Miss이며 raw FAST/SLOW를 유지한다. RFD 0015의 이진 release로 되돌리지 않는다.
- **후보:** hold 수를 감소시키는 모든 유효 up을 후보로 받는다. 1→0으로 제한하지 않고 2→1 등도 같은 기준으로 처리한다. 교대·여분 키·Point 탭에서 나온 up이라는 이유로 후보를 제외하지 않는다. 연결 release([§4-1](#4-1-연결-release))과 경계 전 연결 release([§4-2](#4-2-경계-전에-뗀-연결-release))에 쓰인 up은 실제 release에 다시 쓰지 않는다.
- **소비:** 판정 창과 대상 자격을 충족한 미처리 실제 release 중 차트 시각이 가장 이른 항목을 처리한다([§2-4](#2-4-여러-끝에-적격인-up의-순서와-키-재사용)). 한 up은 하나만 처리하고, 완료한 항목을 다시 소비하지 않는다. 적격 항목이 없는 up에 별도 점수 항목이나 release Miss를 만들지 않는다.
- **보류와 취소 없음:** 교대 여부를 알아보기 위해 실제 release를 20ms 보류하지 않는다. 적격 up은 실제 시각으로 판정하고, 뒤에 다시 누르거나 hold 수가 회복되어도 후보나 판정을 취소하지 않는다.
- **동시 입력:** 같은 timestamp의 유지 확인과 개별 up의 release 처리를 구별한다. batch 전후 hold 수가 같더라도 유효 up은 존재하며, 서로 다른 키의 처리 순서 때문에 결과가 달라져서는 안 된다.
- **책임과 Grace:** 여분 up이 이후 노트에 영향을 주는 결과는 입력한 플레이어의 책임으로 둔다. 사용자는 끝 근처의 교대 up이 이른 Great/Good을 만들 수 있다는 점을 확인했고, 제작자가 필요한 구간의 롱노트에 Grace를 배치하는 방향을 받아들였다(2026-10-15). Point의 `grace`와 롱노트의 `holdOnly`라는 대응과 각각의 면제 동작은 유지하며, 새로운 `grace release` 타입이나 이진 release를 추가하지 않는다.

**모든 감소를 후보로 받는 근거.** N1=`double holdOnly [1000,1500]` → N2=`long [1500,2000]`, A 1000–2000, B 1000–2500에서 N2 끝의 A up은 2→1이다. 1→0에서만 후보를 만들면 이 up으로 N2를 끝낼 수 없다([부록 A-3](#a-3-10에서만-release-후보를-만들고-회복으로-취소)). 사용자는 다음과 같이 다시 물었다(2026-10-15).

> 2-1을 릴리즈로 봐야할지에 대한 문제인데 개수에 상관없이 감소가 발생하면 릴리즈로 봐야할까?

A up 2000(2→1)은 N2의 release 후보가 되며 결과는 Perfect 3이다(PR #188 같음). N1의 면제 때문에 남은 키를 모두 떼도록 강제하지 않는다. 이어 사용자는 “유예를 롱노트가 끊어지지 않게만 하는데 사용하고 릴리즈는 발생시키자는 말이지?”라고 뜻을 확인했다. 유지 실패에만 20ms를 적용하고 적격 up의 실제 release는 뒤의 누름으로 취소하지 않는 방향이라고 설명하자 “그렇게 결정하고 너가 지적한 차트 제작시 유의사항도 반영해줘”라고 결정했다(2026-10-15).

이 선택으로 끝 창 안의 교대 up이나 자연스러운 Point 탭 up이 실제 release를 일찍 처리할 수 있다. 유지가 끊기지 않았다는 사실이나 20ms 안의 재누름은 그 등급을 보호하지 않는다. 후보의 용도를 추측하여 보정하는 대신, 제작자가 요구하는 release와 손 이동을 배치로 드러낸다([§9-3](#9-3-제작-지침-48항)).

**release 자격은 판정 창으로 정한다(2026-10-17).** `head 1000` → head 없는 `long [1100,1200]`에서 A 1000–1090 뒤 A 1140–1200을 치면, A up 1090은 N2 시작 전이지만 N2 끝의 Good 창(1080~1320) 안이다. 시작한 바디만 release를 받는 안을 제시하자 사용자는 다음을 차례로 물었다.

> 그럼 첫번쨰 릴리즈를 1090 이  아니라 1100 이면 릴리즈가 통과되는거?

> 그럼 a를 1080 down 1090 up 일때 1080 이 n2 를 끌어와서 미리 시작하게 되는데 이때는?

> 교대 시 릴리즈 흡수하는 거처럼 롱노트 시작 부근에서 down이 발생하면 흡수해야 하나?

> 흡수 안한다 치더라도 판정 윈도우가 기준이 아니라 롱노트가 시작했는지 여부로 판정이 바뀌는게 어색함

시작 여부를 기준으로 하면 결과가 1100을 경계로 갈린다. A up 1105는 1100에 A로 시작한 바디의 이른 release Good(−95)이다. head 없는 시작은 down을 소비하지 않으므로 A down 1080은 N2를 미리 시작시키지 않는다(PR #188은 그 down을 시작으로 소비해 A up 1090이 Good(−110)). 판정 창 기준안에 사용자는 “ㅇㅇ”라고 답했다(2026-10-17).

- **바디의 끝 창 안에 든 up은 그 바디가 시작했는지와 관계없이 release 후보다.** 그 release로 바디가 끝나며, 시작하지 않은 바디라도 그 뒤에 시작 실패를 세지 않는다. 위의 세 입력(A up 1090, A up 1105, A 1080–1090)은 모두 Perfect 1·Good 1이며, 결과가 갈리는 지점은 끝 창이 열리는 1080이다.
- 끝 창이 시작을 덮을 만큼 짧은 바디(Good 창 두 개보다 짧음)는 누르지 않아도 다른 노트의 up으로 끝날 수 있다. 이런 짧은 바디는 사실상 탭처럼 판정된다.
- 시작 근처의 down을 바디가 흡수하는 규칙은 두지 않는다. down은 지금처럼 Point가 소비하고, 바디의 시작에는 쓰이지 않는다([부록 A-8](#a-8-head-없는-시작의-down-흡수)).
- 실패한 바디는 되살리지 않으므로([§2-1](#2-1-hold-수로-시작과-유지-판단)) release 자격이 없다. 적격 대상 중 차트 시각이 가장 이른 끝을 고르는 순서([§2-4](#2-4-여러-끝에-적격인-up의-순서와-키-재사용))는 그대로다.

시작한 바디만 release를 받는 안은 [부록 A-9](#a-9-시작한-바디만-release를-받기)에 둔다.

#### 구현 규칙: 판정 시각과 입력 순서

**상태:** 판정 코어 구현([#287](https://github.com/nanana3679/not4k/issues/287))이 따르는 시각 규칙이다(2026-10-20 기록). 위의 등급·자격·판정 창은 바꾸지 않고, 진행과 입력이 같은 시각에 겹칠 때와 입력이 늦게 전달될 때 무엇을 먼저 반영하는지만 정한다. 이 규칙은 구현 계획의 타이밍 계약([#287 계획 개정 댓글](https://github.com/nanana3679/not4k/issues/287#issuecomment-6246317885))으로 제시했고, 사용자는 그 개정안 전체에 “ㅇㅋ”라고 답했다(2026-10-18). 아래 기대 결과는 이 규칙에서 도출한 값이며, “수리 브랜치 실측”은 공개 전 로컬 브랜치 `repair/hold-count-core`(7fece8e)의 hold 수 코어 실행 결과다. 코어 경계의 구현 계약(레인별 clamp, 한 drain의 늦은 입력 묶음, 프레임 독립 범위 등)은 [게임 코어 명세](../spec/game-core.md#판정-실행-구조)에 둔다.

- **입력 시각 등급:** 입력이 정하는 판정(Point, 실제 release, `holdOnly` 끝이 가져간 up)은 그 입력의 raw 시각으로 판정 창 안인지와 등급을 정한다. FAST/SLOW가 있는 판정은 FAST/SLOW도 raw 시각으로 정한다. Grace 노트와 `holdOnly`의 유효 입력은 Perfect이며 FAST/SLOW를 만들지 않는다. 확정 시각은 제때 받은 입력이면 입력 시각, 늦게 전달된 입력(관측 batch)이면 관측한 시각이며, 현재 콤보는 확정 순서를 따른다([RFD 0020 §2.9](0020-note-judgment-units-and-inheritance.md#29-보류-판정의-콤보는-확정-순서로-반영--후속-채택)). 예: `head 1000`(Point)의 raw 1000 down을 1080에 관측하면 Perfect(0)이고 확정 시각만 1080이다(지금 게임의 `ObservedBatch.test.ts`와 같다).
- **기한과 같은 시각의 입력은 기한 안:** Point의 Good 기한, 시작·유지 실패 기한, release Miss 기한(E+Good)은 그 시각을 지나야 확정한다. 프레임이 기한 시각에 정확히 멈춰도 그 기한은 열어 두고 같은 시각의 입력을 먼저 반영한다. 지난 기한은 기한 시각 순서로, 기한 시각마다 한 묶음으로 확정한다. 예: `head 1000`에서 프레임이 정확히 1120까지 진행한 뒤 다음 프레임에 down 1120이 오면 Good(+120)이다(지금 게임과 수리 브랜치 같음).
  - **종속 0점의 묶음:** 기한 정산에서 생긴 종속 0점은 그 기한 시각의 묶음에 들어간다(늦은 전달로 다시 계산해 생긴 종속 0점은 관측한 시각의 묶음, 아래 늦은 전달 항목). 그래서 종속 0점이 원인이 된 실패나 head Miss와 늘 같은 묶음인 것은 아니다. 예를 들어 늦은 전달로 다시 계산하면 head Miss와 그 종속 0점이 다른 묶음에 들어갈 수 있다(아래 늦은 전달의 셋째 예).
- **같은 시각에는 진행 먼저:** 바디의 시작 S에 hold 수 요구를 시작하는 것과 끝 E에 바디가 끝나는 것은 같은 시각의 입력보다 먼저 반영한다. 그래서 프레임이 그 시각에 멈추는지와 관계없이 결과가 같다. 예: 길이 0 `holdOnly [1000,1000]`을 A 880–1000으로 치면 1000에 A가 눌린 상태로 끝을 반영해 Perfect다. 1000에 멈추는 프레임이 없어도 같다(수리 브랜치 실측, 지금 게임도 Perfect).
- **같은 timestamp 입력의 순서:** 한 batch에서 서로 다른 키 사이에는 up을 down보다 먼저 처리하고, 같은 키의 순서(같은 ms의 탭은 down·up, 같은 ms의 재누름은 up·down)는 지킨다. 위 동시 입력 항목의 요구(서로 다른 키의 처리 순서로 결과가 달라지지 않음)를 이 순서로 지키며, 지금 게임도 같은 순서로 처리한다. 예: `long [1000,2000]` → `head 2000` + `long [2000,3000]`을 `a-b-`로 치며 A up과 B down이 모두 2000이면, 받은 순서와 관계없이 A up이 연결 release, B down이 N2 head Perfect이고 B up 3000까지 Perfect 2다(도출).
- **head 기한과 같은 시각의 입력:** 연결 head를 놓쳤을 때 그 Good 기한에 뒤 바디(double 연결에서는 head가 맡는 몫)를 채우고 있었는지([§5-2](#5-2-head-창-안에서-끊김)·[§5-3](#5-3-head-창-뒤에-끊김)·[§5-4](#5-4-double-연결에서-head가-맡는-몫)의 구분)는 기한 시각의 입력까지 반영한 hold 수로 본다. 예: §5-2의 차트에서 A를 2120에 떼면 기한 시각의 hold가 0이라 §5-2대로 2120에 head Miss와 N3 끝 종속 0점, Miss 1이다. A를 2121에 떼면 기한 2120을 그 up보다 먼저 정산해 hold 1로 채운 것으로 보고 N3가 2120부터 유지를 요구한다. 유지 유예 뒤 2141에 유지 Miss가 나서 §5-3대로 Miss 2다(수리 브랜치 실측). 이 경계는 [PRD의 미정 사항](../prd.md#12-미정-사항) “연결 head Miss 뒤 바디의 정산”을 다시 정하면 함께 바뀐다.
- **늦은 전달:** 코어가 이미 지난 시각의 입력이 핸들러 지연 등으로 늦게 도착한 경우다. 등급은 위 입력 시각 등급대로 raw 시각으로 정한다. 관측한 시각과 다시 계산하는 범위는 아래와 같다.
  - **관측한 시각:** 실제 세션은 입력을 코어에 넘길 때의 코어 시각을 관측한 시각으로 넘긴다(아래 첫 예에서 1001). 코어를 직접 호출할 때는 그보다 늦은 관측 시각을 넘길 수도 있으며, 그러면 코어가 먼저 그 시각까지 진행한다(세부는 [게임 코어 명세](../spec/game-core.md#판정-실행-구조)).
  - **최종인 것:** 입력이 도착하기 전에 확정한 판정(Miss, 실패한 unit, 점수, 콤보)은 최종이며 되살리거나 소급하지 않는다.
  - **아직 확정하지 않은 것:** 시간 진행이 이벤트 없이 바꾼 상태다. S에서 hold 수 요구를 시작하고 바디를 시작한 것, E에서 release 대기로 넘어가거나 이어지는 몫을 완료한 것, head 기한에서 뒤 바디를 채웠다고 본 정산이 여기에 든다. E−Good 뒤 이벤트 없이 일찍 완료한 것도 같은 성격이라 여기에 넣는다(도출, 2026-10-18에 승인한 목록에는 없다).
  - **기준 시각 h:** 늦은 입력이 그 레인의 hold 수에 반영되는 시각이다. h는 raw 시각이며, 같은 레인에 이미 넣은 입력보다 이르면 그 레인의 마지막 입력 시각이다.
  - **되돌리는 것:** (가) h보다 뒤인 진행(S·E 진행, E−Good 뒤 이른 완료), (나) 기한이 h 이상인 head 기한 정산이다. 그 진행과 함께 바뀐 다른 몫의 상태도 함께 되돌린다(세부는 [게임 코어 명세](../spec/game-core.md#판정-실행-구조)). 되돌린 뒤 그 입력을 넣은 hold 수로 다시 계산하고, 다시 계산해 나온 판정은 관측한 시각에 확정한다.
  - **되돌리지 않는 것:** h와 같은 시각의 S·E 진행(같은 시각에는 진행 먼저)과 확정한 판정이다.
  - **보장:** 입력이 발생 순서대로 도착하고(raw 시각이 더 늦은 입력이 먼저 반영되지 않았고), 그 레인에서 raw 시각 이후의 판정이 도착 전에 확정되지 않았다면, S나 E보다 앞선 입력이 늦게 와도 등급·Miss 수·실패한 unit이 즉시 전달과 같다. 확정 시각과 그 순서를 따르는 콤보 표시는 다를 수 있다.
  - 예: `head 1000` + `doubleLong [1000,3000]`, A 800–990, B·C 1050–3000을 즉시 전달하면 head Great(+50)와 두 끝 Perfect로 Great 1·Perfect 2다. 코어가 1001까지 진행한 뒤 A up 990이 1017 프레임에 도착해 관측 시각 1001로 넘어오면, A가 눌린 채 1000을 지나 한 몫을 시작한 것으로 본 진행을 되돌려 다시 계산하므로 같은 Great 1·Perfect 2다(수리 브랜치 실측). 다시 계산하지 않으면 그 몫이 1020에 유지 실패해 Perfect 1·Great 1·Miss 1이다(되돌리기를 넣기 전 수리 브랜치에서도 같다). 이 값은 지금 [§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지) 문언대로 head가 있는 바디에 재충전이 없을 때의 도출이다.
  - 예: `long [1000,2000]`, A 1000–1500·1515–2000에서 코어가 1530까지 진행해 1520의 유지 Miss를 확정한 뒤 raw 1515의 회복 down이 관측 시각 1530에 도착하면 Miss 1은 그대로다(수리 브랜치 실측). 즉시 전달이면 유예 안의 회복이라 Perfect 1·Miss 0이다.
  - 예: §5-2의 차트에서 A up raw 2115가 관측 시각 2121에 도착하면, 이미 확정한 2120의 head Miss는 남고 그 기한에서 채웠다고 본 정산만 되돌린다. 결과는 즉시 전달과 같은 Miss 1이며 N3 끝 종속 0점만 관측 시각 2121에 확정한다(수리 브랜치 실측). 늦은 전달에서는 이처럼 head Miss와 그 종속 0점이 다른 묶음에 들어갈 수 있다.

**늦은 전달의 기본값 재확인(2026-10-20).** 늦은 전달은 2026-10-18 승인 때 기본값으로 두고 문서화 전에 다시 확인하기로 했다. 위 첫 예를 즉시 전달, 늦은 전달과 다시 계산, 다시 계산 없는 늦은 전달의 세 그림으로 보였다. 사용자가 “실제 이벤트 시간으로 말고 도착한 시간으로 하는게 낫나”라고 물어 그 안과 비교했다. 도착 시각으로 판정하면 프레임 끊김이 등급을 바꾸고, 지금 게임도 늦은 입력의 등급을 raw 시각으로 정하며, 첫 예는 도착 시각으로 판정해도 Miss가 남는다(지금 §4-3 문언 기준의 도출. 수리 브랜치에서 A up을 1017에 제때 넣으면 1037에 유지 Miss다). raw 시각을 유지하는 기본값에 사용자는 “ㅇㅋ”라고 답했다(2026-10-20).

- head 기한 정산의 두 갈래는 이 기본값에서 다음과 같이 도출한다. 뒤 바디를 채웠다고 본 정산은 이벤트가 없으므로 다시 계산한다(위 §5-2 차트의 예). 채우지 못했다고 본 정산(head Miss와 그 몫의 실패, [§5-2](#5-2-head-창-안에서-끊김))은 확정한 판정이라 늦은 입력으로 되돌리지 않는다.

### 2-4. 여러 끝에 적격인 up의 순서와 키 재사용

**up은 적격 대상 중 차트상 끝 시각이 가장 이른 실제 release를 처리한다.** 시간 창, 실패 상태, 같은 double 끝의 키 중복([§3-1](#3-1-두-release는-서로-다른-키)) 등 자격을 먼저 확인한 뒤 고른다(바디의 시작 여부는 자격이 아니다, [§2-3](#2-3-release-등급과-자격-판정-창-기준)). 입력 시각에 더 가깝거나 더 높은 등급을 주는 뒤 끝을 우선하지 않는다. 사용자의 “가까운 릴리즈”라는 표현에 대해 이 규칙을 설명하고 뜻을 확인하자 사용자는 “맞음 가장 이른것”이라고 답했다(2026-10-15).

**사례 1: double에서 쓴 키의 다음 up은 뒤 single을 처리한다.** N1=`doubleLong [1000,2000]`, N2=`long [2010,2060]`이며 10ms 간격을 둔 같은 레인의 독립 바디다. A는 1000–2500에 계속 누르고, B는 1000–1990과 2010–2060에 누른다. 첫 B up 1990은 N1의 release 하나를 처리한다. 두 번째 B up 2060은 N1의 남은 release 창과 N2의 release 창에 모두 든다. 사용자는 유지 키와 별도 키로 끝만 치는 앞선 사례([§3-2](#3-2-유지-키와-다른-키의-up))가 의도한 예시임을 확인하고 다음과 같이 답했다(2026-10-16).

> 내가 생각한 예시가 맞았음 4번 검토는 두번째 릴리즈가 n2 처리하면 될거같은데

**두 번째 B up은 N2의 release를 처리한다.** N1에 이미 쓴 물리 키라는 이유로 독립된 N2에서도 B를 막지 않는다. N1의 남은 release는 같은 double 끝의 키 중복으로 B를 받지 못하지만, 그 부적격 대상이 남아 있다는 이유로 up을 버리거나 N2까지 막지 않는다. N1의 남은 release는 다른 유효 up이 없어 기한에 Miss가 되며, 기대 결과는 N1u1 Perfect(-10), N2 Perfect(0)로 Perfect 2·Miss 1이다(PR #188 같음).

**사례 2: 쓰지 않은 키의 up은 앞 double의 남은 release를 처리한다.** 같은 차트에서 B는 1000–1990만 누르고, 두 번째 입력을 C 2010–2060으로 바꾼다. N1u1은 B up 1990으로 처리했고, C up 2060은 N1u2와 N2 양쪽 창 안이다. C는 N1에서 아직 쓰지 않은 물리 키다. 사용자는 다음과 같이 답했다(2026-10-16).

> n1u2 이처리됨 b가 u1을 처리했고 그다음 가까운 릴리즈를 처리, 이전 예시는 더블 릴리즈가 같은 키로 두번 처리할수 없었음

**C up은 N1u2를 처리한다.** 사례 1의 B는 같은 double 끝에서 이미 사용해 N1에 부적격이었고, C는 사용하지 않은 키라 N1에 적격이다. 답의 “가까운”을 절대 시간 오차가 작은 대상 우선이라는 새 결정으로 기록하지 않는다. 입력 시각 2060은 N1 끝 2000과 60ms, N2 끝 2060과 0ms 차이이므로 가장 가까운 끝은 N2다. 확인한 N1 배정은 가장 이른 적격 대상 우선과 일치하며, 대화에서 이 용어 차이를 설명했다. 기대 결과는 N1u1 Perfect(-10), N1u2 Great(+60), N2 Miss로 Perfect 1·Great 1·Miss 1이다(PR #188: N1u1 Perfect, C up으로 N2 Perfect, N1u2 Miss로 Perfect 2·Miss 1). 사용자가 직접 확인한 것은 C up의 N1u2 배정과 사례 1과의 키 차이이며, 등급과 N2의 결과는 기존 규칙에서 도출했다.

N2까지 성공시키려면 어떤 입력이 더 필요한지 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> 릴리즈가 하나 더 필요하니까 a를 뗴던지 c처럼 하나더 입력하고 떼야함

N1u2에 소비한 C up과 별개로 N2에는 Good 창 안의 실제 up 하나가 더 필요하다. 계속 유지하던 A를 창 안에 떼거나, 같은 레인의 키를 새로 눌렀다 창 안에 떼면 된다.

- 같은 double 끝에 서로 다른 키를 요구하는 범위와, 서로 다른 노트에서 같은 키를 다시 쓰는 범위를 구별한다. 키 사용 이력을 레인이나 차트 전체의 금지로 확대하지 않는다.
- 같은 차트·시각에서 키만 B에서 C로 바꿔도 후보 자격이 달라져 up이 처리하는 끝이 달라질 수 있다. 같은 double 끝에 서로 다른 키를 요구한 결정과 가장 이른 적격 대상 우선의 결과다.
- 한 up으로 두 끝을 동시에 처리하지 않는다. 앞 N1에 소비한 C up을 뒤 N2에 중복 소비하지 않는다. 사례 2는 현재 엔진의 등록 키·release 권한에 따른 배정과 달라지는 회귀 사례로 남긴다.

### 2-5. 바디 중간 교대와 끝 창 안의 교대

**바디 중간에 어떤 판정 창과도 겹치지 않는 시점의 교대는 hold가 유지 유예를 넘겨 끊기지 않는 한 의도된 연주다.** 그 up은 어느 판정에도 쓰이지 않는 중립이다. `long [1000,2000]`에서 A 1000–1500, B 1490–2000으로 교대하면 A up 1500은 끝의 판정 창(1880~2120) 밖이고, B up 2000이 끝을 처리해 Perfect 1이다(PR #188은 등록 키 A를 떼는 순간 유지 실패로 Miss 1). 어떤 release·연결 release 창에도 들지 않는 up을 중립으로 보자는 제안에 사용자는 다음과 같이 답했다(2026-10-16).

> ㅇㅋ 그럼 롱노트 중간에 어떤 윈도우에도 안겹치는 시점에 교대하는거 허용하는거지

**끝 창 안에서 교대한 up은 이른 release로 판정하고, 그 손해가 차트의 의도가 아니면 끝에 Grace를 건다.** N1=`long [1000,2000]`에서 A 1000–1900, B 1895–2500으로 교대하면 B를 먼저 누른 뒤 A를 떼므로 hold 수는 1→2→1이며, 끝의 Good 창 안에 있는 up은 A up 1900 하나다. 사용자는 다음과 같이 답했다(2026-10-16).

> 사용자가 a up에서 릴리즈가 발생한다. 이른 릴리즈가 발생하고, 이로 인해 피해보는게 차트의 의도가 아니라면 그레이스를 건다.

- **일반 끝:** A up 1900이 N1의 실제 release를 처리한다. B가 계속 유지하고 있다는 이유로 A up을 제외하거나 끝 판정을 B up 2500까지 기다리지 않는다.
- **등급:** 기존 판정 창을 적용하면 끝보다 100ms 이른 Good(-100)이다(PR #188 같음). 사용자는 이른 release의 발생을 확인했고, 등급은 창·등급 규칙에서 도출했다.
- **Grace:** 이른 release로 인한 점수 손해가 차트의 의도가 아니라면 제작자가 해당 끝에 Grace를 적용한다. 롱노트 끝의 속성은 `holdOnly`이며 Point의 `grace`와 혼동하지 않는다. 새로운 `grace release` 타입을 도입하지 않는다.
- **속성의 영향:** `holdOnly`는 해당 끝의 release 요구를 면제한다([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다)). 일반 롱노트 전체를 `holdOnly`로 바꾸거나, 실제 release가 필요한 끝에서 계속 누르기만 해도 완료하도록 바꾸는 결정은 아니다.

[§1-2](#1-2-패턴을-먼저-정하고-교대-자체의-점수-손해를-금지)의 점수 손해 금지 목표를 교대 up을 무조건 엔진에서 제외해야 한다는 뜻으로 해석하지 않는다. 이 단독 single 사례를 double의 두 release([§3-1](#3-1-두-release는-서로-다른-키)), 같은 키 재누름([§3-3](#3-3-노트를-처리한-같은-키의-재누름)), 독립된 두 바디의 경계([§2-6](#2-6-짧게-떨어진-독립-롱노트와-분리-표시)), 연결 head([§4-1](#4-1-연결-release)), 미시작 바디([§2-3](#2-3-release-등급과-자격-판정-창-기준))로 자동 확대하지 않으며, 각각은 해당 항목에서 정했다.

### 2-6. 짧게 떨어진 독립 롱노트와 분리 표시

`connection`은 같은 레인에서 앞 바디의 끝과 뒤 바디의 시작이 정확히 맞닿은 경우이며, 이미 정의된 홀드 트릴의 연결 배치와 구분한다. 같은 레인에 아주 짧은 빈틈을 둔 독립 롱노트는 현재 validator를 통과하지만, 그 사실만으로 수록할 가치나 모든 입력을 보존할 필요가 정해지지는 않는다. 사용자는 “롱노트끼리 비정상적으로 붙어있는 차트를 우리 패턴 공간에 넣어야하는지 정해야해”라고 지적했다(2026-10-15). 이어서 짧게 떨어진 독립 롱노트가 요구하는 `a-b-`는 이미 `o-o-`를 처리하는 두 가지 방법 중 하나라고 설명했다. 따라서 새로운 연주 동작이라는 이유로 이 배치를 지원 범위 밖으로 돌리지 않는다. 최소 간격, 자동 배치 금지, 자동 연결, 점수 항목 통합은 채택하지 않았다.

**독립 롱노트 사이의 실제 release는 교대로 흡수하지 않는다.** 사용자는 다음과 같이 결정했다(2026-10-15).

> 지금처럼 떨어저 있는 경우에는 연결됐을 경우와다르게 릴리즈 판정이 아예 존재하니까 흡수하면안돼지

비교하는 같은 unit 수 연결 경계에는 별도 release가 없지만, 독립 롱노트 사이에는 앞 바디를 끝내는 실제 release가 있다. hold 수 회복과 유지 유예만으로 차트가 요구한 release를 없애지 않는다. 연결된 모든 배치에 release가 없다고 일반화하지 않는다(2→1 감소의 release는 [§6-2](#6-2-head-없는-21)·[§6-3](#6-3-head가-있는-21과-감소-release)).

```text
노트: long 1000-2000 | long 2010-3000
입력: A 1000-1950 | B 1960-3000
```

A up은 N1 끝보다 50ms 이르고 B down은 N2 시작보다 50ms 이르다. A up이 N1의 실제 release를 처리하며, 20ms 안에 B down으로 hold 수가 회복되었다는 이유로 취소하지 않는다. 기대 결과는 N1 Great(-50), N2 Perfect(B up 3000)로 Full Combo다(PR #188 같음). 같은 차트에서 A 1000–2000, B 1995–3000처럼 겹쳐 누르면 hold 수가 1→2→1이며, PR #188은 A up 2000으로 N1 Perfect, B up 3000으로 N2 Perfect다. 1→0에서만 후보를 만드는 안은 이 입력에서 앞 롱노트의 release 후보를 만들지 못해 채택하지 않았다([부록 A-3](#a-3-10에서만-release-후보를-만들고-회복으로-취소)).

**분리 표시.** 사용자는 두 롱노트의 끝과 시작을 구별하는 시각 요소를 제안했다(2026-10-15).

> 롱노트 사이 아주짧은 간격은 그 간격이 릴리즈 노트처럼 작용하기 때문에(a-b 교대가 일어나서) 그 공간이 포인트 처럼 박자로 정의되어야 할거같은데 그럼 새로운 노트가 필요해

> 지금 롱노트는 끝부분이 시작부분과 똑같이 보여서 차트 제약이 롱노트 끝에 롱노트 시작할수 없다고 되어있어 그래서 롱노트가 끝났음과 새로 시작함을 알리는 그 틈을 시각화하기 위한 요소가 필요함 이 노트가 요구하는건 없어 기존 롱노트 두개가 up 과 down을 각각 요구하는거야

표현 방식은 “사용자에게는 그냥 빈칸으로 보이게 하면 될거같은데”, “빈칸은 포인트 크기만큼, down과 up 동시에 발생한다고 읽혔으면”, “만약 스킨에 끝 터미널 에셋이 있다면 그냥 그걸 쓰면 됨”으로 구체화했다(2026-10-15).

- **이 요소는 두 롱노트 사이의 분리를 시각적으로 드러낸다.** 앞 롱노트가 끝나고 뒤 롱노트가 새로 시작한다는 정보를 표시하며, up과 down 요구는 기존 두 롱노트에 귀속된다. 요소 자체에는 별도의 입력·타이밍 판정·점수 항목을 추가하지 않는다.
- 해당 스킨에 끝 terminal 에셋이 있으면 그 에셋으로 앞 롱노트의 종료를 나타내고, 없으면 Point 하나 크기의 빈칸으로 분리를 드러낸다. 한 박에서 앞 롱노트의 up과 뒤 롱노트의 down을 함께 하는 경계로 읽히게 하되, 화면상의 빈칸을 손을 떼어 두어야 하는 시간 구간으로 해석하지 않는다. “동시에 읽힌다”는 시각·음악적 의미이며, 실제 입력 timestamp가 완전히 같아야 한다는 조건이나 새 판정 윈도우를 도입한 것은 아니다. 스킨마다 표현을 선택해도 독립된 두 롱노트라는 차트 의미와 판정은 같다.
- 새 경계에서도 미리 누른 키로 뒤 롱노트를 시작해도 되는지 묻자 사용자는 “상관없음 진짜 롱노트 두개 라고 생각하면 됨”이라고 확인했다(2026-10-15). hold 수 기반 독립 시작([§2-1](#2-1-hold-수로-시작과-유지-판단))을 이 경계에도 유지하며, 빈칸 때문에 새 down 소비나 시작 점수를 추가하지 않는다. 앞 release를 놓쳤다는 이유만으로 뒤 바디까지 자동 실패시키는 연쇄 규칙도 추가하지 않는다.
- 이 경계의 release에 별도 자격을 두지 않는다. 앞 롱노트의 release는 [§2-3](#2-3-release-등급과-자격-판정-창-기준)의 일반 규칙으로 판정한다. up과 down을 같은 시각에 처리한 뒤의 hold 수는 이전과 같을 수 있으므로, 최종 hold 수 변화가 아니라 기존 release 항목과 개별 up으로 판정한다.
- 현재 validator가 금지하는 범위는 같은 레인·같은 unit 수의 바디가 정확히 맞닿으면서 head도 앞 `holdOnly`도 없는 배치다. head·`holdOnly`·unit 수 변화가 있는 연결까지 모두 금지하는 것은 아니다. 같은 박에서 독립된 끝과 시작을 표현하려면 시간 좌표가 일치하면 `connection`으로 보는 현재 정의와 배치 제약을 대조해야 한다. 기존의 정상 연결까지 모두 분리하거나 점수 항목 수를 바꾸지 않는다.
- 기존 [glossary의 릴리즈 노트](../context/glossary.md#릴리즈-노트)는 입력을 판정하는 길이 0 롱노트이므로 이 시각 요소의 대체물로 취급하지 않는다.
- 기존 배치의 처리 범위를 묻자 사용자는 “이미 짧은 간격으로 떨어져 있는 두 롱노트가 있는 차트는 현재까지 없음”이라고 설명했다(2026-10-15). 이는 사용자가 제공한 현황이며 차트 전체를 별도로 조사한 결과가 아니다. 일괄 변환은 필수 과제로 두지 않으며, 존재하지 않는 기존 차트에 대한 변환 결정을 반복해서 요구하지 않는다.
- 요소의 이름, 끝 terminal 또는 빈칸을 박 위치에 어떻게 배치할지, 기존 데이터에서 표시를 도출할지 별도로 저장할지는 정하지 않았다([PRD의 미정 사항](../prd.md#12-미정-사항)). 엔진·표시·공식 glossary는 변경하지 않았다.

## 3. double 끝

### 3-1. 두 release는 서로 다른 키

**같은 double 끝의 두 실제 release는 서로 다른 물리 키의 up으로 처리한다.** 같은 키를 다시 눌렀다 떼어 up 개수만 두 개로 만드는 것으로 대체하지 않는다. double Point의 서로 다른 두 키 요구와 연주 의도를 일치시키는 결정이다. 예외는 노트를 처리한 재누름이다([§3-3](#3-3-노트를-처리한-같은-키의-재누름)).

N1=`doubleLong [1000,2000]`에서 A는 1000–2500, B는 1000–1980 및 1990–2000에 누른다. A는 끝을 지나서도 유지하며 B만 두 번 뗀다. B up 1980과 2000은 모두 Perfect 창 안이고, 두 누름 사이에 새로운 Point나 다른 바디 시작은 없다. 사용자는 다음과 같이 답했다(2026-10-16).

> 더블 포인트는 두 키가 다른 키를 입력해야 하니 릴리즈도 다른키를 받아야 일관성이 있음, 플레이 의도에도 맞음

기대 결과는 Perfect 1·Miss 1이다. 첫 B up은 끝 하나를 처리하고 두 번째 B up은 같은 double 끝의 남은 release를 처리하지 않는다. A up 2500은 창 밖이므로 남은 release는 기한에 Miss가 된다. 키 중복 거절 자체에 별도의 추가 Miss를 만들지 않는다(PR #188 같음: N1u1 Perfect(-20), N1u2 release Miss, 달성률 50%). 이 노트 없는 재누름의 결과는 NJ-R15와 같다.

- 서로 다른 키의 필요와, 그 키가 처음부터 해당 바디를 유지하던 키여야 하는지는 구별한다. 고정 owner나 최초 A/B 키에 대한 release 귀속을 도입하지 않는다([§3-2](#3-2-유지-키와-다른-키의-up)).
- 두 개의 서로 다른 single 끝에 같은 키를 다시 쓰는 것과 하나의 double 끝을 처리하는 것은 다른 문제다. 키 이력을 차트 전체에 걸쳐 차단하지 않는다([§2-4](#2-4-여러-끝에-적격인-up의-순서와-키-재사용)).
- 이미 실패한 unit의 부활, `holdOnly`로 면제한 release의 부활, 한 up의 여러 항목 중복 소비를 허용하지 않는다.

### 3-2. 유지 키와 다른 키의 up

**A/B가 double 바디를 계속 유지하는 동안 같은 레인의 다른 키 C/D를 눌렀다 뗀 up도 그 double 끝의 두 실제 release를 각각 처리한다.** 바디를 처음 유지한 A/B를 직접 떼거나, C/D가 별도 head·시작 입력을 처리해야 한다는 조건을 두지 않는다. A/B가 계속 눌려 hold 수가 둘 아래로 내려가지 않아도 인정한다. 서로 다른 키 요구([§3-1](#3-1-두-release는-서로-다른-키))는 C/D로 충족한다.

N1=`doubleLong [1000,2000]`이고 A와 B는 모두 1000–2500, C는 1970–1980, D는 1990–2000에 누른다. 네 키는 같은 레인에 바인딩되어 있고 C/D의 down을 요구하는 별도 Point나 다른 바디 시작은 없다. 사용자는 다음과 같이 답했다(2026-10-16).

> c d 가 n1의 릴리즈로 작용

기대 결과는 C up 1980의 Perfect(-20), D up 2000의 Perfect(0)로 Perfect 2·Miss 0·Full Combo·달성률 100%다(PR #188은 유지·시작에 등록되지 않은 C/D를 인정하지 않아 Miss 2·달성률 0%). 사용자 답은 C/D의 release 소비를 확인한 것이며 등급과 통계는 판정 창과 점수 규칙에서 도출했다.

여분 키의 release를 제한하면 유지 키를 계속 누르고 다른 키로 끝만 치는 플레이를 막을 수 있다는 점을 검토했다. 아무 up 없이 유지하기만 하는 플레이와 다른 키의 실제 up으로 끝을 치는 플레이를 구분해 확인하자 사용자는 다음과 같이 답했다(2026-10-16).

> 그렇게 하는게 더 햇갈려서 그걸 막을 필요까진 없을것 같네

- 유지 키를 계속 누르고 다른 키로 끝을 치는 플레이를 별도로 금지하지 않는다. 이 플레이를 막기 위한 여분 키 배제나 원래 유지 키를 반드시 떼어야 한다는 조건을 추가하지 않는다. 실제 up 요구와 같은 double 끝의 서로 다른 키 요구는 그대로 적용한다.
- 계속 유지한 A/B로 release를 자동 완료하지 않는다. 실제 C/D up 두 개가 필요하며 한 up은 실제 release 하나만 처리한다.
- 이 연주는 끝 뒤에 키가 남으므로 의도된 연주가 아니다. 마지막 끝도 경계로 보아 끝 뒤에 남는 키는 여분 키다([§9-1](#9-1-의도된-연주의-정의)). 막지는 않는다.
- 구현 시 `src/game/judgment/NoteJudgmentCore.ts`의 후보 자격(유지 키 등록·기존 release 권한만으로 C/D를 제외하는 부분)과 관련 테스트를 이 기대 결과에 맞춰 바꾼다.

### 3-3. 노트를 처리한 같은 키의 재누름

**같은 double 끝의 release에 이미 쓴 물리 키라도, 그 키를 다시 눌러 그 double 바디가 시작하는 연결 경계의 head를 처리했다면 그 누름의 up은 같은 double 끝의 남은 release를 처리할 수 있다.** [RFD 0020 §2.8](0020-note-judgment-units-and-inheritance.md#28-유효한-새-입력에-따른-release-권한-갱신--후속-채택)의 권한 갱신을 새 hold 수 모델에서도 유지한다. [§3-1](#3-1-두-release는-서로-다른-키)의 서로 다른 키 요구는 이 예외를 제외하고 유지한다.

- 재누름 자체가 그 연결 head를 처리해야 한다. 다른 키가 head를 치고 같은 키는 노트 없이 다시 누른 경우, 그 키의 두 번째 up은 같은 double 끝에 쓰지 않는다. 독립된 다른 노트의 head를 처리한 재누름도 해당하지 않으며, 이는 RFD 0020 §2.8의 범위(등록 대상과 연결 구간, 독립 Point의 입력은 앞 바디의 권한을 주지 않음)와 같다.
- 노트 없는 재누름은 새 자격을 얻지 못한다. [§3-1](#3-1-두-release는-서로-다른-키)의 B 1990 재누름 결과 Perfect 1·Miss 1은 바뀌지 않으며 NJ-R15와 같다.
- 이 예외는 release 후보를 새로 만드는 규칙이 아니다. 연결 release에 배정되지 않은 up은 이미 release 후보이며([§3-2](#3-2-유지-키와-다른-키의-up)), 이 예외는 같은 키 차단만 해제한다. 한 up은 실제 release 하나만 처리하고, 연결 release의 발생 순서 배정([§4-1](#4-1-연결-release))과 실패한 unit을 되살리지 않는 원칙은 그대로다.

**NJ-R13 형태.** N1=`doubleLong [1000,2000]` → N2=`head 2000` + N3=`doubleLong [2000,2100]`, A 1000–2010, B 1000–2040 및 2050–2100이다. A up 2010은 연결 release, B up 2040은 N3u1 Great(-60), B down 2050은 N2 head Great(+50), B up 2100은 N3u2 Perfect로 Perfect 1·Great 2·Miss 0이다(PR #188 같음). A up 2010 뒤 N3의 hold 수는 2040까지 1, 2050까지 0이다. 나머지 몫은 B up 2040으로 release를 처리해 끝났고, head가 맡는 몫은 N2를 처리한 B down 2050부터 판단하므로([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)) 유지 부족이 없다. 이 결과는 그 규칙을 double 연결로 확대하면서 확정됐다. 이 입력은 의도된 연주가 아니다([§9-1](#9-1-의도된-연주의-정의)).

**동시 up(NJ-R14 형태).** A up만 2040으로 옮겨 A/B를 동시에 떼고 B down 2050 → B up 2100을 유지하면, A/B 중 어느 up을 연결 release에 배정해도 N3u1 Great(-60), N2 head Great(+50), N3u2 Perfect로 Perfect 1·Great 2·Miss 0이다. 채택한 예외에서 도출한 이 결과를 묻자 사용자는 “ㅇㅋ”라고 확인했다(2026-10-16). PR #188과 같다. 같은 키·시각 입력의 결과가 내부 수신 순서에 따라 바뀌면 안 된다는 요구를 이 결과로 충족한다.

**재검토 경위.** 처음 NJ-R13 형태를 확인할 때 사용자는 이 패턴의 연주 방식과 배정을 다음과 같이 설명했다(2026-10-16).

> 이 패턴은 ab--- + ..c. 으로 치던가 a-b- + c--- 로 쳐야함 그래서 교대 릴리즈 1번 있어서 a 흡수 b가 u1 릴리즈 두번째 b 릴리즈는 대응 없음

이에 따라 B up 2100을 대응 없음(N3u2 Miss, Great 2·Miss 1)으로 기록하고 RFD 0020 §2.8의 예외를 유지하지 않기로 했다. 이어 동시 up을 대조하자, A up을 연결용으로 배정하면 B up 2100이 대응 없음이고 B up을 연결용으로 배정하면 N3u2 Perfect라 같은 입력의 결과가 내부 처리 순서에 따라 갈렸다. 사용자는 다음과 같이 지적했다(2026-10-16).

> 이거보니까 패턴 검토 12 에서 사용자가 흡수한 키가 구분할수 없다는걸 알았는데

시간 순서가 있는 NJ-R13에서도 A up 2010과 B up 2040 중 어느 것이 연결 release에 배정됐는지 플레이어는 구분할 수 없다. 그 배정이 B up 2100의 허용 여부를 정하면 보이지 않는 내부 배정이 결과를 바꾸며, 이는 [RFD 0020 §2.7](0020-note-judgment-units-and-inheritance.md#27-동일한-플레이의-결과-일관성--후속-요구사항)의 결과 일관성 요구와 충돌한다. 같은 모순을 NJ-Q08에서 겪고 RFD 0020 §2.8의 권한 갱신으로 해결한 이력이 있으며, 예외를 되돌리면 같은 모순을 다시 만든다. 노트 없는 재누름과 head를 처리한 재누름을 구분하는 예외를 제안하자 사용자는 다음과 같이 정리했고, 재누름 자체가 head를 처리해야 한다는 조건을 덧붙여 채택 여부를 묻자 승인했다(2026-10-16).

> 중간에 n2를 누르면 이미 뗏던거 떼도 ok 인걸로 하자는 거지?

인용의 두 연주 방식은 [§4-4](#4-4-single-head가-있는-double-연결의-연주)에서 이 패턴의 의도된 연주로 확인했다. A/B를 유지하며 C로 연결 head를 탭하는 `ab--- + ..c.`에서 C up은 연결 release에 배정되며 이 예외와 관계없다.

## 4. 연결 head

### 4-1. 연결 release

**연결 release는 연결 경계에서 앞 바디의 몫이 끝날 때 떠나는 up 하나다. 등급과 점수 항목은 없다.** 앞 바디도 끝나면 원래 release가 하나 필요하며, 연결 경계에서는 그 release에 등급이 없을 뿐이다. 교대로 head를 치면 떠나는 키의 up이, 유지하며 다른 키로 head를 탭하면 탭한 키의 up이 연결 release다. 이 up이 경계 전에 오면 그때 앞 바디의 그 몫이 끝나고([§4-2](#4-2-경계-전에-뗀-연결-release)), 경계 뒤나 head 뒤에 오면 이미 끝난 몫의 release로 처리한다. 어느 쪽이든 이 up을 뒤 바디의 실제 release에 다시 쓰지 않으며, 마지막 끝에는 별도의 실제 up이 필요하다.

이 처리는 처음에 연결 보정(경계 뒤·head 뒤의 up)과 앞 바디 종료(경계 전의 up)로 나누어 적었다. 이해 확인 중 사용자가 둘이 같은 처리라고 지적했다(2026-10-17).

> 근데 2000이후에 떼어도 n1이 종료되니까 릴리즈를 하나 소모해서 연결 보정이 앞 바디 종료랑 똑같은거 아님?

> 원래 롱노트가 끝날때 릴리즈가 필요하니까 이걸 보정이라고 부르면 안될거 같은데

`연결 release`라는 이름으로 합치자는 제안에 사용자는 “연결 릴리즈로 하고”라고 답했다(2026-10-17). 판정 결과는 바뀌지 않는다. 기존 엔진(RFD 0020)에서는 같은 처리를 연결 keyup 보정·연결 보정이라 불렀다.

N1=`long [1000,2000]` → N2=`head 2000` + N3=`long [2000,2060]`에서 A 1000–2010, B 2000–2500을 제시하고 B가 N2를 친 뒤 발생하는 A up을 어떤 판정에 쓸지 묻자, 사용자는 두 연주 방식의 동등성을 근거로 답했다(2026-10-16).

> 연결 교대에서 발생하는 릴리즈를 소비한다는건 1. o-o- 를 a-b- 로 칠때 a 릴리즈를 소비, 2. a--- + ..b.  로 칠때 b 릴리즈를 소비하므로 정당하다고 생각하는데

| 연주 | 입력 | 배정 | 기대 결과 |
|---|---|---|---|
| 교대(`a-b-`) | A 1000–2010, B 2000–2060 | B down 2000이 N2, A up 2010이 연결 release, B up 2060이 N3 끝 | Perfect 2 (PR #188 같음) |
| 유지 중 탭(`a--- + ..b.`) | A 1000–2060, B 2000–2010 | B down 2000이 N2, B up 2010이 연결 release, A up 2060이 N3 끝 | Perfect 2 (PR #188: N2 Perfect·N3 Miss) |

유지 중 탭 그림을 본 사용자는 다음과 같이 배정을 직접 확인했다(2026-10-16).

> b 릴리즈가 교대 릴리즈를 소비하고 a 릴리즈가 n3 소비

이 답이 가리키는 사례를 묻자 “2. A를 유지하며 B로 탭 말한건데”라고 명확히 했다. 처음 제시한 입력(A up 2010, B up 2500)은 A up을 연결 release에 배정하면 N3 창 안의 별도 up이 없어 N3 Miss가 도출된다. 이는 원칙에서 도출한 대조이며 사용자의 위 답을 이 입력의 배정이나 Miss에 대한 직접 확인으로 기록하지 않는다.

- **자격:** 연결 release의 자격은 head의 Good 창으로 정한다. 등급을 매기는 창은 없다. 유지 중 탭은 head를 친 뒤 떼므로 연결 release가 경계보다 늦다. 예를 들어 `long [1000,2000]` → `head 2000` + `long [2000,2200]`에서 A 1000–2200, B 2000–2150이면 B up 2150이 head의 Good 창 밖이라 연결 release가 아니고, N3 끝의 이른 release Great(−50)가 되어 Perfect 1·Great 1이다(PR #188은 Perfect 2). 떼는 판정의 창을 누르는 판정보다 관대하게 두는 방향은 사용자가 택했으며 나중에 정한다(“2로 할건데 나중에”, 2026-10-17). 연결 release의 자격 창도 그 결정을 따른다([PRD의 미정 사항](../prd.md#12-미정-사항)).
- **어떤 up인가:** head 하나에 연결 release 하나다. head를 처리하기 전에 경계보다 먼저 뗀 up, 경계 뒤에 뗀 up, head를 처리한 뒤의 up이 모두 연결 release가 될 수 있으며, 먼저 온 up이 그 몫을 채운다([§4-2](#4-2-경계-전에-뗀-연결-release)). 뒤 바디의 끝이 head의 Good 창 안에 있고 head가 아직 처리되지 않았다면 그 끝에서 뗀 up도 연결 release이다([§5-5](#5-5-짧은-뒤-바디)).
- **배정 순서:** 연결 release는 head보다 뒤에 있는 끝의 release보다 먼저 배정하고, head와 같은 시각이거나 그보다 앞선 감소 release보다는 나중에 배정한다([§6-4](#6-4-감소-지점-앞뒤의-head)). 연결 release에 배정할 up이 없어도 Miss가 아니다([§6-3](#6-3-head가-있는-21과-감소-release)).
- **범위:** 단독 바디의 중간 교대·끝 창 교대([§2-5](#2-5-바디-중간-교대와-끝-창-안의-교대))와 명시적인 연결 head가 있는 경계를 구별한다. 모든 up을 release에서 제외하거나 모든 Point의 up을 자동 소비하는 규칙으로 확대하지 않는다. 연결 release에 배정되지 않은 up에는 여분 키 허용·같은 double 끝의 키 구별·가장 이른 적격 실제 release 우선([§2-3](#2-3-release-등급과-자격-판정-창-기준), [§2-4](#2-4-여러-끝에-적격인-up의-순서와-키-재사용), [§3-1](#3-1-두-release는-서로-다른-키), [§3-2](#3-2-유지-키와-다른-키의-up))을 적용한다. 기존 RFD 0020 §2.6·§2.12의 모든 조건이나 head 기한까지의 유지 보류를 일괄 복원하지 않는다.
- **구현:** 유지 중 탭을 지원하려면 Point 탭의 up도 연결 후보로 받아야 한다. PR #188의 `registerConnectionUp`은 해당 token이 등록된 unit의 끝에서 연결 경계를 찾는다. B는 뒤 N3에 등록되므로 B up 2010이 N1의 연결 후보에 등록되지 않고, A up 2060이 N1 경계의 연결 몫으로 소비되어 N3가 Miss가 된다([#281](https://github.com/nanana3679/not4k/issues/281) 형태). 구현 시 `NoteJudgmentCore.ts`의 연결 후보 자격과 `ConnectionCorrections.ts`의 소비를 함께 확인하며, 일반 여분 up과 연결 up을 한 규칙으로 무조건 제외하지 않는다.
- **제작:** 이 연결 사례를 탭 길이 조절이나 `holdOnly`로만 해결해야 하는 패턴으로 설명하지 않는다. 별도의 실제 release 정밀도를 면제하려는 Grace 용도와, 정상적인 연결 입력을 판정하는 규칙은 구별한다.

### 4-2. 경계 전에 뗀 연결 release

**연결 head를 처리하기 전에 경계보다 먼저 뗀 up은 앞 바디의 그 몫을 끝낸다.** `long [1000,2000]` → `head 2000` + `long [2000,3000]`에서 A 1000–1960, B 2000–3000(`a-b-` 교대에서 A를 40ms 일찍 뗌)을 대조했다. 앞 바디가 경계 2000까지 hold를 요구한다고 보면 A up 1960부터 부족해 1980에 N1이 유지 실패한다. 일반 끝이었다면 Perfect(−40)인 타이밍이다(PR #188은 연결 경계의 유지를 head 기한까지 보류해 Perfect 2). 당시에는 이 A up을 연결 보정(경계 뒤의 up을 뒤 release에 쓰지 않는 처리)으로 보자고 제안했고, 사용자는 다음과 같이 정정했다(2026-10-16).

> 여기에서는 연결 보정이 작동하지 않음 a up이 n1 종료 b down이 n2 n3 처리해서 바디가 끊어진적이 없음

up이 앞 바디를 끝낼 수 있는 범위를 앞 바디 끝의 Good 창으로 하자고 묻자 사용자는 “ㅇㅇ”라고 답했다(2026-10-16). 위 입력은 N2 Perfect, N3 끝 Perfect로 Perfect 2다.

- **대상:** hold 수를 앞 바디가 요구하는 수 아래로 떨어뜨린 up에만, head 하나에 하나만 적용하며 그 up을 소비한다.
- **범위:** 앞 바디 끝의 Good 창(Normal 기준 1880부터) 안이면 유지 실패가 아니다. 연결 경계에는 점수 항목이 없으므로 등급을 매기지 않는다. `holdOnly` 끝의 이른 완료(E−Good부터)와 같은 기준이다. 그보다 이르면 평소처럼 유예 뒤 유지 실패다.
- **감소 release와의 순서:** 경계에 감소 release가 있으면(head가 있는 2→1) 경계 근처의 첫 up은 지금처럼 감소 release이고([§6-3](#6-3-head가-있는-21과-감소-release)), 감소 release는 연결 release 몫을 채우지 않는다.
- **앞 바디의 끝:** 이 up은 경계 전에 온 연결 release이며, 앞 바디의 그 몫을 그때 끝낸다. 뒤 바디는 head를 처리한 down부터 유지를 판단하므로([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)) 앞 바디의 종료와 head down 사이는 끊김이 아니다. 경계 뒤에 뗀 up([§3-3](#3-3-노트를-처리한-같은-키의-재누름)의 NJ-R13 입력의 A up 2010)과 head를 처리한 뒤의 up([§4-1](#4-1-연결-release)의 교대 A up, 유지 중 탭의 B up)은 이미 끝난 몫의 연결 release다. 두 처리는 2026-10-17에 연결 release 하나로 합쳤다([§4-1](#4-1-연결-release)).
- **연결 release 몫:** 연결 head 하나에 대응하는 떠나는 up은 하나다. 그 up이 경계 전에 앞 바디를 끝냈다면 그 head의 연결 release 몫도 채운 것으로 보고, 뒤 up을 연결 release에 배정하지 않는다. 이 규칙은 처음에 다른 결정에서 도출해 적었고(2026-10-16), 도출한 규칙을 다시 확인하자 사용자가 “ㅇㅇ”라고 답했다(2026-10-17). 같은 확인에서 single 연결의 `a-a-`를 허용 입력으로 두는 것([§9-2](#9-2-허용-입력탈출구)), 재충전을 head 없이 시작하는 `holdOnly` 바디에도 적용하는 것([§8-1](#8-1-시작-직후의-재충전)), double head 연결의 head별 판단을 잠정 규칙으로 두는 것([§4-5](#4-5-double-head가-있는-double-연결))도 함께 확인했다.
  - `doubleLong [1000,2000]` → `head 2000` + `long [2000,2060]`을 `ab-c-`([§6-3](#6-3-head가-있는-21과-감소-release))로 치면서 A·B를 경계 전에 떼는 경우, 이 규칙이 없으면 head 창 안에 있는 C의 끝 up이 연결 release로 빠져 N3가 Miss가 된다.
  - `doubleLong [1000,1950]` → `head 1950` + `doubleLong [1950,2000]` → `long [2000,3000]`에서 A 1000–3000, B 1000–1945, C 1950–2010으로 B를 C로 넘기면, 이 규칙이 없을 때 C up 2010이 연결 release로 빠져 감소 release가 Miss가 된다. 규칙이 있으면 C up이 감소 release(+10)를 처리해 Perfect 3이다.
- head 없는 경계에서도 앞 바디는 끝의 Good 창 안에서 뗀 up으로 끝낼 수 있다([§8-2](#8-2-head-없는-경계)). 같은 키 재타격의 탈출구도 이 규칙으로 손해가 없다([§9-2](#9-2-허용-입력탈출구)).

### 4-3. head를 처리한 down부터 뒤 바디 유지

**연결 head가 있는 경계에서 뒤 바디의 유지는 head를 처리한 실제 down부터 판단한다.** head를 Good 창 안에서 일찍 처리하든 늦게 처리하든 그 down부터 유지와 유지 유예([§2-2](#2-2-유지-유예))를 적용한다. 그전의 공백을 바디 중간의 20ms 초과 공백으로 취급해 뒤 바디를 실패시키지 않는다. head 판정 창 안에서 허용한 늦은 입력을 더 짧은 유지 유예로 다시 실패시키지 않기 위한 규칙이다. 적용 범위는 같은 unit 수의 single 연결, single head가 있는 double 연결에서 head가 맡는 몫, head가 있는 2→1이다. head가 있는 1→2는 [§6-1](#6-1-12-증가), double head 연결은 [§4-5](#4-5-double-head가-있는-double-연결)(잠정)를 따른다.

**경계의 공백.** N1=`long [1000,2000]` → N2=`head 2000` + N3=`long [2000,3000]`에서 A 1000–2010, B 2040–3000의 30ms 공백 사례를 제시했다(PR #188은 연결 head의 판정 창 안에서 교대가 성립해 Perfect 2). 임시 20ms 유지 유예와의 관계를 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> b를 2030에 입력했더라도 정당한 입력으로 취급되어야 하는데 롱노트의 경계 구간에서는 유예가 있으면 안될거같은데

직접 확인한 입력은 B down을 2030으로 옮긴 경우다. A up 2010부터 공백은 20ms이고 N2의 down 오차는 +30ms이며, 이 입력을 정당하게 처리해야 한다는 요구다. “경계에서는 유예가 없어야 한다”는 말을 즉시 실패하는 0ms 제한, 무제한 공백 허용, head의 Good 창만으로 보호하는 규칙 중 하나로 자동 해석하지 않았고, 바디 중간의 20ms 유예를 폐기하는 답으로도 확대하지 않았다. 적용 기준은 이어서 늦은 head 입력으로 확인했다.

**늦은 head.** 같은 차트에서 A 1000–2010, B 2100–3000이면 A up부터 B down까지 90ms 동안 hold가 없지만 B down은 N2의 Good 창 안이다. 사용자는 N3의 유지 기준을 다음과 같이 정했다(2026-10-16).

> n2가 처리된 이후에 유예를 적용하면 될거같은데 죽 b down부터

N2를 처리한 B down 2100부터 N3의 유지를 판단하고 유예를 적용한다. B down부터 무조건 20ms 타이머를 소진하는 것은 아니며, 유예는 필요한 hold 수가 부족해진 때부터 회복할 때까지 잰다. B down 뒤 계속 1개를 유지하면 부족 시간은 없다. B up 3000까지 유지하면 N2 Good(+100), N3 release Perfect로 Perfect 1·Good 1·Miss 0·Full Combo다(PR #188 같음).

**이른 head.** 같은 차트에서 A 1000–1980, B 1960–1990, C 2015–3000이면 N2는 1960에 처리되고 hold는 1990~2015에 25ms 빈다. N3의 유지 판정을 언제부터 시작할지 묻자 사용자는 “1960”이라고 답했다(2026-10-16). 차트상 시작 2000이 아닌 N2를 처리한 실제 down 1960부터 N3의 유지를 판단한다. 부족은 1990부터 재므로 유예 기한은 2010이며, C down 2015로는 N3의 유지 실패를 막거나 이미 실패한 N3를 되살리지 못한다. 이 실패는 사용자가 고른 시작 시점과 20ms 규칙에서 도출한 결과다. 사용자의 “1960”은 N3의 유지 시작에 대한 확인이며, 앞 N1의 실패나 전체 Miss 개수를 승인한 답으로 확대하지 않는다(PR #188: N3 유지 실패 1980·N1 유지 실패 1984, Perfect 1·Miss 2).

**double 연결에서 head가 맡는 몫.** single head가 있는 double 연결([§4-4](#4-4-single-head가-있는-double-연결의-연주))에서는 한 키가 연결 head를 치며 뒤 double 바디의 두 몫 중 하나를 맡는다. 이 문서는 그 몫을 head가 맡는 몫이라고 부른다. hold 수 모델은 몫을 특정 키에 묶지 않으므로, head가 맡는 몫은 뒤 바디가 요구하는 hold 수 가운데 head 하나에 해당하는 1개를 뜻한다. **뒤 바디가 시작한 뒤 head를 처리하기 전까지는 그 몫을 뺀 hold 수를 요구하고, head를 처리한 실제 down부터는 이르든 늦든 그 몫을 포함한 hold 수로 유지와 유지 유예를 판단한다.**

`doubleLong [1000,2000]` → `head 2000` + `doubleLong [2000,2100]`에서 A 1000–2010, C 1000–2100, B 2050–2100은 한 키 유지 중 교대(`a-b- + c---`)를 늦게 친 입력이다. B down 2050은 N2의 Good 창 안(Great +50)이지만 2010~2050에는 C 하나만 눌려 뒤 바디가 요구하는 hold 2개에 하나가 모자란다. 이 부족을 바로 세면 2030에 N3의 한 몫이 유지 실패해, head 판정 창 안에서 허용한 늦은 입력을 다시 실패시킨다. single 연결의 규칙을 double 연결에서 head가 맡는 몫에도 적용할지 묻자 사용자는 “ㅇㅇ”라고 답했다(2026-10-16). 기대 결과는 N2 Great(+50), N3 두 끝 Perfect로 Perfect 2·Great 1이다(PR #188은 등록 키 방식으로 연결 경계의 유지를 head 기한까지 보류해 같은 결과). `ab--- + ..c.`에서는 계속 누르는 A·B가 두 몫을 이미 채우므로 head를 언제 치든 부족이 생기지 않는다.

**head가 있는 2→1.** `doubleLong [1000,2000]` → `head 2000` + `long [2000,3000]`에서 A 1000–2010, B 1000–2015, C 2040–3000은 `ab-c-`([§6-3](#6-3-head가-있는-21과-감소-release))를 C로 40ms 늦게 친 입력이다. N3가 2000부터 hold를 요구하면 B up 2015 뒤 2035에 N3가 유지 실패해 Perfect 2·Miss 1이다. 이 경계에도 같은 규칙을 적용해 N3의 유지를 C down부터 판단할지 묻자 사용자는 “ㅇㅇ”라고 답했다(2026-10-17). 위 입력은 Perfect 3이다(PR #188 같음). head가 있는 2→1의 의도된 연주가 Perfect 창 안 어디서나 손해가 없다는 판단([§9-1](#9-1-의도된-연주의-정의))이 이 결정에 기댄다.

- 실제 release 등급, 연결 release의 소비, 한 up의 중복 사용 금지는 바꾸지 않는다.
- 이미 유지 중인 앞 바디의 실패를 소급 취소하거나 이미 실패한 unit을 되살리지 않는다.
- head를 놓친 경우는 [§5](#5-head-miss)를, head가 없는 경계는 [§8-2](#8-2-head-없는-경계)를 따른다. head가 있는 바디에는 head 없는 시작의 재충전([§8-1](#8-1-시작-직후의-재충전))을 적용하지 않는다.
- 구현 시 연결 head의 성공 시점과 뒤 바디의 유지 활성화, 부족 시간의 시작을 함께 확인한다. PR #188은 등록 키 방식의 연결 보류로 같은 결과를 내는 사례가 있지만, 새 hold 수 모델은 이 보호를 따로 구현해야 한다. 구현하지 않으면 늦은 head 입력과 창 안에서 끊긴 head Miss 입력([§5-4](#5-4-double-연결에서-head가-맡는-몫))에 유지 Miss가 하나씩 더 생긴다.

### 4-4. single head가 있는 double 연결의 연주

N1=`doubleLong [1000,2000]` → N2=`head 2000` + N3=`doubleLong [2000,2100]`이다. 사용자가 이 패턴을 치는 방식으로 제시한 두 연주([§3-3](#3-3-노트를-처리한-같은-키의-재누름)의 재검토 경위 인용)를 다음과 같이 구체화했다.

| 연주 | 입력 | 배정 | 기대 결과 |
|---|---|---|---|
| 두 키 유지 중 탭(`ab--- + ..c.`) | A/B 1000–2100, C 2000–2020 | C down 2000이 N2, C up 2020이 연결 release, A/B up 2100이 N3의 두 release | Perfect 3 (PR #188: A up 2100을 연결 release에 배정해 N3u2 Miss, Perfect 2·Miss 1, #281 형태 결함) |
| 한 키 유지 중 교대(`a-b- + c---`) | C 1000–2100, A 1000–2010, B 2000–2100 | B down 2000이 N2, A up 2010이 연결 release, B/C up 2100이 N3의 두 release | Perfect 3 (PR #188 같음) |

두 연주에서 도출한 결과 Perfect 3(N2 head와 N3의 두 release)을 제시하자 사용자는 다음과 같이 답했다(2026-10-16).

> ㅇㅇ 그리고 저 두 방법이 저 패턴을 치는 의도된 두가지 방법임

- **두 연주는 single head가 있는 double 연결의 의도된 연주이며 기대 결과는 모두 Perfect 3이다.** 판정 모델이 점수 손해 없이 처리해야 하는 기준 입력이며 구현 시 회귀 사례로 둔다. 두 방식 외의 입력을 금지하거나 별도 불이익을 주지 않는다.
- head를 늦게 친 한 키 유지 중 교대는 방법은 의도된 연주이며 Great는 타이밍 오차다([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지), [§9-1](#9-1-의도된-연주의-정의)).
- NJ-R13 입력(A 1000–2010, B 1000–2040·2050–2100)은 두 방식 어디에도 해당하지 않으며, 결과는 [§3-3](#3-3-노트를-처리한-같은-키의-재누름)의 Perfect 1·Great 2·Miss 0이다.
- 두 키 유지 중 탭은 최상위 차트에서나 나올 패턴이며 다른 패턴과 연계하면 칠 수 없을 만큼 복잡해진다고 사용자는 평가했다([§4-5](#4-5-double-head가-있는-double-연결)의 인용). 등장하더라도 단독으로 배치된다는 뜻이며, 의도된 연주와 기대 결과는 바꾸지 않는다.
- 이 차트의 N3(2000~2100)와 [§4-1](#4-1-연결-release)의 N3(2000~2060)는 끝이 연결 head의 Good 창 안에 있다. 의도된 두 연주는 규칙대로 Perfect를 받지만, 다른 키를 끝 뒤까지 쥐는 입력은 보장하지 않는다. 이 구분은 제작 지침으로 막지 않고 튜토리얼로 전달한다([§9-4](#9-4-여분-키-구분의-튜토리얼-전달)).
- head를 놓쳤을 때 head가 맡는 몫의 처리는 [§5-4](#5-4-double-연결에서-head가-맡는-몫)를 따른다. 두 키 유지 중 탭의 #281 결함 수정은 구현 단계에서 다룬다.

### 4-5. double head가 있는 double 연결

N1=`doubleLong [1000,2000]` → N2=`double head 2000` + N3=`doubleLong [2000,2100]`이다. 한 레인에 키가 4개 바인딩되므로 다음 세 연주를 제시했다.

| 연주 | 입력 | 기대 결과 |
|---|---|---|
| 다른 두 키로 교대(`ab-cd-`) | A/B 1000–2010, C/D 2000–2100 | Perfect 4 (PR #188 같음) |
| 두 키 유지 중 다른 두 키로 탭(`ab--- + ..cd.`) | A/B 1000–2100, C/D 2000–2020 | Perfect 4 (PR #188: A/B up 2100을 연결 release에 배정해 N3의 두 release Miss, Perfect 2·Miss 2, #281 형태 결함) |
| 같은 두 키로 재타격(`ab-ab-`) | A/B 1000–1990, A/B 2000–2100 | Perfect 4 (PR #188 같음) |

세 연주 모두 연결용 up 두 개를 소비하고 남은 up 두 개로 N3의 두 release를 처리하므로, 기대 결과는 N2의 두 head와 N3의 두 release로 Perfect 4다. 사용자는 다음과 같이 답했다(2026-10-16).

> ab-cd- 또는 ab--- + ..cd. 가 의도된 방법인데 ab-ab- 도 허용 해야할듯 그런데 이 패턴은 한 레인에 손가락을 네개나 요구해서 지금 당장은 게임 안에 넣을 생각이 없어 이전에 다뤘던 ab--- + ..c. 이것도 최상위 차트에서나 나올법한 패턴이고 다른 패턴과 연계하면 복잡성이 너무올라가서 못할정도라고 봄 (나오더라도 단독으로 등장할거란뜻)

- **의도된 연주:** 다른 두 키로 교대(`ab-cd-`)와 두 키 유지 중 다른 두 키로 탭(`ab--- + ..cd.`)이다. **같은 두 키로 재타격(`ab-ab-`)은 판정이 손해 없이 처리하는 허용 입력(탈출구)이다**([§9-2](#9-2-허용-입력탈출구)).
- **패턴 범위:** 한 레인에 네 손가락을 요구하므로 **double head가 있는 double 연결은 당분간 게임 차트에 넣지 않는다.** 위 기대 결과는 판정 규칙의 일관성을 확인한 기록으로 남긴다. 연결 release([§4-1](#4-1-연결-release))과 double 끝의 키 구별([§3-1](#3-1-두-release는-서로-다른-키), [§3-3](#3-3-노트를-처리한-같은-키의-재누름))을 이 패턴에 적용한 도출 결과다.
- **head별 유지(잠정):** 사용자의 `ab- + ab-` 해석([§9-2](#9-2-허용-입력탈출구))에 따라 double head 연결에서도 head마다 그 몫의 유지를 그 head를 처리한 down부터 판단한다([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)의 확대). head를 엇갈려 치거나 하나만 놓친 경우를 확인하지 않았으므로 이 규칙은 잠정이며, double head 연결을 차트에 넣을 때 다시 확인한다.
- #281 형태 결함은 single 연결의 유지 중 탭([§4-1](#4-1-연결-release))에서도 발생하므로, 이 패턴을 차트에서 제외하더라도 수정 대상으로 남는다. 지원할 차트 패턴의 범위는 [PRD의 미정 사항](../prd.md#12-미정-사항)에서 추적한다.

## 5. head Miss

연결 head를 놓친 경우의 처리다. [§5-1](#5-1-계속-유지한-뒤-바디)~[§5-3](#5-3-head-창-뒤에-끊김)의 차트는 N1=`long [1000,2000]` → N2=`head 2000` + N3=`long [2000,3000]`이고 N2의 Good 기한은 2120이다. 세 항목은 head를 놓쳤다는 이유만으로 뒤 바디 전체를 실패시키지도, 이후의 모든 유지 실패를 면제하지도 않는다는 구분이다.

### 5-1. 계속 유지한 뒤 바디

A를 1000부터 3000까지 계속 유지하고 끝에 뗀다. N2를 칠 새 down은 없으므로 N2는 Miss이지만, hold 수는 N3 끝까지 1을 충족한다. N3의 판정을 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> n3 릴리즈 처리

**연결 head를 놓쳤다는 이유만으로 계속 유지한 뒤 바디의 release를 막지 않는다.** A up 3000이 N3의 실제 release를 처리해 N2 head Miss, N3 release Perfect, 합계 Perfect 1·Miss 1·달성률 50.00%다(PR #188 같음). head 입력 요구와 바디의 hold 수 충족을 구분하며, 모든 바디의 시작·release에 성공한 head를 필수 전제로 두지 않는다. head down이 없으면 뒤 바디가 계속 미시작이거나 자동 실패한다는 규칙도 두지 않는다. 구현 시 이 사례의 N3 release를 종속 0점이나 유지 Miss로 바꾸지 않는지 검증한다.

**적용 범위:** 뒤 바디의 끝이 head의 Good 기한 뒤에 있을 때의 규칙이다. 끝이 head의 Good 창 안에 있으면 [§5-5](#5-5-짧은-뒤-바디)를 따른다.

### 5-2. head 창 안에서 끊김

A를 1000에 누르고 2010에 뗀 뒤 추가 입력이 없다. N2를 칠 down이 없고, N3의 hold 수는 2010부터 0이다. PR #188의 N2 Miss 하나·N3 끝 0점 처리 결과를 보여 주고 N2와 N3의 Miss 배정을 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> 지금처럼

**head 창 안에서 유지가 끊기고 head도 놓치면 head Miss 하나만 내고, 뒤 끝은 추가 Miss 없이 종속 0점으로 정산한다.** N2의 Good 기한 2120에 처리하며 합계 Perfect 0·Miss 1·달성률 0.00%다(PR #188 같음). N2의 head Miss와 별도 N3 유지 Miss·release Miss로 중복 집계하지 않는다. 2010부터의 공백에 20ms를 바로 적용해 2030에 N3 Miss를 추가하지 않는다. N3의 끝 점수 항목을 삭제하거나 성공으로 바꾸는 규칙은 아니다. 구현 시 연결 head 판정 대기와 유지 부족, `dependentZero` 정산의 순서를 함께 확인한다.

- A를 기한 2120과 같은 시각에 떼도 이 항목을 따른다(Miss 1). 기한 시각의 입력까지 반영한 hold 수로 뒤 바디를 채웠는지 보기 때문이다([구현 규칙](#구현-규칙-판정-시각과-입력-순서), 2026-10-18).

### 5-3. head 창 뒤에 끊김

A를 1000부터 2200까지 누르고 뗀 뒤 추가 입력이 없다. N2에는 새 down이 없어 2120에 head Miss가 되고, 그때까지 N3의 hold 수는 1을 충족한다. 2200부터 유지가 끊긴다. PR #188의 Miss 2 결과를 보여 주고 N3의 유지 부족 처리를 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> 기존대로

**head 창이 끝난 뒤 새로 발생한 유지 부족은 head Miss와 별도의 유지 Miss로 처리한다.** 합계 Miss 2이며 N3의 끝은 종속 0점으로 정산하고 release Miss를 다시 추가하지 않는다. 20ms 유예를 적용하면 부족은 A up 2200부터 시작하므로 **N3 유지 실패의 기한은 2220**이며, N2의 2120 head Miss에는 영향을 주지 않는다(PR #188은 유예가 없어 2200에 유지 실패, 달성률 0.00%). 사용자의 답은 추가 유지 Miss를 처리하는 결과의 확인이며, 유지 유예를 폐기하는 답으로 확대하지 않는다. 프레임과 같은 timestamp 입력의 처리 순서는 [구현 규칙](#구현-규칙-판정-시각과-입력-순서)에서 정했고(2026-10-18), 새 코어의 검증은 [#287](https://github.com/nanana3679/not4k/issues/287)에서 한다.

- A를 기한 바로 뒤인 2121에 떼도 이 항목을 따른다. 기한 2120을 그 up보다 먼저 정산해 뒤 바디를 채운 것으로 보므로 2141에 유지 Miss, Miss 2다([구현 규칙](#구현-규칙-판정-시각과-입력-순서), 2026-10-18).

### 5-4. double 연결에서 head가 맡는 몫

single head가 있는 double 연결에서 head를 놓치면 **head의 Good 기한에 head가 맡는 몫([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지))을 정리한다.** 그때 hold 수가 그 몫까지 채우고 있으면 그 몫은 계속 유지 판정을 받는다. 끝까지 유지하면 실제 release를 처리하고([§5-1](#5-1-계속-유지한-뒤-바디)), 이후 부족해지면 유예 뒤 유지 Miss와 종속 0점으로 처리한다([§5-3](#5-3-head-창-뒤에-끊김)). 채우지 못하고 있으면 head Miss 하나만 내고 그 몫의 release는 종속 0점으로 정산한다([§5-2](#5-2-head-창-안에서-끊김)). 이때부터 뒤 바디가 요구하는 hold 수는 그 몫만큼 줄고, 나머지 몫은 남은 키로 계속 판정한다.

차트는 `doubleLong [1000,2000]` → `head 2000` + `doubleLong [2000,3000]`이고, C는 1000부터 3000까지 누르며 N2를 칠 새 down은 없다.

| 입력 | 대응하는 single 사례 | 기대 결과 |
|---|---|---|
| A 1000–3000 | [§5-1](#5-1-계속-유지한-뒤-바디) | 2120에 N2 Miss. A·C up 3000이 N3의 두 release를 처리한다. Perfect 2·Miss 1 (PR #188 같음) |
| A 1000–2010 | [§5-2](#5-2-head-창-안에서-끊김) | 2120에 N2 Miss, head가 맡는 몫의 release는 추가 Miss 없이 종속 0점. 이후 N3가 요구하는 hold는 1개이며 C up 3000이 남은 release를 처리한다. Perfect 1·Miss 1 (PR #188 같음) |
| A 1000–2200 | [§5-3](#5-3-head-창-뒤에-끊김) | 2120에 N2 Miss. A up 2200부터 hold가 하나 모자라 2220에 N3 한 몫이 유지 Miss, 그 몫의 release는 종속 0점. C up 3000이 남은 release를 처리한다. Perfect 1·Miss 2 (PR #188 같음, 유예가 없어 유지 실패 시각은 2200) |

head가 맡는 몫에 single 사례의 규칙을 그대로 적용할지 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> ㅇㅋ

이 결정은 unit 수가 같은 double 연결에 single head가 있는 경우에 적용한다. double head 연결은 [§4-5](#4-5-double-head가-있는-double-연결)의 잠정 규칙을 따른다. unit 수가 바뀌는 연결의 head에는 이 결정을 자동 확대하지 않았으며, head가 있는 2→1의 뒤 바디 유지는 [§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)에서 정했다. 위 입력은 엔진 이행 시 회귀 사례로 둔다. PR #188은 등록 키 방식의 연결 보류로 같은 결과를 내지만, 새 hold 수 모델은 이 보호를 따로 구현해야 한다.

### 5-5. 짧은 뒤 바디

**뒤 바디의 끝이 head의 Good 창 안에 있고 head가 아직 처리되지 않았다면, 그 끝에서 뗀 up은 연결 release이다.** head를 놓치면 [§5-2](#5-2-head-창-안에서-끊김)처럼 head Miss와 끝 종속 0점으로 정리한다.

`long [1000,2000]` → `head 2000` + `long [2000,2060]`에서 A 1000–2060, head 입력은 없다. N3 끝이 head의 Good 창(2120까지) 안이라 A up 2060이 올 때 head는 아직 처리되지 않았다. 계속 유지한 바디의 release 처리([§5-1](#5-1-계속-유지한-뒤-바디))를 따르면 N3 release를 처리해 Perfect 1·Miss 1이지만, up의 용도를 head 기한까지 미루는 보류가 필요하다. 경계 뒤·head 전의 up을 연결 release로 보면([§3-3](#3-3-노트를-처리한-같은-키의-재누름)의 A up 2010과 같다) A up은 연결 release이고, 2120에 N2 Miss와 N3 끝 종속 0점으로 Miss 1이다(PR #188 같음). 후자를 추천하자 사용자는 “ㅇㅇ”라고 답했다(2026-10-17).

- double(`doubleLong [2000,2060]`, A/B 1000–2060)은 Perfect 1·Miss 1이다.
- 연결 release의 보류([부록 A-6](#a-6-연결-release의-보류))를 들이지 않기 위한 결정이며, [§5-1](#5-1-계속-유지한-뒤-바디)의 적용 범위를 끝이 head 기한 뒤에 있는 바디로 좁힌다.

## 6. 증가와 감소

### 6-1. 1→2 증가

**head 없는 1→2 증가에서 늘어난 unit은 미리 누른 키로 채워도 되고 S+Good까지 채우면 된다. 그 기한을 넘기면 그 unit은 시작 실패 Miss 1개이며, 끝은 추가 Miss 없이 종속 0점으로 정산한다.** 기한 뒤에 hold 수를 채워도 실패한 unit을 되살리지 않는다([§2-1](#2-1-hold-수로-시작과-유지-판단)). 이미 유지 중인 N2u1은 영향을 받지 않는다.

N1=`long [1000,2000]` → N2=`doubleLong [2000,3000]`이며 경계에 head가 없다. A는 1000–3000 동안 유지하고, 늘어난 unit을 채우는 B의 down 시각만 바꿔 대조했다.

| B down | 기대 결과 |
|---|---|
| 2000 | 기본 연주. hold 수가 2000부터 2가 되어 N2가 시작하고, A/B up 3000이 N2의 두 release를 처리해 Perfect 2 (PR #188 같음) |
| 1500 (미리 누름) | 미리 누른 키도 hold 수에 들어가므로 Perfect 2 (PR #188은 B를 시작 입력으로 인정하지 않아 N2u2 시작 실패로 Perfect 1·Miss 1) |
| 2050 | S+Good까지 채울 수 있고 시작 점수가 없으므로 Perfect 2 (PR #188 같음) |
| 2200 | N2 시작의 Good 기한 2120을 80ms 지나서 채운다. 2120에 N2u2 시작 실패 Miss, N2u2의 끝은 종속 0점. 2200의 B는 실패한 N2u2를 되살리지 않는다. Perfect 1·Miss 1 (PR #188 같음) |

B down 2200의 결과를 새 모델에서도 유지할지 묻자 사용자가 동의했다(2026-10-16). 시작 실패와 끝 release Miss를 중복 집계하지 않으며, [§5-2](#5-2-head-창-안에서-끊김)의 head Miss를 Miss 하나와 끝 종속 0점으로 정리한 것과 같은 집계 방식이다. 증가 직후 hold를 잃었을 때의 재충전과, 이어지는 몫까지 S+Good 기회를 받는 규칙은 [§8-1](#8-1-시작-직후의-재충전)·[§8-2](#8-2-head-없는-경계)를 따른다.

**head가 있는 1→2.** 늘어난 몫이 새로 시작하는 몫이라 S+Good까지 채우면 되므로 따로 정하지 않았다. `long [1000,2000]` → `head 2000` + `doubleLong [2000,3000]`, A 1000–3000, B 2040–3000은 Perfect 3이다(PR #188은 B down을 head에만 써서 늘어난 몫이 시작 실패, Perfect 2·Miss 1).

### 6-2. head 없는 2→1

**head 없는 2→1 감소에서는 줄어드는 몫 하나에 실제 release를 판정한다.** 등급은 일반 release와 같은 Perfect / Great / Good / Miss이며, 창 안에 up이 없으면 Miss다. hold 수가 필요한 수보다 많아도 감소 release를 면제하지 않는다. 떼는 동작은 있어야 한다는 원칙([§1-2](#1-2-패턴을-먼저-정하고-교대-자체의-점수-손해를-금지))과 같은 방향이다. 2→1에 `holdOnly`가 붙으면 면제한다([§7-2](#7-2-holdonly-감소에서-키를-남기는-연주)).

**감소 release는 2→1 경계에서 뒤 바디로 이어지지 않고 끝나는 몫의 끝 release다(2026-10-17).** 두 몫 중 하나는 뒤 바디로 이어지므로 연결 경계처럼 등급 있는 release가 필요 없고, 나머지 하나는 경계에서 끝나므로 일반 끝처럼 실제 release가 필요하다. 그래서 등급, 경계 시각 기준의 판정 창, 창 안에 up이 없을 때의 Miss, hold 수가 남아도 면제하지 않는 점, `holdOnly`의 면제가 모두 일반 끝 release와 같다. 몫은 물리 키에 묶이지 않으므로 어느 키를 먼저 떼든 창 안의 첫 적격 up이 이 끝을 처리한다([§2-4](#2-4-여러-끝에-적격인-up의-순서와-키-재사용)). head가 있는 2→1에도 같은 정의를 쓴다([§6-3](#6-3-head가-있는-21과-감소-release)).

이해 확인 중 사용자는 감소 판정 자체가 필요한지 물었다(2026-10-17).

> 감소 릴리즈 라는 용어 자체가 필요한가 a--- + b-.. / ab--c- 릴리즈 개수가 1 또는 2개인데 감소 판정이 필요한게 아니라 발생할수 있는 여분 릴리즈만 조심해서 차트 짜면 될거같은데

두 연주 모두 첫 up이 감소 release를 처리하고 up 1개와 2개의 차이는 연결 release가 받는다고 설명했다. 감소 판정을 없애면 경계에서 아무 키도 떼지 않는 연주(아래 B를 3000까지 유지)는 손해가 없어지지만, A·B를 함께 떼는 연주의 둘째 up이 갈 곳이 없어 짧은 뒤 바디의 끝을 일찍 처리한다([§6-3](#6-3-head가-있는-21과-감소-release)의 짧은 뒤 바디 표 둘째 행이 Perfect 3에서 Perfect 1·Great 1). 사용자는 다음과 같이 다시 정리하고 감소 release의 정의를 이렇게 바꾸자고 했다(2026-10-17).

> 연결된 롱노트 사이에는 릴리즈 없어도 되잖아 근데 감소에서는 n1u1이 n2에 연결된다고 볼수있고 그럼 n1u2는 남아있으니 릴리즈가 필요하지 이러면 감소 릴리즈라는 말 없어도 릴리즈 필요한 이유가 설명되나?

> 감소 릴리즈의 정의를 그렇게 바꾸면 될까

판정 결과는 바뀌지 않는다. 감소 release라는 이름은 이 끝을 가리키는 데 계속 쓴다.

N1=`doubleLong [1000,2000]` → N2=`long [2000,3000]`이며 경계에 head가 없다. A는 1000–3000 동안 유지하고 B를 떼는 시각만 바꿔 대조했다. 새 hold 수 모델에서도 줄어드는 몫에 실제 release 하나를 요구하는 기존 규칙([RFD 0020 §2.13](0020-note-judgment-units-and-inheritance.md#213-head가-있는-21-감소의-release--후속-채택)의 head 없는 경우, NJ-R01·NJ-R03)을 유지할지 묻자 사용자가 동의했다(2026-10-16). 아래 PR #188 실행 결과를 새 모델의 기대 결과로 둔다.

- **B up 2000:** 감소 release Perfect, A up 3000의 N2 release Perfect로 Perfect 2.
- **B up 1950:** 감소 release Great(-50), N2 release Perfect.
- **B를 3000까지 유지:** 경계의 창 안에 up이 없어 2120에 감소 release Miss. 3000의 A/B up 중 하나가 N2 release Perfect를 처리해 Perfect 1·Miss 1.

head 없는 경계에서 경계 전 연결 release와 뒤 바디의 S+Good은 [§8-2](#8-2-head-없는-경계)를 따르며, 2→1에서는 첫 up이 감소 release다.

### 6-3. head가 있는 2→1과 감소 release

**head가 있는 2→1 감소에도 감소 release 하나를 판정한다.** 이 경계의 점수 항목은 head와 감소 release다. [RFD 0020 §2.13](0020-note-judgment-units-and-inheritance.md#213-head가-있는-21-감소의-release--후속-채택)의 감소 release 제거(2026-10-01)를 대체한다. head 유무와 관계없이 2→1 감소에는 끝나는 몫의 끝 release인 감소 release가 하나 있으며([§6-2](#6-2-head-없는-21)), `holdOnly`가 붙으면 면제한다.

**경계 근처의 첫 up이 감소 release를 처리하고, 연결 head의 창 안에 up이 하나 더 있으면 그 up을 연결 release에 배정한다.** 연결 release에 배정할 up이 없어도 Miss가 아니다. 연결 release를 보류했다가 나중에 용도를 정하는 방식은 채택하지 않는다([부록 A-6](#a-6-연결-release의-보류)). 뒤 바디의 유지는 head를 처리한 실제 down부터 판단한다([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)). 경계 전에 앞 바디를 끝내는 up([§4-2](#4-2-경계-전에-뗀-연결-release))보다 첫 up의 감소 release가 먼저다.

차트는 N1=`doubleLong [1000,2000]` → N2=`head 2000` + N3=`long [2000,3000]`이다. §2.13을 유지할지 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> 릴리즈는 있는게 일관성 있을거 같은데

head 없는 2→1([§6-2](#6-2-head-없는-21))처럼 줄어드는 몫에 실제 release를 두는 방향이다. §2.13이 감소 release를 없앤 이유는 한 키만 옮기는 연주에서 경계 근처 up이 하나뿐이라, 그 up을 연결 release에 배정하면 감소 release가 Miss가 되었기 때문이다. 사용자는 정당한 연주끼리도 up 수가 다르다고 지적했다.

> ab--c-- (릴리즈 1) / ab--- + ..c. (릴리즈 1) / a---- + b-.. + ..c. (릴리즈 2) 유효한 걸로 보이는 입력방법이 3가지인데 릴리즈 횟수가 다르네

이에 맞춰 위 우선순위를 제시했다. 연결 release는 남는 up이 뒤 끝에 잘못 쓰이지 않게 막는 장치이므로, 연결 release에 배정할 up이 없어도 Miss가 아니다. 사용자는 이 우선순위를 연결 release 보류의 기각([부록 A-6](#a-6-연결-release의-보류)), 짧은 뒤 바디에 대한 제작 지침 7항(이후 폐지, [§9-3](#9-3-제작-지침-48항))과 함께 확인했다(2026-10-16, “응”). 아래 네 연주는 모두 N2 head, 감소 release, N3 끝으로 Perfect 3이다. PR #188은 §2.13을 아직 구현하지 않아 감소 release 항목이 남아 있고, 연결 release를 감소 release보다 먼저 배정한다.

| 연주 | 경계 근처 up | 기대 결과 | PR #188 |
|---|---|---|---|
| A·B를 떼고 C로 head를 친 뒤 유지(A up 2015, C 2020–3000, B up 2030) | 2개 | Perfect 3 | Perfect 3 |
| A 유지, B만 C로 옮김(`ab--c--`; B up 2015, C 2020–3000) | 1개 | Perfect 3 | Perfect 2·Miss 1 |
| A/B 유지 중 C로 head 탭(`ab--- + ..c.`; C 2000–2020) | 1개 | Perfect 3 | Perfect 2·Miss 1 |
| A 유지, B를 떼고 C로 head 탭(`a---- + b-.. + ..c.`; B up 2010, C 2000–2020) | 2개 | Perfect 3 | Perfect 3 |

**의도된 연주.** 사용자는 결정을 확인하면서 A/B를 유지한 채 C로 head만 탭하는 연주를 다시 평가했다(2026-10-16).

> 응 근데 생각해보니 ab--- + ..c.은 c 이후 싱글 바디인데 더블로 누르니까 한개 down이 남아있고 이거 해결이 안되니까 의도된 플레이라고 보면 안될거같고 이후에 이거때문에 발생하는 릴리즈가 이후 판정에 미치는 영향은 생각 안하기로

같은 기준을 적용하면 A를 유지하고 B만 C로 옮긴 뒤 C를 계속 누르는 연주도 경계 뒤에 A와 C가 남는다. 이 연주는 RFD 0020 §2.13에서 “b만 c로 옮기는 법”으로 인정했던 입력이다. 이를 묻자 사용자는 다음과 같이 답했다(2026-10-16).

> 대신 c를 바로 떼는걸 의도된 연주로 봐줘

- **head가 있는 2→1의 의도된 연주는 두 가지다.** (1) A·B를 모두 떼고 C로 head를 친 뒤 유지한다. (2) A를 유지하고 B를 떼며, C로 head를 쳐서 바로 뗀다. (2)에서 B를 떼는 것과 C를 누르는 순서는 어느 쪽이어도 된다(B up 2015 → C 2020–2040, 또는 C 2000–2020 → B up 2010). 두 연주 모두 경계 뒤 single 바디에 키 하나가 남고, 첫 up이 감소 release, 다음 up이 연결 release, 남은 키의 up이 N3 끝을 처리해 Perfect 3이다.
- **C를 계속 누르는 연주와 A/B 유지 중 C 탭은 의도된 연주가 아니다.** 경계 뒤 single 바디에 키가 두 개 남기 때문이다. 후자에 대해 사용자는 “ab를 끝까지 누르고 있으니까 릴리즈가 하나 남아서 의도된 연주가 아님”이라고 다시 확인했다(2026-10-16). 판정은 같은 규칙으로 처리하고(첫 up이 감소 release) 막지 않으며, 남은 키의 up이 뒤 판정에 주는 영향은 검토하지 않는다. [§2-3](#2-3-release-등급과-자격-판정-창-기준)에서 여분 up의 영향을 플레이어 책임으로 둔 것과 같은 원칙이다. RFD 0020 §2.13의 “b만 c로 옮기는 법”은 C를 바로 떼는 연주로 좁힌다.

**짧은 뒤 바디.** 뒤 바디의 끝이 head의 Good 창 안에 있어도 의도된 연주는 up 수가 감소 release·연결 release·끝 release와 맞으므로 Miss가 나지 않는다. Miss는 경계 뒤에 바디가 요구하는 수보다 키를 더 남긴 입력에서만 난다. 결과는 지금 규칙으로 도출한 값이며, 괄호 안은 PR #188 실행이다.

| 차트 | 입력 | 결과 |
|---|---|---|
| `doubleLong [1000,2000]` → `head 2000` + `long [2000,2060]` | A 1000–2500, B 1000–2015, C 2020–2060 (A를 끝 뒤까지 쥠) | B up 감소 release, C up 2060 연결 release, N3 끝 Miss. Perfect 2·Miss 1 (Perfect 1·Great 1·Miss 1) |
| 같은 차트 | A 1000–2010, B 1000–2015, C 2020–2060 (`ab-c-`) | A up 감소 release, B up 연결 release, C up N3 끝. Perfect 3 (Perfect 3) |
| 같은 차트 | A 1000–2060, B 1000–2015, C 2020–2040 (A 유지, C 탭) | B up 감소 release, C up 연결 release, A up N3 끝. Perfect 3 (Perfect 3) |
| `doubleLong [1000,2000]` → `head 2000` + `long [2000,2200]` | A 1000–2500, B 1000–2015, C 2020–2100 | B up 감소 release, C up 2100(끝 −100)은 head 창(Normal 2120까지) 안이라 연결 release, N3 끝 Miss. Perfect 2·Miss 1 (Perfect 1·Good 1·Miss 1) |

짧은 뒤 바디에서 A를 유지하고 C로 head를 쳐서 바로 떼는 연주가 비직관적이라고 사용자는 평가했다(2026-10-16). 인용의 19i는 리뷰용 사례 페이지 번호로, 위 표의 셋째 행(A 유지, C 탭)이다.

> 19i가 스펙상으로는 의도된 연주인데 너무 비직관적 이어서 실제 연주는 ab-c- 이게 가장무난한거같아

> A도 b랑 같이 떼는거임

`ab-c-`는 A·B를 경계에서 함께 떼고 C로 head를 친 뒤 유지하는 연주로, 의도된 연주 (1)과 같다. 짧은 뒤 바디에서는 `ab-c-`가 가장 무난하고, A를 유지하며 C를 바로 떼는 연주는 비직관적이라는 사용자 평가를 기록한다. 이 배치를 피하라는 제작 지침(7항)은 두었다가 폐지했으며, 여분 키 구분은 튜토리얼로 전달한다([§9-3](#9-3-제작-지침-48항), [§9-4](#9-4-여분-키-구분의-튜토리얼-전달)).

- 위 네 연주와 짧은 뒤 바디 대조 입력은 엔진 이행 시 회귀 사례로 둔다. PR #188은 연결 release를 먼저 배정하므로 up이 하나인 두 연주에서 Miss를 낸다. 구현 시 감소 release를 연결 release보다 먼저 채우도록 바꾸며, 감소 release 제거를 구현하려던 #181의 범위도 이 결정에 맞춰 다시 정한다.
- 경계 자신에 release가 있는 연결은 head가 있는 2→1뿐이므로, 같은 unit 수 연결의 연결 release 결과는 바뀌지 않는다.
- head가 있는 2→1 경계마다 점수 항목이 하나 늘어 §2.13 이전의 판정 수로 돌아간다. 미공개 개발 단계이므로 기존 차트의 판정 수 변화를 따로 이전하지 않는다.
- 짧은 뒤 바디 문제는 같은 unit 수 연결에도 있다. 다른 키를 끝 뒤까지 쥔 채 head를 친 키로 짧은 뒤 바디의 끝을 떼면 그 up이 연결 release에 배정된다.

### 6-4. 감소 지점 앞뒤의 head

바디 안에 Point를 둘 수 없으므로 head를 감소 지점에서 옮기면 감소 경계와 연결 경계가 나뉜다. [§6-3](#6-3-head가-있는-21과-감소-release)의 차트에서 N2 head를 감소 지점에서 50ms 옮긴 두 차트를 대조했다.

**배정 순서: 연결 release는 head보다 뒤에 있는 끝의 release보다 먼저 배정하고, head와 같은 시각이거나 그보다 앞선 감소 release보다는 나중에 배정한다.** [§4-1](#4-1-연결-release)의 연결 release와 [§6-3](#6-3-head가-있는-21과-감소-release)의 첫 up 우선을 차트 시각으로 정리한 순서이며, 감소 release도 끝 release이므로([§6-2](#6-2-head-없는-21)) 연결 release를 head 시각에 두고 같은 시각이면 끝을 먼저 두면 차트 시각이 가장 이른 끝을 먼저 처리하는 규칙([§2-4](#2-4-여러-끝에-적격인-up의-순서와-키-재사용))과 같다. head가 감소 지점과 같은 시각인 [§6-3](#6-3-head가-있는-21과-감소-release)이 그 한 경우다. 감소 release를 모든 경우에 연결 release보다 먼저 채우는 대안은 채택하지 않았다([부록 A-7](#a-7-감소-release를-언제나-연결-release보다-먼저-채우기)).

**head가 감소 뒤.** `doubleLong [1000,2000]` → `long [2000,2050]` → `head 2050` + `long [2050,3000]`, A 1000–3000, B 1000–2010, C 2050–3000. B up 2010이 2000의 감소 release Perfect(+10)를 처리하며 Perfect 3이다(PR #188 같음).

**head가 감소 앞.** `doubleLong [1000,1950]` → `head 1950` + `doubleLong [1950,2000]` → `long [2000,3000]`. 2000의 감소 release는 head보다 뒤의 끝이므로 연결 release가 먼저다.

| 입력 | 결과 |
|---|---|
| A 1000–3000, B 1000–2010, C 1950–3000 (C로 head를 친 뒤 계속 누름) | B up 2010은 1950 head의 교대용 창 안이라 연결 release, 감소 release Miss. Perfect 2·Miss 1 (PR #188 같음) |
| A 1000–3000, B 1000–2010, C 1950–1970 (C로 head 탭) | C up 연결 release, B up 감소 release, A up N4 끝. Perfect 3 (PR #188: B up 2010에 의한 N4 유지 실패로 Perfect 1·Miss 2) |
| A 1000–3000, B 1000–1945, C 1950–2010 (B를 C로 넘김) | B up이 앞 바디를 끝내며 연결 release 몫을 채우고, C up이 감소 release(+10). Perfect 3 ([§4-2](#4-2-경계-전에-뗀-연결-release)) |

첫 행은 C로 head를 친 뒤 계속 눌러 1950~2000의 double 바디에 A·B·C 세 키를 남긴 연주이며 의도된 연주가 아니다. 이 배치는 한때 제작 지침으로 지양했으나 의도된 연주가 손해 없이 처리되므로 그 지침을 폐지했다([§9-3](#9-3-제작-지침-48항)). 감소 지점 뒤의 head와 감소 지점과 같은 시각의 head에도 따로 제한이 없다. 둘째 행의 PR #188 결과는 새 hold 수 모델에서 바뀌며, 위 입력은 엔진 이행 시 회귀 사례로 둔다.

## 7. `holdOnly`

### 7-1. `holdOnly` 끝은 Good 창 안의 up을 가져간다

**`holdOnly` 끝은 자기 Good 창 안의 up 하나를 가져가며 등급은 항상 Perfect다.** up이 없으면 지금처럼 유지로 완료한다(E까지 유지하거나 E−Good 이후에 hold가 줄면 완료). 배정 순서는 다른 끝과 같다. 차트 시각이 이른 끝이 먼저이고, 연결 release는 head 뒤 끝보다 먼저, head와 같거나 앞선 감소 release보다 나중이다([§6-4](#6-4-감소-지점-앞뒤의-head)). [RFD 0020 §2.3](0020-note-judgment-units-and-inheritance.md#23-holdonly)의 “상태 완료는 keyup을 소비하지 않는다”는 새 모델에서 이 규칙으로 대체한다.

**두 연주가 모두 정당하다.** `holdOnly` 끝은 일반 끝과 같은 모양이므로, 플레이어가 그 끝에서 떼는 것(release 1)도 떼지 않는 것(release 0)도 정당하다. 사용자는 다음과 같이 설명했다(2026-10-16).

> 근데 모양이 holdonly 아닌거랑 같으니까 사용자는 똑같이 2060에 릴리즈 하는게 정당한데 그래서 뗄수도 있고 안뗄수도 있음 이거 떄문에 이후에 릴리즈 개수 영향받는 패턴이 가까이 오면 안될듯, 이 지침이 있으면 유지로만 판정해도 될둣

이 판단에 따라 처음에는 `holdOnly`를 유지로만 판정하고 up을 소비하지 않으며, `holdOnly` 끝 바로 뒤에 up 개수에 따라 결과가 달라지는 판정을 두지 않는 제작 지침을 정했다. 이후 그 지침을 지켜도 같은 연주의 결과가 갈리는 사례가 나와 지금의 규칙으로 바꿨다.

**규칙을 바꾼 사례.** `holdOnly [1000,2000]` → `long [2000,2160]`에서 A 1000–2041, B 2040–2160을 대조했다(Codex 리뷰). 이전 지침의 기준(`holdOnly` 끝 뒤 Easy Good 150ms 안에 up 개수 의존 판정을 두지 않음)을 지켜도, `holdOnly` 끝에서 Perfect 창 안으로 늦게 뗀 A up이 N2 끝의 Good 창(2040부터)에 들어 N2의 이른 release Good(−119)이 된다. Perfect 1·Good 1(PR #188 같음)이고, A를 끝까지 누르면 Perfect 2라 같은 연주의 결과가 갈린다. 간격을 Good 창 두 개로 늘리는 안([부록 A-10](#a-10-holdonly-끝-뒤-간격을-good-창-두-개로-늘리기))을 제시하자 사용자는 다음과 같이 답했다(2026-10-17).

> a up을 n1 릴리즈로 보고(grace라서 유지만해도되고 good안에만 떼면 퍼펙트) 그후에 유예기간동안 안누르면 유지 실패 여기서는 b가 있어서 유지, b가 n2 릴리즈

> holdonly가 릴리즈 수가 0 또는 1일수 있어서 up을 가져가긴 해야하는데 사용자가 릴리즈 0인 방법으로 처리했을때 불이익이 없도록 차트 제작자가 유의

위 입력은 Perfect 2다. 계속 누르는 연주(release 0)의 보호는 제작 지침 8항으로 둔다([§9-3](#9-3-제작-지침-48항)).

| 차트 | 입력 | 결과 |

- 정밀한 끝 판정이 의도가 아닐 때 뒤 바디 끝에 `holdOnly`를 적용하는 방법(제작 지침 6항)은 그대로 쓸 수 있다.
- `holdOnly` 끝에서 뗀 up도 그 끝이 쓰므로, 의도된 연주의 정의에서 `holdOnly` 끝의 up을 따로 예외로 둘 필요가 없다([§9-1](#9-1-의도된-연주의-정의)).

### 7-2. `holdOnly` 감소에서 키를 남기는 연주

`doubleLong holdOnly [1000,2000]` → `long [2000,3000]`에서 B를 2000에 떼고 A로 유지하는 연주와, A/B를 3000까지 함께 누르는 연주를 대조했다. 둘 다 `holdOnly` 2개와 N2 끝으로 Perfect 3이다(PR #188 같음). 계속 누르는 연주는 single 바디에 키가 둘 남는다. 떼는 연주만 의도된 연주로 보는 안을 추천하자 사용자는 이를 채택하면서 다음을 덧붙였다(2026-10-16).

> 그렇게 하는데, 만약에 =-=- 가 빠르게 반복되는 패턴이면 ab--- 로 누르는게 의도된 플레이가 될 수도 있음, 이 경우는 d-*-*- 랑 똑같은 패턴과 점수를 주지만 인식난을 원하면 패턴을 이렇게 짤수도 있음, 이 경우에는 의도되지 않은 여분 홀드가 오히려 도움이 되도록 차트를 일부러 짠거임

- **`holdOnly` 2→1에서 줄어드는 키를 경계에서 떼는 연주는 의도된 연주다.** 그 up은 `holdOnly` 끝이 가져간다([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다)).
- **기본적으로 `holdOnly` 감소에서 떼지 않아 키가 남는 연주는 의도된 연주가 아니다.** 막지 않으며, 남는 키의 up이 뒤 판정에 주는 영향은 플레이어 책임이다.
- **차트가 여분 홀드를 일부러 쓰게 짠 패턴은 예외다.** double과 single이 빠르게 번갈아 나오고 감소마다 `holdOnly`인 `=-=-` 반복에서는 A/B를 계속 누르는 `ab---`가 의도된 연주일 수 있다. 이 배치는 `d-*-*-`와 같은 패턴과 점수를 주면서 인식난을 더한다. 의도되지 않은 여분 홀드가 도움이 되도록 제작자가 일부러 짠 것이므로, 이런 패턴에서는 의도된 연주의 기본 정의([§9-1](#9-1-의도된-연주의-정의))보다 차트의 의도를 우선한다.
- 120 BPM 16분음표 간격의 `=-=-` 반복(감소마다 `holdOnly`, 마지막 single 끝은 마지막 `holdOnly` 끝보다 375ms 뒤)을 A/B로 계속 누르면 Perfect 5다(PR #188 같음). 미리 누른 키가 증가를 채우고([§2-1](#2-1-hold-수로-시작과-유지-판단), [§6-1](#6-1-12-증가)) `holdOnly`가 감소를 면제하므로 새 규칙에서도 같다.
- 이 결정 당시(2026-10-16) 이 패턴의 마지막 실제 release는 제작 지침 8항에 따라 마지막 `holdOnly` 끝과 Good 창보다 넓게(Easy 기준 150ms 초과) 떨어뜨린다고 적었다. 8항의 기준은 이후 바뀌었고, 새 8항은 감소하지 않는 `holdOnly` 끝에 적용한다([§9-3](#9-3-제작-지침-48항)).

## 8. head 없는 시작과 경계

### 8-1. 시작 직후의 재충전

**head 없는 시작에서는 시작의 Good 기한(S+Good)까지 다시 채울 기회를 준다.** 독립 바디의 시작과 1→2 증가로 늘어난 몫, head 없는 경계 뒤 바디의 모든 몫([§8-2](#8-2-head-없는-경계))에 적용하며, `holdOnly` 바디도 같다. S+Good 전에 hold가 모자라지면 실패 시각은 부족해진 시각에 유지 유예(임시 20ms)를 더한 시각과 S+Good 중 늦은 쪽이다. 그전에 회복하면 실패하지 않는다. S+Good 뒤에 생긴 부족에는 평소처럼 유지 유예만 적용한다.

- 처음부터 누르지 않고 S+Good 안에 누른 입력([§2-1](#2-1-hold-수로-시작과-유지-판단), [§6-1](#6-1-12-증가))보다 결과가 나빠지지 않게 하는 규칙이다.
- 다시 누른 down은 바디가 소비하지 않으므로([§2-1](#2-1-hold-수로-시작과-유지-판단)) Point 판정과 up의 release 배정은 바뀌지 않는다. 실패한 unit을 되살리지 않는다는 원칙도 그대로이며, 이 기회는 실패를 확정하기 전의 기한만 늦춘다.
- head가 있는 바디는 head를 처리한 down이 유지 판정의 시작을 정하므로([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)) 이 기회를 적용하지 않는다.

차트는 `head 1000`(Point) → head 없는 `long [1100,1500]`이고, Normal 기준 N2의 시작 기한 S+Good은 1220이다.

| 입력 | 기대 결과 | 재충전이 없을 때 | PR #188 |
|---|---|---|---|
| A 1000–1090, A 1140–1500 | 1100에 hold가 없어 N2는 아직 시작하지 않았고, A down 1140으로 시작한다. Perfect 2 | 같음 | Perfect 2 |
| A 1000–1105, A 1140–1500 | 1100에 눌린 A로 N2가 시작하고 A up 1105부터 부족하지만, 실패를 1220까지 미루므로 A down 1140으로 이어 간다. Perfect 2 | 1125에 유지 실패하고 A down 1140으로 되살리지 못한다. Perfect 1·Miss 1 | Perfect 2(head 없는 시작에 새 down을 요구) |

재충전이 없으면 N1을 친 A를 15ms 더(1090→1105, 곧 N2 시작보다 5ms 늦게까지) 누른 것만으로 처음부터 누르지 않은 입력보다 결과가 나빠진다. 시작의 Good 기한까지 다시 채울 기회를 줄지 묻자 사용자는 다음과 같이 물었다(2026-10-16).

> 그럼 good 이전까지는 유예가 없는거네? 기회를 줬을 때 부작용은 없나?

유예가 없어지는 것이 아니라 시작 직후에는 유예가 S+Good까지 늘어난다고 설명했다. 1105에 잃으면 1220, 기한 직전인 1210에 잃으면 1230에 실패한다. 부작용으로는 세 가지를 제시했다.

1. hold 없이 버틸 수 있는 시간은 시작 뒤 Good 창까지이며, 처음부터 늦게 누르는 입력으로 이미 얻을 수 있는 시간이다.
2. 다시 누르지 않으면 실패 확정이 늦어진다. 위 둘째 입력은 1125 대신 1220에 실패하며, 처음부터 누르지 않았을 때의 시작 실패 시각과 같다.
3. hold 수 모델은 키와 몫을 묶지 않으므로 1→2 증가에서는 원래 키의 끊김도 같은 기회를 받는다. `long [1000,2000]` → `doubleLong [2000,3000]`에서 A 1000–2010·2080–3000, B 1990–3000은 기회를 주면 Perfect 2, 주지 않으면 2030에 한 몫이 유지 실패해 Perfect 1·Miss 1이다(PR #188은 A up 2010에 즉시 실패해 Perfect 1·Miss 1). 경계에서 떨어진 바디 중간이라면 70ms 끊김은 언제나 유지 실패다.

다시 채울 기회는 시작 창 안의 실패 시각 하나만 바꾸므로 이를 추천하고, 부작용 3의 관대함을 받아들일지 묻자 사용자는 “ㅇㅋ”라고 답했다(2026-10-16). 1→2 증가에서 원래 키의 끊김까지 같은 기회를 받는 관대함은 증가 직후 Good 창 하나로 한정되므로 받아들인다. 사용자가 함께 제시한 head 없는 시작의 down 흡수는 채택하지 않았다([부록 A-8](#a-8-head-없는-시작의-down-흡수)). 이 기회를 head 없이 시작하는 `holdOnly` 바디에도 적용한다는 점은 2026-10-17의 도출 규칙 확인([§4-2](#4-2-경계-전에-뗀-연결-release))에서 다시 확인했다.

- [§1-4](#1-4-trade-off와-영향-범위)의 `holdOnly [1010,1500]` 예는 실패 기한이 1050에서 1130으로 늦춰져 B down 1060으로 바디를 이어 간다.
- 표의 두 입력과 부작용 3의 1→2 증가 입력은 엔진 이행 시 회귀 사례로 둔다. PR #188은 head 없는 시작에 새 down을 요구해 표의 둘째 입력이 Perfect 2지만, 1→2 증가 입력은 유예 없이 실패한다.

### 8-2. head 없는 경계

**head 없는 경계에서도 앞 바디는 끝의 Good 창 안에서 뗀 up으로 끝낼 수 있다.** unit 수가 바뀌는 경계도 같으며, 2→1에서는 지금처럼 첫 up이 감소 release다([§6-2](#6-2-head-없는-21)). **뒤 바디의 모든 몫은 head 없는 시작처럼 S+Good까지 채우면 된다.** 이어지는 몫과 새로 시작하는 몫을 가리지 않으며, 시작 직후 끊겨도 그 기한까지 다시 채울 수 있다([§8-1](#8-1-시작-직후의-재충전)).

- 경계에서 떨어진 바디 중간의 끊김에는 지금처럼 유지 유예만 적용한다.
- head가 있는 경계는 지금처럼 head를 처리한 down부터 뒤 바디를 판단한다([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)). head 기한까지 끊겨도 된다는 점에서 같은 성격이다.
- 이 결정은 [§8-1](#8-1-시작-직후의-재충전)을 처음 정할 때 둔 “1→2 증가에서 증가 전부터 요구하던 수보다 적어지는 부족에는 평소처럼 유지 유예만 적용” 단서를 대체한다.

`holdOnly [1000,2000]` → `long [2000,3000]`(head 없음)에서 A 1000–1990, B 2030–3000을 대조했다. 이어진 한 바디로 보면 N2가 2020에 유지 실패해 Perfect 1·Miss 1이고, A up이 N1을 끝내고 N2는 head 없는 시작처럼 S+Good까지 채우면 된다고 보면 Perfect 2(PR #188 Perfect 2)다. 제작 지침 6항이 교대할 끝에 `holdOnly`를 권하므로 후자를 추천하자 사용자는 “2”라고 답했다(2026-10-17).

이어서 1→2 증가 `long [1000,2000]` → `doubleLong [2000,3000]`에서 A 1000–2010, B 2040–3000, A 2060–3000을 대조했다. 새로 시작하는 몫에만 재충전 기회를 주면 이어지는 몫이 2030에 유지 실패해 Perfect 1·Miss 1(PR #188 같음)이다. 이를 설명하자 사용자는 다음과 같이 답했고, 위 정리에 “ㅇㅇ”라고 확인했다(2026-10-17).

> 경계 근처에서만 Good 창만큼 끊겨도 괜찮다 맞지 않음? 롱노트가 실제로는 나뉘어 있잖아

위 1→2 입력은 Perfect 2다.

이해 확인 중 사용자는 head 없는 경계도 release 개수가 연주에 따라 달라진다고 정리했다(2026-10-17).

> a--- + ..b- 또는 a-bc- 둘다 정당한 입력이기 때문에, 두번째 방법에 a가 n1를 종료하고 bc가 n2를 시작함 노트가 시작되고 끝날때는 굳 윈도우 안에서 하면되고 유예 기간은 하나의 바디 시작 끝지점 제외한 구간에서만 동작함, 이 패턴도 발생하는 릴리즈 개수가 달라 차트 작성시 유의

그래서 head 없는 경계에도 제작 지침 8항을 적용한다([§9-3](#9-3-제작-지침-48항)). 계속 누르는 연주와 떼고 다시 누르는 연주의 경계 근처 up 개수가 0 또는 1로 달라지므로, 경계 바로 뒤에 그 up에 따라 결과가 달라지는 판정을 두지 않는다.

## 9. 의도된 연주와 제작 지침

### 9-1. 의도된 연주의 정의

**의도된 연주는 차트의 박자에 맞춰 행동하는 연주 중, 각 경계를 지난 뒤 그 바디가 요구하는 hold 수만큼만 키가 남고, 판정 창 안에서 생긴 모든 up이 감소 release·연결 release·끝 release(`holdOnly` 끝 포함) 중 하나에 쓰이며, 각 입력을 그 판정의 Perfect 창 안 어디에서 쳐도 점수 손해가 없는 연주다.** 어떤 판정 창에도 들지 않는 up은 중립이다([§2-5](#2-5-바디-중간-교대와-끝-창-안의-교대)). 같은 키를 연결 경계 앞에서 떼고 뒤에서 다시 눌러 head를 치는 연주는 허용 입력(탈출구)이다([§9-2](#9-2-허용-입력탈출구)). 마지막 끝도 경계로 보아 끝 뒤에 남는 키는 여분 키다. 차트가 여분 홀드를 일부러 쓰게 짠 패턴에서는 이 기본 정의보다 차트의 의도를 우선한다([§7-2](#7-2-holdonly-감소에서-키를-남기는-연주)).

- 판정 모델은 의도된 연주를 점수 손해 없이 처리해야 한다([§1-2](#1-2-패턴을-먼저-정하고-교대-자체의-점수-손해를-금지)). 패턴별로 확인한 의도된 연주는 구현 시 회귀 사례로 둔다.
- 의도된 연주가 아닌 입력도 막지 않고 같은 규칙으로 판정한다. 남는 up이 뒤 판정에 주는 영향은 보장하지 않으며 플레이어 책임으로 둔다([§2-3](#2-3-release-등급과-자격-판정-창-기준)).
- 이 정의는 판정 규칙이 아니라 패턴 검토와 제작 지침의 기준이다. 판정 규칙은 경계 전 연결 release([§4-2](#4-2-경계-전에-뗀-연결-release)) 등 각 항목에 둔다. 용어의 권위 정의는 [glossary](../context/glossary.md#의도된-연주)에 둔다.

**기본 정의(2026-10-16).** head가 있는 2→1의 연주([§6-3](#6-3-head가-있는-21과-감소-release))를 대조하며 의도된 연주로 인정한 입력과 그렇지 않은 입력의 차이를 다음과 같이 정리해 제시했다.

| 연주 | 감소 release | 연결 release | 끝 release | 남는 up |
|---|---|---|---|---|
| A·B를 떼고 C로 head를 친 뒤 유지 | A up | B up | C up | 없음 |
| A 유지, B를 떼고 C로 head를 쳐서 바로 뗌 | B up | C up | A up | 없음 |
| A 유지, B만 C로 옮겨 C 유지 | B up | 없음 | A·C 중 하나 | 하나 |
| A/B 유지 중 C로 head 탭 | C up | 없음 | A·B 중 하나 | 하나 |

경계 뒤에 바디가 요구하는 수만큼만 키가 남아 모든 up이 감소 release·연결 release·끝 release 중 하나에 쓰이는 연주를 의도된 연주의 일반 정의로 기록할지 묻자 사용자가 동의했다(2026-10-16, “ㅇㅋ”).

**보완(2026-10-16).** PR #284 리뷰에서 기본 정의가 다른 결정과 세 군데에서 어긋난다는 지적이 있었다. 단독 바디 중간 교대의 up은 어느 판정에도 쓰이지 않아 글자대로는 의도된 연주가 아니지만 보호하려던 입력이다([§1-1](#1-1-기존-결정과-문제), [§1-2](#1-2-패턴을-먼저-정하고-교대-자체의-점수-손해를-금지)). NJ-R13 입력은 글자대로는 정의에 맞지만 의도된 두 연주([§4-4](#4-4-single-head가-있는-double-연결의-연주))가 아니다. `ab-ab-`는 정의에 맞는다고 적었지만 의도된 연주와 구분해 허용으로 기록했다([§4-5](#4-5-double-head가-있는-double-연결)). 세 항목을 차례로 확인했다. 첫째는 판정 창 밖의 up을 중립으로 보는 것([§2-5](#2-5-바디-중간-교대와-끝-창-안의-교대)), 셋째는 같은 키 재타격을 허용 입력으로 두는 것([§9-2](#9-2-허용-입력탈출구))이다. 둘째는 다음과 같다.

“정확한 타이밍으로 치면 점수 손해가 없을 것”을 조건으로 제안하자 사용자는 다음과 같이 답했다(2026-10-16).

> 정확한 타이밍이라고 해도 사람이 입력하니 그 타이밍은 특정 시점이 아니라 오차범위가 있는 구간이어야 함

이에 따라 조건을 **각 입력을 그 판정의 Perfect 창(Normal ±41ms, Easy ±50ms) 안 어디에서 쳐도 점수 손해가 없을 것**으로 고쳤고, 사용자는 “ㅇㅇ”라고 확인했다(2026-10-16).

- **NJ-R13 입력은 빠진다.** A를 경계에서 떼고 B로 head를 다시 치므로 double인 N3 위에는 B 하나만 남고, B는 head 전에 N3 끝 하나를 일찍 떼야 한다. B up은 N2의 Perfect 창 끝(2041)보다 일러야 하는데 N3 끝의 Perfect 창은 2059부터이므로, 어느 시점에 쳐도 N3 끝 하나는 Perfect가 될 수 없다.
- [§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)의 늦은 head 입력은 [§4-4](#4-4-single-head가-있는-double-연결의-연주)의 `a-b- + c---`를 늦게 친 것이므로 방법은 의도된 연주이며, Great는 타이밍 오차다.
- [§4-4](#4-4-single-head가-있는-double-연결의-연주)의 두 연주와 [§6-3](#6-3-head가-있는-21과-감소-release)의 두 연주는 각 입력이 Perfect 창 안 어디에 있어도 모두 Perfect다. A·B를 함께 떼는 [§6-3](#6-3-head가-있는-21과-감소-release)의 연주는 어느 up이 먼저 오든 감소 release와 나머지 하나가 나눠 가진다. head가 있는 2→1의 뒤 바디 유지를 head down부터 판단하는 결정([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지))이 이 판단의 전제다.
- 리뷰가 제안한 “hold 수가 유예를 넘겨 모자라지 않을 것”은 이 조건에 포함된다. 정확한 오차 범위 안에서 hold가 모자라면 유지 실패로 손해가 나기 때문이다. 그 조건을 차트상 요구 hold 수에 그대로 대면 타이밍만 어긋난 [§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)의 늦은 head까지 빠진다.
- 차트 시각이 없는 up(연결 release, 바디 중간 교대)에는 등급을 매기는 창이 없다. 연결 release의 자격은 head의 Good 창으로 정하고, 바디 중간 교대는 hold를 유예 넘게 끊지 않으면 된다.

**정리.** 연결 경계 전에 앞 바디를 끝낸 up([§4-2](#4-2-경계-전에-뗀-연결-release))도 쓰인 up에 포함한다(2026-10-16). `holdOnly` 끝에서 뗀 up은 그 끝이 가져가므로([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다)) 별도 예외가 필요 없다(2026-10-17). 마지막 끝 뒤에 남는 키는 여분 키이므로(2026-10-17), 유지 키를 계속 누르고 다른 키로 끝만 치는 [§3-2](#3-2-유지-키와-다른-키의-up)의 연주는 그대로 의도된 연주가 아니다.

**확인한 의도된 연주:** 바디 중간 교대([§2-5](#2-5-바디-중간-교대와-끝-창-안의-교대)), 같은 unit 수 연결의 교대와 유지 중 탭([§4-1](#4-1-연결-release)), single head가 있는 double 연결의 두 연주([§4-4](#4-4-single-head가-있는-double-연결의-연주)), double head 연결의 두 연주([§4-5](#4-5-double-head가-있는-double-연결)), head가 있는 2→1의 두 연주([§6-3](#6-3-head가-있는-21과-감소-release)), `holdOnly` 감소에서 떼는 연주([§7-2](#7-2-holdonly-감소에서-키를-남기는-연주)). **의도된 연주가 아닌 입력:** 끝만 치기([§3-2](#3-2-유지-키와-다른-키의-up)), NJ-R13 입력([§3-3](#3-3-노트를-처리한-같은-키의-재누름)), 경계 뒤에 바디가 요구하는 수보다 키를 더 남기는 2→1 입력([§6-3](#6-3-head가-있는-21과-감소-release), [§6-4](#6-4-감소-지점-앞뒤의-head)), `holdOnly` 감소에서 키를 남기는 연주(차트 의도 예외 제외, [§7-2](#7-2-holdonly-감소에서-키를-남기는-연주)). 같은 키 재타격은 허용 입력(탈출구)이다([§9-2](#9-2-허용-입력탈출구)).

### 9-2. 허용 입력(탈출구)

**같은 키를 연결 경계 앞에서 떼고 뒤에서 다시 눌러 head를 치는 연주는 의도된 연주가 아니라 허용 입력(탈출구)이다.** double head 연결의 `ab-ab-`([§4-5](#4-5-double-head가-있는-double-연결))와 single 연결의 `a-a-`가 여기에 해당한다. 정박보다 일찍 떼고 늦게 누를수록 유리하므로 차트의 박자에 맞춰 행동하는 연주가 아니지만, 인지 부하가 가장 적어 처음 접하는 플레이어가 칠 가능성이 높으므로 판정은 손해 없이 처리한다.

`ab-ab-`는 같은 키를 뗐다가 다시 누르므로 Perfect 창 끝에서 늦게 치면 공백이 유예를 넘는다고 설명하자, 사용자는 다음과 같이 답했다(2026-10-16).

> 그 패턴은 ab- + ab- 로 볼수 있음 경계에서 -perfect 안에 떼고 +perfect 안에 누르면 되니까 유예기간이랑은 상관없지

이어서 이 연주를 의도된 연주로 다시 분류할지 묻자 다음과 같이 답했다(2026-10-16).

> 판정 모델로써는 그게 결함없는 플레이는 맞는데 실제 박자는 2000이고 이 박자를 기준으로 행동하는게 아니라 더 빠르고 더 느리게 행동하는게 유리한데 이런 관점에서 좋지는 않지 다만 가장 인지 부하가 적은 플레이는 맞아서 이 패턴을 처음 접하는 플레이어는 이렇게 칠 가능성이 높지 따라서 허용해놓은 탈출구에 가깝지

- 먼저 뗀 up이 앞 바디를 끝내고([§4-2](#4-2-경계-전에-뗀-연결-release)), 다시 누른 down이 head를 치며 뒤 바디의 몫을 시작한다([§4-3](#4-3-head를-처리한-down부터-뒤-바디-유지)). 경계보다 40ms 일찍 떼고 40ms 늦게 다시 누르는 `a-a-`는 Perfect 2, `ab-ab-`는 Perfect 4이며 PR #188도 같다.
- 사용자의 `ab- + ab-` 해석은 double head 연결에서 head마다 그 몫을 판단하는 잠정 규칙([§4-5](#4-5-double-head가-있는-double-연결))의 근거다.
- single 연결의 의도된 연주는 [§4-1](#4-1-연결-release)의 `a-b-`와 `a--- + ..b.`, double head 연결의 의도된 연주는 [§4-5](#4-5-double-head가-있는-double-연결)의 `ab-cd-`와 `ab--- + ..cd.`로 그대로 둔다.
- single 연결의 `a-a-`도 `ab-ab-`와 같은 이유로 허용 입력(탈출구)이라는 점은 2026-10-17의 도출 규칙 확인([§4-2](#4-2-경계-전에-뗀-연결-release))에서 사용자가 “ㅇㅇ”라고 확인했다.

### 9-3. 제작 지침 4~8항

제작자가 계속 참고할 본문과 재현 가능한 사례는 [차트 디자인의 주의사항](../context/chart-design.md#차트-설계-시-주의사항)에 둔다. 아래는 각 항의 결정 근거다. 모두 제작·플레이테스트 지침이며 `validateChart`의 새 거부 조건이 아니다. 적절한 손 선택의 사전 유도와 타이밍 면제를 쓰는 대신, 제작자가 요구하는 손 이동과 정밀 입력을 구별한다. 제작 지침으로 #205·#281 등 기존 엔진 결함을 정당화하거나 제작자 책임으로 돌리지 않는다.

사용자는 판정 모델만으로 모든 배치의 불합리함을 해결하려 하지 말고 제작자가 지양할 규칙을 만들라고 요청했다. `long [1000,1500]` → `head 1500` + `long [1500,1560]`에서 A를 끝까지 유지하고 B로 head만 눌렀다 떼어도(A 1000–1560, B 1500–1510) 이른 release가 생긴다는 사례([부록 A-2](#a-2-시작-여부-검사로-연결-release를-대체))를 바람직하지 않다고 평가하며 사용자는 “판정 모델의 결함이라기 보다는 틀릴수밖에 없는 패턴일수도 있음”이라고 설명했다(2026-10-15). 처음 제시한 L2·L3 롱노트와 L1·L2 Point의 조합에는 “그전에 다른손을 사용하게 만들어서 어느쪽으로 연주해야하는지 확실히 암시”하도록 했고, 이어 “교대할수있는 부분에서 그레이스 걸어주는것도 적어줘”라고 요청했다(2026-10-15). release 계약을 정할 때도 에이전트가 지적한 제작 시 유의사항을 반영하라고 요청했다([§2-3](#2-3-release-등급과-자격-판정-창-기준)).

- **4항 손 선택을 미리 암시한다.** 특정 손으로 롱노트를 잡아야 뒤 배치를 자연스럽게 처리할 수 있다면, 그 손을 선택하기 전에 반대 손이 다른 입력을 담당하는 흐름으로 의도를 충분히 암시한다. L2·L3을 오른손으로 잡게 하려면 앞선 배치에서 왼손을 사용하게 유도하고 오른손이 L2·L3으로 갈 여유를 준다. 뒤늦게 L1·L2 Point를 보여 갑작스러운 손 교대를 요구하는 배치는 지양한다.
- **5항 자연스러운 탭·교대의 up과 가까운 release가 충돌하는 배치를 지양한다.** 제작자가 의도한 down뿐 아니라 자연스러운 탭·교대의 up도 실제 release 창과 대조하고, 배치 간격이나 끝점 요구를 조정한다. 20ms 유지 유예가 이른 release를 막아 줄 것으로 가정하지 않는다. 위의 A 유지·B로 Point 탭 사례는 연결 release([§4-1](#4-1-연결-release))에 따라 Perfect 2가 기대 결과다.
- **6항 교대할 부분에 Grace를 배치한다.** 교대 위치의 Point는 `grace`로 누르는 타이밍 부담을 줄이고, 교대 up의 정밀한 release를 요구하지 않을 롱노트 끝은 `holdOnly`로 떼는 판정을 면제한다. Point의 `grace`와 롱노트 끝의 `holdOnly`를 구별하며, 두 속성의 기존 의미와 배치 제약을 유지한다. Grace를 붙여도 유지 조건은 남고 모든 교대 up을 무시하지 않는다. `holdOnly`는 주변의 다른 실제 release가 up을 받는 것을 막지 않으므로 앞뒤의 가장 이른 적격 끝도 확인한다.
- **7항(폐지) 연결 head 뒤 짧은 바디와 감소 직전 head.** 아래에 적는다.
- **8항 `holdOnly` 끝에서 계속 누르는 연주도 불이익이 없게 배치한다.** 아래에 적는다.

**7항의 추가와 폐지.** 연결 head 뒤 바디의 끝을 그 head의 Good 창 안에 두는 배치는 연결 release의 보류를 기각하면서 제작 지침으로 지양하기로 했다(2026-10-16, [부록 A-6](#a-6-연결-release의-보류), [§6-3](#6-3-head가-있는-21과-감소-release)의 결정과 함께 “응”으로 확인). head 없는 2→1 감소 지점 바로 앞(그 head의 Good 창 안)에 head를 두는 배치도, 감소 release를 언제나 먼저 채우는 안과 비교하자([부록 A-7](#a-7-감소-release를-언제나-연결-release보다-먼저-채우기)) 사용자가 다음과 같이 답해 같은 지침에 넣었다(2026-10-16).

> 21도 지침으로 막아야겠다

이후 PR #284 리뷰에서 두 배치의 근거 입력이 의도된 연주가 아니라는 지적이 있었다. 두 배치의 Miss는 모두 경계 뒤에 바디가 요구하는 수보다 키를 더 남긴 입력에서만 나고, 의도된 연주는 Miss가 나지 않는다([§6-3](#6-3-head가-있는-21과-감소-release), [§6-4](#6-4-감소-지점-앞뒤의-head)). 또 7항의 기준(뒤 바디가 Easy Good 150ms보다 김)은 끝 시각에 정확히 뗀 up만 head 창 밖으로 보낸다. 끝을 Good 범위로 일찍 떼면 기준을 지켜도 같은 Miss가 나며([§6-3](#6-3-head가-있는-21과-감소-release) 짧은 뒤 바디 표의 마지막 행), 끝의 release 창 전체를 head 창 밖으로 보내려면 head와 끝의 간격이 Good 창 두 개(Easy 300ms)보다 커야 한다. 7항을 폐지하는 안에 대해 사용자는 다음과 같이 답했다(2026-10-16).

> 이 모호함을 사용자가 감당한다는 의미인거 같음 이 패턴에 대해 의도한 입력이 무엇인지 전달할 수 있는 장치가 필요 (우리가 봤을때 잘못된 입력이 사용자는 잘못됬다고 인지하지 못하면 판정 모델의 결함이라고 인식할 수 있음)

이어 7항이 가리키는 범위를 150ms와 300ms 중 어느 쪽으로 할지 묻자, 사용자는 “7항 폐지 하기로 한거 아니었음?”이라고 확인했다.

- **제작 지침 7항을 폐지한다.** 배정 순서와 판정 규칙은 바꾸지 않는다. 연결 head 뒤 짧은 바디와 감소 직전 head를 판정 규칙으로 막지 않고, 배치를 피하라는 제작 지침도 두지 않는다. 다만 낮은 레벨에는 쓰지 않는다([§9-4](#9-4-여분-키-구분의-튜토리얼-전달)).
- 경계 뒤에 키를 더 남긴 입력의 Miss는 의도된 연주가 아니므로 판정으로 보호하지 않는다([§9-1](#9-1-의도된-연주의-정의)). 그 구분은 튜토리얼로 전달한다([§9-4](#9-4-여분-키-구분의-튜토리얼-전달)).
- 7항의 기준에 걸리던 배치(100 BPM 이상에서 16분음표 한 칸짜리 연결 head 뒤 바디, 감소 지점 바로 앞의 head)를 다시 쓸 수 있다. 정밀한 끝 판정이 의도가 아닐 때 뒤 바디 끝에 `holdOnly`를 적용하는 방법([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다))은 그대로 쓸 수 있다.
- [제작 지침의 7항](../context/chart-design.md#7-폐지-연결-head-뒤-짧은-바디와-감소-직전-head) 자리는 8항의 번호와 기존 링크를 유지하려고 폐지 표시로 남긴다.

**8항.** `holdOnly` 끝에서 떼는 연주(release 1)와 계속 누르는 연주(release 0)는 모두 정당하다([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다)). 떼는 연주는 `holdOnly` 끝이 up을 가져가므로 판정이 보호하고, 계속 누르는 연주는 제작자가 확인한다. **8항은 떼지 않고 계속 누르는 연주(release 0)도 불이익이 없도록 확인하는 지침이다.** 계속 누른 키의 나중 up이 가까운 뒤 끝의 이른 release가 되거나 뒤 판정에서 여분 키가 되지 않는지 본다. 이 지침을 감소하지 않는 `holdOnly` 끝에만 적용하자는 제안에 사용자는 “ㅇㅇ”라고 답했다(2026-10-17). 같은 이유로 head 없는 경계(같은 unit 수, 1→2 증가)에도 적용한다([§8-2](#8-2-head-없는-경계), 2026-10-17). `holdOnly` 감소에서 계속 누르는 연주는 [§7-2](#7-2-holdonly-감소에서-키를-남기는-연주)의 결정(기본적으로 의도된 연주가 아니고, 여분 홀드를 일부러 쓰게 짠 패턴은 예외)을 따른다. 처음 8항(2026-10-16)은 `holdOnly` 끝 바로 뒤에 up 개수에 따라 결과가 달라지는 판정을 두지 않는 지침(Easy Good 150ms)이었으나, 끝에 정확히 뗀 up만 보호해 지금의 기준으로 바꿨다([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다)의 사례). 본문은 [제작 지침의 8항](../context/chart-design.md#8-holdonly-끝에서-계속-누르는-연주도-불이익이-없게-배치한다)에 있다.

### 9-4. 여분 키 구분의 튜토리얼 전달

경계 뒤에 남긴 여분 키를 떼야 한다는 구분을 플레이어가 잘못된 입력으로 인지하지 못하면 판정 결함으로 받아들일 수 있다([§9-3](#9-3-제작-지침-48항)의 7항 폐지 인용). 전달 장치 후보로 여분 키 실시간 표시, Miss 이유 표시, 튜토리얼을 제시했다. 사용자는 튜토리얼을 택하고 실습을 제안했다(2026-10-16).

> 튜토리얼에 추가하고, 지금 튜토리얼은 그냥 보기만 하는건데 실습도 가능하게 하면 어떨까 그리고 이 모호한 구분을 플레이어가 해야만 하는 패턴은 패터너가 충분히 인지하고 넣어야 함 (밀도가 낮아도 낮은 난이도에서 사용하면 안됨)

이 배치를 기존 난이도명별 패턴 제한(HARD 전용)에 넣는 안을 제시하자 사용자는 다음과 같이 답했다(2026-10-16).

> 지금 차트 제작 경험이 너무 적어서 어느 파츠를 몇레벨에 써야할지 정할수가 없어 그리고 이지 노말 하드는 이제 안써 이런 부분은 나중에 구체화 차트 경험이 쌓이고 나서 튜토리얼은 오토 시연을 보여주고 실습 버튼을 누르면 그 화면에서 바로 따라서 쳐보고 통과하면 기록하게 할수 있음 나중에 레벨별로 튜토리얼을 선행해야 선택할수 있게 하는거 고려

- **여분 키를 경계에서 떼야 한다는 구분을 튜토리얼로 전달한다.** Advanced 시연에 의도된 연주와 여분 키를 남긴 연주를 나란히 넣고([#286](https://github.com/nanana3679/not4k/issues/286)), 오토 시연 뒤 실습 버튼으로 같은 화면에서 따라 치고 통과하면 기록하는 실습을 추가한다([#285](https://github.com/nanana3679/not4k/issues/285)). 레벨별로 튜토리얼 통과를 곡 선택의 선행 조건으로 두는 방안은 이후에 검토한다.
- **이 구분을 요구하는 배치는 패터너가 알고 넣으며, 밀도가 낮아도 낮은 레벨에는 쓰지 않는다.** 어느 레벨부터 쓸지는 차트 제작 경험이 쌓인 뒤 정한다([PRD의 미정 사항](../prd.md#12-미정-사항)). 기존 EASY·NORMAL·HARD 기준의 패턴 제한에는 넣지 않는다.
- 튜토리얼은 아직 변경하지 않았다.

## 부록 A. 검토한 대안

검토했으나 채택하지 않은 안이다. 각 안의 현재 처리는 본문 항목을 따른다.

### A-1. 등록 키만 인정하거나 나중에 누른 키만 교대에 인정

- **등록된 유지 키만 인정:** 현행 규칙을 보존하지만, 바디 중간의 손 이동을 막는다.
- **시작 후 누른 여분 키만 교대에 인정:** 먼저 누르고 있던 키와 나중에 누른 키를 구분해야 한다. 사용자는 같은 hold 수인데 한쪽만 인정하는 차이를 원하지 않았다.
- 채택한 방향은 같은 레인의 실제 hold 수로 시작·유지를 판단하는 것이다([§1-3](#1-3-바디와-point의-역할), [§2-1](#2-1-hold-수로-시작과-유지-판단)).

### A-2. 시작 여부 검사로 연결 release를 대체

사용자는 시작하지 않은 롱노트가 release를 받지 않고 같은 레인의 바디가 겹치지 않으므로, `o-o-`의 교대 up이 뒤 롱노트의 release로 넘어가지 않을 것이라는 가설을 제시하고 Claude와의 검토를 요청했다(2026-10-15). 코드·기존 결정·제한 실행을 대조한 결과는 다음과 같다.

- **이미 시작한 짧은 뒤 바디에는 부족하다.** `long [1000,1500]` → `head 1500` + `long [1500,1560]`, A 1000–1510, B 1500–1560에서 A up 1510 직전의 N3는 `active=true`, `startedAt=1500`이며 A up은 N3의 release 창 [1440,1680] 안이다. 바디끼리 겹치지 않아도 경계 뒤 up 시점에는 N3가 진행 중이므로 시작 여부만으로 A up을 제외할 수 없다. 원본은 연결 교대 보정으로 A up을 제외해 N2 head Perfect, N3 release Perfect이고, 보정과 여분 up 보류를 모두 생략한 제한 실험에서는 N3가 Great(-50)였다.
- **시작 시각의 의미를 새로 정해야 한다.** 조기 head는 S 전에 바디를 활성화할 수 있고, 보류 up은 나중 정산 경로에서 다시 후보를 찾으며, PR #188의 짧은 뒤 바디는 S 전 up을 뒤 release로 쓰는 규칙도 있다. 같은 timestamp의 경계·up·down 처리도 입력 수집 순서와 프레임 위치에 의존하지 않게 정해야 했다.
- **release 제외와 유지 실패 보류는 별도 효과다.** [RFD 0020 §2.6](0020-note-judgment-units-and-inheritance.md#26-교대-keyup과-뒤-release-창이-겹치는-경우--후속-채택)의 연결 교대 up을 release에서 제외하는 기능과 [§2.12](0020-note-judgment-units-and-inheritance.md#212-경계-뒤-교대-up--후속-채택)의 head 기한까지 유지 실패를 보류하는 기능은 다르다. release 제외만 남긴다고 20ms를 넘는 연결 공백까지 허용되지 않는다.
- **교대 없이 Point만 탭해도 이른 release가 생긴다.** 사용자는 같은 배치에서 A를 계속 유지하고 B로 Point만 눌렀다 떼어도(A 1000–1560, B 1500–1510) 이른 release가 발생한다고 지적했다. 여분 up을 허용하면 연결 release 유지 여부와 관계없이 B up 1510이 N3 release Great(-50)를 처리했다. 반면 A를 1510에 떼고 B로 끝까지 유지하는 교대는 연결 release만 남기면 Perfect였다. A와 B를 모두 1560까지 유지하는 대조는 원본과 세 제한 변형 모두 Perfect 2였으므로 이 배치가 어떤 입력으로도 성공할 수 없다고 단정하지 않았다. 원본 엔진의 Point 탭 입력은 N2 Perfect / N3 release Miss였으며, 기존 명세가 허용하는 A 유지+B 탭 방식의 release 배정 문제로 별도 이슈에 기록했다([#281](https://github.com/nanana3679/not4k/issues/281)). 이 사례는 제작 지침 5항의 계기가 되었다([§9-3](#9-3-제작-지침-48항)).
- **검증 범위:** 독립 미시작 바디, 경계 전·정박·뒤 up, 조기 head, 긴 뒤 바디, 동일 키 재타격, double 교대의 8사례에서 main 5aa6006과 PR #188 c847d89 원본의 판정 이벤트와 등급 개수가 같음을 확인하고, PR #188 원본과 두 제한 변형(즉시 up 경로의 연결 release 호출만 생략, 여분 up 보류까지 생략)으로 24회 실행했다. 교대·Point 탭·두 키 끝까지 유지의 세 입력은 원본과 세 제한 변형에서 12회 실행했다. 제한 변형은 Vite의 메모리 변환으로만 적용했고 저장소의 엔진 파일은 수정하지 않았으며, 차트 검증 오류·엔진 예외·미정산 점수 항목은 없었다. 이 실험은 새 hold 수·20ms 모델의 구현이 아니며, 조기 head 뒤 기존 키를 떼는 원본 사례의 Miss 2는 #205와 같은 결함 범주라 새 모델의 정당화 근거로 쓰지 않는다.
- **결과:** 검토 당시(2026-10-15)에는 채택한 안이 없었다. 이후 연결 head에서는 up 하나를 연결 release에 배정하고([§4-1](#4-1-연결-release)), release 자격은 시작 여부가 아니라 판정 창으로 정한다([§2-3](#2-3-release-등급과-자격-판정-창-기준)). Point 탭 사례는 연결 release로 Perfect 2가 기대 결과다.

### A-3. 1→0에서만 release 후보를 만들고 회복으로 취소

사용자는 연결 교대 up의 흡수 여부를 비교한 뒤 “1->0 시점으로 판단하는게 나을까”라고 제안했다. 즉시 release를 확정하면 먼저 떼는 교대가 이른 등급을 받는다고 설명하자, 사용자는 “교대 유예기간 있잖아”라고 정정하고 “홀드 수로 판단해서 릴리즈를 판단하고 유예 기간까지 있는 모델을 클로드랑 검토해줘”라고 요청했다(2026-10-15).

검토한 안은 single의 2→1은 release 후보를 만들지 않고, 1→0에서 후보를 만든 뒤 20ms 기다려 그 안에 같은 유지 요구가 회복되면 교대로 보아 미확정 후보를 취소하고, 회복하지 않으면 원래 up 시각으로 등급을 정해 유예 이후 확정하는 것이다. 채택하지 않은 이유는 다음과 같다.

- **독립 롱노트의 실제 release를 취소한다.** `long [1000,2000]` | `long [2010,3000]`, A 1000–1950, B 1960–3000에서 B down 1960의 회복이 A up의 후보를 취소하면, 2120까지 다른 up이 없어 N1이 release Miss가 된다. 사용자는 독립 롱노트 사이의 실제 release를 흡수하지 않기로 결정했다([§2-6](#2-6-짧게-떨어진-독립-롱노트와-분리-표시)). 취소 범위를 “E 전 회복만 교대로 본다”로 좁혀도 이 사례가 남고, “연결된 후속 바디가 있을 때만 취소한다”로 좁히면 연결이 없는 긴 바디의 끝 창 안 교대도 빠진다.
- **겹쳐 누르면 후보가 생기지 않는다.** 사용자는 “hold개수로 릴리즈 판단하기로 했는데 겹쳐서 떼면 오히려 1-2-1이 되는데?”라고 지적했다(2026-10-15). 다음 키를 먼저 누르고 앞 키를 떼면 single의 hold 수가 1→2→1이므로 1→0 전용 후보로는 앞 롱노트의 실제 release 후보가 생기지 않는다. 이는 유지 유예의 길이와 무관하며, 앞의 실제 release를 보존한다는 결정과 함께 만족시킬 수 없다.
- **`holdOnly`의 면제 몫을 반영하지 못한다.** N1=`double holdOnly [1000,1500]` → N2=`long [1500,2000]`, A 1000–2000, B 1000–2500에서 A up은 2→1이라 single의 후보가 없고, 1→0은 release 창 밖의 2500에만 발생한다. 이 사례에서 사용자는 모든 감소를 release로 볼지 다시 물었다([§2-3](#2-3-release-등급과-자격-판정-창-기준)).
- **회복 취소 범위의 선택지가 모두 대가를 가졌다.** 적격 회복을 모두 취소하면 다음 바디를 미리 누르거나 Point를 탭한 hold도 앞 release 후보를 취소한다. Point를 처리한 down 등 다른 입력 목적을 보호하려면 바디가 down을 소비하지 않는 모델에서 B down이 앞 바디 교대용인지 뒤 바디 준비용인지 입력 자체로 구분되지 않아 추가 예외가 필요하다. 취소한 후보를 마지막 정산용으로 보관하면 취소 이력과 up 재사용 여부를 더 오래 보관해야 하고, 다시 잡은 뒤 끝을 놓쳐도 이전 등급을 받는 관대함이 생긴다. 후보 뒤에 오는 down만 보고 20ms 안에 취소하면 같은 timestamp의 up-first와 down-first의 결과가 갈린다는 점도 임시 reference로 확인했다.
- **분리 경계에만 적용하는 안.** 사용자는 “그럼 지금 만든 노트가 있는 위치의 릴리즈만 이렇게 판정하면어떰”이라고 분리 표시가 있는 경계의 release에만 2→1을 포함한 개별 감소를 받는 방향을 제시했다(2026-10-15). 일반 끝과 분리 경계의 release 자격을 달리해야 하고 위 `holdOnly` 사례를 보존하지 못해, 모든 감소를 후보로 받는 일반 규칙으로 대체했다.

결과는 [§2-3](#2-3-release-등급과-자격-판정-창-기준)의 release 계약(모든 유효 up 후보, 유지에만 유예, 회복에 따른 취소 없음)이다. 구현 요구로 남는 점은 count와 타이머만으로는 이미 끝난 몫에 기준이 반복해서 내려갈 수 있으므로, 점수 항목과 남은 정상 몫을 함께 관리해 “한 up당 release 하나·항목 재사용 금지·실패 부활 금지”를 지키는 것이다. 검토 중 `pnpm case:image`로 재현한 PR #188 원본 결과와, count 감소와 20ms 타이머만 계산한 작은 reference는 새 모델의 실행 검증이 아니다.

### A-4. 이른 up 보관과 등급 개선, 이진 release, `holdOnly` 기본화

교대 자체의 점수 손해를 금지하는 기준([§1-2](#1-2-패턴을-먼저-정하고-교대-자체의-점수-손해를-금지))을 정하며 다음을 비교했다(2026-10-16).

- **이른 up을 보관했다가 더 정확한 up으로 등급을 개선:** 사용자는 의도보다 많은 입력이 허용될 수 있다는 점과 즉시 확정되지 않는 사용감을 우려했다.
- **일반 롱노트를 모두 `holdOnly`처럼 바꾸기:** 계속 눌러 두는 것만으로 통과할 수 있으므로 떼는 동작은 필요하다고 사용자는 설명했다.
- **이진(Perfect/Miss) release:** 사용자는 “이상하지만 차악은 될수있음”이라고 평가했으며, 어색한 점을 “교대하려고 뗀 입력이 끝 판정으로 쓰이는 점”이라고 밝혔다. 비교 후보이며 채택안으로 기록하지 않는다.
- **1→0 전용 release와 연결 release 복원:** 1→0 전용은 [부록 A-3](#a-3-10에서만-release-후보를-만들고-회복으로-취소)과 같다. 연결 release는 이후 연결 head에 한정해 채택했다([§4-1](#4-1-연결-release)).

결과적으로 단독 롱노트의 교대 up은 이른 release로 인정하고 의도가 아니면 Grace를 건다([§2-5](#2-5-바디-중간-교대와-끝-창-안의-교대)).

### A-5. double 공백을 먼저 부족해진 몫부터 채우는 계산

`doubleLong [1000,3000]`에서 A up 1800, B up 1810, C down 1815, D down 1825일 때 1800의 부족을 1815에, 1810의 부족을 1825에 채워 각각 15ms로 보는 방식이다. 사용자는 각 hold 수 기준을 회복할 때까지 재는 방식을 선택했다([§2-2](#2-2-유지-유예)).

### A-6. 연결 release의 보류

head가 있는 2→1([§6-3](#6-3-head가-있는-21과-감소-release))에서 뒤 바디가 짧은 경우를 사용자가 지적했다(2026-10-16).

> 그럼 n3가 짧을 땐 어쩌지 릴리즈 1개 처리법으로 중간 지나가고 n3 종료지점에 뗐는데 흡수되면 안되잖아

N3=`long [2000,2060]`, A 1000–2500, B 1000–2015, C 2020–2060에서 B up이 감소 release를 처리하면, N3 끝의 C up 2060은 연결 head 창(2120까지) 안의 다음 up이라 연결 release에 배정되고 N3는 Miss가 된다. PR #188도 B up을 연결 release에 배정하고 C up을 감소 release Great(+60)로 써서 N3가 Miss다. 연결 release 배정을 보류했다가 끝의 기한 안에 다른 up이 오지 않으면 그 up을 끝 release로 쓰는 안을 제시했으나 사용자는 다음과 같이 답했다(2026-10-16).

> 보류 방식은 좀 위험한거 같아서 차트 제작 지침에 이런 패턴 만들지 말라고 적어줘

보류는 채택하지 않았다. 이 답으로 둔 제작 지침 7항은 이후 폐지했다([§9-3](#9-3-제작-지침-48항)). 이 입력은 A를 끝 뒤까지 남긴 연주이며 의도된 연주는 짧은 뒤 바디에서도 Perfect 3이다([§6-3](#6-3-head가-있는-21과-감소-release)). 짧은 뒤 바디에서 head를 놓친 경우도 보류 없이 처리한다([§5-5](#5-5-짧은-뒤-바디)).

### A-7. 감소 release를 언제나 연결 release보다 먼저 채우기

head가 감소 지점 앞에 있는 차트([§6-4](#6-4-감소-지점-앞뒤의-head))에서 제작 지침으로 막는 방법과, 감소 release를 모든 경우에 연결 release보다 먼저 채우는 방법을 비교해 제시했다. 후자는 head를 탭한 짧은 up이 감소 release로 먼저 쓰여, 뒤에 정확히 뗀 up보다 등급이 낮아질 수 있다. 사용자는 제작 지침을 택했고([§9-3](#9-3-제작-지침-48항)의 “21도 지침으로 막아야겠다”) 배정 순서는 [§6-4](#6-4-감소-지점-앞뒤의-head)대로 유지했다. 그 지침은 이후 폐지했다.

### A-8. head 없는 시작의 down 흡수

시작 직후의 재충전([§8-1](#8-1-시작-직후의-재충전))을 검토하며 사용자는 대안을 함께 제시했다(2026-10-16).

> 이게 싫으면 헤드없는 롱노트도 down을 받게하면 되는데 (교대 릴리즈처럼 흡수만) 근데 이럼 바꿔야될게 또 많아질거같아

head 없는 시작이 시작 창 안의 down 하나를 흡수하면 1→2 증가에서 원래 키의 끊김까지 기회를 받는 관대함은 사라지지만, 미리 누른 키로 시작하기([§2-1](#2-1-hold-수로-시작과-유지-판단))를 되돌리거나(미리 누른 키를 계속 인정하면 시작 직후 hold를 잃는 문제가 남는다) Point와 바디가 down을 나눠 갖는 우선순위 규칙을 다시 만들어야 한다. 미리 누른 키에 기대는 [§6-1](#6-1-12-증가)·[§7-2](#7-2-holdonly-감소에서-키를-남기는-연주)의 사례도 다시 대조해야 한다. 채택하지 않았다. release 자격을 정할 때 사용자가 시작 근처의 down 흡수를 다시 물었으나([§2-3](#2-3-release-등급과-자격-판정-창-기준)의 인용) 흡수 규칙은 두지 않았다.

### A-9. 시작한 바디만 release를 받기

`head 1000` → head 없는 `long [1100,1200]`에서 시작한 바디만 release를 받게 하면 A up 1090과 1100의 결과가 시작 여부로 갈리고, A 1080–1090처럼 시작 근처의 down이 바디를 미리 시작시키는지도 새로 정해야 한다. 사용자는 판정 창이 아니라 시작 여부로 판정이 바뀌는 것이 어색하다고 보았고, 판정 창 기준을 채택했다([§2-3](#2-3-release-등급과-자격-판정-창-기준)).

### A-10. `holdOnly` 끝 뒤 간격을 Good 창 두 개로 늘리기

`holdOnly` 끝에서 늦게 뗀 up이 뒤 끝의 이른 release가 되는 문제를, 제작 지침 8항의 간격을 Good 창 두 개로 늘려 피하는 안이다. 사용자는 `holdOnly` 끝이 Good 창 안의 up을 가져가는 규칙을 택했다([§7-1](#7-1-holdonly-끝은-good-창-안의-up을-가져간다)).

### A-11. 경계 전 up을 연결 보정으로 보기

연결 head를 처리하기 전에 경계보다 먼저 뗀 up을 당시의 연결 보정(경계 뒤의 up을 뒤 release에 쓰지 않는 처리)으로 보고 Good 창 안이면 앞 바디를 끝낸 것으로 보자는 제안이다. 사용자는 이 경우 연결 보정이 작동하지 않으며 바디가 끊어진 적이 없다고 정정했다([§4-2](#4-2-경계-전에-뗀-연결-release)의 인용). 이후 경계 전후의 두 처리를 연결 release 하나로 합쳤다([§4-1](#4-1-연결-release)).

### A-12. 유지 키를 계속 누르고 끝만 치는 플레이의 제한

여분 키의 release를 제한해 유지 키를 계속 누르고 다른 키로 끝만 치는 플레이를 막는 안이다. 사용자는 그렇게 하는 것이 더 헷갈린다며 막을 필요가 없다고 답했다([§3-2](#3-2-유지-키와-다른-키의-up)의 인용).
