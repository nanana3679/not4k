# RFD 0020: 롱노트의 unit 활성화, 승계와 release 면제

- 날짜: 2026-09-07
**Status:** 채택 (2026-09-07) · 판정 세션·플레이·자동 입력 연결 구현 (2026-09-08) · Lab 15개 사례와 Advanced 12개 튜토리얼 구현 (2026-09-08). 세부 검증 기록은 [PRD §12](../prd.md#12-미정-사항)를 따른다.
- 범위: grill에서 확정한 판정 규칙과 특수 사례의 기대 결과. 엔진 자료구조나 전체 상태 전이표의 검증 완료를 뜻하지 않는다.

## 1. 기존 결정과 문제

[RFD 0015](0015-binary-release-judgment.md)는 release를 Perfect/Miss 이진 판정으로 두고 익명 keyup 하나를 가장 이른 대상에 소비했다. [RFD 0006](0006-earliest-matching-headless-long-note.md)의 시작 입력 매칭과 [RFD 0009](0009-hold-only-long-note.md)의 `holdOnly`는 기존 held로 시작 충족 여부를 판단하는 경로를 포함했다.

새 판정 모델에서는 실제 release의 타이밍 등급, 시작 입력의 필요성, 연결된 바디의 승계를 함께 설명해야 한다. 다음 문제를 입력 사례로 대조했다.

- 이미 준비된 끝점이 새 down을 가져가면 뒤 Point를 치는 데 추가 입력이 필요해진다.
- 단순히 held가 충분하다는 이유로 미처리 시작을 완료하면, 키 두 개를 미리 잡는 플레이가 필수 입력을 대신한다.
- 반대로 모든 바디에 새 down을 강제하면 `o-o-`의 유지와 중간 head 탭을 함께 허용할 수 없다.
- `holdOnly`의 자동 Perfect를 실제 keyup처럼 취급하면 면제한 감소를 다시 요구하거나, 다음 바디의 정상 release를 여분 입력으로 버리게 된다.
- 결과만 적고 차트와 입력 시점을 생략하면, 감소 release와 더 뒤의 이른 마지막 release를 혼동하게 된다.

## 2. 채택안

용어의 풀 정의는 [glossary](../context/glossary.md#롱노트-판정-모델), 입력별 기대 결과는 [판정 사례 명세](../spec/note-judgment-cases.md)에 둔다. 구현 순서와 완료 기준은 [구현·검증 계획](../plans/note-judgment-implementation.md)을 따른다. 현재까지 확인한 사항 중 구현 계획 수립 전에 추가로 답해야 할 제품 질문은 없다. 전체 상태 전이의 일관성은 구현 초기에 사례 재생과 불변식 검사로 검증한다.

### 2.1 활성화와 유지

- 바디는 유지·실패를 추적하는 `unit`으로 나눈다. single은 1개, double은 2개이며, double은 겹친 별도 바디 두 개가 아니다.
- 고정 물리 owner를 두지 않는다. 실제 head·시작 입력·정당한 승계로 등록된 유지 키와, 실제 release를 처리할 권한을 구분한다.
- 양수 길이 바디는 자기 시작 입력 또는 정당한 승계로 활성화한다. head 없는 시작은 keydown을 소비하지만 시작 점수는 발생시키지 않는다.
- 이미 정당한 승계로 준비된 unit은 추가 시작 down을 소비하지 않는다. 실제 head가 있으면 그 head의 별도 입력·판정은 필요하다.
- 일반 바디와 양수 길이 `holdOnly` 모두 임의의 raw held만으로 독립 시작하거나 유지하지 않는다. 다른 독립 노트가 소비한 down도 자기 시작 입력을 대신하지 않는다.
- 첫 활성화 기한은 길이와 무관하게 S+Good이다. 허용된 시작 창 안에서는 E 이후의 첫 활성화도 가능하다.
- 이미 활성화한 unit의 유지 실패는 되돌리지 않는다. 같은 timestamp의 입력을 모두 반영한 뒤 유지 부족을 확인한다. 새 down/up의 실제 인과관계를 지우지 않는다.
- 실패는 해당 unit에 적용한다. 뒤 바디를 한꺼번에 실패시키지 않으며, head·`holdOnly`·unit 수 변화로 구분되는 새 바디에는 자기 시작 기회가 있다.
- 실패한 바디를 건너뛰어 오래된 head의 늦은 성공을 더 뒤의 승계로 전달하지 않는다. 살아 있는 다른 unit의 경로까지 초기화하는 규칙은 아니다.

### 2.2 입력 소비와 실제 release

- keydown은 창과 키 자격을 충족한 가장 이른 Point 또는 실제로 필요한 시작 하나에 소비한다.
- keyup은 창·준비·키 자격을 충족한 가장 이른 실제 release 하나에 소비한다. 가까운 시각 우선이 아니다.
- 실제 release는 Perfect / Great / Good / Miss이며 raw FAST/SLOW를 집계한다. Normal은 ±41/82/120ms, Easy는 ±50/100/150ms이다. Bad는 사용하지 않는다.
- double head 및 double 시작 준비에는 서로 다른 두 물리 키가 필요하다. 실제 release는 각 누름의 권한을 따른다. 같은 물리 키라도 유효한 새 head·미처리 시작을 처리하여 새 권한을 얻으면 같은 double 종료의 남은 release를 처리할 수 있다. 후속 채택 근거는 §2.8을 따른다.
- 이미 release에 사용한 누름의 권한은 남은 release 후보와 여분 키 계산에서 제외한다. 유효한 새 입력으로 얻은 권한까지 물리 키 사용 이력으로 차단하지 않는다.
- 일반 여분 키의 keyup은 실제 release를 소비하지 않는다. keyup은 그 press의 자격을 끝내며, 임의의 재누름으로 자격을 복구하지 않는다.
- 여분 여부는 현재 바디의 unit 수만으로 계산하지 않는다. 앞에 남은 실제 종료 요구도 고려한다.
- 같은 연결 구간의 나중 시작에 등록된 키도 앞의 준비된 실제 release를 처리할 수 있다. 이미 실패한 unit은 부활시키지 않는다.
- 앞 release의 미처리 준비나 Miss로 끝난 몫을 뒤 증가분의 미처리 시작에 중복 배정하지 않는다.
- 유효한 head·시작 입력으로 연결 경계의 교대가 성립한 keyup은 뒤 실제 release에 소비하지 않는다. 교대가 성립할 수 있는 up은 용도를 먼저 확정하며, 그 전에는 뒤 끝의 이른 등급을 확정하지 않는다. 적용 배경과 범위는 §2.6을 따른다.

### 2.3 `holdOnly`

- 양수 길이는 활성화된 바디의 끝에서 release를 면제하고 Perfect/Miss 상태 판정을 한다. 등록된 키로 유지해야 한다.
- E까지 유지하면 Perfect이다. 유효한 이른 완료와 S+Good까지의 늦은 첫 활성화도 허용한다. `holdOnly`에는 FAST/SLOW가 없다.
- 상태 완료는 keyup을 소비하지 않는다. 같은 keyup으로 유효한 `holdOnly` 상태 완료와 실제 release 하나가 함께 성립할 수 있다.
- 2→1의 일반 감소는 실제 release 1개를 판정한다. 같은 경계에 `holdOnly`가 붙으면 앞 double의 두 unit을 각각 판정한다. 둘 다 성공하면 Perfect 2개이고, 하나는 종료되고 하나는 뒤 바디로 이어진다.
- 사용자 관점에서도 감소 `holdOnly` 경계는 이어지는 쪽에 노트가 하나 더 보이므로 두 판정이 자연스럽다.
- 자동 Perfect와 종료·승계 배정은 분리한다. 늦게 들어온 두 head가 순서대로 종료 쪽과 이어지는 쪽을 충족할 수 있다. 특정 키를 먼저 고정하지 않는다.
- `holdOnly` 감소는 실제 키 수 감소를 요구하지 않는다. 계속 held인 등록 키의 자격은 남으며, 다음 증가에 정당하게 승계할 수 있다.
- **release를 면제받은 몫은 뒤 실제 release를 막는 여분 키 계산에서 제외한다.** double `holdOnly` → single에서 A/B를 유지하다가 마지막에 A만 떼어 실제 release를 완료하고, B는 계속 잡을 수 있다.
- 이 면제는 일반 여분 키 전체에 적용하는 규칙이 아니다. 면제한 몫이 다음 증가의 새 unit으로 이어지면 그 새 unit의 끝 판정을 따른다. 같은 몫을 새 unit의 활성화와 추가 release 면제에 중복 사용하지 않는다.
- 길이 0 `holdOnly`는 기존 held로 통과하는 상태 판정을 유지한다. 독립된 일반 release 권한을 새로 만들지 않는다. 양수 길이에 대한 시작 입력 요구와 구분한다.

### 2.4 점수와 실패

- head, 실제 release, 명시된 `holdOnly`는 점수 항목이다. 일반 `connection` 성공에는 점수·콤보 증가·고도 회복이 없다.
- 일반 연결 바디의 유지 실패는 Miss 표시·통계·고도 손실·콤보 단절에 반영한다. 별도 점수 감점이나 점수 분모 항목을 추가하지 않는다.
- 점수 항목의 이론 가중치는 차트로 고정한다. 실시간 달성률의 분모는 지금까지 처리한 점수 항목의 이론 가중치 합, 최종 분모는 전체 이론 가중치 합이다.
- head Miss로 새 head 종속 unit이 시작할 수 없으면, 종속 끝점은 0점과 원래 가중치를 head Miss와 함께 처리한다. 끝점에서 추가 Miss 표시·고도 손실을 발생시키지 않는다. 이미 건강하게 승계된 바디는 head Miss와 독립적이다.
- 활성화 후 실패한 unit도 한 번만 실패 처리한다. 실패 시점과 끝점에서 중복 패널티를 주지 않는다.
- 100% 달성률이면서 Full Combo가 아닌 결과를 허용한다. 이를 막기 위해 연결 점수, Miss 감점, 콤보 점수 보너스를 추가하지 않는다.

### 2.5 차트 제약

- 같은 레인의 바디 열린 구간은 겹치지 않으며, 그 내부에 Point를 놓지 않는다.
- 차트상 끝과 다음 시작이 맞닿은 경우에 승계한다. 판정 창이 겹친다는 이유만으로 별개 바디를 연결하지 않는다.
- 같은 unit 수의 경계에는 head 또는 `holdOnly`가 있어야 한다. unit 수가 바뀌는 경계에는 둘이 없어도 된다.
- 양수 길이 바디 끝과 같은 시각에 별도의 길이 0 롱노트를 붙이지 않는다. Point는 배치할 수 있으나, `holdOnly`와 Point의 동시 배치는 금지한다.
- head가 있는 길이 0 롱노트는 없다. `trillLong`에는 head가 필요하고, 양수 길이 `trillLong + holdOnly`는 허용하며 길이 0 조합은 금지한다.

### 2.6 교대 keyup과 뒤 release 창이 겹치는 경우 — 후속 채택

`o-o-`에서 앞 키를 995에 떼고 연결 head 1000을 다른 키로 처리해 1100까지 유지했는데, 앞 up이 마지막 1100의 Good으로 먼저 확정되는 결과를 사용자가 재검토했다. 같은 unit 수의 일반 연결 `o-o-`·`d=d=`는 연속 유지와 경계 교대를 모두 지원해야 한다.

**유효한 교대가 성립한 keyup은 뒤 release 판정에 쓰지 않는다.** 사용자는 “교대 시 발생하는 릴리즈를 릴리즈 판정에 안쓰면 되는구나”로 이 원칙을 채택했다. 임의의 raw down이 있었다는 이유로 모든 이전 up을 교대로 처리하지는 않는다.

**동일 키 재타격에도 서로 다른 키로 넘길 때와 같은 release 제외 보정을 적용한다.** 사용자는 설명하기 어려운 동일 키 예외를 재검토한 뒤 “동일 키라도 같은 보정을 적용한다는 말이라면 동의함”이라고 명시했다. 이에 따라 서로 다른 키에만 보정을 적용하던 제한을 정정한다. 유효한 다음 head·시작 입력으로 바디를 이어가는 데 쓰인 up은 키의 동일 여부와 관계없이 뒤 실제 release에 쓰지 않는다. 동일 키라는 이유로 연결 Miss를 추가하지 않는다.

키 교대라는 입력방식은 계속 서로 다른 키 사이의 전환을 뜻한다. 동일 키 재타격에도 같은 연결 보정을 적용한다는 것이며, 키 교대의 용어 정의를 바꾸지 않는다. 임의의 재누름은 유효한 head·시작 입력을 대신하지 않으며, double head의 서로 다른 물리 키 요구는 유지한다. 실제 release 권한의 갱신은 후속 채택 §2.8을 따른다. 보정한 up은 실제 release 사용 이력에 넣지 않는다. 구체적인 짧은 끝·긴 끝의 동일 키 사례는 [NJ-R09](../spec/note-judgment-cases.md#nj-r09), 부분 연결과 동시 입력의 대조는 NJ-R04·NJ-R11을 따른다.

**double의 한 unit만 교대하면 그 몫에만 보정을 적용한다.** A/B 유지 중 A up 995 → C head 1000으로 한 몫을 교대하고 B up 1030 → C up 1100으로 끝 1100을 처리하면, A의 up만 교대로 제외한다. B의 실제 release는 Great(-70), C는 Perfect이며, 나머지 double head의 Miss가 B로 정상 승계된 unit까지 실패시키지 않는다. 하나의 새 head로 두 교대를 성립시키거나 경계 주변의 모든 up을 보정하지 않는다. 사용자 확인 사례는 [NJ-R10](../spec/note-judgment-cases.md#nj-r10)이다.

**적격인 보류 up 중 먼저 발생한 것부터 연결 보정에 배정한다.** double의 A up 1010 → B up 1040 뒤 single head 1000을 C down 1050으로 처리하면, 먼저 발생한 A up을 보정한다. 끝 1100의 실제 release는 B up 1040의 Great(-60), C up 1100의 Perfect이다. 사용자가 이 발생 순서 우선에 동의했으며 [NJ-R12](../spec/note-judgment-cases.md#nj-r12)에 기록했다.

**동일 키 재타격도 보정 후보가 되지만 발생 순서를 앞질러 우선 배정하지 않는다.** C 대신 B down 1050으로 head를 처리해도 먼저 발생한 A up은 연결용, 두 번째 B up 1040은 마지막 `termination`의 Great이다. 사용자는 이 `=o=`의 중간점에 배정할 연결용 up은 한 개이므로 두 번째 up이 terminal에 적용되는 것이 맞다고 명시했다. B의 재타격을 끝까지 성공시키기 위해 두 up의 배정을 바꾸지 않는다. 이후 B up 1100은 §2.8에서 채택한 새 head의 권한으로 두 번째 실제 release Perfect를 처리한다. [NJ-R13](../spec/note-judgment-cases.md#nj-r13)을 따른다.

중간점의 한 몫은 연결 보정에 쓸 수 있는 up의 개수이며, 그 경계에 점수 release를 새로 추가한다는 뜻이 아니다. 기존 유지와 별도 head 탭 방식도 계속 허용한다. 동일 timestamp 후보의 내부 동률 순서는 §2.7의 결과 일관성과 §2.8의 권한 갱신을 만족해야 하며, 사용자에게 별도 키 우선순위를 선택하도록 요구하지 않는다.

교대와 뒤 release 모두에 해당할 수 있는 up은 용도가 결정되기 전까지 잠정 후보로 둔다. 마지막 E 이후에도 연결 head의 Good 창이 남을 수 있으므로 E만으로 확정하지 않는다. 이미 확정한 등급을 되돌리는 방식으로 정의하지 않는다. 이 변경은 교대 up을 뒤 release의 적격 후보에서 제외하며, 남은 실제 release 후보 사이의 가장 이른 대상 우선과 실제 입력 시각의 타이밍 등급은 유지한다.

교대가 실패하여 다음 unit이 시작·승계되지 못하면 그 unit의 실제 release도 성공 판정할 대상이 없다. 보류한 up으로 뒤 끝의 Good을 만드는 이전 설명은 사용자의 “마지막 교대를 실패했다는건 릴리즈 할 대상도 없다는거 아니야?”라는 지적에 따라 정정한다. 종속 끝점은 0점과 원래 가중치로 정리하며, 끝 시점에 추가 Miss 패널티를 주지 않는다. 연결 1000·맨끝 1100에서 A up 995 후 기한까지 새 입력도 유지 키도 없었던 [NJ-R08](../spec/note-judgment-cases.md#nj-r08)에 적용한다.

이 교대 실패 사례에서는 승계 준비만으로 다음 바디를 S 이전에 조기 완료했다고 간주하는 종전 해석을 사용하지 않는다. head만 Miss이고 바디가 기존 키로 정상 승계된 경우와 구분하며, 그 경우에는 해당 바디의 실제 release가 남는다. 정상 승계된 바디의 유효한 이른 release 전체를 금지하는 변경은 아니다.

Trade-off는 모호한 up의 최종 결과가 후속 입력에 따라 늦게 확정될 수 있다는 점이다. 대신 정상 연결이 의도치 않은 이른 끝 판정으로 확정되는 결과를 피한다. 복수 후보의 발생 순서, 같은 키의 새 권한, 동시 후보의 결과 일관성은 이 문서의 채택 규칙이다. 통합 검증과 구현 이행은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다. 서로 다른 키의 정상·늦은 교대는 [NJ-R06](../spec/note-judgment-cases.md#nj-r06)을 따른다.

### 2.7 동일한 플레이의 결과 일관성 — 후속 요구사항

사용자는 “사용자 입장에서 똑같은 플레이를 하면 같은 결과가 나와야” 한다고 명시했다. 같은 차트에서 같은 키·시각의 입력을 했을 때, 서로 다른 키의 동시 up을 내부에서 배정하거나 수신 순번으로 나눈 방식만으로 이후 성공·Miss가 갈리면 안 된다. 같은 timestamp에서 모든 입력을 반영한 뒤 유지 부족을 확인하는 것만으로는 충분하지 않으며, 그 배정이 남긴 release 사용 키 이력까지 후속 결과에 영향을 주지 않아야 한다.

이 요구사항은 채택한다. 수신 순번에 따라 NJ-Q08의 마지막 B up이 성공하거나 막히는 제안은 이 요구를 충족하지 못한다. 후속으로 사용자가 §2.8의 권한 갱신을 채택했다. 동시 up의 내부 배정이 달라도 새 head 뒤 release의 결과가 같은 대조는 [NJ-R14](../spec/note-judgment-cases.md#nj-r14)를 따른다. 전체 상태 전이 검산과 이행 상태는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### 2.8 유효한 새 입력에 따른 release 권한 갱신 — 후속 채택

기존에는 같은 double 끝의 첫 실제 release에 사용한 물리 키를, 새 head가 성공한 뒤에도 남은 release 후보에서 제외했다. NJ-Q08에서 동시 A/B up 중 어느 것을 연결에 배정했는지에 따라 이후 B head → B up의 성공 여부가 달라져 §2.7의 결과 일관성 요구와 충돌했다.

사용자는 **유효한 새 head·미처리 시작을 처리하면 같은 물리 키도 그 새 누름의 release 권한을 얻는다**는 안을 채택했다. 같은 double 끝에서 실제 release에 한 번 쓴 키라는 이유로 새 권한을 차단하지 않는다. 임의의 재누름은 새 권한을 주지 않으며, 등록 대상과 연결 구간, 창·준비·실패 여부 등 기존 적격 조건은 그대로 적용한다. 독립된 다른 Point의 입력이 앞 바디의 권한을 새로 주는 규칙도 아니다.

한 up은 실제 release 하나만 소비한다. 앞 up의 배정·등급을 취소하지 않으며, 첫 up 연결·다음 적격 up terminal이라는 순서를 유지한다. 실패한 unit의 부활과 실패 경로를 건너뛰는 승계는 허용하지 않는다. double head·double 시작의 서로 다른 물리 키 요구도 바꾸지 않는다.

이에 따라 NJ-R13은 A up 1010을 연결, B up 1040을 첫 terminal Great로 처리하고, B head 1050에서 얻은 새 권한으로 B up 1100을 둘째 terminal Perfect로 처리한다. 전체는 Perfect 3개·Great 2개·Miss 없음이다. 동시 up의 두 내부 배정을 대조한 NJ-R14, 아무 새 head·시작 없는 재누름을 대조한 NJ-R15를 함께 기록한다.

Trade-off는 유효한 새 입력을 사이에 두면 같은 double 끝의 두 release를 같은 물리 키로 처리할 수 있다는 점이다. 과거의 무조건적인 물리 키 중복 금지를 유지하는 안이 아니며, 누름별 권한과 유효한 입력 요구로 대체한다. 배정 전체를 가리는 키 차단이나 성공 결과에 맞춘 보정 후보 재배정은 채택하지 않는다.

### 2.9 보류 판정의 콤보는 확정 순서로 반영 — 후속 채택

NJ-Q10에서는 보류한 release가 실제 입력 이후에 확정될 때, 콤보를 원래 입력 시각에 소급하여 계산하는 안을 검토했다. 사용자는 판정이 결정되는 순서로 처리할 것을 제안했다. **현재 콤보는 판정 확정 순서로 반영한다.** 보류 중인 후보는 콤보에 넣지 않으며, 실제 release로 확정된 뒤 반영한다. 이미 지난 Miss 앞에 성공을 소급해서 끼워 넣지 않는다.

타이밍 등급과 raw FAST/SLOW는 계속 실제 up 시각으로 계산한다. 확정이 늦다는 이유로 원래 Great 입력을 늦은 Good이나 Miss로 바꾸지 않는다. 동일 timestamp·phase의 판정은 기존대로 전 레인 묶음으로 처리하고 Miss가 콤보 결과에서 우선한다.

확정 순서는 유효한 입력과 판정 기한 등 게임 규칙에 따른 순서이다. 같은 플레이에서 프레임 호출 간격, 레인 순회, 이벤트 수집 순서 때문에 결과가 달라져도 된다는 뜻은 아니다. 여러 기한을 한 update에서 관측해도 각 기한의 논리적 순서를 보존해야 한다.

확정된 판정을 따라 콤보가 변하도록 하고, 소급 계산을 위해 이미 처리한 콤보 이력을 되돌리는 부담을 없앤다. 채택 결과는 [NJ-S03](../spec/note-judgment-cases.md#nj-s03)을 따른다. 당시 최대 콤보 비교를 포함했던 논의의 범위는 후속 §2.10에 따라 정리한다.

### 2.10 최대 콤보 통계 미제공 — 후속 채택

NJ-Q11에서 같은 확정 묶음의 성공·Miss가 최대 콤보를 갱신하는지 질문했다. 사용자는 최대 콤보수 통계를 제공하지 않을 것이므로 이 논의가 필요 없다고 명시했다. **최대 콤보 통계는 제공하지 않는다.** 해당 질문과 계산 정책의 결정을 철회하고, 판정 사례에서도 최대 콤보를 제품의 기대 결과로 요구하지 않는다.

현재 콤보의 확정 순서와 동일 묶음의 Miss 우선, Full Combo 조건은 기존 채택안을 따른다. 최대 콤보를 별도 성과 지표나 점수 요소로 도입하지 않는다. 기존 구현의 `maxCombo` 필드나 결과 화면 노출이 이 제품 결정을 대신하지 않는다. 결과 화면의 노출 제거는 구현 이행 대상이며, 이번 grill에서 게임 코드는 변경하지 않는다.

Trade-off는 가장 길게 이어 친 구간의 수치를 결과 통계로 제공하지 않는 것이다. 제공하지 않는 통계의 계산 정책을 판정 모델의 미결정 문제로 남기지 않는다. 이행 상태는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### 2.11 함께 적용할 Point·트릴의 기존 채택 규칙

롱노트 이행 과정에서 이미 결정한 입력 규칙을 과거 구현으로 되돌리지 않도록 함께 명시한다.

- Point도 Good 창 안의 가장 이른 적격 대상이 입력을 소비한다. Bad 등급과 Bad 매칭 구간은 사용하지 않는다. double head는 서로 다른 물리 키를 요구하며 두 성공 키의 입력 기록을 모두 보존한다.
- Grace는 Good 창 안의 타이밍 등급을 Perfect로 처리하며 FAST/SLOW를 집계하지 않는다. 트릴 교대 실패에 따른 `goodTrill`은 별도로 적용한다.
- `goodTrill`은 head에만 적용한다. Good과 같은 점수·콤보 취급 및 별도 표시·집계를 가지며 바디의 release 등급을 대신하지 않는다. 일반 `goodTrill`은 raw 타이밍을 사용하고 Grace의 `goodTrill`은 FAST/SLOW에서 제외한다.
- 트릴 교대 세트에는 **head를 소비한 키만 등록**한다. 바디 유지·승계 키나 release만 소비한 키, 임의 raw down을 등록하지 않는다. 과거 handoff의 body owner 등록 설명은 고정 owner 제거 후의 채택안이 아니다.
- 트릴 head 확정 때 이전 세트를 갱신하고, head Miss에서는 이전 세트를 비운다. 교대 세트의 구간은 입력이 도착한 현재 시각이 아니라 해당 노트의 차트상 `trillZone`을 따른다. 이른 입력과 늦은 입력이 인접 구간의 추적을 오염시키지 않아야 한다.
- 같은 timestamp의 복수 적격 트릴 입력에는 최고 등급 입력 선택과 교대 한 번 인정 규칙을 적용한다. 나머지 적격 head 입력은 `goodTrill`이며, 하나의 입력을 여러 head에 중복 소비하지 않는다. 입력 수집 순서만으로 결과가 바뀌지 않는지 통합 검증한다.

이 절은 대화에서 이미 채택한 규칙의 이행 범위 정리이다. 38개 롱노트 사례만으로 Point·트릴의 모든 조합을 검증했다고 주장하지 않으며, 추가 회귀 범위는 구현 계획에 둔다.

## 3. 대안과 채택 이유

| 대안 | 처리 |
|---|---|
| unit마다 고정 물리 owner 배정 | 채택하지 않는다. 유지 키 수, 시작 준비, release 권한으로 설명한다. |
| 모든 바디가 새 down을 요구 | 정당한 승계까지 막으므로 채택하지 않는다. 부족한 시작만 입력을 요구한다. |
| 양수 길이 `holdOnly`도 raw held 또는 다른 Point의 down을 공유해 독립 시작 | 채택하지 않는다. 정상적인 앞 노트의 입력이 뒤 바디를 조기 실패시키는 문제와 시작 생략을 막는다. |
| `holdOnly` 자동 완료가 held 키 자격까지 소비 | release 면제 후에도 물리 감소를 요구하므로 채택하지 않는다. |
| 실제 release를 가까운 끝점에 우선 배정 | 채택하지 않는다. 앞의 유효한 미처리 release 우선을 유지한다. |
| 연결 유지 실패를 별도 점수 감점 또는 콤보 점수로 보정 | 채택하지 않는다. 고도·콤보·Miss 기록으로 유지 동기를 둔다. |

폐기안은 배경 기록이다. [사례 명세](../spec/note-judgment-cases.md)의 기대 결과에 대안 결과를 섞지 않는다.

## 4. Trade-off

- 물리 owner를 고정하지 않는 대신, 완료한 점수 항목과 아직 결정할 수 있는 종료·승계 배정을 구분해야 한다.
- `holdOnly`는 의도적으로 release와 후속 재누름 부담을 낮춘다. 임의의 raw held에 같은 효과를 주지 않는다.
- 짧은 double에서 두 키를 겹쳐 누르지 않아도 모든 필수 down/up이 자기 창 안에 있으면 성공할 수 있다.
- 일반 연결 유지 실패에 직접 점수 손실이 없으므로 특이한 플레이가 100% 달성률에 도달할 수 있다. Full Combo와 고도가 이를 별도로 드러낸다.
- 차트 끝점과 길이 0 노트를 중복 인코딩하지 못하게 하여, 같은 끝 표현의 복구 동작이 저장 형태에 따라 달라지는 것을 막는다.

## 5. 사례를 동작 정의와 함께 유지

- 특수 사례에는 안정된 ID, 구체적인 한국어 테스트명, 차트, 초기 held·등록 상태, 시간순 입력, 판정 대상·등급, 후속 unit 상태를 기록한다.
- 같은 물리 입력이 여러 효과를 내면 실제 소비 대상과 상태 완료를 구분한다.
- 일반 여분 키와 `holdOnly` 면제 몫처럼 결과가 다른 인접 사례를 함께 둔다.
- 사용자에게 직접 확인한 사례와 채택 규칙에서 도출한 대조 사례를 구분한다. 기대 결과를 추가로 결정해야 하는 후보는 확정 사례로 쓰지 않는다.
- 사례는 엔진 내부 필드나 구현 함수를 정답으로 삼지 않는다. 구현 시 ID를 테스트명에 남기고, 판정 대상·횟수·등급·부활 여부를 검증한다.

이번 산출물은 RFD, 사례 명세, 구현·검증 계획이다. 게임 코드·validator·자동 테스트는 변경하지 않았다. 구현은 [계획](../plans/note-judgment-implementation.md)의 순서와 통과 기준을 따르며, 정합성 검증·이행 상태는 [PRD의 미정 사항](../prd.md#12-미정-사항)에서만 추적한다. 기존 RFD와 검산 기록의 역사적 본문을 새 기대 결과로 읽지 않는다.
