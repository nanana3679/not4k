# 곡·차트 관리 (admin)

곡과 차트의 등록·삭제 수명주기 규칙을 정의한다. 게임의 곡 선택 화면(admin 모드)과
에디터에서 수행하는 관리 작업이 대상이다.

## 데이터 구조

## 곡의 표시 정보

제목·아티스트·자켓은 같은 곡에 속한 모든 차트가 공유한다. 곡의 표시 정보와 난이도명·Lv. 등 차트별 정보를 구분한다. 제목 정정이나 아티스트 표기·자켓 교체처럼 표시 정보만 수정할 때는 기존 기록과 랭킹을 유지하며 기록용 차트 버전을 분리하지 않는다([곡 메타데이터](../context/glossary.md#곡-메타데이터), [RFD 0096](../rfd/0096-song-shared-display-metadata-and-records.md)).

현재 곡 단위 DB·자켓 저장과 차트 문서의 관련 필드가 함께 존재한다. 편집·참조의 정본 일치와 기존 사본 정리의 세부는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

## 곡의 BPM·음원 정렬 오프셋 `[미구현]`

같은 곡의 모든 차트는 초기 BPM·곡 중간의 BPM 변경 목록·박자표·변박 정보·음원 정렬용 오프셋을 공유한다. 이 정보의 논리적 소유자는 곡이며, 차트마다 다른 값을 별도로 확정하지 않는다. 노트 배치와 난이도는 차트별로 관리한다([곡 타이밍](../context/glossary.md#곡-타이밍), [RFD 0095](../rfd/0095-song-shared-bpm-and-audio-offset.md)).

곡의 표시 정보와 공통 타이밍은 **곡 저장**으로 함께 확정하고, 개별 차트는 **차트 저장**으로 확정한다. 각 저장이 다른 범위의 미저장 변경을 함께 확정하지 않는다. 공통 타이밍에 미저장 변경이 있으면 개별 차트 저장을 차단하고, 곡 저장이 성공해 타이밍에 미저장 변경이 없어지면 차트 저장을 허용한다([RFD 0098](../rfd/0098-song-info-drawer-and-save-scope.md)). 상세 조작은 [에디터 스펙](chart-editor.md#곡-타이밍-공유-미구현)을 따른다.

기존 차트를 곡 공통 타이밍 구조로 옮길 때, 같은 곡의 차트마다 BPM·박자표·음원 정렬 오프셋이 다르면 관리자가 기준으로 삼을 차트 하나를 선택한다. 선택한 차트의 초기 BPM·BPM 변경 목록·박자표·변박 정보·음원 정렬 오프셋을 해당 곡의 공통값으로 적용한다. 기준 차트 선택의 결정은 [RFD 0095](../rfd/0095-song-shared-bpm-and-audio-offset.md)를 따른다.

곡 공통 타이밍을 적용할 때 기존 노트·차트별 이벤트의 박 위치를 유지한다. 구간 항목의 시작·끝 박도 그대로 두며, 기존 음원 시각을 유지하기 위한 박 좌표 변환은 하지 않는다. 실제 음원상의 입력 시각과 구간 길이는 새 공통 타이밍에 따라 계산한다.

공통 타이밍 수정으로 실제 입력 시각이 달라지면 영향을 받는 각 차트의 기록과 랭킹을 새 버전으로 분리한다. 저장 구조와 기존 차트의 이행·편집 반영 절차는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

## 현재 데이터 구조

아래 표는 현행 구현이다. 차트별 BPM 이벤트·오프셋 저장을 곡 단위 공유의 완료된 구현으로 보지 않는다. 곡 하나는 두 저장소에 걸쳐 존재한다.

| 위치 | 내용 |
|------|------|
| `songs` 테이블 | 곡 메타데이터 (제목, 아티스트, 재생 구간 등) |
| `charts` 테이블 | 차트 메타데이터 (난이도 라벨/레벨, offset) |
| Storage `songs/{song_id}/` | 음원, 자켓, 프리뷰, 차트 JSON(`{difficulty}.json`, `{difficulty}.extra.json`) |

## 삭제 규칙

**차트를 모두 지운 곡만 삭제할 수 있다.** (2026-07-06 곡 오삭제 사고 후속)

- 차트 삭제는 **에디터에서 한 번에 하나(난이도 하나)씩만** 가능하다. 차트 일괄 삭제 경로는 없다.
- 곡 삭제(곡 선택 화면 admin)는 차트가 0개일 때만 허용된다.
  - 차트가 남아 있으면 삭제 확인 모달에서 Delete 버튼이 비활성화되고 남은 차트 수를 안내한다.
  - 앱을 우회한 삭제(대시보드, SQL)도 DB의 FK 제약(`charts.song_id → songs.id`,
    `on delete restrict`)이 거부한다. 마이그레이션: `20260706000000_restrict_song_delete.sql`
- 곡 삭제 순서는 **DB 행 먼저, Storage 파일 나중**이다. 클라이언트가 아는 차트 수가
  낡았더라도 FK가 행 삭제 단계에서 거부하므로, 거부 시점에 파일은 무손상이다.
  구현: `src/shared/songAssets/chartAssetPersistence.ts`의 `deleteSongAsset`

### 삭제 후 플레이 기록 `[미구현]`

차트를 삭제해도 기존 플레이 기록·최고기록·달성 여부는 원래 차트 버전에 보관하고, 삭제된 차트는 곡·차트 선택과 현재 랭킹에서 제외한다. 삭제한 차트를 다시 등록하면 새 차트로 취급해 기록을 새로 쌓으며, 이전 기록은 승계하지 않는다.

삭제 전에 시작한 플레이나 이미 완료된 미전송 결과는 삭제 후에도 원래 차트 버전의 기록으로 접수·보관한다. 이 기록은 현재 랭킹에 반영하거나 재등록된 차트에 연결하지 않는다. 로그인 등 기존 기록 접수 요건과 Quit·Retry 중단 기록 제외는 그대로 적용한다.

차트·곡 콘텐츠의 삭제와 플레이 기록의 삭제를 구별한다([RFD 0097](../rfd/0097-preserve-records-after-chart-deletion.md)). 기록 보관과 원래 차트 버전 참조를 유지하는 저장 구조는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다. 위의 현행 DB·Storage 삭제 절차가 이 기록 보존 정책까지 구현했다는 뜻은 아니다.

## 백업 (다중화)

차트·곡 데이터의 유일한 사본이 Supabase에만 존재하지 않도록 백업을 이중으로 유지한다.

- **수동**: `pnpm backup` → `backups/<UTC타임스탬프>/`에 `songs`·`charts` 테이블 덤프와
  Storage `songs/`, `tutorials/` 전체 파일을 저장한다. `--charts-only`를 붙이면
  DB 덤프 + 차트 JSON만 (수백 KB). `backups/`는 gitignore 대상이다.
  구현: `scripts/backup-supabase.ts`
- **자동** (`.github/workflows/backup.yml`): 매일 03:00 KST에 charts-only,
  매주 일요일 04:00 KST에 풀 백업을 실행해 Actions 아티팩트로 90일 보관한다.
  필요 시크릿: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`
- 사용자 데이터(`play_records` 등)는 RLS 때문에 publishable key로 백업할 수 없다 — 미포함.
