# not4k — 게임 코어 설계

> 새 판정 규칙은 [RFD 0037](../rfd/0037-explicit-score-notes-and-body.md)과 [glossary](../context/glossary.md#바디-판정과-실패-종속)의 **채택 계약·일반 기본 경로 구현·검증**이다(명시 테스트 재생은 #346, 일반 곡 재생 전환은 #347). [대표 사례](explicit-note-judgment-cases.md)의 PNG는 엔진 출력과 구별하는 설계 도식이다. 일반 곡 재생은 새 세션을 사용하며 기존 튜토리얼 목록과 구형 에디터/Lab 복귀 경로의 테스트는 과도기 구형 경계로 보존한다. 미정 사항·실제 이행은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다.

<summary>RFD 0035 당시의 구형 후속 설계 기록</summary>

> **후속 설계(엔진 이행 전):** [RFD 0035](../rfd/0035-release-presence-and-grace.md)에서 롱노트의 유지와 별도 릴리즈 노트의 뗌을 분리하고 `holdOnly`를 폐지했다. 바디 끝에 릴리즈 노트를 명시하는 조합을 허용하며, 릴리즈 없음·일반 릴리즈·그레이스 릴리즈를 구분한다. 바디는 점수 항목·가중치에서 제외하고 유지 판정으로 콤보와 고도에만 관여하되, 유지 실패 시 연결된 릴리즈 기회도 잃는다. 그레이스 릴리즈도 실제 뗌은 필수이며 타이밍 등급만 면제한다. 아래 `holdOnly` 설명은 현재 구현의 기록이고, 새 정의는 [glossary](../context/glossary.md#release-판정)를 따른다.

이 기록과 새 명시 모델의 차이는 RFD 0037의 철회·대체 범위를 따른다.
</details>

일반 곡 선택은 메인·별도 보조 파일을 `ChartDocument`로 읽어 전체 문서 검증 뒤 새 세션을 시작한다. **일반 곡 선택은 명시 판정만 실행한다.** main에 구형 게임 노트(single·double·trill·long·doubleLong·trillLong)가 하나라도 남은 차트는 구형 판정 경로로 재생하지 않고 로딩 화면에서 "This chart uses an older note format." 안내로 거부하며, 에디터에서 명시 노트로 다시 제작할 때까지 곡 선택에서 재생할 수 없다(사용자 결정, 2026-10-26, [RFD 0037 §8](../rfd/0037-explicit-score-notes-and-body.md#8-구형-차트와-과도기)). 구형 main을 명시 실행으로 자동 변환하지 않는다. 구형 판정 경로의 재생은 에디터/Lab 테스트 플레이 복귀 경로와 곡 선택의 기존 튜토리얼 미리보기에만 남는다. 로딩 실패의 안내는 [차트 형식·검증 오류](#차트-형식검증-오류)를 따른다. 일반 첫 시작·Retry는 에셋 준비 뒤 바로 재생하고 완료 결과는 실제 세션에서 공식 화면으로 전달한다. 저장 포맷과 소비자 경계는 [차트 문서 포맷](chart-format.md)을 따른다.

## 현재 채택 판정 경계

새 모델은 정적 lane·Beat 관계, 무점수 바디 몫, 명시적 탭·릴리즈·틱 노트 항목, 세션의 확정 사실·현재 상태·표시 수명을 구분한다. 바디에서 숨은 릴리즈·점수를 만들지 않고 관계를 ms 창 겹침으로 다시 추정하지 않는다. 실패 종속·시작·완료와 입력 소비는 아래 새 계약을 따른다. 저장/API의 구체적인 필드·배열·ID는 구현에서 정한다.

이 문서는 노트 시스템과 스코어링 이외의 게임 본체 동작 — 플랫폼, 인증, 랭킹, 입력 매칭, 스크롤, 오프셋, 게임 화면, 상태 흐름 — 을 정의한다.

## 플랫폼

**웹 게임**으로 개발한다. 브라우저에서 직접 플레이하며, 별도 설치가 필요 없다.

**웹을 선택한 이유**: not4k는 무료 게임이다. 무료 게임의 핵심 과제는 진입 장벽 최소화이며, 웹은 "URL 클릭 → 즉시 플레이"라는 가장 낮은 진입 장벽을 제공한다. 설치 과정이 유저 이탈의 주요 원인이 되는 점을 감안하면, 웹이 최적의 배포 방식이다. 부수적으로 Windows/Mac/Linux를 동시에 지원하며, 업데이트 배포가 즉각적이다.

### 온라인 전용

**오프라인 플레이는 지원하지 않는다.** 차트·음원은 서버에서 불러와 재생 전에 준비하므로, 콘텐츠를 불러올 때 서버 연결이 필요하다.

**온라인 전용인 이유**: 차트·음원을 서버에서 관리해 제공하고, 로그인한 플레이어의 기록과 랭킹을 서버에 연동하기 위한 선택이다.

## 인증

### 소셜 로그인

**Google 소셜 로그인**을 제공한다. `[미구현 — 게임 클라이언트]` 에디터에서만 Google OAuth 구현.

**Google만 제공하는 이유**: 단일 제공자로 시작하여 구현 복잡도를 최소화한다. Google은 가장 범용적인 계정이며, 게임 유저 대부분이 보유하고 있다. 필요에 따라 추후 제공자를 추가할 수 있다.

### 첫 로그인의 닉네임 `[미구현]`

처음 로그인할 때 닉네임이 없으면 Guest 뒤에 6자리 숫자 난수를 공백 없이 붙인 이름을 기존 닉네임과 겹치지 않게 자동 생성한다. 닉네임 입력을 필수로 요구하지 않는다. 생성한 이름은 계정에 유지하며 이후 로그인에서는 기존 닉네임을 사용한다. 이후 사용자가 직접 변경할 수 있다. 입력 제약은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

### admin 권한

admin 권한은 Supabase Database의 `profiles` 테이블에서 `is_admin` 플래그(`boolean`, 기본값 `false`)로 관리한다. 클라이언트는 로그인 시 `profiles.is_admin`을 조회하여 admin 여부를 판단한다.

**현재 admin 부여 방식**: 별도의 admin 관리 UI는 없다. 개발자가 **Supabase 콘솔에서 직접** `profiles` 테이블의 `is_admin` 값을 변경한다.

**admin 권한의 영향 범위**:
- 곡 선택 화면: 비공개 곡 접근, Edit 버튼 표시
- 차트 에디터: 진입 가능 (admin이 아닌 유저는 에디터 접근 불가)

### 비로그인 플레이

**로그인 없이도 플레이할 수 있다.** 단, 비로그인 상태에서는 다음 기능이 제한된다:

- 플레이 기록 저장 불가(최고 점수·클리어·풀콤보 포함)
- 랭킹 등록 불가
- 계정 설정의 서버 동기화 불가(입력·시각 오프셋과 마스터 볼륨은 로그인 여부와 관계없이 기기별 로컬 저장)

**비로그인 플레이를 허용하는 이유**: 로그인 없이 먼저 게임을 플레이할 수 있게 하고, 기록을 저장하고 싶을 때 로그인하도록 한다. 기록 저장은 로그인한 플레이에만 제공하는 기존 방침을 유지한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

### 비로그인 유저의 로컬 설정 저장

**로그아웃 후 설정 유지**: 로그아웃한 뒤에도 직전에 사용하던 키 바인딩·스크롤 속도 등 게임 설정을 유지한다. 비로그인 상태에서 변경한 설정은 해당 브라우저에 저장한다. 다음 로그인 시에는 아래의 서버 설정 우선 동기화 규칙을 따른다([RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

비로그인 상태에서도 다음 설정은 **브라우저 localStorage에 저장**되어 재방문 시 유지된다:

- 키 바인딩 프리셋 및 커스텀 바인딩
- 스크롤 속도
- 입력/시각 오프셋
- 리프트/서든 설정
- 마스터 볼륨
- 스킨 선택 (`skinId`)
- 키봄 크기 (`bombScale`, 기본 1배)
- 선택한 언어

**localStorage를 사용하는 이유**: 플레이 기록의 저장 여부와 별개로, 재방문할 때 키 바인딩과 오프셋 등 설정을 유지하기 위해 브라우저에 저장한다.

### 계정 설정 동기화

계정 설정 동기화는 `[미구현]`이다. 설정 변경은 현재 브라우저에 먼저 적용하고 저장하며, 로그인 상태에서는 동기화 대상 설정을 서버에 저장한다. 서버 저장 성공을 현재 기기에서의 설정 적용 조건으로 두지 않는다([RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

로그인 시에는 선택창 없이 **서버 설정을 우선**한다. 서버에 설정이 없는 경우에만 동기화 대상인 로컬 설정을 업로드한다. 입력·시각 오프셋과 마스터 볼륨은 기기별 브라우저에 저장하며 서버 동기화에서 제외한다.

**동기화 실패의 공통 처리**: 서버에서 설정을 불러오거나 서버에 저장하는 데 실패해도 현재 브라우저의 설정과 로컬 변경값을 유지하며 게임 이용을 계속할 수 있다. 실패한 작업이 불러오기인지 저장인지 구분해 안내한다.

서버 설정 불러오기 실패를 로그인 실패로 처리하지 않는다. 불러오기 실패는 서버에 설정이 없는 경우와 구별하며, 서버 설정이 없다고 확인되지 않은 상태에서 로컬 설정을 업로드하지 않는다.

## 랭킹 `[미구현]`

### 차트별 랭킹

로그인한 플레이어의 완주 기록뿐 아니라 `flightRule`에 따라 곡 도중 실패로 종료된 기록도 점수 기록과 랭킹 반영 대상에 포함한다. 곡 도중 실패로 종료되면 그때까지 얻은 점수를 반영한다. 더 높은 점수라면 최고기록을 갱신하며, 해당 플레이의 클리어 여부는 점수와 별도로 판정한다. 기존에 달성한 클리어 기록은 유지한다. 플레이어가 직접 중단한 Quit·Retry 경로는 기록을 남기지 않는다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

**차트(곡 + 난이도) 단위로 점수 순위**를 제공한다. 로그인한 유저의 플레이 기록 중 최고 점수가 차트별 랭킹에 등록된다. Normal과 Easy 모두 차트별 랭킹을 제공하며, 두 판정 설정의 순위는 따로 집계한다. 각 설정에서 달성한 기록만 해당 설정의 랭킹에 반영한다([glossary](../context/glossary.md#랭킹), [RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

**차트별 랭킹을 선택한 이유**: 같은 차트의 점수를 비교하고 싶은 플레이어에게 해당 차트의 기록과 순위를 제공한다. 여러 차트의 기록을 집계하는 종합 실력 지표는 플레이어 풀이 쌓인 뒤 도입 필요성부터 검토한다. 미정 사항은 [PRD §12](../prd.md#12-미정-사항)를 따른다.

같은 점수에서는 해당 점수를 먼저 달성한 플레이어가 앞 순위에 오른다. 같은 점수를 다시 달성해도 그 점수의 최초 달성 시각을 유지한다.

랭킹도 차트 버전별로 분리해 새로 집계하며, 이전 버전의 기록을 수정된 버전의 순위에 반영하지 않는다. 노트 배치 수정뿐 아니라 곡 공통 BPM·음원 정렬 오프셋 수정으로 실제 입력 시각이 달라진 차트도 새 버전으로 분리한다([RFD 0095](../rfd/0095-song-shared-bpm-and-audio-offset.md)).

제목·아티스트·자켓 같은 곡의 표시 정보만 수정하면 기존 기록·달성 여부·랭킹을 유지하며, 기록용 차트 버전을 분리하지 않는다([RFD 0096](../rfd/0096-song-shared-display-metadata-and-records.md)).

삭제된 차트는 현재 랭킹에서 제외한다. 삭제 전 플레이와 미전송 결과는 원래 버전에 보관하며, 재등록된 차트의 기록·순위로 승계하지 않는다([RFD 0097](../rfd/0097-preserve-records-after-chart-deletion.md)).

### 랭킹 표시

랭킹에 표시할 플레이어 이름은 현재 닉네임으로 한다. 초기 닉네임은 자동 생성하며 사용자가 이후 변경할 수 있다([닉네임](../context/glossary.md#닉네임)). 사용자가 직접 변경하는 닉네임은 중복을 허용한다. 닉네임은 이후 변경할 수 있으며, 변경해도 해당 플레이어의 기존 기록과 순위를 유지한다. 닉네임을 변경하면 기존 랭킹에 표시되는 이름도 새 닉네임으로 바뀐다. 랭킹은 조회 시점의 현재 닉네임을 표시하며, 이미 열린 창에서는 기존 갱신 정책에 따라 다음 조회 때 반영한다. 닉네임이 같아도 플레이어별 기록과 순위는 구분한다.

랭킹은 창을 열 때 최신 기록을 불러오며, 같은 랭킹 창을 열어둔 동안에는 자동 갱신하지 않는다. 창을 닫았다 다시 열면 최신 기록을 다시 불러온다. 랭킹을 불러오지 못하면 랭킹 창 안에 오류 안내와 재시도 버튼을 표시한다. 재시도 버튼을 누르면 현재 대상의 랭킹 조회를 다시 시도한다.

랭킹의 기록 수치는 점수만 표시하며 달성률은 표시하지 않는다.

랭킹에는 같은 차트 버전·판정 설정에서 최고 점수와 독립적으로 보존한 풀콤보·올퍼펙트 달성 배지를 표시한다. 미러 사용 여부는 같은 기록으로 합친다. 올퍼펙트를 달성했으면 풀콤보 대신 올퍼펙트 배지만 표시하며, 일반 성공·실패는 표시하지 않는다. 배지는 최고 점수를 낸 특정 플레이의 상태로 제한하지 않는다. 100점 풀콤보 뒤 110점 실패를 기록하면 랭킹에는 110점과 풀콤보 배지를 함께 표시한다. 같은 점수로 올퍼펙트를 새로 달성해도 배지를 갱신하며, 해당 점수의 최초 달성 시각과 동점 순서는 바꾸지 않고 최고 점수 갱신 안내도 표시하지 않는다. 배지의 유무·종류는 점수 순위와 동점 순서에 영향을 주지 않는다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

현재 차트 버전의 새 기록만 표시한다. 이전 버전 랭킹의 조회 화면은 이번 출시 전 설계 범위에서 제외한다.

곡 선택 화면에서 **랭킹 모달**을 열어 차트별 상위 기록과 자신의 순위를 확인할 수 있다. 본인의 기록이 상위 목록 밖에 있더라도 내 순위와 점수는 별도로 표시한다. 곡 선택 화면 자체에 랭킹이 직접 표시되지는 않으며, 유저가 원할 때 모달로 접근한다.

## 새 모델의 입력과 바디 진행

**채택 계약·일반 기본 경로 구현·검증(명시 테스트 재생 #346, 일반 곡 재생 #347).** 정식 정의는 [glossary의 바디 판정과 실패 종속](../context/glossary.md#바디-판정과-실패-종속), 승인 근거는 [RFD 0037 §2～5](../rfd/0037-explicit-score-notes-and-body.md#2-구성과-점수-의미)를 따른다.

탭 노트는 가장 이른 적격 down을, 명시 릴리즈는 가장 이른 적격 up 하나를 소비한다. 바디·틱 노트는 down/up을 소비하지 않는다. 같은 down이 탭을 처리하면서 실제 hold로 바디 조건도 충족할 수 있다. 탭 노트를 친 up·교대 up을 숨은 연결 release로 먼저 소비하지 않는다. 창 안의 적격 up이 뒤 명시 릴리즈를 일찍 처리할 수 있으며 배치 의도는 제작 지침에서 확인한다.

시작 창 전부터 누른 키는 창이 열릴 때 조기 시작시키지 않고 차트상 시작에서 확인한다. 시작 창 안의 유효한 새 down은 그 입력 시각부터 충족하는 몫을 시작한다. head 없는 독립 single·double과 1→2 추가 몫에도 적용한다. 정상 유지한 앞 키가 이어지면 짧은 뒤 바디도 자기 차트상 시작에 시작하며 시작 탭 미처리 때문에 이를 취소하지 않는다([ENJ-01～04·14](explicit-note-judgment-cases.md#enj-01)).

탭 담당 몫의 유지 실패 대기와 유효한 실제 탭 down 기준은 RFD 0032 §4-3·§5-2～5-4의 충돌하지 않는 기존 계약을 보존한다. double 탭으로 시작하는 single 바디는 두 탭 몫 중 먼저 성공한 down에 시작하며, 탭의 모든 몫이 Miss일 때만 탭 Miss로 실패한다(사용자 결정, 2026-10-26, [RFD 0037 §3-1](../rfd/0037-explicit-score-notes-and-body.md#3-1-시작-시각과-유지)). 건강한 승계의 차트상 시작을 확인한 결정으로 이 대기를 제거하거나, 뒤 탭 입력으로 이미 확정한 실패·정상 완료를 되돌리지 않는다.

바디에 붙은 릴리즈와 이른 정상 종료에는 실제 시작이 전제다. 이미 시작한 바디는 끝의 Good 이른 폭에서 정상 완료할 수 있고, 릴리즈 없는 끝은 up을 소비하지 않는다. 정상 유지하면 차트상 끝에 무점수 완료하며 명시 릴리즈만 남은 늦은 창까지 실제 up을 기다린다. 끝 뒤에도 시작 창이 남은 single의 유효한 첫 down은 실제 시작 → 즉시 유지 완료 → 명시 릴리즈 대기다. 미시작을 끝 시각만으로 완료하거나 실제 시작 뒤 새 유지 시간을 더하지 않는다([ENJ-03·04·09·18](explicit-note-judgment-cases.md#enj-18)).

실제 바디 경계·정상 분리 연주의 앞 끝/뒤 시작 창을 보존한다. 같은 hold 수의 탭·릴리즈 없는 연결은 배치 금지라 실행 차트에 오지 않는다. 이 금지에서 빠지는 트릴 바디와 같은 hold 수 일반 바디의 탭·릴리즈 없는 경계(두 방향)도 판정 대상 배치가 생기지 않는다. 메인 레인에서는 `trillExclusive`가 트릴 → 일반 접점을 막고 `trillLongInvalid`가 트릴 바디에 시작 트릴 탭을 요구하며, 보조 레인은 판정하지 않기 때문이다([RFD 0037 §6-1](../rfd/0037-explicit-score-notes-and-body.md#6-1-배치와-소속), 2026-10-27·2026-10-28). 탭 없는 1→2는 앞 탈락과 별개로 뒤 두 몫의 새 시작을 허용한다. 탭 없는 2→1은 건강한 몫을 이어주고, 두 몫 모두 탈락했어도 뒤 single이 자기 조건으로 새로 시작할 수 있다(2026-10-27). 바디 사이에는 실패를 전파하지 않는다. 릴리즈가 있는 1→1·릴리즈 하나인 2→2와 single 탭이 있는 2→2의 새 시작 범위는 [RFD 0037 §4](../rfd/0037-explicit-score-notes-and-body.md#4-경계실패-종속)를 따른다. 탭 수·릴리즈 수를 뒤 시작 가능 몫 수로 사용하지 않는다.

같은 더블 릴리즈의 두 항목은 서로 다른 물리 키를 요구하되, 같은 키 재누름이 해당 바디의 시작 탭을 실제 처리했다면 그 누름의 up은 남은 항목을 처리할 수 있다. single 바디에 붙은 double 릴리즈에도 적용한다. 임의 재누름·다른 탭으로 확대하거나 double 바디의 두 유지 몫을 한 키로 채우지 않는다([ENJ-15](explicit-note-judgment-cases.md#enj-15)).

같은 raw 시각 up은 가능한 적격 배정을 함께 확인해 키 수신 순서 때문에 처리 가능한 항목을 놓치지 않는다. 서로 다른 raw 시각 순서·같은 키 down/up 인과관계·확정 판정 불번복은 유지한다. 같은 시각 입력을 반영한 뒤 유지 부족을 판단하며 유지 유예와 head 없는 시작 직후의 기존 재충전은 보존한다. 탭이 있는 double의 비담당 몫에 시작 창 끝까지 재충전을 넓히지 않는다. 유지 유예 20ms는 사례의 임시 설정이며 최종 튜닝 값은 아니다.

### 점수·확정 효과와 표시 수명

바디 진행, 명시 점수 항목의 정산, 화면 잔존은 별개 상태다. 바디는 항목·가중치 0이고 탭·릴리즈·틱 노트만 요구 한 몫당 가중치 3의 항목을 만든다. 미처리 종속 항목은 원래 가중치의 0점으로 한 번 정산하고 원인 실패 외에 추가 Miss·콤보 단절·고도 손실을 만들지 않는다. 실패색과 화면 잔존은 입력 기회나 효과를 다시 여는 신호가 아니다.

틱 노트에는 자체 창·독립 기한·선판정이 없다. 틱 시각의 정상 유지, 시작/회복 결과 대기와 유효한 이른 종료의 미처리 틱 일괄 Perfect를 따른다. 성공은 틱당 Perfect 3점·콤보 +1·일반 Perfect 고도 기여·Perfect 글자·해당 레인의 일반 타격 이펙트다. 타이밍 오차·FAST/SLOW는 없으며 미확정 상태·종속 0점·상태 재조회에 새 성공 효과를 만들지 않는다. 일반 릴리즈가 Good이어도 틱 노트 성공은 Perfect다.

같은 확정 시각의 대표 판정 글자는 가장 낮은 등급이다. 그 등급 안에서 표시 가능한 타이밍을 가진 실제 입력을 우선하고 여러 개면 raw 오차 절대값이 가장 큰 입력을 사용한다. 종속 0점은 후보가 아니며 틱·Grace의 오차를 새로 만들거나 다른 등급에서 빌리지 않는다. 표시 임계값·설정·항목별 통계를 보존하고, 서로 다른 확정 시각을 프레임이나 별도 폭으로 묶지 않는다. 후보 수신·호출 순서로 대표 글자가 바뀌지 않아야 한다.

| 대상·상태 | 새 모델의 표시 계약 |
| --- | --- |
| 정상 완료 바디 | 이른 종료·연결 여부와 관계없이 즉시 숨김. 명시 릴리즈 대기는 별도 유지 |
| 더블 한 몫 정상 완료 | 전체 바디 alpha 0.7, 모두 정상 완료하면 숨김. 릴리즈 성공 수로 추정하지 않음 |
| 실패 바디·릴리즈 | 실패색으로 원래 차트 위치에서 스크롤되어 화면 밖까지 남김. 더블 바디는 모든 몫이 실패했을 때 이 상태다 |
| 더블 일부 실패·일부 성공 | 실패한 절반만 실패색, 일부 성공은 전체 alpha 0.7로 별도 합성. 혼합 상태도 부분 실패 도안 전체 alpha 0.7 |

| 놓친 탭 노트 | 싱글도 더블처럼 실패 도안으로 그림 (사용자 결정 2026-10-29) |
| 틱 노트 | 성공한 틱만 즉시 숨김. 남은 틱은 원래 위치·크기·밝기, 종속 0점 확정 틱은 즉시 실패색 |

기존 스킨·타격 설정과 판정선·리프트 배치를 따른다. 더블 틱 노트는 틱 개수로 요구 수를 표현하므로 전체 alpha 0.7 규칙의 예외다. 구체적인 근거는 [RFD 0037 §7](../rfd/0037-explicit-score-notes-and-body.md#7-표시와-확정-효과), 정산은 [스코어링](scoring.md#명시적-점수-항목과-정산), 설계 기대값은 [새 판정 사례](explicit-note-judgment-cases.md)를 따른다.

### AutoPlayer·튜토리얼과 입력 수명

새 모델의 `AutoPlayer`는 바디의 hold 요구와 명시 탭·릴리즈를 함께 만족하는 합법적인 합성 down/up을 만든다. 틱 노트 전용 타이밍 입력이나 바디에서 자동 생성한 끝 점수를 만들지 않는다. Grace 릴리즈에도 실제 up을 만들고, 릴리즈 없는 끝을 별도 뗌 필수 요구로 바꾸지 않는다. 바디 hold 수와 릴리즈 수가 달라도 각각의 요구 수를 보존하며 double·연결·겹치는 창에서 같은 판정 세션으로 검증한다.

실제 키보드·합성 입력은 raw 시각과 키별 down/up 인과관계, 같은 raw 시각의 개별 입력 참조를 보존해 공통 세션으로 전달한다. 입력 오프셋은 한 번만 적용한다. 현재 상태 snapshot과 한 번 실행할 확정 효과를 분리하고 어댑터·렌더러가 판정을 재구현하지 않는다.

튜토리얼·Lab 예제와 도움말의 새 설명도 같은 판정·정산·효과 경로를 사용하며 명시 항목 수·분모·릴리즈 요구를 드러내야 한다. 반복 경계의 마지막 입력은 이전 세션에서 처리하고, 다음 반복은 같은 원본 참조라도 새 판정·표시 인스턴스를 사용한다. 이전 세션의 늦은 입력·타격·글자·정산 효과를 다음 반복에 붙이거나 재조회로 재실행하지 않는다. 이 문서 반영만으로 현행 튜토리얼 차트나 예제가 전환됐다고 보지 않는다.

중간 재생은 [RFD 0040](../rfd/0040-countdown-and-note-reentry.md)의 고정 3초 되감기·이후 상태 복원·음악 준비를 따른다. 새 테스트의 커서 앞 항목은 Miss 없이 제외하며 원본을 보존한다. 일반 첫 재생·Retry는 음악 준비 없이 즉시 시작한다. 구형·신형 혼합 차트는 에디터에서 수리·저장을 이어갈 수 있지만 새 실행에서는 구형 의미가 남은 차트를 차단한다. #347 머지 뒤 일반 곡 선택은 명시 판정만 실행하므로 구형 게임 노트가 남은 차트는 다시 제작하기 전까지 곡 선택에서 플레이할 수 없다(미출시라 감수한 공백, 사용자 결정 2026-10-26, 운영 차트 현황은 [PRD §12](../prd.md#12-미정-사항)). 기존 튜토리얼 목록 개편은 이번 전환에서 제외한 후속 작업이며 [PRD §12](../prd.md#12-미정-사항)에서 추적한다. 일반 곡 선택(#347)과 에디터/Lab의 명시 테스트 재생(#346)에 이 계약을 적용했다.

## 입력-노트 매칭

아래는 과도기 구형 입력-노트 매칭과 당시 결정 이유다. 등록 키·시작 down 소비·연결 보정·`holdOnly`는 새 모델의 입력 계약으로 적용하지 않는다. 현행 코드·구형 읽기/편집 의미·기존 사례 결과를 보존하며 새 계약은 [앞 절](#새-모델의-입력과-바디-진행)을 따른다.

### 매칭 규칙

유저가 키를 누르면, 해당 레인에서 **가장 이른(earliest) 노트**에 매칭된다. Good 판정 창(Normal ±120ms, Easy ±150ms) 안에 복수의 노트가 존재하면, 시간순으로 가장 앞에 있는 노트가 입력을 `consume`한다.

**가장 이른 노트 매칭을 선택한 이유**: "가장 가까운 노트" 매칭은 이른 입력이 뒤의 노트에 `consume`되어 앞의 노트가 Miss 처리되는 직관적이지 않은 상황을 만든다. 가장 이른 노트 매칭은 노트의 판정 순서가 항상 배치 순서와 일치하므로, 유저가 결과를 예측하기 쉽다. osu!mania 등 대부분의 리듬게임이 이 방식을 사용한다.

### 헤드 없는 롱노트의 keydown `consume`

양수 바디의 실제 미처리 시작은 S±Good 안의 down을 소비하되 시작 점수는 없다. 자기 head가 담당하는 unit은 그 head 입력으로 시작하고, single head + double 바디의 남은 unit은 자기 시작 down 또는 정당한 승계가 필요하다.

이미 정당한 승계로 준비한 unit은 S 전에도 불필요한 down을 가져가지 않는다. 임의의 raw held와 다른 독립 Point가 소비한 down은 시작을 대신하지 않는다. 길이 0 일반 release도 시작 준비를 요구하지만, 길이 0 `holdOnly`는 기존 held 상태를 공유하며 down을 소비하지 않는다. 입력 사례는 [NJ-A01～A06 및 NJ-Z01](note-judgment-cases.md#nj-a01)을 따른다.

### keyup 소비 (약칭 R2 — 가장 이른 매칭)

keydown은 적격한 Point·head·미처리 시작 unit 중 가장 이른 대상을 소비한다. keyup은 누름별 release 권한과 정적 score item의 대상 unit을 따라 실제 release 하나만 소비한다. release는 Perfect/Great/Good/Miss로 판정하며, `holdOnly` 완료는 keyup 소비와 분리한다. Beat가 정확히 맞닿은 connection의 계속되는 몫은 무점수 승계이며, 줄어드는 몫은 실제 release 또는 명시된 holdOnly로 처리한다. 고정 물리 owner를 두지 않고 등록된 유지 키와 누름별 권한을 추적한다. 실패한 unit은 부활하지 않고 다른 unit에 전파하지 않는다.

### 빈 레인 입력

시각적으로 비어 보이는 레인에서 키를 눌렀다고 임의의 Bad를 생성하지 않는다. 적격한 Point·head·시작 대상이 없으면 입력은 소비하지 않는다.

입력 소비는 차트의 적격 대상과 score item을 기준으로 하며, 차트에 없는 Bad 패널티를 추가하지 않는다.

## 노트 스킨

곡 선택 화면의 `Settings → Skin`에서 **Classic**을 선택한다. 기본값은 Classic이며 선택한 `skinId`는 localStorage에 저장되어 다음 플레이와 재방문에 적용된다. Crystal은 완성도가 낮아 개발 중으로 돌려 숨기고, Prism·Simple·Note Asset Lab도 인게임 선택지에서 숨긴다. 숨긴 스킨도 매니페스트와 에셋은 남아 있어 개발용 스킨 선택과 테스트에서 불러올 수 있다. 곡 선택의 튜토리얼 재생기도 기본 스킨인 Classic으로 재생한다.

Classic은 현재 적용본 v014(흰빛 포인트, 세로 트렌치 바디, 포인트 접촉 그림자, 석영 트릴 포인트와 반투명 사각 기둥 트릴 켜짐 바디, 에디터와 같은 회색 마름모 트릴 끝 터미널)와 Grace, 16프레임 실버 봄을 사용한다. 실제 플레이와 Lab 시연은 같은 `/skins/classic/` PNG를 읽는다. 시연 페이지와 SVG 자료는 개발 빌드에만 포함하지만, 이 런타임 PNG는 프로덕션 빌드에도 포함한다. 디자인 규격과 제작 방법은 [노트 에셋 Lab 명세](note-asset-lab.md)를 따른다.

같은 `Skin` 설정의 `Key Bomb Size`에서 인게임 키봄 크기를 **0～3배**, **0.1배** 단위로 조절한다. 기본값 1배는 75×75 논리 픽셀(레인 100 기준 설계값 120 × 플레이필드 배율 0.625, [RFD 0029](../rfd/0029-frame-aspect-fit-narrow-lanes.md))이며, 3배는 225×225다. 레인 중앙·판정선을 중심으로 가로·세로를 같은 배율로 바꾸고 재생 시간은 유지한다. 0배는 키봄을 생성하지 않으며 판정·점수에는 영향을 주지 않는다. 값은 모든 스킨에 공통 적용하고 localStorage에 저장한다. 이 값이 없는 기존 설정은 1배로 복원한다.

## 곡의 BPM·음원 정렬 오프셋 `[미구현]`

같은 곡의 모든 차트는 초기 BPM·곡 중간의 BPM 변경 목록·박자표·변박 정보·음원 정렬용 오프셋을 공유한다. 노트의 박 좌표를 실제 시간으로 해석할 때 동일한 곡 타이밍을 사용한다. 기기별 입력·시각 오프셋과 플레이어의 스크롤 속도는 별도 설정이다([곡 타이밍](../context/glossary.md#곡-타이밍), [RFD 0095](../rfd/0095-song-shared-bpm-and-audio-offset.md)).

현재 구현은 차트별 메타데이터·이벤트에서 시간 기준을 읽으며 곡 단위 공유는 후속 구현이다. 공통 타이밍 수정으로 실제 입력 시각이 달라지면 영향을 받는 각 차트의 기록과 랭킹을 새 버전으로 분리한다.

## 스크롤 속도

### BPM 독립 절대 속도

스크롤 속도(노트 낙하 속도)는 **BPM과 무관한 절대 속도**이며, 유저가 자유롭게 조절할 수 있다. 범위 **1.0～8.0**, 기본값 **4.0**, 소수점 아래 1자리까지 표시.

- 곡의 BPM이 변해도 스크롤 속도는 일정하다.
- BPM 변화 구간에서 노트 간격이 변하지 않으므로, 유저의 읽기 리듬이 깨지지 않는다.

**BPM 독립 속도를 선택한 이유**: BPM 연동 속도(IIDX의 Hi-Speed)는 BPM이 변하는 곡에서 소프란(soflan) 현상을 만든다. 유저가 BPM 변화 구간을 암기해야 하며, 이것은 리듬 감각이 아닌 암기력을 테스트하는 요소다. not4k는 가변 손배치와 차트 인식이라는 핵심 인지 부하에 집중해야 하므로, 스크롤 속도를 BPM에서 분리하여 불필요한 인지 부하를 제거한다. osu!mania, Arcaea 등 최근 리듬게임은 대부분 이 방식을 채택하고 있다.

## 프레임레이트

**렌더링 프레임레이트의 상한(cap)을 유저가 선택**할 수 있다. 선택지: **60fps / 120fps / 144fps / 무제한(Uncapped)**.

- 기본값은 60fps. 유저가 설정 화면에서 변경할 수 있다.
- 판정 로직은 프레임레이트에 의존하지 않는다. 입력 타이밍은 `KeyboardEvent.timeStamp` 기반이고, 오디오 동기화는 AudioContext 마스터 클럭 기반이므로 프레임레이트가 판정 정확도에 영향을 주지 않는다.

### 구현 원리

`requestAnimationFrame`(rAF)은 브라우저가 모니터 주사율에 맞춰 호출하며, 호출 주기 자체를 변경할 수 없다. 프레임레이트 캡은 **rAF 콜백 내에서 목표 간격 미달 시 렌더링을 스킵**하는 방식으로 구현한다. 예: 144Hz 모니터에서 60fps 캡을 설정하면 rAF는 144회/초 호출되지만 렌더링은 약 60회/초만 실행된다. 무제한 설정 시 매 rAF마다 렌더링한다.

이 설정은 프레임레이트를 "보장"하는 것이 아니라 **상한을 제한**하는 것이다. 실제 프레임레이트는 모니터 주사율, GPU 성능, 브라우저 상태에 의존한다. 다만 2D 노트 렌더링의 GPU 부하가 극히 낮으므로, 일반적인 하드웨어에서 60fps 유지는 사실상 보장 가능한 수준이다.

**유저 선택으로 제공하는 이유**: 고주사율 모니터(120Hz, 144Hz) 유저는 높은 프레임레이트에서 더 부드러운 노트 낙하를 경험할 수 있다. 반면 저사양 환경에서는 높은 프레임레이트가 프레임 드롭을 유발할 수 있으므로, 하드웨어에 맞는 설정을 유저가 직접 선택하도록 한다.

## 마스터 볼륨 (Master Volume)

게임 전체의 오디오 출력 볼륨을 조절하는 설정. 범위 **0～100%**, 기본값 **100%**. 내부적으로 0.0～1.0 값으로 저장된다.

- **적용 범위**: 게임 플레이 음원, 에디터 재생 음원, 곡 선택 화면 프리뷰 음원 등 모든 오디오 출력에 적용된다.
- **설정 모달**: 곡 선택 화면에서 여는 설정 모달의 Gameplay 섹션에서 슬라이더로 조절한다.
- **에디터 접근**: 에디터 툴바의 Settings 버튼을 통해 마스터 볼륨 슬라이더가 포함된 팝오버를 열어 조절할 수 있다. 에디터에는 별도의 볼륨 슬라이더를 두지 않고, 마스터 볼륨으로 통합한다.
- **저장**: 기기별 브라우저의 localStorage에 저장되어 재방문 시 유지된다. 계정 설정 동기화에서 제외하며, 로그인해도 해당 기기의 볼륨을 유지한다([glossary](../context/glossary.md#마스터-볼륨-master-volume), [RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

**단일 마스터 볼륨으로 통합하는 이유**: 게임·에디터·프리뷰 각각에 별도의 볼륨 설정을 두면, 유저가 컨텍스트를 전환할 때마다 볼륨을 재조정해야 한다. 단일 마스터 볼륨으로 통합하면 한 곳에서 조절한 값이 모든 오디오에 일관되게 적용된다.

## 리프트 / 서든 (Lift / Sudden)

시각 정보를 의도적으로 차단하여 집중력을 높이기 위한 플레이 설정.

서든과 리프트는 둘 다 레인 위끝～리프트 0% 판정선 높이를 100%로 쓴다. 레인 위끝(y 0)부터 리프트 0% 판정선(y 426)까지라 이 높이는 426이고, 1%는 4.26 논리 단위다. IIDX의 흰숫이 이 높이를 1000으로 놓고 위쪽 서든+와 아래쪽 리프트를 같은 기준으로 재는 방식과 같아, 위쪽·아래쪽 흰숫은 각 %의 10배이고 흔히 말하는 합계 흰숫은 (서든 + 리프트) %의 10배다([glossary](../context/glossary.md#흰숫-white-number)). 노트가 보이는 레인 높이는 426 × (100 − 서든 − 리프트)%이고, 둘을 더해 100%면 노트가 보이지 않는다([#291](https://github.com/nanana3679/not4k/issues/291), 2026-10-18).

- **화면 높이(600)를 기준으로 하지 않는다.** 노트가 보이는 레인은 426이라, 화면 높이 기준이면 서든 30%가 레인의 약 42%를 가려 설정 숫자가 실제로 가려지는 비율과 어긋난다.
- **판정선 아래 틈(레인 끝인 키 윗면 y 456.5까지)은 기준에 넣지 않는다.** 판정선을 지난 노트가 지나가는 곳이라, 넣으면 서든 100%가 판정선 아래까지 덮고 리프트는 100%가 되기 전(약 93.3%)에 판정선이 레인 위끝에 닿는다.

### 서든 (Sudden) `[부분 구현 — 설정값만 저장, 마스크 렌더링 미구현]`

레인 상단을 커버로 가려, 노트가 화면에 보이는 시간을 줄인다. 유효 시야(Effective Field of View)를 제한함으로써 뇌가 처리해야 할 정보량을 줄이고, 역설적으로 처리 효율을 높인다.

커버는 레인 위끝에서 서든 %만큼 내려온다. 1%는 레인 위끝～리프트 0% 판정선 높이의 1%인 4.26 논리 단위라 서든 30%면 커버 높이는 127.8이고, 100%면 리프트 0% 판정선까지 가린다.

### 리프트 (Lift)

판정선의 위치를 기본 위치에서 위로 올린다. 노트의 이동 거리가 짧아지므로, 유저의 시선이 화면 하단에 고정되지 않고 보다 자연스러운 위치에서 노트를 읽을 수 있다.

리프트 0%의 기본 판정선은 논리 높이 600 화면의 y 426(아래에서 174)이다. 처음 정한 y 416(아래에서 184)에서 기어와 함께 10 내린 위치로([#257](https://github.com/nanana3679/not4k/issues/257)), 기어 덱 위끝(y 439.7)보다 노트 두께 약 1배 위다. 설정은 0～100%이고 1%는 레인 위끝～리프트 0% 판정선 높이의 1%인 4.26 논리 단위다(리프트 20%면 85.2 올라 y 340.8, 100%면 판정선이 레인 위끝 y 0). 리프트는 판정선과 판정선에 딸린 표시(노트 판정 위치·판정 글자·콤보와 정확도 글자·키봄)만 올리고, 기어와 레인 끝(키 윗면)은 움직이지 않는다([RFD 0029](../rfd/0029-frame-aspect-fit-narrow-lanes.md)). 그래서 리프트를 올릴수록 판정선 아래로 노트가 보이는 틈이 커진다. 리프트 상한과 큰 리프트의 처리는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### 조합 사용

서든과 리프트를 함께 사용하면, 화면 중앙의 좁은 영역에서만 노트가 보이게 된다. 상급 플레이어는 이 조합을 통해 시선의 초점 범위를 극도로 좁혀 집중력을 극대화한다. IIDX에서 Sudden+와 Lift를 병용하는 것과 동일한 원리다.

## 오프셋

입력·시각 오프셋은 해당 기기의 브라우저에 로컬 설정으로 저장하고 계정 설정 동기화에서 제외한다. 로그인 여부와 관계없이 해당 기기의 값을 유지한다([RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

입력·시각 오프셋은 숫자 입력 확정과 저장 설정 병합 때 모두 실제 시간 −1000～+1000ms로 제한한다. 유효하지 않거나 유한하지 않은 숫자는 기본 0ms로 둔다.

### 입력 오프셋 (Input Offset)

`inputOffsetMs`는 입력 장치 지연과 개인 체감을 보정하는 실제 시간 ms(기본 0)다. 입력 시간은 `J − handlerDelay·r + inputOffsetMs·r`이며 SLOW가 많으면 음수, FAST가 많으면 양수로 조절한다. 판정 시간과 노트 위치에는 적용하지 않는다.

### 시각 오프셋 (Visual Offset)

`visualOffsetMs`는 화면 표시 지연을 보정하는 실제 시간 ms(기본 0)다. 시각 시간 `V = J + visualOffsetMs·r`로 노트·마디선·구간을 그린다. 화면이 소리보다 늦게 보이면 양수로 노트를 앞당겨 그린다. 입력 시간과 판정에는 적용하지 않는다.

### 오디오 레이턴시와 두 오프셋을 나눈 이유

판정 시간은 `J = P − L₀·r`로 지금 들리는 곡 위치를 나타낸다. P는 `AudioEngine.currentTimeMs`, r은 실제 재생 배속이다. 출력 지연 L₀는 재생 전 로딩 중 running `AudioContext`의 `baseLatency + outputLatency`를 잠시 관측해 한 번 확정한다. 미지원 `outputLatency`는 0이며, 일시정지·재개 동안 유지하고 Retry·다음 곡에서 다시 읽는다. [읽기 절차와 계산식](audio-visual-sync.md#보정-설계)을 따른다.

출력 지연은 L₀가 자동 보정하고, 입력 지연·체감과 화면 표시 지연은 서로 독립적인 두 오프셋이 맡는다. Audio Offset은 제거했다. 옛 설정 키 `audioOffsetMs`·`judgmentOffsetMs`·`offsetMs`는 로드할 때 버리고 이전하지 않는다. 차트의 `offsetMs`는 음원 자체와 차트 정렬을 위한 별개 값으로 유지한다.

### 오프셋 조절과 캘리브레이션

설정 모달 Gameplay > Audio에서 `Input Offset`·`Visual Offset`을 숫자 입력(ms)으로 조절한다. `Calibrate…` 진입은 숨겨 두었다. [RFD 0031](../rfd/0031-audio-first-timing-model.md) PR 2에서 소리에 맞춘 탭 기반 입력 캘리브레이션을, PR 3에서 비프와 떨어지는 노트를 보고 맞추는 시각 캘리브레이션을 구현한다.

## `flightRule` (`altitude` 게이지) `[미구현 — 난이도별 비행 배경·새 기어 고도 게이지·임시 `altitude` 모델 구현, 클리어/실패 규칙 미구현]`

Play에는 **`altitude`** 기반 클리어/실패를 결정하는 **`flightRule`**이 적용된다. 초기 스펙의 "게이지 없음, 무조건 완주, 게임 오버 없음" 결정은 RFD 0001로 대체되었다.

**`altitude` 시각화 (기어 게이지)**: 새 기어 양옆 유리관 게이지가 플레이 중 `altitude` 값(0～1)을 아래 기준 채움으로 보여 준다. 두 유리관은 같은 값이다. 채움 방식은 [고도 게이지 시연](../design/classic-frame-keywords-20260929.md#게이지-채움-조절)(`press-animation.html`)과 같다. 기어 그림의 가득 찬 유리관 위에 생성한 빈 유리를 유리 안쪽 윤곽(경계 2px)으로 잘라, 위에서부터 채움 경계까지 덮는다. 채움 구간은 유리 안쪽 821행이고, 경계는 8행에 걸쳐 부드럽게 옅어진다. 채움 1은 그림 그대로, 0은 두 유리관이 모두 빈 유리다. 값이 바뀌면 표시는 약 300ms ease-out 느낌으로 따라간다(시간 상수 75ms의 지수 접근). 이징은 렌더 프레임 간격 `deltaMs`(최대 50ms)로만 나아가 일시정지 중에는 멈춘다. `setChart` 때와 warm-up(`prepareForPlayback`)의 첫 프레임(곡 중간에서 시작하는 시험 재생 포함)에는 이징 없이 바로 맞춘다. 그 밖에는 운영체제의 모션 감소 설정(`prefers-reduced-motion`, macOS·iOS '동작 줄이기', Android '애니메이션 삭제', Windows 11 '애니메이션 효과')과 관계없이 늘 이징한다([RFD 0030](../rfd/0030-ignore-os-reduced-motion.md)). 빈 유리 텍스처는 [곡 시작 전 준비](#플레이-화면-배치)에서 GPU 업로드해, 덮개가 곡 중 처음 나타나는 프레임에 GPU 업로드가 몰리지 않게 한다. 낮은 고도에서도 칠한 청록색을 바꾸지 않고 경고 표시를 더하지 않는다. 게이지는 `gearMotion`(기어 위 장식 애니메이션: 광원 띠·게이지 액체 흐름과 기포·발광선·하단 바 빛)보다 위에 겹쳐, `gearMotion`을 켜면 액체·기포가 채운 부분에서만 흐른다. `gearMotion`을 꺼도 게이지는 같다. 옛 기어의 분리 기둥 게이지는 옛 기어와 함께 지웠다([RFD 0029](../rfd/0029-frame-aspect-fit-narrow-lanes.md)). `flightRule`이 구현되기 전까지 고도는 배경 연출과 동일한 임시 `altitude` 모델(곡 진행에 따라 1→0, MISS·BAD로 즉시 하강, 그 밖의 판정으로 서서히 회복)로 구동된다.

**도입 이유**: 첫째, 비행이라는 가벼운 내러티브를 게임 규칙과 연결하기 위해서다. `altitude`에 따라 배경 연출(지평선, 광원, 시야각)이 변하는 비행 콘셉트는, `altitude`가 장식이 아니라 실제 클리어/실패와 연결될 때 의미를 가진다. 둘째, 리듬게임에 익숙하지 않은 유저에게 클리어/실패라는 목표 구조와 동기를 제공하기 위해서다(RFD 0003).

**난이도명·시나리오**: `Liftoff → Infiltration → Breakthrough` 순서로 한 곡 안의 차트를 구분하며, 각 단계의 비행 시나리오와 연결한다([RFD 0022](../rfd/0022-flight-difficulty-names-and-visuals.md)). 이름 표시와 공개 시연 배경을 실제 게임에 연결했다([RFD 0026](../rfd/0026-game-flight-backgrounds.md)). 클리어/실패 규칙은 미구현이다. 풀 정의는 [glossary](../context/glossary.md#flightrule-flight-rule)를 따른다.

**단계별 연출**: `Liftoff`는 시선 각도를 유지하며 고도가 변한다. `Infiltration`은 낮아질수록 시선이 지면을 향해 회전하고 지평선이 위로 사라진다. `Breakthrough`는 낮은 고도에서 전방을 보며 계속 비행한다. `Breakthrough`의 낮은 시각 고도는 정상적인 숙련 비행이며, 실패 직전 상태로 일괄 해석하지 않는다. 중앙 레인·판정선·노트 속도는 배경 연출의 영향을 받지 않는다.

**시각적 구별**: 난이도별 색상 배합과 광원 밀도에 차이를 둔다. `Breakthrough`는 지평선 없이 화면 맨 위까지 광원이 움직이며 지나가도록 구성한다. 돌파의 주홍 후보는 사용자가 수용했으며, 다른 후보 배합과 광원 분포 제안은 [아트 디렉션 기록](../design/art-direction-notes.md#난이도별-색상과-광원-분포)을 따른다. 실제 게임에는 공개 시연의 현재 배색·광원 밀도를 사용한다. `Liftoff`는 속도300%, `Infiltration`은600%, `Breakthrough`는1000%이며 돌파의 건축 배경은 밝기10%·재귀 확대300%다. 세부 튜닝은 계속 가능하다.

**비행 배경 움직임 설정 `[미구현]`**: 비행 배경의 움직임은 기어 모션과 별도의 게임 내 설정으로 끌 수 있게 한다. 설정의 기본값은 켬이며, 일반 플레이와 옵저버가 같은 설정을 사용한다. 끄면 어두운 고정 배경으로 바꾸고, 노트·기어·고도 게이지는 그대로 표시한다. 이 설정으로 노트 진행·입력 판정·고도 계산을 멈추지 않는다. 기어 모션은 기존 `Gear Motion` 설정을 독립적으로 따른다. 운영체제의 모션 감소 설정을 자동으로 따르지 않는 원칙은 유지한다([비행 배경](../context/glossary.md#비행-배경), [RFD 0100](../rfd/0100-flight-background-motion-setting.md)).

**게임 배경 수명**: 기존 격자 배경을 공개 시연의 세 배경으로 교체했으며 이전 프리셋·시연·저장 API는 제거했다. 고도 모델은 `flightAltitude`, 배경 표시 옵션은 `showFlightBackground`로 관리한다. 렌더러가 프레임마다 고도를 한 번 계산해 비행 배경과 새 기어 게이지에 같은 값을 준다. 배경을 끈 렌더러에서도 기어 게이지는 이 값을 따르고, 둘 다 없는 렌더러(튜토리얼 재생기)는 고도를 계산하지 않는다. 곡 진행·판정에 따른 기존 임시 고도 모델을 유지하며, 돌파 직선은 고도1에서 좌우 하단→중앙 상단, 고도0에서 좌우 상단→중앙 하단을 향한다. 배경 시간은 게임 프레임만 진행시키고 일시정지·숨긴 탭에서는 전진하지 않는다. 운영체제의 `prefers-reduced-motion`은 읽지 않는다([RFD 0030](../rfd/0030-ignore-os-reduced-motion.md)). 재시작은 새 캔버스와 초기 이동 상태를 사용하며 화면 종료 시 해당 GPU 자원을 해제한다. 광원·잔광·정점 데이터는 매 프레임 같은 버퍼를 다시 써서 프레임마다 큰 할당을 만들지 않는다. 프레임마다 쌓이는 할당은 주기적인 GC 정지로 이어져 화면이 끊기기 때문이다. 중앙 레인·판정선·노트는 기존 Pixi 렌더러가 앞쪽에 표시한다.

**관대한 밸런싱**: `Liftoff`의 고도 0 시작·곡 종료 기준 클리어·곡 중 게임 오버 없음의 기존 관대한 역할을 유지한다. `Liftoff`는 Good·`goodTrill`을 포함해 Miss 없이 완주하면 클리어 조건을 충족하도록 게이지 상승량을 설정한다. 따라서 풀콤보 완주가 고도 조건 때문에 실패하는 상황을 배제한다([RFD 0093](../rfd/0093-liftoff-no-miss-completion-clears.md)). 종전 `Survival`의 Perfect-only 회복·0 도달 실패 규칙을 새 단계에 자동으로 배정하지 않는다.

**실패 조건 없는 완주/학습**: 실패 조건 없이 차트를 끝까지 확인하거나 구간을 반복 학습하려는 유저는 Observer 계열을 사용한다(`observer-mode.md`).

**후속 설계**: 세부 판정 규칙·상태와 시각 고도의 대응·기존 차트의 이행·속도와 각도 조정은 [PRD §12](../prd.md#12-미정-사항)에서 단일 추적한다. 이번 결정은 실제 충돌이나 레이더 탐지 판정을 도입하지 않는다.

**결정 배경**: 현재 이름·연출 배치는 [RFD 0022](../rfd/0022-flight-difficulty-names-and-visuals.md), 하향 시점의 표현은 [RFD 0021](../rfd/0021-low-altitude-downward-view.md), 초기 도입 목적과 과거 규칙은 RFD 0001～0003·0005를 참조한다.

## 플레이 중 노트 가시성

### 포인트 겹침과 연결 바디의 켜짐 표시

포인트 노트는 바디나 시작·끝 터미널과 겹치면 항상 그 위에 표시한다. 아래부터 바디→터미널→포인트 순서이며, 차트 배열의 노트 순서나 렌더 순서에 영향받지 않는다.

싱글·더블에서 실제로 유지 중인 바디가 있으면 아직 시작하지 않은 후속 연결 바디와 터미널도 켠다. 여러 구간을 연속해서 따르며, 유지 중인 unit 수와 경로상 각 구간의 건강한 unit 수 중 작은 수만 표시한다. 예를 들어 더블2개 유지→싱글→더블은 마지막 더블을1/2만 켠다. 실패한 unit을 켜거나 시작한 구간의 해제·실패·완료를 건너뛰지 않는다. 앞 구간이 끊긴 뒤에도 후속 구간 자체를 새로 유지하면 그 구간부터 다시 표시가 이어진다.

Trill은 연결 켜짐 표시에서 제외한다. 각 바디·터미널은 자기 구간의 실제 홀드가 활성화될 때만 켜며, 앞 구간을 유지해도 뒤쪽 Trill은 대기 상태다. Trill이 섞인 연결은 그 구간을 건너뛰어 켜짐 표시를 전파하지 않는다.

표시 전파로 후속 판정 unit을 활성화하거나 head·시작·승계·release 규칙을 변경하지 않는다. 단순히 판정선을 지났다는 이유로 실제 입력이 없는 연결 구간을 켜지 않는다.

위 켜짐 표시는 켜짐 효과가 있는 스킨에만 적용한다. 테마 `heldEffect: false`로 선언한 스킨은 켜짐 에셋 없이 유지 중에도 대기 바디·터미널을 그리고, 연결 켜짐을 전파하지 않는다. 더블의 부분 실패와 실패는 효과 유무와 관계없이 표시한다. 헤드 없는 롱노트를 미리 잡았을 때 바디를 판정선까지 당기는 위치 처리는 효과 유무와 관계없이 같다. 현재 공개 스킨 Classic은 효과가 있다([RFD 0028](../rfd/0028-skin-held-effect.md)).

### 처리된 노트 숨기기

입력이 처리된(판정이 완료된) 노트는 **즉시 화면에서 제거**된다. 판정선을 지나 화면 아래로 스크롤되기를 기다리지 않는다.

- **포인트 노트** (싱글, 더블, 트릴): 판정이 완료되면 즉시 사라진다. 롱노트 헤드 역할의 포인트 노트도 동일하게 판정 완료 시 사라진다.
- **롱노트 바디** (RangeNote): 정적 차트 컴파일이 unit과 Beat 연결 관계를 만든다. 런타임은 자기 시작 입력 또는 정당한 승계로 unit을 활성화하며, unit별 완료·실패 상태를 표시한다. 성공한 한 unit 때문에 whole body를 즉시 processed로 확정하지 않는다.

**처리된 노트를 숨기는 이유**: 판정이 완료된 노트가 화면에 남아 있으면, 아직 처리되지 않은 노트와 시각적으로 혼재되어 읽기 복잡도가 불필요하게 증가한다. 처리된 노트를 즉시 제거함으로써, 유저의 시각적 주의를 미처리 노트에 집중시킨다.

### 더블 노트 부분 입력 피드백

더블 노트(및 더블 롱노트 헤드)에서 2개의 입력 중 1개만 처리된 상태일 때, 해당 노트가 **50% 불투명도**로 변한다. 유저가 "1개는 눌렀지만 나머지 1개가 남아있다"는 것을 즉시 인지할 수 있으며, 2개 모두 성공한 경우와 명확히 구분된다.

- 더블 포인트 노트: 첫 번째 입력 후 노트가 반투명 → 두 번째 입력 후 사라짐 (롱노트 헤드 역할의 더블 노트도 동일)

## 미러 옵션 `[미구현]`

레인 배치를 좌우 반전하는 미러 옵션을 제공한다. 1-2-3-4 레인이 4-3-2-1로 뒤집힌다.

**미러를 제공하는 이유**: 왼손잡이 유저를 위한 접근성 보장이 주 목적이다. 키보드 리듬게임은 왼손이 낮은 레인, 오른손이 높은 레인을 담당하는 것이 관례인데, 왼손잡이에게는 주력 손이 단순한 파트를 담당하게 되어 불리하다. 미러 옵션으로 레인을 반전하면 오른손잡이와 동등한 조건이 된다. 부수적으로, 차트의 변주 효과도 제공한다.
같은 판정 설정 안에서는 미러 사용 여부와 관계없이 같은 차트의 최고기록·클리어 여부·풀콤보 여부로 합쳐 보존한다. Normal/Easy의 기록은 분리한다. 두 경우 모두 같은 최고기록의 갱신 대상이며 달성 여부도 함께 보존한다. 별도 미러 기록으로 나누지 않는다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

## 에러 처리

### 플레이 중 네트워크 단절

음원과 차트 데이터는 플레이 시작 전에 전체 로드되므로, **플레이 중 네트워크가 단절되어도 플레이는 끝까지 계속된다.** 결과 전송은 네트워크 복구 후 재시도한다. 로그인한 플레이의 기록 전송에 실패하면 결과 화면에 전송 실패 안내와 **전송 재시도** 버튼을 표시한다. 버튼을 누르면 해당 플레이 결과의 서버 전송을 다시 시도한다. 곡을 재생하는 Retry와 구별한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)). 결과 화면을 나가도 미전송 기록을 브라우저에 보관해 나중에 재전송할 수 있게 한다. 미전송 기록은 해당 플레이를 한 계정과 연결해 보관한다. 다음 접속 때 해당 플레이를 한 계정으로 로그인되어 있으면 브라우저에 보관한 미전송 기록을 자동 재전송한다. 기록 저장·전송은 미구현이다.

### 차트·음원 로딩 실패

본 플레이 로딩이 진행 중일 때는 사용자 취소와 곡 선택 복귀 조작을 제공하지 않는다. 본 플레이 로딩에서 응답이 없는 상태가 제한 시간 동안 이어지면 해당 로딩 시도를 실패로 처리한다. 차트 파일 전송과 음원 로딩의 시간 초과에는 자동 재시도와 최종 실패 화면의 선택 규칙을 적용한다.

곡 시작 전 차트 파일을 네트워크 문제로 받아오지 못하거나 본 플레이 음원 로딩이 실패하면, **최대 3회 자동 재시도**한다. 로딩 안내는 백분율 진행률 대신 **차트 불러오는 중**·**음원 준비 중**처럼 현재 진행 중인 작업을 표시한다. 자동 재시도 중에는 현재 재시도 횟수와 최대 횟수를 **재시도 1/3**처럼 표시한다. 첫 자동 재시도에서 1/3으로 시작하고 재시도가 진행될 때 갱신한다. 모두 실패하면 실패 화면에 오류 안내와 **재시도**, **곡 선택으로 돌아가기** 버튼을 표시한다. 재시도를 선택하면 같은 곡·차트의 로딩을 다시 시도하고, 복귀를 선택하면 곡 선택으로 돌아간다([RFD 0087](../rfd/0087-audio-load-failure-retry-or-return.md)). 현재 오류 표시·곡 선택 복귀 버튼은 구현되어 있으며, 현재 작업 안내·응답 제한 시간 처리·자동 재시도·실패 화면의 재시도 조작은 미구현이다. 제한 시간 수치는 실제 파일의 로딩 시간을 확인한 뒤 구현 단계에서 정하며 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### 차트 형식·검증 오류

일반 플레이용 차트에는 점수 노트가 최소 1개 필요하다. 점수 항목이 전혀 없는 차트는 일반 플레이 진입을 차단하고 아래 검증 오류 경로를 따른다. 제작 중 저장·에디터 테스트와 튜토리얼의 바디 연습에는 적용하지 않는다([RFD 0091](../rfd/0091-normal-play-requires-score-note.md)). 이 진입 제한은 미구현이다.

보조 파일이 없는 차트(빈 차트를 새로 만들어 보조 파일을 쓰지 않은 경우 등)는 오류가 아니라 보조 자료 없음으로 읽는다. 판별 기준은 [차트 문서 포맷](chart-format.md#현재-소비자-경계)을 따른다.

차트 자체의 형식·검증 오류에는 자동 재시도나 수동 재시도를 제공하지 않고, 오류 안내와 **곡 선택으로 돌아가기** 버튼만 표시한다. 차트 파일을 서버에서 받아오지 못한 전송 실패와 구별한다([RFD 0087](../rfd/0087-audio-load-failure-retry-or-return.md)). 에디터는 관리자만 접근할 수 있다. 차트 형식·검증 오류가 나면 일반 플레이어에게는 다른 차트 선택을 안내하고, 관리자에게는 에디터에서 수정할 수 있다는 안내도 제공한다. 현재 `LoadingScreen`도 형식·검증 오류와 곡 선택 복귀 버튼을 제공하지만, 관리자 여부에 따른 안내 문구 분기는 미구현이다.

### 서버 점검

서버 점검 중에는 로그인 여부와 관계없이 새 접속·새 플레이 진입을 막고 점검 안내를 제공한다. 이미 재생 중인 곡은 끝까지 플레이하고 결과 화면으로 진행한다. 플레이 중 점검이 시작돼도 점검 안내를 띄우지 않고, 곡이 끝난 뒤 결과 화면에서 안내한다. 완료한 로그인 플레이의 기록 전송에 실패하면 기존 전송 실패 안내·재시도·브라우저 보관·원래 계정의 다음 접속 시 자동 재전송 규칙을 따른다([RFD 0088](../rfd/0088-finish-current-play-during-maintenance.md)). 점검 감지·진입 제한·안내 처리는 미구현이다.

### 플레이 화면 배치

아래 시작·끝 터미널과 판정선에 멈추는 롱노트의 설명은 현행 구형 렌더러 기준이다. 새 모델의 마감 에셋 제외·정상 완료 즉시 숨김·실패 잔존은 [점수·확정 효과와 표시 수명](#점수확정-효과와-표시-수명)을 따른다(명시 테스트 재생 #346·일반 곡 재생 #347에서 구현·검증).

플레이 화면은 논리 높이 600에 화면 비율을 곱한 논리 폭(16:9면 1067, 4:3이면 800)으로 그리며, 기어 실루엣과 양옆 여백이 들어가는 466보다 좁히지 않는다. 배치는 [RFD 0029](../rfd/0029-frame-aspect-fit-narrow-lanes.md)를 따른다.

- **플레이필드:** 레인 4개(각 62.5)로 된 폭 250의 레인 영역을 화면 가운데에 둔다. 노트는 62.5×12.5(1:5)이고, 판정선 두께·판정과 콤보·정확도 글자·키봄·레인 구분선·마디선도 같은 플레이필드 배율(레인 100 기준 설계값 × 0.625)로 그린다. 마디선은 낮은 렌더 높이에서도 화면 1px보다 얇아지지 않는다. 스크롤 속도는 논리 px/s라 노트가 화면을 지나는 시간은 배율과 무관하다.
- **기어:** 스킨 공통 [기어](../context/glossary.md#기어-gear) 그림 한 장을 비율 그대로 줄여, 그림 속 레인 창을 레인 영역에 정확히 겹치고 실루엣 아래끝을 화면 아래보다 10 아래에 둔다. 판정선도 같은 양만큼 함께 내려([기어 y 오프셋](../context/glossary.md#오프셋-구분) `GEAR_OFFSET_Y` 10, 화면 y축이라 +가 아래, [#257](https://github.com/nanana3679/not4k/issues/257)) 판정선과 덱·키 윗면 사이 틈은 그대로다. 기어는 판정선·레인 위, 키봄·글자 아래에 그리며 리프트로 움직이지 않는다. 위쪽 원본 119행과 아래쪽 원본 약 22행(1444～1465행)이 화면 밖으로 잘리고 게이지·덱은 모두 보인다.
- **`gearMotion`:** 기어 바로 위(키봄·글자 아래)에 `gearMotion` 시안 SVG(확정한 v19, `54-ambient-motion-v19.svg`)의 장식 애니메이션을 Pixi 레이어로 다시 구성해 추가한다([RFD 0029](../rfd/0029-frame-aspect-fit-narrow-lanes.md#프레임-움직임-게임-적용-2026-10-05)). 큰 광원 띠가 60초에 한 번 위에서 아래로 지나가며 장갑의 명암 대비를 키우고, 양옆 유리관의 채운 부분에서 액체가 흐르며 기포가 오르고, 파란 발광선이 4.4초 주기로 밝아졌다 돌아오고, 하단 바 빛이 3.2초마다 가운데에서 양옆으로 흐른다.
  - **시간 기준:** 비행 배경과 같다. 애니메이션 경과 시간은 곡 시간이나 벽시계가 아니라 렌더러가 그린 렌더 프레임 간격으로만 나아가고, 일시정지·숨긴 탭에서는 나아가지 않는다. 일시정지를 풀면 멈춘 시점에서 이어 간다. 한 프레임에 최대 50ms만 나아가 긴 프레임이나 탭 복귀에서 건너뛰지 않는다. 재시도·새 곡은 새 렌더러라 0초부터 시작한다.
  - **`prefers-reduced-motion`:** 운영체제·브라우저의 모션 감소 설정(`prefers-reduced-motion`. macOS·iOS '동작 줄이기', Android '애니메이션 삭제', Windows 11 '애니메이션 효과')은 읽지 않는다. `gearMotion`은 설정 `Gear Motion`만 따르며, 비행 배경과 고도 게이지 이징도 이 설정과 관계없이 움직인다([RFD 0030](../rfd/0030-ignore-os-reduced-motion.md)).
  - **읽기와 곡 시작:** `gearMotion` 에셋(`gear-motion.json`과 텍스처, 약 2MB)은 스킨 텍스처와 같은 필수 에셋이다. 곡을 시작하기 전에 스킨과 함께 받아 기어 위에 추가하고, 재생 직전 준비(아래 **곡 시작 전 준비**)에서 텍스처를 GPU 업로드하고 첫 프레임을 그려 마스크를 준비한다. 시간 제한으로 건너뛰거나 곡 도중에 추가하지 않는다. 설정이 켜진 동안 받은 에셋의 lease를 keep-alive로 두어 재시도·다음 곡은 다시 받지 않는다. 받지 못하면 스킨 텍스처를 받지 못했을 때와 같이 곡을 시작하지 않고 오류 문구와 `Back to Song Select`가 있는 오류 화면으로 간다. 설정을 끄면 받지도 기다리지도 않는다.
  - **설정:** `Settings → Gameplay → Display`의 `Gear Motion`(기본 켬, 저장 키 `gearMotion`)을 끄면 `gearMotion`을 만들지도 에셋을 읽지도 않아 프레임마다 드는 비용이 없다. 약한 GPU에서 프레임 시간을 지키기 위한 선택이다. 값은 localStorage에 저장하고, 이 값이 없는 설정은 켬으로 복원한다.
  - **그리지 않는 화면:** 기어를 그리지 않는 튜토리얼 재생기와 노트 에셋 시연실은 `gearMotion`도 그리지 않는다.
- **고도 게이지:** 기어 양옆 유리관이 `altitude`를 아래 기준 채움으로 보여 준다(위 `flightRule` 절의 **`altitude` 시각화**). 빈 유리 덮개는 `gearMotion` 위에 겹쳐 빈 부분의 액체·기포를 가리며, `Gear Motion` 설정과 무관하게 그린다. 기어를 그리지 않는 화면에는 없다.
- **레인 끝:** 레인은 판정선이 아니라 키 윗면(y 456.5)에서 끝난다(`laneEndY`). 레인 배경·구분선은 레인 끝까지만 그리고, 노트·롱노트·마디선·`trillZone`·`restZone`·키빔을 담은 레인 내용 컨테이너(`laneContentLayer`)는 기어 유무와 관계없이 레인 끝 위 사각형 클립 하나로 자른다([#247](https://github.com/nanana3679/not4k/issues/247)). 판정선·키봄·판정 글자와 기어는 클립 밖이다. 키 아래 기어는 레인 폭에서 불투명하다. 맨 아래 반투명 가장자리 9행(그림 1457～1465행)은 기어를 10 내려 화면 밖이다. Pixi 8.21에는 scissor 경로가 없어 이 클립은 스텐실 마스크이며, 렌더러마다 프레임당 클립 사각형을 2번 더 그리고 그 앞뒤로 batch break가 생긴다(`/lab/gear`에서 프레임당 draw call 약 17.5 → 21.5, swiftshader 측정). 판정선 아래 틈과 꺾인 덱 사이로 실제 레인이 이어져, 판정되지 않은 노트는 판정선을 지나서도 보이고 놓친 노트는 열린 덱을 지나 키 밑으로 사라진다. 리프트가 크거나 스크롤이 느려 틈을 지나는 데 오래 걸려도 노트 박스와 그 위 접촉 그림자가 키 윗면 아래로 다 내려갈 때까지 그린다. 처리된 노트는 판정과 함께 사라진다.
- **노트 그리는 기준:** 노트의 시간 위치는 노트 박스의 세로 가운데다([#224](https://github.com/nanana3679/not4k/issues/224)). 판정 순간(곡 시각 = 노트 시각) 노트 가운데가 판정선에 오고, 노트 박스는 판정선 위아래로 노트 두께의 절반(6.25)씩 걸친다. 판정 엔진의 시각은 그대로이고 그리는 위치만 이 기준을 따른다.
  - **롱노트:** 바디는 끝 시각 칸의 윗변부터 시작 시각 칸의 아랫변까지 이어진다. 시작·끝 터미널(반쪽 캡 또는 노트 한 칸 높이)은 각 칸 안에 그려 바디와 틈이나 겹침 없이 맞물리고, 같은 시각 포인트 노트와 같은 칸이다. 길이 0 롱노트는 같은 시각 포인트 노트와 정확히 같은 칸이다. 트릴 롱노트 바디는 끝 마름모 가운데부터 시작 trill 포인트 가운데까지다.
  - **판정선에 멈추는 롱노트:** 잡고 있는 롱노트, 미리 잡아 판정선까지 당긴 헤드 없는 롱노트, 놓친 롱노트([#214](https://github.com/nanana3679/not4k/issues/214) 전까지)는 머리 칸 가운데가 판정선에 멈춘다. 끝 터미널은 끝 시각에 칸 가운데가 판정선에 온다. 길이가 노트 한 칸보다 짧은 Classic(노트 한 칸 높이 터미널) 롱노트는 두 터미널이 겹쳐 시작 전에는 시작 터미널만, 시작 후에는 끝 터미널만 보이는데, 끝 터미널은 시작 터미널이 있던 판정선 가운데 칸에서 그대로 이어받아 끝 시각까지 그 자리에 머문다(길이 0 롱노트와 같음).
  - **구간·선:** 트릴 구간 띠는 같은 박의 롱노트 바디와 같은 범위를 덮는다. 마디선은 판정선처럼 선 두께의 가운데가 마디 시각에 온다. 휴지 구간은 노트 칸이 아니라 시각 구간 자체를 덮는다(에디터 타임라인과 같음). 키봄은 판정선을 가운데로 둔다.
  - **같은 기준을 쓰는 화면:** 곡 선택 튜토리얼 재생기·Lab 노트 에셋 시연실(같은 렌더러), Visual 캘리브레이션 화면, 판정 사례 그림(`pnpm case:image`). 기어를 그리지 않는 튜토리얼 재생기는 레인 끝이 판정 순간 노트 칸의 아래끝(판정선 + 노트 반 칸)이라, 판정선에 가운데가 걸친 노트·터미널 한 칸이 게임처럼 모두 보이고 그 아래는 잘려 캔버스 바탕색이 보인다(리프트를 올리면 레인 끝도 함께 올라간다).
- **키보드 표시:** 오른쪽 아래 구석에 현재 바인딩의 키보드 배치를 작게 그린다([키 바인딩 명세](keybinding.md#플레이-중-표시)).
- **곡 시작 전 준비:** 음원을 재생하기 직전에 렌더러가 곡 중 그릴 수 있는 텍스처를 화면에 보이든 말든 전부 GPU 업로드한 뒤, 곡 시작 시각의 첫 프레임을 그려 셰이더·마스크를 준비한다(`GameRenderer.prepareForPlayback`, [#239](https://github.com/nanana3679/not4k/issues/239)). 대상은 스킨이 불러온 텍스처 전부(키봄 16프레임, 실패·켜짐·부분 실패·idle 노트·바디·터미널, Grace 등. 켜짐 효과 없는 스킨은 켜짐 텍스처를 불러오지 않는다), 기어 그림·빈 유리, `gearMotion` 텍스처(재생 중일 때만), 키빔 그라데이션이다. 목록은 렌더러가 스스로 모으며, 여러 텍스처가 나눠 쓰는 그림은 한 번만 GPU 업로드한다. 곡 중 처음 쓰는 텍스처(첫 판정의 키봄, 첫 MISS의 실패 노트 등)가 그 프레임에 GPU 업로드되어 프레임 시간을 늘리지 않게 하기 위해서다. 이 텍스처들은 렌더러를 dispose할 때까지 Pixi 자동 GC(`autoGarbageCollect`)에서 빠져, 곡 중 오래(기본 60초 넘게) 그리지 않아도 GPU 텍스처가 해제되지 않는다. dispose하면 원래 설정으로 돌아간다. 판정·콤보·정확도 글자는 값이 바뀔 때마다 새로 그려 GPU 업로드하므로 여기서 미리 하지 않는다. 곡 선택 튜토리얼 재생기와 Lab 미리보기는 이 준비를 하지 않아 텍스처를 처음 그릴 때 GPU 업로드한다.

### 곡 선택 화면 `[부분 구현 — 게임/에디터 별도 화면 존재, 통합·로그인·키보드 조작·admin 분기 미구현]`

곡 선택 화면은 **게임과 에디터가 공유하는 단일 화면**이다. 기존에는 게임(`SongSelectScreen`)과 에디터(`SongListPage`)가 별도의 곡 리스트를 가지고 있었으나, 이를 하나로 통합한다.

#### 상단 헤더

- **로그인 버튼**: 비로그인 상태에서 로그인 버튼을 표시한다. 로그인 상태에서는 유저 정보와 로그아웃 버튼을 표시한다.
- **튜토리얼 도움말 버튼**: 상단의 `?` 버튼을 누르면 중앙 팝업에서 `Basic`의 입문 17개와 `Advanced`의 판정 규칙 12개 시연을 표시한다. 탭별 이동 위치와 본 항목 체크를 제공하며, 자세한 동작은 `tutorial.md`를 따른다. 팝업에는 실제 `GameRenderer` 기반 축소 재생기, 튜토리얼 차트의 `tutorialInput` 이벤트로 구동되는 키 입력 표시, `tutorialDiagram` 이벤트로 표시되는 에디터 노트 렌더러 방식 도식이 포함된다. 도식은 뷰포트 전체를 dim 한 확인 모달로 표시하며, OK를 눌러야 다음 시연으로 재개된다.
- Settings, Back 등 기존 버튼은 유지한다.

#### 곡 리스트

- 서버에서 곡 목록을 조회한다. **admin 권한이 있는 유저는 비공개 곡까지 포함**된 목록을 받고, 일반 유저는 공개 곡만 받는다.
- 곡 리스트는 **마우스 휠** 또는 **키보드 Up/Down**으로 스크롤할 수 있다.

#### Song Item 구조

하나의 song item에는 **여러 chart가 존재**하며 난이도명으로 구분된다. 채택된 이름과 순서는 `Liftoff → Infiltration → Breakthrough`다. 곡 선택·로딩에서는 기존 `EASY / NORMAL / HARD`를 세 이름으로 표시하며 새 차트도 세 이름에서 선택한다. 기존 `EXPERT`는 이름·순서를 유지하고 돌파 배경을 쓴다. 저장 키·URL·차트 원본은 바꾸지 않으며 기존 라벨과 새 이름이 같은 단계면 새 차트 선택에서 중복을 막는다. 원격 데이터 일괄 이행은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다.

- **차트 선택**: 클릭 또는 **좌우 화살표**로 해당 곡 내에서 차트(난이도)를 선택한다.
- **차트별 개인 기록**: 차트 선택에서 해당 차트의 플레이 기록이 없으면 클리어 상태 표시를 비워둔다. 0점이더라도 실패 기록이 있으면 실패를 표시한다. 차트 선택에서는 올퍼펙트를 달성한 경우 풀콤보 표시 대신 올퍼펙트를 표시한다. 최고 점수가 갱신되지 않는 동점 플레이에서 새로 달성한 올퍼펙트도 표시에 반영한다. 현재 차트 버전의 최고기록(최고 점수)·클리어 여부·풀콤보 여부를 바로 확인할 수 있게 한다. 더 높은 점수를 얻으면 최고기록을 갱신한다. 플레이 횟수는 통계창에서 확인한다. 첫 클리어 시점 등 다른 상세 기록은 예시이며 저장 항목으로 확정하지 않는다. 표시 정책은 [glossary](../context/glossary.md#개인-플레이-기록)·[RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)를 따르며, 집계·저장과 상세 항목·화면은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다. 이번 결정으로 기록 저장·집계·표시의 구현 완료를 선언하지 않는다.
- **차트 수정 시 기록**: 노트 배치가 바뀌면 기존 최고 점수·클리어 여부·풀콤보 여부는 이전 차트 버전의 기록으로 보관하고, 수정된 차트 버전의 기록은 새로 쌓는다. 이전 버전의 달성 여부나 점수로 수정된 버전의 기록을 채우지 않는다. 곡·차트 선택과 랭킹에는 현재 차트 버전의 새 기록만 표시한다. 이전 버전 기록의 조회 화면과 표시 방식은 이번 출시 전 설계 범위에서 제외한다.
- **차트 삭제 후 기록**: 기존 기록은 원래 차트 버전에 보관하고 삭제된 차트는 선택 목록·현재 랭킹에서 제외한다. 재등록은 새 차트로 취급하며 이전 기록을 승계하지 않는다([RFD 0097](../rfd/0097-preserve-records-after-chart-deletion.md)).
- **판정 설정별 기록**: Normal과 Easy의 최고 점수·클리어 여부·풀콤보 여부는 판정 설정별로 분리해 보존한다. 한 설정에서 달성한 기록으로 다른 설정의 기록을 갱신하지 않는다.
- **기록별 독립 보존**: 최고기록·클리어 여부·풀콤보 여부는 서로 다른 플레이에서 달성해도 각각 보존한다. 새 최고기록의 플레이에서 클리어·풀콤보를 달성하지 못해도 이전 달성 여부는 유지하며, 최고기록을 갱신하지 못한 플레이에서 처음 달성한 클리어·풀콤보도 보존한다.
- **Play**: **엔터** 키 또는 선택된 차트의 **Play 버튼**을 클릭하면 로딩 → 플레이 화면으로 이동한다.
- **Edit** `[admin 전용]`: admin 권한이 있는 유저에게만 Play 버튼 옆에 **Edit 버튼**이 표시된다. Edit 버튼을 클릭하면 해당 차트의 **에디터 화면으로 이동**한다.

#### 개발 환경의 스킨 버전 비교

- PC 곡 선택 화면의 **Settings → Skin → 개발용 스킨**에서 게임 설정 사용, 현재 Classic, 보관 버전 `v014`·`v013`·`v012`·`v002`·`v001`을 선택한다. `v014`는 현재 적용본(흰빛 포인트·트렌치 바디·싱글·더블 포인트 위아래와 트릴 포인트 마름모 테두리 접촉 그림자·반투명 사각 기둥 트릴 켜짐 바디·에디터와 같은 회색 마름모 트릴 끝 터미널)이고, `v013`은 트릴 켜짐 바디가 이전 석영인 버전, `v012`는 트릴 접촉 그림자가 없는 후보, `v002`는 고채도 포인트·아주 밝은 바디다. 보관본과 시연은 [노트 에셋 Lab](note-asset-lab.md)을 따른다.
- 기존 Supabase 곡 목록에서 곡과 난이도를 고른 뒤 `Play` 또는 Enter로 시작한다. 차트·음원은 기존 `LoadingScreen`에서 불러오며 `gameplayRange`, 입력·판정·재시도·결과 흐름을 그대로 사용한다.
- 개발용 스킨은 기본 스킨보다 우선 적용한다. Settings의 탭을 바꾸거나 닫았다 다시 열어도, 곡 선택으로 돌아오거나 재시도해도 현재 탭에서 선택을 유지한다. 게임의 저장된 `skinId`는 바꾸지 않는다. **게임 설정 사용**을 고르거나 새로고침하면 저장된 스킨으로 돌아간다.

#### 곡 프리뷰 `[미구현]`

곡 선택 화면에서 같은 곡을 1초 동안 선택하면 프리뷰를 불러와 **자동 재생**한다. 대기 중 선택을 바꾸면 새로 선택한 곡을 기준으로 다시 기다린다. 곡 선택 화면에서 같은 곡을 선택한 동안에는 프리뷰 음원이 끝나면 처음부터 반복 재생한다. 선택한 곡이 바뀌거나 곡 선택 화면을 나가면 해당 프리뷰의 재생을 중단한다. 곡을 고르기 전에 해당 곡의 일부를 미리 들을 수 있게 한다.

**프리뷰 음원은 곡마다 필수로 제공하는, 본편과 별개의 오디오 파일**이다([RFD 0089](../rfd/0089-required-preview-audio-file.md)). 차트 메타데이터(`chart-editor.md`)에 프리뷰 전용 음원파일 필드를 두어, 차트 제작자가 곡의 하이라이트 구간을 별도로 편집하여 제공한다. 전용 파일이 없을 때 본편 음원의 지정 구간으로 대체하지 않는다. 프리뷰 파일 한 개의 길이는 로딩 용량을 위해 **5초 이상 15초 이하**로 제한하며, 제작자는 그 안에서 프리뷰 구간을 선택한다. 프리뷰 파일을 생성할 때 시작 0.5초에 선형 페이드 인, 끝 0.5초에 선형 페이드 아웃을 고정 적용하며, 제작자가 페이드 길이를 조절하는 옵션은 두지 않는다. 한 번 불러온 프리뷰 음원은 브라우저에 저장해 다음 접속에도 재사용한다. 저장된 파일이 없으면 서버에서 불러오고, 프리뷰 파일이 바뀌면 저장본을 갱신한다. 저장된 프리뷰를 재사용할 때도 같은 곡을 1초 동안 선택한 뒤 재생한다. 프리뷰 저장 용량이 차면 마지막으로 들은 지 가장 오래된 프리뷰부터 자동으로 삭제한다. 저장 용량의 상한은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

프리뷰만 로딩에 실패하면 미리 듣기를 건너뛰고 곡 선택과 플레이 진입은 허용한다. 프리뷰 로딩 실패 안내는 팝업 없이 곡 정보 영역에 작게 표시한다. 본 플레이의 차트·음원 로딩과 검증은 기존 규칙을 따른다.

튜토리얼 또는 곡 추가 창을 열면 곡 선택 화면의 프리뷰 재생과 재생 전 대기를 중단한다. 창을 닫으면 그때 선택된 곡을 기준으로 1초 기다린 뒤 프리뷰를 처음부터 다시 재생한다. 일반 설정 창을 열어도 곡 선택 프리뷰의 재생을 유지한다. 마스터 볼륨을 바꾸면 재생 중인 프리뷰에도 바로 적용한다.

곡 선택 프리뷰의 자동 재생을 끄는 별도 설정은 제공하지 않는다.

프리뷰 재생·브라우저 저장·필수 여부 검증은 미구현이다.

### 미구현 흐름

튜토리얼의 입력 학습은 시연 후 직접 연주를 항목별 요구 횟수만큼 누적 성공하면 통과하는 방식으로 개편한다. 튜토리얼을 닫았다 다시 열면 마지막으로 선택한 탭과 항목을 연다. 마지막으로 선택한 탭과 항목은 해당 기기의 브라우저에만 저장해 게임을 껐다 켜도 복원하며 계정과 동기화하지 않는다. 선택 이력이 없는 최초 진입은 `Basic` 첫 항목에서 시작한다. 항목 위치 복원과 미완료 실습의 성공 횟수 복원은 구별한다. 실습 기록으로는 항목 전체 통과 여부만 로그인 여부와 관계없이 브라우저에 저장한다. 로그인하면 항목 전체 통과 여부를 계정과 동기화해 다른 기기에서도 같은 통과 표시를 확인할 수 있게 한다. 게스트 튜토리얼의 항목 전체 통과 기록은 로그인 시 계정당 1회 인계할 수 있다. 이미 인계한 게스트 기록은 다른 계정으로 재인계하지 않는다. 계정에 귀속된 통과 기록은 같은 계정의 여러 기기에서 계속 공유하며, 로컬에 표시된 계정 기록을 게스트 기록으로 재분류하거나 다른 계정으로 인계하지 않는다.  현재 방법·부분 성공 횟수·중간 방법 완료 여부는 현재 실습 세션에서만 유지하고 영구 저장·계정 동기화하지 않는다. 미완료 항목을 닫았다 다시 열거나 다른 항목에서 돌아오거나 게임을 재시작하면 첫 번째 방법의 성공 횟수 0회부터 시작한다. 이미 전체 통과한 항목의 재실습도 첫 번째 방법 0회부터 새로 진행하되 과거 항목 통과 기록은 지우지 않는다. 같은 항목 안에서 시연/직접 입력을 토글할 때는 현재 방법과 누적 성공 횟수를 유지하며 기존 전환·집계 규칙을 따른다. 튜토리얼 목록에서 통과한 항목에 체크 표시를 붙인다. 시연만 본 항목에는 통과 체크를 붙이지 않으며, 별도의 열람 표시도 두지 않는다. 롱노트 중 탭 한 항목은 기존 키 유지 방법을 먼저 시연·실습한 뒤 목표 달성 시 반복을 멈추고, `다음` 버튼으로 유지 키 교대 방법에 이동한다. 방법을 자유롭게 번갈아 선택하거나 자동으로 다음 방법에 이동하지 않으며, 두 방법 모두 통과해야 항목 전체를 통과로 표시한다. 전체 튜토리얼 항목의 순서를 잠그지는 않는다. 모달은 처음부터 바로 닫을 수 있으며, 튜토리얼 완료·통과를 차트 선택의 선행 조건으로 두지 않는다([튜토리얼 스펙](tutorial.md#시연-후-직접-입력으로-통과), [RFD 0081](../rfd/0081-tutorial-demonstration-and-three-practice-successes.md)).

```
타이틀 → 로그인 → 타이틀

곡 선택 → [admin + Edit] → 차트 에디터 → 곡 선택

```

### 곡 종료와 결과 이동 `[미구현]`

결과 화면의 기록 갱신 안내는 최고 점수를 갱신했을 때만 표시한다. 해당 차트 버전·판정 설정에 기존 기록이 없으면 첫 기록에도 최고 점수 갱신 표시를 보여준다. 첫 기록이 0점이어도 같은 기준을 적용한다. 기존 최고 점수를 넘기면 결과 화면의 갱신 안내와 함께 이전 최고 점수 대비 증가분을 +1,234점 형식으로 표시한다. 증가분은 이번 점수에서 이전 최고 점수를 뺀 값이다. 점수가 기존 최고 점수와 같거나 낮으면 점수 차이는 표시하지 않는다. 기존 기록이 없는 첫 기록에는 갱신 안내만 표시하고 증가분은 표시하지 않는다. 클리어 상태 갱신은 별도로 안내하지 않는다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

종료한 한 플레이의 클리어 상태는 실패·성공·풀콤보·올퍼펙트 중 하나로 표시한다. 클리어 상태는 내부 용어이며 점수·달성률·랭크·판정 통계와 구별한다([RFD 0092](../rfd/0092-exclusive-play-outcome-and-chart-display.md)).

곡이 종료되면 해당 플레이의 클리어 성공·실패에 맞는 연출을 보여준 뒤 결과 화면으로 이동한다. 풀콤보·올퍼펙트를 달성하면 일반 클리어 연출 대신 해당 달성의 전용 종료 연출을 보여준다. 풀콤보와 올퍼펙트 조건을 모두 충족하면 올퍼펙트 종료 연출만 보여준다. 올퍼펙트는 곡을 끝까지 연주하고 모든 점수 노트를 Perfect로 처리하며, 무점수 바디 실패를 포함한 Miss가 한 번도 없는 경우에만 인정한다. 전용 연출도 3초 이내로 표시하며 건너뛰기 없이 완료 후 결과 화면으로 이동한다. 성공·실패 연출은 모두 3초 이내로 짧게 표시하며 건너뛰기 조작을 제공하지 않는다. 연출이 끝나면 자동으로 결과 화면으로 이동한다. 곡 도중 `flightRule`의 실패가 확정되면 즉시 곡 재생과 입력 판정을 종료하고, 실패 연출을 보여준 뒤 결과 화면으로 이동한다. 클리어 여부를 알리는 연출과 점수 랭크는 구별한다([RFD 0090](../rfd/0090-song-end-presentation-before-results.md)).

```
곡 완주 → 일반 종료 연출 또는 풀콤보·올퍼펙트 전용 종료 연출 → 결과 화면
곡 도중 실패 확정 → 곡 재생·입력 판정 종료 → 실패 연출 → 결과 화면
```

곡 도중 실패로 종료되면 판정 통계는 종료 시점까지 실제로 확정된 판정만 집계한다. 미처리 노트를 종료 때문에 새 Miss로 채우지 않는다. 최종 달성률의 분모는 기존대로 차트 전체 점수 항목의 이론 가중치 합을 사용한다([RFD 0090](../rfd/0090-song-end-presentation-before-results.md)).

Quit·Retry와 옵저버 종료에는 기존대로 결과 화면을 표시하지 않는다. 단계별 실패 조건과 연출의 세부는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### 일시정지

플레이와 옵저버 모드에서 **일시정지가 가능**하다. 다만 재생 전 로딩 중(플레이 화면에 들어온 뒤나 Retry 뒤 음원 재생이 시작되기 전)에는 Esc를 눌러도 일시정지하지 않는다.

- **플레이 중 일시정지**: 차트·판정선을 가린다. 재개는 **이번 플레이 시작 시각을 하한으로 곡 시간 3초 되감기 → 목표 앞 음악만 실제 3초 준비 → 목표부터 차트·판정 재개** 순서다. 별도 3·2·1은 없다. 목표 T까지 반영된 판정·점수·콤보·바디·릴리즈/트릴 이력·고도를 복원하고 그 뒤 입력·결과는 버려 다시 플레이한다. 미래 노트의 이른 성공도 실제 처리 시점으로 보존 여부를 정하며 노트 시각으로 정산을 잘라내지 않는다. 준비 입력은 점수 입력으로 재생하지 않고 현재 hold만 반영한다. 준비 중 다시 멈추면 같은 T로 준비만 다시 시작한다. 원본문서·source와 원래 플레이 항목 범위는 바꾸지 않는다. `[채택 계약·일반 기본 경로 구현·검증]` 세부는 [RFD 0040](../rfd/0040-countdown-and-note-reentry.md)과 [PRD §12](../prd.md#12-미정-사항)를 따른다.
- **옵저버 모드 일시정지**: 노트 출력부가 **가려지지 않는다.** 일시정지 중에도 차트를 확인할 수 있다. 시작·끝 핸들이나 몸통을 드래그하는 동안 재생을 멈추고, 화면 패턴은 현재 선택 구간의 시작 핸들 위치를 기준으로 갱신한다. 끝 핸들만 바꿔 시작 위치가 같으면 화면의 기준 위치도 그대로이며, 시작 핸들이나 몸통을 옮기면 새 시작 위치를 따른다. 드래그를 놓아도 정지 상태를 유지한다. 이후 재생 버튼을 누르면 선택 구간 시작에 앞선 최대 3초 준비 구간부터 재생해 페이드 인 후 선택 구간에 진입한다. 이 준비 구간은 배속과 무관한 실제 시간 기준이며 실제 음원 범위까지만 사용하고 부족한 시간은 무음으로 보충하지 않는다. 재개는 별도 카운트다운 없이 재생하는 방향이다. 반복 재생은 음원 범위 안에서 선택 구간 앞뒤를 배속과 무관한 실제 시간으로 각각 최대 3초 더 재생하며 페이드 인·아웃하고, 부족한 시간은 무음으로 채우지 않는다. Retry도 구간 시작을 기준으로 앞 페이드 구간을 거쳐 진입한다. 기본 구간은 전곡이며 직접 나갈 때까지 현재 구간을 반복한다. Auto 중에는 판정만 보여주고 콤보·달성률은 숨기며 Auto 노트는 집계에서 제외한다. 수동 집계는 구간 종료·Retry·구간 변경·Auto 전환에 초기화하고, 명시적으로 종료할 때 리절트 없이 곡 선택으로 복귀한다([RFD 0075](../rfd/0075-observer-manual-only-statistics.md)).

일시정지에서는 **재개(Resume)**, **재시도(Retry)**, 또는 **중도 포기(Quit)**를 선택할 수 있다. Play의 Retry는 결과 화면을 거치지 않고 곡을 처음부터 재시작한다. 옵저버의 Retry는 지정한 구간의 시작으로 돌아간다.


### 중도 포기

플레이 도중 중도 포기하면 **결과 화면을 거치지 않고 곡 선택 화면으로 돌아간다.** 중도 포기한 플레이는 기록되지 않는다.

**결과·기록 처리 정책**: Quit은 진행 중인 플레이를 종료하고 곡 선택으로 복귀하는 조작으로 제공한다. 이 경로에서는 결과를 표시하거나 플레이 기록을 남기지 않는다. 플레이어가 중도 포기한 이유나 미완주 결과를 어떻게 받아들이는지는 단정하지 않는다.

**중도 포기와 `flightRule` 실패의 구분**: 중도 포기는 유저의 자발적 선택이고, `flightRule` 실패는 해당 규칙에 의한 게임 오버다. 규칙에 따라 곡 도중 실패로 종료된 로그인 플레이는 그때까지 얻은 점수를 기록과 랭킹에 반영한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)). 실패 확정 시 즉시 곡 재생·입력 판정을 종료하고 실패 연출 후 결과 화면으로 이동한다([RFD 0090](../rfd/0090-song-end-presentation-before-results.md)). 풀콤보는 완주한 플레이에서만 인정하므로 곡 도중 실패로 종료된 플레이에는 부여하지 않는다. 단계별 실패 조건은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다. 낮은 시각 고도 자체를 모든 단계의 실패 조건으로 두지 않는다.

### 설정의 프로필 탭

프로필 탭·로그인·로그아웃·닉네임 편집·저장·검증을 구현했다. 로그인 상태에서는 `Signed in`과 이메일(있는 경우), 닉네임 입력·저장 버튼과 로그아웃 버튼을 표시한다.

설정 화면에 프로필 탭을 제공한다. 비로그인 상태에는 로그인 버튼, 로그인 상태에는 닉네임 편집과 로그아웃 버튼을 표시한다([RFD 0094](../rfd/0094-settings-profile-tab.md)). 기존 닉네임과 겹치지 않는 기본 이름의 자동 생성·직접 변경하는 닉네임의 중복 허용·기록 보존·기존 랭킹의 이름 반영은 [닉네임](../context/glossary.md#닉네임)을 따른다.

**닉네임 입력 제약**: 길이는 1～16자이며 빈 이름이나 16자를 초과하는 이름은 저장할 수 없다. 앞뒤를 포함한 공백, 특수문자와 이모지를 허용하지 않는다. 공백이 있으면 자동 제거 없이 저장을 거부하고 **닉네임에는 공백을 사용할 수 없습니다.**라고 안내한다. 특수문자와 이모지가 있어도 저장을 거부하고 오류를 표시한다. 입력값은 유지하여 사용자가 직접 수정할 수 있게 한다. 지원 언어에 따른 허용 문자 범위는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

**닉네임 저장과 확정**: 저장 버튼을 눌러 변경을 요청하며, 실제 이름은 서버 저장 성공 후 변경한다. 입력 중이거나 저장에 실패한 값은 편집 초안으로 취급한다. 닉네임은 랭킹에 표시되는 계정 정보이므로 저장에 실패한 새 이름을 변경 완료로 표시하지 않는다. 이는 로컬에 먼저 적용한 뒤 서버에 동기화하는 게임 설정과 구별한다.

저장 요청 후 설정을 닫아도 같은 계정으로 로그인되어 있으면 저장 성공을 계정 닉네임에 반영하고, 다시 열면 그 이름을 표시한다. 저장이 끝나기 전에는 다시 연 설정에서도 닉네임 입력과 저장 버튼을 비활성화한다. 닫힌 폼의 완료·오류 안내는 표시하지 않는다.

| 상황 | 동작 | 상태 |
|------|------|------|
| 닉네임 저장 성공 | 실제 닉네임에 새 이름 적용. 설정과 프로필 탭이 열려 있으면 저장 완료 안내 표시 | 구현 |
| 닉네임 저장 실패 | 기존 닉네임과 입력 초안 유지. 오류를 표시하고 같은 저장 버튼으로 재시도 | 구현 |
| 설정 닫기 | 미저장 입력 초안 폐기. 진행 중인 저장 성공은 계정에 반영하고 다시 열 때 현재 닉네임 표시 | 구현 |
| 로그인 버튼 선택 | 기존 Google 로그인 흐름으로 진입 | 구현 |
| 로그인 성공 | 설정과 프로필 탭을 유지하고 로그인 상태 표시. 현재 닉네임을 편집할 수 있는 화면으로 전환 | 구현 |
| 로그인 실패 | 프로필 탭을 유지하고 탭 안에 오류 표시. 같은 로그인 버튼으로 재시도 | 이동 전 반환·예외 오류, 복귀 URL 오류와 인증 SDK 초기화 오류 처리 구현 |
| 사용자 로그인 취소 | 오류 표시 없이 비로그인 상태의 프로필 탭으로 복귀 | `error=access_denied`이고 별도 실패 코드가 없는 복귀 처리 구현 |
| 로그아웃 버튼 선택 | 확인창 없이 로그아웃 실행. 완료 시 프로필이 마운트되어 있고 설정이 열려 있으면 설정을 닫고 타이틀 화면으로 이동. 먼저 설정을 닫았다면 현재 화면 유지. 실패하면 열린 탭에 오류 표시 | 구현 |

Google로 이동하기 전에 현재 탭의 `sessionStorage`에 시작 시각과 함께 복귀 의도를 저장한다. 시작 후 10분까지 유효하며, 10분을 넘겼거나 값이 잘못된 의도는 지우고 무시한다. 앱 재시작 또는 뒤로 가기의 bfcache 복원(`pageshow.persisted`) 때 곡 선택 위에 설정·프로필 탭을 열며, 실제로 탭을 열 때 의도를 한 번만 소비한다. 데스크톱에서 첫 실행 상태라면 키보드 프리셋 선택을 먼저 마친 뒤 프로필 탭을 연다. 프리셋 설정 중 새로고침해도 원래 시작 시각의 의도를 유지하며, 유효 시간이 지나면 자동 복귀하지 않는다. 모바일은 곡 목록 전용 경험을 유지하며 프리셋 선택 없이 목록 위에 프로필 탭을 열고 첫 실행 상태를 보존한다. 모바일 로그아웃도 내부 화면은 타이틀로 바꾸고 설정을 닫지만, 기존 모바일 분기에 따라 곡 목록을 계속 표시한다.

복귀 URL의 query·hash에서 인증 오류를 읽고, 프로필 탭을 열 때 인증 결과 매개변수(오류와 처리하지 못하고 남은 토큰)만 제거한다. Google 로그인의 복귀 주소에는 현재 경로와 나머지 query·hash를 그대로 넣되 이전 로그인이 남긴 인증 결과 매개변수는 넣지 않아, 새 로그인이 이전 오류나 토큰을 다시 읽지 않게 한다. 프로필 탭의 로그인은 Google로 이동하기 전에 현재 history 항목의 주소에서도 같은 매개변수를 제거한다. 그래서 Google에서 뒤로 가기로 돌아온 bfcache 복원이나 새로고침이 헤더 로그인 등이 남긴 이전 오류를 새 복귀의 결과로 표시하지 않는다. 주소를 바꾸지 못해도 로그인은 진행한다. `error=access_denied`이면서 `error_code`가 없거나 `access_denied`인 경우만 사용자 취소로 취급한다. `signup_disabled` 등 다른 `error_code`가 있으면 실패로 처리해 설명을 표시한다. 실제 Google 취소 URL의 왕복 검증은 아직 하지 않았다. 인증 SDK의 초기화 결과도 기다려 토큰 처리·사용자 조회 실패를 해당 페이지 로드의 첫 복귀 시도에 표시하며, 사용자 취소에는 SDK 오류를 표시하지 않는다. bfcache 복원은 새 OAuth 콜백을 처리하지 않으므로 이전 SDK 초기화 오류를 다시 표시하지 않고 현재 복귀 URL의 결과만 사용한다. 단, 같은 복귀 의도를 아직 소비하지 않은 채(첫 실행 프리셋 선택 대기 등) 복원되면 그 의도에 대해 이미 얻은 결과를 SDK 초기화 오류까지 그대로 유지해 프로필 탭을 열 때 표시한다. 세션의 로그인 상태는 기존 인증 흐름으로 확인한다. `sessionStorage` 접근이 차단되면 로그인 자체는 계속 사용할 수 있지만 페이지 이동 후 프로필 자동 복귀는 보장하지 않는다.

로그아웃 대기 중 설정을 닫거나 다른 화면으로 이동해도 로그아웃 자체는 완료하지만 뒤늦게 타이틀로 이동하거나 새 설정에 오류를 쓰지 않는다. 로그아웃 후에도 직전에 쓰던 게임 설정을 유지한다. 서버 설정 불러오기·저장 실패 등 설정 동기화 동작은 [계정 설정 동기화](#계정-설정-동기화)를 따른다.

### 설정 접근

```
곡 선택 → 설정 → 곡 선택
설정 → 오프셋 캘리브레이션 → 설정  [진입 숨김, PR 2·3 대기]
곡 선택 → ? 도움말 모달 열기 → 닫기  [구현]
```

**첫 기동 튜토리얼 모달**: 프리셋 설정 뒤 곡 선택 화면 위에 도움말을 연다. 모달은 처음부터 바로 닫을 수 있으며, 단계 진행이나 스킵을 닫기의 조건으로 두지 않는다. 모달 자체와 `?` 버튼 재진입은 구현되어 있으나 첫 기동 자동 열기는 미구현이다([RFD 0055](../rfd/0055-first-launch-tutorial-modal.md)).

튜토리얼은 첫 기동 이후에도 곡 선택 화면에서 재진입할 수 있다. 유저가 특정 메커니즘을 복습하고 싶을 때 접근할 수 있어야 한다.
현재 도움말 모달은 `Basic`과 `Advanced` 탭에서 기본 입력과 복합 판정 규칙을 확인하는 미리보기이며, Phase 1～4의 전체 학습·실습 구현과는 구별한다. 이 팝업은 오디오 없이 튜토리얼 전용 차트와 예시 입력을 반복 재생한다. 실제 플레이와 같은 `NoteJudgmentSession`으로 판정·정산하며 판정 이펙트를 표시한다. 결과 기록은 만들지 않는다. 반복 경계 시각의 마지막 입력까지 이전 세션에서 정산한 뒤 세션과 노트 표시 상태를 초기화한다.

### 스페셜 땡스

```
타이틀 → 스페셜 땡스 → 타이틀
```

**타이틀에서 접근하는 이유**: 스페셜 땡스는 게임 플레이와 무관한 크레딧 정보이므로, 플레이 흐름(곡 선택 → 플레이 → 결과) 안에 배치할 필요가 없다. 타이틀 화면에 배치하여 관심 있는 유저만 자발적으로 접근하도록 한다.

**스페셜 땡스에 표시하는 내용**: 음원 제공자(아티스트), 이미지·에셋 제공자, 오픈소스 라이브러리 라이선스(`project-assets.md`의 저작권 표기 의무 이행), 기타 기여자 크레딧. 라이선스에 의해 표기가 의무인 항목은 반드시 이 화면에 포함한다.

## 판정 실행 구조

아래는 현행 실행 경로와 구형 hold 수 수리 브랜치의 검증 기록이다. 해당 커밋의 수치·옛 사례 결과는 그대로 보존한다. 새 모델의 컴파일러는 바디에서 점수 항목을 추론하지 않고, 명시 항목·바디 몫·실패 종속 관계를 세션에 전달해야 한다. 기존 `createCore` 교체만으로 새 차트·정산·표시를 지원한다고 보지 않는다. 현행 커서 필터와 `max(시작·끝)+Good` 계산도 새 유지 보류·명시 릴리즈 기한을 대신하는 확정 계약으로 고정하지 않는다.

`compileJudgmentChart`가 정확한 Beat 경계, head 관계, unit 수, 점수 항목, 트릴 구간 귀속을 한 번 계산한다. 에디터 커서부터 테스트할 때는 `selectCompiledJudgmentChart`로 원래 noteIndex를 보존하면서 제외한 노트의 점수 항목·시간 맵·연결을 함께 제거한다.

`NoteJudgmentCore`는 차트와 시각별 입력만 받아 상태 전이와 확정 판정을 만든다. `NoteJudgmentSession`이 이 core와 `ScoreManager`를 묶고 `ConfirmedJudgmentEffects`를 적용한다. 세션은 core를 구현 클래스 대신 `JudgmentCore` 경계로 다루며 생성 함수 `createCore`로 받는다. 기본값은 `NoteJudgmentCore`이고, 다른 core는 테스트에서만 `createCore`로 넘긴다. 실제 플레이와 튜토리얼의 판정 진입점은 이 세션이다. 이전 `JudgmentEngine`은 호환 회귀용이며 현재 모델의 규칙 원본으로 사용하지 않는다.

`InputTimeline`은 키보드와 `AutoPlayer.eventsThrough` 입력을 원래 timestamp별로 묶는다. 입력 오프셋은 `GameClock.toInputTimeMs`에서 한 번만 적용한다. 프레임 진행은 판정 시간과 현재 입력 시간 중 이른 시각까지로 제한하여 음수 오프셋(늦게 누르는 사람의 보정)의 Good 창을 잘라내지 않는다. 합성(auto) 입력도 그 진행 시각까지만 만들어, 뒤의 auto 입력이 늦게 도착할 수동 입력보다 먼저 core를 앞당기지 않게 한다. 곡 끝 정산 조건을 통과한 뒤에도 남은 auto 입력 생성·큐 비우기 순서를 유지한다(`finishPlaySession`). 이미 수집한 양수 오프셋(일찍 누르는 사람의 보정) 입력이 core를 앞당겼으면 과거 프레임 시각으로 되돌리지 않고, 큐에 앞서 있는 시각까지 합성 입력을 먼저 수집하여 시간순으로 전달한다.

핸들러 지연으로 core보다 과거의 입력이 도착하면(관측 batch, `processObservedBatch`) 미확정 대상에만 원래 입력 시각의 창·등급을 적용하고, 관측한 현재 시각에 확정한다. 미확정 대상은 아직 판정하지 않은 점수 항목이며, hold 수 코어에서는 시간 진행이 이벤트 없이 바꾼 바디 상태(S에서 hold 수 요구를 시작하고 바디를 시작한 것, E에서 release 대기로 넘어가거나 이어지는 몫을 완료한 것, E−Good 뒤 이벤트 없이 일찍 완료한 것, head 기한 정산에서 뒤 바디를 채웠다고 본 것)도 포함한다. 이 상태는 늦은 입력이 그 레인 hold 수에 반영되는 시각을 기준으로, S·E 진행과 E−Good 뒤 이른 완료는 그 시각보다 뒤의 것을, head 기한 정산은 기한이 그 시각 이상인 것을 되돌려 다시 계산한다. 그 진행에 딸려 바뀐 다른 몫의 상태도 함께 되돌린다([RFD 0032 구현 규칙](../rfd/0032-body-held-count.md#구현-규칙-판정-시각과-입력-순서)의 늦은 전달). 이미 확정한 Miss·실패 unit을 복구하거나 점수·콤보를 소급 변경하지 않는다.

**hold 수 코어의 시각 계약(구현 중, [#287](https://github.com/nanana3679/not4k/issues/287)).** 플레이어가 느끼는 규칙은 RFD 0032 구현 규칙을 따르고, 코어 경계에서는 아래를 지킨다. 실제 플레이는 교체 전까지 기존 `NoteJudgmentCore`를 쓰며, 기존 코어는 크래시가 아니면 고치지 않는다. 예의 결과는 따로 적지 않으면 공개 전 로컬 수리 브랜치(`repair/hold-count-core`, `7fece8e`)의 실측이다.

- **입력 전 기한 확정:** 입력을 넣기 전에 그 입력 시각보다 이른 기한을 먼저 확정한다. `LaneHoldTracker`는 지난 부족을 기억하지 않으므로 회복 down을 먼저 넣으면 이미 지난 유지 실패를 확정하지 못한다.
- **늦은 전달의 다시 계산:** RFD 0032 구현 규칙의 “늦은 전달은 확정 전 상태만 다시 계산”의 세부다.
  - **관측한 시각:** 실제 세션은 입력을 코어에 넘길 때의 코어 시각을 관측한 시각으로 넘긴다. 코어를 직접 호출할 때는 그보다 늦은 관측 시각도 받으며, 그러면 먼저 그 시각까지 진행한다(아래 “관측 시각이 코어 시각보다 늦은 호출”).
  - **아직 확정하지 않은 상태:** S에서 hold 수 요구를 시작하고 바디를 시작한 것, E에서 release 대기로 넘어가거나 이어지는 몫을 완료한 것, head 기한에서 뒤 바디를 채웠다고 본 정산이다. E−Good 뒤 이벤트 없이 일찍 완료한 것도 같은 성격이라 여기에 넣는다(도출, 2026-10-18에 승인한 목록에는 없다).
  - **기준 시각 h:** 늦은 입력이 그 레인의 hold 수에 반영되는 시각이다. raw 시각이며, 같은 레인에 이미 넣은 입력보다 이르면 그 레인의 마지막 입력 시각이다(레인별 clamp).
  - **되돌리는 것:** h보다 뒤인 진행(S·E 진행, E−Good 뒤 이른 완료)과 기한이 h 이상인 head 기한 정산, 그리고 그 진행에 딸려 바뀐 다른 몫의 상태다. h와 같은 시각의 S·E 진행(같은 시각에는 진행 먼저)과 확정한 판정은 되돌리지 않는다. 다시 계산해 나온 판정은 관측한 시각에 확정한다.
  - **head 기한 정산의 두 갈래:** 뒤 바디를 채웠다고 본 정산은 이벤트가 없어 다시 계산한다. 채우지 못했다고 본 정산(head Miss와 그 몫의 실패)은 확정한 판정이라 되돌리지 않는다. 예: RFD 0032 §5-2 차트에서 A up raw 2115가 관측 시각 2121에 도착하면 2120의 head Miss는 남고, 채웠다고 본 정산만 되돌려 Miss 1이다. N3 끝 종속 0점은 관측 시각 2121의 확정 묶음에 들어간다(기한 정산에서 생긴 종속 0점은 보통 그 기한 시각의 묶음이다).
  - **예:** `head 1000` + `doubleLong [1000,3000]`, A 800–990, B·C 1050–3000에서 코어가 1001까지 진행한 뒤 A up 990이 1017 프레임에 도착해 관측 시각 1001로 넘어오면, A가 눌린 채 1000을 지나 한 몫을 시작한 것으로 본 진행을 되돌려 Great 1·Perfect 2다. 다시 계산하지 않으면 그 몫이 1020에 유지 실패해 Perfect 1·Great 1·Miss 1이다(되돌리기를 넣기 전 수리 브랜치에서도 같다. RFD 0032 §4-3 문언대로 head가 있는 바디에 재충전이 없을 때의 값). `long [1000,2000]`, A 1000–1500·1515–2000에서 1520 유지 Miss가 확정된 뒤 회복 down 1515가 관측 시각 1530에 도착하면 Miss 1은 그대로다. 즉시 전달이면 Perfect 1·Miss 0이다.
- **레인별 clamp:** 관측 batch에서 raw 시각이 같은 레인에 이미 넣은 입력보다 이르면 그 레인의 마지막 입력 시각으로 hold 수에 넣는다. [#287 설계 결정 3](https://github.com/nanana3679/not4k/issues/287#issuecomment-6243743086)(“관측 batch에서 raw 시각이 이미 넣은 입력보다 이르면 tracker에는 마지막으로 넣은 시각으로 올려 넣는다(시간 역행 방지)”, 2026-10-18 승인)의 구현 세부이며, 부족 기록이 레인별이라 레인별로 지킬 수 있다. 전역 clamp를 쓰면 다른 레인 입력 유무로 결과가 바뀐다. 예: 레인 1 `long [1000,2000]`을 A down 1000으로 시작하고, 코어가 1501까지 진행한 뒤 A up raw 1490을 관측 시각 1501에 받고, 이어서 A down 1512·A up 2000이면 1510에 유지 Miss다. 레인 2에 `long [1400,2000]`과 제때 전달된 B down 1500이 있어도 같다. 수리 전 첫 구현(전역 clamp)에서 실측하면 레인 2 입력이 있는 쪽만 release Perfect였다.
- **lane 필수:** [#287 설계 결정 2](https://github.com/nanana3679/not4k/issues/287#issuecomment-6243743086)(“새 코어는 lane을 필수로 받는다”, 2026-10-18 승인)에 따라 lane 없는 입력이 하나라도 있으면 그 batch를 전혀 반영하지 않고 예외를 던진다.
- **같은 at 분할과 첫 호출:** 같은 at의 `processBatch`가 두 번 오면 도착 순서대로 처리하며, 같은 timestamp 입력의 순서 보장은 한 batch 안에만 적용한다. 첫 호출이 `processBatch`여도 그 앞의 기한을 입력보다 먼저 확정한다. 기존 코어는 시작 시각이 `-Infinity`라 첫 `processBatch`에서는 지난 기한을 입력 뒤에 정산하며, 교체 전까지 두는 알려진 차이다.
- **한 drain의 늦은 입력 묶음:** 세션 drain은 raw가 코어 시각보다 이른 입력 묶음을 모아 한 번에 넘기고(가칭 `processObservedBatches(groups, observedAt)`, 지금은 입력 묶음마다 `processObservedBatch`), raw가 코어 시각 이상인 입력 묶음은 지금처럼 `processBatch`로 넘긴다. hold 수 코어는 모든 입력 묶음의 되돌리기를 먼저 한 뒤 raw 순서로 넣고, 입력 묶음 사이에는 다음 raw보다 이른 기한과 그 raw까지의 진행만 처리한다. 기존 코어는 입력 묶음마다 `processObservedBatch`를 부르는 위임이라 동작이 같다. 예: `long [1000,2000]`을 A down 1000으로 시작하고 코어가 프레임 1490·1530으로 1530까지 진행한 뒤, A up raw 1500과 B down raw 1507이 다음 프레임(1546)의 drain에 함께 오면 관측 시각 1530으로 한 번에 넘긴다. 그러면 B up 2000이 release Perfect다. 입력 묶음마다 따로 넘기면 첫 입력 묶음이 1530까지 진행해 기한 1520의 유지 Miss를 1530에 확정한다.
- **제때 전달의 프레임 독립:** 입력을 모두 제때 전달하면(`processBatch`만) 프레임 간격, 같은 시각 `advance` 삽입, 한 batch 안 서로 다른 키의 순서, 키 이름 치환, 다른 레인 추가는 등급·실패·확정 시각을 바꾸지 않는다. [#287](https://github.com/nanana3679/not4k/issues/287) 계획의 3e-1·3j-3에서 테스트로 고정할 계약이다.
  - 수리 브랜치는 그 일부만 실측했다. 독립 노트 행렬(E=1000·1060·2000)의 같은 시각 `advance` 유무, RFD 0032 §5-2 차트와 §5-4 차트의 16ms 프레임, 길이 0 `holdOnly [1000,1000]`의 같은 시각 `advance` 유무(진행 먼저), `head 1000`에서 1120에 멈춘 프레임 뒤 down 1120의 Good(+120, 두 코어 모두) 등이다.
- **지연 동치와 깨끗한 실행:** 입력 순서를 지킨 지연에서 깨끗한 실행은 등급·Miss 수·실패한 unit·release를 받은 unit이 즉시 전달과 같고, 확정 시각과 그 순서를 따르는 콤보 표시만 다르다. 깨끗한 실행은 지연된 입력을 넘긴 drain 전에 그 레인에서 확정 시각이 raw 시각 이상인 판정이 없는 실행이다. clamp와 되돌리기가 레인별이라 이 조건도 그 레인만 본다. 늦은 입력이 up뿐이면 이 조건에서 head Miss는 빼고 본다(up은 head를 치지 못한다). 실측: 세션 drain 지연 퍼즈(프레임 간격 8～50ms, 순서를 지킨 지연 0～15·0～40·0～130ms)에서 깨끗한 실행 6,479·7,489·2,851건(지연 범위 순)이 즉시 전달과 차이 0이었다. 두 레인 실행에서 깨끗한 레인 784·295개(0～40·0～130ms)의 그 레인 판정이 즉시 전달과 같았다(수리 브랜치에서 `7fece8e`보다 앞선 커밋으로 실행).
- **관측 시각이 코어 시각보다 늦은 호출:** 관측 시각까지 진행한 뒤 도착한 것과 같다. 그래서 관측 시각보다 이른 기한은 입력보다 먼저 확정한다. 예: `head 1000` + `long [1000,2000]`을 A 1000–1480·1490–2000으로 치고 1490 down만 늦게 전달한다. 코어가 1500까지 진행한 뒤 그 down을 관측 시각 1501에 받으면, 유지 기한 1500을 입력보다 먼저 확정해 1500에 유지 Miss다. 관측 시각이 1500이면 열린 기한 1500 전에 회복해 Perfect 2다. 기존 코어도 `processObservedBatch`에서 `sweepBefore(observedAt)`로 관측 시각 전 기한을 먼저 확정한다.
- **같은 시각 이벤트 순서:** 같은 확정 묶음에서 같은 시각에 끝나는 두 unit의 이벤트 순서는 보장하지 않는다.

오디오가 끝나도 P는 AudioContext 경과 × r로 계속 진행한다. J가 재생 구간 끝에 닿고 진행 상한이 모든 노트의 max(시작·끝) + Good 창 중 최댓값을 지난 뒤에만 남은 수집 입력을 전달하고 `finalize()`로 정산한다. `NoteJudgmentSession.latestJudgmentDeadlineMs`를 곡 끝 검사와 `finalize()`가 공유하므로 끝의 늦은 입력 창을 강제로 자르지 않는다. 이 대기 중 일시정지하면 P를 고정하고 재개하면 시계만 이어 가며, 끝난 음악은 다시 재생하지 않는다. 결과와 디버그 로그는 정산 뒤 만든다.

`SessionRendererAdapter`는 head의 처리 상태와 바디의 unit 상태를 구분한다. 바디 상태 조회는 같은 렌더 시각에 한 번만 복사하고, 새로운 확정 묶음·반복 초기화 뒤에는 다시 조회한다. 판정 사례와 테스트 경계는 [구현 계획](../plans/note-judgment-implementation.md)을 따른다.
