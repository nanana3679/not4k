# not4k — 게임 코어 설계

> 판정 규칙은 [RFD 0020](../rfd/0020-note-judgment-units-and-inheritance.md)와 [판정 사례 명세](note-judgment-cases.md)를 우선한다. 현재 플레이·자동 입력·튜토리얼은 이 모델을 공통으로 사용하며, 세부 검증 기록은 [PRD §12](../prd.md#12-미정-사항)를 따른다.

## 현재 채택 판정 경계

정적 차트 해석이 Beat 기반 연결 topology와 score item을 한 번 계산한다. 런타임은 그 결과를 소비하며 ms threshold로 차트 관계를 다시 추정하지 않는다. unit별 시작·유지·release 상태를 독립적으로 처리하고, 유효한 head 또는 시작 입력으로 승계된 unit은 추가 down을 소비하지 않는다. 일반 connection 성공은 점수·콤보를 증가시키지 않으며, head·실제 release·`holdOnly`만 ScoreManager에 정산한다. 실패한 unit은 부활하지 않고 다른 건강한 unit으로 전파하지 않는다.

이 문서는 노트 시스템과 스코어링 이외의 게임 본체 동작 — 플랫폼, 인증, 랭킹, 입력 매칭, 스크롤, 오프셋, 게임 화면, 상태 흐름 — 을 정의한다.

## 플랫폼

**웹 게임**으로 개발한다. 브라우저에서 직접 플레이하며, 별도 설치가 필요 없다.

**웹을 선택한 이유**: not4k는 무료 게임이다. 무료 게임의 핵심 과제는 진입 장벽 최소화이며, 웹은 "URL 클릭 → 즉시 플레이"라는 가장 낮은 진입 장벽을 제공한다. 설치 과정이 유저 이탈의 주요 원인이 되는 점을 감안하면, 웹이 최적의 배포 방식이다. 부수적으로 Windows/Mac/Linux를 동시에 지원하며, 업데이트 배포가 즉각적이다.

### 온라인 전용

**오프라인 플레이는 지원하지 않는다.** 차트 데이터는 서버에서 스트리밍되며, 서버 연결이 필수이다.

**온라인 전용인 이유**: 첫째, 음원 저작권 비용 구조상 스트리밍이 유리하다. 저작권이 있는 음원을 사용할 경우, 유저에게 다운로드(복제)를 허용하면 복제권 라이선스 비용이 높아지지만, 스트리밍(전송)은 상대적으로 비용이 낮다. 향후 라이선스 음원을 도입할 가능성을 고려하면, 처음부터 스트리밍 기반으로 설계하는 것이 합리적이다. 둘째, 차트 추가·수정이 서버 측에서만 이루어지므로 배포가 단순하고, 랭킹과 플레이 기록도 서버 의존이므로 온라인 전용으로 통일하는 것이 구조적으로 일관된다. 오프라인 모드를 별도로 유지하면 로컬 캐싱, 동기화, 충돌 해결 등의 복잡도가 발생한다.

## 인증

### 소셜 로그인

**Google 소셜 로그인**을 제공한다. `[미구현 — 게임 클라이언트]` 에디터에서만 Google OAuth 구현.

**Google만 제공하는 이유**: 단일 제공자로 시작하여 구현 복잡도를 최소화한다. Google은 가장 범용적인 계정이며, 게임 유저 대부분이 보유하고 있다. 필요에 따라 추후 제공자를 추가할 수 있다.

### admin 권한

admin 권한은 Supabase Database의 `profiles` 테이블에서 `is_admin` 플래그(`boolean`, 기본값 `false`)로 관리한다. 클라이언트는 로그인 시 `profiles.is_admin`을 조회하여 admin 여부를 판단한다.

**현재 admin 부여 방식**: 별도의 admin 관리 UI는 없다. 개발자가 **Supabase 콘솔에서 직접** `profiles` 테이블의 `is_admin` 값을 변경한다.

**admin 권한의 영향 범위**:
- 곡 선택 화면: 비공개 곡 접근, Edit 버튼 표시
- 차트 에디터: 진입 가능 (admin이 아닌 유저는 에디터 접근 불가)

### 비로그인 플레이

**로그인 없이도 플레이할 수 있다.** 단, 비로그인 상태에서는 다음 기능이 제한된다:

- 플레이 기록 저장 불가
- 랭킹 등록 불가
- 설정/오프셋 서버 동기화 불가

**비로그인 플레이를 허용하는 이유**: 웹 게임의 진입 장벽 최소화 원칙과 일치한다. "계정 만들기"가 첫 플레이 전에 강제되면 이탈률이 급증한다. 유저가 먼저 게임을 체험하고, 기록을 남기고 싶을 때 자발적으로 로그인하는 흐름이 전환율 측면에서 유리하다.

### 비로그인 유저의 로컬 설정 저장

비로그인 상태에서도 다음 설정은 **브라우저 localStorage에 저장**되어 재방문 시 유지된다:

- 키 바인딩 프리셋 및 커스텀 바인딩
- 스크롤 속도
- 오디오/입력 오프셋
- 리프트/서든 설정
- 마스터 볼륨
- 스킨 선택 (`skinId`)
- 키봄 크기 (`bombScale`, 기본 1배)
- 선택한 언어

**localStorage를 사용하는 이유**: 매 방문마다 키 바인딩과 오프셋을 재설정해야 한다면, 비로그인 플레이의 진입 장벽 최소화 의도가 무의미해진다. localStorage는 별도 서버 통신 없이 브라우저에 데이터를 유지하므로, 비로그인 구조와 일관된다.

**로그인 시 동기화**: 비로그인 상태에서 설정을 변경한 뒤 로그인하면, 로컬 설정과 서버 설정 중 **서버 설정을 우선**한다. 단, 서버에 설정이 없는 경우(첫 로그인) 로컬 설정을 서버로 업로드한다. `[미구현]`

## 랭킹 `[미구현]`

### 차트별 랭킹

**차트(곡 + 난이도) 단위로 달성률 순위**를 제공한다. 로그인한 유저의 플레이 기록 중 최고 달성률이 차트별 랭킹에 등록된다.

**차트별 랭킹을 선택한 이유**: 리듬게임의 경쟁은 특정 차트에서의 성적 비교가 핵심이다. 전체 순위(볼포스류)는 난이도 책정이 정확해야 의미가 있으므로 추후 도입하고, 차트별 랭킹은 난이도 책정과 무관하게 즉시 동작한다. 유저가 "이 곡에서 내가 몇 등인지" 확인하는 것이 가장 직접적인 동기 부여다.

### 랭킹 표시

곡 선택 화면에서 **랭킹 모달**을 열어 차트별 상위 기록과 자신의 순위를 확인할 수 있다. 곡 선택 화면 자체에 랭킹이 직접 표시되지는 않으며, 유저가 원할 때 모달로 접근한다.

## 입력-노트 매칭

### 매칭 규칙

유저가 키를 누르면, 해당 레인에서 **가장 이른(earliest) 노트**에 매칭된다. Good 판정 창(Normal ±120ms, Easy ±150ms) 안에 복수의 노트가 존재하면, 시간순으로 가장 앞에 있는 노트가 입력을 `consume`한다.

**가장 이른 노트 매칭을 선택한 이유**: "가장 가까운 노트" 매칭은 이른 입력이 뒤의 노트에 `consume`되어 앞의 노트가 Miss 처리되는 직관적이지 않은 상황을 만든다. 가장 이른 노트 매칭은 노트의 판정 순서가 항상 배치 순서와 일치하므로, 유저가 결과를 예측하기 쉽다. osu!mania 등 대부분의 리듬게임이 이 방식을 사용한다.

### 헤드 없는 롱노트의 keydown `consume`

양수 바디의 실제 미처리 시작은 S±Good 안의 down을 소비하되 시작 점수는 없다. 자기 head가 담당하는 unit은 그 head 입력으로 시작하고, single head + double 바디의 남은 unit은 자기 시작 down 또는 정당한 승계가 필요하다.

이미 정당한 승계로 준비한 unit은 S 전에도 불필요한 down을 가져가지 않는다. 임의의 raw held와 다른 독립 Point가 소비한 down은 시작을 대신하지 않는다. 길이 0 일반 release도 시작 준비를 요구하지만, 길이 0 `holdOnly`는 기존 held 상태를 공유하며 down을 소비하지 않는다. 입력 사례는 [NJ-A01~A06 및 NJ-Z01](note-judgment-cases.md#nj-a01)을 따른다.

### keyup 소비 (약칭 R2 — 가장 이른 매칭)

keydown은 적격한 Point·head·미처리 시작 unit 중 가장 이른 대상을 소비한다. keyup은 누름별 release 권한과 정적 score item의 대상 unit을 따라 실제 release 하나만 소비한다. release는 Perfect/Great/Good/Miss로 판정하며, `holdOnly` 완료는 keyup 소비와 분리한다. Beat가 정확히 맞닿은 connection의 계속되는 몫은 무점수 승계이며, 줄어드는 몫은 실제 release 또는 명시된 holdOnly로 처리한다. 고정 물리 owner를 두지 않고 등록된 유지 키와 누름별 권한을 추적한다. 실패한 unit은 부활하지 않고 다른 unit에 전파하지 않는다.

### 빈 레인 입력

시각적으로 비어 보이는 레인에서 키를 눌렀다고 임의의 Bad를 생성하지 않는다. 적격한 Point·head·시작 대상이 없으면 입력은 소비하지 않는다.

입력 소비는 차트의 적격 대상과 score item을 기준으로 하며, 차트에 없는 Bad 패널티를 추가하지 않는다.

## 노트 스킨

곡 선택 화면의 `Settings → Skin`에서 **Crystal**과 **Classic**을 선택한다. 기본값은 Crystal이며 선택한 `skinId`는 localStorage에 저장되어 다음 플레이와 재방문에 적용된다. Prism·Simple·Note Asset Lab은 인게임 선택지에서 숨긴다.

Classic은 확정한 유광 싱글·더블 포인트, 석영 Trill, 반복 바디, 수정된 시작·끝 터미널, 그림자·Grace와 16프레임 실버 봄을 사용한다. 실제 플레이와 Lab 시연은 같은 `/skins/classic/` PNG를 읽는다. 시연 페이지와 SVG 자료는 개발 빌드에만 포함하지만, 이 런타임 PNG는 프로덕션 빌드에도 포함한다. 디자인 규격과 제작 방법은 [노트 에셋 Lab 명세](note-asset-lab.md)를 따른다.

같은 `Skin` 설정의 `Key Bomb Size`에서 인게임 키봄 크기를 **0~3배**, **0.1배** 단위로 조절한다. 기본값 1배는 기존 120×120 논리 픽셀 크기이며, 3배는 360×360이다. 레인 중앙·판정선을 중심으로 가로·세로를 같은 배율로 바꾸고 재생 시간은 유지한다. 0배는 키봄을 생성하지 않으며 판정·점수에는 영향을 주지 않는다. 값은 모든 스킨에 공통 적용하고 localStorage에 저장한다. 이 값이 없는 기존 설정은 1배로 복원한다.

## 스크롤 속도

### BPM 독립 절대 속도

스크롤 속도(노트 낙하 속도)는 **BPM과 무관한 절대 속도**이며, 유저가 자유롭게 조절할 수 있다. 범위 **1.0~8.0**, 기본값 **4.0**, 소수점 아래 1자리까지 표시.

- 곡의 BPM이 변해도 스크롤 속도는 일정하다.
- BPM 변화 구간에서 노트 간격이 변하지 않으므로, 유저의 읽기 리듬이 깨지지 않는다.

**BPM 독립 속도를 선택한 이유**: BPM 연동 속도(IIDX의 Hi-Speed)는 BPM이 변하는 곡에서 소프란(soflan) 현상을 만든다. 유저가 BPM 변화 구간을 암기해야 하며, 이것은 리듬 감각이 아닌 암기력을 테스트하는 요소다. not4k는 가변 손배치와 차트 인식이라는 핵심 인지 부하에 집중해야 하므로, 스크롤 속도를 BPM에서 분리하여 불필요한 인지 부하를 제거한다. osu!mania, Arcaea 등 최근 리듬게임은 대부분 이 방식을 채택하고 있다.

## 프레임레이트

**렌더링 프레임레이트의 상한(cap)을 유저가 선택**할 수 있다. 선택지: **60fps / 120fps / 144fps / 무제한(Uncapped)**.

- 기본값은 60fps. 유저가 설정 화면에서 변경할 수 있다.
- 판정 로직은 프레임레이트에 의존하지 않는다. 입력 타이밍은 `KeyboardEvent.timeStamp` 기반이고, 오디오 동기화는 AudioContext 마스터 클럭 기반이므로 프레임레이트가 판정 정확도에 영향을 주지 않는다.

### 구현 원리

`requestAnimationFrame`(rAF)은 브라우저가 모니터 주사율에 맞춰 호출하며, 호출 주기 자체를 변경할 수 없다. 프레임레이트 캡은 **rAF 콜백 내에서 목표 간격 미달 시 렌더링을 스킵**하는 방식으로 구현한다. 예: 144Hz 모니터에서 60fps 캡을 설정하면 rAF는 144회/초 호출되지만 렌더링은 ~60회/초만 실행된다. 무제한 설정 시 매 rAF마다 렌더링한다.

이 설정은 프레임레이트를 "보장"하는 것이 아니라 **상한을 제한**하는 것이다. 실제 프레임레이트는 모니터 주사율, GPU 성능, 브라우저 상태에 의존한다. 다만 2D 노트 렌더링의 GPU 부하가 극히 낮으므로, 일반적인 하드웨어에서 60fps 유지는 사실상 보장 가능한 수준이다.

**유저 선택으로 제공하는 이유**: 고주사율 모니터(120Hz, 144Hz) 유저는 높은 프레임레이트에서 더 부드러운 노트 낙하를 경험할 수 있다. 반면 저사양 환경에서는 높은 프레임레이트가 프레임 드롭을 유발할 수 있으므로, 하드웨어에 맞는 설정을 유저가 직접 선택하도록 한다.

## 마스터 볼륨 (Master Volume)

게임 전체의 오디오 출력 볼륨을 조절하는 설정. 범위 **0~100%**, 기본값 **100%**. 내부적으로 0.0~1.0 값으로 저장된다.

- **적용 범위**: 게임 플레이 음원, 에디터 재생 음원, 곡 선택 화면 프리뷰 음원 등 모든 오디오 출력에 적용된다.
- **설정 모달**: 곡 선택 화면에서 여는 설정 모달의 Gameplay 섹션에서 슬라이더로 조절한다.
- **에디터 접근**: 에디터 툴바의 Settings 버튼을 통해 마스터 볼륨 슬라이더가 포함된 팝오버를 열어 조절할 수 있다. 에디터에는 별도의 볼륨 슬라이더를 두지 않고, 마스터 볼륨으로 통합한다.
- **저장**: localStorage에 저장되어 재방문 시 유지된다.

**단일 마스터 볼륨으로 통합하는 이유**: 게임·에디터·프리뷰 각각에 별도의 볼륨 설정을 두면, 유저가 컨텍스트를 전환할 때마다 볼륨을 재조정해야 한다. 단일 마스터 볼륨으로 통합하면 한 곳에서 조절한 값이 모든 오디오에 일관되게 적용된다.

## 리프트 / 서든 (Lift / Sudden)

시각 정보를 의도적으로 차단하여 집중력을 높이기 위한 플레이 설정.

### 서든 (Sudden) `[부분 구현 — 설정값만 저장, 마스크 렌더링 미구현]`

레인 상단을 커버로 가려, 노트가 화면에 보이는 시간을 줄인다. 유효 시야(Effective Field of View)를 제한함으로써 뇌가 처리해야 할 정보량을 줄이고, 역설적으로 처리 효율을 높인다.

### 리프트 (Lift)

판정선의 위치를 기본 위치(레인 최하단)에서 위로 올린다. 노트의 이동 거리가 짧아지므로, 유저의 시선이 화면 하단에 고정되지 않고 보다 자연스러운 위치에서 노트를 읽을 수 있다.

### 조합 사용

서든과 리프트를 함께 사용하면, 화면 중앙의 좁은 영역에서만 노트가 보이게 된다. 상급 플레이어는 이 조합을 통해 시선의 초점 범위를 극도로 좁혀 집중력을 극대화한다. IIDX에서 Sudden+와 Lift를 병용하는 것과 동일한 원리다.

## 오프셋

### 오디오 오프셋 (Audio Offset)

오디오 출력 지연을 보정하는 값. 음악 재생 타이밍을 전체적으로 이동시킨다. 출력 장치(스피커, 헤드폰, 블루투스 등)에 따라 달라지는 오디오 지연을 유저가 보정할 수 있다.

### 입력 오프셋 (Input Offset)

입력 장치 지연을 보정하는 값. 유저의 키 입력 타이밍을 전체적으로 이동시킨다. 키보드의 입력 지연이나 유저 개인의 체감 타이밍 차이를 보정한다.

### 오디오 레이턴시

오디오 동기화는 AudioContext 마스터 클럭 기반으로 최소 지연을 보장하며, 유저 하드웨어에 의한 나머지 지연은 오프셋 캘리브레이션으로 보정한다.

### 두 오프셋을 분리한 이유

오디오 지연과 입력 지연은 원인이 다르다. 블루투스 이어폰을 사용하면 오디오 지연만 크게 증가하고, 무선 키보드를 사용하면 입력 지연만 증가한다. 단일 오프셋으로는 이 두 가지를 독립적으로 보정할 수 없다. 유저가 출력 장치를 교체했을 때 오디오 오프셋만 재조정하면 되고, 입력 오프셋은 유지할 수 있다.

### 오프셋 캘리브레이션

가이드된 캘리브레이션을 제공한다. 설정 모달의 Gameplay > Audio에서 "Calibrate…"로 진입하며, **별도 화면이 아니라 설정 모달 내부의 서브뷰**로 열린다(진입/복귀 시 화면 전환 없음). Visual 보정(노트가 판정선에 도달하는 시점에 탭 → `judgmentOffsetMs`)과 Audio 보정(비트음에 맞춰 탭 → `audioOffsetMs`)을 각각 측정한다. 이와 별개로 같은 섹션에서 오디오/판정 오프셋을 수동 수치 입력(ms)으로도 조정할 수 있다.

**전용 화면을 제공하는 이유**: 오프셋 조정은 수치를 직접 입력하는 것보다 실제 음원에 맞춰 탭하고 편차를 측정하는 방식이 정확하고 직관적이다. 리듬게임 초보자에게 "오프셋을 ms 단위로 조정하세요"는 의미가 없으므로, 가이드된 측정 과정을 제공해야 한다.

## `flightRule` (`altitude` 게이지) `[미구현 — 난이도별 비행 배경·임시 `altitude` 모델·기어 게이지 구현, 클리어/실패 규칙 미구현]`

Play에는 **`altitude`** 기반 클리어/실패를 결정하는 **`flightRule`**이 적용된다. 초기 스펙의 "게이지 없음, 무조건 완주, 게임 오버 없음" 결정은 RFD 0001로 대체되었다.

**`altitude` 시각화 (기어 기둥 게이지)**: 기어 프레임 양 기둥 안의 발광 게이지는 프레임 이미지에서 분리된 별도 레이어이며(`scripts/split-gear-gauge.mjs` → `public/gear/`), 플레이 중 `altitude` 값(0~1)에 따라 아래 기준으로 높이가 변한다. `flightRule`이 구현되기 전까지는 배경 연출과 동일한 임시 `altitude` 모델(곡 진행에 따라 1→0)로 구동된다.

**도입 이유**: 첫째, 비행이라는 가벼운 내러티브를 게임 규칙과 연결하기 위해서다. `altitude`에 따라 배경 연출(지평선, 광원, 시야각)이 변하는 비행 콘셉트는, `altitude`가 장식이 아니라 실제 클리어/실패와 연결될 때 의미를 가진다. 둘째, 리듬게임에 익숙하지 않은 유저에게 클리어/실패라는 목표 구조와 동기를 제공하기 위해서다(RFD 0003).

**난이도명·시나리오**: `Liftoff → Infiltration → Breakthrough` 순서로 한 곡 안의 차트를 구분하며, 각 단계의 비행 시나리오와 연결한다([RFD 0022](../rfd/0022-flight-difficulty-names-and-visuals.md)). 이름 표시와 공개 시연 배경을 실제 게임에 연결했다([RFD 0026](../rfd/0026-game-flight-backgrounds.md)). 클리어/실패 규칙은 미구현이다. 풀 정의는 [glossary](../context/glossary.md#flightrule-flight-rule)를 따른다.

**단계별 연출**: `Liftoff`는 시선 각도를 유지하며 고도가 변한다. `Infiltration`은 낮아질수록 시선이 지면을 향해 회전하고 지평선이 위로 사라진다. `Breakthrough`는 낮은 고도에서 전방을 보며 계속 비행한다. `Breakthrough`의 낮은 시각 고도는 정상적인 숙련 비행이며, 실패 직전 상태로 일괄 해석하지 않는다. 중앙 레인·판정선·노트 속도는 배경 연출의 영향을 받지 않는다.

**시각적 구별**: 난이도별 색상 배합과 광원 밀도에 차이를 둔다. `Breakthrough`는 지평선 없이 화면 맨 위까지 광원이 움직이며 지나가도록 구성한다. 돌파의 주홍 후보는 사용자가 수용했으며, 다른 후보 배합과 광원 분포 제안은 [아트 디렉션 기록](../design/art-direction-notes.md#난이도별-색상과-광원-분포)을 따른다. 실제 게임에는 공개 시연의 현재 배색·광원 밀도를 사용한다. `Liftoff`는 속도300%, `Infiltration`은600%, `Breakthrough`는1000%이며 돌파의 건축 배경은 밝기10%·재귀 확대300%다. 세부 튜닝은 계속 가능하다.

**게임 배경 수명**: 기존 격자 배경을 공개 시연의 세 배경으로 교체했으며 이전 프리셋·시연·저장 API는 제거했다. 고도 모델은 `flightAltitude`, 배경 표시 옵션은 `showFlightBackground`로 관리한다. 게임이 계산한 고도 하나를 기어 게이지와 배경에 함께 전달한다. 곡 진행·판정에 따른 기존 임시 고도 모델을 유지하며, 돌파 직선은 고도1에서 좌우 하단→중앙 상단, 고도0에서 좌우 상단→중앙 하단을 향한다. 배경 시간은 게임 프레임만 진행시키고 일시정지·숨긴 탭·움직임 줄이기에서는 전진하지 않는다. 재시작은 새 캔버스와 초기 이동 상태를 사용하며 화면 종료 시 해당 GPU 자원을 해제한다. 중앙 레인·판정선·노트는 기존 Pixi 렌더러가 앞쪽에 표시한다.

**관대한 밸런싱**: `Liftoff`의 고도 0 시작·곡 종료 기준 클리어·곡 중 게임 오버 없음의 기존 관대한 역할을 유지한다. 종전 `Survival`의 Perfect-only 회복·0 도달 실패 규칙을 새 단계에 자동으로 배정하지 않는다.

**실패 조건 없는 완주/학습**: 실패 조건 없이 차트를 끝까지 확인하거나 구간을 반복 학습하려는 유저는 Observer 계열을 사용한다(`observer-mode.md`).

**후속 설계**: 세부 판정 규칙·상태와 시각 고도의 대응·기존 차트의 이행·속도와 각도 조정은 [PRD §12](../prd.md#12-미정-사항)에서 단일 추적한다. 이번 결정은 실제 충돌이나 레이더 탐지 판정을 도입하지 않는다.

**결정 배경**: 현재 이름·연출 배치는 [RFD 0022](../rfd/0022-flight-difficulty-names-and-visuals.md), 하향 시점의 표현은 [RFD 0021](../rfd/0021-low-altitude-downward-view.md), 초기 도입 목적과 과거 규칙은 RFD 0001~0003·0005를 참조한다.

## 플레이 중 노트 가시성

### 포인트 겹침과 연결 바디의 켜짐 표시

포인트 노트는 바디나 시작·끝 터미널과 겹치면 항상 그 위에 표시한다. 아래부터 바디→터미널→포인트 순서이며, 차트 배열의 노트 순서나 렌더 순서에 영향받지 않는다.

싱글·더블에서 실제로 유지 중인 바디가 있으면 아직 시작하지 않은 후속 연결 바디와 터미널도 켠다. 여러 구간을 연속해서 따르며, 유지 중인 unit 수와 경로상 각 구간의 건강한 unit 수 중 작은 수만 표시한다. 예를 들어 더블2개 유지→싱글→더블은 마지막 더블을1/2만 켠다. 실패한 unit을 켜거나 시작한 구간의 해제·실패·완료를 건너뛰지 않는다. 앞 구간이 끊긴 뒤에도 후속 구간 자체를 새로 유지하면 그 구간부터 다시 표시가 이어진다.

Trill은 연결 켜짐 표시에서 제외한다. 각 바디·터미널은 자기 구간의 실제 홀드가 활성화될 때만 켜며, 앞 구간을 유지해도 뒤쪽 Trill은 대기 상태다. Trill이 섞인 연결은 그 구간을 건너뛰어 켜짐 표시를 전파하지 않는다.

표시 전파로 후속 판정 unit을 활성화하거나 head·시작·승계·release 규칙을 변경하지 않는다. 단순히 판정선을 지났다는 이유로 실제 입력이 없는 연결 구간을 켜지 않는다.

### 처리된 노트 숨기기

입력이 처리된(판정이 완료된) 노트는 **즉시 화면에서 제거**된다. 판정선을 지나 화면 아래로 스크롤되기를 기다리지 않는다.

- **포인트 노트** (싱글, 더블, 트릴): 판정이 완료되면 즉시 사라진다. 롱노트 헤드 역할의 포인트 노트도 동일하게 판정 완료 시 사라진다.
- **롱노트 바디** (RangeNote): 정적 차트 컴파일이 unit과 Beat 연결 관계를 만든다. 런타임은 자기 시작 입력 또는 정당한 승계로 unit을 활성화하며, unit별 완료·실패 상태를 표시한다. 성공한 한 unit 때문에 whole body를 즉시 processed로 확정하지 않는다.

**처리된 노트를 숨기는 이유**: 판정이 완료된 노트가 화면에 남아 있으면, 아직 처리되지 않은 노트와 시각적으로 혼재되어 읽기 복잡도가 불필요하게 증가한다. 처리된 노트를 즉시 제거함으로써, 유저의 시각적 주의를 미처리 노트에 집중시킨다.

### 더블 노트 부분 입력 피드백

더블 노트(및 더블 롱노트 헤드)에서 2개의 입력 중 1개만 처리된 상태일 때, 해당 노트가 **50% 불투명도**로 변한다. 유저가 "1개는 눌렀지만 나머지 1개가 남아있다"는 것을 즉시 인지할 수 있으며, 2개 모두 성공한 경우와 명확히 구분된다.

- 더블 포인트 노트: 첫 번째 입력 후 노트가 반투명 → 두 번째 입력 후 사라짐 (롱노트 헤드 역할의 더블 노트도 동일)

## 미러 옵션 `[미구현]`

레인 배치를 좌우 반전하는 미러 옵션을 제공한다. 1-2-3-4 레인이 4-3-2-1로 뒤집힌다.

**미러를 제공하는 이유**: 왼손잡이 유저를 위한 접근성 보장이 주 목적이다. 키보드 리듬게임은 왼손이 낮은 레인, 오른손이 높은 레인을 담당하는 것이 관례인데, 왼손잡이에게는 주력 손이 단순한 파트를 담당하게 되어 불리하다. 미러 옵션으로 레인을 반전하면 오른손잡이와 동등한 조건이 된다. 부수적으로, 차트의 변주 효과도 제공한다.

## 게임패드

**게임패드는 지원하지 않는다.**

**게임패드를 지원하지 않는 이유**: not4k의 핵심인 "레인당 다중키 바인딩"은 한 손으로 같은 레인의 2개 이상의 키를 빠르게 교대하는 것을 전제로 한다. 게임패드의 버튼 배치는 이 동작에 적합하지 않다 — 엄지로 조작하는 페이스 버튼은 트릴 교대가 극도로 불편하고, 트리거/범퍼는 키 수가 부족하다. 게임패드를 지원하면 "게임패드로도 플레이할 수 있다"는 기대가 생기지만, 실제로는 핵심 경험을 제대로 전달할 수 없으므로 지원하지 않는다.

## 차트 에디터

**차트 에디터는 같은 웹 앱 내에서 라우팅으로 분리하며, admin 권한 유저만 접근한다.**

**곡 선택 화면 통합**: 기존에는 에디터가 별도의 곡 리스트(`SongListPage`)를 가지고 있었으나, 게임의 곡 선택 화면과 통합한다. admin 유저는 곡 선택 화면에서 각 차트의 Edit 버튼을 통해 에디터에 진입한다. 에디터 전용 로그인 페이지(`LoginPage`)와 별도 곡 리스트는 제거하고, 곡 선택 화면의 admin 분기로 대체한다.

**라우팅으로 분리하는 이유**: 차트 에디터는 게임 플레이와 완전히 다른 UI/UX를 필요로 한다 — 타임라인 편집, 노트 배치, 미리보기 등은 게임 클라이언트의 구조와 양립하기 어렵다. 라우팅으로 분리함으로써 게임 클라이언트와 에디터의 관심사를 분리하면서도, 공유 도메인(타입, 시간 변환, 배치 검증 등)을 하나의 패키지 안에서 직접 참조할 수 있다.

차트 에디터의 상세 설계는 `chart-editor.md`를 참고한다.

## 에러 처리

### 플레이 중 네트워크 단절

음원과 차트 데이터는 플레이 시작 전에 전체 로드되므로, **플레이 중 네트워크가 단절되어도 플레이는 끝까지 계속된다.** 결과 전송은 네트워크 복구 후 재시도한다. 복구되지 않으면 결과가 서버에 기록되지 않을 수 있으나, 플레이 경험 자체는 보호된다.

### 음원 로딩 실패

곡 시작 전 음원 로딩이 실패하면, **최대 3회 자동 재시도**한다. 재시도 중에는 로딩 상태를 유저에게 표시한다. 3회 모두 실패하면 에러 메시지를 표시하고 **곡 선택 화면으로 복귀**한다.

### 서버 점검

서버 점검 중에는 **로그인 여부와 무관하게 전체 접속이 차단**된다. 차트와 음원이 서버에 있으므로 비로그인 유저도 플레이할 수 없다. 점검 안내 화면을 표시한다.

### 곡 선택 화면 `[부분 구현 — 게임/에디터 별도 화면 존재, 통합·로그인·키보드 조작·admin 분기 미구현]`

곡 선택 화면은 **게임과 에디터가 공유하는 단일 화면**이다. 기존에는 게임(`SongSelectScreen`)과 에디터(`SongListPage`)가 별도의 곡 리스트를 가지고 있었으나, 이를 하나로 통합한다.

#### 상단 헤더

- **로그인 버튼**: 비로그인 상태에서 로그인 버튼을 표시한다. 로그인 상태에서는 유저 정보와 로그아웃 버튼을 표시한다.
- **튜토리얼 도움말 버튼**: 상단의 `?` 버튼을 누르면 중앙 팝업에서 `Basic`의 입문 17개와 `Advanced`의 판정 규칙 12개 시연을 표시한다. 탭별 이동 위치와 본 항목 체크를 제공하며, 자세한 동작은 `tutorial.md`를 따른다. 팝업에는 실제 `GameRenderer` 기반 축소 재생기, 튜토리얼 차트의 `tutorialInput` 이벤트로 구동되는 키 입력 표시, `tutorialDiagram` 이벤트로 표시되는 에디터 노트 렌더러 방식 도식이 포함된다. 도식은 뷰포트 전체를 dim 한 확인 모달로 표시하며, OK를 눌러야 다음 시연으로 재개된다.
- Settings, Back 등 기존 버튼은 유지한다.

#### 곡 리스트

- 서버에서 곡 목록을 조회한다. **admin 권한이 있는 유저는 비공개 곡까지 포함**된 목록을 받고, 일반 유저는 공개 곡만 받는다.
- 곡 리스트는 **마우스 휠** 또는 **키보드 Up/Down**으로 스크롤할 수 있다.

#### Song Item 구조

하나의 song item에는 **여러 chart가 존재**하며 난이도명으로 구분된다. 채택된 이름과 순서는 `Liftoff → Infiltration → Breakthrough`다. 곡 선택·로딩에서는 기존 `EASY / NORMAL / HARD`를 세 이름으로 표시하며 새 차트도 세 이름에서 선택한다. 기존 `EXPERT`는 이름·순서를 유지하고 돌파 배경을 쓴다. 저장 키·URL·차트 원본은 바꾸지 않으며 기존 라벨과 새 이름이 같은 단계면 새 차트 선택에서 중복을 막는다. 원격 데이터 일괄 이행은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다.

- **차트 선택**: 클릭 또는 **좌우 화살표**로 해당 곡 내에서 차트(난이도)를 선택한다.
- **Play**: **엔터** 키 또는 선택된 차트의 **Play 버튼**을 클릭하면 로딩 → 플레이 화면으로 이동한다.
- **Edit** `[admin 전용]`: admin 권한이 있는 유저에게만 Play 버튼 옆에 **Edit 버튼**이 표시된다. Edit 버튼을 클릭하면 해당 차트의 **에디터 화면으로 이동**한다.

#### admin 권한 분기

| 상태 | 곡 목록 | Edit 버튼 |
|------|---------|-----------|
| 비로그인 / 일반 유저 | 공개 곡만 | 미표시 |
| admin 유저 | 공개 + 비공개 곡 | 표시 (Play 버튼 옆) |

#### 곡 프리뷰 `[미구현]`

곡 선택 화면에서 커서가 위치한 곡의 **프리뷰 음원이 자동 재생**된다. 유저가 곡을 선택하기 전에 어떤 곡인지 들을 수 있어야 한다. 대부분의 리듬게임(osu!, DJMAX, SDVX 등)이 이 기능을 제공하며, 리듬게임 유저에게 기대되는 기본 기능이다.

**프리뷰 음원은 본편 음원과 별개의 오디오 파일**이다. 차트 메타데이터(`chart-editor.md`)에 프리뷰 전용 음원파일 필드를 두어, 차트 제작자가 곡의 하이라이트 구간을 별도로 편집하여 제공한다. 본편 음원에서 시작/종료 지점을 계산하는 방식이 아니므로, 페이드 인/아웃, 길이, 편집 등을 프리뷰 파일 자체에서 자유롭게 제어할 수 있다.

```
타이틀 → 로그인 → 타이틀

```

### 일시정지

플레이와 옵저버 모드에서 **일시정지가 가능**하다.

- **플레이 중 일시정지**: 노트 출력부(판정선, 낙하 노트 등)가 **가려진다.** `[미구현 — 노트 가림]` 일시정지 중에 다가오는 노트를 미리 읽고 손배치를 계획하면, 실시간 인지 능력이 아닌 암기와 준비로 성적을 올릴 수 있으므로 공정성을 위해 가린다. 재개 시 **3초 카운트다운** 후 재생된다. `[미구현 — 카운트다운]` 카운트다운 동안 노트 위치를 재계산하여, 재개 시점에 노트가 자연스럽게 낙하하는 상태에서 시작한다.
- **옵저버 모드 일시정지**: 노트 출력부가 **가려지지 않는다.** 옵저버 모드의 목적이 차트 확인이므로, 일시정지 중에도 노트를 볼 수 있어야 한다. 재개 시 카운트다운 없이 **즉시 재생**된다. 차트가 끝까지 재생되어도 자동으로 나가지지 않으며, 유저가 일시정지 후 나가기를 선택해야 곡 선택으로 복귀한다.

일시정지에서는 **재개(Resume)**, **재시도(Retry)**, 또는 **중도 포기(Quit)**를 선택할 수 있다. Retry는 결과 화면을 거치지 않고 곡을 처음부터 재시작한다.

- **튜토리얼 스킵**: 튜토리얼 차트를 플레이 중일 때, 일시정지와 동일한 동작(노트 가림, 재생 정지)을 수행하되 모달 메시지만 다른 **스킵 버튼**을 제공한다. 스킵을 선택하면 해당 튜토리얼을 건너뛰고 다음 단계로 진행한다.

### 중도 포기

플레이 도중 중도 포기하면 **결과 화면을 거치지 않고 곡 선택 화면으로 돌아간다.** 중도 포기한 플레이는 기록되지 않는다.

**결과 화면을 표시하지 않는 이유**: 중도 포기는 "이 차트를 더 이상 진행할 의사가 없다"는 의미이다. 완주하지 않은 플레이의 달성률과 랭크는 유저에게 유의미한 정보가 아니며, 불완전한 결과를 보여주는 것은 부정적 경험을 강화할 뿐이다.

**중도 포기와 `flightRule` 실패의 구분**: 중도 포기는 유저의 자발적 선택이고, `flightRule` 실패는 해당 규칙에 의한 게임 오버다. 단계별 실패 조건과 실패 시 화면 전환·기록 처리는 [PRD §12](../prd.md#12-미정-사항)에서 추적한다. 낮은 시각 고도 자체를 모든 단계의 실패 조건으로 두지 않는다.

### 설정 접근

```
곡 선택 → 설정 → 곡 선택
설정 → 오프셋 캘리브레이션 → 설정  [미구현]
곡 선택 → 튜토리얼 (재진입) → 곡 선택  [미구현]
```

튜토리얼은 첫 기동 이후에도 곡 선택 화면에서 재진입할 수 있다. 유저가 특정 메커니즘을 복습하고 싶을 때 접근할 수 있어야 한다.
현재 곡 선택 화면의 `?` 도움말 팝업은 전체 튜토리얼 재진입이 아니라, `Basic`과 `Advanced` 탭에서 기본 입력과 복합 판정 규칙을 확인하는 미리보기이다. 이 팝업은 오디오 없이 튜토리얼 전용 차트와 예시 입력을 반복 재생한다. 실제 플레이와 같은 `NoteJudgmentSession`으로 판정·정산하며 판정 이펙트를 표시한다. 결과 기록은 만들지 않는다. 반복 경계 시각의 마지막 입력까지 이전 세션에서 정산한 뒤 세션과 노트 표시 상태를 초기화한다.

### 스페셜 땡스

```
타이틀 → 스페셜 땡스 → 타이틀
```

**타이틀에서 접근하는 이유**: 스페셜 땡스는 게임 플레이와 무관한 크레딧 정보이므로, 플레이 흐름(곡 선택 → 플레이 → 결과) 안에 배치할 필요가 없다. 타이틀 화면에 배치하여 관심 있는 유저만 자발적으로 접근하도록 한다.

**스페셜 땡스에 표시하는 내용**: 음원 제공자(아티스트), 이미지·에셋 제공자, 오픈소스 라이브러리 라이선스(`project-assets.md`의 저작권 표기 의무 이행), 기타 기여자 크레딧. 라이선스에 의해 표기가 의무인 항목은 반드시 이 화면에 포함한다.

개발 전용 `/lab/judgment-playtest`에서 연결 유지·교대, 감소, `holdOnly`, 부분 실패·복구를 직접 입력한다. 실제 `PlayScreen`과 메트로놈을 사용하며 카드별 입력 방법·기대 결과와 현재 키 바인딩을 표시한다. 완주 뒤 `Back to Lab`으로 해당 사례와 결과에 돌아온다. 세부는 [판정 실플레이 명세](judgment-playtest.md)를 따른다.

## 판정 실행 구조

`compileJudgmentChart`가 정확한 Beat 경계, head 관계, unit 수, 점수 항목, 트릴 구간 귀속을 한 번 계산한다. 에디터 커서부터 테스트할 때는 `selectCompiledJudgmentChart`로 원래 noteIndex를 보존하면서 제외한 노트의 점수 항목·시간 맵·연결을 함께 제거한다.

`NoteJudgmentCore`는 차트와 시각별 입력만 받아 상태 전이와 확정 판정을 만든다. `NoteJudgmentSession`이 이 core와 `ScoreManager`를 묶고 `ConfirmedJudgmentEffects`를 적용한다. 실제 플레이와 튜토리얼의 판정 진입점은 이 세션이다. 이전 `JudgmentEngine`은 호환 회귀용이며 현재 모델의 규칙 원본으로 사용하지 않는다.

`InputTimeline`은 키보드와 `AutoPlayer.eventsThrough` 입력을 원래 timestamp별로 묶는다. 입력 오프셋은 `GameClock.toInputTimeMs`에서 한 번만 적용한다. 프레임 진행은 판정 시간과 현재 입력 시간 중 이른 시각까지로 제한하여 음수 오프셋의 Good 창을 잘라내지 않는다. 이미 수집한 양수 오프셋 입력이 core를 앞당겼으면 과거 프레임 시각으로 되돌리지 않는다. 같은 논리 시각까지 합성 입력도 먼저 수집하여 시간순으로 전달한다.

핸들러 지연으로 core보다 과거의 입력이 도착하면 미확정 대상에만 원래 입력 시각의 창·등급을 적용하고, 관측한 현재 시각에 확정한다. 이미 확정한 Miss·실패 unit을 복구하거나 점수·콤보를 소급 변경하지 않는다. 곡 종료는 남은 수집 입력을 먼저 전달하고 `finalize()`로 원래 점수 항목과 마지막 기한을 정산한 뒤 결과와 디버그 로그를 만든다.

`SessionRendererAdapter`는 head의 처리 상태와 바디의 unit 상태를 구분한다. 바디 상태 조회는 같은 렌더 시각에 한 번만 복사하고, 새로운 확정 묶음·반복 초기화 뒤에는 다시 조회한다. 판정 사례와 테스트 경계는 [구현 계획](../plans/note-judgment-implementation.md)을 따른다.
