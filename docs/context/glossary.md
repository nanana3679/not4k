# not4k — 용어 사전

이 문서는 not4k 설계 문서 전체에서 사용하는 용어를 정의한다. 같은 단어가 다른 맥락에서 다른 의미로 사용되는 혼동을 방지하기 위해 작성되었다.

엔진·웹·수명 주기 용어(reference counting, lease, warm-up 등)의 표기와, 기술 개념을 가리킬 때 판정·놓다·올리다·시계·프레임을 다른 뜻으로 쓰지 않는 규칙은 [term-map](term-map.md) E를 따른다.

**새 계약의 상태:** [RFD 0037](../rfd/0037-explicit-score-notes-and-body.md)의 바디·명시적 점수 노트 계약은 **채택 계약·일반 기본 경로 구현·검증**이다. 아래에서 **과도기 구형 계약·논의 기록**으로 구분한 등록 키·자동 끝점·`holdOnly`·연결 release·선택 해제 게이트 설명은 구형 읽기·표시·편집과 과거 결정 대조용이다. 그 안의 “현재”·“후속”은 당시 모델의 시점을 가리키며 새 계약을 덮지 않는다. 구형 의미의 보존과 제거 시점은 [구형 차트와 과도기](#구형-차트와-과도기)를 따른다. 공식 미정 사항은 [PRD §12](../prd.md#12-미정-사항)에서만 추적한다. 이 문서는 새 API·JSON 필드명을 확정하지 않는다.

## 게임 구조

### 튜토리얼

노트의 연주 방법과 판정 규칙을 배우는 선택적 학습 흐름이다. 입력을 배우는 항목은 시연을 본 뒤 제시된 동작이나 짧은 패턴을 직접 연주하여 항목별 요구 횟수만큼 누적 성공하면 통과한다. 실습 중 실패해도 이미 쌓인 성공 횟수는 유지하며 연속 성공을 요구하지 않는다. 단순 열람과 실습 통과는 구별하며, 튜토리얼 완료·통과를 차트 선택의 선행 조건으로 두지 않는다. 처음부터 도움말 모달을 바로 닫고 곡 선택을 이용할 수 있다([RFD 0081](../rfd/0081-tutorial-demonstration-and-three-practice-successes.md)).

**실습 진입과 시연 전환**: 처음 실습에 들어갈 때부터 `직접 입력 / 시연` 토글을 사용하며, 플레이어가 직접 입력을 선택하면 실습으로 넘어간다. 같은 토글로 시연 확인과 실습을 오가며 시연 종료만으로 자동 전환하지 않는다. 별도의 실습 시작 버튼은 두지 않고, 시연의 자동 입력은 실습 성공 횟수에 포함하지 않는다.

**리듬 안내**: 시연과 직접 입력 실습 모두 메트로놈의 박자 소리에 맞춰 진행한다. 처음 재생을 시작할 때만 첫 입력 전에 메트로놈을 4박 들려주는 준비 구간을 둔다. 반복 예제의 구간 자체에 다음 입력을 준비할 여유를 포함한다. 별도의 4박 준비 구간은 첫 재생 앞에만 두며, 이후 패턴을 반복할 때는 다시 추가하지 않는다. 예제 차트의 박자·노트·판정 시간과 소리를 맞추며, 튜토리얼 전용 음악은 요구하지 않는다([RFD 0083](../rfd/0083-tutorial-metronome.md)).

**학습 범위**: 노트의 연주 방법과 판정 규칙을 다룬다. 키 추가·손배치 발견을 단계적으로 체험하는 튜토리얼 과정은 별도로도, 노트 학습에 통합해서도 두지 않는다. 실습에 필요한 실제 키 설정과 노트를 처리하는 여러 키 교대·유지·탭의 학습은 유지한다([RFD 0104](../rfd/0104-no-keybinding-discovery-tutorial.md)).

**실습용 키 설정**: 필요한 키가 현재 바인딩에 부족하면 먼저 키 설정을 수정하도록 안내하고, 실제 설정이 요구를 충족한 뒤 실습을 시작한다. 현재 키 설정으로 실습할 수 없어도 시연은 이용할 수 있다. `직접 입력 / 시연` 토글의 직접 입력 옵션을 비활성화하고 키가 부족한 이유와 실제 키 설정을 수정하는 경로를 안내한다. 실제 설정이 요구를 충족하면 직접 입력 옵션을 활성화하지만 자동으로 실습에 전환하지 않으며, 플레이어가 직접 선택해야 한다. 별도 실습 시작 버튼이나 임시 키 자동 배정은 추가하지 않는다. 시연용 표시 키 보충은 실제 실습의 키 요건을 충족한 것으로 취급하지 않는다. 실습 중에만 쓸 임시 키를 자동 배정하지 않는다.

**실습 과제**: 올바른 연주 방법을 익히는 내용으로만 구성한다. 실패 사례는 시연으로 설명하며, 실패 동작의 직접 재현을 통과 조건으로 두지 않는다. 실제 발생한 실패는 일반 규칙대로 판정하고 항목별 달성률·추가 조건에 따라 성공 여부를 판단한다.

**토글 적용과 횟수 유지**: 시연에 다녀와도 성공 횟수는 유지한다. 직접 입력에서 시연으로 바꿀 때 이미 패턴이 재생 중이면 다음 패턴 시작부터 적용하고, 재생 중이 아니면 바로 적용한다. 시연에서 직접 입력으로 바꿀 때는 현재 재생 위치에서 즉시 적용한다. 시연 도중 직접 입력으로 바꾼 현재 패턴은 성공 집계에서 제외하고, 다음 패턴부터 성공 횟수를 집계한다. 이 규칙은 튜토리얼의 전환 규칙이다.

**실습 중 키 선택**: 노트를 보고 직접 사용할 키를 판단하며, 다음에 눌러야 할 키를 미리 알려주는 가이드는 표시하지 않는다. 실제 누른 키의 표시와 노트·`trillZone` 등 입력 요구를 알리는 시각 표시는 유지한다.

**노트 낙하 속도**: 튜토리얼용 고정값을 사용한다. 플레이어의 본 플레이 설정에 연동하거나 본 플레이의 설정값을 변경하지 않는다. 구체적인 값은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

요구 성공 횟수는 개발자가 실습항목별로 정하는 양의 정수이며 기본값은 3회다. 플레이어가 목표 횟수를 바꾸는 설정 UI는 두지 않는다.

**실습 반복**: 실습을 시작하면 성공·실패마다 버튼을 다시 누르지 않고 같은 실습을 자동 반복한다. 실패해도 성공 횟수는 유지하며, 항목별 요구 횟수만큼 누적 성공하면 반복을 마치고 통과 처리한다. 이미 통과한 항목을 다시 실습해도 새 실습에서 항목별 요구 횟수만큼 누적 성공하면 반복을 종료하며, 기존 통과 기록은 유지한다. 통과 전에도 모달을 닫을 수 있다.

**통과 후 이동**: 항목 전체를 통과한 뒤에는 현재 항목에 머물며 `다음` 버튼을 누르면 다음 항목으로 이동한다. 통과만으로 자동 이동하지 않는다.

**실습 1회 성공**: 튜토리얼 항목별로 목표 달성률과 추가 조건을 정하고 해당 튜토리얼에 표시한다. 실습 한 차례의 결과가 모든 조건을 만족하면 성공 횟수를 1회 더한다. 일반 Good은 달성률에 반영하며 발생 자체만으로 실패 처리하지 않는다. 트릴 교대 학습에는 `goodTrill` 0회 조건을 두어 교대 실패를 성공으로 집계하지 않는다. 이 성공을 해당 항목의 요구 횟수만큼 누적해야 통과한다.

롱노트 중 탭은 한 항목 안에서 기존 키를 유지하는 방법을 먼저 시연·실습하고, 그 방법의 목표를 달성한 뒤 유지 키를 교대하는 방법을 시연·실습한다. 첫 방법의 목표를 달성하면 반복을 멈추고 현재 단계에 머물며, `다음` 버튼으로 두 번째 방법으로 이동한다. 자동으로 다음 방법으로 전환하지 않는다. 두 방법 모두 목표를 달성해야 항목 전체를 통과한다. 두 방법을 자유롭게 번갈아 선택하는 방식으로 만들거나 전체 튜토리얼 항목의 순서를 잠그는 것으로 확대하지 않는다. 성공 횟수를 방법별로 별도 집계한다. 기존 키를 유지하는 방법과 유지 키를 교대하는 방법 모두 각각 항목별 요구 횟수만큼 누적 성공해야 하며, 두 방법의 횟수를 합산하지 않는다.

**통과 조건 표시**: 콤보 아래에 조건을 한 줄씩 표시한다. 충족은 초록 체크 아이콘, 실패는 빨강 X 아이콘으로 표시하며 중립 상태는 흰색 글씨로 표시한다. 조건 상태는 연주 도중 실시간으로 갱신한다. 조건 목록 바로 아래에는 성공 횟수 진행도를 `현재 성공 횟수/해당 항목의 요구 성공 횟수`로 표시한다(기본값 3회인 항목의 예: `1/3`). 성공 횟수는 패턴 결과가 확정될 때 집계하며, 성공이 확정되면 진행도도 즉시 갱신한다.

**기록과 재진입**: 튜토리얼을 닫았다 다시 열면 마지막으로 선택한 탭과 항목을 연다. 마지막으로 선택한 탭과 항목은 해당 기기의 브라우저에만 저장해 게임을 껐다 켜도 복원하며 계정과 동기화하지 않는다. 선택 이력이 없는 최초 진입은 `Basic` 첫 항목에서 시작한다. 항목 위치 복원과 미완료 실습의 성공 횟수 복원은 구별한다. 실습 기록으로는 항목 전체 통과 여부만 로그인 여부와 관계없이 브라우저에 저장한다. 로그인하면 항목 전체 통과 여부를 계정과 동기화해 다른 기기에서도 같은 통과 표시를 확인할 수 있게 한다. 게스트 튜토리얼의 항목 전체 통과 기록은 로그인 시 계정당 1회 인계할 수 있다. 이미 인계한 게스트 기록은 다른 계정으로 재인계하지 않는다. 계정에 귀속된 통과 기록은 같은 계정의 여러 기기에서 계속 공유하며, 로컬에 표시된 계정 기록을 게스트 기록으로 재분류하거나 다른 계정으로 인계하지 않는다.  현재 방법·부분 성공 횟수·중간 방법 완료 여부는 현재 실습 세션에서만 유지하고 영구 저장·계정 동기화하지 않는다. 미완료 항목을 닫았다 다시 열거나 다른 항목에서 돌아오거나 게임을 재시작하면 첫 번째 방법의 성공 횟수 0회부터 시작한다. 이미 전체 통과한 항목의 재실습도 첫 번째 방법 0회부터 새로 진행하되 과거 항목 통과 기록은 지우지 않는다. 같은 항목 안에서 시연/직접 입력을 토글할 때는 현재 방법과 누적 성공 횟수를 유지하며 기존 전환·집계 규칙을 따른다. 튜토리얼 목록에서 통과한 항목에 체크 표시를 붙인다. 시연만 본 항목에는 통과 체크를 붙이지 않으며, 별도의 열람 표시도 두지 않는다. 여러 연주 방법을 각각 실습하는 항목은 필요한 모든 방법을 통과해야 항목 전체를 통과로 표시한다. 튜토리얼을 닫았다 다시 열면 미완료 실습은 성공 횟수 0회부터 시작하며, 누적 성공 1회·2회 같은 중간 진행도는 복원하지 않는다. 이미 전체 통과한 항목의 기록은 유지한다. 실습 중 실패만으로 성공 횟수를 초기화하지는 않는다. 다른 튜토리얼 항목으로 이동했다 돌아오는 경우에도 미완료 실습의 성공 횟수는 0회로 초기화한다. 같은 항목에서 직접 입력/시연을 토글할 때는 성공 횟수를 유지한다.

현재 공개 목록은 자동 시연 중심이며 직접 입력·항목별 요구 횟수 누적 성공 통과는 미구현이다. 실습 세부와 목록 개편은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### 곡 프리뷰

곡 선택 화면에서 선택한 곡의 일부를 미리 듣는 기능이다. 곡마다 본편과 별개의 프리뷰 전용 음원 파일을 필수로 제공하고, 본편 음원의 지정 구간으로 대체하지 않는다([RFD 0089](../rfd/0089-required-preview-audio-file.md)).

프리뷰는 로딩 용량을 제한하기 위해 음원 파일 한 개의 재생 길이를 **5초 이상 15초 이하**로 제한한다. 곡 선택 화면에서 같은 곡을 선택한 동안에는 프리뷰 음원이 끝나면 처음부터 반복 재생한다. 선택한 곡이 바뀌거나 곡 선택 화면을 나가면 해당 프리뷰의 재생을 중단한다.

같은 곡을 1초 동안 선택한 뒤 프리뷰를 불러와 재생한다. 대기 중 곡을 바꾸면 이전 곡의 프리뷰를 불러오지 않고, 새로 선택한 곡을 기준으로 다시 기다린다.

한 번 불러온 프리뷰 음원은 브라우저에 저장해 다음 접속에도 재사용한다. 저장된 파일이 없으면 서버에서 불러오고, 프리뷰 파일이 바뀌면 저장본을 갱신한다. 저장된 프리뷰를 재사용할 때도 같은 곡을 1초 동안 선택한 뒤 재생한다. 프리뷰 저장 용량이 차면 마지막으로 들은 지 가장 오래된 프리뷰부터 자동으로 삭제한다. 삭제한 프리뷰를 다시 선택하면 필요할 때 서버에서 불러온다. 저장 용량의 상한은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

프리뷰만 로딩에 실패하면 미리 듣기를 건너뛰고 곡 선택과 플레이 진입은 허용한다. 프리뷰 로딩 실패 안내는 팝업 없이 곡 정보 영역에 작게 표시한다. 본 플레이의 차트·음원 로딩과 검증은 기존 규칙을 따른다.

튜토리얼 또는 곡 추가 창을 열면 곡 선택 화면의 프리뷰 재생과 재생 전 대기를 중단한다. 창을 닫으면 그때 선택된 곡을 기준으로 1초 기다린 뒤 프리뷰를 처음부터 다시 재생한다. 일반 설정 창을 열어도 곡 선택 프리뷰의 재생을 유지한다. 마스터 볼륨을 바꾸면 재생 중인 프리뷰에도 바로 적용한다.

프리뷰 파일을 생성할 때 시작 0.5초에 선형 페이드 인, 끝 0.5초에 선형 페이드 아웃을 고정 적용하며, 제작자가 페이드 길이를 조절하는 옵션은 두지 않는다.

곡 선택 프리뷰의 자동 재생을 끄는 별도 설정은 제공하지 않는다.

### 로딩

차트·음원을 서버에서 불러와 재생 전에 준비하는 흐름이다. 본 플레이 로딩이 진행 중일 때는 사용자 취소와 곡 선택 복귀 조작을 제공하지 않는다. 본 플레이 로딩에서 응답이 없는 상태가 제한 시간 동안 이어지면 해당 로딩 시도를 실패로 처리한다. 차트 파일 전송과 음원 로딩의 시간 초과에는 자동 재시도와 최종 실패 화면의 선택 규칙을 적용한다. 본 플레이의 차트 파일 전송 실패와 음원 로딩 실패에 최대 3회 자동 재시도한 뒤에도 실패하면 실패 화면에 오류 안내와 **재시도**, **곡 선택으로 돌아가기** 버튼을 표시한다. 재시도는 같은 곡·차트의 로딩을 다시 시도하며, 곡 선택 복귀는 플레이어가 선택했을 때 수행한다([RFD 0087](../rfd/0087-audio-load-failure-retry-or-return.md)).

로딩 안내는 백분율 진행률 대신 **차트 불러오는 중**·**음원 준비 중**처럼 현재 진행 중인 작업을 표시한다. 자동 재시도 중에는 현재 재시도 횟수와 최대 횟수를 **재시도 1/3**처럼 표시한다. 첫 자동 재시도에서 1/3으로 시작하고 재시도가 진행될 때 갱신한다.

차트 자체의 형식·검증 오류에는 자동 재시도나 수동 재시도를 제공하지 않고, 오류 안내와 **곡 선택으로 돌아가기** 버튼만 표시한다. 차트 파일의 전송 실패와는 구별한다([RFD 0087](../rfd/0087-audio-load-failure-retry-or-return.md)). 에디터는 관리자만 접근할 수 있다. 차트 형식·검증 오류가 나면 일반 플레이어에게는 다른 차트 선택을 안내하고, 관리자에게는 에디터에서 수정할 수 있다는 안내도 제공한다.

### 서버 점검

서버 점검 중에는 로그인 여부와 관계없이 새 접속·새 플레이 진입을 막고 점검 안내를 제공한다. 이미 재생 중인 곡은 끝까지 플레이하고 결과 화면으로 진행한다. 플레이 중 점검이 시작돼도 점검 안내를 띄우지 않고, 곡이 끝난 뒤 결과 화면에서 안내한다. 완료한 로그인 플레이의 기록 전송에 실패하면 기존 전송 실패 안내·재시도·브라우저 보관·원래 계정의 다음 접속 시 자동 재전송 규칙을 따른다([RFD 0088](../rfd/0088-finish-current-play-during-maintenance.md)).

### 클리어 상태

종료한 한 플레이를 실패·성공·풀콤보·올퍼펙트 중 하나로 나타내는 내부 용어다. 한 플레이에는 클리어 상태 하나만 표시하며, 점수·달성률·랭크·판정 통계와 구별한다. 올퍼펙트와 풀콤보를 모두 충족하면 올퍼펙트로 표시한다([RFD 0092](../rfd/0092-exclusive-play-outcome-and-chart-display.md)). `Liftoff`는 Miss 없이 완주하면 클리어 조건을 충족하도록 게이지 상승량을 설정하므로 풀콤보 완주가 고도 조건 때문에 실패하는 경우를 배제한다([RFD 0093](../rfd/0093-liftoff-no-miss-completion-clears.md)). 개별 달성 표시 명칭은 [PRD §12](../prd.md#12-미정-사항)에서 추후 결정한다.

### 플레이 종료와 결과

종료한 한 플레이에는 [클리어 상태](#클리어-상태) 하나를 표시한다.

곡이 종료되면 해당 플레이의 클리어 성공·실패에 맞는 연출을 보여준 뒤 결과 화면으로 이동한다. 풀콤보·올퍼펙트를 달성하면 일반 클리어 연출 대신 해당 달성의 전용 종료 연출을 보여준다. 풀콤보와 올퍼펙트 조건을 모두 충족하면 올퍼펙트 종료 연출만 보여준다. 전용 연출도 3초 이내로 표시하며 건너뛰기 없이 완료 후 결과 화면으로 이동한다. 성공·실패 연출은 모두 3초 이내로 짧게 표시하며 건너뛰기 조작을 제공하지 않는다. 연출이 끝나면 자동으로 결과 화면으로 이동한다. 곡 도중 `flightRule`의 실패가 확정되면 즉시 곡 재생과 입력 판정을 종료하고, 실패 연출을 보여준 뒤 결과 화면으로 이동한다. 성공·실패 연출은 점수 랭크와 구별한다. Quit·Retry와 옵저버 종료에는 기존대로 결과 화면을 표시하지 않는다([RFD 0090](../rfd/0090-song-end-presentation-before-results.md)).

곡 도중 실패로 종료되면 판정 통계는 종료 시점까지 실제로 확정된 판정만 집계한다. 미처리 노트를 종료 때문에 새 Miss로 채우지 않는다. 최종 달성률의 분모는 기존대로 차트 전체 점수 항목의 이론 가중치 합을 사용한다. 미완주 플레이는 풀콤보로 인정하지 않는다([풀콤보](#풀콤보-full-combo)).

올퍼펙트의 달성 조건은 [올퍼펙트](#올퍼펙트-all-perfect)를 따른다. 달성 표시 명칭은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다. 일반 플레이는 점수 노트가 최소 1개 있는 차트만 허용한다([RFD 0091](../rfd/0091-normal-play-requires-score-note.md)).

### 개인 플레이 기록

결과 화면의 기록 갱신 안내는 최고 점수를 갱신했을 때만 표시한다. 해당 차트 버전·판정 설정에 기존 기록이 없으면 첫 기록에도 최고 점수 갱신 표시를 보여준다. 첫 기록이 0점이어도 같은 기준을 적용한다. 기존 최고 점수를 넘기면 결과 화면의 갱신 안내와 함께 이전 최고 점수 대비 증가분을 +1,234점 형식으로 표시한다. 증가분은 이번 점수에서 이전 최고 점수를 뺀 값이다. 점수가 기존 최고 점수와 같거나 낮으면 점수 차이는 표시하지 않는다. 기존 기록이 없는 첫 기록에는 갱신 안내만 표시하고 증가분은 표시하지 않는다. 클리어 상태 갱신은 별도로 안내하지 않는다. 해당 플레이의 클리어 상태 표시·전용 종료 연출과 기록 갱신 안내는 구별한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

차트 선택에서 해당 차트의 플레이 기록이 없으면 클리어 상태 표시를 비워둔다. 0점이더라도 실패 기록이 있으면 실패를 표시한다([RFD 0092](../rfd/0092-exclusive-play-outcome-and-chart-display.md)).

차트 선택에서는 올퍼펙트를 달성한 경우 풀콤보 표시 대신 올퍼펙트를 표시한다. 최고 점수가 갱신되지 않는 동점 플레이에서 새로 달성한 올퍼펙트도 표시에 반영한다. 기존 최고 점수·클리어·풀콤보 달성 기록의 독립 보존은 유지한다([RFD 0092](../rfd/0092-exclusive-play-outcome-and-chart-display.md)).

로그인한 플레이어의 완주 기록뿐 아니라 `flightRule`에 따라 곡 도중 실패로 종료된 기록도 점수 기록과 랭킹 반영 대상에 포함한다. 곡 도중 실패로 종료되면 그때까지 얻은 점수를 반영한다. 더 높은 점수라면 최고기록을 갱신하며, 해당 플레이의 클리어 여부는 점수와 별도로 판정한다. 기존에 달성한 클리어 기록은 유지한다. 플레이어가 직접 중단한 Quit·Retry 경로는 기록을 남기지 않는다.

플레이어 자신의 차트별 플레이 결과와 이력이다. 플레이 기록 저장은 로그인한 플레이어에게 제공한다. 비로그인 플레이는 허용하되 플레이 기록을 저장하거나 랭킹에 등록하지 않는다. 곡·차트 선택에서는 해당 차트의 최고기록·클리어 여부·풀콤보 여부를 바로 확인할 수 있게 한다. 세 항목을 보기 위해 별도 상세 기록 화면에 들어갈 필요는 없다. 최고기록은 해당 차트에서 얻은 최고 점수이며, 더 높은 점수를 얻으면 갱신한다.

플레이 횟수는 통계창에서 확인한다. 첫 클리어 시점 등 다른 상세 기록은 예시이며 저장 항목으로 확정하지 않는다. 개인 기록을 타인에게 기본 공개하지 않는 원칙은 유지하며, 기본 기록과 상세 기록 모두 사실을 담백하게 표시한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)). 상세 항목·화면 등 남은 세부는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

최고기록·클리어 여부·풀콤보 여부는 서로 다른 플레이에서 달성해도 각각 독립적으로 보존한다. 새 최고기록을 세운 플레이에서 클리어·풀콤보를 달성하지 못해도 기존 달성 여부는 유지한다. 최고기록을 갱신하지 못한 플레이에서 처음 달성한 클리어·풀콤보도 보존한다.

Normal과 Easy의 최고 점수·클리어 여부·풀콤보 여부는 판정 설정별로 분리해 보존한다. 한 설정에서 달성한 기록으로 다른 설정의 기록을 갱신하지 않는다.

같은 판정 설정 안에서는 미러 사용 여부와 관계없이 같은 차트의 기록으로 합쳐 보존한다. 두 경우 모두 같은 최고기록의 갱신 대상이며 클리어·풀콤보 달성 여부도 함께 보존한다. 미러 여부에 따라 별도 기록 항목을 만들지 않는다.

노트 배치가 바뀌면 기존 최고 점수·클리어 여부·풀콤보 여부는 이전 차트 버전의 기록으로 보관하고, 수정된 차트 버전의 기록은 새로 쌓는다. 이전 버전의 달성 여부나 점수로 수정된 버전의 기록을 채우지 않는다. Normal/Easy 분리와 각 설정 안의 미러 통합은 같은 차트 버전 안에서 적용한다. 곡·차트 선택과 랭킹에는 현재 차트 버전의 새 기록만 표시한다. 이전 버전 기록의 조회 화면과 표시 방식은 이번 출시 전 설계 범위에서 제외한다.

곡이 공유하는 BPM·음원 정렬 오프셋을 수정하여 실제 입력 시각이 달라지면, 영향을 받는 각 차트의 기록과 랭킹을 새 버전으로 분리한다. 이전 기록은 보관하고 새 버전에 승계하지 않는다([RFD 0095](../rfd/0095-song-shared-bpm-and-audio-offset.md)).

제목·아티스트·자켓 같은 곡의 표시 정보만 수정하면 기존 기록·달성 여부·랭킹을 유지하며, 기록용 차트 버전을 분리하지 않는다([RFD 0096](../rfd/0096-song-shared-display-metadata-and-records.md)).

차트를 삭제해도 기존 플레이 기록·최고기록·달성 여부는 원래 차트 버전에 보관하고, 삭제된 차트는 곡·차트 선택과 현재 랭킹에서 제외한다. 삭제한 차트를 다시 등록하면 새 차트로 취급해 기록을 새로 쌓으며, 이전 기록은 승계하지 않는다.

삭제 전에 시작한 플레이나 이미 완료된 미전송 결과는 삭제 후에도 원래 차트 버전의 기록으로 접수·보관한다. 이 기록은 현재 랭킹에 반영하거나 재등록된 차트에 연결하지 않는다. 로그인 등 기존 기록 접수 요건과 Quit·Retry 중단 기록 제외는 그대로 적용한다. 삭제 후 기록 보존 정책은 [RFD 0097](../rfd/0097-preserve-records-after-chart-deletion.md)을 따른다.

로그인한 플레이의 기록 전송에 실패하면 결과 화면에 전송 실패 안내와 **전송 재시도** 버튼을 표시한다. 버튼을 누르면 해당 플레이 결과의 서버 전송을 다시 시도한다. 곡을 다시 플레이하는 Retry와 구별한다. 결과 화면을 나가도 미전송 기록을 브라우저에 보관해 나중에 재전송할 수 있게 한다. 미전송 기록은 해당 플레이를 한 계정과 연결해 보관한다. 다음 접속 때 해당 플레이를 한 계정으로 로그인되어 있으면 브라우저에 보관한 미전송 기록을 자동 재전송한다.

### 프로필

로그인한 플레이어의 서비스 권한과 개인 기록을 연결하는 사용자 정보다. 게임 설정의 프로필 탭에서 닉네임 변경과 로그인·로그아웃을 제공하며, 비로그인 상태에서도 탭에 접근할 수 있다([RFD 0094](../rfd/0094-settings-profile-tab.md)). 닉네임의 생성·변경·랭킹 표시 규칙은 [닉네임](#닉네임), 입력·오류·화면 이동의 상세 동작은 [게임 코어 스펙](../spec/game-core.md#설정의-프로필-탭-미구현)을 따른다.

게임 설정은 로컬에 먼저 적용한 뒤 계정 설정만 서버에 저장한다. `GameSettings` 중 입력 오프셋 `inputOffsetMs`·시각 오프셋 `visualOffsetMs`·마스터 볼륨 `masterVolume`·최초 실행 상태 `isFirstLaunch`·디버그 상태 `debugMode`는 기기별 브라우저에만 저장하며 업로드하거나 서버 값으로 덮어쓰지 않는다. 나머지 설정은 계정 설정이다. 로그아웃 후에도 직전 설정을 유지하며, 서버 불러오기·저장 실패 시 현재 설정을 브라우저에 유지하고 실패한 작업을 안내한다. 로그인 시 서버 설정을 우선하는 정책과 실패 처리의 상세는 [계정 설정 동기화](../spec/game-core.md#계정-설정-동기화)를 따른다([RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

### 닉네임

랭킹에 플레이어 이름으로 표시하는 이름이다. 사용자가 직접 변경하는 닉네임의 중복을 허용한다. 이름이 같아도 플레이어별 기록과 순위는 구분하며, 닉네임을 변경해도 기존 기록과 순위를 유지한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

처음 로그인할 때 닉네임이 없으면 Guest 뒤에 6자리 숫자 난수를 공백 없이 붙인 이름을 기존 닉네임과 겹치지 않게 자동 생성한다. 자동 생성 시의 충돌 방지는 닉네임 전체에 전역 고유성을 요구하는 규칙이 아니며, 사용자가 이후 직접 변경하는 이름은 중복을 허용한다. 닉네임 입력을 필수로 요구하지 않는다. 생성한 이름은 계정에 유지하며 이후 로그인에서는 기존 닉네임을 사용한다.

닉네임의 길이는 1～16자다. 빈 이름, 앞뒤를 포함한 공백, 특수문자와 이모지를 허용하지 않는다. 공백은 자동으로 제거하지 않고 저장을 거부한다. 지원 언어에 따른 허용 문자 범위는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

닉네임 변경은 게임 설정의 [프로필](#프로필) 탭에서 저장 버튼으로 요청하며, 서버 저장 성공 후 실제 이름의 변경을 확정한다. 실패한 입력값은 편집 초안으로 유지한다. 저장 안내·재시도·초안 폐기의 상세는 [게임 코어 스펙](../spec/game-core.md#설정의-프로필-탭-미구현)을 따른다([RFD 0094](../rfd/0094-settings-profile-tab.md)).

닉네임을 변경하면 기존 랭킹에 표시되는 이름도 새 닉네임으로 바뀐다. 랭킹은 조회 시점의 현재 닉네임을 표시하며, 이미 열린 창에는 다음 조회 때 반영한다.

### 랭킹

랭킹에 표시할 플레이어 이름은 현재 닉네임으로 한다.

랭킹은 창을 열 때 최신 기록을 불러오며, 같은 랭킹 창을 열어둔 동안에는 자동 갱신하지 않는다. 창을 닫았다 다시 열면 최신 기록을 다시 불러온다. 랭킹을 불러오지 못하면 랭킹 창 안에 오류 안내와 재시도 버튼을 표시한다. 재시도 버튼을 누르면 현재 대상의 랭킹 조회를 다시 시도한다.

랭킹의 기록 수치는 점수만 표시하며 달성률은 표시하지 않는다. 같은 차트 버전·판정 설정의 최고 점수를 비교한다. 본인의 기록이 상위 목록 밖에 있더라도 내 순위와 점수는 별도로 표시한다.

랭킹에는 같은 차트 버전·판정 설정에서 최고 점수와 독립적으로 보존한 풀콤보·올퍼펙트 달성 배지를 표시한다. 미러 사용 여부는 같은 기록으로 합친다. 올퍼펙트를 달성했으면 풀콤보 대신 올퍼펙트 배지만 표시하며, 일반 성공·실패는 표시하지 않는다. 배지는 최고 점수를 낸 특정 플레이의 상태로 제한하지 않는다. 100점 풀콤보 뒤 110점 실패를 기록하면 랭킹에는 110점과 풀콤보 배지를 함께 표시한다. 같은 점수로 올퍼펙트를 새로 달성해도 배지를 갱신하며, 해당 점수의 최초 달성 시각과 동점 순서는 바꾸지 않고 최고 점수 갱신 안내도 표시하지 않는다. 배지로 동점 순서를 정하지 않는다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

로그인한 플레이어의 완주 기록과 `flightRule` 실패로 곡 도중 종료된 기록 모두 랭킹 반영 대상에 포함한다. 직접 중단한 Quit·Retry 경로의 플레이는 제외한다.

같은 차트 버전의 플레이 기록을 다른 플레이어와 비교해 보여주는 순위이다. Normal과 Easy 모두 차트별 랭킹을 제공하며, 두 판정 설정의 순위는 따로 집계한다. 각 설정에서 달성한 기록만 해당 설정의 랭킹에 반영한다. 곡·차트 선택의 기본 화면에는 개인 기록을 표시하고, 랭킹은 플레이어가 선택해 여는 별도 경로에서 확인한다([RFD 0085](../rfd/0085-chart-records-and-detailed-history-visibility.md)).

같은 점수에서는 해당 점수를 먼저 달성한 플레이어가 앞 순위에 오른다. 같은 점수를 다시 달성해도 그 점수의 최초 달성 시각을 유지한다. 랭킹도 차트 버전별로 분리해 새로 집계하며, 이전 버전의 기록을 수정된 버전의 순위에 반영하지 않는다.

삭제된 차트는 현재 랭킹에서 제외한다. 삭제 후 접수된 원래 차트 버전의 결과도 보관만 하고 현재 랭킹에는 반영하지 않는다([개인 플레이 기록](#개인-플레이-기록)).

### 옵저버 모드 (Observer Mode)

연주 방법을 모르겠거나 동작 자체가 익숙하지 않을 때, 원하는 구간을 반복해 관찰하고 직접 따라 치며 판정을 확인하는 선택적 학습 도구다. 낮은 레벨에서도 사용할 수 있고, 본 플레이의 필수 사전 절차로 두지 않는다([RFD 0060](../rfd/0060-observer-for-understanding-and-practice.md), [RFD 0061](../rfd/0061-observer-input-and-judgment.md)).

감속 재생(0.25x～1.0x)에서도 원곡의 음높이를 유지한다. 진입·재진입 시 재생 속도는 1.0x로 초기화하며 마지막 감속 설정을 복원하지 않는다. 재생 중 속도를 바꾸면 현재 곡 위치에서 즉시 적용하며, 구간을 다시 시작하거나 수동 집계를 초기화하지 않는다. Auto 관찰과 직접 입력 연습 모두 같은 요구를 적용한다. 처리 방식은 아직 정하지 않았으며 음질·지연·동기화를 검증해 결정한다([RFD 0076](../rfd/0076-observer-slowdown-preserves-pitch.md), [PRD §12](../prd.md#12-미정-사항)).

옵저버에 진입하면 Auto가 기본으로 켜진 상태로 바로 재생한다. 토글로 자동연주 관찰과 직접 입력 연습을 전환한다. 토글은 현재 재생 위치에서 즉시 적용하며 구간을 다시 시작하지 않는다. Auto를 끄면 진행 중인 바디도 즉시 직접 이어받으며, 자동 유지를 남기지 않고 실제로 누르고 있는 키를 기준으로 일반 바디 규칙에 따라 유지 여부를 판단한다([RFD 0062](../rfd/0062-observer-controls-loop-and-exit.md)). Auto를 켜거나 끄는 전환은 수동 연습을 끊는 경계로 취급해 수동 콤보·달성률을 초기화한다. 수동에서 Auto로 전환하면 기존 수동 집계를 끝내고 초기화하며, Auto에서 직접 입력으로 돌아오면 새 수동 집계를 0부터 시작한다. 재생 위치는 현재 그대로 유지하며 전환은 즉시 적용한다. Auto가 처리한 노트의 점수·이론 가중치는 계속 집계에서 제외한다. Auto 중에는 판정만 보여주고 콤보·달성률은 숨기며, Auto로 처리한 노트는 집계에서도 제외한다. 해당 점수와 이론 가중치도 달성률 계산에 넣지 않는다. 직접 연습할 때는 수동 연습 부분의 판정으로 집계한 콤보·달성률을 표시한다([RFD 0075](../rfd/0075-observer-manual-only-statistics.md)).

오른쪽에는 에디터와 같은 미니맵을 둔다. 기본 구간은 곡 처음부터 끝까지이며, 시작·끝 핸들로 구간 길이를 조절하고, 몸통을 끌면 길이를 유지한 채 위치를 옮긴다. 시간 위치는 자유롭게 지정하며 박자 스냅을 적용하지 않는다. 시작·끝 핸들이나 몸통을 드래그하는 동안 재생을 멈추고, 화면 패턴은 현재 선택 구간의 시작 핸들 위치를 기준으로 갱신한다. 끝 핸들만 바꿔 시작 위치가 같으면 화면의 기준 위치도 그대로이며, 시작 핸들이나 몸통을 옮기면 새 시작 위치를 따른다. 드래그를 놓아도 정지 상태를 유지한다. 이후 재생 버튼을 누르면 선택 구간 시작에 앞선 최대 3초 준비 구간부터 재생해 페이드 인 후 선택 구간에 진입한다. 이 준비 구간은 배속과 무관한 실제 시간 기준이며 실제 음원 범위까지만 사용하고 부족한 시간은 무음으로 보충하지 않는다. 직접 나갈 때까지 반복하고 곡 종료로 자동 퇴장하지 않는다. 반복 구간이 끝나면 수동 연습의 콤보·달성률을 초기화해 다음 반복으로 누적하지 않는다. 구간 변경·Retry도 새 시도로 초기화한다. Retry는 현재 선택 구간 시작을 기준으로 앞 준비 구간을 거쳐 다시 진입한다. 명시적으로 종료하면 리절트 없이 곡 선택으로 복귀한다([RFD 0064](../rfd/0064-observer-whole-song-loop-and-reset.md)).

반복 재생은 음원 범위 안에서 선택 구간 앞뒤를 실제 시간으로 각각 최대 3초 더 재생하며, 앞 구간에서 페이드 인하고 뒤 구간에서 페이드 아웃한다. 배속과 무관한 실제 시간 기준이며, 0.5배속을 유지하면 곡 시간으로 앞뒤 각각 1.5초가 해당한다. 음원 시작·끝을 벗어나는 부족한 시간은 무음으로 채우지 않는다. 선택한 연습 구간 자체는 바꾸지 않는다([RFD 0062](../rfd/0062-observer-controls-loop-and-exit.md)). 앞뒤 추가 재생 구간에 속한 노트는 표시·판정 대상에서 제외한다. 경계에 걸친 롱노트는 선택 구간의 시작·끝에 맞춰 자르고, 구간 밖 헤드·릴리즈는 제외하며 잘린 경계에 새로 만들지 않는다. 원본 차트는 바꾸지 않는다([RFD 0063](../rfd/0063-observer-range-note-clipping.md)). 선택 구간 안의 첫 노트는 확보된 앞 페이드 구간 동안 미리 낙하하는 모습이 보인다. 앞뒤 여유 시간 동안 차트 전체를 숨기는 방식은 아니다. 시작 경계에서 잘려 헤드가 없는 바디는 일반적인 헤드 없는 바디와 같은 시작 규칙을 적용한다. 미리 누른 키와 구간 시작에 누른 키 모두 허용하며, 기존 바디의 시작 허용 범위를 따른다. Auto 전환과 반복 경계의 키·바디 상태 처리 등 남은 세부는 [PRD §12](../prd.md#12-미정-사항)를 따른다.

`Observer 계열`은 실패 조건 없이 차트를 관찰·학습하는 흐름을 가리키는 기존 범위 명칭이다. 개별 입력의 실패 판정은 확인할 수 있으나 `flightRule` 실패로 학습을 중단하지 않으며, 공식 기록 대상인 Play와 구별한다. 입력 없는 관찰로만 한정하지 않는다. 옵저버 런타임은 미구현이며, 구체적인 표시·반복 상태 처리는 [PRD §12](../prd.md#12-미정-사항)를 따른다.

### 일시정지 후 재개

새 재개 목표는 **T = max(이번 플레이 시작 시각, 일시정지한 곡 시각 − 3000ms)**다. 노트나 판정 창에 맞춰 위치를 조정하지 않고 곡 시간으로 고정 3초를 되감는다. T까지의 상태를 복원하고 그 뒤 입력·판정·점수·콤보·바디 상태를 버려 다시 플레이한다. 되감은 구간의 확정 성공/실패도 변경할 수 있다([RFD 0040](../rfd/0040-countdown-and-note-reentry.md)). 일반 진행 중 확정 실패 불복구와 구별한다.

T 앞부분의 음악만 재생하는 **실제 시간 3초의 준비 → T부터 차트 표시·판정 재개** 순서다. 별도 3·2·1은 없다. 곡 시작 전은 무음으로 채운다. 준비 중에는 노트를 표시·판정하지 않고 키를 자유롭게 바꿀 수 있다. 준비 down/up은 새 타격·릴리즈로 재생하지 않고 현재 hold를 T에 반영한다. 준비 중 재정지는 같은 T로 준비를 다시 시작한다(사용자 결정, 2026-10-26).

복원한 T 이전의 상태는 유지한다. 보관 프레임 사이의 빈 시간은 입력 보정을 반영한 목표 판정 시각까지 진행하고, 그 경계 전의 자동 입력도 복원한다. 미래 노트라도 T 전에 실제로 처리한 판정은 남고, 과거 노트라도 T 뒤에 확정한 판정은 복원에서 빠진다. 바디·릴리즈 이력·트릴 교대·고도도 함께 복원하며 과거 타격/판정 표시를 다시 재생하지 않는다. T 뒤 실패는 되돌릴 수 있지만 T 이전 실패는 유지한다. 살아 있는 바디의 남은 부분과 일반 시작 조건을 사용하고, 미판정 시작 탭 노트를 자동 성공시키거나 실패 종속을 면제하지 않는다. 구현에서 남은 바디는 T 기준 시작 창이나 차트 시각의 원래 시작 창 중 한쪽 안에 든 새 down을 받고, 바디 시작은 T보다 앞서지 않는 hold 시각으로 잡는다(시작 탭 노트가 있는 바디와 없는 바디 모두). 원본 차트·source 참조를 보존하며 잘린 위치에 새 탭 노트나 점수 항목을 만들지 않는다.

처음부터/커서부터 새 테스트도 같은 음악 준비를 둔다. 새 커서 세션은 시작 시각 S보다 앞의 점수 항목을 Miss 없이 제외하고 같은 시각부터 포함한다. 처음부터 테스트는 곡 시간 0에서 자르지 않고 일반 재생과 같은 S·항목 범위를 쓰므로 음수 `meta.offsetMs`로 0보다 앞에 놓인 항목도 포함한다(사용자 결정, 2026-10-26). 전체 원본문서를 검증한 뒤 범위를 고른다. 기존 플레이를 되감을 때 S·원래 항목 범위를 바꾸지 않으며 커서 앞으로 되감거나 범위를 재선택하지 않는다.

일반 곡의 첫 재생·Retry는 음악 준비 3초 없이 바로 시작한다(사용자, 2026-10-26). 처음부터/커서부터 테스트의 음악 준비와 일시정지 재개의 되감기·음악 준비는 유지한다.

고정 3초 되감기와 일반·명시 테스트 플레이 연결을 구현·검증했다(코어·이력 복원은 #342, 테스트 재생 연결은 #346, 일반 곡 재생 연결은 #347). 튜토리얼 목록과 후속 범위는 [PRD §12](../prd.md#12-미정-사항)에서 추적한다.

### 레인 (Lane)

화면에 표시되는 노트 낙하 경로. not4k에는 항상 4개의 레인(L1～L4)이 존재한다. 레인의 수는 변하지 않으며, 유저가 바인딩하는 키의 수만 변한다.

### 레인 분할 (Lane Split)

유저가 양손으로 4개의 레인을 어떻게 나누어 담당하는지를 가리킨다. 기존 4키 게임은 2/2 고정이지만, not4k에서는 트릴 노트의 존재로 인해 1/3, 3/1, 0.5/3/0.5 등 가변적인 분할이 가능해진다.

### 스냅 (Snap)

두 뜻을 함께 가리킨다.

- **배치 격자의 한 칸**: 비트 분할(4비트, 8비트, 16비트)로 박을 나눈 배치 격자의 한 칸. 비트 분할에 따라 스냅 간격이 달라진다. 피스 표기법에서 한 행이 한 스냅에 대응하고, 에디터의 "한 스냅씩 이동"은 지금 고른 간격 한 칸만큼 옮긴다는 뜻이다.
- **편집 보조**: 에디터에서 노트 배치·이동 위치를 이 격자의 가장 가까운 칸에 맞추는 기능. 간격은 `snapDivision`(1/N박, 예: 1/4박·1/8박·1/16박)으로 고른다.

스냅은 편집 중 위치 보정이며 차트 해상도 제약이 아니다. 차트의 박은 임의의 분수를 가질 수 있고, 지금 격자 밖에 놓인 기존 노트(예: 스냅 1/4박에서 1/16박 위치)도 그대로 hover·선택·삭제할 수 있다. 히트 테스트는 스냅과 무관하게 실제 위치를 쓴다([차트 에디터 스펙](../spec/chart-editor.md#스냅)).

### 비트 분할 (Bit Division)

한 박자를 몇 등분하는지를 나타낸다. 4비트는 1박 1노트, 8비트는 1박 2노트, 16비트는 1박 4노트. BPM과 결합하여 초당 노트 수(노트 밀도)를 결정한다.

### 비행 배경

플레이 화면에서 비행 시나리오와 고도에 따른 공간 흐름을 표현하는 배경이다. 비행 배경의 움직임은 기어 모션과 별도의 게임 내 설정으로 끌 수 있게 한다. 설정의 기본값은 켬이며, 일반 플레이와 옵저버가 같은 설정을 사용한다. 끄면 어두운 고정 배경으로 바꾸고, 노트·기어·고도 게이지는 그대로 표시한다. 이 설정으로 노트 진행·입력 판정·고도 계산을 멈추지 않는다. 기어 모션은 별도 설정을 따르며, 운영체제의 모션 감소 설정을 자동으로 따르지 않는다([RFD 0100](../rfd/0100-flight-background-motion-setting.md)). 비행 배경 움직임 설정의 런타임 반영은 후속 작업이다.

### 기어 (Gear)

플레이 화면에서 레인 영역을 둘러싼 요소. 장식 그림(기둥·장갑·하단 바)과 그 위의 `gearMotion`(기어 위 장식 애니메이션: 광원 띠·게이지 액체 흐름과 기포·발광선·하단 바 빛), 양옆 유리관 게이지, 레인 아래 키 덱을 함께 가리킨다. 한국 리듬게임 커뮤니티에서 레인을 둘러싼 테두리 스킨을 부르는 established 이름이라 "기어"로 쓴다([term-map](term-map.md) B).

- **배치**: [RFD 0029](../rfd/0029-frame-aspect-fit-narrow-lanes.md)에 따라 그림 한 장을 비율 그대로 줄여 그림 속 레인 창을 게임 레인 영역에 정확히 맞추고, 기어 아래끝을 화면 아래보다 [기어 y 오프셋](#오프셋-구분) `GEAR_OFFSET_Y`(10, 화면 y축이라 +가 아래)만큼 아래에 고정한다. 리프트 0%의 판정선도 같은 양만큼 함께 내려(y 426) 판정선과 덱·키 윗면 사이 틈은 y 오프셋 0일 때와 같고, 기어 아래쪽 원본 약 22행은 화면 밖으로 잘린다([#257](https://github.com/nanana3679/not4k/issues/257)). 리프트와 무관하게 움직이지 않는다. 레인은 키 윗면에서 끝난다(레인 끝, `GameRenderer`의 `laneEndY`). 레인 배경은 레인 끝까지만 그리고, 노트·롱노트·마디선·`trillZone`·`restZone`·키빔을 담은 `laneContentLayer`는 레인 끝 위 사각형 클립(`laneEndClip`)으로 자른다([#247](https://github.com/nanana3679/not4k/issues/247)). 판정선·키봄·판정 글자와 기어는 클립 밖이다. 기어를 그리지 않는 렌더러(튜토리얼 재생기·노트 에셋 시연실)의 레인 끝은 판정선 + 노트 반 칸이다.
- **에셋**: 지금은 스킨 공용 에셋(기어 그림 `public/gear/gear.png`, 스킨 매니페스트 키 `gearImage`와 그 유리관에 겹치는 고도 게이지 빈 유리 `public/gear/gear-gauge-empty.png`, 키 `gearGaugeEmpty`)을 모든 스킨이 함께 쓴다. 그래서 기어 이름에는 Classic 같은 노트 스킨 이름을 붙이지 않는다. 스킨마다 다른 기어를 쓸지는 [PRD §12](../prd.md#12-미정-사항)에서 추적하며, 그렇게 되면 노트 스킨 이름이 아니라 기어 디자인 이름으로 나눈다(예: `public/gear/<디자인>/`).
- **`gearMotion`**: 기어 위에 추가(`addGearOverlay`)하는 장식 애니메이션이다(광원 띠·게이지 액체 흐름과 기포·발광선·하단 바 빛, 구 표기: 기어 움직임). 애니메이션 경과 시간(`GearMotionControls.timeMs`)은 곡 시간(`GameClock`)이 아니라 렌더 프레임 간격(`renderFrame`의 `deltaMs`) 누적으로만 나아가 일시정지 중에는 멈춘다. "움직이다"는 위치가 바뀌는 것(노트 스크롤, 리프트로 오르는 판정선)에만 쓰고 이 애니메이션에는 쓰지 않는다. 설정 `Gear Motion`(기본 켬)을 끄면 만들지 않으며, 운영체제의 모션 감소 설정(`prefers-reduced-motion`, macOS·iOS '동작 줄이기', Android '애니메이션 삭제', Windows 11 '애니메이션 효과')은 따르지 않는다([RFD 0030](../rfd/0030-ignore-os-reduced-motion.md)). 에셋(`gear-motion.json`과 텍스처)은 `public/gear/gear-motion/`에 둔다.
- **유리관 게이지(고도 게이지)**: 기어 양옆 유리관이 `altitude`(0～1)를 아래 기준 채움으로 보여 준다. 두 유리관은 같은 값이고, 비행 배경과 같은 프레임의 같은 고도를 쓴다. 기어 그림의 가득 찬 유리관 위에 빈 유리(스킨 공용 `gearGaugeEmpty`)를 위에서부터 채움 경계까지 덮으며, 경계 8행은 부드럽게 옅어진다(채움 1은 그림 그대로, 0은 전부 빈 유리). 값이 바뀌면 약 300ms ease-out 느낌으로 따라가고(렌더 프레임 간격 `deltaMs`로 나아감, 일시정지 중 멈춤, `prefers-reduced-motion`과 무관), `setChart` 때와 warm-up(`prepareForPlayback`)의 첫 프레임에는 이징 없이 바로 맞춘다. 낮은 고도에서도 색을 바꾸거나 경고하지 않는다([비행 콘셉트](../design/flight-concept.md)). `gearMotion`의 게이지 액체·기포는 채운 부분에서만 보인다. 기어를 그리지 않는 렌더러(튜토리얼·노트 에셋 재생기)에는 없다.
- **코드 식별자**: `gearImage`(스킨 매니페스트 키·텍스처, 기어 바탕 그림), `gearGaugeEmpty`(스킨 매니페스트 키·텍스처, 고도 게이지 빈 유리 아틀라스 `public/gear/gear-gauge-empty.png`), `showGear`·`gearOffsetY`(렌더러 옵션, 기어를 그릴 때 기본 `GEAR_OFFSET_Y`), `constants.ts`의 `GEAR_OFFSET_Y`, `GameRenderer`의 `gearLayer`·`buildGear`·`buildGearGauge`, 레인 끝 `laneEndY`·`laneContentLayer`·`laneEndClip`, `gearGeometry.json`·`gearLayout.ts`의 `GearLayout`·`GearGeometry`(`silhouetteBottom`·`gauge` 등)·`GearGaugeGeometry`·`GearStage`(`offsetY`)·`layoutGear`·`clampGearOffsetY`·`GEAR_GEOMETRY`·`GEAR_TEXTURE_OPTIONS`·`GEAR_CLEARANCE`, `GameRenderer.gearLayout`·`addGearOverlay`, 고도 게이지 `gearGauge.ts`의 `GearGauge`·`gaugeEmptyRows`·`easeGaugeLevel`·`GEAR_GAUGE_EASE_TAU_MS`(`GameRenderer.gearGaugeLevel`, Lab 미리보기 고도 고정 `GameRenderer.setAltitudeOverride`), `gearMotion`의 `GearMotionController`·`GearMotionControls`(`GameRenderer.gearMotion`, 옵션 `gearMotion`), `gearMotion*.ts`의 `createGearMotion`·`acquireGearMotionAssets`·`GEAR_MOTION_*`, `gearMotionKeepAlive.ts`의 `keepGearMotionAssets`, 게임 설정 `gearMotion`. 생성기가 만드는 측정 데이터와 `gearMotion` 에셋도 같은 이름을 쓴다(`gearGeometry.json`의 `silhouetteBottom`, `gear-motion.json`의 `image: {width, height}` = `GearMotionData.image`).
- **쓰지 않는 표현**: 이 뜻으로 "프레임"을 쓰지 않는다. 프레임은 화면 한 장(`renderFrame`, `requestAnimationFrame`, 게임 프레임, 프레임 시간)과 헷갈리기 때문이다. 옛 이름(`classicFrame*`, `FrameMotionController`, 설정 `Frame Motion`, 매니페스트 키 `gearFrame`, 렌더러 옵션 `showGearFrame`, 스킨 이름을 붙인 `classicGear*`·`/lab/classic-gear`)은 [#231](https://github.com/nanana3679/not4k/issues/231)에서 바꿨다. 보관한 Classic 버전의 매니페스트(`assets-lab/classic/versions/*`, `classicSkinVersions.ts`)는 보관 당시 키 `gearFrame`을 그대로 둔다. 결정 기록(RFD 본문·디자인 문서·CHANGELOG 지난 항목)의 "프레임"은 그때의 표기로 남긴다.

### 마스터 볼륨 (Master Volume)

게임 플레이·에디터 재생·곡 프리뷰 등 전체 오디오 출력의 음량을 조절하는 설정이다(코드 `masterVolume`, 범위 0～100%, 기본 100%). 기기별 브라우저에 저장하고 계정 설정 동기화에서 제외하며, 로그인해도 해당 기기의 값을 유지한다([RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

### 오프셋 구분

플레이 설정·렌더링에서 "오프셋"이라 부르는 값은 넷이다. 입력·시각은 실제 시간(ms), 판정선·기어 y는 화면 위치(논리 px)이고 기준과 부호가 서로 다르다([RFD 0031](../rfd/0031-audio-first-timing-model.md)).

| 이름 | 식별자 | 종류 | 단위 | 기준과 부호 |
|---|---|---|---|---|
| [입력 오프셋](#입력-오프셋-input-offset) | `inputOffsetMs` (설정 `Input Offset`, 기본 0) | 시간 | 실제 ms | 배속 r을 곱해 입력 시간에만 더한다(`GameClock.toInputTimeMs`). 늦게 누르면(SLOW) 음수다 |
| [시각 오프셋](#시각-오프셋-visual-offset) | `visualOffsetMs` (설정 `Visual Offset`, 기본 0) | 시간 | 실제 ms | 배속 r을 곱해 시각 시간에만 더한다. 화면이 소리보다 늦게 보이면 양수 |
| 판정선 오프셋 | `judgmentLineOffset` (기본 `JUDGMENT_LINE_OFFSET`) | 위치 | 논리 px | 화면 아래에서 **위로** 잰 거리, 기본 184(튜토리얼 재생기 50). 클수록 판정선이 위다 |
| 기어 y 오프셋 | `gearOffsetY` (게임 값 `GEAR_OFFSET_Y`) | 위치 | 논리 px | 화면 y축이라 **+가 아래**, 게임 값 10. 기어와 판정선을 함께 옮긴다([#257](https://github.com/nanana3679/not4k/issues/257)) |

"오프셋"만 따로 쓰지 않고 어느 오프셋인지 이름을 붙인다. 시간 오프셋의 자세한 정의는 [입력 오프셋](#입력-오프셋-input-offset)·[시각 오프셋](#시각-오프셋-visual-offset)에 있다. 현재 차트 메타데이터의 `offsetMs`는 음원 정렬용 오프셋의 저장 표현이다. 기존 문서의 차트 오프셋이라는 이름으로도 기록되어 있지만, 채택한 소유 규칙은 같은 곡의 차트들이 공유하는 [곡 타이밍](#곡-타이밍)이다. 설정에서 제거한 옛 `offsetMs` 키와 음원 정렬용 오프셋은 별개다.

### 녹숫 (Green Number)

노트가 레인 위끝(서든을 쓰면 서든 커버 아래끝)에 처음 보이고 판정선에 닿기까지 걸리는 시간이다. 비트매니아 IIDX의 녹색 숫자(green number)를 가리키는 한국 리듬게임 커뮤니티 이름이다. IIDX의 녹색 숫자는 60Hz 기준 프레임 수의 10배라(녹숫 300 ≈ 0.5초) 단위가 다르며, not4k는 시간(초·ms)으로 다룬다. 스크롤 속도(`scrollSpeed`, px/초)·리프트(판정선 높이)·서든이 모두 이 값 하나로 모이므로, 사용자마다 다른 설정을 한 숫자로 비교할 때 쓴다. 게임 설정 화면에는 아직 표시하지 않는다. 기본 설정(스크롤 속도 800, 리프트 0%, 판정선 y 426)에서는 약 0.54초다.

**추정 녹숫**은 차트 Lv.마다 정하는 기준 녹숫으로, 그 Lv.를 치는 사용자가 흔히 쓸 녹숫을 넉넉하게(길게) 잡은 값이다. Lv.1 3000ms부터 Lv.15 500ms까지 선형으로 줄어, Lv.n은 3000 − (n − 1) × 2500 / 14 ms다(Lv.8은 1750ms). Lv.15보다 높으면 500ms, Lv.1보다 낮거나 Lv.가 없으면 3000ms다. `restZone` 판넬 연출([RFD 0034](../rfd/0034-rest-zone-lane-panel.md), [Lab `restZone Lane`](../spec/lab-preview-catalog.md#restzone-lane))의 전환 시각과 [`restZone` 최소 길이 지침](chart-design.md#9-restzone은-판넬-연출이-들어갈-만큼-길게-잡는다)의 기준이다.

### 흰숫 (White Number)

서든 커버와 리프트가 노트가 보이는 레인을 얼마나 줄이는지를, 레인 위끝(y 0)부터 리프트 0% 판정선(y 426)까지를 1000으로 놓고 잰 값이다. 비트매니아 IIDX의 흰색 숫자(white number)를 가리키는 한국 리듬게임 커뮤니티 이름이다. IIDX에는 화면 위쪽의 SUD+ 흰숫과 아래쪽의 LIFT 흰숫이 따로 있고, 흰숫을 숫자 하나로 말할 때는 보통 둘을 더한 합계를 뜻한다. not4k 설정은 같은 높이를 100%로 놓고 %로 보여 주므로 위쪽 흰숫은 서든 %의 10배, 아래쪽 흰숫은 리프트(판정선을 올리는 양) %의 10배, 합계 흰숫은 (서든 + 리프트) %의 10배다(서든 30%·리프트 20%면 300 + 200 = 500). 노트가 보이는 레인은 426 × (1000 − 합계 흰숫) / 1000, 곧 426 × (100 − 서든 − 리프트)%이고 합계가 1000(100%)이면 보이는 레인이 없다. not4k의 리프트는 판정선만 올리고 판정선 아래를 덮지 않으므로, 판정선 아래로는 노트가 계속 보인다. [녹숫](#녹숫-green-number)은 이 보이는 높이에 노트 반 칸을 더해 스크롤 속도로 나눈 값이다. 게임 설정 화면에는 흰숫을 표시하지 않는다. 기준과 세부는 [게임 코어 스펙](../spec/game-core.md#리프트--서든-lift--sudden)을 따른다([#291](https://github.com/nanana3679/not4k/issues/291)).

## 입력 체계

### 다중키 바인딩 (Multi-Key Binding)

하나의 레인에 2개 이상의 물리 키를 할당하는 not4k의 핵심 메커니즘. 이것이 트릴, 더블, 홀드 중 탭 등의 피스를 가능하게 한다.

### 가변 손배치 (Variable Hand Position)

유저가 차트의 흐름에 따라 손가락 배치를 실시간으로 바꾸는 플레이 방식. not4k의 정체성을 정의하는 핵심 개념이다. 키 수 자체는 고정이지만, 어떤 손가락이 어떤 역할을 하는지가 차트에 따라 달라진다.

### 엄검중약

약지·중지·검지·엄지를 활용하는 not4k 기본 프리셋의 추천 손가락 배치. 기본 예시에서는 소지에 주 역할을 배정하지 않는다. 손배치를 익히는 출발점이며, 플레이어는 손 크기·키보드·선호에 맞춰 바인딩과 운용을 조정할 수 있다. 편의·성능이나 재학습 없는 전환을 보장하거나 손가락 사용을 강제하는 규칙은 아니다([RFD 0044](../rfd/0044-keybinding-presets-as-starting-points.md)).

### 주키 (Main Key)

기본 손 위치에서 주로 사용하는 바인딩 키. 시스템상으로는 모든 바인딩 키가 동등하며(`keybinding.md` 핵심 규칙 2), 주키/보조키는 유저의 운용 개념이다.

### 보조키 (Auxiliary Key)

손 옮기기 등 특정 패턴에서만 한정적으로 사용하는 바인딩 키. 16키 프리셋은 16키를 동시에 쓰라는 뜻이 아니다. 동시 활용 8키는 일반적인 운용의 예시이며, 이를 넘겨 활용하는 배치는 흔치 않을 것으로 예상하지만 차트 제작·시스템 검증의 상한으로 두지 않는다. 패턴마다 유도되는 보조키가 달라져 차트 전체에서는 최대 16키가 활용될 수 있다([RFD 0058](../rfd/0058-simultaneous-key-count-as-example.md)). 사운드 볼텍스의 손 위치 이동(좌/우 분담을 12/34에서 12/23으로 옮기는 동작)을 키보드의 다중키 바인딩으로 치환한 것이 보조키의 대표 용도다. 상세는 `../spec/keybinding.md`의 "주키와 보조키" 섹션을 따른다.

### 손 이동

손이 담당 레인 또는 키 위치를 옮기는 동작. 특정 패턴과 무관하게 동작 자체를 가리킨다. bare "이동"은 에디터의 엔티티 이동과 충돌하므로 항상 "손 이동"으로 한정한다. 방향에 따라 둘로 나뉜다.

- **수평 이동**: 손이 **레인 축(좌우)** 으로 옮겨 담당 레인이 바뀐다(예: 오른손 34→23). **2/2 분할 경계를 넘는 수평 이동**이 피스 `PP-009`(구 표기: 건너가기, Crossover)이며, 양손이 교대해 부담을 분산한다(`L1L2 → L3L4 → L2L3`). PLv.11. 양손의 물리적 교차는 필수 조건이 아니며, 실제 손의 경로는 키 바인딩과 손배치에 따라 달라진다([RFD 0065](../rfd/0065-horizontal-movement-and-lane-assignment.md)).
- **수직 이동**: 손이 **키보드 행(상하)** 으로 옮긴다. 같은 레인쌍을 연속으로 동시치기-트릴할 때, 해부학적으로 불리한 손가락쌍 전환(검중↔엄약)을 피해 같은 손가락쌍(엄중)을 상하로 옮겨 같은 폼으로 친다.

### 파지

특정 패턴을 파훼하기 위한 손배치 전략. 손 이동을 동원해 패턴에 대응하는 응용 개념이다. 손배치가 "어느 손이 어느 레인을 맡는가"라는 구성·상태라면, 파지는 그 손배치를 패턴에 맞춰 운용하는 전략이다. IIDX의 파지법에서 이름을 가져왔다.

### 키 교대

한 레인 안에서 활성 키를 같은 레인의 다른 바인딩 키로 전환하는 가장 기본 단위(primitive)의 동작. 다중키 바인딩이 전제다. 레인 내 입력 단위의 전환만을 가리키며, 손 단위의 전환은 파지가 담당한다 — bare "교대"는 쓰지 않고 항상 "키 교대"로 한정한다.

**파생**: 트릴 = 빠른 키 교대 반복 / 릴리즈탭 = 롱노트 끝 키 교대 / 홀드 교대 = 홀드 중 키 교대 / `goodTrill` = 키 교대 실패.

**구현**: `alternation`/`trillAlternation`.

### NM 트릴 표기 규약

트릴을 점유하는 두 레인의 쌍으로 표기하는 규약. N<M으로 적는다 (예: 12 트릴, 23 트릴, 34 트릴). 23 트릴은 2/2 분할의 중앙 경계를 넘으므로 경계를 넘는 손 이동·파지와 직결되며, 같은 트릴이라도 손배치(2/2 vs 1/3 등)에 따라 난이도가 달라진다. 레인 번호와 기존어 트릴의 조합이라 표기는 한국어/영어와 무관하다.

## 입력방식

한 레인에 2키 이상이 바인딩된 환경에서 발생하는 고유한 입력 처리 방식. 일부는 대응하는 피스(PP-000 체계)를 가진다.

### 홀드 중 탭 (Tap-in-Hold)

한 키(A)로 롱노트 홀드를 유지한 채 다른 키(B)로 싱글 노트를 탭하는 입력방식. 두 키가 동시에 활성 상태가 된다. 가장 직관적인 처리 방식. 탭 빈도가 낮을 때 유리하다 (인지 부하 적음). 롱노트 중 탭(`PP-003`)에서 활용된다. 입력방식인 홀드 중 탭과 피스명인 롱노트 중 탭을 구별한다([RFD 0103](../rfd/0103-long-note-mid-tap-piece-name.md)).

### 릴리즈탭 (Release-Tap)

한 레인에서 롱노트가 끝날 때, 유지하던 키(A)를 떼면서 같은 레인의 다른 키(B)를 누르는 입력방식. 릴리즈와 탭이 동시에 발생하는 키 교대 동작이다. 롱노트가 끝나는 패턴에서 사용된다. 롱노트 끝 탭(`PP-004`) 등의 피스에서 활용된다. 릴리즈탭은 입력방식명이며 피스 이름과 구별한다([RFD 0077](../rfd/0077-long-note-end-tap-piece-name.md)).

연결된 바디의 중간 head를 처리하는 대안이기도 하다. head에서 키를 교대하고 정당한 승계를 사용하면 바디를 이어갈 수 있다. 실제 감소 release가 있는 끝과 감소 없는 연결 경계는 구분한다. 세부는 [홀드 교대](#홀드-교대)와 [사례 NJ-F02](../spec/note-judgment-cases.md#nj-f02)를 따른다.

### 홀드 교대

**채택 계약·일반 기본 경로 구현·검증:** 같은 레인의 hold 수로 바디를 유지하므로 바디 도중 누른 다른 키도 유지를 이어받을 수 있다. 물리 키를 바디 몫의 고정 owner로 두지 않으며 확정 실패를 복구하지 않는다. 교대 up은 [명시된 릴리즈](#릴리즈-노트)의 적격 입력이 될 수 있고 숨은 연결 release로 소비하지 않는다.

#### 과도기 구형 계약·논의 기록

연결된 바디에서 같은 레인의 다른 등록 키로 유지를 이어받는 메커니즘. head·시작 입력으로 얻은 자격과 유효한 경계 판정 창을 사용하며, 고정 물리 owner는 두지 않는다. 임의의 raw held나 이미 실패한 바디의 재누름만으로 성립하지 않는다. 이 설명은 기존 엔진 기준이며, 후속 hold 수 모델([RFD 0032 §2-1](../rfd/0032-body-held-count.md#2-1-hold-수로-시작과-유지-판단), 엔진 이행 전)에서는 같은 레인의 hold 수로 유지를 판단하므로 바디 도중 누른 키도 유지를 이어받는다. 세부는 [롱노트 판정 모델](#롱노트-판정-모델)을 따른다. 대응 피스 없음 (메커니즘 단위).

### 의도된 연주

**채택 계약·일반 기본 경로 구현·검증:** 차트 제작자가 의도한 박자·손배치 흐름에서 바디의 hold 요구와 명시된 탭 노트·릴리즈 노트·틱 노트를 처리하는 연주를 검토하는 제작·플레이테스트 기준이다. 의도한 연주를 각 타이밍 입력의 Perfect 창 안에서 점수 손해 없이 처리해야 한다는 검토 기준은 유지한다. 새 모델에서는 아래 구형 정의의 “모든 up이 연결 release·`holdOnly` 끝에 쓰인다”를 요구하지 않는다. 명시하지 않은 up 소비나 점수를 만들지 않으며, 탭·교대의 up이 가까운 릴리즈에 배정되는 결과도 [제작 지침](chart-design.md#채택된-새-차트의-제작-계약)에서 확인한다.

#### 과도기 구형 계약·논의 기록

차트의 한 패턴을 박자에 맞춰 치는 방법 중, 각 경계를 지난 뒤 그 바디가 요구하는 hold 수만큼만 키가 남고, 판정 창 안에서 생긴 모든 up이 감소 release·연결 release·끝 release(`holdOnly` 끝 포함) 중 하나에 쓰이며, 각 입력을 그 판정의 Perfect 창 안 어디에서 쳐도 점수 손해가 없는 연주. 어떤 판정 창에도 들지 않는 up(바디 중간 교대)은 중립이다. 같은 키를 연결 경계 앞에서 떼고 뒤에서 다시 눌러 head를 치는 연주(`a-a-`, `ab-ab-`)는 정박보다 일찍 떼고 늦게 누를수록 유리하므로 의도된 연주가 아니라, 판정은 손해 없이 처리하는 허용 입력(탈출구)이다([RFD 0032 §9-2](../rfd/0032-body-held-count.md#9-2-허용-입력탈출구)). 판정 모델은 의도된 연주를 점수 손해 없이 처리해야 하며, 패턴별로 확인한 의도된 연주는 회귀 사례가 된다. 의도된 연주가 아닌 입력도 막지 않고 같은 규칙으로 판정하지만, 남는 up이 뒤 판정에 주는 영향은 보장하지 않고 플레이어 책임으로 둔다. 예를 들어 head가 있는 2→1에서 A·B를 떼고 C로 head를 친 뒤 유지하는 연주와, A를 유지하고 B를 떼며 C로 head를 쳐서 바로 떼는 연주는 의도된 연주다. A/B를 쥔 채 C로 head만 탭하면 single 바디에 키가 둘 남아 의도된 연주가 아니다. `holdOnly` 끝에서 뗀 up은 그 끝이 가져간다([RFD 0032 §7-1](../rfd/0032-body-held-count.md#7-1-holdonly-끝은-good-창-안의-up을-가져간다)). 마지막 끝 뒤에 남는 키는 여분 키다. 위 정의는 기본 기준이며, 차트가 여분 홀드를 일부러 쓰게 짠 패턴(예: 감소마다 `holdOnly`인 빠른 `=-=-` 반복을 A/B로 계속 누르기)에서는 차트의 의도를 우선한다([RFD 0032 §7-2](../rfd/0032-body-held-count.md#7-2-holdonly-감소에서-키를-남기는-연주)). 판정 규칙이 아니라 패턴 검토와 [제작 지침](chart-design.md#차트-설계-시-주의사항)의 기준이다. 근거는 [RFD 0032 §9-1](../rfd/0032-body-held-count.md#9-1-의도된-연주의-정의).

### 허용 입력(탈출구)

**채택 계약·일반 기본 경로 구현·검증:** 실제 바디 경계에서 앞 바디를 끝내고 뒤 바디를 자기 시작 조건에 따라 따로 시작하는 연주도 허용한다. 아래 구형 연주의 숨은 연결 up 소비는 이식하지 않으며, 이미 실패한 연결의 복구 가능 여부는 [바디 판정과 실패 종속](#바디-판정과-실패-종속)을 따른다.

#### 과도기 구형 계약·논의 기록

의도된 연주는 아니지만 판정이 점수 손해 없이 처리하도록 일부러 허용해 둔 연주. 같은 키를 연결 경계 앞에서 떼고 뒤에서 다시 눌러 head를 치는 `a-a-`(single 연결)와 `ab-ab-`(double head 연결)가 여기에 해당한다. 정박보다 일찍 떼고 늦게 누를수록 유리해 차트의 박자에 맞춰 행동하는 연주는 아니지만, 인지 부하가 가장 적어 처음 접하는 플레이어가 칠 가능성이 높으므로 허용한다. 경계 전에 뗀 up이 앞 바디를 끝내고([연결 release](#연결-release)) 다시 누른 down이 head를 치므로 손해가 없다. 근거는 [RFD 0032 §9-2](../rfd/0032-body-held-count.md#9-2-허용-입력탈출구)다.

### 홀드 트릴 (Hold Trill)

롱노트 중 탭을 짧은 롱노트의 연결로 표현했던 구 명칭. 바디 위에 노트를 놓을 수 없던 제약 때문에 이어 놓은 동일한 배치이며, 독립 입력방식이나 피스로 분류하지 않는다. 기존 `PP-010`은 롱노트 중 탭(`PP-003`)으로 통합했다([RFD 0079](../rfd/0079-merge-hold-trill-into-mid-tap.md)).

### 엄지 눕히기 (Thumb Lay)

엄지를 세우지 않고 옆으로 눕혀서 인접한 키 두 개를 동시에 누르는 입력방식. 엄검중약 배치에서 엄지의 접촉 면적을 넓혀 인접 레인을 함께 커버한다. 더블 노트 처리나 수평 이동 상황에서 활용된다. 대응 피스 없음 (메커니즘 단위).

## 노트 타입

> **원칙: 모든 노트 타입은 Lv.1부터 사용할 수 있다.** 각 차트에 모든 타입을 넣어야 한다는 뜻은 아니며, 노트 타입 자체에는 최소 레벨 제한이 없다. 차트의 의도에 맞춰 사용할 타입을 선택한다. 난이도는 피스의 활용 정도와 실제 배치의 부담으로 조절한다. PLv.보다 낮은 레벨의 짧은 체험은 [피스 레벨](#피스-레벨-plv)의 기준을 따른다.

입문 트릴·더블은 내측 2·3번 레인에 한정하지 않는다. 충분히 느리고 단순한 짧은 체험은 외측 1·4번 레인에서도 허용하며, 독해·연주 부담과 앞뒤 손배치 흐름이 차트 수준에 맞는지 확인한다. 모든 레인에 배치해야 한다는 뜻은 아니다([RFD 0057](../rfd/0057-beginner-trill-double-on-outer-lanes.md)).

### 노트 종류의 시각적 구분

기본 디자인에서 색을 구별하지 않아도 모양·표식으로 노트 종류를 알아볼 수 있어야 한다. 색상은 구분을 보조할 수 있으나 유일한 단서로 사용하지 않는다. 구체적인 형태·표식은 입력 요구를 단순하고 명확하게 읽는 원칙을 유지하며 정한다([RFD 0084](../rfd/0084-note-types-distinguishable-without-color.md)). 실제 에셋의 검증과 남은 세부는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

롱노트의 유지 중·실패 같은 상태를 색 이외의 단서로 구분하는 것은 실제 화면에서 검토할 개선 목표다. 모든 상태에 새 표식을 붙이는 필수 조건으로 두지 않는다. 기존의 밝기·투명도·코어 점등으로 구분 가능한지와 추가 표식의 독해 부담을 함께 확인한다([RFD 0084](../rfd/0084-note-types-distinguishable-without-color.md)).

### 탭 노트 (`tap`)

특정 시점의 누름을 요구하는 명시적 점수 노트다. 싱글·더블·트릴을 포함하며 시작점에 배치하면 헤드 노트라고 부른다. 요구 한 몫당 down 하나를 소비하고 이론 가중치 3인 점수 항목 하나를 만든다. 같은 down의 hold가 바디의 시작·유지 조건에도 참여할 수 있다. 탭 노트와 바디는 별개 엔티티이며 탭 노트 판정 하나가 double 바디의 두 몫을 자동 충족시키지는 않는다. 새 바디와의 관계는 [RFD 0037 §2～4](../rfd/0037-explicit-score-notes-and-body.md#2-구성과-점수-의미)를 따른다(채택 계약·일반 기본 경로 구현·검증). 저장 JSON `type`과 코드 이름은 `tap`이다. 이전 이름 포인트 노트(Point)·`point`는 [RFD 0041](../rfd/0041-explicit-score-note-names-tap-tick.md)에서 바꿨다. 구형 v3의 포인트 노트(`PointNote`, `single`·`double`·`trill` 타입)는 과도기 구형 의미로 그 이름을 유지한다.

### 바디

같은 레인에서 필요한 hold 수를 요구하는 구간이다. single은 1, double은 2이며 양수 길이와 길이 0을 허용한다. 바디 자체의 점수 항목·이론 가중치는 0이고 down·up을 소비하지 않는다. 시작 탭 노트·끝 릴리즈·틱 노트는 각각 명시하는 별개 노트다. 실제 시작·끝 경계는 저장·컴파일·편집에서 보존하며 맞닿은 바디를 자동 병합하지 않는다. 바디의 정상 완료와 릴리즈 정산·화면 잔존은 서로 다른 사실이다. 세부는 [바디 판정과 실패 종속](#바디-판정과-실패-종속)을 따른다(채택 계약·일반 기본 경로 구현·검증).

### 틱 노트 (`tick`)

양수 길이 또는 길이 0 바디 위에 명시하여 **바디와 같은 판정 상태에 점수 정산만 더하는 노트**다. 화면 표시도 틱 노트라고 부르며 따로 이름을 두지 않는다. 자체 down·up 소비, 독립 허용 창·기한·실패 조건은 없다. 같은 입력과 바디 상태를 여러 틱 노트가 확인할 수 있으며, 틱 노트의 추가·제거가 기존 바디 진행·탭 노트/릴리즈 배정·바디 실패 효과를 바꾸지 않는다(채택 계약·일반 기본 경로 구현·검증). 저장 JSON `type`과 코드 이름은 `tick`이다. 이전 이름 유지 노트(화면 표시는 유지 표식)·`sustain`은 [RFD 0041](../rfd/0041-explicit-score-note-names-tap-tick.md)에서 바꿨다. 바디의 hold를 확인하는 [유지 판정](#유지-판정)·유지 유예의 "유지"와 구별한다.

- 정상 유지 중이면 틱 노트 시각에 성공한다. 바디의 최초 시작 판단·회복 유예 중이면 그 결과를 기다리며 유효한 늦은 시작·회복 뒤 성공, 확정 실패 뒤 종속 0점으로 처리한다.
- 유효한 이른 정상 종료에서는 **그 종료 몫에 속한** 미처리 틱 노트를 함께 성공 처리한다. 뒤 바디 소속 경계 틱 노트는 포함하지 않는다. 그 밖에는 이른 down만으로 미래 틱 노트를 선판정하지 않는다.
- 성공한 틱 노트 한 몫당 Perfect 3점·이론 가중치 3·콤보 +1이며 일반 Perfect와 같은 고도 계산에 한 번 참여한다. 일반 릴리즈가 Good이어도 틱 노트 성공은 Perfect다. 타이밍 오차·FAST/SLOW는 만들지 않는다.
- 이미 성공한 몫은 이후 실패로 되돌리지 않는다. 바디 실패로 기회가 사라진 미처리 몫은 원래 가중치의 0점으로 한 번 정산하고 추가 Miss·콤보·고도 효과를 만들지 않는다.
- 틱 노트의 몫 수(`count`)는 소속 바디의 hold 수를 따라 single 1개·double 2개다. 소속은 같은 레인의 시작·끝을 포함한 바디 구간에서 도출하며 제작자에게 별도 소속 ID를 요구하지 않는다. 공유 경계에서는 뒤 바디에만 속한다.
- 같은 hold 수의 1→1·2→2 연결점과 트릴 바디에는 배치하지 않는다. 한 바디 내부·독립 길이 0·1→2·2→1은 허용한다. 증가 경계는 뒤 double에 맞춘 두 몫, 감소 경계는 뒤 single에 맞춘 한 몫이다. 틱 노트 자체가 경계·새 시작·실패 복구를 만들지는 않는다.

길이 0에도 바디 자체의 시작 허용을 적용하며 정확한 한 시각 입력으로 좁히지 않는다. 표시·편집은 [판정 효과](#판정-효과-confirmedjudgmenteffects)와 [바디와 명시 노트의 편집 관계](#바디와-명시-노트의-편집-관계)를 따른다. 근거는 [RFD 0037 §5～6](../rfd/0037-explicit-score-notes-and-body.md#5-유지-노트)다.

### 싱글 노트 (Single Note)

레인에 바인딩된 키 중 아무 키 하나를 누르는 기본 노트. 표기: `o`

### 롱 노트 (Long Note)

**채택 계약·일반 기본 경로 구현·검증:** 긴 유지 구간을 읽는 관용 이름이다. 새 모델의 [바디](#바디)에는 끝 release나 상태 점수가 내장되지 않는다. 시작점의 별도 탭 노트를 헤드 노트라고 부르며, 명시된 릴리즈가 있을 때만 실제 뗌 점수 노트를 요구한다. 아래의 분리할 수 없는 구형 시작점·바디·끝점 엔티티는 과도기 구형 의미로만 보존한다.

#### 과도기 구형 계약·논의 기록

키를 누르고 유지하다가 끝 지점에서 떼는 노트. 바디는 `-`(싱글) 또는 `=`(더블)로 표기한다.

##### 구성요소

롱노트에는 유지 구간의 시작점과 끝점이 있다. 끝점은 구간의 경계이며, 그 자체가 뗌을 요구하는 릴리즈 노트는 아니다. 같은 레인·시각의 바디 끝과 릴리즈 노트는 허용하는 조합이다. 이전 모델의 바디 끝·별도 길이 0 롱노트 중복 금지를 새 조합에 적용하지 않는다.

| 구성요소 | 정의 | 역할 |
|----------|------|------|
| **시작점** | 롱노트의 유지 구간이 시작되는 위치 | 바디의 시작 경계이며 별도 head와 조합할 수 있다 |
| **바디 (Body)** | 시작점과 끝점 사이의 구간 | 요구하는 키 수를 유지해야 하는 영역 |
| **끝점** | 롱노트의 유지 구간이 끝나는 위치 | 바디의 끝 경계이며 뗌을 요구하려면 별도의 릴리즈 노트를 명시한다 |

> **"바디"의 용법**: "바디"는 시작점과 끝점 사이의 구간만을 가리킨다. 롱노트 전체를 가리킬 때는 "롱노트"를 사용한다. 예: "바디 유지 실패"(구간 내 키 홀드 실패), "롱노트 판정"(롱노트 전체에 대한 판정).

##### 헤드 노트

롱노트 자체에는 헤드가 포함되지 않는다. 시작점에 **별개의 일반 노트**(싱글/더블/트릴)를 배치함으로써 헤드를 구현한다. 헤드 노트와 롱노트는 별개의 엔티티이다. 성공한 head가 자기 담당 unit을 활성화하고 키를 등록한다. 이미 승계한 건강한 unit은 별도 head의 Miss로 실패하지 않는다. 시작점에 노트를 배치하지 않으면 "헤드 없는 롱노트"가 된다. 배정 세부는 [롱노트 판정 모델](#롱노트-판정-모델)을 따른다.

- **새 모델의 점수 범위**: 점수는 명시된 탭 노트·릴리즈 노트·틱 노트로 판정하며, 바디는 획득 점수와 달성률의 이론 가중치에서 제외한다. 바디의 유지 실패는 콤보 단절과 고도 손실로 반영한다.
- **판정 횟수(이행 전 엔진)**: 실제 head, 실제 release, 명시된 `holdOnly`가 각각 점수 항목이다. 일반 `connection` 성공에는 점수·콤보가 없으며 유지 실패는 무점수 Miss이다. double 끝점은 unit별로 판정한다. 새 바디·릴리즈 조합의 집계와 기존 데이터 이전은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다.
- **헤드-롱노트 타입 혼합**: 싱글 헤드 + 더블 롱노트, 더블 헤드 + 싱글 롱노트 등의 조합이 자유롭다.

### 트릴 노트 (Trill Note)

키 교대라는 입력 조건과 배치의 반복성·난이도는 별개다. 트릴 노트로 구성되어도 리듬이나 배치가 복잡할 수 있으며, 일정한 반복 패턴이나 낮은 부담을 보장하지 않는다([RFD 0042](../rfd/0042-trill-rules-and-pattern-repetition.md)).

`trillZone` 안에서 직전 입력과 다른 키를 눌러야 하는 노트. 2개 이상의 키 바인딩이 필요하다. 트릴 노트는 롱노트일 수 있다 (트릴 롱노트). 표기: `t`, 트릴 롱노트 바디: `t-`

교대 세트에는 head를 소비한 키만 등록한다. 바디 유지·승계나 release만 처리한 키는 등록하지 않는다. head 확정으로 세트를 갱신하고 head Miss로 이전 세트를 비우며, 추적 구간은 해당 노트의 차트상 `trillZone`을 따른다. 같은 timestamp의 복수 적격 입력은 최고 등급 입력 선택과 교대 한 번 인정 규칙을 적용하고 나머지 적격 head는 `goodTrill`로 처리한다. `goodTrill`은 head에만 적용하며 바디는 독립 판정한다. 기존 채택 규칙의 이행 범위는 [RFD 0020 §2.11](../rfd/0020-note-judgment-units-and-inheritance.md#211-함께-적용할-point트릴의-기존-채택-규칙)을 따른다.

### `trillZone` (구 표기: 트릴 구간)

트릴 노트가 등장할 수 있는 시각적 영역. `trillZone` 자체는 입력을 요구하지 않으며, 예고·시각적 구분·긴장도 유지의 역할을 한다. 구간 내 빈 스냅에서의 입력은 구간 밖의 빈 스냅과 동일하게 동작한다 — `trillZone`이 있든 없든 결과가 같다. 표기: `{` (시작) / `}` (종료) / `~` (구간 내 빈 스냅)

`trillZone`은 메인·보조 레인 모두에 배치하며 `lane`은 1 이상의 정수다. 구간 포함·시작 트릴 탭·트릴 바디·릴리즈 배타·겹침 제약과 생성·선택·이동·리사이즈·클립보드·취소는 두 영역에서 동일하다. 기존 보조 트릴이 구간 밖에 있으면 자동 구간 생성 없이 의미 위반으로 표시해 수리한다. 보조 구간은 `.extra.json`의 `extraTrillZones`에 `{ extraLane, beat, endBeat }`로 저장하고 에디터에서 `chart.trillZones`로 합친다. 게임에는 메인 노트·구간만 전달한다. 보조 위반도 저장·테스트 플레이 진입은 막는다([RFD 0086](../rfd/0086-auxiliary-lane-trill-zones.md)).

### `restZone` (구 표기: 휴지 구간)

차트 제작자가 배치하는 **레인별 저작 구간** `{ lane, beat, endBeat }`으로, 그 레인이 해당 구간 동안 안 쓰임을 나타낸다. `trillZone`의 형제(레인+박 범위 저작 구간)다. 목적은 가변 손배치에서 제작자가 의도한 **손 파킹 창**을 표면화해, 유저가 "이 레인은 당분간 안 쓰니 손을 옮겨도 되겠다"로 읽게 하는 것이다. 기능은 **오직 둘**이다: (1) 그 레인 구간을 "안 쓰는 레인"으로 보이게 하는 **시각 효과**(게임은 어둡게 dim하고(레인 판넬로 바꾸기로 [RFD 0034](../rfd/0034-rest-zone-lane-panel.md)에서 정했고 구현 전이다), 에디터 타임라인은 레인을 살짝 어둡게 깐 위에 검정 빗금을 긋는다), (2) 그 레인·구간에 노트나 `trillZone`이 오면 **의미 위반**으로 다루는 **배치 제약**(`trillZone`은 트릴 노트 등장의 암시라 "레인 안 씀"과 모순 → `restZone` 안에 존재 불가). 배치 제약은 RFD 0017 낙관적 편집을 따라 편집 중 transient 허용 + 저장·플레이 게이트에서 차단한다(structural 하드 거부 아님). **런타임 입력·판정·기록·랭킹·실패 조건에는 일절 개입하지 않는다.** 배경·대안·결정은 [RFD 0019](../rfd/0019-rest-zone-lane-guidance.md)를, 게임의 판넬 표시는 [RFD 0034](../rfd/0034-rest-zone-lane-panel.md)를 따른다.

### 더블 노트 (Double Note)

같은 레인에 바인딩된 서로 다른 물리 키 2개로 처리하는 노트. 각 키의 입력이 판정 창 안에 있어야 하며, 반드시 두 held가 겹쳐야 하는 것은 아니다. 같은 키를 두 번 누르는 더블클릭은 인정되지 않는다. 같은 double 끝의 두 실제 release에도 서로 다른 물리 키를 요구하며, 자격의 세부와 이행 상태는 [release 판정](#release-판정)을 따른다. 키 바인딩이 3개 이상인 레인에서는 서로 다른 아무 2개를 사용할 수 있다. 임팩트 강조와 플레이 다양성 확장의 역할을 수행한다. 표기: `D`

### Grace 노트 (Grace Note)

탭 노트(싱글/더블/트릴)의 누름 또는 명시된 릴리즈의 뗌에서 타이밍 등급 부담을 면제하는 노트. 명시 릴리즈에의 적용은 채택 계약·일반 기본 경로 구현·검증이다. 바디·틱 노트에 Grace나 구형 `holdOnly`를 붙이지 않는다. 탭 노트와 구형 포인트 노트에는 Grace 플래그를 부여한다. Good 윈도우 안의 유효한 입력은 타이밍 정밀도와 무관하게 타이밍 등급 Perfect를 받으며 FAST/SLOW를 집계하지 않는다. 트릴 교대 실패의 [`goodTrill`](#goodtrill-트릴-오입력-good--화면-표시-good)은 Grace 트릴 노트에도 그대로 적용한다. 기한까지 처리하지 못하면 Miss이고 Bad 단계는 없다. 음악 용어의 장식음(grace note)에서 이름을 가져왔다. 판정 창은 [판정 윈도우](#판정-윈도우-judgment-window)를 따른다.

- **설계 의도**: 학습·부담 조절·연출을 위해 선택적으로 사용하는 도구다. 복잡한 손배치와 정밀한 타이밍을 함께 요구하는 패턴도 해당 레벨에 맞으면 허용하며, 손배치 전환이나 교대라는 이유만으로 Grace를 의무 적용하지 않는다([RFD 0053](../rfd/0053-grace-as-selective-chart-tool.md)).
- **활용**: 새로운 입력방식의 학습 보조, 손배치 전환의 부담 조절, 해당 난이도에 비해 복잡한 리듬이나 빠른 입력 구간의 타이밍 정밀도 부담 완화, 곡의 강조점·연주 흐름을 드러내는 연출. 손배치가 단순한 구간이나 연출 목적만으로도 사용할 수 있다.
- **상세 리서치**: `../research/auto-best-judgment-note.md`

### `holdOnly` (구 표기: 유지 전용 롱노트)

**새 계약에서는 폐지했다.** 아래 정의는 과도기 동안 미수정 구형 항목을 읽고 표시·편집하기 위해 보존한다. 사용자가 에디터에서 승인한 [1차 기계 변환](#convertlegacychart) 밖에서는 새 릴리즈 없는 바디·Grace 릴리즈·틱 노트로 치환하지 않는다. 그 변환은 사슬 끝의 `holdOnly`를 릴리즈 없는 바디로, head 없는 같은 hold 수 연결의 `holdOnly`를 합친 바디의 틱 노트로, 길이 0 `holdOnly`를 길이 0 바디 + 틱 노트로 옮긴다. 증가·감소 연결과 트릴 바디가 낀 연결의 `holdOnly`, 보조 레인의 길이 0 `holdOnly` `trillLong`은 틱 노트 없이 변환 검토 목록에 싣는다. 릴리즈 없는 바디는 무점수이고, Grace 릴리즈는 실제 up을 요구하며, 틱 노트는 별도 명시 점수 노트다. 세 차이는 [구형 차트와 과도기](#구형-차트와-과도기)와 [RFD 0037](../rfd/0037-explicit-score-notes-and-body.md)을 따른다(채택 계약·일반 기본 경로 구현·검증).

<summary>이행 전 엔진과 이전 결정의 holdOnly 규칙</summary>

#### 과도기 구형 계약·논의 기록

롱노트 끝점의 **떼는 판정 면제 속성**. 아래 시작·유지·여분 키 설명은 기존 엔진 기준이며, 후속 hold 수 모델의 차이는 [RFD 0032 §2-1](../rfd/0032-body-held-count.md#2-1-hold-수로-시작과-유지-판단)·[§7-1](../rfd/0032-body-held-count.md#7-1-holdonly-끝은-good-창-안의-up을-가져간다)을 따른다(엔진 이행 전). 양수 길이는 자기 바디가 정당하게 활성화되고 등록된 키로 유지되어야 하며, 끝에서 실제 release 대신 Perfect/Miss 상태 판정을 한다. 현재 결정은 [RFD 0020](../rfd/0020-note-judgment-units-and-inheritance.md), 구체적 입력은 [판정 사례 명세](../spec/note-judgment-cases.md#nj-h01)를 따른다.

- **양수 길이의 시작**: 기존 엔진 기준으로는 자기 head·시작 입력 또는 정당한 승계가 필요하다. 기존 raw held나 다른 독립 노트가 소비한 down으로 자동 시작하지 않는다. head 없는 자기 시작은 down을 소비하되 시작 점수는 없다. 후속 hold 수 모델([RFD 0032 §2-1](../rfd/0032-body-held-count.md#2-1-hold-수로-시작과-유지-판단), 엔진 이행 전)에서는 미리 누른 키도 hold 수에 들어가고, head 없는 시작은 down을 별도로 소비하지 않으며 S+Good까지 hold 수를 채우면 된다. 시작 직후 hold를 잃어도 같은 기한까지 다시 채울 수 있다([RFD 0032 §8-1](../rfd/0032-body-held-count.md#8-1-시작-직후의-재충전)).
- **유지·완료**: 등록된 유지 키로 E까지 유지하면 Perfect. 유효한 이른 완료는 E−Good부터 가능하며, S+Good까지의 늦은 첫 활성화도 허용한다. 이미 활성화했다가 실패한 바디는 복구하지 않는다. FAST/SLOW는 집계하지 않는다.
- **이벤트 소비**: 상태 완료는 keyup을 소비하지 않는다. 같은 up으로 유효한 `holdOnly` 완료와 실제 release 하나가 함께 성립할 수 있다. 후속 hold 수 모델에서는 `holdOnly` 끝이 자기 Good 창 안의 up 하나를 가져가며 등급은 항상 Perfect이고, up이 없으면 유지로 완료한다([RFD 0032 §7-1](../rfd/0032-body-held-count.md#7-1-holdonly-끝은-good-창-안의-up을-가져간다), 이전 결정인 무소비를 대체). 끝 모양이 일반 끝과 같아 그 끝에서 떼는 것과 계속 누르는 것이 모두 정당하므로, 제작자는 계속 누르는 연주가 불이익을 받지 않게 배치한다([제작 지침](chart-design.md#8-holdonly-끝에서-계속-누르는-연주도-불이익이-없게-배치한다)).
- **double과 감소**: 앞 double의 두 unit 끝을 각각 판정한다. 2→1에서도 둘 다 성공하면 Perfect 2개이고, 하나는 종료되고 하나는 승계된다. 자동 Perfect가 물리 키의 종료·승계 배정까지 고정하지 않는다.
- **계속 유지한 키**: 감소에서 실제 keyup을 요구하지 않는다. 계속 held인 등록 키는 유효하게 남고 다음 증가에 승계할 수 있다. 자동 완료를 실제 keyup으로 취급하지 않는다.
- **면제 몫과 여분 키**: release를 면제받은 몫은 뒤 실제 release를 막는 여분 키 계산에서 제외한다. double `holdOnly` → single에서 A/B를 유지하다가 마지막에 A만 떼어도 single release를 처리할 수 있다. 임의의 일반 여분 키에는 이 면제가 없다. 두 unit을 나눠 시작해 둘째가 바로 이어지는 뒤 바디의 시작 이후에 활성화해도, 그 바디가 진행 중이면 모든 unit의 시작·실패가 정해진 뒤 같은 면제 몫을 가진다. 그 바디가 끝난 뒤의 활성화는 미정이다([PRD §12](../prd.md#12-미정-사항)). 면제 몫이 새 unit의 시작으로 이어지면 새 unit의 끝 판정을 따른다.
- **길이 0**: 시작=끝의 Good 창 안에서 기존 held로 통과할 수 있다. 기존 held를 확인하는 시점은 S−Good이며, 계속 유지하면 표시는 S에, 유효한 이른 up이면 그 시점에 처리한다. 독립된 일반 release 권한을 새로 만들지 않는다. double은 서로 다른 두 물리 키를 요구하지만 반드시 동시에 held일 필요는 없다.
- **트릴**: `trillLong`은 head가 필요하다. 양수 길이 `trillLong + holdOnly`는 허용하며 길이 0 조합은 금지한다.
- **점수·시각**: 명시된 `holdOnly`는 unit별 점수·콤보 항목이다. 마커는 `*`이며 Grace 노트와 시각 언어를 공유하되 판정 모델은 다르다.
- **배치**: 같은 레인·시각의 Point와 공존하지 않는다. 양수 바디 끝에 별도의 길이 0 롱노트를 붙이지 않는다. 일반 바디 끝의 Point는 허용한다.

## 피스

### 피스 (piece)

복수의 노트가 배치를 통해 상호작용하여 난이도를 발생시키는 단위. 개별 노트 타입과 달리, 피스는 각각 고유한 PLv.(피스 레벨)를 가진다. `piece-definition.md`의 피스 카탈로그에서 `PP-001` 등의 고유 ID로 관리하며 통합한 ID의 참조 이력은 보존한다.

**분류 기준**: 요구 입력과 동작 계획의 차이를 기준으로 나눈다. 필요한 누름·뗌·유지·키 교대와 이를 수행할 손배치 선택·전환이 같고, 자료 구조나 제작 제약 때문에 표현만 다르면 같은 피스로 묶는다. 겉모양이나 바디 구획만으로 독립 피스를 만들지 않는다([RFD 0079](../rfd/0079-merge-hold-trill-into-mid-tap.md)). 표현에 따른 독해 부담의 차이는 [차트 Lv.](#차트-레벨-lv)에 별도로 반영한다.

**이름의 사용 범위**: 제작·분석 문서에서는 공식 피스 이름과 ID를 사용한다. 플레이어에게는 튜토리얼 제목 정도에만 피스 이름을 사용하고, 본문은 실제 입력 동작과 연주 방법을 설명한다. 피스 이름의 암기를 요구하거나 일반 플레이·옵저버에 피스 이름 라벨을 표시하지 않는다. 노트 이름과 `trillZone` 등 입력 요구를 알리는 시각 표시는 별개다([RFD 0080](../rfd/0080-piece-names-in-tutorial-titles.md)).

**노트 타입과 피스의 관계**: 노트 타입은 개별 요소(싱글, 더블, 트릴, 롱)이며 Lv.1부터 사용할 수 있다. 피스는 이 요소들의 배치가 상호작용하여 난이도를 만들어내는 것이다. 예를 들어, 롱노트와 싱글 노트는 각각 Lv.1부터 사용할 수 있지만, 롱노트 끝에서 같은 레인의 다른 키로 탭하는 롱노트 끝 탭(`PP-004`)은 PLv.4의 피스이다.

> 구 용어: 패턴 조각 (Pattern Piece).

**용례**:

- "Lv.8 차트의 사비 구간에 PLv.7 피스 PP-002가 배치되어 있다"
- "앵커와 롱노트 중 탭을 결합한 고난이도 피스"

### 대표 피스

아래는 문서 전반에서 자주 참조되는 피스의 간략한 정의이다. 정식 피스 정의(PP-000 체계)는 `piece-definition.md`에서 관리한다.

- **짧은 트릴 (Short Trill)**: 짧은 구간에서 트릴 키 교대를 익히는 배치. 트릴 노트 2～4개는 대표 예시이며 개수를 성립 조건으로 고정하지 않는다. 실제 속도·지속 길이·다른 입력과의 조합으로 짧은 체험에 적절한지 확인한다([RFD 0073](../rfd/0073-short-trill-note-count-as-example.md)). PLv.1.
- **롱노트 중 탭**: 롱노트가 유지되는 동안 같은 레인에 싱글 노트가 나오는 배치(`-o`). 탭이 한 번 나오거나 여러 번 연속되는 경우 모두 포함하며 홀드 중 탭 또는 홀드 교대 입력방식으로 처리한다. 바디 위 노트 배치를 대신해 짧은 롱노트를 이어 놓았던 홀드 트릴도 같은 피스로 통합한다([RFD 0079](../rfd/0079-merge-hold-trill-into-mid-tap.md)). 피스 `PP-003`의 공식 명칭이다([RFD 0103](../rfd/0103-long-note-mid-tap-piece-name.md)). 구성 노트 타입: 싱글 + 롱. PLv.7.
- **롱노트 끝 탭**: 롱노트가 끝날 때 같은 레인의 다른 키로 탭하는 키 교대 배치. 뒤에 트릴이 없어도 성립하며, 트릴로 연결하는 것은 선택적인 활용 예시다. 피스 `PP-004`의 공식 명칭이다([RFD 0077](../rfd/0077-long-note-end-tap-piece-name.md)). PLv.4.
- **앵커 (Anchor)**: 한 손이 한 레인의 반복적 처리에 묶여 다른 일을 할 수 없는 상태를 만드는 배치. not4k에서는 트릴 노트를 일정하게 반복 배치하는 것이 한 가지 예시다. 트릴 자체의 반복성이나 낮은 난이도를 전제하지 않는다. PLv.7.
- **비트 복합 트릴 (Bit Complex Trill)**: 하나의 `trillZone`에 서로 다른 비트 분할이 복합 등장하는 배치. BPM 변화와 별개이며, BPM이 일정해야 한다는 조건은 없다. BPM 변화에 대응하는 부담과 비트 분할의 복합 부담을 구분한다([RFD 0071](../rfd/0071-subdivision-changes-and-bpm-changes.md)). 선행 학습은 트릴 키 교대와 리듬 변화 대응이며, 앵커는 필수 선행 조건이 아니다([RFD 0070](../rfd/0070-mixed-subdivision-trill-prerequisites.md)). PLv.10.
- **수평 이동 (Crossover)**: 수평 이동 입력방식이 요구되는 배치. `L1L2 → L3L4 → L2L3` 등 2/2 분할 경계를 넘는 패턴에서 파지를 유도한다. 왼손이 3번, 오른손이 2번 레인을 담당하는 것은 대표 예시이며, 내측 2·3번으로 제한하지 않는다. 대상 레인과 실제 이동 부담은 키 바인딩과 손배치에 따라 판단한다([RFD 0066](../rfd/0066-horizontal-movement-lanes-as-examples.md)). 양손의 물리적 교차는 요구하지 않는다. PLv.11.
- **가변 분할 (Variable Split)**: 2/2 이외의 레인 분할(1/3, 3/1 등)을 사용하는 배치. 처음부터 해당 손배치를 잡고 유지하는 경우도 포함하며, 수평 이동은 필수 조건이 아니다. 분담을 바꾸는 과정에서 수평 이동을 조합할 수 있다([RFD 0069](../rfd/0069-variable-split-without-hand-movement.md)). 1/3이 2/2보다 항상 부담이 적은 것은 아니며, 유리한 분담은 패턴과 키 바인딩, 앞뒤 손배치에 따라 달라진다. PLv.11.

## 차트 설계

### 곡 메타데이터

곡 전체를 설명하는 정보다. 제목·아티스트·자켓은 곡이 소유하며, 같은 곡에 속한 모든 차트가 공통으로 사용한다. 차트별로 다른 값을 따로 확정하지 않는다. 이 표시 정보만 수정하면 기존 플레이 기록·최고기록·달성 여부·랭킹을 유지하며, 기록용 차트 버전을 분리하지 않는다([RFD 0096](../rfd/0096-song-shared-display-metadata-and-records.md)).

현재 차트 문서에도 `title`·`artist`·`imageFile`이 들어 있지만, 저장된 사본·참조와 정보의 논리적 소유자를 구별한다. 편집·참조 이행의 세부는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### 곡 저장

곡의 표시 정보(제목·아티스트·자켓 등)와 공통 타이밍(BPM·박자표·음원 정렬 오프셋 등)의 변경을 함께 확정하는 저장 작업이다. 노트·차트별 이벤트·난이도 등 개별 정보는 차트 저장으로 확정하며, 두 저장은 상대 범위의 미저장 변경을 저장하지 않는다. 공통 타이밍이 미저장 상태이면 곡 저장을 먼저 완료해야 Save Chart·Save As를 사용할 수 있다([RFD 0098](../rfd/0098-song-info-drawer-and-save-scope.md)). UI·저장 구조의 런타임 반영은 후속 작업이다.

곡 정보 변경과 차트 편집의 Undo·Redo는 저장 범위와 별개로 하나의 시간순 이력을 사용한다. 가장 최근 작업부터 되돌리며 정지 상태에서만 실행할 수 있다. 곡 정보 변경 취소도 이력 한 작업이며 Undo·Redo로 복원·재적용할 수 있다. 변경 취소를 Undo하면 복원된 곡 정보를 드로어를 다시 열어 보여준다.

### 차트 메타데이터

난이도명·Lv. 등 개별 차트를 설명하는 정보다. 제목·아티스트·자켓은 [곡 메타데이터](#곡-메타데이터), BPM·박자표·음원 정렬 오프셋은 [곡 타이밍](#곡-타이밍)의 곡 단위 소유 규칙을 따른다. 현재 `ChartMeta`가 이 값들을 함께 담는 저장 표현과 소유 규칙을 구별한다.

### 차트 (Chart)

한 곡에 대한 노트 배치 데이터 전체. 곡 하나에 난이도별로 복수의 차트가 존재할 수 있다. "이 곡의 Lv.8 차트"처럼 쓴다. "채보"는 리듬게임 커뮤니티에서 통용되는 동의어이다.

### 곡 타이밍

한 곡의 박·마디와 실제 음원 시간의 관계를 정하는 초기 BPM·BPM 변경 목록·박자표·변박 정보·음원 정렬용 오프셋이다. 같은 곡에 속한 모든 차트가 공통으로 사용하며, 노트 배치와 난이도는 차트별로 관리한다. 음원 정렬용 오프셋은 플레이에 쓰는 음원 시작점에서 0박까지의 시간 차이이며, `gameplayRange`가 있으면 그 시작점을 기준으로 해석한다. 기기별 입력·시각 오프셋과 구별한다([RFD 0095](../rfd/0095-song-shared-bpm-and-audio-offset.md)).

에디터에서 오프셋·BPM·박자표 값은 정지 상태에서만 수정할 수 있다. 재생 중 수정 시도는 값과 재생 상태를 바꾸지 않으며, 드로어를 열어 둔 채 재생·일시정지는 사용할 수 있다. 타이밍 값을 수정하기 직전 커서의 박 좌표를 유지한다. 수정 전 타이밍에서 현재 커서의 박을 구하고, 수정 후 같은 박에 해당하는 새 음원 시각으로 커서를 갱신한다. 다시 재생하면 그 위치부터 시작한다. 일시정지 후 사용자가 seek했다면 seek한 뒤 수정 직전의 커서 박을 기준으로 한다. 정지 순간의 박을 계속 고정하거나 수정 전 음원 시각을 그대로 유지하는 규칙은 아니다. 이 커서 기준 전환은 후속 구현이다([RFD 0099](../rfd/0099-editor-playback-editing-boundary.md)).

공통 타이밍을 수정하여 실제 입력 시각이 달라지면 영향을 받는 차트의 기록과 랭킹을 새 버전으로 분리한다. 이전 기록은 보관하고 새 버전에 승계하지 않는다.

기존 차트의 타이밍이 서로 다른 곡을 곡 공통 구조로 이행할 때는 관리자가 기준 차트 하나를 골라 그 타이밍을 곡 공통값으로 적용한다. 노트·차트별 이벤트의 기존 박 좌표는 유지하고, 실제 입력 시각은 새 공통 타이밍에 따라 계산한다.

현재 구현은 각 차트의 `events`에 `BpmChangeEvent`를, `meta.offsetMs` 등에 음원 정렬 오프셋을 저장한다. 곡 단위 공유는 채택 규칙이며 아직 구현하지 않았다. 저장·이행의 세부는 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### `ChartDocument`

구형 항목과 명시적 점수 노트·바디를 함께 보존하는 저장·편집 문서 타입이다. `notes`는 `DocumentNoteEntity[]`이며 각 항목의 `type`으로 구형/신형 의미를 구별한다. 파일 버전 하나로 모든 항목의 의미를 바꾸지 않는다. 메타데이터·이벤트·구간과 메인/보조 자료를 유지하며 의미 위반 위치도 수리·비교를 위해 보존한다.

기존 `Chart`·`NoteEntity`는 아직 전환하지 않은 구형 소비자의 입력 타입으로 유지한다. 문서 입출력은 `ChartDocument`를 받아 구형·신형·혼합을 왕복하고, 구형 전용 소비자에 전달할 때는 지원 여부를 검사한다. 구형 배열에 새 항목을 캐스트해 판정을 실행하는 호환은 허용하지 않는다. 저장 버전·필드와 API는 [차트 문서 포맷](../spec/chart-format.md)을 따른다. 구형 수리 지원·혼합 저장과 새 재생 제한은 [과도기 계약](#구형-차트와-과도기)을 따른다.


### `ChartTiming`

차트 하나에서 파생되는 시간 뷰. 노트 시작/끝 ms, `trillZone` 시작 ms, 마디 시작 ms, 판정 수 집계를 소유하는 deep module로, beat→ms 파생은 콜사이트에 인라인하지 않고 항상 이 뷰를 통해 읽는다. (_Avoid_: 노트 타임맵, 시간 맵)

### 구형 차트와 과도기

새 계약으로 사람이 차트를 수리하는 동안 구형 읽기·표시·선택·속성·편집·Undo 의미를 보존하는 기간이다. **채택 계약·일반 기본 경로 구현·검증**이며 근거는 [RFD 0037 §8](../rfd/0037-explicit-score-notes-and-body.md#8-구형-차트와-과도기)다.

- 미수정 구형 항목은 계속 구형 의미로 읽고, 사람이 명시적으로 새 구조로 바꾸거나 에디터에서 승인한 [1차 기계 변환](#convertlegacychart)으로 옮긴 항목만 새 의미를 갖는다. 문서 버전 하나로 모든 항목을 새 의미로 간주하지 않는다. 파일 버전이나 불러오기만으로 노트 배치를 조용히 변환·일괄 수정하거나 `holdOnly`를 릴리즈/틱 노트로 바꾸지 않는다. 구형 노트가 있는 차트를 에디터에서 열 때 모달로 물어 사용자가 승인하면 1차 기계 변환을 하고, 거절하면 구형·혼합 상태로 열며 새로 열 때마다 다시 묻는다([RFD 0037 §8-1](../rfd/0037-explicit-score-notes-and-body.md#8-1-구형-차트-1차-기계-변환)).
- 일부만 수리한 구형·신형 혼합 차트도 저장·재불러와 작업을 이어간다. 양쪽 의미·메타데이터·main/aux 자료와 dirty 비교·Undo를 손실 없이 보존한다. 실제 의미 위반의 저장 제한과 구형 항목 존재 자체를 구별한다.
- 구형 의미가 남은 게임 차트는 새 compiler/인게임 재생을 차단한다. 읽기·수리·혼합 저장 가능성과 새 의미 재생 가능성은 별개다. 수정용 불러오기를 새 의미 위반 때문에 막거나 사람에게 JSON 선수정을 요구하지 않는다.
- #347 머지 뒤 일반 곡 선택은 명시 판정만 실행하므로 구형 게임 노트가 남은 차트는 사람이 새 계약으로 다시 제작하기 전까지 곡 선택에서 플레이할 수 없다. 미출시라 사용자가 이 공백을 감수했다(2026-10-26). 운영 차트 현황은 [PRD §12](../prd.md#12-미정-사항)를 따른다.
- 구형이라는 이유만으로 별도 배지·라벨·강조·빗금을 추가하지 않는다. 구형 노트 자체의 표시·편집과 실제 배치 위반의 진단·빗금은 유지한다.
- 수리 범위는 저장소에 올라와 관리되는 차트이며 완료 후 **사용자가 종료 시점을 알릴 때** 구형 스펙 제거를 진행한다. 과도기 종료 뒤에는 저장소 밖의 구형 차트까지 에디터 지원을 보장하지 않는다. 구형 런타임 제거와 구형 읽기·수리 지원은 별도로 판단하며 기존 실행·결정 기록은 보존한다.

### `convertLegacyChart`

구형 차트 1차 기계 변환. 구형 Point·롱노트를 탭 노트·바디·릴리즈·틱 노트로 옮기는 순수 함수이며, 구형 노트가 있는 차트를 에디터에서 열 때 사용자가 모달에서 승인한 경우에만 실행한다. **사용자 결정(2026-10-27～2026-10-28)·변환 함수 구현(PR #367)·에디터 모달·변환 검토 목록 구현(2026-10-28)**이며 근거는 [RFD 0037 §8-1](../rfd/0037-explicit-score-notes-and-body.md#8-1-구형-차트-1차-기계-변환)이다. (_Avoid_: 자동 변환, 일괄 수리)

- 같은 레인에서 이어진 구형 롱노트 전체(사슬)를 하나의 롱노트로 본다. 구형 Point는 같은 kind·Grace의 탭 노트, 구형 롱노트는 같은 hold 수의 바디가 된다.
- 사슬 끝이 `holdOnly`면 릴리즈 없는 바디이고, 그 밖의 사슬 끝에는 hold 수만큼의 일반 릴리즈를 둔다. head가 있는 같은 hold 수 연결에는 탭 노트만 남긴다.
- head 없이 앞 끝의 `holdOnly`로 표시한 같은 hold 수 연결은 두 바디를 하나로 합치고 옛 경계에 틱 노트를 둔다. 트릴 바디끼리면 틱 노트 없이 합치고, 트릴 바디와 일반 바디 사이면 합치지 않으며 둘 다 변환 검토 목록에 싣는다(트릴 바디 위 틱 노트는 금지).
- 길이 0 일반 롱노트는 단독 릴리즈, 길이 0 `holdOnly`는 길이 0 바디 + 틱 노트다.
- 증가·감소 연결(1→2·2→1)은 두 바디만 옮기고 경계를 비운다. `trillZone` 안(양 끝 포함)의 끝과 탭 노트가 놓인 `o-o` 끝에는 기존 규칙대로 릴리즈를 두지 않는다.
- 트릴 바디의 사슬 끝에는 메인·보조 레인 모두 릴리즈를 두지 않는다. 보조 레인의 길이 0 `trillLong`은 일반·`holdOnly` 모두 길이 0 트릴 바디만 두고 릴리즈·틱 노트를 두지 않는다(사용자 결정, 2026-10-28). 그 밖의 보조 레인 노트도 메인과 같은 규칙이다.
- 옮기지 못한 구형 점수 항목의 위치는 보고로 돌려주며 변환 검토 목록의 근거가 된다. 항목마다 레인(보조는 4 + 보조 레인 번호인 통합 레인)·박·종류와 그 위치에서 옮기지 않은 구형 점수 항목 수를 담는다. 사슬 끝 `holdOnly`가 사용자 규칙으로 잃는 항목은 위치를 싣지 않고 개수(`terminalHoldOnlyItemsDropped`)로만 센다.
- 종류는 `holdCountChangeConnection`(증가·감소 연결), `releaseOmittedTrillBodyEnd`(트릴 바디의 사슬 끝)·`releaseOmittedInTrillZone`(`trillZone` 안의 일반 바디 끝), `releaseOmittedTapAtEnd`(`o-o` 끝), `holdOnlyConnectionNotTickable`(트릴 바디가 낀 `holdOnly` 연결), `auxZeroLengthTrillBody`(보조 레인 길이 0 `trillLong`), `sameHoldCountConnectionWithoutHeadOrHoldOnly`(구형 NJ-C02 위반), `explicitNoteAtLegacyPosition`(구형 롱노트의 시작·끝이나 길이 0 위치에 이미 있는 명시 노트), `violationBeforeConversion`(변환 전 입력에서 구형 노트가 연루된 위반과 그 rule)이다.
- 기존 명시 노트는 바꾸지 않고, 명시 노트가 놓인 구형 롱노트의 시작·끝에는 릴리즈·틱 노트를 더하거나 바디를 합치지 않으며, 그 위치의 길이 0 구형 롱노트는 아무 노트도 만들지 않는다.
- 구형에서도 위반이던 배치는 고치지 않고 그대로 옮기지만 명시 검증이 그 위반을 늘 다시 보고하지는 않는다. 구형 바디 안의 Point는 합법인 바디 중간 탭 노트가 되는 등 뜻이 바뀔 수 있으므로 변환 전 입력의 위반을 보고에 싣는다. 끝이 시작보다 앞선 구형 롱노트는 구형 노트 그대로 남긴다.
- 구형 노트가 없으면 같은 차트를 돌려준다. 파일 버전이나 불러오기만으로 실행하지 않는다.
- **변환 검토 목록**은 승인한 변환 뒤 에디터가 세션 동안 보여 주는 보고 항목 목록이다. 행마다 레인·마디 박·종류 설명을 보이고, 누르면 그 위치로 이동해 같은 레인·박의 노트를 선택하며, 텍스트로 복사할 수 있다. 화면과 조작은 [차트 편집기 스펙](../spec/chart-editor.md#구형-차트-변환-모달과-변환-검토-목록)을 따른다.

## 난이도 체계

### 차트 레벨 (Lv.)

차트 하나에 부여되는 난이도 수치. 평가의 기준은 클리어 난이도와 특정 랭크 달성 난이도이며, 처음 보는 패턴의 독해 부담과 동작 계획·물리 부하를 함께 고려한다. 연주 방법을 파악한 뒤의 수행 난도만으로 평가하지 않는다([RFD 0047](../rfd/0047-chart-levels-include-reading-load.md)).

같은 패턴도 비행 규칙과 초반·후반의 배치 위치에 따라 체감과 결과가 달라질 수 있다. 고난도 차트에서는 앞선 연주의 누적 피로로 후반 동작 수행 여력이 줄어 같은 패턴의 실행 부담이 커질 수 있으므로, 클리어 가능성에 미치는 영향을 함께 고려한다. 모든 차트에서 후반을 일률적으로 더 어렵게 평가하거나 정량 피로 수치를 정하는 규칙은 아니다. 차트 제작에서는 클리어 난이도와 특정 랭크 달성 난이도가 이질적으로 크게 어긋나는 구성을 지양한다. 이는 현재 채택한 방향이며, 구체적 평가 기준은 [PRD §12](../prd.md#12-미정-사항)에서 미정으로 관리한다([RFD 0048](../rfd/0048-clear-rank-and-chart-position.md)).

한 번 본 뒤 의도된 연주 방법을 파악해 다음 시도가 수월해지는 것은 학습 경험의 목표다. 처음 읽을 때의 어려움도 Lv.에 포함하면서, 시각적 요구는 단순하고 명확하게 제시한다.

### 피스 레벨 (PLv.)

개별 피스가 의미 있는 난이도 요소로 본격 활용되기 시작하는 기준 차트 레벨. 등장 가능한 절대 하한은 아니며, 충분히 느리고 단순한 짧은 체험은 더 낮은 레벨에서도 허용한다. 실제 속도·밀도·지속 길이·다른 입력과의 조합으로 차트 수준에 맞는지 확인한다. 노트 타입 자체의 사용 가능 여부(항상 Lv.1)와는 구별한다([RFD 0046](../rfd/0046-piece-levels-and-early-exposure.md)).

예: 롱노트 끝 탭의 PLv.4는 그 피스를 본격 활용하기 시작하는 기준이다. 느리고 단순한 짧은 체험까지 Lv.4 미만에서 금지하는 뜻은 아니다.

### 난이도명 (Difficulty Name)

한 곡에 배정되는 차트의 이름. 리듬게임에서는 일반적으로 한 곡에 여러 난이도의 차트가 존재하며, 각 차트에 난이도명이 붙는다 (예: IIDX의 NORMAL/HYPER/ANOTHER, DJMAX의 NM/HD/MX).

not4k의 난이도명은 **`Liftoff → Infiltration → Breakthrough`** 순서다. 한 곡 안의 차트를 구분하며 각 단계의 비행 시나리오·연출에 대응한다. 명칭과 배치는 [RFD 0022](../rfd/0022-flight-difficulty-names-and-visuals.md)에서 채택했으며, [RFD 0026](../rfd/0026-game-flight-backgrounds.md)에 따라 곡 선택·로딩 표시와 인게임 배경에 적용한다. 기존 `EASY / NORMAL / HARD`는 저장 식별자를 유지하며 각각 새 이름으로 표시한다. 기존 `EXPERT`는 별도 이름을 유지하고 돌파 배경을 사용한다. 새 차트의 선택지는 세 공식 이름이다. 원격 데이터 일괄 이행은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다. 판정명의 잠정 상태는 이 결정과 별개다.

난이도명은 차트 레벨(Lv.)과는 별개의 개념이다. 난이도명은 같은 곡 내에서 차트를 구분하는 라벨이고, 차트 레벨은 차트의 절대적 난이도 수치이다.

헤드 없이 시작하는 바디 패턴(`.-`, `-=`, `o-=`)은 난이도명에 따른 사용 제한을 두지 않는다. 독해 부담과 속도·밀도·지속 길이·다른 입력과의 조합이 차트 수준에 맞는지 확인하며, 충분히 느리고 단순한 짧은 체험은 낮은 레벨에서도 허용한다. 기존 `HARD` 전용 제한은 폐지한다([RFD 0050](../rfd/0050-headless-body-patterns-by-load.md)). 차트 구조·판정에 필요한 배치 제약은 별도로 적용한다.

### `flightRule` (Flight Rule)

Play에서 **`altitude`** 상태와 클리어/실패를 다루는 비행 규칙. 차트 난이도명 `Liftoff / Infiltration / Breakthrough`에 대응하는 시나리오와 연결된다. `Lv.`·난이도 등급·달성률·랭크를 대체하지 않는다. 현재 명칭과 연출 배치는 [RFD 0022](../rfd/0022-flight-difficulty-names-and-visuals.md)를 따른다.

세 단계의 이름·순서·연출 배치는 확정했으며 이름 표시와 배경 연결을 구현했다. 클리어·실패를 결정하는 비행 규칙은 미구현이며, 세부 판정 규칙은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다.

`flightRule`은 리듬게임에 익숙하지 않은 유저에게 클리어/실패라는 목표 구조와 동기를 제공한다. `Liftoff`의 관대한 역할은 유지한다. 각 단계의 회복·감소·실패 규칙과 실제 선택 UI는 이름·연출 배치만으로 확정하지 않는다.

| `flightRule` | 정의 |
| --------- | ---- |
| **`Liftoff`** | 첫 번째 난이도명·이륙 시나리오. 시선 각도를 유지하며 고도가 변한다. 기존 `altitude` 0 시작·곡 종료 기준 클리어·곡 중 게임 오버 없음의 관대한 역할을 유지한다. Miss 없이 완주하면 클리어 조건을 충족하도록 게이지 상승량을 설정한다([RFD 0093](../rfd/0093-liftoff-no-miss-completion-clears.md)). |
| **`Infiltration`** | 두 번째 난이도명·침투 시나리오. 낮아질수록 시선이 지면을 향해 꺾이고, 지평선이 위로 사라지며 지면이 평면에 가까워진다. |
| **`Breakthrough`** | 세 번째·최상위 난이도명·돌파 시나리오. 낮은 고도에서 전방을 보며 계속 비행한다. 가까운 지면과 빠른 광원 속에서 안정된 자세를 유지하는 숙련 비행이다. |

`Survival`과 `Stealth`는 현재 단계 이름이 아니다. 종전 `Survival`의 Perfect-only 회복·0 도달 실패 규칙은 새 단계에 자동 승계하지 않으며, 과거 `Breakthrough`와 현재 같은 이름의 시나리오를 동일한 세부 규칙으로 취급하지 않는다. 과거 규칙의 근거는 RFD 0002·0005에 보존한다.

### `altitude` (Altitude)

`flightRule`의 상태와 고도 연출을 연결하는 플레이 중 지표. 시각 고도와 위험의 관계는 시나리오에 따라 다르며, `Breakthrough`의 낮은 시각 고도는 정상적인 숙련 비행이다. 모든 단계에 "낮을수록 실패 위험"을 일괄 적용하지 않는다. 구체적인 상태·시각 고도 대응은 [PRD §12](../prd.md#12-미정-사항)에서 추적한다. 달성률이나 랭크와는 다른 개념이다.

### 난이도 등급 (Difficulty Class)

레벨 구간을 묶어 분류한 것. 피스에도 적용된다.

| 등급   | 레벨 구간 | 키 바인딩 전제             |
| ------ | --------- | -------------------------- |
| 입문   | Lv.1～3    | 4키 주로 활용, 드물게 엄지 |
| 초급   | Lv.4～6    | 엄지 비중 상승 (6키)       |
| 중급   | Lv.7～10   | 8키 입문 (약지 추가)       |
| 상급   | Lv.11～13  | 8키 활성화                 |
| 최상급 | Lv.14～15  | 16키 완전 활용             |

> **용어 규칙**: 차트 단위의 난이도는 **Lv.**, 피스 단위의 난이도는 **PLv.**, 구간 분류는 **난이도 등급**으로 통일한다.
> **`flightRule`**은 차트 난이도명에 대응하는 비행 규칙이다. 난이도명의 라벨 역할과 규칙의 동작은 구분하며, `Lv.`·`PLv.`·난이도 등급을 대체하지 않는다.

### 난이도 축 (Difficulty Axis)

레벨을 구성하는 4가지 독립적인 차원. `../spec/difficulty-design.md`에서 정의한다.

1. **노트 밀도** — 초당 입력 수 (BPM × 비트 분할)
2. **트릴 복합도** — 트릴의 길이, 속도, 다른 레인과의 동시 진행 여부
3. **더블·동시치기 복합도** — 더블 노트의 등장 위치와 빈도
4. **레인 내 복합도** — 홀드 중 탭, 릴리즈탭 등

### 인지 부하 (Cognitive Load)

유저가 차트의 요구사항을 파악하고, 이를 수행할 입력 동작을 계획하는 데 드는 정신적 부담. not4k의 설계에서는 다음 두 측면을 구분한다.

- **독해 부담**: 어떤 노트를 언제 누르고, 무엇을 유지하거나 떼어야 하는지 파악하는 부담이다. 노트 구별이 어렵거나 요구가 모호할수록 커진다.
- **동작 계획 부담**: 파악한 요구사항을 어떤 손·손가락·키의 조합과 순서로 수행할지 판단하는 부담이다. 현재 유지 중인 키와 뒤따르는 노트를 고려한 손배치 선택·전환, 키 교대 준비 등을 포함한다.

새로운 게임의 노트와 규칙을 익히는 독해 부담도 실제 난이도의 일부다. 피스의 `cognitive_load`는 독해와 동작 계획을 함께 평가하며, 노트 종류 수만으로 등급을 결정하지 않는다. 카탈로그의 등급은 대표 배치에 대한 참고값이며, 실제 배치와 입력 조건에 따라 다시 평가한다([RFD 0072](../rfd/0072-piece-load-ratings-as-reference.md)). 평가 기준은 [피스 명세](../spec/piece-definition.md#cognitive_load와-physical_load의-기준)를 따른다.

**not4k가 핵심 난이도로 요구하는 것은 동작 계획 부담이다. 입력 요구는 단순하고 명확하게 제시하고, 그 요구를 수행할 방법은 플레이어가 판단하게 한다.** 기본적인 차트 독해는 필요하지만, 가림·구별하기 어려운 표현·불명확한 규칙을 핵심 도전으로 삼지 않는다. 노트 종류·속성·동시 조건의 조합을 해독하는 부담도 낮게 유지하며, 손배치의 깊이는 단순한 요구의 배치와 연결에서 만든다.

동작 계획의 난이도는 최상급을 포함해 **한 번 눈에 익힌 뒤 다시 하면 대응할 수 있는 정도**를 지향한다. 해당 난이도의 기본 규칙과 입력방식에 익숙한 플레이어가 초견에서 놓친 흐름을 파악하고, 다음 시도에는 화면과 현재 손 상태를 바탕으로 다음 동작을 알고 손배치를 시도할 수 있는 수준이다. 실제 속도·정확도를 맞추고 성공하는 데는 반복 연습이 필요할 수 있다. 짧은 사전 경험과 수행 숙련도를 높이는 학습은 포함하되, 긴 손순서를 따로 외우는 과도한 암기를 핵심 도전으로 삼지 않는다. 적용 기준은 [난이도 설계](../spec/difficulty-design.md#5-단순한-요구에서-실시간-동작-판단을-만든다)를 따른다.

모든 패턴 학습에서 속도·밀도·지속 길이·다른 입력과의 조합을 조절해 부담이 낮은 형태부터 점진적으로 익힐 기회를 제공한다. 고급 패턴도 해당 수준에서 부담을 낮춘 형태부터 더 높은 부담의 형태까지 단계적으로 경험하게 하며, 입문이나 낮은 레벨에 한정하지 않는다. 고급 패턴을 입문 차트에 반드시 넣거나 모든 차트에 모든 패턴·단계를 포함하는 요구는 아니다([RFD 0051 후속 명확화](../rfd/0051-beginner-trill-load-and-judgment.md#후속-명확화-고급-패턴을-포함한-모든-패턴의-점진적-학습-2026-10-31)).

이 구분은 게임의 설계 목적을 설명하며 인지 부하 전체를 두 종류로 한정하는 학술적 분류는 아니다. 실제 동작의 속도·힘·지구력에 따른 물리 부하와 타이밍 정밀도는 별도로 구별한다. 채택 근거는 [RFD 0101](../rfd/0101-cognitive-load-and-action-planning.md)을 따른다.

### 물리 부하 (Physical Load)

요구된 동작을 실제로 수행하는 데 드는 신체적 부담. 입력 속도, 손가락의 독립적인 움직임, 손 이동과 자세 전환, 힘과 지구력 등을 포함한다. 순간적인 수행 어려움과 누적 피로를 모두 다루며, 연주 방법을 알아도 동작 자체가 익숙하지 않거나 요구 속도로 수행하기 어려운 경우를 포함한다([RFD 0074](../rfd/0074-physical-load-includes-execution-difficulty.md)).

어느 손·손가락·키를 사용할지 판단하는 동작 계획 부담, 입력 시점을 정밀하게 맞추는 타이밍 정밀도와 구별한다. 실제 연주에서는 이 부담들이 함께 발생할 수 있다.

피스의 `physical_load` 등급은 대표 배치에 대한 참고값이다. 실제 입력 속도·밀도·지속 길이·키 바인딩·양손의 배치와 앞뒤 흐름에 따라 평가가 달라진다. `cognitive_load`와 `physical_load`를 피스 종류의 고정 등급이나 차트 Lv.의 자동 산정값으로 사용하지 않는다([RFD 0072](../rfd/0072-piece-load-ratings-as-reference.md)).

## 판정 및 스코어링

### 올퍼펙트 (All Perfect)

올퍼펙트는 곡을 끝까지 연주하고 모든 점수 노트를 Perfect로 처리하며, 무점수 바디 실패를 포함한 Miss가 한 번도 없는 경우에만 인정한다. 점수 노트를 모두 Perfect로 처리했어도 바디에서 Miss가 발생하면 인정하지 않는다. 달성 시 전용 종료 연출로 일반 클리어 연출을 대체한다([RFD 0090](../rfd/0090-song-end-presentation-before-results.md)). 최종 표시 명칭은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다. 일반 플레이에는 점수 노트가 최소 1개 필요하다([RFD 0091](../rfd/0091-normal-play-requires-score-note.md)).

### 풀콤보 (Full Combo)

풀콤보는 곡을 끝까지 연주하고, 무점수 유지 실패를 포함해 Miss가 한 번도 없는 경우에만 인정한다. 곡 도중 실패로 종료된 플레이는 종료 시점까지 Miss가 없더라도 풀콤보로 인정하지 않는다. `goodTrill`은 Good처럼 취급하므로 풀콤보를 끊지 않는다. 달성률 100%와는 별개이며, 클리어 여부와 독립적으로 기록한다([RFD 0090](../rfd/0090-song-end-presentation-before-results.md)).

### 판정 윈도우 (Judgment Window)

노트 기준 시점 주변에서 입력을 허용하는 범위. 등급은 Perfect / Great / Good / Miss이다. 채택된 새 계약에서 일반 릴리즈의 등급별 창은 누름과 같고 앞뒤 대칭이다. Grace 릴리즈의 최대 창과 릴리즈 없는 바디의 이른 종료 폭은 누름 Good 폭을 공유한다. 틱 노트는 자체 창이 없다. 새 계약은 #342에서 구현하고 일반·명시 테스트 재생에서 검증했다. Normal의 Perfect/Great/Good은 ±41/82/120ms, Easy는 ±50/100/150ms이다. head와 실제 release에 타이밍 등급을 적용한다. 과도기 구형 `holdOnly`는 Perfect/Miss 상태 판정이다.

같은 판정 설정 안에서 차트 레벨이 낮거나 초급 트릴이라는 이유로 윈도우를 자동 완화하지 않는다. 초급 트릴의 부담은 속도·밀도·지속 길이·다른 입력과의 조합으로 조절한다. Normal/Easy의 설정별 차이와 Grace의 별도 타이밍 완화는 유지한다([RFD 0051](../rfd/0051-beginner-trill-load-and-judgment.md)).

### 오디오 오프셋 (Audio Offset, 제거됨)

[RFD 0031](../rfd/0031-audio-first-timing-model.md)에 따라 설정 `Audio Offset`·코드 `audioOffsetMs`를 제거했다. 출력 장치 지연은 재생 전 로딩 중 running `AudioContext`에서 안정된 `baseLatency + outputLatency`를 읽어 고정한 L₀로 자동 보정한다. `outputLatency` 미지원이면 그 몫만 0이다. L₀는 일시정지·재개에 유지하고 새 `AudioEngine`을 만드는 Retry·다음 곡에서 다시 읽는다. 곡 중 출력 장치 변경은 반영하지 않는다.

### 입력 오프셋 (Input Offset)

입력 장치 지연과 개인 체감 타이밍을 보정하는 설정이다(설정 `Input Offset`, 코드 `inputOffsetMs`, 실제 시간 ms, 기본 0). 숫자 입력 확정과 저장 설정 병합 때 −1000～+1000ms로 제한하며, 유한한 숫자가 아닌 저장값은 0ms로 둔다. 배속 r을 곱해 입력 시간에만 더한다(`입력 = J − handlerDelay·r + inputOffsetMs·r`, `J = P − L₀·r`). 판정 시간·시각 시간에는 닿지 않는다. 늦게 눌러 SLOW가 많으면 음수, FAST가 많으면 양수다([PR #242](https://github.com/nanana3679/not4k/pull/242)의 부호 유지).

입력·시각 오프셋은 해당 기기의 브라우저에 로컬 설정으로 저장하고 계정 설정 동기화에서 제외한다. 로그인 여부와 관계없이 해당 기기의 값을 유지한다([RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

현재는 설정 숫자 입력으로 조절한다. 입력 캘리브레이션은 [RFD 0031](../rfd/0031-audio-first-timing-model.md) PR 2에서 게임과 같은 시간 경로의 비프·탭 비교로 구현한다. 옛 설정 `judgmentOffsetMs`·`audioOffsetMs`·`offsetMs`는 읽을 때 버리고 이전하지 않는다.
_Avoid_: 오디오 오프셋, 판정 오프셋, 이름 없는 "오프셋"

### 시각 오프셋 (Visual Offset)

화면 표시 지연을 보정하는 설정이다(설정 `Visual Offset`, 코드 `visualOffsetMs`, 실제 시간 ms, 기본 0). 숫자 입력 확정과 저장 설정 병합 때 −1000～+1000ms로 제한하며, 유한한 숫자가 아닌 저장값은 0ms로 둔다. 시각 시간 `V = J + visualOffsetMs·r`로 노트·마디선·구간을 그리며 판정과 입력 시간에는 닿지 않는다. 화면이 소리보다 늦게 보이면 양수로 노트를 앞당겨 그린다. 브라우저의 출력 지연 보고가 정확하면 화면 표시 지연과 같다.

입력·시각 오프셋은 해당 기기의 브라우저에 로컬 설정으로 저장하고 계정 설정 동기화에서 제외한다. 로그인 여부와 관계없이 해당 기기의 값을 유지한다([RFD 0102](../rfd/0102-device-local-input-and-visual-offsets.md)).

현재는 설정 숫자 입력으로 조절한다. 비프와 함께 떨어지는 노트를 보고 맞추는 시각 캘리브레이션은 [RFD 0031](../rfd/0031-audio-first-timing-model.md) PR 3에서 구현한다. 입력 오프셋과 달리 장치가 늦을 때 양수다. 브라우저 지연 보고의 고정 오차는 두 오프셋이 함께 흡수할 수 있다.
_Avoid_: 화면 오프셋, 디스플레이 딜레이, 이름 없는 "오프셋"

### 바디 판정과 실패 종속

[RFD 0037 §3～4](../rfd/0037-explicit-score-notes-and-body.md#3-바디-시작유지끝과-릴리즈-자격)의 **채택 계약·일반 기본 경로 구현·검증**이다. 바디 몫은 시작·유지·완료·실패를 추적하는 단위로 single 1개·double 2개이며 고정 물리 키 소유권이 아니다.

- 시작 창 전부터 누른 키는 창이 열리는 순간에 조기 시작시키지 않는다. 차트상 시작 시각에 필요한 hold가 있으면 시작한다. 시작 창 안의 유효한 새 down으로 충족한 몫은 그 입력 시각에 시작하며 down은 소비하지 않는다. head 없는 독립 single·double과 1→2의 추가 몫에도 적용한다.
- 앞 바디를 정상 유지한 키가 계속 눌려 있으면 뒤 바디는 자기 차트상 시작 시각에 시작한다. 짧은 뒤 바디의 시작 탭 노트 미처리를 이유로 건강한 승계를 미시작으로 바꾸지 않는다. 건강한 승계가 없는 첫 탭 노트 실패와 탭 노트가 맡는 몫의 종속은 구별한다. 탭 노트 담당 몫의 유지 실패 대기와 유효한 실제 탭 노트 down 기준은 RFD 0032 §4-3·§5-2～5-4의 충돌하지 않는 계약을 보존한다. 이미 확정한 실패나 정상 완료를 뒤 탭 노트 입력으로 되돌리지 않는다.
- double 탭 노트로 시작하는 single 바디는 두 탭 노트 몫 중 먼저 성공한 down의 시각에 시작한다. 탭 노트의 모든 몫이 Miss일 때만 바디가 탭 노트 Miss로 실패하고, 한 몫만 Miss면 그 탭 노트 항목만 Miss다(사용자 결정, 2026-10-26).
- 같은 시각 입력을 반영한 뒤 hold 부족을 판단하며 유지 유예와 head 없는 시작 직후의 기존 재충전을 보존한다. 탭 노트가 있는 double의 비담당 몫에도 시작 창 끝까지 재충전을 넓히지는 않는다. 그 몫이 시작한 뒤에는 기존 유지 유예를 적용한다.
- 실제 시작한 바디만 자기 끝의 Good 이른 폭에서 정상 종료할 수 있다. 이른 종료 창(E − Good) 직전에 시작한 hold 부족은 유지 유예가 창 안에서 끝나도 유지 실패이며, 유지 유예가 이른 종료 창을 넓히지 않는다(사용자 결정, 2026-10-26). 미시작 바디를 끝 창의 up만으로 완료하지 않으며 끝 창으로 시작 범위를 늘리지 않는다. 릴리즈 없는 바디의 이른 종료는 up을 소비하지 않고 같은 up이 적격인 명시 릴리즈 하나를 처리할 수도 있다.
- 끝까지 정상 유지한 바디는 차트상 끝에 무점수로 완료한다. 남은 릴리즈는 자기 늦은 창까지 기다리며 누락하면 릴리즈만 Miss다. 완료한 바디에 유지 실패를 새로 추가하지 않는다. 끝 뒤에도 시작 창 안인 single의 유효한 첫 down은 실제 시작 → 즉시 유지 완료 → 명시 릴리즈 대기로 처리한다.
- 릴리즈 없는 짧은 double도 서로 다른 두 키로 처리한다. 두 키의 입력 시각은 달라도 되지만 시작·끝 창이 겹친다는 이유로 같은 키를 두 번 눌러 두 유지 몫을 완료하지 못한다.
- 같은 레인에서 hold 수가 같은 두 바디가 맞닿을 때 뒤 시작 탭 노트도 앞 끝 릴리즈도 없으면 [의미 위반](#의미-위반과-수리)이며, 이 배치에는 실패 공유 같은 판정 규칙을 두지 않는다(사용자 결정, 2026-10-27). 트릴 바디와 일반 바디가 맞닿는 경계는 모양이 달라 구별되므로 방향과 관계없이 이 금지에서 빠지며, 금지는 트릴 여부가 같은 경계에만 적용한다(사용자 결정, 2026-10-27, 일반 바디 → 트릴 바디는 2026-10-28 정정). 트릴 바디 뒤에 같은 hold 수의 일반 바디가 탭 노트 없이 맞닿으면 판정이 이어지지 않는다. 앞 실패를 공유하지 않고 뒤 바디는 자기 조건으로 시작한다(사용자 결정, 2026-10-27). 기존 규칙의 적용(사용자 결정이 아님): 메인 레인에서는 기존 `trillExclusive`가 트릴 바디 → 일반 바디 접점을 막고 `trillLongInvalid`가 트릴 바디에 시작 트릴 탭 노트를 요구하며 보조 레인은 게임 판정에서 제외되므로, 이 제외는 보조 레인의 배치 허용에만 영향을 주고 실제로 판정되는 차트에는 나타나지 않는다.
- 탭 노트 없는 1→2는 앞 탈락과 별개로 뒤 double 두 몫 모두 자기 조건에 따른 새 시작을 허용한다. 탭 노트 없는 1→1의 릴리즈 경계와 탭 노트 없는 2→2의 릴리즈 하나인 경계도 뒤 바디 전체가 자기 조건으로 새로 시작할 수 있다. 앞 릴리즈 성공·새 down·정확한 동시성을 추가 조건으로 요구하지 않는다.
- single 탭 노트가 있는 2→2에서도 뒤 두 몫 모두 자기 조건으로 새로 시작한다. 탭 노트를 놓쳐도 비담당 몫은 미리 누른 키로 차트상 시작 시각에 시작할 수 있으며 탭 노트 Miss 확정을 기다리지 않는다. 탭 노트 몫의 실패를 정상 시작한 다른 몫으로 확대하거나 같은 원인의 바디 Miss를 더하지 않는다.
- 탭 노트 없는 2→1은 건강한 몫을 뒤 single로 이어준다. 두 몫 모두 탈락했어도 뒤 single은 함께 탈락하지 않고 자기 시작 조건(시작 창 안의 새 down 또는 차트상 시작 시각의 hold)으로 새로 시작할 수 있으며, 시작하지 못하면 자기 시작 기한에 실패한다(사용자 결정, 2026-10-27). 한 몫 실패 시 감소 지점의 명시 싱글 릴리즈는 끝나는 실패 몫에 귀속한다. 감소 지점의 더블 릴리즈도 허용하며, 이는 두 키를 모두 떼고 뒤 single을 새 키로 잡는 연주를 요구한다(사용자 결정, 2026-10-26).
- double 전체 끝에 릴리즈 두 몫이면 한 바디 몫의 유지 실패는 릴리즈 하나만 소멸시킨다. 전체 끝에 릴리즈 하나면 건강한 몫 하나로 기회를 보존하고 두 몫 모두 실패하면 닫는다. 2→1 감소의 단일 릴리즈와 귀속이 다르다.
- 위 2→1 결정과 같은 수 연결 금지에서 도출한 정리(사용자 결정이 아님): 앞 바디의 확정 실패를 뒤 바디의 실패로 옮기지 않으며 그 실패는 앞 바디와 종속 항목에만 남는다. 다만 탭 노트가 맡는 뒤 몫이 탭 노트 처리 없이 hold만으로 시작하는 것은 앞 바디를 건강하게 이어받을 때뿐이다. 앞 바디가 실패하면 그 몫은 자기 탭 노트 판정을 따르고 탭 노트를 놓치면 자기 탭 노트 Miss로 실패한다([RFD 0037 §3-1](../rfd/0037-explicit-score-notes-and-body.md#3-1-시작-시각과-유지)·[§4](../rfd/0037-explicit-score-notes-and-body.md#4-경계실패-종속)).
- 확정 실패와 소멸한 기회는 뒤 입력으로 복구하지 않는다. 종속 릴리즈·틱 노트 항목은 0점·원래 가중치로 정확히 한 번 정산하고 추가 Miss·콤보 단절·고도 손실을 만들지 않는다. 이미 확정한 성공도 뒤 실패로 되돌리지 않는다.

### 롱노트 판정 모델

**새 계약:** [바디 판정과 실패 종속](#바디-판정과-실패-종속)을 따른다. 아래 등록 키·시작 down 소비·연결 보정은 구형 엔진과 과거 이행 논의의 설명이며 새 구현 기준이 아니다.

#### 과도기 구형 계약·논의 기록

바디의 활성화·유지·끝 처리와 별개 head 판정으로 구성한다. 아래 등록 키·시작 준비·연결 보정(후속 모델의 [연결 release](#연결-release))의 설명은 [RFD 0020](../rfd/0020-note-judgment-units-and-inheritance.md)을 구현한 기존 엔진 기준이다. **후속 설계는 패턴별로 release와 Grace의 역할을 확인하며, 현재 합의 범위는 [release 판정](#release-판정)을 우선한다(엔진 미이행).** 특수 사례는 [판정 사례 명세](../spec/note-judgment-cases.md), 새 모델의 잔여 대조와 이행 상태는 [PRD](../prd.md#12-미정-사항)에서 확인한다.

- **unit**: 바디에서 활성화·유지·실패를 추적하는 한 몫이다. single은 1개, double은 2개이다. 고정 물리 owner나 별도 겹친 바디를 뜻하지 않는다.
- **등록된 유지 키**: 실제 head·시작 입력·정당한 승계로 해당 바디를 유지할 자격을 얻은 held 키이다. 레인의 임의 raw held와 구분한다.
- **시작 준비**: 실제 시작 입력 또는 정당한 승계로 충족한 시작의 몫이다. 이미 준비된 unit은 새 시작 down을 소비하지 않는다. held 수만 충분한 미처리 시작과는 다르다.
- **release 권한**: 등록된 키의 한 번의 누름에 부여하며, 그 누름을 끝내는 up을 준비된 실제 release에 사용할 자격이다. 같은 연결 구간에서 공유할 수 있지만 한 up으로 실제 release 하나만 소비한다. 유효한 새 head·미처리 시작을 처리하면 같은 물리 키도 새 누름의 권한을 얻으며, 같은 double 끝의 이전 사용 이력으로 이를 차단하지 않는다. 임의의 재누름에는 새 권한이 없다.
- **활성화**: 양수 길이는 자기 head·시작 입력 또는 정당한 승계로 시작한다. head 없는 시작은 down을 소비하되 시작 점수는 없다. 기한은 S+Good이며 길이가 짧거나 E를 지났어도 유효한 첫 활성화를 허용한다. S보다 늦은 첫 활성화도 정당한 시작이므로 맞닿은 뒤 바디의 승계나 연결 보정을 막지 않는다([NJ-H08](../spec/note-judgment-cases.md#nj-h08)).
- **head와 unit**: double head + double 바디는 unit별로 시작한다. single head + double 바디는 한 unit이 head를 담당하고 나머지는 별도 시작 또는 승계를 받는다. double head + single 바디는 첫 성공 head로 활성화하며 두 성공 키 모두 등록한다. 건강하게 승계된 바디는 자신의 head Miss와 독립적이다.
- **유지 실패**: 같은 timestamp의 입력을 모두 반영한 뒤 유효 유지 키가 부족하면 해당 활성 unit이 실패한다. 연결 교대 후보로 보류한 up은 용도가 정해질 때까지 부족으로 확정하지 않으며, 교대가 끝내 성립하지 않으면 유지 실패가 아니라 교대 실패로 정리한다([`consume`](#consume-구-표기-흡수소비)의 연결 keyup 보정·교대 실패). 실제 입력의 인과관계를 보존한다. 실패한 같은 바디는 되살리지 않고 끝점에서 중복 실패시키지 않는다.
- **동시 입력의 결과 일관성**: 같은 차트의 같은 키·시각 입력은 서로 다른 키의 동시 up을 내부에서 배정한 순서가 달라도 후속 판정 결과가 같아야 한다. 유지 부족 확인뿐 아니라 이후 release 자격과 성공·Miss에도 적용한다. 유효한 새 입력의 권한 갱신은 [RFD 0020 §2.8](../rfd/0020-note-judgment-units-and-inheritance.md#28-유효한-새-입력에-따른-release-권한-갱신--후속-채택), 전체 검산 상태는 [PRD §12](../prd.md#12-미정-사항)를 따른다.
- **보류 판정과 콤보**: 현재 콤보는 판정 확정 순서로 반영한다. 보류 중인 up은 콤보에 넣지 않고, 확정된 뒤에도 원래 입력 시각으로 소급하지 않는다. 등급과 raw FAST/SLOW는 실제 입력 시각으로 계산한다. 동일 timestamp·phase의 판정 묶음에서는 Miss가 콤보 결과에 우선하며, 입력·기한에 따른 확정 순서를 프레임이나 레인 순회 순서로 바꾸지 않는다. [RFD 0020 §2.9](../rfd/0020-note-judgment-units-and-inheritance.md#29-보류-판정의-콤보는-확정-순서로-반영--후속-채택)를 따른다.
- **콤보 통계 범위**: 최대 콤보수 통계는 제공하지 않는다. 최대값 갱신 방식은 판정 모델의 제품 요구사항에 포함하지 않는다. 현재 콤보와 Full Combo의 채택 규칙은 그대로 적용한다. [RFD 0020 §2.10](../rfd/0020-note-judgment-units-and-inheritance.md#210-최대-콤보-통계-미제공--후속-채택)을 따른다.
- **새 바디와 승계**: head·`holdOnly`·unit 수 변화로 구분되는 다음 바디에는 자기 시작 기회가 있다. 실패한 바디를 건너뛰는 승계는 없다. 부분 실패로 건강한 다른 unit까지 종료하지 않는다.

### 분할 릴리즈 (Split Release)

**채택 계약·일반 기본 경로 구현·검증:** 2→1에서 한 몫이 끝나고 건강한 다른 몫이 뒤 single로 이어져 서로 다른 시각에 끝나는 구조다. 점수·실제 뗌 요구는 각 위치에 명시한 릴리즈 수만 따르며 감소량으로 합성하지 않는다. 세부 실패 귀속은 [바디 판정과 실패 종속](#바디-판정과-실패-종속)을 따른다.

#### 과도기 구형 계약·논의 기록

double에서 두 release를 서로 다른 시점에 수행하는 것. `D=-`에서는 감소 시 한 release, 마지막에 남은 한 release를 판정한다. double head 두 개까지 합치면 점수 판정은 네 개이다. 각 실제 release는 자기 타이밍 등급을 가진다.

### `termination` 판정

**채택 계약·일반 기본 경로 구현·검증:** 뒤 바디로 이어지지 않는 끝의 릴리즈도 [명시된 릴리즈](#릴리즈-노트)가 있을 때만 판정한다. 바디 끝 자체에서 점수 항목이나 뗌 요구를 만들지 않는다. 아래 코드 중심 용어는 구형 구현 설명이다.

#### 과도기 구형 계약·논의 기록

뒤 바디로 이어지지 않고 끝나는 unit의 실제 release 판정이다. Point가 끝에 함께 있어도 그 자체로 바디 승계를 만들지는 않는다. 등록·준비·창 조건을 충족한 up을 가장 이른 실제 release 하나에 사용하며 Perfect/Great/Good/Miss와 raw FAST/SLOW를 판정한다.

### 감소 release

**채택 계약·일반 기본 경로 구현·검증:** 2→1에서 끝나는 몫에 대응하여 명시한 릴리즈다. 생략한 끝에는 뗌·점수를 자동 생성하지 않는다. 일부 실패 시 건강한 몫을 뒤 single로 이어주고 이 싱글 릴리즈는 실패 몫의 종속 0점이 된다. 같은 위치의 탭 노트와 릴리즈 중첩은 새 차트에서 금지한다.

#### 과도기 구형 계약·논의 기록

2→1 경계에서 뒤 바디로 이어지지 않고 끝나는 몫의 끝 release이다. 이어지는 몫은 연결이라 등급 있는 release가 필요 없지만, 끝나는 몫은 일반 끝처럼 실제 release가 필요하다. 등급·판정 창·Miss·`holdOnly` 면제는 일반 끝 release와 같고, 몫은 물리 키에 묶이지 않아 창 안의 첫 적격 up이 처리한다([RFD 0032 §6-2](../rfd/0032-body-held-count.md#6-2-head-없는-21), 2026-10-17). head 없는 일반 2→1(`D=-`)은 한 번의 실제 keyup을 요구한다. 2→1 경계에 head가 있어도 감소 release 하나를 판정한다(엔진 이행 전, 기존 엔진은 감소 release 항목을 남기되 연결 보정(새 모델의 연결 release)을 먼저 배정한다. [RFD 0032 §6-3](../rfd/0032-body-held-count.md#6-3-head가-있는-21과-감소-release), 2026-10-01의 [RFD 0020 §2.13](../rfd/0020-note-judgment-units-and-inheritance.md#213-head가-있는-21-감소의-release--후속-채택) 제거를 대체). 경계 근처의 첫 up이 감소 release를 처리하고, 연결 head 창 안에 up이 하나 더 있으면 그 up이 연결 release다. 연결 release가 될 up이 없어도 Miss가 아니다. 의도된 연주는 A·B를 모두 떼고 새 키로 head를 친 뒤 유지하는 것과, 한 키를 유지하고 다른 키를 떼며 새 키로 head를 쳐서 바로 떼는 것이다. 경계 뒤 single 바디에 키가 둘 남는 입력(새 키를 계속 누르기, 두 키를 쥔 채 새 키로 탭)은 같은 규칙으로 판정하되 의도된 연주가 아니며, 남은 키의 up이 뒤 판정에 주는 영향은 플레이어 책임이다. 경계 뒤에 키를 더 남기면 끝의 up이 연결 release로 쓰여 끝이 Miss가 될 수 있으며, 뒤 바디가 Good 창 두 개(Easy 300ms)보다 짧으면 끝을 일찍 뗄 때도 생긴다. head가 있는 2→1에서도 뒤 바디의 유지는 head를 처리한 실제 down부터 판단한다([RFD 0032 §4-3](../rfd/0032-body-held-count.md#4-3-head를-처리한-down부터-뒤-바디-유지)). 의도된 연주에는 영향이 없으며, 이 구분은 제작 지침으로 막지 않고 튜토리얼로 전달한다([RFD 0032 §9-4](../rfd/0032-body-held-count.md#9-4-여분-키-구분의-튜토리얼-전달)). 2→1에 `holdOnly`가 붙으면 실제 감소를 면제하고 앞 double의 두 unit을 각각 상태 판정한다.

### 연결 release

**새 계약에서는 숨은 연결 up 소비를 제거했다.** 명시 릴리즈만 up을 소비한다. 탭 노트를 친 키의 up·교대 up도 적격인 명시 릴리즈에 배정할 수 있으며, 연결이라는 이유로 먼저 가져가지 않는다. 아래는 과거 연결 보정과 후속 논의의 기록이다. 근거는 [RFD 0037 §3-3](../rfd/0037-explicit-score-notes-and-body.md#3-3-up-배정과-같은-키-재누름)이며 #342에서 구현하고 일반·명시 테스트 재생에서 검증했다.

#### 과도기 구형 계약·논의 기록

연결 경계에서 앞 바디의 몫이 끝날 때 떠나는 up 하나를 처리하는 release. 앞 바디도 끝나면 원래 release가 필요하며, 연결 경계에서는 등급과 점수 항목이 없다. 교대로 head를 치면 떠나는 키의 up이, 유지하며 다른 키로 head를 탭하면 탭한 키의 up이 연결 release다. head 하나에 하나만 적용하며(head 없는 경계는 [RFD 0032 §8-2](../rfd/0032-body-held-count.md#8-2-head-없는-경계)) 먼저 온 up이 그 몫을 채우고, 그 up을 뒤 끝의 release로 다시 쓰지 않는다. 경계 전에 오면(연결 head가 있으면 head를 처리하기 전) 그때 앞 바디의 그 몫이 끝나며, hold 수를 앞 바디가 요구하는 수 아래로 떨어뜨린 up이 앞 바디 끝의 Good 창 안에 있으면 유지 실패가 아니다(`holdOnly` 끝의 이른 완료와 같은 기준). 경계 뒤나 head 뒤에 오면 이미 끝난 몫의 release로 처리하며, 자격은 head의 Good 창이다. 떠나는 up이 없어도 Miss가 아니다. 경계에 감소 release가 있으면 경계 근처의 첫 up은 감소 release이며, 감소 release는 연결 release 몫을 채우지 않는다. 뒤 바디는 head가 있으면 head를 처리한 down부터, 없으면 head 없는 시작처럼 S+Good까지 채우면 된다. 유지 중 탭의 up이 head의 Good 창보다 늦을 때의 처리는 떼는 판정 창의 완화와 함께 나중에 정한다([PRD §12](../prd.md#12-미정-사항)). 기존 엔진([RFD 0020](../rfd/0020-note-judgment-units-and-inheritance.md))에서는 같은 처리를 연결 keyup 보정·연결 보정이라 불렀다. 근거는 [RFD 0032 §4-1](../rfd/0032-body-held-count.md#4-1-연결-release)·[§4-2](../rfd/0032-body-held-count.md#4-2-경계-전에-뗀-연결-release)(엔진 이행 전).

### `connection` 판정

**채택 계약·일반 기본 경로 구현·검증:** 같은 레인에서 앞 바디 끝과 뒤 바디 시작이 차트상 맞닿는 관계다. 실제 경계는 보존하지만 경계 자체로 입력 소비·점수·콤보·고도 회복을 만들지 않는다. 정상 승계·새 시작은 [바디 판정과 실패 종속](#바디-판정과-실패-종속)을 따르며 경계를 넘어 실패를 공유하지 않는다.

새 모델에서 hold 수와 트릴 여부가 같은 경계에는 뒤 바디 시작 탭 노트나 앞 바디 끝 릴리즈가 필요하다(사용자 결정, 2026-10-27, [의미 위반과 수리](#의미-위반과-수리)). 아래 구형 head/`holdOnly` 필수 제약은 구형 롱노트에만 적용한다. 트릴 바디와 같은 hold 수 일반 바디의 경계는 모양이 달라 방향과 관계없이 이 요구에서 빠진다(사용자 결정, 2026-10-27, 일반 바디 → 트릴 바디는 2026-10-28 정정). 트릴 바디 → 일반 바디는 판정이 이어지지 않는다(사용자 결정, 2026-10-27).

#### 과도기 구형 계약·논의 기록

같은 레인에서 앞 바디의 끝과 다음 바디의 시작이 차트상 맞닿는 연결 구조와 유지·승계 처리이다. 판정 창이 겹치는 별개 노트를 자동 연결하지 않는다. 같은 unit 수의 경계에는 head 또는 `holdOnly`가 필요하고, 수가 바뀌는 경계에는 둘이 없어도 된다.

일반 연결 성공에는 점수·콤보 증가·고도 회복이 없다. 실제 감소 release와 명시된 `holdOnly`는 각각 점수 항목이다. 연결 바디의 유지 실패는 무점수 Miss로 기록하고 고도·콤보에 반영한다. 유효한 경계 기회는 E−Good부터 E+Good까지 다루되 이미 완료한 기회를 재사용하지 않는다.

### 유지 판정

**채택 계약·일반 기본 경로 구현·검증:** 실제 시작한 바디의 요구 hold 수를 같은 레인에서 충족하는지 확인한다. 바디 도중 새로 누른 키도 참여하며 고정 물리 owner는 없다. 몫별 확정 실패를 재누름으로 복구하지 않고 틱 노트는 이 같은 상태만 따른다.

#### 과도기 구형 계약·논의 기록

활성화된 바디의 요구 unit 수를 등록된 held 키가 충족하는지 확인한다. 고정 owner를 두지 않으며, 임의의 바디 중간 down으로 유지 키를 바꾸지 않는다. 같은 timestamp의 모든 입력 후 부족을 확인한다. `holdOnly`도 양수 길이의 활성화·유지 조건을 따른다. 길이 0에는 지속 바디 유지가 없다.

### lane-held (레인 유지 모델)

**구형 등록 키 모델의 이름**이다. 새 계약의 실제 레인 hold 수 기반 시작·유지와 구별한다. 새 규칙은 [바디 판정과 실패 종속](#바디-판정과-실패-종속)을 따른다.

#### 과도기 구형 계약·논의 기록

레인 안의 등록된 유지 키 집합으로 요구 unit 수를 충족하는 모델이다. 물리 owner 한 키를 고정하지 않지만, 레인의 아무 held나 유지에 사용할 수 있다는 뜻은 아니다. 유지 키, 시작 준비, 실제 release 권한을 구분한다.

### 유예 시간 (Grace Period)

**채택 계약·일반 기본 경로 구현·검증:** 필요한 hold 수가 부족해진 짧은 공백의 유지 실패를 보호하는 시간이다. 몫별로 다루고 이미 실패한 몫은 되살리지 않는다. 사례에서 쓰는 20ms는 임시 값이며 최종 튜닝 값은 아니다. head 없는 시작의 기존 재충전과 탭 노트 담당 몫의 실제 down 기준을 보존하며, 틱 노트는 회복 결과를 기다린다. 릴리즈 up 소비나 Grace의 타이밍 면제와 다른 규칙이다. 아래의 연결 release·`holdOnly` 관련 적용 설명은 구형 논의다.

#### 과도기 구형 계약·논의 기록

필요한 hold 수보다 적어진 짧은 공백 때문에 바디가 바로 유지 실패하는 것을 보호하는 시간이다. [RFD 0032 §2-2](../rfd/0032-body-held-count.md#2-2-유지-유예)의 후속 채택값은 임시 20ms이며 최종값은 플레이테스트 뒤 정한다. double은 각 hold 수 기준을 회복할 때까지 따로 재고 이미 실패한 unit은 되살리지 않는다. head 없는 시작(독립 바디, 1→2 증가로 늘어난 몫)과 head 없는 경계 뒤 바디의 모든 몫([RFD 0032 §8-2](../rfd/0032-body-held-count.md#8-2-head-없는-경계))에서 S+Good 전에 생긴 부족은 [RFD 0032 §8-1](../rfd/0032-body-held-count.md#8-1-시작-직후의-재충전)에 따라 부족 시각에 유예를 더한 시각과 S+Good 중 늦은 쪽에 실패한다. 경계에서 떨어진 바디 중간의 끊김에는 유예만 적용한다. 유지 유예와 release 후보의 처리 시점은 별개의 문제이며, release 정책은 아래 후속 설계 기준에 따라 재검토 중이다. Grace 노트의 타이밍 등급 면제와도 구분한다.

연결 head를 처리한 single 사례에서는 head를 일찍 또는 늦게 처리해도 그 실제 down부터 뒤 바디의 유지를 판단하고 유지 유예를 적용한다. 그전의 공백은 20ms를 넘었다는 이유만으로 뒤 바디의 유지 실패로 삼지 않는다. 따라서 A up 2010 뒤 B down 2100으로 head 2000을 Good 처리하는 90ms 공백은 허용한다. down 시점부터 무조건 타이머를 소진하는 것은 아니며, 이후 필요한 hold 수가 부족해진 때부터 부족 시간을 잰다. head 2000을 1960에 처리하면 뒤 바디의 유지 판정도 1960부터 시작한다. 이후 hold가 1990～2015에 비면 25ms 공백이므로 유지 실패가 되며, 차트상 시작 2000부터 부족을 다시 세지 않는다. head Miss와 계속 유지한 바디의 release는 [RFD 0032 §5-1](../rfd/0032-body-held-count.md#5-1-계속-유지한-뒤-바디)을 따른다. 연결 head 창 안에서 hold가 끊기고 head도 놓친 사례는 [RFD 0032 §5-2](../rfd/0032-body-held-count.md#5-2-head-창-안에서-끊김)에 따라 head Miss 하나와 뒤 끝 종속 0점으로 정리한다. head 기한까지 유지한 뒤 A를 2200에 떼는 사례는 [RFD 0032 §5-3](../rfd/0032-body-held-count.md#5-3-head-창-뒤에-끊김)에 따라 N2 head Miss와 별도로 N3 유지 Miss를 처리한다. 임시 20ms를 적용한 N3 실패 기한은 2220이다. single head가 있는 double 연결에서는 [RFD 0032 §4-3](../rfd/0032-body-held-count.md#4-3-head를-처리한-down부터-뒤-바디-유지)·[§5-4](../rfd/0032-body-held-count.md#5-4-double-연결에서-head가-맡는-몫)에 따라 head가 맡는 몫에 같은 규칙을 적용한다. head가 있는 2→1에도 같은 규칙을 적용하며, 뒤 바디의 끝이 head의 Good 창 안에 있고 head가 아직 처리되지 않았다면 그 끝에서 뗀 up은 연결 release다([RFD 0032 §4-3](../rfd/0032-body-held-count.md#4-3-head를-처리한-down부터-뒤-바디-유지)·[§5-5](../rfd/0032-body-held-count.md#5-5-짧은-뒤-바디)). 나머지 적용 범위는 PRD를 따른다.

엔진은 아직 기존 연결 head의 Good 창을 이용한 보류를 구현하고 있다([RFD 0020 §2.12](../rfd/0020-note-judgment-units-and-inheritance.md#212-경계-뒤-교대-up--후속-채택)). 기존 연결 유지 보류와 새 유지 유예의 상세 이행은 PRD에서 추적한다.

### 가장 이른 노트 매칭

**채택 계약·일반 기본 경로 구현·검증:** 창·레인·키 자격을 충족한 명시 탭 노트 또는 릴리즈 중 차트 시각이 가장 이른 적격 대상에 해당 down/up을 배정한다. 바디·틱 노트는 소비 후보가 아니다. 같은 관측 묶음의 같은 raw 시각 up은 가능한 배정을 함께 대조해 키 수신 순서로 처리 가능한 항목을 놓치지 않는다. 서로 다른 시각 순서·같은 키 인과관계·확정 판정은 보존한다.

#### 과도기 구형 계약·논의 기록

창과 키 자격을 충족한 대상 중 차트 시각이 가장 이른 대상에 입력을 배정한다. head와 그 바디 시작이 같으면 head 입력이 담당 unit의 시작을 제공한다. double의 남은 head에 이미 사용한 물리 키는 그 head의 적격 후보가 아니다.

head 없는 실제 미처리 시작은 창 안의 down을 소비한다. 정당한 승계 준비가 충분하면 S 전에도 불필요한 down을 소비하지 않는다. 아직 받지 못한 시작은 raw held가 충분해도 완료하지 않는다. 길이 0 `holdOnly`의 상태 공유는 별도로 정의한다.

### `consume` (구 표기: 흡수·소비)

**채택 계약·일반 기본 경로 구현·검증:** 입력 한 건을 명시된 적격 점수 항목 하나에 배정하여 중복 사용을 막는 것이다. 탭 노트는 down을, 릴리즈는 up을 소비한다. 바디와 틱 노트는 down·up을 소비하지 않으며 탭 노트를 처리한 down의 hold도 바디에 참여한다. 릴리즈 없는 이른 정상 종료의 up도 적격인 명시 릴리즈 하나에 쓸 수 있다. 숨은 연결 release·`holdOnly` 끝의 up 소비는 새 모델에 없다.

#### 과도기 구형 계약·논의 기록

입력 이벤트를 적격 대상 하나에 사용하여 같은 이벤트로 다른 동일 종류의 요구를 중복 충족하지 못하게 하는 것.

아래 등록 키·연결 keyup 보정·일반 여분 키 제외는 기존 엔진의 설명이다. 후속 설계는 패턴별로 release 후보·소비와 Grace의 역할을 확인하며, 세부는 [release 판정](#release-판정)을 따른다. 기존 keydown·시작 처리와 전체 모델 이행은 별도로 대조한다.

- **keydown 소비**: 가장 이른 적격 Point 또는 실제로 필요한 시작 하나가 소비한다. double 시작과 double head에는 서로 다른 두 물리 키가 필요하다.
- **keyup 소비**: 가장 이른 적격 실제 release 하나가 소비한다. 같은 연결 구간의 뒤 시작에 등록된 키도 앞의 준비된 release를 처리할 수 있다.
- **연결 keyup 보정**: 유효한 head·시작 입력으로 다음 바디를 이어가는 데 쓰인 up은 뒤 실제 release에 소비하지 않는다. 서로 다른 키 교대와 동일 키 재타격에 같은 보정을 적용하며, 보정한 up은 실제 release 사용 이력에 넣지 않는다. 연결과 뒤 release에 모두 해당할 수 있으면 용도가 결정될 때까지 잠정 후보로 두며, 뒤 끝의 이른 등급을 먼저 확정하지 않는다. 마지막 E 이후에도 유효한 연결 입력이 남을 수 있다. 경계 뒤에 뗀 up도 연결 head의 Good 창 안이면 같은 잠정 후보이며, 그동안 이어받은 뒤 바디의 유지 실패를 확정하지 않는다([NJ-R16](../spec/note-judgment-cases.md#nj-r16)). 동일 키라는 이유의 추가 연결 Miss는 없다. [RFD 0020 §2.6](../rfd/0020-note-judgment-units-and-inheritance.md#26-교대-keyup과-뒤-release-창이-겹치는-경우--후속-채택)을 따른다.
- **부분 교대**: double의 한 unit만 교대하면 그 몫의 up에만 보정을 적용한다. 하나의 새 head로 두 교대를 성립시키지 않는다. 다른 unit이 기존 키로 정상 승계됐다면 그 unit의 유효한 up은 실제 release로 판정하며, 별도 head의 Miss만으로 그 바디를 실패시키지 않는다.
- **연결 보정 후보 순서**: 해당 경계에서 허용하는 몫만큼 적격 보류 up을 발생 순서로 배정한다. 새 head와 같은 키의 up도 후보가 되지만 이를 우선하여 앞 후보를 건너뛰지 않는다. 중간 head 하나에 연결용 up 하나를 배정한 `=o=`의 다음 적격 up은 실제 terminal release로 처리한다. 이후 같은 키의 새 head가 성공하면 새 누름의 권한으로 남은 release를 처리할 수 있으며, 이를 위해 앞 두 up의 배정을 바꾸지 않는다.
- **교대 실패**: 교대 실패로 다음 unit이 시작·승계되지 못하면, 보류한 up으로 그 unit의 release를 성공 처리하지 않는다. 종속 끝점은 0점과 원래 가중치를 반영하고 끝에서 추가 Miss 패널티를 주지 않는다. head만 Miss이고 기존 키로 바디가 정상 승계된 경우에는 실제 release가 남는다. 경계 뒤에 뗀 up의 교대가 성립하지 않아도 뒤 바디 길이와 관계없이 경계 전에 뗀 경우와 같다. 경계에서 그 up 하나로만 이어받은 뒤 바디는 연결 head 기한에 head Miss와 함께 종속 0점으로 정리하며, 유지 Miss나 release Miss를 더하지 않는다. 다른 등록 키로 유지 중인 바디는 계속 이어진다([RFD 0020 §2.12](../rfd/0020-note-judgment-units-and-inheritance.md#212-경계-뒤-교대-up--후속-채택)).
- **상태 완료**: `holdOnly`의 완료는 up 소비가 아니다. 한 입력의 Point/시작 소비와 상태 효과, 한 up의 실제 release 소비와 `holdOnly` 상태 완료를 구분한다.
- **일반 여분 키**: up으로 충분한 유지 키가 남으면 실제 release를 소비하지 않는다. 앞에 남은 종료 요구를 함께 고려한다. 이미 release에 사용한 누름의 권한은 남은 후보·여분 계산에서 제외한다. 같은 물리 키가 유효한 새 head·미처리 시작으로 얻은 새 권한까지 제외하지 않는다.
- **면제 몫**: `holdOnly`로 release를 면제받은 몫은 뒤 실제 release를 막는 여분 키 계산에서 제외한다. 모든 일반 여분 키를 면제하는 규칙은 아니다.

실제 up은 그 press의 자격을 끝낸다. 다시 누르는 것만으로 복구되지 않고, 새 적격 head·시작·승계가 필요하다. 앞 release의 미처리 준비나 Miss를 뒤 증가분 시작에 중복 배정하지 않는다.

### 공릴리즈 (`emptyRelease`)

구형·새 계약 모두에서 사용하지 않는 과거 도장 장치다. 역사적 결정은 [RFD 0015](../rfd/0015-binary-release-judgment.md)에 남긴다. 등록 키·시작 준비·release 권한 설명은 과도기 구형 모델이며, 새 계약의 입력 소비는 명시 탭 노트·릴리즈로 한정한다.

### 이벤트 라우팅

**채택 계약·일반 기본 경로 구현·검증:** 명시 탭 노트의 down 소비와 실제 hold에 따른 바디 시작·유지를 분리한다. 명시 릴리즈는 적격 up을 하나만 소비하고 틱 노트는 바디 상태에 정산만 연결한다. 건강한 승계와 첫 탭 노트 실패의 종속, single 탭 노트가 붙은 double의 비담당 몫을 구별한다.

#### 과도기 구형 계약·논의 기록

head가 시작에 함께 있으면 해당 head의 down 소비가 담당 unit의 시작을 제공한다. 별개의 독립 노트 입력은 양수 바디의 시작을 대신하지 않는다. head Miss로 시작하지 못한 종속 unit과 건강하게 승계된 unit을 구분한다.

### 릴리즈 노트

현재는 같은 레인의 `trillZone` 시작·끝을 포함한 구간 안에 명시 릴리즈를 도입하지 않는다. 트릴 바디 끝·단독, 일반/Grace·싱글/더블에 따른 예외를 두지 않으며 트릴 생성 조작에서도 끝 릴리즈를 만들지 않는다([RFD 0038](../rfd/0038-release-notes-in-trill-zones.md)). 구형 `trillLong`의 과도기 의미와 새 바디의 무점수는 각각 유지한다.

하나의 더블 릴리즈는 두 항목이 같은 일반/Grace 종류를 사용한다. 일반 한 항목과 Grace 한 항목을 섞지 않으며 저장·편집·검증에서도 이 제약을 보존한다([RFD 0037 §2](../rfd/0037-explicit-score-notes-and-body.md#2-구성과-점수-의미), 채택 계약·일반 기본 경로 구현·검증).

실제 뗌을 요구하는 명시적 점수 노트다. 같은 레인의 바디 끝점 또는 바디 밖의 단독 위치에 둔다. 바디 내부의 끝점 아닌 위치와 길이 0 바디와의 조합은 금지한다. 바디에 붙으면 그 몫의 실제 시작과 소멸하지 않은 기회가 전제이며, 바디가 정상 완료해도 남은 창은 유지한다. 단독 릴리즈에는 존재하지 않는 바디의 시작 조건을 붙이지 않는다(채택 계약·일반 기본 경로 구현·검증).

요구 한 몫당 실제 up 하나와 이론 가중치 3의 점수 항목 하나다. 일반 릴리즈는 누름과 같은 대칭 Perfect·Great·Good 창·FAST/SLOW를, Grace 릴리즈는 같은 Good 최대 창·Perfect와 FAST/SLOW 제외를 사용한다. Grace도 실제 up이 필요하다. 더블의 두 몫은 모두 일반 또는 모두 Grace로 통일한다.

바디의 hold 수와 릴리즈 수가 다르다는 이유로 금지하거나 수량을 자동 보정하지 않는다. double 전체 끝의 릴리즈 하나와 single 끝의 더블 릴리즈도 명시 수량을 보존한다. 더블 릴리즈의 두 up은 서로 다른 키가 원칙이지만, **해당 바디의 시작 탭 노트를 실제로 처리한 재누름**의 up은 같은 키로 남은 항목을 처리할 수 있다. 이 예외는 싱글 바디의 더블 릴리즈에도 적용하고 임의 재누름·다른 탭 노트·double 유지 두 몫의 같은 키 충족으로 확대하지 않는다. 한 up은 항목 하나만 처리한다.

#### 과도기 구형 계약·논의 기록

길이 0인 일반 롱노트로, 유효한 선행 시작 down으로 준비한 뒤 같은 키의 적격 up을 실제 release에 사용한다. 고정된 긴 바디는 없지만 시작 준비를 생략하지 않는다. double은 서로 다른 물리 키가 필요하며, head가 있는 길이 0 롱노트는 없다.

### 그레이스 릴리즈

**실제 뗌을 요구하면서 타이밍 등급만 면제**하는 릴리즈 노트. 허용 창 안의 유효한 뗌은 항상 Perfect이고 FAST/SLOW를 집계하지 않는다. 유효한 뗌을 놓치면 Miss이며, 계속 유지하는 것으로 대신할 수 없다. 누름 노트의 Grace는 그 누름에, 그레이스 릴리즈는 그 뗌에 적용한다. 기존 `holdOnly`의 상태 완료와 다르다. [RFD 0035](../rfd/0035-release-presence-and-grace.md)에서 채택했고 허용 창은 [RFD 0037 §2](../rfd/0037-explicit-score-notes-and-body.md#2-구성과-점수-의미)의 Good 최대 창이다(채택 계약·일반 기본 경로 구현·검증).

### 릴리즈 없음

해당 바디 끝에 릴리즈 노트를 두지 않아 **뗌을 요구하지 않는 상태**. 바디의 유지 요구는 남지만 끝에서 계속 누르는 것으로 뗌 누락 Miss를 받지 않는다. Grace의 타이밍 등급 면제와 구분한다([RFD 0035](../rfd/0035-release-presence-and-grace.md)). 기존 `holdOnly`의 점수 항목·입력 소비를 그대로 승계한다고 보지 않는다. 바디 정상 완료 자체에는 점수·콤보·고도 회복이 없다([RFD 0037](../rfd/0037-explicit-score-notes-and-body.md)).

### release 판정

**새 계약:** [릴리즈 노트](#릴리즈-노트)의 실제 up을 판정한다. 바디의 무점수 완료·틱 노트의 Perfect 정산·종속 0점은 구별한다. 아래의 `holdOnly`, 숨은 연결 up 소비, 미시작 바디의 끝 판정은 새 모델에서 대체된 과거 기록이다.

#### 과도기 구형 계약·논의 기록

실제 release는 Perfect / Great / Good / Miss이며 타이밍 오차를 FAST/SLOW에 반영한다. `holdOnly` 상태 완료는 Perfect/Miss이고 FAST/SLOW가 없다. 일반 연결 성공에는 별도 점수 판정이 없다.

**패턴별 확인, 엔진 미이행(2026-10-16):** [RFD 0032 §2-5](../rfd/0032-body-held-count.md#2-5-바디-중간-교대와-끝-창-안의-교대)의 단독 일반 롱노트 사례에서는 교대 up이 이른 실제 release를 처리하며, 다른 키가 계속 유지해도 그 입력을 제외하지 않는다. 이른 release의 점수 손해가 차트의 의도가 아니라면 해당 끝에 Grace(`holdOnly`)를 적용한다. 이는 [§1-2](../rfd/0032-body-held-count.md#1-2-패턴을-먼저-정하고-교대-자체의-점수-손해를-금지)의 교대 보호 목표를 구체화한 것으로, 모든 교대 up을 자동 면제하거나 release를 이진 등급으로 바꾸는 결정은 아니다. `holdOnly`는 그 끝의 release 요구를 면제하고 유지·완료 조건으로 판정하며, 실제 release를 요구하는 일반 끝에서는 계속 누르기만 해서는 완료할 수 없다. 나머지 패턴과 공통 release 자격·소비·등급·확정 시점은 계속 확인한다.

**double 끝의 키 구별(2026-10-16):** [RFD 0032 §3-1](../rfd/0032-body-held-count.md#3-1-두-release는-서로-다른-키)에 따라 같은 double 끝의 두 실제 release는 서로 다른 물리 키의 up을 요구한다. 같은 키를 두 번 눌렀다 떼는 입력으로 두 몫을 대신하지 않는다. [RFD 0032 §3-2](../rfd/0032-body-held-count.md#3-2-유지-키와-다른-키의-up)의 A/B 유지 중 C/D를 눌렀다 떼는 사례도 허용한다. C/D는 별도 head·시작에 쓰이지 않아도 N1의 release를 각각 처리하며, 두 up이 Perfect 창 안이면 Perfect 2이다. 유지한 A/B에 release를 고정하거나 hold 수가 두 개 아래로 내려갈 것을 요구하지 않는다. 이는 실제 up을 요구하는 규칙이며 계속 유지하기만 해서 자동 완료하는 규칙은 아니다. 유지 키를 계속 누르고 다른 키로 끝만 치는 플레이를 막기 위한 별도 여분 키 제한은 두지 않는다. [RFD 0032 §3-3](../rfd/0032-body-held-count.md#3-3-노트를-처리한-같은-키의-재누름)에 따라 같은 double 끝에 이미 쓴 물리 키라도 다시 눌러 그 double 바디가 시작하는 연결 head를 처리했다면, 그 누름의 up은 같은 double 끝의 남은 release를 처리할 수 있다. NJ-R13 형태에서 A up은 연결용, 첫 B up은 N3u1 release, B로 N2 head를 다시 친 뒤의 두 번째 B up은 N3u2 release다. 연결 release에 배정된 키를 플레이어가 구분할 수 없으므로 그 배정이 결과를 바꾸지 않게 하는 규칙이며, 노트 없는 재누름에는 적용하지 않는다. 한때 정한 새 head 뒤 재사용 금지는 이 규칙으로 정정했다.

**서로 다른 끝에서의 키 재사용(2026-10-16):** [RFD 0032 §2-4](../rfd/0032-body-held-count.md#2-4-여러-끝에-적격인-up의-순서와-키-재사용)의 앞 double에서 한 번 쓴 B는 뒤 독립 single의 release에 다시 사용할 수 있다. 두 끝의 창이 겹쳐도 B를 이미 쓴 앞 double은 해당 up에 부적격이므로 건너뛰고, 적격인 뒤 single을 처리한다. 키 중복 제한을 서로 다른 노트까지 확대하거나 앞 부적격 대상 때문에 뒤 적격 대상의 입력을 막지 않는다. 한 up은 실제 release 하나만 처리한다.

**여러 끝에 적격인 up의 순서(2026-10-16):** [RFD 0032 §2-4](../rfd/0032-body-held-count.md#2-4-여러-끝에-적격인-up의-순서와-키-재사용)에서 앞 double의 첫 release를 B로 처리한 뒤, 그 double에서 쓰지 않은 C의 up은 앞 double의 남은 release를 처리한다고 확인했다. 적격 대상 중 차트상 끝 시각이 가장 이른 실제 release를 고른다. 절대 시간 오차가 가장 작은 끝이나 가장 좋은 등급을 주는 끝을 고르지 않는다. 앞 double에 이미 쓴 B라면 위 재사용 사례처럼 앞 대상을 건너뛰지만, 아직 쓰지 않은 C라면 앞 대상을 처리한다.

**연결 head의 up 소비(2026-10-16):** [RFD 0032 §4-1](../rfd/0032-body-held-count.md#4-1-연결-release)의 같은 unit 수 연결에서 head를 치며 발생한 up 하나는 연결 release에 배정한다. A에서 B로 교대하면 A up을, A를 유지하며 B로 head를 탭하면 B up을 사용하며, 그 up을 뒤 실제 release에 중복 소비하지 않는다. 마지막 끝에는 별도 실제 up이 필요하다. 이는 이 두 연주에서 확인한 원칙이며 단독 바디의 모든 교대·모든 Point 탭에 확대하지 않는다. 기존 유지 보류와 임시 20ms 유예의 관계, 보정 창·개수·실패 조건 및 double의 세부는 계속 대조한다. 기존 엔진의 유지 중 탭 실패는 새 기대 결과가 아니다. [RFD 0032 §4-2](../rfd/0032-body-held-count.md#4-2-경계-전에-뗀-연결-release)에 따라 연결 head를 처리하기 전에 경계보다 먼저 뗀 up은 연결 release가 아니라 앞 바디의 그 몫을 끝내며, 앞 바디 끝의 Good 창 안이면 유지 실패가 아니다(등급 없음). 이 up은 그 head의 연결 release 몫도 채운 것으로 보아 뒤 up을 연결 release에 배정하지 않는다. 경계 뒤 또는 head를 처리한 뒤의 up은 지금처럼 연결 release이다.

**연결 release와 감소 release의 배정 순서(2026-10-16):** [RFD 0032 §6-4](../rfd/0032-body-held-count.md#6-4-감소-지점-앞뒤의-head)에 따라 연결 release는 head보다 뒤에 있는 끝의 release보다 먼저 배정하고, head와 같은 시각이거나 그보다 앞선 감소 release보다는 나중에 배정한다. head가 있는 2→1에서 경계 근처의 첫 up이 감소 release를 처리하는 것([§6-3](../rfd/0032-body-held-count.md#6-3-head가-있는-21과-감소-release))이 이 순서의 한 경우다. 엔진 이행 전이며 기존 엔진은 연결 release를 먼저 배정한다.

**연결 head Miss와 유지한 바디(2026-10-16):** [RFD 0032 §5-1](../rfd/0032-body-held-count.md#5-1-계속-유지한-뒤-바디)에 따라 연결 head를 놓쳐도 hold 수를 계속 충족한 뒤 바디의 실제 release를 처리한다. N1 1000～2000 → N2 head 2000 + N3 2000～3000을 A 1000～3000만으로 처리하면 N2는 Miss, A up 3000으로 N3는 Perfect이다. head를 놓쳤다는 이유만으로 정상 유지한 바디의 끝을 종속 0점으로 바꾸지 않는다. 같은 차트에서 A를 2010에 떼고 추가 입력이 없으면 연결 head 창 안에서 유지가 끊긴 경우로, [RFD 0032 §5-2](../rfd/0032-body-held-count.md#5-2-head-창-안에서-끊김)에 따라 N2의 기한 2120에 N2 Miss 하나와 N3 끝 종속 0점을 처리한다. N3의 별도 유지·release Miss를 더하지 않는다. head 기한 2120까지 유지하다가 A를 2200에 떼는 경우는 [RFD 0032 §5-3](../rfd/0032-body-held-count.md#5-3-head-창-뒤에-끊김)에 따라 N3 유지 Miss를 추가하고 그 끝은 종속 0점으로 정산한다. 합계 Miss 2이며 끝에서 별도 release Miss를 더하지 않는다. single head가 있는 double 연결에서는 [RFD 0032 §5-4](../rfd/0032-body-held-count.md#5-4-double-연결에서-head가-맡는-몫)에 따라 head가 맡는 몫에 같은 규칙을 적용한다. head 기한에 hold 수가 그 몫까지 채우면 계속 판정하고, 채우지 못하면 N2 Miss 하나와 그 몫의 종속 0점으로 정산한 뒤 뒤 바디가 요구하는 hold 수를 하나 줄인다. 나머지 적용 범위는 PRD에서 추적한다.

**리뷰 후속 결정(2026-10-17):** [RFD 0032 §2-3](../rfd/0032-body-held-count.md#2-3-release-등급과-자격-판정-창-기준)·[§7-1](../rfd/0032-body-held-count.md#7-1-holdonly-끝은-good-창-안의-up을-가져간다)·[§4-2](../rfd/0032-body-held-count.md#4-2-경계-전에-뗀-연결-release)·[§5-5](../rfd/0032-body-held-count.md#5-5-짧은-뒤-바디)에 따라 바디의 끝 창 안에 든 up은 그 바디가 시작했는지와 관계없이 release 후보이며, 그 release로 바디가 끝나고 이후 시작 실패를 세지 않는다. `holdOnly` 끝은 자기 Good 창 안의 up 하나를 가져가며(등급 Perfect), up이 없으면 유지로 완료한다. 경계 전에 뗀 up은 [연결 release](#연결-release)로 처리하며, 경계에 감소 release가 있으면 첫 up이 감소 release다. 뒤 바디의 끝이 head의 Good 창 안에 있고 head가 아직 처리되지 않았다면 그 끝에서 뗀 up은 연결 release이며, head를 놓치면 끝은 종속 0점이다. 엔진 이행 전이다.

**이전 후속 결정, 재검토 중(2026-10-15):** [RFD 0032 §2-3](../rfd/0032-body-held-count.md#2-3-release-등급과-자격-판정-창-기준)에 따라 hold 수를 감소시키는 모든 유효한 up을 release 후보로 받는다. 1→0으로 한정하지 않으며 여분 키·교대·Point 탭에서 나온 up도 같은 기준을 따른다. 후보 중 판정 창과 대상의 자격을 충족한 미처리 실제 release를 차트 시각이 가장 이른 순서로 처리한다. 한 up은 항목 하나만 처리하고, 처리한 항목은 다시 사용하지 않는다. 적격 항목이 없는 up에 별도 점수나 release Miss를 만들지 않는다.

위 이전 결정에서 20ms는 유지 실패에만 적용했다. 적격 up의 실제 release는 교대 여부를 기다리기 위해 보류하지 않고 실제 up 시각으로 판정하며, 이후 hold 회복으로 후보나 판정을 취소하지 않는다. 같은 timestamp의 개별 up을 보존하여 서로 다른 키의 입력 처리 순서가 결과를 바꾸지 않게 한다. 이 규칙은 분리 경계에만 적용하는 예외가 아니다.

끝 근처의 교대·Point 탭 up도 실제 release를 처리할 수 있으므로, 제작자는 down과 up을 함께 고려한다. 교대에 정밀한 release를 요구하지 않을 끝에는 `holdOnly`를 사용한다. Point의 `grace`만으로 release 요구는 면제되지 않으며, `holdOnly`도 주변의 다른 실제 release가 up을 받는 것을 막지 않는다. 세부 제작 원칙은 [차트 디자인의 주의사항](chart-design.md#차트-설계-시-주의사항)을 따른다.

### 점수 항목과 무점수 Miss

**채택 계약·일반 기본 경로 구현·검증(판정 코어·세션 정산은 #342, 실제 재생·결과 연결은 #346·#347):** 명시 탭 노트·릴리즈 노트·틱 노트의 요구 한 몫이 이론 가중치 3의 점수 항목 하나다. 바디만 있는 차트의 항목 수는 0이며 바디 유지·정상 완료·경계 자체는 점수·콤보·고도 회복을 만들지 않는다. 바디 실패는 원인 실패의 Miss·콤보·고도 효과를 내지만 별도 이론 항목을 추가하지 않는다.

실시간 분모는 처리한 항목, 최종 분모는 차트 전체 항목의 이론 가중치 합이다. 실패에 종속된 미처리 릴리즈·틱 노트도 원래 가중치의 0점으로 한 번 정산한다. 추가 Miss 효과는 없지만 실패 표시와 기회 소멸은 남는다. 일반 진행에서는 이미 확정한 항목을 다시 처리하거나 성공을 되돌리지 않는다. 일시정지 뒤 되감기는 [별도의 복원 경계](#일시정지-후-재개)에서 이후 결과를 버리고 다시 처리한다.

전체 이론 가중치 합이 0인 유효한 차트도 재생할 수 있으며, 플레이 중 달성률과 결과의 달성률·랭크를 표시하지 않는다. 바디 판정·원인 Miss와 기존 Full Combo 기준은 유지한다. 획득 점수만 0이거나 아직 실시간 분모가 0인 경우와 구별하며, 점수 항목이 있는 차트의 전부 Miss는 0%·F다([RFD 0039](../rfd/0039-unscored-chart-results.md)). 새 테스트 플레이와 일반 공식 결과 모두 이 표시 경계를 사용한다. 실제 세션·화면과 공식 결과를 연결하고 단위·브라우저 테스트로 검증했다.

#### 과도기 구형 계약·논의 기록

head, 실제 release, 명시된 `holdOnly`는 차트로 이론 가중치가 정해지는 점수 항목이다. 일반 연결 유지 실패는 Miss 기록·고도 손실·콤보 단절에 반영하지만 새로운 점수 항목이나 직접 감점을 추가하지 않는다.

이행 전 엔진은 head Miss로 시작할 수 없는 종속 끝점도 0점과 원래 가중치를 head Miss와 함께 처리하고, 끝점에서 추가 Miss 표시·고도 손실을 주지 않는다. 활성 후 실패한 unit도 한 번만 실패 처리한다.

Miss가 있으면 Full Combo가 아니지만, 릴리즈 기회 소멸 등 점수 항목의 실패 없이 무점수 유지·연결 Miss만 있다면 달성률 100%가 될 수 있다. 기존 엔진의 무점수 연결 Miss 사례는 [NJ-S01](../spec/note-judgment-cases.md#nj-s01)을 따른다.

### `goodTrill` (트릴 오입력 Good — 화면 표시 GOOD◇)

트릴 노트에서 키 교대에 실패했을 때(같은 키를 연속 입력) 발생하는 특수 Good 판정. ◇ 기호는 트릴 노트의 마름모 형태에서 가져왔다. 일반 Good(타이밍 부정확)과 별도로 집계되어, 유저에게 "타이밍 문제"와 "손배치 문제"를 구분한 피드백을 제공한다. 결과 화면에서 별도 행으로 표시한다. **각 `trillZone`의 첫 노트에서는 발생하지 않는다** — `trillZone`이 시작되면 교대 추적 상태가 초기화되므로, 첫 노트는 항상 교대 성공으로 판정된다.

**구현**: `JudgmentGrade.GOOD_TRILL`(`src/shared/constants/judgment.ts`), `PointJudgmentState`의 교대 판정.

### 배드말림 (Bad Train)

앞의 미처리 노트가 뒤에 의도한 입력을 먼저 받아 후속 판정이 밀리는 현상. 현재 모델에서는 가장 이른 적격 노트가 입력을 소비하는 것을 리듬게임의 정상 특성으로 인정한다. 준비가 끝난 시작이 불필요한 down을 다시 가져가는 문제와 구분한다.

### 판정 효과 (`ConfirmedJudgmentEffects`)

**채택 계약·일반 기본 경로 구현·검증:** 확정된 판정·정산이 일으키는 점수·통계·콤보·고도·판정 글자·타격 효과다. 현재 상태의 재조회와 한 번만 실행할 확정 효과를 구별하며 표시 복구·렌더러 재부착으로 정산이나 효과를 재실행하지 않는다. 기존 코드 식별자는 아래 구형 구현의 이름이며 새 API 이름을 고정하지 않는다.

- 틱 노트 성공도 Perfect 판정 글자와 해당 레인의 일반 타격 이펙트를 낸다. 정상 확인·시작/회복 대기 뒤 성공·유효한 이른 종료 일괄 성공에 적용하며 기존 스킨·효과 설정·판정선 배치를 따른다. 미확정 상태와 종속 0점에는 성공/추가 Miss 글자나 성공 이펙트를 만들지 않는다.
- 같은 확정 시각의 표시 대상 중 가장 낮은 등급을 대표 판정 글자로 고른다. 종속 0점은 후보에서 제외하며 후보 수신·호출 분할 순서에 좌우되지 않는다. 서로 다른 확정 시각을 프레임이나 별도 허용 폭으로 묶지 않는다.
- 대표 등급 안에서 표시 가능한 타이밍이 있는 실제 입력을 우선하고 여러 개면 raw 오차 절대값이 가장 큰 입력의 FAST/SLOW·타이밍 수치를 쓴다. 오차 0도 타이밍 정보다. 틱 노트/Grace에 오차를 만들거나 다른 등급의 오차를 빌리지 않으며 기존 임계값·사용자 설정을 유지한다. 동률의 안정 선택은 구현 사항이다.
- 대표 표시와 각 항목의 점수·통계·콤보·고도·타격 정산은 별개다. 현재 콤보는 기존 확정 순서와 같은 timestamp·phase의 Miss 우선 규칙을 유지한다. 틱 노트 성공은 몫당 콤보 +1·일반 Perfect 고도 기여이며 타이밍 오차·FAST/SLOW는 없다.
- 틱 노트는 성공 확정 시 즉시 숨긴다. 더블은 성공한 쪽만 숨기고 남은 쪽의 원래 위치·크기·밝기를 유지한다. 미래 틱 노트도 종속 0점 확정 즉시 실패색으로 바꾸고 원래 위치에서 화면 밖까지 스크롤한다. 시작·회복 대기를 미리 성공/실패 표시하지 않는다.
- 바디 정상 완료는 유효한 이른 종료·연결 여부와 관계없이 즉시 숨긴다. 대기 중인 명시 릴리즈는 별도로 표시·판정한다. 더블 한 몫만 정상 완료되면 전체 바디 도안을 alpha 0.7로 남기고 모두 정상 완료하면 숨긴다. 릴리즈 성공 수로 바디 완료를 추정하지 않는다.
- 실패한 바디·릴리즈는 실패색으로 화면 밖까지 남긴다. 더블 일부 실패는 실패한 절반만 실패색이고, 일부 성공/정상 완료는 전체 alpha 0.7이다. 한쪽 성공·한쪽 실패인 바디와 릴리즈는 두 축을 합성해 부분 실패 도안 전체 alpha 0.7로 남긴다. 틱 노트는 몫마다 따로 그려 요구 수를 표현하므로 전체 alpha 0.7의 예외다.
- 놓친 탭 노트는 싱글도 더블처럼 실패 도안으로 그린다.
- 더블 릴리즈 본체는 전체 대기 alpha 1 → 한 몫 성공·나머지 대기 전체 alpha 0.7 → 두 몫 모두 성공 시 숨김으로 표시한다. 원래 위치·크기·색·모양을 유지하며 이 릴리즈 성공 수로 바디의 알파를 바꾸지 않는다. 성공·실패 혼합은 위의 부분 실패 도안 전체 alpha 0.7을 따른다.
- Grace 탭 노트(트릴 탭 포함)·Grace 릴리즈의 전체 흰 외곽은 본체가 보이는 동안 실패를 포함해 원래 밝기를 유지한다. 본체 alpha와 분리하고 본체가 숨겨지거나 스크롤 밖으로 제거될 때 함께 숨긴다.
- 별도 바디 시작·끝 마감 에셋을 두지 않는다. 명시된 탭 노트·릴리즈 노트·틱 노트만 자기 상태로 표시하고 마감·릴리즈를 중복 합성하지 않는다. 화면 잔존·실패색은 입력 기회·효과를 다시 여는 신호가 아니다.

근거는 [RFD 0037 §7](../rfd/0037-explicit-score-notes-and-body.md#7-표시와-확정-효과)다. 아래의 연결 바디 완료 후 원래 끝까지 남김과 시작/끝 터미널 전파는 구형 표시 기록이다.

#### 과도기 구형 계약·논의 기록

확정 판정 하나가 점수·화면에 일으키는 효과의 순수 기술이다. `decideConfirmedJudgmentEffects(event, note)`가 점수 항목 정산, 종속 0점 정산, 무점수 Miss를 구분하고 판정 텍스트·밤 이펙트·고도 효과를 결정한다. 실제 release는 raw 타이밍 차이를 기록하고 `holdOnly`와 Grace는 FAST/SLOW를 만들지 않는다. 종속 0점 정산에는 별도의 Miss 통계·콤보·고도·판정 표시가 없다.

`NoteJudgmentSession`이 점수 효과를 적용하고 확정 묶음을 전달한다. `SessionRendererAdapter`는 현재 콤보·달성률, head의 전체/부분 처리 표시와 디버그 기록을 렌더러에 전달한다. 바디는 unit별 상태 조회로 표시하며, 연결 구간이 일찍 완료돼도 차트상 경계까지 남긴다. 튜토리얼은 같은 판정·효과 경로를 사용하고 필요한 표시만 적용한다.

싱글·더블 바디의 켜짐 표시는 아직 시작하지 않은 후속 연결 구간의 바디·터미널에도 이어진다. Trill 구간은 연결 켜짐 표시를 보내거나 이어받지 않고, 자기 구간의 실제 유지 상태만 표시한다. 표시 수는 경로에서 가장 작은 건강한 unit 수를 넘지 않는다. 이미 시작한 구간의 해제·실패·완료와 Trill 구간을 건너뛰지 않으며, 이 표시는 후속 판정 unit의 활성화나 점수 정산을 앞당기지 않는다. 포인트 노트는 겹치는 바디와 시작·끝 터미널보다 항상 위에 표시한다.

이 켜짐 표시는 켜짐 효과가 있는 스킨에만 적용한다. 스킨은 테마의 `heldEffect`로 효과 유무를 선언하며 생략하면 효과가 있다. `heldEffect: false`인 스킨은 켜짐 에셋 없이 유지 중에도 대기 바디·터미널을 그려 unit별 유지 상태와 연결 켜짐 전파를 표시하지 않는다. 부분 실패·실패는 효과 유무와 관계없이 표시하며, 켜짐·꺼짐 디자인은 포인트에 두지 않는다. 결정 근거는 [RFD 0028](../rfd/0028-skin-held-effect.md)이다.

**노트 표시 효과(`NoteDisplayEffect`)**는 렌더러에 전달하는 `{body, visibility}` 형태의 표시 명령이다. 새 세션에서는 head 표시 명령과 바디 상태 조회를 구분하며, 실패한 double의 건강한 unit을 함께 실패 표시하지 않는다.

**구현**: `src/game/judgment/confirmedJudgmentEffects.ts`, `NoteJudgmentSession.ts`, `SessionRendererAdapter.ts`.
_Avoid_: 판정 전파(표시 외 효과를 배제하는 인상)

## 차트 이벤트

### `ChartEvent`

이 절의 이벤트 명칭·공통 편집 계약은 [RFD 0067](../rfd/0067-chart-event-names.md)·[RFD 0068](../rfd/0068-common-event-editing.md)을 따른다. 이벤트 명칭의 코드 전환은 PR [#368](https://github.com/nanana3679/not4k/pull/368), 공통 편집·배치 겹침 검증·초기 설정 선택 제외는 PR [#369](https://github.com/nanana3679/not4k/pull/369)로 반영했다. 로드 시 초기 설정 자동 분리는 후속 구현이다.

차트에 배치되는 이벤트의 통합 타입. `type` 필드로 구분되는 디스크리미네이티드 유니온이다. 시점 이벤트(`BpmChangeEvent`, `TimeSignatureChangeEvent`)와 구간 이벤트(`TextEvent`, `AutoEvent`, `StopEvent`, `TutorialInputEvent`, `TutorialDiagramEvent`)로 나뉜다. 저장 데이터와 에디터의 편집·렌더링에서 같은 이벤트를 가리키며, 화면에 그렸다는 이유로 별도 도메인 개념인 “마커”로 부르지 않는다. 명명 근거는 [RFD 0067](../rfd/0067-chart-event-names.md)를 따른다.

이벤트 편집은 노트와 같은 선택·이동·리사이즈·복사·잘라내기·삭제·취소·undo 흐름을 사용한다. 선택은 `Selection.events`가 소유하고 노트·구간 선택과 공존한다. 클릭·Shift 추가·Alt 해제·토글·박스·전체 선택을 지원하며, 0박 초기 BPM·박자는 모든 선택에서 제외한다([RFD 0082](../rfd/0082-initial-timing-events-not-selectable.md)). 구간 이벤트는 박스와 일부라도 겹치면 선택한다. 가로 이동은 `editorLane`만 바꾸며 보조 레인 안에 머문다. 저장 모델은 `chart.events`로 유지한다. 더블클릭은 이벤트 속성 모달을 연다.

클립보드는 명시적으로 선택한 이벤트만 담으며 `TimeSignatureChangeEvent`도 복사한다. 노트나 구간의 시간 범위에 겹친다는 이유로 이벤트를 자동 복사하지 않는다. 초기 BPM·박자는 선택 기반 이동·복사·잘라내기·삭제의 대상이 아니다. 더블클릭 속성 모달에서 값과 보조 레인을 편집하며, 불러온 뒤의 초기 설정 보조 레인은 모달에서 수동으로 수정할 수 있다. 시간 위치 변경·직접 삭제는 계속 보호한다. BPM 변경 드래그의 좌표 해석은 down 시점으로 고정해, 이동 중 시간 계산이 바뀌어도 포인터가 같은 움직임을 반복 적용하지 않게 한다. 근거는 [RFD 0068](../rfd/0068-common-event-editing.md)이다.

이벤트의 배치 겹침은 같은 보조 레인(`editorLane`, 생략 시 1)에서 종류에 관계없이 의미 위반이다. 시점 이벤트와 길이 0 구간은 점, 양수 길이 구간은 시작을 포함하고 끝을 제외한 구간으로 검사하므로 끝과 다음 시작의 맞닿음은 허용한다. 다른 보조 레인의 동시 배치는 허용하되 BPM·박자 중복이나 같은 종류 구간의 시간 모순 등 기존 의미 제약은 유지한다. 위반 항목은 빨간 해칭으로 표시하고 편집·수리는 허용하지만 저장·플레이를 막는다. 일반 이벤트의 자동 레인 이동은 하지 않는다. 겹친 0박 초기 BPM·박자 설정의 로드 정리는 아래 후속 예외를 따른다([RFD 0078](../rfd/0078-event-placement-overlap.md)).

차트를 불러올 때 겹친 0박 초기 BPM·박자 설정은 값·박 위치를 유지하고 충돌 없는 보조 레인으로 자동 분리한다. 일반 이벤트는 자동 재배치하지 않으며, 같은 종류의 초기 설정 중복 등 기존 의미 위반은 별도로 유지한다. 빈 표시 레인이 없으면 필요한 만큼 보조 레인 표시 범위를 확장한다. 자동 분리 결과와 필요한 보조 레인 수는 불러온 기본 상태로 취급한다. 이 정리는 Undo·Redo 이력에 넣지 않고 별도 미저장 변경 표시도 하지 않는다. 이후 사용자가 저장하면 정리된 레인 배치를 저장하며, 저장 전에는 서버·원본 파일에 자동으로 쓰지 않는다. 선택 제외와 더블클릭 수동 편집은 유지한다([RFD 0082](../rfd/0082-initial-timing-events-not-selectable.md), 자동 분리 런타임은 후속 구현).

### `BpmChangeEvent`

`bpm` 타입의 시점 이벤트. 해당 박부터 다음 `BpmChangeEvent` 전까지의 BPM을 정의한다. 0박의 초기 BPM 설정도 포함한다. BPM은 박과 실제 시간의 관계를 정하며 게임의 스크롤 속도와 구별한다. 저장 JSON의 `type: "bpm"`은 유지한다.

초기 BPM과 변경 목록은 같은 곡의 모든 차트가 공유하는 [곡 타이밍](#곡-타이밍)에 속한다. 현재 차트별 `events` 저장은 곡 단위 공유의 완료된 구현을 뜻하지 않는다.

### `TimeSignatureChangeEvent`

`timeSignature` 타입의 시점 이벤트. 해당 박부터 다음 `TimeSignatureChangeEvent` 전까지 한 마디의 박 수(`beatPerMeasure`)를 정의한다. 0박의 초기 박자 설정도 포함하며, 이후 변경은 마디 경계에 둔다. 분수 박 수(예: `7/2`)를 허용한다. 저장 JSON의 `type: "timeSignature"`는 유지한다. 초기 박자표와 변박 정보는 같은 곡의 모든 차트가 공유하는 [곡 타이밍](#곡-타이밍)에 속한다. 현재 차트별 `events` 저장의 곡 단위 공유 전환은 후속 구현이다.

### `BpmChange`·`TimeSignatureChange`

시간 계산을 위해 시점 이벤트에서 추출한 데이터다. `BpmChange`는 `{ beat, bpm }`으로 박↔시간 변환에 쓰이고, `TimeSignatureChange`는 `{ measure, beatPerMeasure }`로 마디 시작 계산에 쓰인다. 후자의 `measure`는 이벤트의 `beat`에서 계산한 마디 번호다. 초기 설정도 변경 목록에 포함한다. 이벤트 자체나 화면 표식을 뜻하지 않으며 별도로 저장하지 않는다.

### `AutoEvent` (구 표기: Auto 구간)

튜토리얼에서 시범 연주를 보여주는 전용 `auto` 타입의 구간 이벤트다. 일반 차트의 연출용 자동연주 기능으로 사용하지 않는다. 기존 이벤트 구간에서는 사용자 입력이 차단되고 노트가 자동으로 Perfect 타이밍에 판정되며 스코어에 반영된다. 새 튜토리얼의 시연 자동 입력은 실습 성공 횟수에 포함하지 않는다. `직접 입력 / 시연` 토글과의 구체적 연결은 [PRD §12](../prd.md#12-미정-사항)에서 관리한다.

### `TextEvent` (구 표기: 메시지 이벤트)

`text` 타입의 구간 이벤트. `beat~endBeat` 구간 동안 게임 화면 오른쪽에 텍스트 메시지를 표시한다. 튜토리얼에서 설명을 보여주는 용도로 사용한다.

### `StopEvent` (구 표기: 정지 이벤트)

`stop` 타입의 구간 이벤트. 이 구간 안에는 노트를 배치할 수 없다 (배치 제약 조건).

## 곡 에셋

### `gameplayRange` (구 표기: 인게임 구간)

원본 음원 중 실제 **플레이 세션**에서 사용할 시작～끝 구간. 곡이 너무 길거나 무음 구간이 길 때, 원본 음원 파일은 보존하면서 플레이 화면에서는 이 구간의 시작을 0ms로 간주해 재생한다. 차트의 박 좌표와 곡 공통 음원 정렬 오프셋은 `gameplayRange` 시작점을 기준으로 해석한다. (UI 라벨은 화면 표시 예외로 "인게임 구간"을 유지한다.)

### `gameplayRange` 페이드 인·아웃 (code `fadeInTime`/`fadeOutTime`, 구 표기: 인게임 페이드)

`gameplayRange`의 시작과 끝에 적용하는 페이드 인/페이드 아웃 시간. 초 단위로 저장하며, 페이드가 구간 길이보다 길어지지 않도록 각 값은 `gameplayRange` 길이의 절반 이하로 제한한다. 같은 필드 이름이 `previewRange`(곡 선택 미리듣기 구간)에도 있으므로 문서에서는 "`gameplayRange` 페이드 인·아웃"처럼 구간을 앞에 붙여 쓴다([term-map](term-map.md) B).

## 외부 참조 용어

다른 리듬게임에서 유래하여 not4k 문서에서 비교·참조 용도로 등장하는 용어.

| 용어            | 원작          | 의미                           | not4k에서의 대응                |
| --------------- | ------------- | ------------------------------ | ------------------------------- |

## 게임 입력

플레이 세션에서 판정 엔진에 레인 press/release 이벤트를 공급하는 계층. 실제 키보드(`InputSystem`)와 합성 입력(`AutoPlayer`)이 같은 seam에 서는 두 어댑터다.

### `AutoPlayer`

**새 계약과의 경계:** 아래는 구형 런타임의 합성 입력 설명이다. 새 모델에서는 명시된 탭 노트·릴리즈와 바디 요구를 따라야 하며 구형 `holdOnly`나 자동 끝 점수를 생성하지 않는다. 중간 재생은 [RFD 0040](../rfd/0040-countdown-and-note-reentry.md)의 고정 3초 되감기·상태 복원을 따르며 현행 커서 필터를 공통 계약으로 고정하지 않는다. 새 경로의 `AutoPlayer` 연결은 #346에서 구현·검증했다.

#### 과도기 구형 계약·논의 기록

`AutoEvent`의 노트를 합성 press/release로 변환하는 순수 상태머신이다. 정적 차트의 연결·종료 요구를 사용해 유효한 키 입력을 만들며 판정 엔진·렌더러는 알지 못한다. `eventsThrough(timeMs)`는 각 입력의 원래 timestamp를 보존한다. 이미 누른 키에 중복 down을 만들지 않고, 연결 head에는 필요한 별도 입력을 만든다. 감소 `holdOnly`는 유지 중인 키를 보존한다.

press는 `AutoEvent` 안에서만 생성하고, 구간에서 시작한 누름의 release는 구간 밖이어도 전달한다. `InputTimeline`이 실제 키보드 입력과 합성 입력을 함께 모아 원래 timestamp별로 `NoteJudgmentSession`에 전달한다. 같은 프레임 안의 서로 다른 timestamp를 하나로 합치지 않으며, 같은 키의 down/up 인과관계를 보존한다. `GameClock`의 입력 오프셋은 수집할 때 한 번만 적용한다.

**구현**: `src/game/input/AutoPlayer.ts`, `InputTimeline.ts`.

## 에디터 입력

차트 편집기의 포인터 입력을 제스처로 인식하고 편집 의도로 라우팅하는 계층. raw 입력(입력층)과 도메인 판정(히트 테스트·스냅, 도메인층)을 2층으로 분리한다.

### 바디와 명시 노트의 편집 관계

[RFD 0037 §6](../rfd/0037-explicit-score-notes-and-body.md#6-위치-관계와-편집)의 **채택 계약·구현·검증**이다. 판정 종속과 편집 선택 집합은 구별하며 관계는 같은 레인·박 위치에서 도출한다. 새 저장 필드·ID·배열 모양을 이 정의에서 고정하지 않는다.

- 바디 클릭은 시작 탭 노트·소속 틱 노트·끝점 릴리즈를 함께 선택한다. 중간 탭 노트는 포함하지 않는다. 미선택 노트 직접 클릭은 그 노트만 선택하고 노트 hit가 바디보다 우선한다. 이미 선택된 노트를 누르면 현재 선택을 유지하고 끌면 선택 전체를 이동한다(구형 노트와 같음, 사용자 결정 2026-10-26). 박스에 바디 일부가 걸치면 연결 항목도 선택하고 틱 노트·릴리즈만 들어오면 그 항목만 선택한다.
- 개별 토글 제외를 허용하고 바디를 제외해도 남은 노트의 선택은 보존한다. 복사·이동·삭제는 실제 선택 집합을 따르며 명령 실행 시 제외 항목을 다시 넣지 않는다. 미선택 바디 끝 핸들은 바디 클릭과 같은 선택을 먼저 적용하되 이미 선택된 바디에서는 현재 선택·제외를 보존한다.
- 끝점 리사이즈는 선택된 끝 릴리즈만 끝점을 따라간다. 시작 탭 노트·내부 틱 노트는 선택되어 있어도 비례 이동하지 않는다. 틱 노트를 밖으로 내보내는 바디 축소와 내부 트릴 노트를 내보내는 `trillZone` 축소는 막는다.
- 바디 삭제·Cut에서 소속 틱 노트가 삭제 집합에 빠졌으면 거부한다. 모두 포함하면 한 편집에서 틱 노트부터 지우고 바디를 지운다. Cut 거부 시 클립보드도 바꾸지 않고 복사는 허용한다. 틱 노트만 삭제한 길이 0 바디는 남기며 틱 노트 없는 길이 0도 무점수·hold 요구가 있는 유효 요소다.
- 미선택 바디 직접 삭제는 시작 탭 노트·소속 틱 노트·끝 릴리즈를 함께 지운다. 선택된 바디 우클릭은 클릭한 바디 쪽의 현재 선택에 남은 관련 항목만 지우고 다른 선택과 제외한 릴리즈는 남긴다. Delete 키는 선택 전체, 개별 노트 직접 삭제는 그 노트만 대상으로 한다.
- 우클릭 드래그로 노트를 지워 드러난 바디는 같은 드래그에서 추가 삭제하지 않는다. 한 드래그의 삭제 전체가 Undo/Redo 한 단위이며 다른 드래그·편집과 시간으로 합치지 않는다. 도중 Esc는 그 삭제만 복구·취소하고 새 기록을 만들지 않는다. 버튼을 떼기 전 이동으로 삭제를 재개하지 않는다.
- 기존 바디 위의 틱 노트 배치는 hold 수에 맞춘 1몫·2몫을 한 편집으로 만든다. 다른 바디로 이동하면 새 바디에 맞춰 수량·이론 항목 수를 변경한다. 빈 위치 새 생성은 길이 0 싱글 바디+1몫 틱 노트이며 배치 상태에서 다시 클릭하면 더블로 바꾼다. 더블 재클릭은 변화가 없고 싱글 토글·빈 Undo를 만들지 않는다. 이동·붙여넣기로 바디 밖에 온 틱 노트에는 바디를 임의 생성하지 않는다.
- 탭 노트 드래그 생성은 시작 탭 노트·바디·끝 릴리즈를 하나의 생성·취소·Undo 조작으로 만든다. 싱글·더블에 맞춘 기본 릴리즈를 명시적으로 생성하며 Grace 모드는 탭 노트와 릴리즈 둘 다 Grace다. 컴파일러의 자동 끝 항목 생성과 구별한다. 더블 탭 노트·릴리즈는 한 번에 전체를 삭제하는 편집 단위다.

### 의미 위반과 수리

**채택 계약·일반 기본 경로 구현·검증:** 같은 레인·같은 시각에 탭 노트+릴리즈·탭 노트+틱 노트·릴리즈+틱 노트처럼 서로 다른 점수 의미를 겹치지 않는다. 같은 의미의 더블 수량과 합법적인 바디 위 노트는 구별한다. 길이 0 바디+탭 노트와 길이 0 바디+릴리즈도 금지하며 단독 릴리즈·길이 0 바디+틱 노트·틱 노트 없는 길이 0은 허용한다. 바디 밖 틱 노트·끝점 아닌 내부 릴리즈도 의미 위반이다.

**경계에 탭 노트도 릴리즈도 없는 같은 hold 수 바디 연결(채택 계약, 검증은 #341에서 구현):** 같은 레인에서 hold 수가 같은 두 바디가 맞닿고 뒤 시작 탭 노트도 앞 끝 릴리즈도 없으면 의미 위반이다(`sameHoldCountConnectionWithoutTapOrRelease`, 표시 이름 “탭·릴리즈 없는 같은 hold 수 바디 연결”). 화면에서 하나의 바디와 구별되지 않는데 판정이 달라지기 때문이다(사용자 결정, 2026-10-27). 같은 수 바디 끝에 맞닿은 길이 0 바디도 포함한다. 길이 0에는 탭 노트·릴리즈를 둘 수 없으므로 그 위치를 확인하려면 앞 바디 끝에 틱 노트를 둔다. 보조 레인도 같고 구형 롱노트는 구형 규칙([NJ-C02](../spec/note-judgment-cases.md#nj-c02))을 따른다. 트릴 바디와 일반 바디는 모양이 달라 구별되므로 트릴 바디 → 일반 바디(사용자 결정, 2026-10-27)와 일반 바디 → 트릴 바디(사용자 결정, 2026-10-28 정정)는 모두 이 규칙에서 빠지며, 이 위반은 일반 → 일반·트릴 → 트릴처럼 트릴 여부가 같은 경계에만 적용한다. 근거는 [RFD 0037 §6-1](../rfd/0037-explicit-score-notes-and-body.md#6-1-배치와-소속)이다.

사용자 결정이 아닌 기존 규칙의 적용과 구현 세부: 메인·보조 레인의 트릴 바디는 기존 `trillLongInvalid`대로 시작 트릴 탭 노트가 필요하므로, 메인·보조 레인의 일반 바디 → 트릴 바디에 탭 노트가 없으면 그 트릴 바디를 `trillLongInvalid`로 보고하고 이 위반으로는 보고하지 않는다. 메인·보조 레인의 트릴 바디 → 트릴 바디 경계에 시작 트릴 탭 노트가 없을 때도 `trillLongInvalid`만 보고하고 이 위반을 겹쳐 보고하지 않는다. 메인·보조 레인의 트릴 바디 → 일반 바디 접점은 기존 `trillExclusive`가 별도로 막는다. 과도기 혼합 차트에서는 같은 레인의 접점 박에 놓인 구형 포인트 노트(`single`·`double`·`trill` 타입)도 경계의 탭 노트로 인정해 일부만 수리한 차트의 저장을 막지 않는다([구형 차트와 과도기](#구형-차트와-과도기)). 구형 롱노트는 경계의 탭 노트로 인정하지 않으며, 구형 게임 노트가 남은 차트의 새 재생 차단은 그대로다.

미리보기부터 관계와 빗금을 갱신하고 이동·붙여넣기·리사이즈 등의 의미 위반 상태도 확정할 수 있다. **위반 항목의 선택 해제·다른 선택을 허용한다.** 기존 선택 해제 게이트와 구별하며 실제 위반의 저장·플레이 차단, 구조 오류 거부와 위의 바디 삭제·축소 보호는 유지한다. 과도기 혼합 저장은 구형 항목 존재 자체만으로 막지 않는다. 근거는 [RFD 0037 §6-3](../rfd/0037-explicit-score-notes-and-body.md#6-3-삭제취소수리)이다.

### Extra 노트

별도 엔티티가 아니라 `chart.notes`에서 `lane >= 5`인 노트. 메인 레인(`lane` 1..4) 노트와 같은 모델·인덱스 공간을 쓰되 게임 판정에서는 제외되고 에디터의 보조 영역에만 표시된다. 선택·이동·삭제·복사·검증은 메인 노트와 같은 경로를 사용한다. 상세 결정은 [RFD 0018](../rfd/0018-unified-lane-model.md)을 따른다.

### `laneAxis`

메인/보조 레인 경계 지식을 단독 소유하는 얇은 모듈. `MAIN_LANE_COUNT`와 `isMainLane`/`isAuxLane`이 경계를 정의하고, `mainNotes`/`auxNotes`가 게임 진입·직렬화 경계의 노트를 나누며, `toAuxIndex`/`fromAuxIndex`가 보조 파일 포맷 및 좌표의 1-기반 인덱스를 왕복한다. `isVisibleLane`은 `extraLaneCount`에 따른 표시 범위를, `maxAuxLane`은 로드 병합·자동 확장에 필요한 최대 보조 레인을 계산한다.

**불변식**: `lane > MAIN_LANE_COUNT`를 아는 코드는 `laneAxis`와 직접 소비자(게임 필터·직렬화 분리/병합·규칙 조건·좌표 투영·숨김 경계)뿐이다. 이동·선택·삭제·복사·히스토리·공통 검증은 메인/보조 노트를 구분하지 않는다. 이벤트의 `editorLane`은 별도 배치 공간이므로 `laneAxis` 관할이 아니다. 구현은 `src/shared/chart/laneAxis.ts`, 결정 근거는 [RFD 0018 §3-1](../rfd/0018-unified-lane-model.md#3-1-모델-확정)을 따른다.

### GestureRecognizer

raw 포인터 입력을 편집·뷰포트 제스처로 인식하는 순수 상태머신. 도메인(히트 테스트·스냅)을 전혀 모르며(입력층/도메인층 분리), 마우스·터치·펜을 정규화된 **`PointerSample`**로 받아 **`EditGesture`**/**`ViewportGesture`**를 방출한다. 시간을 `PointerSample.timeMs`와 `advanceTo(nowMs)`로 주입받아(`Date.now`/`setTimeout` 미사용) 포인터 시퀀스 단위로 테스트된다. 편집 모드는 인식기가 방출한 제스처만 받고 터치 상태(롱프레스 타이머·후보·핀치 세션)는 모른다. 두 손가락이 닿으면 진행 중 편집을 `editCancel`로 폐기한다.

**구현**: `src/editor/hooks/gestureRecognizer.ts`. 내비게이션 순수 함수는 `touchGesture.ts`를 내부 부품으로 재사용.

### PointerSample

DOM 포인터 입력을 정규화한 한 건: `{pointerId, pointerType(mouse|touch|pen), phase(down|move|up|cancel), x, y, clientX, clientY, timeMs, button, buttons}`. 마우스·터치를 같은 모양으로 만들어 **`GestureRecognizer`**에 넣는다. client 좌표는 click-slop·멀티터치 거리 계산에, x/y는 방출 제스처에 실려 모드로 전달된다.

**구현**: `src/editor/hooks/gestureRecognizer.ts`.

### EditGesture

차트를 편집하는 의미를 갖는 제스처. 현재: `editCancel`(두 손가락 내비가 편집을 가로챌 때 진행 중 편집 폐기), `longPress`(단일 터치를 click-slop 안에서 유지; 좌표는 down 시점). 무엇을 뜻하는지(이동/리사이즈/범위생성/삭제)는 모드·히트 테스트를 아는 어댑터가 순수 라우팅 함수로 정한다. click/drag/box 트랜잭션은 후속 슬라이스에서 이 어휘로 이관된다.

**구현**: `src/editor/hooks/gestureRecognizer.ts`(타입), 라우팅 `longPressRouting.ts`·`touchEditRouting.ts`.

### ViewportGesture

차트를 건드리지 않고 뷰포트만 움직이는 제스처. `viewportZoom`(핀치)·가로/세로 `viewportScroll`(두 손가락 팬). 셋은 이동량이 가장 큰 축으로 하나만 잠겨 동시 발생(부들거림)을 막는다.

**구현**: `src/editor/hooks/gestureRecognizer.ts`.

### `resolveGrab` (grab 우선순위 사다리)

Select 모드 down이 한 좌표에서 **무엇을 잡는지**(`GrabTarget`)를 정하는 순수 우선순위 사다리. z-order 9단계(끝 리사이즈 캡 4종 `noteEndCap`·`eventEndCap`·`trillZoneEndCap`·`restZoneEndCap` > 통합 `note` > `event` > 몸통 `trillZoneBody`·`restZoneBody` > `empty`)를 **단독으로 소유**한다. 캡 게이트(사다리 1·3·4)는 down 시점 선택(`sel`)을 읽어, 미선택 구간의 끝 캡은 리사이즈로 잡지 않고 겹친 노트/몸통으로 하강한다(RFD 0016 §6-6). 범위 노트 끝 캡의 hit 영역(`hitTestNoteEnd`)은 탭 노트·릴리즈·틱 노트와 겹친 자리를 비우고, 그 노트가 덮은 끝은 노트 hit 바로 위 띠(끝+1/16～3/16박)로 옮긴다. 그 띠에 겹친 노트가 없으면 미선택 바디도 사다리 1에서 바로 잡힌다. 연결 경계처럼 이어진 뒤 바디가 그 띠를 덮어도 띠는 앞 바디의 끝 hit이며, 사다리 1의 게이트(선택됐거나 최상위)에 따라 앞 바디가 선택됐을 때만 끝 캡으로 잡히고 미선택이면 뒤 바디를 잡는다. 선택 게이트가 없는 끝 캡 롱프레스는 그 띠에서 앞 바디 끝을 리사이즈한다. 수식자(shift/alt/toggle)는 대상 확정 "후"의 동작이라 사다리에 나타나지 않는다.

**불변식**: grab 우선순위를 아는 코드는 `resolveGrab` 한 곳뿐이다. 마우스(`SelectMode.onPointerDown`)와 터치(`useCanvasEvents` → `scheduleFromGrabTarget`)는 `SelectMode.resolveGrabAt(x, y)`라는 **같은 seam**을 소비하므로 두 경로로 갈라질 코드 위치가 없다. 터치 스케줄은 `GrabTarget`을 "`note`·`event`면 클릭 토글, 그 외 전부 지연-드래그(재생 위임)"의 2택으로 접기만 한다. 롱프레스 발화 사다리(`resolveLongPressAction`)는 선택 게이트 없는 별개 "직접 조작" 축이라 흡수하지 않는다(#143). 구현은 `src/editor/modes/resolveGrab.ts`.

### 차트 변이 게이트 (Chart Mutation Gate)

**새 계약:** 구조 오류 거부와 실제 의미 위반의 저장·플레이 제한은 유지하고, 편집 중 의미 위반의 확정·선택 해제는 허용한다. 바디 삭제·축소 보호와 과도기 혼합 저장의 예외는 [의미 위반과 수리](#의미-위반과-수리)를 따른다(채택 계약·구현·검증). 아래 store 구현은 새 에디터에서도 그대로 쓰며, 선택 해제 게이트와 엮인 서술은 제거 전 기록이다.

#### 과도기 구형 계약·논의 기록

에디터의 모든 차트 쓰기가 수렴하는 store `setChart`에 내장된 **구조 검증**. 낙관적 편집(RFD 0017)에서 setChart는 **구조 위반**(`validateChartStructural`: 구간 역전 `rangeInverted`·분자 0 박자표 `timeSigNotNatural` 등 malformed/크래시 유발)만 거부하고(차트·히스토리 무변) 토스트로 사유를 알린다. **의미 위반**(겹침·중복·트릴 헤드 등)은 편집 중 **transient로 허용해 커밋**한다 — "일단 옮기고 나중에 고치기". 따라서 **라이브 차트는 더 이상 항상 valid가 아니다**(렌더러·프리뷰·undo가 invalid를 견뎌야 한다).

**층1 안의 구조 vs 의미**: 구조 = malformed(그 자체로 성립 안 함) ∨ 크래시 유발(`timeSigNatural`은 measure 무한루프 방지를 위해 구조 — measure 루프 3곳 step≤0 가드로 하드닝됨) → setChart가 항상 거부. 의미 = 판정 전제 위반(겹침 등) → 커밋 허용, 커밋 게이트가 강제. **배치 제약의 두 층**(직교 축): 층1 = 모델 불변(`validateChart`), 층2 = 편집 배치 가드(`isCreatePlacementBlocked` — 시각 겹침 tolerance 등 UX 정책, 모드 소관). 층2 규칙을 게이트에 넣으면 레인 내 분리(`-o`) 같은 합법 배치까지 막게 되므로 섞지 않는다.

**커밋 게이트(의미 강제 지점)**: 의미 위반은 (1) **저장 게이트**(`useFileOperations`의 `validateChart`)와 (2) **플레이/프리뷰 진입 게이트**(`performPlayTest` + 툴바 Test Play 버튼 비활성)가 강제한다 — 위반이 남아 있으면 저장·플레이를 막는다. 위반 노트·트릴존은 빨간 해칭으로 표시된다(App이 차트 변경 시 `chartViolationIndices`로 재계산 — 캔버스 빨강 == 게이트 판정, 단일 소스). 되돌리기는 능동 **undo**(위반 상태도 커밋이라 히스토리에 남음).

**축소 커밋과 선택**: 노트·구간 개수가 줄어드는 커밋은 같은 트랜잭션에서 선택을 **엔티티 identity로 재매핑**한다 — 남은 엔티티는 새 인덱스로 계속 선택되고 지워진 엔티티만 빠진다. 인덱스 밀림으로 엉뚱한 엔티티가 선택되는 것을 막으면서, 선택된 바디 우클릭처럼 일부만 지우는 삭제가 다른 선택을 잃지 않게 한다. 개수가 줄지 않는 커밋은 재정규화만 한다.

**편집 transaction**: 붙여넣기 대기·이동 드래그·끝점 리사이즈·우클릭 드래그 삭제처럼 한 조작의 여러 쓰기는 `beginEditTransaction`이 준 token을 달고 history를 쌓지 않다가, 소유자가 확정하면 Undo 한 단위로 기록하고 취소하면 시작 전 차트·선택으로 돌린다. token 없는 쓰기·모드 전환·Undo/Redo·로드 같은 독립 명령은 열린 transaction을 먼저 확정하고 소유자에게 `onInterrupt`로 알린다. 소유자(`SelectMode`·`EraseGesture`)는 그때 진행 중 조작을 끝내 옛 token으로 쓰지 않는다. 끊긴 조작의 마우스·터치 누름은 손을 뗄 때까지 같은 누름으로 새 조작을 다시 열지 않는다(터치의 지연 박스·클릭 토글·롱프레스 후보 포함). Undo 가능 여부(`selectCanUndo`)는 아직 history에 들어가지 않은 transaction 변경도 셈한다.

**`loadChart`**: 레거시/외부 위반 차트를 구조·의미 모두 열어 수리를 허용한다(경고만). 재저장은 저장 게이트가 차단하므로 위반 상태가 저장·전파되지는 않는다 — "열 수는 있되, 다 고쳐야 저장할 수 있다".

**구현**: `src/editor/stores/editorStore.ts`.

### 선택 해제 게이트 (Deselect Gate)

**새 에디터에서 제거했다**([RFD 0037 §6-3](../rfd/0037-explicit-score-notes-and-body.md#6-3-삭제취소수리)). 의미 위반이 남아도 선택을 풀거나 다른 항목으로 바꿀 수 있다. `SelectionSlice.setSelection`·`clearSelection`은 정규화만 하고 전이를 거부하지 않는다. 위반 표시·저장·플레이 검증과 인덱스 유효성·트릴 등 기존 선택 정규화는 유지한다. 아래는 RFD 0017 §3-5의 결정과 제거 전 구현을 설명하는 보존 기록이며 현재 동작이 아니다.

#### 과도기 구형 계약·논의 기록

**제거 전 구현**: `src/editor/stores/selectionSlice.ts`의 `setSelection`(정규화 게이트와 같은 자리 — `clearSelection`도 이 관문을 지났고, 거부하면 false를 반환했다). `notes` 단일 축이 메인·보조 노트를 통합 인덱스로 다루므로, 보조 레인 위반 노트를 선택에서 떨구는 전이도 같은 게이트가 봉쇄했다. 삭제·붙여넣기 취소는 차트 축소 커밋(`setChart`)이 선택을 원자적으로 비워 게이트를 지나지 않았다. **전이 = 확정된 선택 변경**: 박스 드래그의 프레임 재구성은 프리뷰(`setSelectionTransient`)라 전이가 아니며, 드래그 종료 시 (시작 전 → 최종) 전이 하나로 게이트한다. select→move 체인은 커밋이 거부되면 이동을 시작하지 않는다.

"해제"를 제스처가 아니라 **선택 집합의 상태 전이**로 정의하는 게이트. 선택이 `현재`→`다음`으로 바뀔 때 **빠지는 노트**(`removed = 현재 − 다음`)에 **의미 위반에 관여하는 노트가 있으면 그 전이를 거부**하고 토스트로 사유를 알린다. 낙관적 편집(RFD 0017)에서 위반 시각화(해칭)는 뷰포트 안에서만 보이므로, 위반 노트가 화면 밖으로 벗어나 인지되지 못한 채 방치되는 것을 막는다 — **위반 노트를 선택에서 놓는 순간 = 편집 묶음 마무리** 신호로 규정하고 그 순간의 이탈만 봉쇄한다(하드 거부 아님, place-then-fix 유지). 제스처 열거(Esc·빈 곳 클릭·교체) 대신 전이 diff로 정의하는 이유: 교체(`{A}→{B}`)·부분 해제(`{A,C}→{C}`)·전체 비우기가 전부 `removed`로 한 규칙에 걸리고, 선택 확장(`removed=∅`)은 자연히 통과하기 때문이다.

**저장 게이트와 진짜 대칭 (단일 관문)**: 저장 게이트가 `setChart`(차트 쓰기 단일 수렴점)에서 차트 전역 위반을 막듯, 선택 해제 게이트는 `SelectionSlice`(선택 쓰기 단일 수렴점)에서 선택 집합 국소 위반을 막는다 — 조기(국소)/최종(전역)의 2단 방어. 선행: 흩어진 선택 해제 지점을 `SelectionSlice` 관문으로 수렴시켜야 게이트를 얹을 수 있다. **탈출구는 특례가 아니라 발화 경계의 귀결**: 게이트는 **위반을 남긴 채 위반 노트를 떨구는 전이**만 발화한다(면제 조건 = 전이 후 그 노트가 더 이상 위반이 아니게 됨). 따라서 undo/redo·위반 노트 삭제·붙여넣기 취소(차트를 함께 바꿔 위반을 없앰)는 `removed`가 있어도 통과한다. **구조 위반**(`timeSigNatural` 등)은 `setChart`가 항상 거부(§3-2)해 애초에 커밋 불가라 해제 시점엔 의미 위반만 남는다. 선택에 든 적 없는 화면 밖 위반은 이 게이트가 못 잡고 저장 게이트가 최종 방어선이며, §7의 미니맵 지시자는 이와 보완 관계(병행 가능). 상세는 [RFD 0017 §3-5](../rfd/0017-optimistic-edit-transient-invalid.md).

### SelectionSlice

**선택 의미:** [바디와 명시 노트의 편집 관계](#바디와-명시-노트의-편집-관계)의 실제 선택 집합·개별 제외와 [의미 위반과 수리](#의미-위반과-수리)의 선택 해제 허용을 따른다. 아래 배열·인덱스·`setSelection` 설명은 현행 구현이며 새 저장 포맷을 고정하지 않는다(채택 계약·구현·검증).

에디터 선택 상태(`selection: {notes, zones, restZones}`)의 **단독 소유자**. 보조 노트도 `chart.notes`의 통합 인덱스로 `notes`에 선택된다. 쓰기는 슬라이스 액션(`setSelection`·`clearSelection`)으로만 하며, 모든 액션이 **정규화 게이트**(`normalizeSelection`)를 지난다 — 차트 변이 게이트가 위반을 **거부**하는 것과 달리 이 게이트는 섞인 입력을 가장 가까운 합법 값으로 **접는다**. 선택은 휘발성 UI 상태이고, 박스 드래그 중 매 프레임 호출되는 경로에서 거부는 복구 동작이 없기 때문이다(구 `updateBoxSelection`의 조용한 정리 정책 승계). **선택 해제 게이트**(§3-5)는 새 에디터에서 제거해 `setSelection`은 정규화만 하고 항상 true를 돌려준다 — 그쪽 표제어 참조.

합법 상태(불변, RFD 0016·0018): ① notes는 동질적이다 — 일반 노트들(메인·보조 포함), 또는 같은 `trillZone`의 트릴 노트들만(`filterHomogeneousSelection`). ② `trillZone` 유닛(zones)은 일반 notes와 **공존**한다. 단 개별 트릴 노트 선택(트릴 노트 모드)은 배타 — 그때 zones는 빈 집합. ③ zones는 notes에 내부 노트를 주입하지 않는다 — 이동·삭제·복사 동사가 **실행 시점에 파생**한다(포함 기준, `zoneContainedNoteIndices`). ④ 모든 인덱스는 `chart.notes` 또는 해당 구간 배열 범위 안이다(차트 변이에 따른 보정은 변이 액션 소관 — 개수 불변이면 재정규화, 축소면 남은 엔티티를 identity로 재매핑해 지워진 것만 뺀다). ⑤ `restZones`(RFD 0019)는 note/zone과 **공존**하는 독립 축이다 — 내부 노트가 없어 동질성 machinery와 무관하며 정규화는 범위 prune만 한다. 단순 클릭은 전축 교체(SelectMode 선택 구성이 보장), 박스는 **부분 겹침**(`restZoneOverlapsBox` — 롱노트식)으로 픽업하며, 혼합 선택은 note·zone과 함께 이동·삭제·복붙된다. SelectMode·훅·컴포넌트에 선택 사본을 저장하지 말 것 — 이전에는 SelectMode private 필드가 진짜 권위였고 store는 파생 캐시라, store만 지우는 경로(undo/redo 등)에서 stale 선택이 남을 수 있었다.

**구현**: `src/editor/stores/selectionSlice.ts` (editorStore에 결합).

### ViewportSlice

에디터 뷰포트 상태(zoom·snapDivision·scrollY·horizontalPanX)의 **단독 소유자**. 쓰기는 `ViewportSlice`의 액션으로만 하며, 클램프(줌 50～2000, 세로 스크롤 범위)와 제스처→값 변환 규칙(휠 ×1.1, 핀치 거리 비율, 스냅 프리셋 사이클)을 순수 함수로 함께 소유한다(구 `SnapZoomController` 승계). 줌·범위·뷰포트 높이가 바뀌면 scrollY를 함께 재클램프한다. 클램프 입력(타임라인 ms 범위, 뷰포트 높이)은 외부 사실로 슬라이스에 입주하며, 콘텐츠 높이는 저장하지 않고 파생 계산한다.

렌더러 등 비-React 소비자는 **`ViewportSource`**(읽기 전용 스냅샷 `get()` + 변경 구독 `subscribe()`)로만 읽는다 — 이 통로로는 쓰기가 불가능하고, 테스트는 fake source를 쓴다(adapter 2개 = 실재 seam). 렌더러·컨트롤러·훅에 뷰포트 상태를 복제 저장하지 말 것: 이전에는 3곳 복제 + App useEffect 양방향 동기화가 이중 쓰기 race를 만들었다.

**구현**: `src/editor/stores/viewportSlice.ts` (editorStore에 결합).

### `TimelineSpace`

에디터의 **입력 좌표 공간**(픽셀 → 도메인 변환·스냅·히트테스트)을 한 인터페이스로 접은 deep module. 픽셀 좌표를 레인(`xToLane`·`xToUnifiedLane`)·박(`yToBeat`·`yToBeatRaw`·`snapBeat`)으로 변환하고, 노트·이벤트·`trillZone`의 히트테스트를 제공한다.

store·renderer를 모르는 **주입 source 기반 팩토리**(`createTimelineSpace(source)`)다 — 필요한 외부 사실(차트, 스냅 분할, 선택, 보조 레인 수, y→시간 변환)은 전부 `TimelineSpaceSource`에서 **호출 시점에 라이브로 읽는다**(클로저 스냅샷 없음). 이 라이브 읽기가 구 `useCoordinateHelpers`의 ref 이중화(stale closure 방지용 ref 11개)를 불필요하게 만든다. React 조립(store·renderer ref 접기)은 `useTimelineSpace` 훅이 담당하고, 테스트는 fake source로 순수 조립한다.

그리기 방향(도메인 → 픽셀)을 담당하는 **Projection**(`timelineProjection`)과 구분된다 — `TimelineSpace`는 입력 방향만 소관한다.

**구현**: `src/editor/timeline/TimelineSpace.ts` (팩토리) + `src/editor/hooks/useTimelineSpace.ts` (React 어댑터).
