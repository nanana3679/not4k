# not4k — Product Requirements Document (PRD)

> 4레인 노트낙하형 가변 손배치 PC 리듬게임

---

## 1. 문제 정의

PC 노트낙하형 고정키 리듬게임은 세 가지 구조적 한계를 공유한다.

| # | 문제 | 근본 원인 | 영향 |
|---|------|-----------|------|
| A | **연타의 물리적 고통** | 한 키에 한 손가락이 고정되어 반복 충격이 집중 | 건초염·손목 터널 증후군, 고난이도 패턴 단순화 |
| B | **키 수 간 난이도 단절** | 4B→5B→6B→8B 전환 시 레인 구조가 변경 | 키 수마다 사실상 다른 게임, 통합 성장 경로 부재 |
| C | **고정 손배치의 해부학적으로 불리한 패턴** | 레인-키 1:1 고정으로 해부학적 한계에 충돌. 키 수가 늘수록(5B·7+1) 심화 | IIDX 4756 문제, 랜덤 의존, 실력이 아닌 운에 의한 클리어 |

아케이드 리듬게임(SDVX, 츄니즘, maimai)은 물리적 인터페이스 특성으로 이 문제를 부분적으로 해결하지만, PC 키보드 환경으로 이식할 수 없다.

**근거 문서**: `docs/context/rationale.md`, `docs/research/` (6개 역기획 보고서)

## 2. 해법

### 핵심 메커니즘: 4레인 + 레인당 다중키 바인딩

- 화면에는 항상 4개의 레인이 존재한다.
- 유저는 각 레인에 **2개 이상의 키**를 바인딩한다.
- 같은 레인의 노트는 바인딩된 키 중 아무 키로든 처리할 수 있다.

| 기존 문제 | 해법 | 효과 |
|-----------|------|------|
| 연타의 고통 | 연타를 트릴(키 교대)로 처리 가능 | 반복 충격 분산, 패턴 다양성 확보 |
| 키 수 단절 | 레인 수 불변, 키 수만 유저가 확장 | 4키→16키가 하나의 연속된 성장 경로 |
| 해부학적으로 불리한 패턴 | 어떤 키 조합을 쓸지 유저가 선택 | 해부학적 한계가 시스템에 의해 강제되지 않음 |

**트레이드오프**: 입력 난이도 감소 대신 인식 난이도(어떤 키로 처리할지의 실시간 판단) 증가. 트릴 노트와 난이도 계단으로 관리.

## 3. 타겟 유저

### 1차 타깃: 기존 노트낙하형 리듬게임 유저 중 신체적 부하와 물리적 한계로 흥미를 잃은 유저

osu!mania, DJMAX 등 4키+ 리듬게임 경험자 중 고난이도에서 **신체적 부하와 물리적 한계**로 흥미를 잃은 유저.

| 기존 4키의 문제 | not4k의 해법 |
|---------------|-------------|
| 물리적 속도·지구력이 난이도 천장 | 신체 부하 대신 **인식 부하**(손배치 전환 판단)로 난이도 상승 |
| 특정 손가락에 부하 집중 (약지·소지) | 8키 분산 → 손가락 사용이 **균등하게 분산** |
| 배치가 불편해도 강제 | 원하는 손가락을 선택 가능 → **배치 스트레스 없음** |

### 2차 타깃: 리듬게임 입문자

리듬게임을 처음 접하는 유저도 not4k로 시작할 수 있도록 **진입 장벽을 낮추는 장치**를 마련한다:

- 튜토리얼 (Phase B): 연주 방법 → 복합 패턴 단계적 학습
- Lv.1~3: 전 노트 타입이 등장하지만, 패턴 밀도와 조합이 단순
- 옵저버 모드 (Phase B): 어려운 구간을 미리 연습 가능

단, **메인 타깃은 신체적 부하와 물리적 한계로 기존 리듬게임에서 흥미를 잃은 유저**이다. 입문자는 "이 게임으로도 시작할 수 있다"는 접근성을 보장하되, 게임 설계의 핵심 의사결정은 1차 타깃 기준으로 내린다.

### 3차 타깃: 상급 유저

고난이도 도전과 랭킹 경쟁을 원하는 유저. 기존 게임에 없는 차트 공간(홀드 중 탭, 수평 이동 등)이 동기 부여.

### 지역 타깃

한국 → 일본 → 글로벌 순. 다국어(ko/ja/en) 확정.

#### 4.1.3 상태 흐름

**구현된 흐름:**

```
타이틀 → [첫 기동] → 프리셋 설정 → 곡 선택
타이틀 → [이후 기동] → 곡 선택
곡 선택 → 로딩 → 플레이 → 결과 → 곡 선택
곡 선택 → 설정 → 곡 선택
```

일시정지(Escape): Resume / Retry(결과 없이 곡 재시작) / Quit(곡 선택 복귀, 기록 미저장).

**미구현 흐름:**

```
타이틀 → 로그인 → 타이틀
곡 선택 → 로그인 → 곡 선택
곡 선택 → [admin + Edit] → 차트 에디터 → 곡 선택
타이틀 → 스페셜 땡스 → 타이틀
곡 선택 → 옵저버 모드 → 곡 선택
설정 → 오프셋 캘리브레이션 → 설정
프리셋 설정 → 튜토리얼 → 곡 선택
```

## 5. 노트 시스템

### 5.1 노트 타입

모든 노트 타입은 **Lv.1부터 등장**. 난이도에 따라 변하는 것은 빈도와 복합도.

개념적으로 4종(싱글, 롱, 트릴, 더블)이며, 코드상 포인트 3종 + 구간 3종 = **6종**으로 구현:

| 노트 타입 | 코드명 | 메커니즘 | 요구 키 수 | 판정 | 형상 | 색상 |
|-----------|--------|----------|------------|------|------|------|
| **싱글** | single | 레인 내 아무 키 1개 | 1+ | 1회 | 직사각형 | #4488ff |
| **더블** | double | 서로 다른 키 **2개 동시** | 2+ | 독립 싱글 판정 × 2 | 직사각형 | #ffcc00 |
| **트릴** | trill | 직전 키와 **다른 키**. `trillZone` 내에서만 등장 | 2+ | 1회 (교대 실패 시 `goodTrill`) | 다이아몬드 | #ffffff |
| **싱글롱** | long | 키 누르기 → 유지 → 떼기. 시작점·바디·끝점 구조 | 1+ | 최대 2회 (헤드+릴리즈) | 직사각형 | #88bbff |
| **더블롱** | doubleLong | 2키 동시 홀드 | 2+ | 헤드+릴리즈 각각 더블 판정 | 직사각형 | #ffee88 |
| **트릴롱** | trillLong | `trillZone` 내 롱노트 | 2+ | 헤드+릴리즈 (교대 실패 시 `goodTrill`) | 다이아몬드 | #aaaaaa |

### 5.2 특수 메커니즘

| 메커니즘 | 설명 |
|----------|------|
| **홀드 교대** | 등록된 유지 키와 연결 경계의 유효 판정 창으로 교대. 이미 실패한 unit은 새 입력으로 부활하지 않음 |
| **끝점 판정** | 실제 release는 Perfect/Great/Good/Miss. `holdOnly`는 release를 면제하고 활성화된 바디의 유지로 Perfect/Miss. 일반 승계 성공에는 점수·콤보 없음 |
| **더블의 미처리 입력** | 창과 키 자격을 충족하면 앞 double의 남은 head가 먼저 입력을 소비. 같은 double head에서 이미 사용한 물리 키는 남은 head의 후보에서 제외 |
| **바디 구간 독립성** | `o-o-`의 각 바디 구간은 독립 판정 |
| **`trillZone`** | 시각적 예고 영역. 입력 불요구. 긴장도 유지·시각적 다양성 역할 |

### 5.3 피스 (노트 배치의 상호작용)

| 피스 | PLv. | 설명 |
|------|------|------|
| 짧은 트릴 | 1 | 트릴 노트가 2~4개만 등장하는 최소 `trillZone` |
| 릴리즈탭 | 4 | 롱노트 릴리즈 + 같은 레인 키 교대 |
| 싱글→더블 전환 | 4 | 싱글 노트 흐름이 더블 노트로 전환되는 배치 |
| 홀드 중 탭 | 7 | A키 홀드 유지 + B키로 싱글 노트 |

## 6. 난이도 체계

Lv.1~15, 5단계 등급.

| 등급 | 레벨 | 키 바인딩 | 핵심 경험 |
|------|------|-----------|-----------|
| **입문** | 1~3 | 4키 주로, 드물게 엄지 | 4레인 인식. 싱글 90%↑, 트릴·더블 극소량 |
| **초급** | 4~6 | 엄지 비중 상승 (6키) | `trillZone` 명확화, 릴리즈탭(PLv.4) 본격화 |
| **중급** | 7~10 | 8키 입문 (약지 추가) | 앵커 본격화, 홀드 중 탭(PLv.7) 등장 |
| **상급** | 11~13 | 8키 활성화 | 수평 이동·가변 분할 등장. 전 피스 고밀도 복합 결합 |
| **최상급** | 14~15 | 16키 완전 활용 | 새 피스 없이 극한 결합. 기존 4키 게임에 없는 차트 공간 |

**등급 간 전이 설계**: 온보딩 차트(새 피스 저밀도 도입), 역방향 동기 부여(키 추가 후 같은 곡 재시도), 난이도 표시(Lv. + 등급 명시).

## 7. 스코어링

아래는 [RFD 0020](rfd/0020-note-judgment-units-and-inheritance.md)의 채택 규칙이다. 구현 이행 상태는 [§12](#12-미정-사항)를 따른다.

| 항목 | 규격 |
|------|------|
| **달성률** | (획득 점수 / 차트 점수 항목의 이론 가중치 합) × 100%. 실시간 분모에는 지금까지 처리한 점수 항목의 가중치를 반영. 무점수 유지 Miss는 분모를 늘리지 않음 |
| **점수** | Perfect=3, Great=2, Good=1, `goodTrill`=1, Miss=0. Miss 자체의 별도 감점 없음 |
| **콤보 유지** | Perfect, Great, Good, `goodTrill` |
| **콤보 파괴** | Miss — 무점수 유지 실패도 포함 |
| **풀콤보** | Miss=0 (`goodTrill`은 영향 없음). 달성률 100%이면서 Full Combo가 아닌 결과 허용 |
| **랭크** | SSS(≥99.5%) / SS(≥99.0%) / S(≥97.0%) / AAA(≥95.0%) / AA(≥90.0%) / A(≥85.0%) / B(≥80.0%) / C(≥70.0%) / D(≥60.0%) / F(<60%) |
| **`flightRule`** | `altitude` 기반 클리어/실패 (Liftoff / Survival 2종). 약간의 내러티브(비행 콘셉트) 도입과 입문 유저 동기 부여가 목적. Liftoff는 숙련 유저 기준 사실상 실패하지 않게 관대하게 밸런싱하고 기본값으로 두며, 정확도 압박은 Survival이 전담. 실패 조건 없는 완주·학습은 옵저버 모드 담당. 초기의 "게이지 없음, 무조건 완주" 결정은 `docs/rfd/0001`~`0003`, `0005`로 대체됨 |

## 8. 키 바인딩

### 8.1 손배치 철학

**엄검중약**: 약지-중지-검지-엄지의 4손가락. 소지 배제(힘줄 간섭, 약한 근력, 자세 비틀림).

### 8.2 기본 프리셋 (16키)

기본 프리셋은 **16키**(레인당 4키)이다. 8키(레인당 2키)는 개념적 최소 바인딩이며, 실제 기본값은 아래 16키 구성이다.

| 레인 | TKL (기본) | Numpad |
|------|-----------|--------|
| 1 | Q, W, S, X (4키) | Q, W, S, X (4키) |
| 2 | E, D, C, O (4키) | E, D, C, PageDown (4키) |
| 3 | P, L, ,, R (4키) | Numpad7, Numpad4, Numpad1, R (4키) |
| 4 | [, ], ;, . (4키) | Numpad8, Numpad9, Numpad5, Numpad2 (4키) |

기본값: **TKL 배치** (게이밍 키보드 다수가 텐키리스).

### 8.3 키 규칙

- 레인당 2키 이상 바인딩 필수 (최소 8키). 기본 프리셋은 레인당 4키 (총 16키)
- 바인딩된 키는 시스템상 모두 동등. 주키/보조키는 유저의 운용 개념 — 기본 손 위치의 주키 4개와, 손 옮기기 등 특정 패턴에서만 쓰는 보조키로 나뉜다
- 16키 프리셋도 **동시 사용은 최대 8키 수준**. 패턴마다 유도되는 보조키가 달라져 차트 전체에서 최대 16키가 활용된다 (`docs/spec/keybinding.md`의 "주키와 보조키")
- 하나의 물리 키는 하나의 레인에만 바인딩 (충돌 불가)

## 11. 에셋 전략

### 왜 무료로 시작하는가

초기 자본이 없으므로 음원을 구매할 수 없다. 대신 동인(BMS) 작곡가들이 **비상업 목적 사용을 허가**한 곡을 활용하여 게임을 공개한다. 비상업 단계에서 재미를 검증하고 유저를 확보한 뒤, 수요가 확인되면 이미 커넥션이 형성된 작곡가들과 **상업 라이선스 계약으로 전환**한다. 비상업 단계의 협력 관계가 상업화 전환 비용을 낮추는 핵심 자산이다.

### 단계별 계획

| 단계 | 목표 곡수 | 에셋 수급 | 비용 |
|------|----------|-----------|------|
| **Phase A: 프로토타입** | 3~5곡 | 플레이스홀더(단순 도형), CC0 효과음, Noto Sans CJK | 0원 |
| **Phase B: 알파 (비영리 공개)** | 5~10곡 | 노트 타입별 디자인 자체 제작, BMS 작가 비상업 허가 교섭, Freesound 가공 | 0~30만원 |
| **Phase C: 베타** | 10곡+ | 최종 노트 스킨 커미션, 로고, 자켓 의뢰 | 10~100만원 |
| **Phase D: 상업화 (선택)** | — | 기존 BMS 작가와 상업 라이선스 계약 전환, CC-NC 곡 교체, 오리지널 곡 커미션, 법률 검토 | 별도 |

**음원 확보**: BMS 작가 비상업 허가(핵심), CC 라이선스 곡, Newgrounds/SoundCloud CC 필터, 자체 작곡, 작곡 콘테스트.

**라이선스 원칙**: 모든 외부 에셋 출처·조건 기록, CC-NC 에셋에 `non-commercial-only` 태그, BMS 작가 허가 서면 보존.

**근거 문서**: `docs/spec/project-assets.md`

### 2026-09-07 판정 모델 구현 검증 기록

- `npx vitest run`: 118개 파일, **1,859개 통과**. 사례 명세의 38개 ID 모두 대응 테스트가 존재한다.
- `npm run build`: TypeScript 검사와 production Vite build 통과.
- 변경한 `src/` 파일의 ESLint: 오류 0. 기존 `TutorialPreviewPlayer`의 Fast Refresh 경고 2개는 남아 있다. 새 E2E 파일은 기존 ESLint 설정 대상 밖이다. 저장소 전체 lint는 기존 다른 스코프의 오류와 `.claude/.worktrees` 스캔 문제 때문에 통과로 기록하지 않는다.
- `git diff --check`: 통과.
- Playwright 실행 제약 해소: 사용자가 권한을 변경하고 재시도를 요청한 뒤 로컬 Vite 서버와 Chromium 실행에 성공했다.
- 새 판정 브라우저 E2E **4개 통과**. `npx playwright test e2e/game/note-judgment.spec.ts e2e/game/manual-note-judgment.spec.ts --project=game --workers=1`의 3개와 `npx playwright test e2e/game/tutorial-note-judgment.spec.ts --project=game --workers=1`의 1개를 각각 검증했다.
  - 연결·`holdOnly` AutoPlayer 차트는 Perfect 3·Miss 0·100%·Full Combo이며 최대 콤보 통계를 표시하지 않는다. 재시작 후 전체 결과가 동일하고 이전 정산이 누적되지 않는다.
  - 브라우저 키보드 이벤트를 실제 `InputSystem → NoteJudgmentSession → 결과 화면` 경로로 전달하면 Perfect 2·Miss 0·100%이다. 테스트에서 입력 시각을 1000/2000ms로 제어했으며 물리 키보드의 체감 타이밍 검증을 대신하지 않는다.
  - 실제 튜토리얼 팝업에서 도식 확인 후 연결 예시를 반복 재생하고, 서로 다른 두 세션의 4000ms 마지막 release가 각각 한 번만 Perfect로 정산되는지 확인했다. 100%·Miss 0과 브라우저 page error 0도 확인했다.
- 브라우저에서 발견한 회귀 수정: `TutorialPreviewPlayer`가 루프 끝과 같은 시각의 입력을 처리하기 전에 세션을 초기화하여 마지막 release를 누락했다. 이제 이전 세션을 `loopMs`까지 진행한 뒤 새 반복을 시작한다. `tutorialPreviewSession.test.ts`에 3970 → 4000 → 0ms의 마지막 release·점수·초기화 검사를 추가했다.
- 기존 game/editor E2E는 전체 통과하지 않았다. game의 기존 19개 중 11개 통과·8개 실패: 설정 입력의 순서 기반 selector와 사라진 Placeholder Song/EASY fixture가 현재 화면과 맞지 않는다. editor는 필수 `songId`·`difficulty` 없이 `/editor`로 이동하여 `/game`으로 되돌아가는 공통 준비 단계에서 10개가 실패했다. 같은 원인 확인 후 통합 실행을 중단하여 그 실행의 나머지 25개는 실행하지 않았다. 해당 라우팅과 설정·곡 선택 화면은 이번 판정 변경 전부터 같은 동작이었다. editor 테스트 두 파일의 ESM `__dirname` 오류는 `import.meta.url` 기반 경로로 수정했지만 기존 시나리오 전반의 보수는 남아 있다.
- 시각 주입 통합 검사: ±100ms 입력 오프셋의 Good 경계, 늦은 프레임에서 입력을 기한보다 먼저 전달, 과거 timestamp의 raw 등급 보존과 확정 Miss 불가역, +200ms 오프셋과 AutoPlayer 병합, 같은 관측 묶음의 Miss 우선을 검증했다.
- 독립 성능 측정: 4ms 간격의 합법 `holdOnly` 연결 1,000개를 한 키로 유지하고 16ms마다 총 259회 진행했다. Perfect 1,000개·Miss 0개, 초기화 약 65ms, 판정 처리 p50 3.8ms / p95 6.5ms / 최대 8.8ms였다. 이 환경의 core 측정이며 GPU 렌더링이나 실제 브라우저 프레임률을 보장하는 결과는 아니다.

기존 `JudgmentEngine`·`tutorialPreviewJudgment`는 이전 동작의 호환 회귀용으로 표시하여 보존했다. 현재 PlayScreen·TutorialPreviewPlayer는 이 경로를 호출하지 않는다. 이번 검증에 추가 권한은 필요하지 않다. 배포·커밋·외부 데이터 변경은 수행하지 않았다.
